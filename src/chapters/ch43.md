# 第 43 章 Kafka 深入：副本、消费恢复与长期运维

第42章已经把Redis故障拆成派生数据、准入状态与数据库权威事实。本章继续检查Kafka链路中的成功条件：商品事务提交了，是否代表事件已经送达？生产者收到确认了，是否代表投影已经更新？消费组lag为0，是否代表所有权威商品都能在读模型中找到？

本章沿用现有商品事务、Outbox relay、事件Envelope、独立投影数据库与Inbox。先解释分区和副本，再在独立的三控制器、三broker实验中观察副本不足；随后复现数据库已提交但消费位点未提交的窗口、两个消费者重平衡、坏消息停机与历史位点越界。工程继续使用Rust1.92.0、rdkafka0.39.0及Kafka4.0.0的受测组合，不把Java客户端参数直接套给librdkafka。

## 43.1 先画出同一条事实的五个位置

### 43.1.1 【入门】五个位置各自回答不同问题

| 位置 | 保存什么 | 能证明什么 |
| --- | --- | --- |
| Catalog数据库 | 商品与同事务Outbox | 业务变更和待传播事件一起提交 |
| relay租约与交付记录 | 当前发送者、重试时间、交付标记 | 哪个事件仍待发送或已收到Kafka确认 |
| Kafka分区日志 | 按分区排列的消息 | broker接受并保留的日志位置 |
| 投影数据库与Inbox | 应用结果、事件身份与摘要 | 数据库内该事件的效果已提交 |
| 消费组位点 | 某分区下次应读取的位置 | 该组向Kafka报告的处理进度 |

这五处没有一个共同的跨系统事务。商品和Outbox可以共用一个PostgreSQL事务；投影和Inbox也可以共用另一个事务；Kafka确认与消费位点属于另外的协议。工程通过重试与幂等连接这些边界，而不是声称它们在同一瞬间全部成功。

### 43.1.2 【进阶】为什么仍保留Outbox与Inbox

如果先提交商品再直接发送Kafka，提交后进程退出会留下传播缺口。Outbox把待发送事实放进同一事务，使relay可以继续接手。relay发送成功但写交付标记前退出，则同一事件可能再次发送。

Inbox解决后一类重放的数据库副作用问题：同一event_id与相同摘要再次到达，只确认重复；同一ID却携带不同内容，拒绝处理。同一商品的revision还防止迟到的旧快照覆盖新快照。这些既有约束在本章继续保留。

### 43.1.3 【精通】链路健康不是单个绿色指标

Outbox排队、Kafka副本不足、消费组停滞、投影过旧可以分别发生。比如Kafka没有新消息时lag为0，而商品数据库里可能已经积压未交付Outbox；消费位点被人为移到末尾时lag也可能为0，但投影仍然缺行。

因此验收既查看位点，也在停止写入并排空传播链路后，对权威商品和读模型执行完整对账。第37章的`projection-audit --writers-stopped`仍是这个项目的业务证据之一。

## 43.2 分区、键与可见顺序

### 43.2.1 【入门】offset属于分区

`topic=A, partition=1, offset=9`表示A主题的分区1中的位置。另一个分区也有offset9，它们之间没有由这个数字提供的全局先后关系。消费组位点记录的是下次读取的位置，因此处理offset9以后通常提交10。

不要把offset当成商品revision。offset描述日志中的位置，revision描述单个商品在数据库中的业务版本；同一商品事件重复发送时，可以具有相同revision、相同event_id，却占据不同Kafka位置。

### 43.2.2 【进阶】当前项目以商品ID作为键

生产者将aggregate_id转换为字符串作为Kafka key。消费时还校验key与Envelope中的aggregate_id一致，防止错误路由的消息被当成合法商品事件。没有key或key不匹配都属于需要停下处理的契约错误。

同一个键在固定分区布局与分区器下通常落到同一分区。扩分区可能改变映射，新旧事件可能分布到不同分区；数据库revision判断因此仍有意义。它不是取消有序传播设计的理由，而是面对重放与迟到的额外保护。

### 43.2.3 【精通】可见消息的offset不保证逐个连续

事务控制记录、被中止的事务与日志清理都可能让应用观察到的offset存在间隔。不能仅因前一个可见消息是7、后一个是10，就断言丢了两条业务事件；也不能简单要求每次收到的offset等于数据库记下的位置加1。

本章检查的是已提交的下次读取位点是否仍位于保留范围内，而不是把每一个Kafka位置都假设成可见的商品事件。事务消费者还要区分日志末尾与最后稳定位置，后面会进一步讨论。

## 43.3 KRaft控制面与broker数据面

### 43.3.1 【入门】两种角色的职责

controller管理集群元数据与相关选举；broker保存分区数据并响应生产、消费请求。第40章单节点将两种角色放在一个进程中，便于读者启动，但同时也把故障域合在一起。

本章实验将三controller与三broker分成六个进程。这样停掉两个broker时，三个controller仍可维持仲裁，实验才有条件观察“控制面仍在、数据副本不足”的情况，而不会把两种故障混为一谈。

### 43.3.2 【进阶】监听地址和广播地址必须从客户端看

LISTENERS决定进程在哪个地址接收连接，ADVERTISED_LISTENERS告诉客户端后续应连接哪里。bootstrap地址只负责第一次找到集群；它能连接并不代表元数据里返回的每个broker地址都能从该客户端访问。

实验客户端运行在同一个私有Docker网络，broker广播b1、b2、b3各自的服务名。它们没有宿主机端口；宿主程序直接使用b1:9092不会自动得到容器DNS。本章不会靠在宿主机临时改hosts来掩盖命名空间问题。

### 43.3.3 【精通】六个容器仍属于一台机器

六进程布局可以演示协议中的独立角色和进程故障，却不能证明跨机架、跨可用区或宿主断电的高可用。磁盘、内核、宿主网络与Docker引擎仍是共同依赖。

生产规划还要分离故障域、评估网络时延和磁盘吞吐，并建立元数据、访问策略及升级恢复流程。本章只把本地已测边界写清楚，不把容器数直接换算成生产可靠性。

## 43.4 RF、ISR、acks和确认边界

### 43.4.1 【入门】三个数字不要混用

| 项目 | 含义 | 本章多副本实验 |
| --- | --- | --- |
| replication factor | 配置了多少个副本 | 3 |
| ISR数量 | 当前在同步副本集合中的成员数 | 正常3，故障时可能1 |
| min.insync.replicas | acks=all写入所需的最少同步副本数 | 2 |

副本因子3不表示任何时刻都有3个同步副本。配置min ISR为2后，当同步集合不足2，写入可以被拒绝；这是降低保护水平时拒绝继续接受写入的策略，不是relay应忽略的错误。

### 43.4.2 【进阶】acks=all并不是永远只等待min ISR个副本

当ISR有3个成员时，acks=all依照当前同步副本集合完成确认；min ISR=2是可接受写入的门槛，不能据此声称第三个同步副本永远不影响确认延迟。副本跟不上时，集合变化和超时会影响结果。

第40章RF1的单节点即使设置acks=all，也没有额外数据副本。新实验使用RF3与min ISR2来观察一类受控故障，但原主Compose仍是单节点开发入口，不会因为增加了实验文件而自动升级。[Kafka4主题配置](https://kafka.apache.org/40/configuration/topic-level-configs/)

### 43.4.3 【精通】确认不等于每条记录都做独立磁盘刷盘

确认策略、日志复制、操作系统页面缓存与磁盘持久化属于不同层次。多副本可以在约定故障模型下保护已确认记录，但把同一宿主上的多个进程一起失去电源，与只停止一个broker并不是同一个实验。

因此报告会写明停止的是哪些进程、controller仲裁是否仍存在、ISR变成多少、发送方观察到什么，以及恢复后读到了哪些事实。不能只展示一次生产者返回成功，就推导断电不丢数据。

## 43.5 生产者幂等与业务事件身份

### 43.5.1 【入门】当前运行配置
```rust
use crate::event::Envelope;
use anyhow::Context;
use rdkafka::{
    ClientConfig, Message, Offset, TopicPartitionList,
    consumer::{CommitMode, Consumer, ConsumerContext, DefaultConsumerContext, StreamConsumer},
    producer::{FutureProducer, FutureRecord},
};
use std::{sync::Arc, time::Duration};

pub fn producer(brokers: &str) -> anyhow::Result<FutureProducer> {
    Ok(ClientConfig::new()
        .set("bootstrap.servers", brokers)
        .set("enable.idempotence", "true")
        .set("acks", "all")
        .set("delivery.timeout.ms", "5000")
        .set("request.timeout.ms", "3000")
        .set("linger.ms", "5")
        .set("queue.buffering.max.kbytes", "10240")
        .create()?)
}
pub async fn send(producer: &FutureProducer, topic: &str, event: &Envelope) -> anyhow::Result<()> {
    let payload = event.encode()?;
    let key = event.aggregate_id.to_string();
    tokio::time::timeout(
        Duration::from_secs(8),
        producer.send(
            FutureRecord::to(topic).key(&key).payload(&payload),
            Duration::from_millis(250),
        ),
    )
    .await
    .context("producer await budget exhausted; delivery may still happen")?
    .map_err(|(error, _)| anyhow::anyhow!("Kafka delivery failed: {error}"))?;
    Ok(())
}
pub fn consumer(brokers: &str, group: &str, topic: &str) -> anyhow::Result<Arc<StreamConsumer>> {
    let consumer: StreamConsumer = ClientConfig::new()
        .set("bootstrap.servers", brokers)
        .set("group.id", group)
        .set("enable.auto.commit", "false")
        .set("enable.auto.offset.store", "false")
        .set("auto.offset.reset", "earliest")
        .set("isolation.level", "read_committed")
        .set("max.poll.interval.ms", "30000")
        .set("session.timeout.ms", "10000")
        .set("socket.timeout.ms", "3000")
        .create()?;
    consumer.subscribe(&[topic])?;
    Ok(Arc::new(consumer))
}
pub fn decode_message(message: &impl Message) -> anyhow::Result<Envelope> {
    let event = Envelope::decode(message.payload().context("empty Kafka payload")?)?;
    let key = std::str::from_utf8(message.key().context("missing aggregate key")?)?;
    anyhow::ensure!(
        key == event.aggregate_id.to_string(),
        "Kafka key does not match event aggregate"
    );
    Ok(event)
}
/// Called only after a processed position is synchronously acknowledged by Kafka.
/// A rebalance alone must not retire an empty partition's validated zero bootstrap.
pub trait CommitProgress: ConsumerContext {
    fn processed_commit(&self, _topic: &str, _partition: i32) {}
}
impl CommitProgress for DefaultConsumerContext {}

pub async fn commit_processed<C: CommitProgress + 'static>(
    consumer: Arc<StreamConsumer<C>>,
    topic: String,
    partition: i32,
    offset: i64,
) -> anyhow::Result<()> {
    let mut positions = TopicPartitionList::new();
    positions.add_partition_offset(
        &topic,
        partition,
        Offset::Offset(offset.checked_add(1).context("offset overflow")?),
    )?;
    tokio::time::timeout(
        Duration::from_secs(5),
        tokio::task::spawn_blocking(move || {
            consumer.commit(&positions, CommitMode::Sync)?;
            consumer.context().processed_commit(&topic, partition);
            Ok::<_, rdkafka::error::KafkaError>(())
        }),
    )
    .await
    .context("offset commit wait budget exhausted")???;
    Ok(())
}
```

生产者启用幂等与acks=all，交付时限5秒，外层等待8秒。入队等待与已经入队后的交付不是同一阶段；错误或超时可能产生“没有确认，但服务端已经接受”的不确定窗口。

### 43.5.2 【进阶】为什么同一event_id仍可能出现两次

生产者幂等用于约束其协议会话中的重试，不知道PostgreSQL里哪个Outbox已经写过交付标记。relay重启后重发一个旧业务事件，或调用方因不确定结果重新发起应用层send，都不能仅凭这个配置推导没有第二条记录。

因此Outbox重试保留原event_id，Inbox继续按event_id与摘要去重。本书的保证是数据库内效果可安全重放，不是Kafka日志里永远只有一条同ID记录，更不是跨PostgreSQL和Kafka天然具有统一事务。

### 43.5.3 【精通】处理发送结果不确定

relay收到明确确认后尝试写交付标记，写标记时仍要验证租约token。发送失败则保存重试状态，不能删除Outbox。旧进程迟到写标记而租约所有者已经变化时，条件更新拒绝它。

外层等待结束不保证librdkafka内部请求也在同一时刻被撤销。安全处理是保留原事件身份并允许重放，不是生成一个新ID把不确定结果当成全新事件。

## 43.6 消费位点与数据库提交顺序

### 43.6.1 【入门】先提交数据库，再提交下次读取位置

当前投影逐条处理：校验消息，事务内写Inbox与读模型，提交数据库，然后同步提交该分区的offset+1。自动提交与自动位点存储均关闭，避免取到消息便被当成处理完成。

如果先提交位点再更新数据库，进程中断会使Kafka认为已经完成，而读模型还没更新。先提交数据库的代价是故障时可能重放；Inbox负责让这类重放安全。

### 43.6.2 【进阶】没有消息的分区可能没有已提交位点

某分区的日志末尾为0，表示尚无可读记录；当前组没有提交位点是合理状态。Kafka工具可能显示CURRENT-OFFSET为短横线，而不是0。验收不能要求所有空分区都人为写一个位点。

本章第一轮实验已将三个商品投影成功，却因检查器把空分区的无位点当作未追平而超时。修复的是验收判断：末尾0且无提交可以视为当前无待处理记录；非空分区缺失位点仍不能这样处理。原失败报告保留，没有计入整链通过。

### 43.6.3 【精通】提交等待超时也可能已经成功

同步commit被放进阻塞任务，外层等待有5秒上限。停止等待不保证阻塞调用立即停止；它随后可能成功，也可能因重平衡而失败。进程应报告并停止当前处理循环，恢复以后按实际位点和Inbox接续。

不能在超时后直接提交更大的位置“修一下”，也不能假设前一条没有应用而绕过Inbox再做副作用。

## 43.7 为什么持久投影不能无条件回到earliest

### 43.7.1 【入门】earliest表示现存最早，不表示世界的第一条

假设某组下次应读10，但保留策略已将起点推进到50。自动回到earliest会从50继续，10到49之间的缺口不会因此恢复。更换新group.id也不能把已删除的日志找回来。

原演示`consume-once`仍保留earliest，适合第27章观察新组消费；当前持久`projection-worker`则采用新严格策略。不同入口的目标要区分，不能把演示的便利设置当作生产恢复规则。[Kafka消费者起点语义](https://kafka.apache.org/40/configuration/consumer-configs/)

### 43.7.2 【进阶】启动时检查每个分区

严格消费者在订阅前读取主题元数据、该组已提交位点和每个分区的low、high。low是当前保留起点，high是日志末尾的下一位置；已有next必须位于闭区间low到high中，next等于high表示暂时没有新记录。

无已提交位点时，本项目仅允许low为0，在首次成功提交处理位点之前，显式分配到0。low大于0时需要受控基线与恢复流程，不直接从剩余日志拼凑一个貌似完整的投影。启动查询有总预算，失败不会被解释成“没有位点”。冷启动中协调器暂时NotCoordinator、尚在加载或运输超时会在同一总预算内重试；权限拒绝与语义缺口直接失败，不无限重试，也不退成earliest。

### 43.7.3 【进阶】运行中也不能悄悄重置

librdkafka的配置值是`auto.offset.reset=error`，不要照搬Java客户端的`none`字符串，参见与当前绑定版本一致的[librdkafka配置](https://github.com/confluentinc/librdkafka/blob/v2.12.1/CONFIGURATION.md)。这样即使启动检查以后日志继续清理，读取越界也会成为错误，而不会自动跳到另一个位置。

启动检查无法代替权限、配置与完整业务对账。人为把位点调到仍在范围内的错误位置，或用不合适的清理策略删除语义上必需的记录，未必表现为数值越界；因此该检查只是阻断一类可识别缺口，不是重建完整性的充分证明。

### 43.7.4 【精通】新组与首次分配之间的竞争

启动预检与真正分配不是同一个原子步骤。如果预检确认新分区可从0开始，回调仍必须显式请求0，而不能在等待分配时再次按earliest计算一个更晚的起点。若0此时已被清理，运行配置将报错。

这份起点许可保留到该进程确认过一次真正处理位点的同步提交。空分区可能经历多次分配而始终没有提交，不能仅因第一次分配就撤销许可；否则普通重平衡会被误判为恢复缺口。首次成功提交后撤销许可，后续分配使用已提交位置。若另一成员在此期间已向前消费，可能出现保守重放，Inbox负责去重，不能为了省重放而允许跳过未证明完成的记录。

## 43.8 严格消费者的完整实现

### 43.8.1 【进阶】校验逻辑与有界启动
```rust
//! Never turn expired/missing historical offsets into a silent successful rebuild.
//! Zero bootstrap remains valid until a real processed offset is acknowledged.
use anyhow::{Context, ensure};
use rdkafka::{
    ClientConfig, Offset, TopicPartitionList,
    client::ClientContext,
    consumer::{BaseConsumer, Consumer, ConsumerContext, StreamConsumer},
    error::{KafkaError, RDKafkaErrorCode},
    message::BorrowedMessage,
    types::RDKafkaRespErr,
};
use std::{
    collections::HashSet,
    sync::{Arc, Mutex},
    time::{Duration, Instant},
};

#[derive(Default)]
pub struct StrictContext {
    initial_zero: Mutex<HashSet<(String, i32)>>,
    fatal: Mutex<Option<String>>,
}
impl ClientContext for StrictContext {}
impl crate::kafka::CommitProgress for StrictContext {
    fn processed_commit(&self, topic: &str, partition: i32) {
        self.initial_zero
            .lock()
            .unwrap()
            .remove(&(topic.to_owned(), partition));
    }
}

impl ConsumerContext for StrictContext {
    fn rebalance(
        &self,
        consumer: &BaseConsumer<Self>,
        error: RDKafkaRespErr,
        list: &mut TopicPartitionList,
    ) {
        // Explicit eager range assignment: do not reuse this callback for cooperative protocols.
        let result = match error {
            RDKafkaRespErr::RD_KAFKA_RESP_ERR__ASSIGN_PARTITIONS => {
                let zero = self.initial_zero.lock().unwrap();
                let selected: Vec<_> = list
                    .elements()
                    .into_iter()
                    .map(|p| (p.topic().to_owned(), p.partition()))
                    .filter(|key| zero.contains(key))
                    .collect();
                for (topic, partition) in selected {
                    if let Err(error) =
                        list.set_partition_offset(&topic, partition, Offset::Offset(0))
                    {
                        *self.fatal.lock().unwrap() = Some(error.to_string());
                        return;
                    }
                }
                tracing::info!(
                    partitions = list.count(),
                    "durable consumer assigned eager partitions"
                );
                consumer.assign(list)
            }
            RDKafkaRespErr::RD_KAFKA_RESP_ERR__REVOKE_PARTITIONS => {
                tracing::info!(
                    partitions = list.count(),
                    "durable consumer revoked eager partitions"
                );
                consumer.unassign()
            }
            _ => {
                *self.fatal.lock().unwrap() = Some(format!("rebalance failed: {error:?}"));
                consumer.unassign()
            }
        };
        if let Err(error) = result {
            *self.fatal.lock().unwrap() = Some(error.to_string());
        }
    }
}
pub type DurableConsumer = Arc<StreamConsumer<StrictContext>>;

/// Validate one partition without assuming that every visible message has a contiguous offset.
/// Transactions/control records can create visible gaps even when retention has removed nothing.
pub fn validate_start(low: i64, high: i64, committed: Offset) -> anyhow::Result<Option<i64>> {
    ensure!(low >= 0 && high >= low, "invalid Kafka watermark range");
    match committed {
        Offset::Invalid => {
            ensure!(
                low == 0,
                "new group has no baseline and retained history starts after zero"
            );
            Ok(Some(0))
        }
        Offset::Offset(next) => {
            ensure!(
                (low..=high).contains(&next),
                "committed offset is outside retained history; explicit recovery required"
            );
            Ok(None)
        }
        _ => anyhow::bail!("unexpected stored offset kind"),
    }
}
fn remaining(deadline: Instant) -> anyhow::Result<Duration> {
    let left = deadline.saturating_duration_since(Instant::now());
    ensure!(!left.is_zero(), "Kafka startup validation budget exhausted");
    Ok(left.min(Duration::from_secs(1)))
}
/// Retry transport/coordinator transitions, never authorization or semantic gaps.
fn startup_query<T>(
    deadline: Instant,
    mut query: impl FnMut(Duration) -> Result<T, KafkaError>,
) -> anyhow::Result<T> {
    loop {
        match query(remaining(deadline)?) {
            Ok(value) => return Ok(value),
            Err(error)
                if matches!(
                    error.rdkafka_error_code(),
                    Some(
                        RDKafkaErrorCode::NotCoordinator
                            | RDKafkaErrorCode::CoordinatorLoadInProgress
                            | RDKafkaErrorCode::CoordinatorNotAvailable
                            | RDKafkaErrorCode::WaitingForCoordinator
                            | RDKafkaErrorCode::BrokerTransportFailure
                            | RDKafkaErrorCode::AllBrokersDown
                            | RDKafkaErrorCode::OperationTimedOut
                            | RDKafkaErrorCode::TimedOutQueue
                            | RDKafkaErrorCode::RequestTimedOut
                            | RDKafkaErrorCode::LeaderNotAvailable
                            | RDKafkaErrorCode::NotLeaderForPartition
                    )
                ) =>
            {
                let pause = remaining(deadline)?.min(Duration::from_millis(50));
                std::thread::sleep(pause);
            }
            Err(error) => return Err(error.into()),
        }
    }
}
/// Blocking startup preflight: call on spawn_blocking, before subscribing.
pub fn create(brokers: &str, group: &str, topic: &str) -> anyhow::Result<DurableConsumer> {
    ensure!(
        !group.trim().is_empty() && !topic.trim().is_empty(),
        "group/topic required"
    );
    let consumer: StreamConsumer<StrictContext> = ClientConfig::new()
        .set("bootstrap.servers", brokers)
        .set("group.id", group)
        .set("enable.auto.commit", "false")
        .set("enable.auto.offset.store", "false")
        .set("auto.offset.reset", "error")
        .set("allow.auto.create.topics", "false")
        .set("isolation.level", "read_committed")
        .set("partition.assignment.strategy", "range")
        .set("max.poll.interval.ms", "30000")
        .set("session.timeout.ms", "10000")
        .set("socket.timeout.ms", "3000")
        .create_with_context(StrictContext::default())?;
    let deadline = Instant::now() + Duration::from_secs(5);
    let metadata = startup_query(deadline, |limit| {
        consumer.fetch_metadata(Some(topic), limit)
    })?;
    let topic_meta = metadata
        .topics()
        .iter()
        .find(|t| t.name() == topic)
        .context("topic absent")?;
    ensure!(topic_meta.error().is_none(), "topic metadata error");
    ensure!(
        !topic_meta.partitions().is_empty() && topic_meta.partitions().len() <= 64,
        "expected1..64 partitions for bounded startup audit"
    );
    let mut requested = TopicPartitionList::new();
    for partition in topic_meta.partitions() {
        ensure!(partition.error().is_none(), "partition metadata error");
        requested.add_partition(topic, partition.id());
    }
    let offsets = startup_query(deadline, |limit| {
        consumer.committed_offsets(requested.clone(), limit)
    })?;
    for partition in offsets.elements() {
        partition.error()?;
        let (low, high) = startup_query(deadline, |limit| {
            consumer.fetch_watermarks(topic, partition.partition(), limit)
        })?;
        let start = validate_start(low, high, partition.offset()).with_context(|| {
            format!(
                "topic={topic} partition={} low={low} high={high}",
                partition.partition()
            )
        })?;
        if start == Some(0) {
            consumer
                .context()
                .initial_zero
                .lock()
                .unwrap()
                .insert((topic.to_owned(), partition.partition()));
        }
    }
    consumer.subscribe(&[topic])?;
    Ok(Arc::new(consumer))
}
/// Rebalance assignment failures must wake the worker rather than leave it silently idle.
pub async fn recv(consumer: &DurableConsumer) -> anyhow::Result<BorrowedMessage<'_>> {
    loop {
        if let Some(error) = consumer.context().fatal.lock().unwrap().clone() {
            anyhow::bail!("durable consumer stopped: {error}");
        }
        match tokio::time::timeout(Duration::from_secs(1), consumer.recv()).await {
            Ok(result) => return Ok(result?),
            Err(_) => continue,
        }
    }
}
```

### 43.8.2 【精通】回调只做短小的分配工作

本实现显式选择eager range分配策略。回调从已经预检且尚未成功提交的集合中读取起点，修改分配列表，再调用assign；撤销时unassign。它不在回调里查询数据库或等待远端网络。

不能把配置改成cooperative分配后继续沿用完整assign/unassign逻辑。合作式协议需要增量分配与撤销规则；本实现没有声称支持该切换。分配失败被记录为fatal，受检recv周期性观察并结束进程，避免错误后永久静默空转。

```rust
            .with_context(|| format!("projection rejected: {location}; no offset commit"))?;

                .await
                .with_context(|| format!("database committed, offset commit failed: {location}"))?;
```

## 43.9 重平衡与正在处理的消息

### 43.9.1 【入门】消费者数量不是任意并行度

三个分区由同一个组的两个正常成员分摊时，通常有成员持有两个分区、另一个持有一个。成员数量超过分区数，新增实例未必获得工作；单个热点商品也不会因为多启动十个消费者就自动拆到十个分区。

独立投影与重建投影使用不同组和不同物理数据库；同组多个成员则共享同一逻辑投影身份。混淆这两种扩容会造成不同的重放与数据所有权问题。

### 43.9.2 【进阶】分配撤销不回滚已经提交的数据库事务

旧成员可能已提交数据库、尚未成功提交位点，就失去了分区。新成员从已提交位点读取同一事件，Inbox再次确认重复。即使旧成员迟到的数据库事务与新成员重叠，事件身份、摘要和revision规则仍要成立。

当前实现每个成员一次只处理一条消息，没有加入跨分区并发批量流水线。若未来并行处理，必须为每个分区维护连续完成的提交水位，不能看见较大offset完成就越过前面尚未完成的记录。

### 43.9.3 【精通】处理超时不能靠无限增大poll间隔掩盖

当前max.poll.interval为30秒，数据库应用和位点提交分别有边界。出现重平衡频繁时，应检查数据库等待、broker协调器、网络与回调耗时，确认是否超过处理预算。

把poll间隔无限增大会延迟检测失效成员；把会话时间无限减小则可能放大短暂停顿导致的反复分配。参数应根据实际最坏处理时间和恢复目标选择，并用故障实验验证。

## 43.10 当前契约的兼容边界

### 43.10.1 【入门】schema_version与revision分别负责什么

schema_version选择消息结构协议，revision表示商品的业务版本。当前只接受schema_version1和kind为product.snapshot.v1；事件ID不能为nil，aggregate_id必须正数并与payload.id一致，名称与金额库存还要通过领域规则。

JSON能解析不表示语义相同。价格单位、listed含义或revision生成方式改变，都可能破坏应用结果，即使字段名没有变化。

### 43.10.2 【进阶】本工程明确拒绝未知字段

Envelope与Snapshot都使用serde的deny_unknown_fields。因此给JSON增加一个字段，并不能在本工程中自动被旧消费者忽略；旧稿中“新增可选字段通常可忽略”的泛化不能直接套到现有契约。

配套固定历史样本保留Unicode名称、以分为单位的金额与listed=false状态；回归还明确验证新增顶层字段、嵌套字段都会被当前消费者拒绝。它不是新旧两代消费者的滚动升级实测。

契约演进需要同时考虑生产者、旧消费者、历史记录与摘要规则。若修改解析器来接受未知字段，还要回答摘要是否包含原始字段、同ID不同载荷如何判断，不能为了滚动发布临时绕开摘要冲突保护。

### 43.10.3 【精通】本书删除事件不是Kafka空值墓碑

当前商品下架仍发送完整Snapshot，并把listed设为false。它是业务删除状态的快照；Kafka压缩主题里key对应的null value则具有日志清理墓碑语义，两者不能混写为同一种记录。

当前主题使用cleanup.policy=delete，没有在本章悄悄切到compaction。投影保留下架行来抵御迟到旧事件；恢复时也要保留这类事实，不能只导出仍上架的商品。
## 43.11 保留、压缩与从头重建

### 43.11.1 【入门】保留期不是消费完成的承诺

当前快照主题按时间保留7天。消息被删除不等待每一个消费组都追平；组长时间停机以后，旧位点可能不再有效。增加保留时间会增加磁盘需求，也不能代替备份与基线设计。

删除以日志段和后台清理规则执行，不是每条消息恰好到第七天就立即消失。容量规划需要同时考虑写入速率、保留时间、副本数、段文件和额外空间；不能把一个主题的逻辑字节数当作整个集群所需磁盘。

### 43.11.2 【进阶】compaction保留的是按键清理后的日志

压缩适合某些“恢复每个键的最新状态”场景，但清理异步进行，不能假设日志里立刻只剩每键一条记录。空值墓碑还有自己的保留语义，长时间离线的消费者可能错过删除事实。

本工程下架快照是非空JSON，并非Kafka空值墓碑；如果未来切换主题策略，需要检查业务删除、晚到旧revision、事件ID去重和新组基线是否仍成立，不能只改cleanup.policy后宣称恢复问题更简单了。

### 43.11.3 【精通】日志起点为0也不是完整性的充分证明

严格启动检查拒绝明显越界，但不能发现所有语义缺口。错误的主题策略、手动移动仍在范围内的组位点、发错主题或错误的历史事件，都可能不造成low大于next。

需要受控基线时，应从权威数据库导出包含所有商品、revision和下架状态的完整状态，明确停止写入或一致快照的边界，再确定后续事件的接续位置。新投影使用独立数据库与身份，最终完整对账，再考虑切换。不能把两个不同系统各自“差不多同一时刻”的查询当成原子切面。

## 43.13 故障实验分别证明什么

### 43.13.1 【入门】正常传播与位点观察

实验先用实际store事务创建三个商品，启动实际relay，观察Outbox排空，再由严格投影处理。数据库行、Inbox与消费组位点一起核对，而不是只运行console consumer看到一行JSON就结束。

空分区末尾为0时允许没有组提交记录。检查器只对该情况作等价判断，非空分区仍必须达到明确的末尾位置。

### 43.13.2 【进阶】数据副本不足而控制面仍可用

实验停止b2、b3，等待每个业务分区的leader与ISR都只剩b1，再用元数据仲裁工具确认controller leader仍存在。新创建的商品事务仍可提交，但relay因保护不足无法确认交付，原event_id保留在未交付Outbox中，并记录尝试与重试时间。

恢复两个broker、等待它们重新进入ISR以后，relay以同一事件身份完成交付，读模型随后追平。不能在实验中途把min ISR改成1来取得绿色结果，否则验证的已经是另一种持久性策略。

### 43.13.3 【进阶】数据库先提交但没有位点提交

停止正式worker，发布一个新商品事件，再用实验工具完成数据库应用后直接退出。检查该event_id已在Inbox中，但Kafka组位点仍与之前相同；重新启动生产worker，它再次读取该事件，数据库确认Duplicate，随后提交下次读取位置。

最终商品与Inbox数量都没有多出第二份事实。这个结果依赖事件ID和摘要约束，并非依赖消费者恰好只收到一次。

### 43.13.4 【精通】两成员重平衡必须覆盖空分区

两个成员分摊三个分区，再停止一个成员，要求剩余成员接管三个分区，并继续应用后续事件。仅验证两个进程都存活不够；还要查看实际分配与最后的数据库对账。

第二轮真实实验发现：空分区尚未提交任何位点，第一次assign却过早撤销了从0开始的许可，下一次分配便报AutoOffsetReset。最终实现把许可撤销放到真正的同步提交确认后，而不是把配置退回earliest。这个修复保留严格恢复目标，也允许正常空分区重平衡。

### 43.13.5 【精通】坏消息不应被悄悄跳过

独立毒消息主题先写入一个无效载荷，再写入合法事件。生产投影应在offset0退出，Inbox仍为空，组位点没有越过该记录。日志保留主题、分区、offset和错误分类，不能泄露载荷哨兵。

本工程选择停下定位问题，没有实现自动DLQ与跳过。若未来加入隔离队列，需要定义隔离记录的可靠保存、原位点提交、授权修复与重放责任；一次console producer发送成功不能证明这套协议已经实现。

### 43.13.6 【精通】用受控删除制造保留缺口

实验在另一个专用主题写入两个记录，建立已提交位点0，然后调用DeleteRecords把保留起点推进到2。这是为了确定地产生与保留清理同类的位点缺口，不是等待自然七天到期的测量，也不演示手工删除broker日志文件。

已有组的next0应被严格预检拒绝；一个没有位点的新组也应因low2而拒绝。检查结束后原组提交值仍为0，证明程序没有替操作者静默修改恢复边界。

| --- | --- | --- |
| 生产传播 | Outbox待交付数、最老年龄、尝试次数、采样时间 | 采样失败不能把旧值清零当恢复 |
| broker | leader/ISR、欠复制与离线分区、磁盘、请求错误 | RF配置正常不代表当前ISR足够 |
| 消费组 | 各分区提交位置、日志起点/末尾、成员分配 | 空位点与0不同，改组名会改变观察对象 |
| 业务投影 | 最近应用时间、权威对账结果、缺行与错误revision | 最近成功一次不代表全部商品均已追平 |

第38章已有Outbox和投影应用时间指标，本章没有假装已经部署完整broker指标采集器。生产还需要按所选发行版和安全策略接入broker/JVM与磁盘监控，并校验抓取权限。[Kafka4监控指标](https://kafka.apache.org/40/operations/monitoring/)

### 43.14.2 【进阶】high、稳定位置与事务可见性

read_committed会避开已中止事务中的记录；未结束事务也可能阻止其后记录成为当前可见数据。命令行显示的日志末尾、可读取的稳定边界、消费者已提交位置，不一定是同一个数。

本章实验没有开启Kafka事务生产，因此追平断言可以直接对比该组提交与日志末尾。不能把这条简化验收原样用于存在长事务的主题，再把任何差值都解释为消费处理慢。[Kafka设计](https://kafka.apache.org/40/design/design/)

### 43.14.3 【进阶】积压恢复先估计追赶速度

设平时每秒新增a条事件、恢复后消费者稳定处理b条，只有b大于a时积压才可能持续下降。积压N条的粗略追赶时间为N除以b-a；这还没有计入数据库竞争、重平衡、热点分区、网络和未来流量变化。

例如新增100条/秒、可处理150条/秒，五万条积压的理想净追赶时间约1000秒。若只按150条/秒估算，会低估持续写入的影响。实际还要确认最慢分区不会在追平前超过保留边界。

### 43.14.4 【精通】磁盘和分区调整都需要计划

磁盘紧张时先分析写入、保留、副本和重分配工作量，不能直接删除数据目录中文件。重分配本身会产生网络和磁盘负载，应设定节流、观察ISR并保留回退计划。

增加分区会影响key映射，且不能按同样方式随意缩回。变更前明确消费者并发、热点和恢复目标，保留真实基准，而不是看到lag就反复加分区或重置位点。

## 43.15 诊断顺序与分层练习

### 43.15.1 【入门】先回答是哪一段没有推进

| 症状 | 应核对 | 避免的动作 |
| --- | --- | --- |
| 商品已提交、投影没更新 | Outbox是否存在、是否仍待交付 | 直接重建整个数据库 |
| relay反复失败 | broker可达、ISR、min ISR、发送时限 | 删除Outbox或生成新ID重发 |
| consumer启动即退出 | topic/partition、low/high、原提交位点与错误链 | 无条件改成latest |
| 两实例却只有一实例有工作 | 分区数、实际成员与分配、重平衡日志 | 只看容器数量 |
| lag0但读模型缺商品 | 是否换组、是否移动位点、Outbox与完整对账 | 宣布业务已恢复 |
| 毒消息停住 | 可定位位置、契约版本、隔离与修复记录 | 记录原始载荷到公共日志 |

### 43.15.2 【入门】解释RF3与min ISR2

问题：正常ISR有三个成员时，为什么不能把acks=all解释成“永远只等任意两个”？只剩一个同步副本时该怎样处理Outbox？

答案：min ISR约束最少可接受保护水平，确认仍与实际ISR及复制过程有关。只剩一个时，本章策略拒绝写入；relay保留同ID事件并重试，而不是降低门槛或标为已交付。

### 43.15.3 【进阶】判断三个起点

问题：low50/high100时next49、next50、next100分别如何处理？没有提交位点的新组呢？

答案：49已经越过保留边界，需要显式恢复；50和100都在有效范围，100表示当前末尾。新组没有基线且low大于0，严格预检拒绝；改group.id不会恢复丢失的历史。

### 43.15.4 【进阶】解释空分区重平衡

问题：low0/high0且没有提交位点，分区经历两次分配后仍没有收到消息，应当报错还是继续等待？什么时候撤销从0开始的许可？

答案：保留从0开始的预检许可，重新分配时仍显式请求0。只有确认过一次真实处理位点的同步提交，才撤销该许可；若0在此期间已经不可读，读取失败而不自动跳过。

### 43.15.5 【精通】设计不会跳过副作用的并发消费

问题：某分区的消息10、11、12并发处理，12先完成，能否立即提交13？

答案：不能。位点13意味着之前都已处理完成；需要按分区追踪连续完成水位，等待10和11成功后再推进。还要设计撤销期间等待、取消、迟到数据库事务与提交失败的处理。本章逐条实现没有假装已经提供该并行协议。

### 43.15.6 【精通】从本章接续Linux与网络

故障实验依赖进程、网络命名空间、DNS、磁盘与时间预算。下一章将继续同一个工程，检查Linux运行环境、连接、TLS与性能诊断，把“服务不可达”拆成可以逐步验证的层次。Kafka副本语义不会替代安全传输、证书轮换或操作系统容量设计。

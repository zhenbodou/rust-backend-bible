# 第 32 章 库存调整：补货、盘亏与幂等收据

第30章建立预留状态机，也禁止普通商品更新覆盖库存；第31章让可信调用方通过RPC操作同一事务。现在有一个实际需求尚未解决：管理员收到一批新货，或者仓库确认盘亏，怎样改变可售量，并说明是谁基于什么凭据做了这次改变？

本章在原商品数据库内增加库存调整模块、持久化收据、查询与受控本地CLI。新增一次迁移，继续复用商品revision和Outbox。不会再造一套商城或库存表；也不会把已修好的商品资料编辑整个关闭。普通商品PUT仍能修改名称和价格，但不能替代库存命令。

学完应能区分绝对覆盖与业务增量，解释增量为什么仍会重复执行，推导所有Held释放时的数值边界，并从数据库收据恢复一次回复丢失的调整。完整公网管理员接口、审批与仓储账本将有各自的边界；本章CLI供隔离实验与受控管理使用。

## 32.1 从“把库存改成十”拆出业务含义

### 32.1.1 【入门】旧页面为什么不能决定库存

管理员打开商品页面，看见可售量10。订单随后预留2，数据库可售量变为8。管理员只改名称，却把旧页面上的stock=10一起提交；如果后台照单全收，释放原预留后就会得到12。

行锁使SQL依次执行，却不知道页面上的10来自过期观察。第30章已在商品存储层锁行后比较stock：若请求想替换实际库存，则返回专门错误，由catalog与HTTP转换为FailedPrecondition和409；名称、价格等资料更新保留。第32章必须沿用这个边界。

### 32.1.2 【入门】增量表达的是一次业务变化

补货3件写delta=3，盘亏2件写delta=-2；含义是“根据这张业务凭据增加或减少这些可售量”。它不要求调用者先拿到一个可能过期的stock，再自行加减后覆盖数据库。

盘点得到的物理总数还可能包含已预留、损坏、待检与在途货物，不能直接把物理总数赋给可售量。若需要完整仓储系统，应另外建立实物库存、预留、移动与对账模型。本章只有可售量调整，不假装已经具备完整WMS。

### 32.1.3 【进阶】增量仍不天然幂等

第一次+3已提交，CLI在收到回复前退出。操作者重新运行同一个加三操作，数据库如果只执行stock=stock+3，就会加六。原子SQL解决并发丢更新，没有替你识别两次请求是否属于同一个业务意图。

因此每次调整有command_id，同时绑定product_id、delta、actor_id和reason。恢复原操作必须保留这五项；新的业务决定才使用新的UUID。随机UUID重复概率很低，也不能代替数据库唯一约束。

### 32.1.4 【进阶】三个入口各负责什么

| 入口 | 意图 | 身份与持久化依据 |
| --- | --- | --- |
| 商品创建 | 建立初始资料与可售量 | 第29章创建幂等键和保存结果 |
| 商品资料更新 | 修改名称、价格；库存值须与锁后当前值相同 | 第30章StockWriteForbidden边界 |
| Reserve/Confirm/Release | 某订单尝试的占用、确认和归还 | saga_id与预留收据 |
| 本章库存调整 | 基于管理凭据增减可售量 | command_id与调整收据 |
| 下架 | 停止新预留、保留历史和释放能力 | 商品墓碑与快照事件 |

这里的资料更新仍没有乐观版本条件：两位管理员并发改名可能后写覆盖前写。那是资料编辑契约的后续问题，不能因为库存已保护就宣称所有管理员并发冲突都已解决。

### 32.1.5 【精通】审计字段不等于授权证明

actor_id说明这次命令记录的是谁，reason说明业务依据；本地CLI的参数本身不能证明操作者身份。持有商品库写凭据的人本来就有高权限，必须通过受控终端、凭据发放与执行记录管理。

以后注册管理员网络接口时，actor_id应来自已验证身份与授权上下文，不能相信请求JSON自己声称“我是管理员7”。不要把本章CLI的actor_id参数直接复制成公网授权方案。

## 32.2 先写下可检查的不变量

### 32.2.1 【入门】当前可售量不能小于零

令S为当前stock，D为delta，调整后N=S+D。首先要求N&gt;=0。可售2件时盘亏3件应保存rejected，而不是写出负库存，也不应偷扣其他订单持有的库存来让请求成功。

如果盘亏反映的真实物理损失已影响Held，业务需要处理缺货订单或履约决策。本章不会悄悄删除预留来让数字好看。

### 32.2.2 【进阶】还要为未来释放留空间

products.stock使用PostgreSQL INT，Rust对应i32。令H为该商品所有state='held'的quantity之和，还要求N+H&lt;=i32::MAX。否则当前补货成功，未来释放原预留时却可能数值溢出。

例如当前S=i32::MAX-4，Held总量2，补货3后N仍在i32范围内，但N+H已超上限；应拒绝这次补货。Confirmed不会被普通Release归还，不计入H。约束针对当前模型的可表示性，不等于已经证明真实仓库账平衡。

### 32.2.3 【进阶】先扩大计算范围，再检查

不能先用i32做stock+delta，再判断结果。溢出可能已发生。next_stock把数值提升到i64，使用checked_add计算N与N+H，确认边界后才转回i32。

聚合H使用bigint，并检查负值与加法失败。输入delta限制在正负一百万且不等于零，是本章明确的业务上限；Rust校验和SQL CHECK必须一致。单次上限改变时要同步更新两层规则及其用例。

### 32.2.4 【精通】建立一个小规则实验

这一层不需要网络、数据库或线程调度。完整模块中的next_stock单元测试会检查普通增减、不能花掉不可售量、为Held释放留空间、坏数据与输入边界。

## 32.3 增量迁移：调整收据与Held索引

### 32.3.1 【入门】新增第四次商品迁移

新建services/catalog/migrations/0004_inventory_adjustments.sql，前面三次迁移不改写：
```sql
CREATE TABLE inventory_adjustments (
    command_id UUID PRIMARY KEY,
    product_id BIGINT NOT NULL CHECK (product_id > 0),
    delta INT NOT NULL CHECK (delta <> 0 AND delta BETWEEN -1000000 AND 1000000),
    actor_id BIGINT NOT NULL CHECK (actor_id > 0),
    reason TEXT NOT NULL CHECK (char_length(reason) BETWEEN 1 AND 200),
    outcome TEXT NOT NULL CHECK (outcome IN ('pending','applied','rejected','missing')),
    before_stock INT CHECK (before_stock >= 0),
    after_stock INT CHECK (after_stock >= 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK (
        (outcome IN ('pending','missing') AND before_stock IS NULL AND after_stock IS NULL)
        OR (outcome='applied' AND before_stock IS NOT NULL AND after_stock IS NOT NULL
            AND after_stock::bigint = before_stock::bigint + delta::bigint)
        OR (outcome='rejected' AND before_stock IS NOT NULL AND after_stock IS NOT NULL
            AND after_stock=before_stock)
    )
);
CREATE INDEX inventory_reservations_product_held_idx
    ON inventory_reservations(product_id) INCLUDE (quantity) WHERE state='held';
```

command_id是主键，其他意图字段保存原始绑定值。before_stock、after_stock记录这次动作当时的观察和结果。created_at是收据创建时间，不代表收货或盘点实际发生的业务时间。

### 32.3.2 【入门】四种outcome

pending只存在正常事务内部；applied表示增量与事件已一起提交；rejected表示商品存在但数量或释放空间不满足规则；missing表示这次命令执行时商品不存在。

rejected和missing都是可重放的稳定结果。以后补货、创建商品，不会使旧命令重试时重新执行。操作者若基于新事实重新决定调整，要建立新的业务命令，保留旧收据。

### 32.3.3 【进阶】用约束检查收据形状

applied要求前后数量存在且after=before+delta；rejected要求前后相等；pending与missing都没有前后数量。SQL加法先转bigint，避免检查约束本身在i32边界溢出。

这些约束不能独立禁止某个错误程序提交pending；事务协议和读取时的CorruptReceipt检查仍必要。数据库CHECK也没有证明actor_id已认证，或reason中的业务单号真实存在。

### 32.3.4 【进阶】missing为何不使用商品外键

我们要记住“这个命令执行时商品不存在”。如果收据product_id强制外键到products，missing就无法持久化。执行成功调整仍须锁住并更新真实商品行。

不要为了让外键成立而自动创建空白商品；这会把一次明确的缺失结果变成无依据的业务数据。

### 32.3.5 【精通】部分索引只解决查询成本

inventory_reservations_product_held_idx只索引Held记录，并包含quantity，帮助按商品求和。它不保证查询一定走索引或一定只读索引页；实际计划还受数据量、可见性与统计信息影响。

历史收据增长、热点商品和索引维护成本后面仍需分析。不能按年龄直接删除Held或幂等收据来省空间，那可能破坏释放与重放能力。

## 32.4 实现完整调整模块

### 32.4.1 【入门】新增文件并注册模块

新建inventory/src/adjustment.rs，完整内容如下：
```rust
use crate::{ProductRow, append_snapshot};
use sqlx::PgPool;
use uuid::Uuid;

#[derive(Debug, Clone)]
pub struct Command {
    pub command_id: Uuid,
    pub product_id: i64,
    pub delta: i32,
    pub actor_id: i64,
    pub reason: String,
}

#[derive(Debug, thiserror::Error)]
pub enum Error {
    #[error("invalid adjustment input")]
    InvalidInput,
    #[error("adjustment identity reused with different input")]
    IdentityConflict,
    #[error("invalid stored adjustment receipt")]
    CorruptReceipt,
    #[error("operation deadline exceeded; result may be unknown")]
    Deadline,
    #[error(transparent)]
    Database(#[from] sqlx::Error),
    #[error(transparent)]
    Snapshot(#[from] crate::Error),
}

#[derive(Debug, Clone, PartialEq, Eq, sqlx::FromRow)]
pub struct Outcome {
    pub outcome: String,
    pub before_stock: Option<i32>,
    pub after_stock: Option<i32>,
}

#[derive(sqlx::FromRow)]
struct Receipt {
    product_id: i64,
    delta: i32,
    actor_id: i64,
    reason: String,
    outcome: String,
    before_stock: Option<i32>,
    after_stock: Option<i32>,
}

impl Receipt {
    fn verify(&self, cmd: &Command) -> Result<Outcome, Error> {
        if self.product_id != cmd.product_id
            || self.delta != cmd.delta
            || self.actor_id != cmd.actor_id
            || self.reason != cmd.reason
        {
            return Err(Error::IdentityConflict);
        }
        let valid = match (self.outcome.as_str(), self.before_stock, self.after_stock) {
            ("applied", Some(before), Some(after)) => {
                before >= 0
                    && after >= 0
                    && i64::from(after) == i64::from(before) + i64::from(self.delta)
            }
            ("rejected", Some(before), Some(after)) => before >= 0 && before == after,
            ("missing", None, None) => true,
            _ => false,
        };
        if !valid {
            return Err(Error::CorruptReceipt);
        }
        Ok(Outcome {
            outcome: self.outcome.clone(),
            before_stock: self.before_stock,
            after_stock: self.after_stock,
        })
    }
}

pub async fn find(pool: &PgPool, cmd: &Command) -> Result<Option<Outcome>, Error> {
    cmd.validate()?;
    let row = tokio::time::timeout(
        std::time::Duration::from_millis(1200),
        sqlx::query_as::<_, Receipt>(
            "SELECT product_id,delta,actor_id,reason,outcome,before_stock,after_stock
             FROM inventory_adjustments WHERE command_id=$1",
        )
        .bind(cmd.command_id)
        .fetch_optional(pool),
    )
    .await
    .map_err(|_| Error::Deadline)??;
    row.map(|r| r.verify(cmd)).transpose()
}

impl Command {
    pub fn validate(&self) -> Result<(), Error> {
        if self.command_id.is_nil()
            || self.product_id <= 0
            || self.actor_id <= 0
            || self.delta == 0
            || !(-1_000_000..=1_000_000).contains(&self.delta)
            || self.reason != self.reason.trim()
            || !(1..=200).contains(&self.reason.chars().count())
            || self.reason.chars().any(char::is_control)
        {
            return Err(Error::InvalidInput);
        }
        Ok(())
    }
}

/// Held quantities must still fit when they are all released later.
pub fn next_stock(stock: i32, held: i64, delta: i32) -> Option<i32> {
    if stock < 0 || held < 0 {
        return None;
    }
    let next = i64::from(stock).checked_add(i64::from(delta))?;
    let after_release = next.checked_add(held)?;
    if next < 0 || after_release > i64::from(i32::MAX) {
        return None;
    }
    i32::try_from(next).ok()
}

async fn inside(pool: &PgPool, cmd: &Command) -> Result<Outcome, Error> {
    let mut tx = pool.begin().await?;
    sqlx::query("SET TRANSACTION ISOLATION LEVEL READ COMMITTED")
        .execute(&mut *tx)
        .await?;
    sqlx::query("SET LOCAL lock_timeout='400ms'")
        .execute(&mut *tx)
        .await?;
    sqlx::query("SET LOCAL statement_timeout='500ms'")
        .execute(&mut *tx)
        .await?;
    let inserted = sqlx::query(
        "INSERT INTO inventory_adjustments
         (command_id,product_id,delta,actor_id,reason,outcome)
         VALUES($1,$2,$3,$4,$5,'pending') ON CONFLICT DO NOTHING",
    )
    .bind(cmd.command_id)
    .bind(cmd.product_id)
    .bind(cmd.delta)
    .bind(cmd.actor_id)
    .bind(&cmd.reason)
    .execute(&mut *tx)
    .await?;
    let old = sqlx::query_as::<_, Receipt>(
        "SELECT product_id,delta,actor_id,reason,outcome,before_stock,after_stock
         FROM inventory_adjustments WHERE command_id=$1 FOR UPDATE",
    )
    .bind(cmd.command_id)
    .fetch_one(&mut *tx)
    .await?;
    if old.outcome != "pending" {
        let result = old.verify(cmd)?;
        tx.commit().await?;
        return Ok(result);
    }
    // A committed pending row cannot be produced by this transaction protocol.
    if inserted.rows_affected() != 1 {
        return Err(Error::CorruptReceipt);
    }
    let product = sqlx::query_as::<_, ProductRow>(
        "SELECT id,name,price_cents,stock,revision,
                delisted_at IS NULL AS listed
         FROM products WHERE id=$1 FOR UPDATE",
    )
    .bind(cmd.product_id)
    .fetch_optional(&mut *tx)
    .await?;
    let result = if let Some(row) = product {
        let held: i64 = sqlx::query_scalar(
            "SELECT COALESCE(sum(quantity),0)::bigint
             FROM inventory_reservations WHERE product_id=$1 AND state='held'",
        )
        .bind(cmd.product_id)
        .fetch_one(&mut *tx)
        .await?;
        if let Some(next) = next_stock(row.stock, held, cmd.delta) {
            let updated = sqlx::query_as::<_, ProductRow>(
                "UPDATE products SET stock=$2,revision=revision+1,updated_at=now()
                 WHERE id=$1
                 RETURNING id,name,price_cents,stock,revision,
                           delisted_at IS NULL AS listed",
            )
            .bind(cmd.product_id)
            .bind(next)
            .fetch_one(&mut *tx)
            .await?;
            append_snapshot(&mut tx, updated).await?;
            Outcome {
                outcome: "applied".into(),
                before_stock: Some(row.stock),
                after_stock: Some(next),
            }
        } else {
            Outcome {
                outcome: "rejected".into(),
                before_stock: Some(row.stock),
                after_stock: Some(row.stock),
            }
        }
    } else {
        Outcome {
            outcome: "missing".into(),
            before_stock: None,
            after_stock: None,
        }
    };
    sqlx::query(
        "UPDATE inventory_adjustments
         SET outcome=$2,before_stock=$3,after_stock=$4 WHERE command_id=$1",
    )
    .bind(cmd.command_id)
    .bind(&result.outcome)
    .bind(result.before_stock)
    .bind(result.after_stock)
    .execute(&mut *tx)
    .await?;
    tx.commit().await?;
    Ok(result)
}

pub async fn execute(pool: &PgPool, cmd: &Command) -> Result<Outcome, Error> {
    cmd.validate()?;
    tokio::time::timeout(std::time::Duration::from_millis(1200), inside(pool, cmd))
        .await
        .map_err(|_| Error::Deadline)?
}
```

### 32.4.2 【入门】校验发生在申请事务之前

Command拒绝nil UUID、非正数商品与操作者、零或超范围delta、首尾空白和控制字符reason。reason限制一至两百个Unicode字符，不按UTF-8字节截断中文。

重试中的reason按原字符串比较，不在数据库里临时trim成另一值。调用者应在建立业务意图前规范化并确认参数，然后保存稳定输入。

### 32.4.3 【进阶】先争取命令身份

INSERT ON CONFLICT DO NOTHING使相同command_id竞争同一主键；随后SELECT FOR UPDATE锁住收据。首个事务创建pending，其他事务等待后读取完成结果，不会各加一次。

rows_affected还区分“本事务刚创建的pending”与“已经提交的异常pending”。后者不是正常可恢复中间状态，应报告CorruptReceipt并停止自动写入，避免把损坏记录解释成执行许可。

### 32.4.4 【进阶】原意图不能被重试改写

Receipt::verify先核对商品、增量、操作者、理由，再验证完成结果的形状与算术关系。只要身份参数不同，就返回IdentityConflict；不能把旧行更新成新参数后继续执行。

恢复查询也使用同一个Command，既查询UUID，也验证绑定。相比只返回一个outcome字符串，这让调用方知道自己恢复的是原业务意图。

### 32.4.5 【精通】查询历史结果不读取当前库存替代它

一次+3使库存从10到13，随后另一命令+5到18。原命令查询应仍回答before=10、after=13，而不是用当前18拼出一份新收据。

find返回Ok(None)只是当前查询未见收据，不能证明另一个事务以后不会提交。Error::Deadline或Database也不能解释为None；恢复时保留原UUID与输入，并把不确定状态展示出来。

## 32.5 并发：为什么锁顺序和快照都重要

### 32.5.1 【入门】先锁收据，再锁商品

不同命令有不同收据，但可能修改同一商品；因此读取product时还要FOR UPDATE。取得商品锁后，才能把观察到的stock作为本次调整起点。

重复命令先读收据即可返回原结果，不需要再改变商品。正常新调整则锁商品、汇总Held、计算并写回，然后在同一事务保存收据。

### 32.5.2 【进阶】求和发生在取得商品锁之后

Reserve和Release改变可售量时同样需要商品行锁，并在一个事务内改变收据。因此调整取得锁之后，再以新的语句汇总已提交Held，才能与当前stock配对理解。

如果先在事务开头读H，再排队等待商品锁，其他预留可能在等待期间提交；拿旧H配新S，就可能低估释放空间。把SELECT写在同一个事务里，并不自动使所有读取时机正确。

### 32.5.3 【进阶】本章显式使用Read Committed

本章在第一条业务语句前设置Read Committed。该级别允许后续语句看到开始前新提交的事实，因此取得商品锁后再读Held，能看到先前持锁事务已提交的变化。[PostgreSQL 17隔离级别文档](https://www.postgresql.org/docs/17/transaction-iso.html)解释了每条语句的快照和等待更新行为。

这只支撑当前单商品锁协议，不意味着任意跨表规则都能靠Read Committed自动正确。改用长期快照、增加批量多商品命令，或加入不遵守商品锁的新写入口，都必须重新推导并测试。

### 32.5.4 【精通】Confirm不拿商品锁有什么影响

Confirm把Held改为Confirmed，不增加可售量。如果与调整并发，调整可能还把即将Confirmed的数量计入H，结果更保守；不会因此少预留释放空间。Release则先更新商品再改变状态，受商品锁串行化。

这里没有为求和额外锁住所有预留行，避免形成“调整先锁商品再锁预留、Release先锁预留再锁商品”的反向锁顺序。若以后改变Confirm或Release语义，这段证明也需重写。

### 32.5.5 【精通】并发规则依赖全部写入口

商品资料更新已经不能覆盖stock，但数据库超级用户、旧版本进程和手工SQL仍可绕过应用约束。切流时要检查所有仍持有写凭据的运行实例，不能只看新catalog的健康检查。

同理，外部系统不能直接改inventory_reservations.state。锁是一套合作协议；[PostgreSQL显式锁文档](https://www.postgresql.org/docs/17/explicit-locking.html)提供行锁行为的依据，具体业务不变量仍由我们的写路径共同维持。

## 32.6 让库存、版本、事件和收据一起提交

### 32.6.1 【入门】一次成功包含四项事实

更新products.stock时同时revision+1；append_snapshot写入同版本商品快照；调整收据记下applied与前后数量；最后commit。任何一步失败，都不应留下“库存变了但事件没有”或“收据成功但库存没变”。

Outbox是数据库事务的一部分，Kafka发送继续由独立relay完成。本章不在持有商品锁时等待Kafka确认。

### 32.6.2 【进阶】业务拒绝没有商品事件

rejected和missing只保存完成收据，不改变商品revision，也不产生商品快照。重复读取applied也不再写商品事件。事件描述商品状态变化，不能把每一次查询或重放都当成新商品修订。

当前没有为管理审计另建事件主题。若后面需要审计流，应定义独立契约、隐私字段与可靠投递机制，而不是把reason等字段随意塞入所有公开商品快照。

### 32.6.3 【进阶】下架不阻止受控调整

本章允许下架商品在管理流程中盘亏或补货，但不自动重新上架。返回事件的listed仍由delisted_at决定，消费方不能因为收到新revision就复活墓碑。

这是一个明确业务选择。若团队要求下架后一律禁止调整，应同时修改判断、测试和管理流程；不要在远程客户端私自猜测服务端规则。

### 32.6.4 【精通】预算失败不能伪装成未执行

每个锁等待400ms、每条语句500ms，整个调整有1200ms外层预算。多个SQL的总耗时仍可能触及外层预算，提交附近断开也可能留下未知结果。

发生错误后以原Command调用find，或同身份execute恢复；不要换UUID“再补一次”。只有明确的applied/rejected/missing才能解释为相应业务结果，CorruptReceipt则需要排查异常写入。

### 32.7.1 【入门】完整工具代码

```rust
use anyhow::{Context, bail};
use inventory::adjustment::{self, Command};
use sqlx::postgres::PgPoolOptions;
use std::time::Duration;
use uuid::Uuid;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let args: Vec<String> = std::env::args().skip(1).collect();
    if args.len() != 7 || !matches!(args[0].as_str(), "apply" | "query") {
        bail!(
            "usage: inventory-adjust apply/query UUID PRODUCT_ID DELTA ACTOR_ID REASON --local-admin"
        );
    }
    if args[6] != "--local-admin" {
        bail!("explicit local admin mode required");
    }
    let command = Command {
        command_id: Uuid::parse_str(&args[1]).context("invalid command UUID")?,
        product_id: args[2].parse().context("invalid product id")?,
        delta: args[3].parse().context("invalid delta")?,
        actor_id: args[4].parse().context("invalid actor id")?,
        reason: args[5].clone(),
    };
    command.validate()?;
    let pool = tokio::time::timeout(
        Duration::from_secs(2),
        PgPoolOptions::new()
            .max_connections(2)
            .acquire_timeout(Duration::from_millis(500))
            .connect(&std::env::var("DATABASE_URL").context("DATABASE_URL missing")?),
    )
    .await
    .context("database connection budget exhausted")??;
    let result = if args[0] == "apply" {
        adjustment::execute(&pool, &command).await.map(Some)
    } else {
        adjustment::find(&pool, &command).await
    };
    pool.close().await;
    match result? {
        Some(row) => println!(
            "{} {} {:?} {:?}",
            command.command_id, row.outcome, row.before_stock, row.after_stock
        ),
        None => println!("not_found"),
    }
    Ok(())
}
```

它先解析并校验全部参数，再建立最多两个连接的数据库池。连接有两秒预算，获取连接还有500ms上限；执行使用模块自己的总预算。结束前关闭连接池。

### 32.7.2 【进阶】显式本地管理模式的含义

--local-admin要求使用者明确选择这条受控路径，防止误把它当成普通服务RPC客户端。这个字符串不是安全认证；任何拿到可写DATABASE_URL的人都可能执行其他SQL。

普通订单进程继续使用第31章InventoryRemote，不能因为本章有CLI就给它商品库密码。CLI不读取库存RPC令牌，也没有给公网新增任何路由。

### 32.8.2 【进阶】重复与身份变化要分别检查

replay_does_not_apply_delta_twice核对重放的库存、版本和事件；concurrent_same_identity_has_one_effect同时发送同一命令，验证数据库唯一键争用。只顺序调用两次，不能代替并发重复场景。

query_keeps_original_result_and_checks_identity在后续新调整后查询原收据，并分别改变商品、delta、actor与reason，验证查询和执行都拒绝身份冲突。

### 32.8.3 【进阶】业务拒绝与不存在也有记忆

rejected_attempt_stays_rejected验证补货不会重新打开旧拒绝；missing_is_stable_after_product_is_created验证商品后来出现也不改变原missing。

这不是缓存“暂时找不到”的处理，而是命令已经作出并保存的业务结果。缓存miss与持久化missing收据不能混为一谈。

### 32.8.4 【精通】注入事件失败与锁等待

outbox_failure_rolls_back_everything给新Outbox写入注入失败，检查商品与收据全部回滚。lock_timeout_leaves_no_receipt由另一个事务持有商品锁，检查SQLSTATE 55P03并释放阻塞者，再确认无收据残留。

每个测试独立数据库，因此故障约束不污染其他用例。这里检查结构化SQLSTATE，不依赖某个版本的错误显示文案。

### 32.8.5 【精通】跨动作验证释放空间

replenishment_preserves_release_headroom接近i32上限预留后尝试补货，要求拒绝且原Release仍能完成；normal_replenishment_then_release验证普通补货与释放的最终数量；release_and_adjustment_serialize_correctly让两个动作并发，核对最终stock、revision和事件。

一次并发调度通过不等于穷举全部执行顺序。它与锁协议推导、边界规则测试共同支撑当前实现；吞吐与长期压力还需要独立实验。

### 32.8.6 【进阶】异常收据与下架快照

committed_pending_is_rejected_without_writing故意建立正常代码不应留下的pending，验证不会擅自继续。delisted_product_can_be_adjusted_without_relisting检查数据库和新事件的listed都保持false。

legacy_overwrite_is_disabled继续验证绝对库存覆盖被拒绝；名称含legacy不表示整个商品Update接口已关闭。原第30章元数据编辑回归仍须通过。

### 32.9.3 【精通】生产审计还需要什么

本章收据包含操作者编号和理由，但没有审批人、附件、外部仓储凭据唯一约束、防篡改存储和数据保留策略。数据库写权限本身仍可修改历史；不能把普通业务表描述成不可篡改的合规账本。

在当前教学工程里，我们先建立一致的事务效果和恢复身份。后续权限、审计与运维设计要围绕同一命令继续扩展，而不是允许另一条无收据SQL绕过它。

## 32.10 分层练习与工程检查点

### 32.10.1 【入门练习】原子加法解决了什么

stock=stock+3已经是数据库原子更新，为什么还要command_id？

参考答案：原子更新避免并发读改写丢失，但两个请求仍可能各加三。command_id与保存结果用于识别重放，使同一意图只产生一次调整效果。

### 32.10.2 【操作练习】历史结果和当前状态

先+3，再用新UUID加5，最后查询第一次命令。记录两份收据和当前商品stock、revision、Outbox。

评分要点：从10开始当前为18，第一次收据仍为10到13；两次新动作产生两次修订和事件；查询与重复原命令不再增加任何效果。

### 32.10.3 【推理练习】为何Held参与上界

当前可售i32::MAX-4，Held=2，补货3。只检查补货后stock会接受吗？正确结果是什么？

参考答案：补货后stock=i32::MAX-1，在单字段范围内；但全释放会到i32::MAX+1，因此本章拒绝并保存rejected。不能等到用户取消订单才发现无法归还。

### 32.10.4 【推理练习】能否改成先求Held再锁商品

参考答案：不能直接调换。等待商品锁期间另一预留可能提交，旧H与锁后S不再对应。必须重新推导快照与锁协议；当前实现以取得商品锁后的后续Read Committed语句读取H。

### 32.10.5 【推理练习】既然是pending，为什么不接着做

参考答案：正常pending与库存操作、完成收据处于同一事务，外部不应读到已提交pending。它表示协议外写入或异常历史，不能把它当成尚未执行的证明；当前返回CorruptReceipt以避免猜测造成重复效果。

### 32.10.6 【扩展练习】调整如何接入管理员HTTP

设计请求、授权上下文、状态码和未知结果查询，不要求本章直接开放公网。

参考要点：actor来自认证身份，限制业务权限；保存command_id与规范化输入；成功和稳定拒绝都有收据；超时保留未知结果并提供查询；错误不暴露数据库秘密；不能让订单普通服务取得任意调整权限。还要决定幂等身份的租户范围和审计留存。

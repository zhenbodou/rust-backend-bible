# 第 7 章 智能指针与多线程并发

第 2 章的所有权规则说“一个值只有一个所有者”。但后端服务里到处是“共享”：一个数据库连接池被成千上万个请求同时使用，一份配置被所有模块读取，一个内存缓存被多个线程同时读写。本章讲 Rust 怎样在不破坏内存安全的前提下做到这些：智能指针负责“共享所有权”和“内部可变性”，Send /Sync与锁负责“线程安全”。项目部分为第 5 章的内存仓储加上线程安全的共享包装，并用多线程测试证明并发扣库存不会超卖。

本章只讲操作系统线程（std::thread ）。后端服务实际使用的异步任务（Tokio）在第 11 章讲解，但它使用的 Arc 、Send 、Sync 、锁的规则与本章完全相同。

## 7.1 Box：把值放到堆上

### 7.1.1 【入门】什么是智能指针

普通引用 &amp;T 只是一个地址，不拥有数据。智能指针是“像指针一样使用、但拥有额外能力的结构体”：它们实现了 Deref （可以用 * 和自动解引用像引用一样访问内部值）和 Drop （离开作用域时执行清理）。第 1 章的 String 、Vec 其实就是智能指针：它们拥有堆上的数据，并在 drop 时释放。

| 智能指针 | 一句话 | 线程安全 | 本章小节 |
| --- | --- | --- | --- |
| Box&lt;T&gt; | 单一所有者，值放在堆上 | 取决于 T | 7.1 |
| Rc&lt;T&gt; | 单线程共享所有权（引用计数） | 否 | 7.2 |
| Weak&lt;T&gt; | 不增加计数的弱引用，打破循环 | 随 Rc / Arc | 7.2 |
| Cell&lt;T&gt; / RefCell&lt;T&gt; | 单线程内部可变性 | 不实现 Sync，不能直接跨线程共享；T: Send 时可以整体转移 | 7.3 |
| Arc&lt;T&gt; | 多线程共享所有权（原子引用计数） | 仅当 T: Send + Sync 时，Arc&lt;T&gt; 才是 Send + Sync | 7.6 |
| Mutex&lt;T&gt; / RwLock&lt;T&gt; | 多线程内部可变性（加锁） | Mutex&lt;T&gt; 的 Sync 要求 T: Send；RwLock&lt;T&gt; 的 Sync 还要求 T: Sync | 7.6 |
| OnceLock&lt;T&gt; / LazyLock&lt;T&gt; | 只初始化一次的全局值 | 取决于 T 以及具体初始化类型的 Send / Sync 约束 | 7.7 |

### 7.1.2 【入门】Box 的基本用法
```rust
fn main() {
    // 42 放在堆上，b（一个指针）放在栈上
    let b = Box::new(42);

    // 解引用得到内部值
    println!("{}", *b + 1);
    // Display 会自动穿透 Box
    println!("{b}");

    // 取出内部值（i32 是 Copy）
    let inner: i32 = *b;

    // 1 KB 数组放在堆上
    let big = Box::new([0u8; 1024]);

    // 方法调用自动解引用
    println!("{inner} {}", big.len());

// b 和 big 离开作用域，堆内存自动释放
}
```

Box 除了“把值放在堆上”之外几乎没有额外开销：它就是一个指针，大小 8 字节。

### 7.1.3 【进阶】Box 的四种用途

1. 递归类型：编译器必须知道每个类型的大小。一个直接包含自己的类型大小是无穷大，需要用 Box 打断：
```rust
/// 商品分类树：每个分类可以有子分类
#[derive(Debug)]
enum Category {
    Leaf(String),
    // Vec 本身已经把元素放在堆上，所以这里不需要 Box
    Node(String, Vec<Category>),
}

/// 优惠条件表达式：and / or 嵌套
#[derive(Debug)]
enum Condition {
    MinAmount(i64),
    IsVip,
    // 直接写 Condition 会报 E0072: recursive type has infinite size
    And(Box<Condition>, Box<Condition>),
    Or(Box<Condition>, Box<Condition>),
}

fn eval(c: &Condition, amount: i64, vip: bool) -> bool {
    match c {
        Condition::MinAmount(m) => amount >= *m,
        Condition::IsVip => vip,
        // &Box<T> 自动解引用为 &T
        Condition::And(a, b) => eval(a, amount, vip) && eval(b, amount, vip),
        Condition::Or(a, b) => eval(a, amount, vip) || eval(b, amount, vip),
    }
}

fn main() {
    // “满 300 元且是会员”或者“满 1000 元”
    let rule = Condition::Or(
        Box::new(Condition::And(Box::new(Condition::MinAmount(30_000)), 
            Box::new(Condition::IsVip))),
        Box::new(Condition::MinAmount(100_000)),
    );

    // true
    println!("{}", eval(&rule, 50_000, true));
    let tree = Category::Node("数码".into(), vec![Category::Leaf("键盘".into())]);
    println!("{tree:?}");
}
```

2. trait 对象：Box&lt;dyn Trait&gt; 存放“实现了某个 trait 的任意类型”，第 5.5 节和第 6.4.5 节已经用过。

3. 减小枚举体积：第 3.4.7 节提到，枚举的大小由最大的变体决定。把很大的变体数据放进 Box，其他变体就不必为它付出空间（clippy 的 large_enum_variant 会提示）。

4. 转移大对象的所有权时避免复制：移动一个 [u8; 1_000_000] 会复制 1 MB 的栈数据，移动一个Box&lt;[u8; 1_000_000]&gt; 只复制 8 字节的指针。

### 7.1.4 【精通】Box 的细节

Box&lt;str&gt; 、Box&lt;[T]&gt; 是“不再增长的 String / Vec”，比后者少一个容量字段，适合存放大量只读字符串。String::into_boxed_str() 可以转换。

Box::leak(b) 故意泄漏内存，得到一个 &amp;'static mut T ：用于程序启动时创建、整个运行期都存在的全局数据（例如解析一次的配置）。不要在循环中调用。

栈上构造再移入：Box::new([0u8; 10_000_000]) 在 debug 模式下可能先在栈上构造数组再复制到堆，导致栈溢出；大缓冲区用 vec![0u8; n].into_boxed_slice() 。

## 7.2 Rc 与 Weak：单线程共享所有权

### 7.2.1 【入门】为什么需要 Rc

有些数据天然有多个“主人”：多个订单都引用同一个促销活动配置，谁最后用完谁负责释放。所有权规则不允许多个所有者，借用又要求引用不能比数据活得久--这时用 Rc&lt;T&gt;（Reference Counted，引用计数）：
```rust
use std::rc::Rc;

#[derive(Debug)]
struct Campaign { name: String, percent: i64 }

struct Order { id: u64, campaign: Rc<Campaign> }

fn main() {
    let campaign = Rc::new(Campaign { name: "双十一".into(), percent: 85 });

    // 1
    println!("计数 {}", Rc::strong_count(&campaign));
    // 计数 +1，不复制 Campaign
    let a = Order { id: 1, campaign: Rc::clone(&campaign) };
    let b = Order { id: 2, campaign: Rc::clone(&campaign) };

    // 3
    println!("计数 {}", Rc::strong_count(&campaign));

    drop(a);

    // 2
    println!("计数 {}", Rc::strong_count(&campaign));
    println!("{} 使用活动 {}（{} 折）", b.id, b.campaign.name, b.campaign.percent);

// b 和 campaign 先后被 drop，计数归零时 Campaign 才被释放
}
```

约定写法 Rc::clone(&amp;x) ：它和 x.clone() 效果相同，但明确告诉读者“这里只增加计数，不是深拷贝”。

### 7.2.2 【入门】Rc 的限制

1. 只读：Rc&lt;T&gt; 只能得到 &amp;T ，因为多个所有者同时持有，任何一方都不能独占修改。需要修改时配合 7.3 节的 RefCell 。

2. 只能单线程：计数的增减不是原子操作，多线程同时修改会出错。编译器会阻止你把 Rc 发送到其他线程（7.5 节），多线程场景使用 Arc 。

### 7.2.3 【进阶】循环引用与 Weak

引用计数有一个经典陷阱：A 持有 B 的 Rc，B 又持有 A 的 Rc，两者的计数永远不会归零，内存泄漏。典型场景是父子关系（父节点拥有子节点，子节点又想访问父节点）。解决办法是让“反向”的那一边使用Weak&lt;T&gt; ：
```rust
use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Department {
    name: String,
    // 指向父部门：弱引用，不拥有
    parent: RefCell<Weak<Department>>,
    // 拥有子部门：强引用
    children: RefCell<Vec<Rc<Department>>>,
}

fn main() {
    let root = Rc::new(Department { name: "总部".into(), parent: RefCell::new(Weak::new()), 
        children: RefCell::new(vec![]) });
    let tech = Rc::new(Department { name: "技术部".into(), parent: RefCell::new(Weak::new()), 
        children: RefCell::new(vec![]) });

    // 生成弱引用
    *tech.parent.borrow_mut() = Rc::downgrade(&root);
    root.children.borrow_mut().push(Rc::clone(&tech));

    // Weak 不保证目标还活着，使用前要 upgrade，返回 Option<Rc<T>>
    if let Some(parent) = tech.parent.borrow().upgrade() {
        println!("{} 的上级是 {}", tech.name, parent.name);
    }

    // 1，1
    println!("root 强引用 {}，弱引用 {}", Rc::strong_count(&root), Rc::weak_count(&root));
}
```

规则：拥有关系用强引用，回指关系用弱引用。Weak 不阻止释放，所以访问前必须 upgrade() 检查对象是否还在。后端中的另一个常见用法是缓存：缓存只持有 Weak，数据真正的所有者释放后，缓存自然失效。

### 7.2.4 【精通】后端中 Rc 用得少的原因

后端服务几乎总是多线程（或多任务）的，跨请求共享的数据都要 Send + Sync ，所以实际代码里Arc远多于 Rc 。Rc 主要出现在：单线程的数据结构（解析器、图算法）、tokio::task::LocalSet 中的本地任务、以及性能敏感且确定不跨线程的场景（Rc 的计数是普通加减，比 Arc 的原子操作略快）。不确定时用 Arc，代价可以忽略。

## 7.3 内部可变性：Cell、RefCell、OnceCell

### 7.3.1 【入门】什么是内部可变性

借用规则要求“修改必须通过 &amp;mut ”。但有时我们只有 &amp;T ，却确实需要修改内部的某个状态，例如：一个只读的服务对象内部要统计调用次数；一个缓存在“读”的时候需要顺便写入。内部可变性是一组类型，它们允许通过共享引用修改内部数据，并把安全检查从编译期移到运行期（或用其他方式保证安全）。

### 7.3.2 【入门】Cell：用于 Copy 类型的简单值
```rust
use std::cell::Cell;

struct PriceService { calls: Cell<u32> }

impl PriceService {
    // 注意是 &self
    fn quote(&self, cents: i64) -> i64 {
        self.calls.set(self.calls.get() + 1);
        cents * 9 / 10
    }
}

fn main() {
    let svc = PriceService { calls: Cell::new(0) };
    svc.quote(100);
    svc.quote(200);

    // 2
    println!("调用了 {} 次", svc.calls.get());
}
```

Cell&lt;T&gt; 从不交出内部值的引用，只能整体 get （要求 Copy）、set 、replace 、take ，所以永远不会出现悬垂引用，零运行时开销。第二卷第 5 章综合练习 2 的 CountingRepository 用的就是它。

### 7.3.3 【入门】RefCell：运行时检查的借用
```rust
use std::cell::RefCell;

struct Cache { entries: RefCell<Vec<String>> }

impl Cache {
    fn remember(&self, key: &str) {
        // 运行时获取可变借用
        self.entries.borrow_mut().push(key.to_string());
    }
    fn size(&self) -> usize {
        // 运行时获取只读借用
        self.entries.borrow().len()
    }
}

fn main() {
    let cache = Cache { entries: RefCell::new(vec![]) };
    cache.remember("product:1");
    println!("{}", cache.size());

    let r1 = cache.entries.borrow();

    // 运行时 panic：already borrowed: BorrowMutError
    let w = cache.entries.borrow_mut();
    println!("{} {}", r1.len(), w.len());
}
```

RefCell 在运行时执行和第 2 章完全相同的借用规则（多读或单写），违反时 panic 而不是编译错误。borrow() 返回 Ref&lt;T&gt; ，borrow_mut() 返回 RefMut&lt;T&gt; ，它们是 RAII 守卫：守卫离开作用域时借用结束。不想 panic 时用 try_borrow() / try_borrow_mut() ，返回 Result。

使用建议：RefCell 是“编译器无法证明但你能保证”时的工具，能用普通的 &amp;mut 解决就不要用RefCell；守卫的作用域要尽量小，不要把 borrow_mut() 的结果长时间持有。

### 7.3.4 【进阶】OnceCell：只赋值一次
```rust
use std::cell::OnceCell;
struct Report { rows: Vec<i64>, total: OnceCell<i64> }

impl Report {
    /// 第一次调用时计算并缓存，之后直接返回缓存值
    fn total(&self) -> i64 {
        *self.total.get_or_init(|| self.rows.iter().sum())
    }
}
```

延迟计算并缓存结果是 OnceCell 的典型用法。它的多线程版本 OnceLock 在 7.7 节介绍。

### 7.3.5 【精通】UnsafeCell：一切内部可变性的基础

Cell 、RefCell 、Mutex 、原子类型内部都包装了 UnsafeCell&lt;T&gt; --这是 Rust 中唯一合法地“通过共享引用修改数据”的原语，编译器对它关闭了“共享引用指向的数据不会变”这一优化假设。业务代码不需要直接使用它，但理解这一点就能明白：内部可变性不是绕过了借用规则，而是由这些类型用运行时检查（RefCell）、限制 API（Cell）或同步原语（Mutex、原子操作）保证了同样的安全性。

### 7.3.6 常见编译错误与运行时错误

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| E0072 | recursive type Condition has infinite size | 类型直接包含自身 | 用 Box 包装递归字段 |
| E0594 /E0596 | cannot assign to data in an Rc | 通过 Rc 修改数据 | Rc&lt;RefCell&lt;T&gt;&gt; ，或重新设计为单一所有者 |
| 运行时 panic | already borrowed: BorrowMutError | RefCell 同时存在读守卫和写守卫 | 缩小守卫作用域；用try_bo rrow_mut |
| E0599 | no method named get found for Cell&lt;String&gt; | 对非 Copy 类型调用Cell::get | 用 take / replace ，或改用 RefCell |
| E0277 | Rc&lt;...&gt; cannot be sent between threads safely | 把 Rc 交给其他线程 | 改用 Arc |
| 内存泄漏（无报错） | 计数永远不为 0 | Rc 循环引用 | 反向引用改为 Weak |

## 7.4 线程基础

### 7.4.1 【入门】创建线程
```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("后台线程：第 {i} 步");
            thread::sleep(Duration::from_millis(10));
        }

        // 线程的返回值
        42
    });

    println!("主线程继续工作");

    // 等待线程结束并取回返回值
    let result = handle.join().expect("后台线程 panic 了");
    println!("后台线程返回 {result}");
}
```

要点：

thread::spawn 接收一个闭包，立即在新的操作系统线程中运行它，返回 JoinHandle&lt;T&gt; 。

join() 阻塞等待线程结束，返回 Result&lt;T, _&gt; ：线程 panic 时是 Err。线程中的 panic 不会让整个进程崩溃，只会终止那个线程（主线程 panic 才会结束进程）。

如果不 join，main 返回时进程退出，所有还在运行的线程被直接终止。

多个线程的输出顺序不确定，每次运行都可能不同。

### 7.4.2 【入门】move 与 'static
```rust
use std::thread;

fn main() {
    let order_ids = vec![1001, 1002];
    // let h = thread::spawn(|| println!("{order_ids:?}"));   // E0373：闭包可能比 main 活得久，却借用了 order_ids
    // move：把Vec 的所有权交给新线程
    let h = thread::spawn(move || println!("{order_ids:?}"));

    h.join().expect("线程不应 panic");
}
```

thread::spawn 的签名要求闭包满足 F: FnOnce() -&gt; T + Send + 'static ：新线程可能比创建它的函数活得更久，所以闭包不能借用局部变量（'static ，见 2.5.6），并且捕获的数据必须能安全地送到另一个线程（Send ，见 7.5）。

### 7.4.3 【进阶】作用域线程：可以借用局部变量

很多时候我们只想“把一批工作分给几个线程并行做完再继续”，线程不会活过当前函数。thread::scope 正是为此设计的：作用域结束前保证所有线程都已结束，所以线程可以借用局部变量。
```rust
use std::thread;

fn main() {
    let prices: Vec<i64> = (1..=1_000).collect();
    let chunks: Vec<&[i64]> = prices.chunks(250).collect();

    let total: i64 = thread::scope(|s| {
        let mut handles = Vec::new();
        for chunk in &chunks {
            // 借用 prices 的一部分
            handles.push(s.spawn(move || chunk.iter().sum::<i64>()));
        }
        handles.into_iter().map(|h| h.join().expect("线程不应 panic")).sum()
    // 走到这里时所有线程都已结束
    });

    // 500500
    println!("总和 {total}");
    println!("prices 仍可使用：{}", prices.len());
}
```

这里的 move 把 chunk （一个 &amp;&amp;[i64] 引用，本身是 Copy）复制进闭包，而不是移动 prices。项目中的并发测试（7.10 节）就用作用域线程。

### 7.4.4 【进阶】线程 Builder 与其他 API
```rust
use std::thread;

fn main() -> std::io::Result<()> {
    let handle = thread::Builder::new()
        // 线程名会出现在 panic 信息和调试器、性能分析工具中
        .name("outbox-relay".into())
        // 栈大小，默认 2 MB
        .stack_size(4 * 1024 * 1024)
        // 创建失败（资源耗尽）返回 Err
        .spawn(|| println!("当前线程：{:?}", thread::current().name()))?;
    handle.join().expect("线程不应 panic");
    println!("CPU 并行度：{:?}", thread::available_parallelism());
    Ok(())
}
```

available_parallelism() 返回可用的 CPU 核数，用来决定线程池大小；Tokio 默认的工作线程数就是这个值（第 11 章）。

### 7.4.5 【精通】线程的代价

每个操作系统线程有独立的栈（默认 2 MB 虚拟内存）、需要内核调度，创建和切换的成本在微秒级。一万个并发连接如果每个开一个线程，光栈就要 20 GB 虚拟内存，上下文切换也会吃掉大量 CPU。这正是后端服务改用异步任务的原因：Tokio 用少量线程运行成千上万个轻量任务（每个只占几百字节到几 KB）。但线程仍然适用于：CPU 密集的计算（配合线程池，如 rayon ）、阻塞调用（Tokio 的spawn_blocking 内部就是一个线程池）、少量长期运行的后台工作。

## 7.5 Send 与 Sync：编译期的线程安全

### 7.5.1 【入门】两个标记 trait

| trait | 含义 | 不满足的典型类型 |
| --- | --- | --- |
| Send | 这个类型的值可以安全地转移到另一个线程 | Rc&lt;T&gt; 、裸指针 |
| Sync | 这个类型的引用 &amp;T 可以安全地被多个线程同时持有 | Cell&lt;T&gt; 、RefCell&lt;T&gt; 、Rc&lt;T&gt; |

等价定义：T: Sync 当且仅当 &amp;T: Send 。

它们是自动 trait：如果一个结构体的所有字段都是 Send，它自动就是 Send，不需要（也通常不应该）手动实现。绝大多数类型同时是 Send 和 Sync：整数、String、Vec、HashMap、以及由它们组成的你自己的结构体。

### 7.5.2 【入门】编译器如何阻止数据竞争
```rust
use std::rc::Rc;
use std::thread;

fn main() {
    let shared = Rc::new(vec![1, 2, 3]);
    let s2 = Rc::clone(&shared);
    thread::spawn(move || println!("{s2:?}"));
    // 错误 E0277：`Rc<Vec<i32>>` cannot be sent between threads safely
    //   = help: within `{closure}`, the trait `Send` is not implemented for `Rc<Vec<i32>>`
}
```

Rc 的计数增减不是原子的，如果两个线程同时 clone / drop 同一个 Rc，计数会被写坏，导致提前释放或内存泄漏。编译器通过 Send 约束在编译期就拒绝了这段代码--在其他语言中这是只会在高并发时偶发、极难复现的 bug。这就是 Rust 宣称的“无畏并发”（fearless concurrency）：数据竞争是编译错误，而不是运行时事故。

### 7.5.3 【进阶】常见类型的 Send / Sync 速查

| 类型 | Send | Sync | 说明 |
| --- | --- | --- | --- |
| i32 、String 、Vec&lt;T&gt;（T满足时） | 是 | 是 | 普通拥有数据的类型 |
| &amp;T | T: Sync 时是 | T: Sync 时是 | 共享引用 |
| &amp;mut T | T: Send 时是 | T: Sync 时是 | 独占引用 |
| Rc&lt;T&gt; | 否 | 否 | 用 Arc 替代 |
| Arc&lt;T&gt; | T: Send + Sync时是 | T: Send + Sync时是 |  |
| Cell&lt;T&gt; 、RefCell&lt;T&gt; | T: Send 时是 | 否 | 可以整体移到另一个线程，但不能被多线程共享 |
| Mutex&lt;T&gt; | T: Send 时是 | T: Send 时是 | 加锁把“只能 Send”提升为 Sync |
| RwLock&lt;T&gt; | T: Send 时是 | T: Send + Sync时是 | 多个读者同时持有 &amp;T |
| MutexGuard&lt;T&gt; | 否 | T: Sync 时是 | 锁必须在加锁的线程上释放 |

最后一行很重要：std::sync::MutexGuard 不是 Send。第 11 章在 async 函数中持有标准库的锁跨越.await 时，会因此遇到“future cannot be sent between threads safely”的报错。

### 7.5.4 【精通】手动实现 Send / Sync

unsafe impl Send for MyType {} 是在向编译器保证“我确认它是线程安全的”。只有在封装裸指针、FFI 句柄等编译器无法推断的场景才需要，而且写错会导致未定义行为。RustMall 在第 1 章就用unsafe_code = "forbid" 禁止了 unsafe，所以项目中不会出现。反过来，想让一个本来是 Send 的类型变成非 Send，可以加一个 PhantomData&lt;*const ()&gt; 字段。

## 7.6 Arc、Mutex、RwLock 与死锁

### 7.6.1 【入门】Arc：多线程共享所有权

Arc&lt;T&gt; （Atomically Reference Counted）是 Rc 的线程安全版本：计数用原子操作增减。
```rust
use std::sync::Arc;
use std::thread;

struct Config { db_url: String, max_conn: u32 }

fn main() {
    let config = Arc::new(Config { db_url: "postgres://...".into(), max_conn: 20 });
    let mut handles = Vec::new();
    for worker in 0..3 {
        // 每个线程一份“钥匙”
        let cfg = Arc::clone(&config);
        handles.push(thread::spawn(move || {
            println!("worker {worker} 连接 {}，最多 {} 个连接", cfg.db_url, cfg.max_conn);
        }));
    }
    for h in handles { h.join().expect("线程不应 panic"); }

    // 1：线程结束后它们持有的 Arc 都已 drop
    println!("计数 {}", Arc::strong_count(&config));
}
```

Arc&lt;T&gt; 只提供共享的只读访问。只读数据（配置、编译好的正则、只读的数据库连接池句柄）直接放进Arc 即可；需要修改时，配合 Mutex 或 RwLock。

### 7.6.2 【入门】Mutex：互斥锁
```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let stock = Arc::new(Mutex::new(10_i32));
    let mut handles = Vec::new();
    for _ in 0..15 {
        let stock = Arc::clone(&stock);
        handles.push(thread::spawn(move || {
            // 加锁，得到 MutexGuard
            let mut guard = stock.lock().expect("锁已中毒");
            if *guard > 0 {
                // 通过守卫修改
                *guard -= 1;
                true
            } else {
                false
            }

        // 守卫在这里 drop，自动解锁
        }));
    }
    let sold = handles.into_iter().filter_map(|h| h.join().ok()).filter(|&ok| ok).count();

    // 卖出 10 件，剩余 0
    println!("卖出 {sold} 件，剩余 {}", *stock.lock().expect("锁已中毒"));
}
```

要点：

Mutex&lt;T&gt; 把数据包在锁里面，不加锁就根本拿不到数据--不可能出现“忘了加锁就访问”的bug，这一点比 Java、Go 的“锁和数据分开放”更安全。

lock() 返回的 MutexGuard 是 RAII 守卫（第 2.2.6 节），离开作用域自动解锁，不会忘记解锁。

“检查库存 + 扣减”必须在同一次加锁中完成。如果先加锁读出库存、解锁，再加锁扣减，两次加锁之间别的线程可能已经卖掉了最后一件--这就是“检查后再操作”（check-then-act）竞态，第 5章仓储的 get + update 组合正有这个问题，7.10 节会解决它。

### 7.6.3 【进阶】锁中毒（poisoning）

如果一个线程在持有锁时 panic，标准库会把这把锁标记为“中毒”，之后的 lock() 返回Err(PoisonError) ，提醒你“数据可能处于被修改了一半的状态”。处理方式：

| 做法 | 写法 | 适用 |
| --- | --- | --- |
| 视为 bug，一起panic | lock().expect("锁已中毒") | 数据不一致就无法继续时 |
| 忽略中毒，继续使用数据 | lock().unwrap_or_else(PoisonError::into_inner) | 保护的数据在任何时刻都保持一致（例如每次修改都是一步完成的整体替换） |
| 恢复并清除中毒标记 | Mutex::clear_poison() （Rust 1.77+） | 能修复数据时 |

第三方的 parking_lot 锁没有中毒机制，API 更简洁（lock() 直接返回守卫）、性能也略好，很多项目选择它。Tokio 的异步锁（第 11 章）也没有中毒。

### 7.6.4 【进阶】RwLock：读写锁
```rust
use std::collections::HashMap;
use std::sync::{Arc, RwLock};

fn main() {
    let cache: Arc<RwLock<HashMap<i64, String>>> = Arc::new(RwLock::new(HashMap::new()));

    {
        // 写锁：独占
        let mut w = cache.write().expect("锁已中毒");
        w.insert(1, "机械键盘".into());

    // 写锁释放
    }

    // 读锁：可以同时有多个
    let r1 = cache.read().expect("锁已中毒");
    let r2 = cache.read().expect("锁已中毒");
    println!("{:?} {}", r1.get(&1), r2.len());
}
```

RwLock 实现的正是第 2 章的借用规则--“多读或单写”--只不过是在运行时、跨线程地执行。读多写少（缓存、配置、路由表）时比 Mutex 并发度更高；但它本身比 Mutex 更重，写操作频繁或临界区很短时，Mutex 往往更快。不确定时先用 Mutex，压测证明是瓶颈再换。

### 7.6.5 【进阶】死锁与锁的使用纪律

死锁：线程 A 持有锁 1 等锁 2，线程 B 持有锁 2 等锁 1，两者永远等下去。Rust 能防止数据竞争，但不能防止死锁。
```text
// 危险：两个线程以相反顺序获取两把锁
// 线程 A：let _a = account_a.lock(); let _b = account_b.lock();
// 线程 B：let _b = account_b.lock(); let _a = account_a.lock();
```

纪律：

1. 固定加锁顺序：需要同时持有多把锁时，所有代码都按同一顺序获取（例如按 ID 从小到大）。

2. 缩小临界区：只在真正读写共享数据时持锁；计算、日志、网络 I/O 都放到锁外。用 { } 代码块或drop(guard) 尽早释放。

3. 不要在持锁时调用外部代码：回调、trait 对象的方法可能在内部再次获取同一把锁。标准库的 Mutex不可重入，同一线程对同一把 Mutex 加锁两次会死锁（或 panic）。

4. 同一表达式中的临时守卫：if map.lock().unwrap().contains_key(&amp;k){map.lock().unwrap().insert(..) } 在 Rust 2024 之前，if 条件中的临时守卫会活到整个 if块结束，第二次 lock 就会死锁。2024 Edition 缩短了这类临时值的生命周期，但最好的做法始终是：只加一次锁，把守卫绑定到变量上。

5. 用一个锁保护“必须一起变化”的数据：库存和已售数量如果放在两把锁里，就无法保证它们之间的一致性。

### 7.6.6 【精通】锁的粒度与替代方案

粗粒度：一把锁保护整个 HashMap，简单可靠，但所有访问串行化。

细粒度 / 分片：把数据按键哈希分成 N 个分片，每片一把锁，不同分片的访问互不阻塞。dashmap crate 就是分片的并发 HashMap。

无锁读：arc-swap crate 让读者无锁地读取一个 Arc&lt;T&gt; 快照，写者整体替换--非常适合配置热更新、路由表这类“极少写、极多读”的数据。

消息传递：让唯一一个线程拥有数据，其他线程通过通道发消息请求修改（7.8 节），彻底避免锁。

交给数据库：多实例部署时，进程内的锁根本管不到其他机器。库存这类数据的最终正确性要由数据库保证（第 14 章的条件更新、第 29 章的幂等）；进程内的锁只用于进程内的数据。

### 7.6.7 常见编译错误与解读

| 错误码 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| E0373 | closure may outlive the current function, but it borrows x | spawn 的闭包借用局部变量 | 加 move ，或改用thread::scope |
| E0277 | Rc&lt;T&gt; cannot be sent between threads safely | 跨线程使用 Rc | 改用 Arc |

| 错误码 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| E0277 | RefCell&lt;T&gt; cannot be shared between threads safely | Arc&lt;RefCell&lt;T&gt;&gt; 跨线程 | 改用 Arc&lt;Mutex&lt;T&gt;&gt; 或Ar c&lt;RwLock&lt;T&gt;&gt; |
| E0596 | cannot borrow data in an Arc as mutable | 通过 Arc 修改数据 | 内部包一层 Mutex /RwLock /原子类型 |
| E0382 | use of moved value: stock | 在循环中把同一个 Arc move 进多个闭包 | 每次循环先 Arc::clone 一份 |
| 运行时 | 程序卡住不动 | 死锁 | 检查加锁顺序与重复加锁；用调试器查看各线程栈 |
| 运行时panic | PoisonError | 其他线程持锁时 panic | 按 7.6.3 选择处理方式 |

## 7.7 原子类型、内存序与一次性初始化

### 7.7.1 【入门】原子类型：不加锁的计数器

对单个整数或布尔值的简单操作（加一、比较后交换、读取、写入），不需要 Mutex，用原子类型即可，速度快得多：
```rust
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};
use std::thread;

// 全局计数器：const fn 构造，可以放进 static
static REQUESTS: AtomicU64 = AtomicU64::new(0);
static SHUTTING_DOWN: AtomicBool = AtomicBool::new(false);

fn handle_request() {
    // 原子地加一，返回加之前的值
    REQUESTS.fetch_add(1, Ordering::Relaxed);
}

fn main() {
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| for _ in 0..1_000 { handle_request(); });
        }
    });

    // 一定是 4000
    println!("共处理 {} 个请求", REQUESTS.load(Ordering::Relaxed));

    // 通知其他线程准备停机
    SHUTTING_DOWN.store(true, Ordering::Release);
}
```

常用原子类型：AtomicBool 、AtomicI32/I64/U32/U64/Usize 、AtomicPtr 。常用操作：

| 方法 | 作用 |
| --- | --- |
| load(order) / store(v, order) | 读 / 写 |
| fetch_add / fetch_sub | 加减，返回旧值（溢出时回绕） |
| fetch_max / fetch_min | 取最大 / 最小，返回旧值 |
| swap(v, order) | 写入新值，返回旧值 |
| compare_exchange(当前期望值, 新值, 成功序,失败序) | 只有当前值等于期望值时才写入（CAS），是无锁算法的基础 |

### 7.7.2 【进阶】用 CAS 实现“不超过上限”的扣减
```rust
use std::sync::atomic::{AtomicI64, Ordering};

/// 原子地扣减库存，库存不足时不扣减并返回 false
fn try_deduct(stock: &AtomicI64, qty: i64) -> bool {
    let mut current = stock.load(Ordering::Relaxed);
    loop {
        if current < qty {
            return false;
        }
        match stock.compare_exchange_weak(current, current - qty, Ordering::AcqRel, 
            Ordering::Relaxed) {
            // 成功：期间没有别人修改
            Ok(_) => return true,
            // 失败：别人先改了，用最新值重试
            Err(actual) => current = actual,
        }
    }
}
```

这是“乐观并发”的典型写法：先读、计算，写入时检查“值是否还是我读到的那个”，不是就重试。第14 章数据库中的乐观锁（UPDATE ... WHERE version = $old ）是完全相同的思想。标准库也提供了封装好的 fetch_update 方法。

### 7.7.3 【精通】内存序（Ordering）

现代 CPU 和编译器会为了性能重排内存读写的顺序。内存序告诉它们“哪些重排是不允许的”：

| 内存序 | 保证 | 典型用途 |
| --- | --- | --- |
| Relaxed | 只保证这个原子变量本身的读写是原子的，不约束其他内存操作的顺序 | 独立的统计计数器、ID 生成 |
| Release（写）/ Acqu ire （读） | 配对使用：写线程在 Release 之前的所有写入，对用Acquire 读到该值的线程可见 | “准备好数据，再设置标志位”的发布/订阅 |
| AcqRel | 同时具有 Acquire 和 Release，用于读-改-写操作 | CAS 实现的同步 |
| SeqCst | 对 SeqCst 原子操作建立一致的全序，并提供相应的获取/释放约束 | 需要跨原子变量推理时可先采用；不能修复错误的算法 |

实用规则：计数器用 Relaxed；用原子变量作为“标志”来同步其他数据时用 Release/Acquire；拿不准就用 SeqCst。真正需要精细推理内存序的场景（实现无锁数据结构）在业务开发中很少见，推荐阅读Mara Bos 的《Rust Atomics and Locks》。

### 7.7.4 【进阶】OnceLock 与 LazyLock：线程安全的一次性初始化

全局配置、编译好的正则表达式、全局 HTTP 客戶端，这些值需要在运行时创建（不能用 const），但只创建一次、之后全程只读：
```rust
use std::collections::HashMap;
use std::sync::{LazyLock, OnceLock};

/// LazyLock：第一次访问时自动执行初始化闭包（Rust 1.80+）
static ERROR_MESSAGES: LazyLock<HashMap<&'static str, &'static str>> = LazyLock::new(|| {
    HashMap::from([("NOT_FOUND", "资源不存在"), ("CONFLICT", "状态冲突")])
});

/// OnceLock：由程序在合适的时机显式设置一次
static APP_NAME: OnceLock<String> = OnceLock::new();

fn main() {
    APP_NAME.set("rustmall".to_string()).expect("只能设置一次");

    // Some("rustmall")
    println!("{:?}", APP_NAME.get());

    // 第一次访问时才构建 HashMap
    println!("{}", ERROR_MESSAGES["NOT_FOUND"]);

    // 已经设置过，返回已有值
    let v = APP_NAME.get_or_init(|| "default".into());
    println!("{v}");
}
```

| 类型 | 初始化方式 | 适用 |
| --- | --- | --- |
| LazyLock&lt;T&gt; | 定义时给出闭包，第一次访问自动执行 | 初始化逻辑固定、不依赖运行时参数 |

| 类型 | 初始化方式 | 适用 |
| --- | --- | --- |
| OnceLock&lt;T&gt; | 运行时调用 set 或 get_or_init | 初始化需要运行时信息（例如启动时读到的配置） |

多个线程同时第一次访问时，只有一个线程执行初始化，其他线程等待结果。旧代码中常见的lazy_static! 宏和 once_cell crate 已经被这两个标准库类型取代。

后端中的态度：全局变量会让测试变得困难（测试之间共享状态、无法注入替身），所以 RustMall 只把真正“全进程唯一且不变”的东西放进全局（例如错误码表、编译好的正则）；数据库连接池、配置、仓储等依赖都通过参数或 Axum 的 State 显式传递（第 12 章）。

## 7.8 通道与消息传递

### 7.8.1 【入门】用通信来共享内存

Go 语言有一句名言：“不要通过共享内存来通信，而要通过通信来共享内存。”通道（channel）就是线程之间的传送带：发送方把值放上去，接收方从另一端取走，值的所有权随之转移，不需要加锁。
```rust
// multi-producer, single-consumer：多个发送者，一个接收者
use std::sync::mpsc;
use std::thread;

#[derive(Debug)]
enum Event { OrderCreated(u64), OrderPaid(u64) }

fn main() {
    let (tx, rx) = mpsc::channel::<Event>();

    let mut producers = Vec::new();
    for worker in 0..2_u64 {
        // 每个生产者一个发送端
        let tx = tx.clone();
        producers.push(thread::spawn(move || {
            tx.send(Event::OrderCreated(worker * 100 + 1)).expect("接收端已关闭");
            tx.send(Event::OrderPaid(worker * 100 + 1)).expect("接收端已关闭");
        }));
    }

    // 关键：丢掉 main 自己持有的发送端
    drop(tx);

    // 所有发送端都 drop后，循环自动结束
    for event in rx {

        println!("收到 {event:?}");
    }
    for p in producers { p.join().expect("生产者不应 panic"); }
}
```

为什么要 drop(tx) ：接收端的 for 循环在“所有发送端都已关闭”时才结束。main 持有的原始tx如果不 drop，循环会永远等下去--这是使用通道时最常见的“程序卡住”原因。

### 7.8.2 【进阶】有界通道与背压

mpsc::channel() 是无界的：生产比消费快时，队列无限增长直到内存耗尽。生产环境更推荐有界通道：
```rust
use std::sync::mpsc;

// 最多缓存 100 条
let (tx, rx) = mpsc::sync_channel::<u64>(100);
// tx.send(x)：队列满时阻塞等待，自然地让生产者慢下来--这叫“背压”（backpressure）
// tx.try_send(x)：队列满时立即返回 Err(TrySendError::Full)，由调用方决定丢弃还是降级
// 示例到此为止
let _ = (tx, rx);
```

背压是高并发系统稳定性的核心概念：与其让过载的数据堆积直到崩溃，不如让上游感知到压力并减速或拒绝。第 28 章的 Kafka 消费、第 39 章的限流与负载削减都是这一思想在不同层次的体现。

### 7.8.3 【进阶】接收的几种方式

| 方法 | 行为 |
| --- | --- |
| recv() | 阻塞等待，所有发送端关闭后返回 Err |
| try_recv() | 不等待，没有消息时立即返回 Err |
| recv_timeout(d) | 最多等待 d，超时返回 Err |
| for msg in rx / rx.iter() | 循环接收直到所有发送端关闭 |

### 7.8.4 【精通】共享状态还是消息传递

| 维度 | 共享状态（Arc + Mutex） | 消息传递（通道） |
| --- | --- | --- |
| 适合 | 多方需要随机读写同一份数据（缓存、计数器） | 有明确的“生产-消费”流水线（事件处理、后台任务） |
| 风险 | 死锁、锁竞争 | 队列堆积、忘记关闭发送端导致卡住 |
| 性能 | 临界区短时很快 | 每条消息有一次入队出队的开销 |
| 典型例子 | 内存仓储、限流计数 | 日志写入线程、Outbox 投递任务（第 29 章） |

两者常常组合使用。另一种重要模式是 Actor：一个线程（或任务）独占某份状态，外界只能发消息请求它读写，请求中附带一个“回复通道”接收结果。它用消息传递实现了“共享”的效果，又完全不需要锁。标准库的 mpsc 只有一个接收端；需要多消费者、select 多个通道时，可以使用 crossbeam-channel ；异步代码中使用 tokio::sync::mpsc （第 11 章）。

## 7.9 后端视角：并发原语的选择

### 7.9.1 【进阶】决策表

| 需求 | 选择 |
| --- | --- |
| 多个线程/任务共享只读数据（配置、连接池句柄） | Arc&lt;T&gt; |
| 共享且需要修改，临界区短 | Arc&lt;Mutex&lt;T&gt;&gt; |
| 共享且读远多于写 | Arc&lt;RwLock&lt;T&gt;&gt; ，或 arc-swap 整体替换 |
| 单个计数器、开关、ID 序列 | 原子类型 |
| 全局只初始化一次 | LazyLock / OnceLock |
| 高并发的键值存储 | dashmap ，或分片的 Vec&lt;Mutex&lt;HashMap&gt;&gt; |
| 生产者-消费者流水线 | 有界通道 |
| 需要跨多台机器的一致性 | 进程内原语都不够用：数据库事务、分布式锁（第 18 章）、幂等设计（第 29 章） |

### 7.9.2 【精通】标准库锁与异步代码

第 11 章开始，服务代码运行在 Tokio 的异步任务中，选择规则如下（这里先给结论，第 11 章详细解释）：

临界区内没有 .await 、且很短（读写一个 HashMap）：使用标准库的 std::sync::Mutex ，它比异步锁更快。

临界区内需要 .await （例如持锁期间访问数据库）：使用 tokio::sync::Mutex ；更好的做法是重新设计，避免持锁等待 I/O。

绝不在异步任务中执行阻塞操作（长时间持有标准锁、thread::sleep 、同步 I/O）：它会卡住整个工作线程上的所有任务。

本章项目的 Shared 包装使用标准库的 RwLock ，它的方法接收同步闭包，闭包中不可能出现.await，从 API 上就杜绝了“持锁跨 await”的问题。

## 7.10 项目进度：线程安全的共享仓储与并发扣库存

第 5 章的 InMemoryRepository 方法签名是 &amp;mut self ，只能被一个所有者使用。真实服务中，成百上千个并发请求要同时读写同一个仓储。本节新增两个模块：

### 7.10.2 设计决策

| 问题 | 选择 | 理由 |
| --- | --- | --- |
| 共享所有权 | Arc | 多线程共享，见 7.6.1 |
| 读写保护 | RwLock | 商品查询远多于扣减；读操作可以并发 |
| 暴露锁守卫还是闭包 | 闭包：read(\|r\|...)、write(\|r\|...) | 调用方拿不到守卫，就不可能把锁持有到函数外、更不可能跨越.await（7.9.2）；锁的作用域一目了然 |
| 锁中毒 | 忽略中毒（PoisonError::into_inner ） | 仅当能证明任意写闭包 panic 后不变量仍成立，才可恢复使用；否则应停止相关操作并修复。该包装允许任意闭包，不能单凭仓储单次写入保证安全。 |

| 问题 | 选择 | 理由 |
| --- | --- | --- |
| 扣库存的原子性 | 读取、检查、扣减、写回放在同一个 write 闭包中 | 消除 check-then-act 竞态（7.6.2） |
| ID 生成 | AtomicI64::fetch_add + Relaxed | 只需要唯一性，不用来同步其他数据（7.7.3） |

### 7.10.3 第 1 步：新建 shared.rs

```rust
//! 线程安全的共享仓储句柄。
//!
//! [`Shared<R>`] 把任意仓储包装进 `Arc<RwLock<R>>`，克隆句柄只增加引用计数，
//! 所有克隆指向同一份数据。读写通过闭包进行，调用方拿不到锁守卫，
//! 因此锁的持有范围永远局限在闭包内部。

use std::sync::{Arc, PoisonError, RwLock};

use crate::error::{DomainError, DomainResult};
use crate::ids::ProductId;
use crate::product::Product;
use crate::quantity::Quantity;
use crate::repository::Repository;

/// 可在线程间克隆、共享的仓储句柄。
pub struct Shared<R> {
    inner: Arc<RwLock<R>>,
}

// 手写 Clone：#[derive(Clone)] 会生成 `impl<R: Clone> Clone`，
// 要求仓储本身可克隆，而克隆句柄只需要克隆 Arc。
impl<R> Clone for Shared<R> {
    fn clone(&self) -> Self {
        Self { inner: Arc::clone(&self.inner) }
    }
}

impl<R> Shared<R> {
    /// 包装一个仓储。
    pub fn new(inner: R) -> Self {
        Self { inner: Arc::new(RwLock::new(inner)) }
    }

    /// 持有读锁执行闭包。多个线程可以同时读。
    pub fn read<T>(&self, f: impl FnOnce(&R) -> T) -> T {
        let guard = self.inner.read().unwrap_or_else(PoisonError::into_inner);
        f(&*guard)
    }

    /// 持有写锁执行闭包。同一时刻只有一个写者，且没有读者。
    pub fn write<T>(&self, f: impl FnOnce(&mut R) -> T) -> T {
        let mut guard = self.inner.write().unwrap_or_else(PoisonError::into_inner);
        f(&mut *guard)
    }
}

/// 扣减商品库存，返回扣减后的商品。
///
/// 读取、检查、扣减、写回在同一把写锁内完成，因此任意多个线程并发调用也不会超卖。
///
/// # Errors
/// - 商品不存在：[`DomainError::NotFound`]
/// - 库存不足：[`DomainError::InsufficientStock`]，此时库存不变
pub fn reserve_stock<R>(repo: &Shared<R>, id: ProductId, qty: Quantity) -> 
    DomainResult<Product>
where
    R: Repository<Product>,
{
    repo.write(|r| {
        let mut product = r.get(&id)?;
        if !product.can_buy(qty) {
            return Err(DomainError::InsufficientStock {
                product_id: id.to_string(),
                requested: u32::try_from(qty.get()).unwrap_or(0),
                available: u32::try_from(product.stock()).unwrap_or(0),
            });
        }
        product.deduct_stock(qty).map_err(DomainError::Internal)?;
        r.update(product.clone())?;
        Ok(product)
    })
}

### 7.10.4 代码精讲

f(&amp;*guard) 的含义：guard 的类型是 RwLockReadGuard&lt;R&gt; ，*guard 通过 Deref 得到 R ，再取引用得到 &amp;R 。直接写 f(&amp;guard) 在多数情况下也能通过自动解引用转换编译，这里显式写出 &amp;*，让“从守卫取出内部引用”这一步一目了然。写锁同理使用 &amp;mut *guard 。闭包执行完毕、函数返回时，守卫被 drop，锁随之释放。

reserve_stock 为什么是泛型函数：它只依赖 Repository&lt;Product&gt; 这个能力，而不关心具体是内存仓储还是将来的数据库仓储（第 5 章的设计）。where R: Repository&lt;Product&gt; 这个约束使得闭包中可以调用 r.get 、r.update 。

闭包中的 ? ：write 的闭包返回 DomainResult&lt;Product&gt; ，所以闭包内部可以直接用 ? 传播get 、update 的错误；write 把闭包的返回值原样返回给 reserve_stock 。

map_err(DomainError::Internal) ：第 3 章的 deduct_stock 返回 Result&lt;(), String&gt; ，元组变体 DomainError::Internal 本身就是一个 fn(String) -&gt; DomainError ，可以直接当作函数传给map_err 。因为前面已经检查过 can_buy ，这里理论上不会失败；万一失败，说明 can_buy与deduct_stock 的逻辑不一致，属于内部错误。

u32::try_from(...).unwrap_or(0) ：第二卷 InsufficientStock 的字段是 u32 ，而第 3 章的库存和数量是 i32 。用 try_from 安全转换（1.3.5 节）；Quantity 保证为正、Product 保证库存不为负，所以转换实际不会失败，unwrap_or(0) 只是兜底，也避开了 clippy 的 unwrap_used 。

两个并发测试的区别：

concurrent_reservations_never_oversell 使用作用域线程（7.4.3），线程直接借用局部变量store 和 one ，不需要克隆。8 个线程争抢 5 件库存，无论线程调度顺序如何，成功次数都恰好是5、剩余库存恰好是 0。

handle_moves_into_spawned_threads 使用 thread::spawn （要求 'static ），每个线程move进一个克隆出来的句柄。这证明 Shared&lt;InMemoryRepository&lt;Product&gt;&gt; 满足 Send +'static，可以像第 12 章 Axum 的 State 一样被分发到各个请求处理任务中。

动手体会竞态：把 reserve_stock 改成先用 repo.read(|r| r.get(&amp;id)) 读出商品并检查库存，再用repo.write(|r| r.update(...)) 写回--两次加锁之间存在空窗。多次运行concurrent_reservations_never_oversell （可以把线程数加到 64），你会看到成功次数偶尔大于5，也就是超卖。这正是 7.6.2 节说的 check-then-act 竞态，体会完请恢复原实现。

//! 进程内的单调递增 ID 序列。
//!
//! 只用于内存实现和测试。接入数据库后，ID 由数据库的自增序列生成（第 14 章），
//! 微服务之间需要全局唯一 ID 时使用 UUID v7 或雪花算法（第 29 章）。

use std::sync::atomic::{AtomicI64, Ordering};
/// 线程安全的递增序列。
///
/// 可以放进 `static`，也可以作为结构体字段通过 `Arc` 共享。
///
/// 
```
/// use common::id_gen::Sequence;
///
/// static ORDER_NO: Sequence = Sequence::starting_at(1001);
/// assert_eq!(ORDER_NO.next_value(), 1001);
/// assert_eq!(ORDER_NO.next_value(), 1002);
/// 
```
#[derive(Debug)]
pub struct Sequence {
    next: AtomicI64,
}

impl Sequence {
    /// 从 `first` 开始的序列。`const fn`，因此可以用于 `static`。
    pub const fn starting_at(first: i64) -> Self {
        Self { next: AtomicI64::new(first) }
    }

    /// 取下一个值。多个线程同时调用也不会得到重复的值。
    ///
    /// 达到 `i64::MAX` 后会回绕为负数；按每秒一百万个计算，需要约 29 万年。
    pub fn next_value(&self) -> i64 {
        // 只需要“每个值只被取走一次”，不用它同步其他数据，所以 Relaxed 足够
        self.next.fetch_add(1, Ordering::Relaxed)
    }
}

impl Default for Sequence {
    fn default() -> Self {
        Self::starting_at(1)
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::collections::HashSet;
    use std::thread;
    #[test]
    fn values_are_sequential() {
        let seq = Sequence::default();
        let values: Vec<i64> = (0..3).map(|_| seq.next_value()).collect();
        assert_eq!(values, vec![1, 2, 3]);
    }

    #[test]
    fn concurrent_values_are_unique() {
        let seq = Sequence::default();
        let all: Vec<i64> = thread::scope(|s| {
            let mut handles = Vec::new();
            for _ in 0..8 {
                handles.push(s.spawn(|| (0..1_000).map(|_| seq.next_value()).collect:: 
                    <Vec<_>>()));
            }
            handles
                .into_iter()
                .flat_map(|h| h.join().expect("线程不应 panic"))
                .collect()
        });
        let unique: HashSet<i64> = all.iter().copied().collect();
        assert_eq!(all.len(), 8_000);
        assert_eq!(unique.len(), 8_000, "不能出现重复的 ID");
        assert_eq!(all.iter().max(), Some(&8_000));
    }
}
````

为什么方法叫 next_value 而不是 next ：名为 next 的方法会让 clippy 提示“应当实现Iterator trait”（should_implement_trait ）。Sequence 永远不会结束、而且通过 &amp;self 调用，不适合作为迭代器，所以换个名字。

测试中的 flat_map ：每个线程返回一个 Vec&lt;i64&gt; ，flat_map 把 8 个 Vec 展开成一个序列再collect（第 6.6.1 节）。8 个线程交错取号，单个线程拿到的号不连续，但合在一起恰好是 1~8000、没有重复也没有遗漏。

### 7.10.10 本章小结

Box 把值放到堆上，用于递归类型、trait 对象和缩小枚举；Rc 提供单线程共享所有权，Weak打破循环引用。

内部可变性把借用检查推迟到运行时：Cell 适合 Copy 小值，RefCell 违规时 panic，OnceCell用于延迟初始化；它们都不能跨线程共享。

thread::spawn 要求闭包 Send + 'static ，作用域线程 thread::scope 可以借用局部变量。

Send 表示值可以安全地移到另一线程，Sync 表示共享引用可以安全地跨线程使用。Rc 既不是 Send 也不是 Sync；RefCell&lt;T&gt; 在 T: Send 时可以整体转移，但不是 Sync。标准库 MutexGuard 不能跨线程移动。

Arc 提供多线程共享所有权；Mutex / RwLock 把数据包在锁里，守卫自动解锁；Rust 防止数据竞争但不防止死锁，要遵守固定加锁顺序、缩小临界区等纪律。

原子类型适合计数器与开关，CAS 是乐观并发的基础；LazyLock / OnceLock 实现线程安全的一次性初始化；通道通过转移所有权在线程间通信，有界通道提供背压。

RustMall 新增 Shared&lt;R&gt; 与 reserve_stock ，用多线程测试证明并发扣库存不超卖；新增原子ID序列。单元测试在当前配套检查点中为 64 个。

# 第 30 章 库存预留：状态机与并发事务

上一章把商品变更、版本与 Outbox 放进同一个事务，消费者也能处理事件重复和旧版本。但订单尚不能安全地占用库存：普通商品更新只是把 stock 替换成另一个数，没有描述谁占用了多少、是否已确认、失败后应该归还几次。

本章给 RustMall 增加 inventory 包，使用现有商品数据库建立持久化预留记录。先定义可独立测试的状态机，再用事务将预留状态、条件扣减和商品快照事件绑在一起。最后通过一个可信本地命令行入口，以及真实 PostgreSQL 并发和失败注入测试，验证这些规则。

inventory 目前是商品能力内部的事务模块，不是已经部署的独立库存微服务。它与 products 和 Outbox 共用商品库，是为了在一个数据库事务中落实库存约束；下一章再为这个能力增加网络契约。本章同时收紧旧商品更新入口，避免管理员的绝对库存覆盖破坏预留账。

学完后，你应能解释为什么预留时扣可售量、确认时不再扣一次，能重现两个请求竞争最后一件的结果，也能说明取消先到、重复释放、价格变化、数据库超时和结果未知时应怎样恢复。

## 30.1 先把库存的含义说清楚

### 30.1.1 【入门】stock 现在表示可供新订单占用的数量

假设商品最初可售十件，一个订单预留两件以后，stock 变成八。两件仍可能在仓库里，但已经不能再被另一个订单占用。因此本章 stock 表达的是可售数量，不是物理仓库盘点总量。

确认预留只把预留状态从 held 改为 confirmed，不再把八减二。释放未确认的预留才把两件归还，使可售量从八回到十。物理发货、退货入库与盘点属于后续独立业务动作，不能混进一个含义不明的整数。

### 30.1.2 【入门】为什么只检查 stock &gt;= 0 不够

两个请求都先读到 stock=1，各自在应用内判断足够，再分别执行“把库存改成零”。最终数字没有负数，却有两个订单都认为自己拿到了最后一件。

这个反例说明，不超卖不能只用“最终列值非负”证明。检查与扣减必须在能协调并发的边界内完成，并且每个成功预留都要有对应收据，不能仅让两个应用计算结果碰巧相同。

### 30.1.3 【进阶】预留记录是持久化收据

inventory_reservations 保存一次预留意图的标识、商品、数量、单价与当前状态。请求重试时先核对收据，而不是重新减库存；进程重启后也能查询已经发生到哪一步。

收据不是临时日志。它决定重复请求是否可以再次产生副作用，以及迟到的 Reserve 是否已被更早的取消挡住。删除收据会改变恢复语义，不能把它当作随时可清理的调试信息。

### 30.1.4 【进阶】本章一个标识对应一个商品预留

Command 使用 saga_id 作为 UUID。这里先把它理解为某次业务流程的预留标识，不要求读者已经掌握完整 Saga 协调器。一个标识绑定一个 product_id、quantity 和 unit_price_cents。

本章不是多商品购物车一次全部预留。后续订单需要协调多个步骤时，要设计每个明细的稳定标识或明确聚合边界；不能对同一 saga_id 换不同商品反复调用，再期望表主键自动变成多明细主键。

### 30.1.5 【精通】幂等是保持同一意图，而非忽略参数

第一次用某标识预留商品一件，重试却改成三件，属于身份复用冲突。不能因为标识相同就直接返回成功，更不能按新数量释放旧收据。

本章每次操作都比较商品、数量与价格，不一致返回 IdentityConflict。合法重试保留全部参数；真正的新购买尝试才使用新标识。不能一遇到超时就换新标识，否则同一意图可能被扣两次。

## 30.2 先用纯函数定义状态机

### 30.2.1 【入门】状态与动作分开

状态描述“现在是什么”，动作描述“这次希望做什么”。本章状态有 Pending、Held、Confirmed、Released、Rejected；动作有 Reserve、Confirm、Release。

Pending 是尚未决定的初始状态，Held 表示已经占用可售量，Confirmed 表示占用已经确认，Released 表示这次意图已关闭且不再占用，Rejected 表示预留条件不成立。本章没有自动超时状态，不应把 Held 随意解释成即将自行过期。

### 30.2.2 【入门】完整模型文件

创建 inventory/src/model.rs：
```rust
use uuid::Uuid;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Action {
    Reserve,
    Confirm,
    Release,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum State {
    Pending,
    Held,
    Confirmed,
    Released,
    Rejected,
}

impl State {
    pub fn as_str(self) -> &'static str {
        match self {
            Self::Pending => "pending",
            Self::Held => "held",
            Self::Confirmed => "confirmed",
            Self::Released => "released",
            Self::Rejected => "rejected",
        }
    }

    pub fn from_stored(value: &str) -> Result<Self, crate::Error> {
        match value {
            "pending" => Ok(Self::Pending),
            "held" => Ok(Self::Held),
            "confirmed" => Ok(Self::Confirmed),
            "released" => Ok(Self::Released),
            "rejected" => Ok(Self::Rejected),
            _ => Err(crate::Error::CorruptState),
        }
    }
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Command {
    pub saga_id: Uuid,
    pub product_id: i64,
    pub quantity: i32,
    pub unit_price_cents: i64,
}

impl Command {
    pub fn validate(&self) -> Result<(), crate::Error> {
        if self.saga_id.is_nil()
            || self.product_id <= 0
            || !(1..=999).contains(&self.quantity)
            || self.unit_price_cents < 0
        {
            return Err(crate::Error::InvalidInput);
        }
        Ok(())
    }
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Step {
    TryHold,
    GiveBack,
    Store(State),
}

pub fn decide(state: State, action: Action) -> Step {
    match (state, action) {
        (State::Pending, Action::Reserve) => Step::TryHold,
        (State::Pending, Action::Confirm | Action::Release) => Step::Store(State::Released),
        (State::Held, Action::Confirm) => Step::Store(State::Confirmed),
        (State::Held, Action::Release) => Step::GiveBack,
        _ => Step::Store(state),
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn every_terminal_state_is_stable() {
        for state in [State::Confirmed, State::Released, State::Rejected] {
            for action in [Action::Reserve, Action::Confirm, Action::Release] {
                assert_eq!(decide(state, action), Step::Store(state));
            }
        }
    }

    #[test]
    fn cancellation_before_reservation_leaves_a_fence() {
        assert_eq!(
            decide(State::Pending, Action::Release),
            Step::Store(State::Released)
        );
        assert_eq!(
            decide(State::Released, Action::Reserve),
            Step::Store(State::Released)
        );
        assert_eq!(
            decide(State::Pending, Action::Confirm),
            Step::Store(State::Released)
        );
    }

    #[test]
    fn holding_and_settlement_are_different_effects() {
        assert_eq!(decide(State::Pending, Action::Reserve), Step::TryHold);
        assert_eq!(
            decide(State::Held, Action::Reserve),
            Step::Store(State::Held)
        );
        assert_eq!(
            decide(State::Held, Action::Confirm),
            Step::Store(State::Confirmed)
        );
        assert_eq!(decide(State::Held, Action::Release), Step::GiveBack);
    }
}
```

decide 只接收状态与动作，不连接数据库、不读取时钟。它返回 Step，描述下一步需要尝试占用、归还，还是只保存某个状态。将决策与 SQL 执行分开，可以先穷举规则，再测试数据库副作用。

### 30.2.3 【进阶】完整转移表

| 当前状态 | Reserve | Confirm | Release |
| --- | --- | --- | --- |
| Pending | 尝试条件扣减，成功 Held，否则 Rejected | Released，不凭空确认 | Released，建立取消屏障 |
| Held | 保持 Held，不重复扣减 | Confirmed，不再扣库存 | 归还一次，转 Released |
| Confirmed | 保持 Confirmed | 保持 Confirmed | 保持 Confirmed |
| Released | 保持 Released | 保持 Released | 保持 Released |
| Rejected | 保持 Rejected | 保持 Rejected | 保持 Rejected |

表中“保持”表示不再产生库存变化。execute 仍可能更新收据的 updated_at，因此不是所有重复调用都没有任何数据库写入；幂等保证针对本章业务效果。

### 30.2.4 【进阶】先写三个最小规则测试

录入模型和下一节包入口以后，在工作区根执行：
```bash
cargo +1.92.0 test -p inventory --lib
```

应看到三个测试：终态稳定、取消或过早确认挡住迟到预留、占用与结算效果不同。它们不依赖 PostgreSQL，适合先检查状态表是否一致；不能据此证明 SQL 的条件扣减已经正确。

### 30.2.5 【精通】取消先到为何需要留下记录

设 Reserve 还在网络或队列里，Release 已先到达。若看到“没有预留”就直接返回且不记录，迟到的 Reserve 仍会创建 Held，让已取消流程重新占库存。

本章先插入 Pending，再把它转换成 Released，即使商品暂不存在也保留屏障。后续相同标识的 Reserve 只能观察 Released，不再扣减。这也是表中不强制要求取消记录立即引用一个存在商品行的原因。

### 30.2.6 【精通】过早 Confirm 的策略要明确

Confirm 在 Pending 上不会凭空制造成功，也不会扣库存，而是关闭为 Released，阻止迟到 Reserve。这是本书当前协议的明确选择，调用方不能把 Released 当作购买成功。

另一种系统可以返回顺序错误并等待协调器重试，但必须设计其迟到和取消语义。本章采用稳定关闭策略；后续协调器必须在确认 Held 后才请求 Confirm，并检查返回状态。方法名叫 Confirm 不表示返回值一定是 Confirmed。

### 30.2.7 【精通】确认以后不再用 Release 回滚

Confirmed 是本章终态。迟到的 Release 保持 Confirmed，不直接把已售出数量加回可售库存，避免一个取消重试让已确认购买再次可售。

如果业务需要退款退货，应该通过明确的退款、退货与入库流程处理，不复用这次未确认预留的释放动作。状态机的终态定义反映业务边界，不是把所有反向操作都禁止在整个系统之外。

### 30.3.2 【入门】完整第三次商品迁移

新增 services/catalog/migrations/0003_inventory_reservations.sql：
```sql
CREATE TABLE inventory_reservations (
    saga_id UUID PRIMARY KEY,
    product_id BIGINT NOT NULL CHECK (product_id > 0),
    quantity INT NOT NULL CHECK (quantity BETWEEN 1 AND 999),
    unit_price_cents BIGINT NOT NULL CHECK (unit_price_cents >= 0),
    state TEXT NOT NULL CHECK (
        state IN ('pending', 'held', 'confirmed', 'released', 'rejected')
    ),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX inventory_reservations_held_idx
  ON inventory_reservations(updated_at, saga_id)
  WHERE state = 'held';
```

不修改已经执行过的前两次迁移。saga_id 主键协调同一预留意图的并发，数量范围和状态 CHECK 防止明显非法值进入数据库。product_id 正数检查并不等价于存在性外键，本章保留不存在商品的取消屏障。

### 30.3.3 【进阶】为什么保存单价

预留请求携带调用方观察到的 unit_price_cents，真正扣减时要求商品当前价格仍一致。价格已经变化时，不静默按新价占用，也不以旧报价继续成交，而是记录 Rejected。

这不是完整报价系统。优惠、运费、税额、多币种与报价有效期还没有建模；本章只保证整数单价与当前商品价格的检查处于同一次条件 UPDATE，避免校验和扣减之间又改了价格。

### 30.3.4 【进阶】初始 Pending 通常不会单独提交

execute 在同一个事务中插入 Pending、锁定收据、决定下一状态并提交。正常调用不会先提交 Pending 再另外开事务扣库存。因此数据库里短暂插入 Pending 不是一次可供其他事务依赖的公开阶段完成信号。

如果管理员或其他代码直接写入了 Pending，find 可能读到它；状态机仍能处理，但这不属于正常入口保证。数据结构允许某值与业务通常会观察到某值，需要分开理解。

### 30.3.5 【精通】Held 索引不是自动过期机制

部分索引按 updated_at、saga_id 定位 held 记录，可辅助检查积压与人工对账。它不会运行定时器，也不会替你释放库存。

重复操作当前还会刷新 updated_at，因此不能直接把它当作不可延长的预留到期时间。将来若引入业务期限，应保存明确 expires_at、协调订单状态并设计竞争处理，不能仅凭一条“更新时间超过十分钟”的 SQL 就归还库存。

## 30.4 一笔事务完成预留、库存与事件

### 30.4.1 【入门】完整事务实现

创建 inventory/src/lib.rs：
```rust
pub mod model;

use messaging::{
    event::{Envelope, Snapshot},
    store,
};
use model::{Action, Command, State, Step};
use sqlx::{PgPool, Postgres, Transaction};
use std::time::Duration;
use uuid::Uuid;

#[derive(Debug, thiserror::Error)]
pub enum Error {
    #[error("invalid reservation input")]
    InvalidInput,
    #[error("saga identity reused with different reservation parameters")]
    IdentityConflict,
    #[error("stored reservation state is invalid")]
    CorruptState,
    #[error("reservation operation exceeded its budget; result may be unknown")]
    Deadline,
    #[error(transparent)]
    Database(#[from] sqlx::Error),
}

#[derive(Debug, Clone, sqlx::FromRow)]
pub struct Reservation {
    pub saga_id: Uuid,
    pub product_id: i64,
    pub quantity: i32,
    pub unit_price_cents: i64,
    pub state: String,
}

#[derive(sqlx::FromRow)]
struct ProductRow {
    id: i64,
    name: String,
    price_cents: i64,
    stock: i32,
    revision: i64,
    listed: bool,
}

async fn append_snapshot(tx: &mut Transaction<'_, Postgres>, row: ProductRow) -> Result<(), Error> {
    let event = Envelope::new(
        Snapshot {
            id: row.id,
            name: row.name,
            price_cents: row.price_cents,
            stock: row.stock,
            listed: row.listed,
        },
        row.revision,
    );
    store::append(tx, &event).await?;
    Ok(())
}

async fn inside_transaction(
    pool: &PgPool,
    command: &Command,
    action: Action,
) -> Result<State, Error> {
    let mut tx = pool.begin().await?;
    sqlx::query("SET LOCAL lock_timeout = '400ms'")
        .execute(&mut *tx)
        .await?;
    sqlx::query("SET LOCAL statement_timeout = '500ms'")
        .execute(&mut *tx)
        .await?;
    sqlx::query(
        "INSERT INTO inventory_reservations
         (saga_id,product_id,quantity,unit_price_cents,state)
         VALUES($1,$2,$3,$4,'pending') ON CONFLICT DO NOTHING",
    )
    .bind(command.saga_id)
    .bind(command.product_id)
    .bind(command.quantity)
    .bind(command.unit_price_cents)
    .execute(&mut *tx)
    .await?;
    let old = sqlx::query_as::<_, Reservation>(
        "SELECT saga_id,product_id,quantity,unit_price_cents,state
         FROM inventory_reservations WHERE saga_id=$1 FOR UPDATE",
    )
    .bind(command.saga_id)
    .fetch_one(&mut *tx)
    .await?;
    if (old.product_id, old.quantity, old.unit_price_cents)
        != (
            command.product_id,
            command.quantity,
            command.unit_price_cents,
        )
    {
        return Err(Error::IdentityConflict);
    }
    let next = match model::decide(State::from_stored(&old.state)?, action) {
        Step::TryHold => {
            let product = sqlx::query_as::<_, ProductRow>(
                "UPDATE products
                 SET stock=stock-$2,revision=revision+1,updated_at=now()
                 WHERE id=$1 AND stock >= $2 AND price_cents=$3
                   AND delisted_at IS NULL
                 RETURNING id,name,price_cents,stock,revision,true AS listed",
            )
            .bind(command.product_id)
            .bind(command.quantity)
            .bind(command.unit_price_cents)
            .fetch_optional(&mut *tx)
            .await?;
            if let Some(product) = product {
                append_snapshot(&mut tx, product).await?;
                State::Held
            } else {
                State::Rejected
            }
        }
        Step::GiveBack => {
            let product = sqlx::query_as::<_, ProductRow>(
                "UPDATE products
                 SET stock=stock+$2,revision=revision+1,updated_at=now()
                 WHERE id=$1
                 RETURNING id,name,price_cents,stock,revision,
                   delisted_at IS NULL AS listed",
            )
            .bind(command.product_id)
            .bind(command.quantity)
            .fetch_one(&mut *tx)
            .await?;
            append_snapshot(&mut tx, product).await?;
            State::Released
        }
        Step::Store(state) => state,
    };
    sqlx::query(
        "UPDATE inventory_reservations SET state=$2,updated_at=now()
         WHERE saga_id=$1",
    )
    .bind(command.saga_id)
    .bind(next.as_str())
    .execute(&mut *tx)
    .await?;
    tx.commit().await?;
    Ok(next)
}

pub async fn execute(pool: &PgPool, command: &Command, action: Action) -> Result<State, Error> {
    command.validate()?;
    tokio::time::timeout(
        Duration::from_millis(700),
        inside_transaction(pool, command, action),
    )
    .await
    .map_err(|_| Error::Deadline)?
}

pub async fn find(pool: &PgPool, saga_id: Uuid) -> Result<Option<Reservation>, Error> {
    if saga_id.is_nil() {
        return Err(Error::InvalidInput);
    }
    tokio::time::timeout(
        Duration::from_millis(700),
        sqlx::query_as::<_, Reservation>(
            "SELECT saga_id,product_id,quantity,unit_price_cents,state
             FROM inventory_reservations WHERE saga_id=$1",
        )
        .bind(saga_id)
        .fetch_optional(pool),
    )
    .await
    .map_err(|_| Error::Deadline)?
    .map_err(Error::from)
}
```

execute 是写操作入口，find 是按稳定标识查询收据的入口。Reservation 是数据库行，model::State 是经过解析的状态枚举，未知状态返回 CorruptState，不默认为可释放或可确认。

### 30.4.2 【进阶】事务顺序有意固定

inside_transaction 先开始事务并设置本地等待限制，接着 INSERT ... ON CONFLICT DO NOTHING 创建收据，再 SELECT ... FOR UPDATE 锁住对应收据，检查身份参数，然后才执行商品更新与 Outbox。

同标识请求在收据主键及行锁处协调；不同标识竞争同一商品，在商品 UPDATE 处协调。这个顺序给后续扩展提供统一锁顺序，避免有的路径先锁商品再锁收据，另一些路径反过来形成死锁环。

### 30.4.3 【进阶】条件扣减在 SQL 中完成

Reserve 的关键条件同时检查商品 id、stock &gt;= quantity、价格一致和未下架，再执行 stock=stock-quantity 与 revision+1。成功 RETURNING 的行才产生库存变化快照。

两个事务竞争最后一件时，等待者在并发更新结束后会依据可更新行状态重新判断条件，而不是继续相信应用之前读到的数字。这里依赖 PostgreSQL 对相应并发 UPDATE 的处理，不是“异步请求刚好没有同时运行”。

### 30.4.4 【进阶】零行更新为什么记录 Rejected

没有匹配行可能表示商品不存在、已下架、价格不符或库存不足。本章统一记录 Rejected，让这次稳定意图已经有确定结果；不会在未来补货后自动把同一标识变成 Held。

后续若需要向用户区分更细原因，可以设计在同一事务边界内保存明确拒绝类别。不能在事务外随便再查一次价格，就把后来观察到的状态当作当时失败的唯一原因。

### 30.4.5 【进阶】释放只加回收据的数量

Held 遇到 Release，商品 UPDATE 加回已经核对过的 quantity，递增修订，再生成快照。收据随后变为 Released。重复 Release 已不再走 GiveBack，因此不会每次重试都加库存。

释放不要求商品仍上架，否则商品下架后已有预留无法归还。RETURNING 读取真实 delisted_at 并形成 listed=false，避免释放动作把已经下架的商品事件错误标成可见。

### 30.4.6 【进阶】Outbox 仍使用同一事务

messaging::store::append 在本章改为 pub，接收调用者借来的 Transaction。inventory 先更新商品，再使用同一事务连接插入快照事件，最后更新收据并 commit。

append 不独立提交，也不重新取连接池。商品修订、库存、收据和事件一起回滚或一起成立。若 Outbox 因约束失败，测试必须同时验证库存没少、收据没留下，而不是只确认函数返回错误。

### 30.4.7 【精通】哪些动作需要新商品事件

成功 Reserve 改变可售库存，成功释放也改变，因此都增加商品修订并产生快照。Confirm 只改变预留收据，不再改变商品可售量，因此不额外产生商品快照。

这不表示整个系统不需要库存预留领域事件。本章尚未发布独立的 ReservationConfirmed 等事件，未来订单协调有自己的持久化流程；不要假设每一种状态变化都已经被 product.snapshot.v1 完整表达。

## 30.5 时间预算与结果未知

### 30.5.1 【入门】三种预算各限制什么

lock_timeout=400ms 限制锁等待，statement_timeout=500ms 限制事务内单条语句执行，外层 Tokio 700ms 包住整次操作，包括获取连接和多条 SQL。SET LOCAL 只在当前事务内生效，不污染连接池下一位使用者。

这些预算不是精确的实时调度承诺，也没有保证所有故障都以同一种错误先发生。本章在专用环境验证锁等待会及时失败，释放阻塞后可以用同一标识重试。

### 30.5.2 【进阶】数据库超时与外层 Deadline 不同

如果 PostgreSQL 先报告锁等待或语句超时，会得到 Error::Database；如果外层等待先结束，得到 Error::Deadline。不要在客户端仅按错误显示文字搜索“timeout”，再统一认为请求没有执行。

数据库事务中发生语句错误后要结束事务，不能继续把失败事务当作正常连接提交。当前实现通过错误返回和事务释放处理，不在失败事务内盲目再执行一次扣减。

### 30.5.3 【进阶】超时以后先查询同一收据

在提交附近失去响应时，调用方可能不知道是否成功。应保留 saga_id 和原参数，查询 find 或按协议重复原动作，从持久化状态恢复判断。

换一个新 UUID 重试无法和原操作汇聚，可能造成第二次占用。只有确认业务发起了新的独立尝试，才更换标识；“网络失败了”本身不是新业务意图。

### 30.5.4 【精通】整数溢出也必须完整回滚

stock 用 i32。若有人绕过正常入口把库存直接改到最大值，Held 释放再加一会触发数据库算术错误。本章不允许环绕为负数，也不把失败当作已经释放。

对应故障注入测试核对：收据仍为 Held，原商品版本和 Outbox 数量不变。这是验证坏状态下不继续破坏账目，不是正常业务补货方式。修复前必须找出绕过入口的原因，并对账确认实际可售量。

### 30.5.5 【精通】不自动重试整个业务流程

锁等待失败后，可以按同一意图重试事务，但重试要有上界并区分身份冲突、永久拒绝与暂时故障。Rejected 是持久业务结果，不能因为过了一秒就强行把它重置为 Pending。

本章 execute 不内置无界重试，也不自动改标识。服务治理章节会为可重试故障加入退避和预算；协调器还要考虑剩余业务期限，避免每一层都重新获得完整等待时间。

## 30.6 收紧旧的绝对库存更新入口

### 30.6.1 【入门】为什么必须现在处理旧路径

如果预留已把十件扣成九件，旧商品 PUT 又根据旧页面把 stock=10 写回，另一个订单就可能使用被重新放出来的一件。预留事务本身再严格，也挡不住系统里的第二条绕行写入。

因此本章提前收紧 Remote 商品更新：名称、价格仍可修改，但请求中的 stock 必须与锁定后的当前可售量相同。库存变化交给库存命令。创建新商品仍可以指定初始库存；后面的库存调整章节再增加有幂等凭据的补货与盘点入口。

### 30.6.2 【进阶】完整受限更新函数

替换 messaging/src/store.rs 中的 update，并增加 UpdateError。其他已经修复的 Outbox、收据与租约函数继续保留：
```rust
#[derive(Debug, thiserror::Error)]
pub enum UpdateError {
    #[error("product update cannot replace inventory; use inventory commands")]
    StockWriteForbidden,
    #[error(transparent)]
    Database(#[from] sqlx::Error),
}
pub async fn update(
    pool: &PgPool,
    id: i64,
    draft: &Draft,
) -> Result<Option<Envelope>, UpdateError> {
    let mut tx = pool.begin().await?;
    let current_stock: Option<i32> = sqlx::query_scalar(
        "SELECT stock FROM products WHERE id=$1 AND delisted_at IS NULL FOR UPDATE",
    )
    .bind(id)
    .fetch_optional(&mut *tx)
    .await?;
    let Some(current_stock) = current_stock else {
        return Ok(None);
    };
    if current_stock != draft.stock {
        return Err(UpdateError::StockWriteForbidden);
    }
    let row=sqlx::query_as::<_,Row>("UPDATE products SET name=$2,price_cents=$3,stock=$4,updated_at=now(),revision=revision+1 WHERE id=$1 AND delisted_at IS NULL RETURNING id,name,price_cents,stock,true AS listed,revision")
        .bind(id).bind(&draft.name).bind(draft.price_cents).bind(draft.stock).fetch_optional(&mut *tx).await?;
    let Some(row) = row else { return Ok(None) };
    let event = row.event();
    append(&mut tx, &event).await?;
    tx.commit().await?;
    Ok(Some(event))
}
```

先锁定目标商品并读取 stock，再比较输入，比较与后续写入都在同一事务内。不能先在事务外读取、比较，再执行更新，否则预留可能在中间改变可售量，原问题仍然存在。

### 30.6.3 【进阶】类型化拒绝与协议转换

StockWriteForbidden 是明确的业务入口拒绝，数据库故障是另一个分支。catalog 的 update_product 用同一七百毫秒预算等待，并把前者转换为 FailedPrecondition，后者按原数据库错误规则处理。

完整方法如下，替换 Catalog trait 实现中的对应方法：
```rust
    async fn update_product(
        &self,
        request: Request<UpdateProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let input = request.into_inner();
        validate_id(input.id)?;
        let value = validate_draft(&input.name, input.price_cents, input.stock)?;
        let draft = store::Draft {
            name: value.name().into(),
            price_cents: value.price_cents(),
            stock: value.stock(),
        };
        let event = tokio::time::timeout(
            Duration::from_millis(700),
            store::update(&self.pool, input.id, &draft),
        )
        .await
        .map_err(|_| Status::deadline_exceeded("catalog update budget exhausted"))?
        .map_err(|error| match error {
            store::UpdateError::StockWriteForbidden => {
                Status::failed_precondition("product update cannot replace inventory")
            }
            store::UpdateError::Database(error) => database_error(error),
        })?
        .ok_or_else(|| Status::not_found("product not found"))?;
        Ok(Response::new(snapshot_wire(event.payload)))
    }
```

RemoteProductRepo 已将 FailedPrecondition 转为 Conflict，因此公共 HTTP 当前返回 409。这个拒绝不应该隐藏成商品不存在，也不应该泄露数据库错误细节。

### 30.6.4 【精通】价格修改与库存预留怎样竞争

元数据更新锁商品行，库存扣减也需要更新同一行。它们被数据库协调：预留若拿到旧价格对应的行并先完成，可以形成旧价预留；价格先改变则旧价预留条件不成立，记录 Rejected。

已经 Held 的收据保留原 unit_price_cents，确认和释放核对的是这次意图的参数，不因商品后来涨价而擅自改变原收据。当前价格检查只用于新的 TryHold，后续结算还需要订单价格快照。

### 30.6.5 【精通】接口约束不能阻止高权限直写

本章关闭的是当前应用的普通商品更新路径。持有高权限数据库账户的人仍能直接执行 UPDATE，因此生产系统还需角色权限、受控迁移、审计和对账。

测试里的直接 SQL 专门用于构造竞争或坏数据，不是书中建议业务绕过库存模块的捷径。正确性结论必须带上前提：业务写入使用已经收口的接口，其他高权限写入受管理。

### 30.7.1 【入门】完整命令行程序

创建 inventory/src/bin/inventory-command.rs：
```rust
use anyhow::{Context, bail};
use inventory::{
    execute, find,
    model::{Action, Command},
};
use sqlx::postgres::PgPoolOptions;
use std::time::Duration;
use uuid::Uuid;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let args: Vec<String> = std::env::args().skip(1).collect();
    if args.len() != 2 && args.len() != 5 {
        bail!(
            "usage: inventory-command query UUID | reserve/confirm/release UUID PRODUCT_ID QUANTITY PRICE_CENTS"
        );
    }
    let saga_id = Uuid::parse_str(&args[1]).context("invalid saga UUID")?;
    let pool = PgPoolOptions::new()
        .max_connections(2)
        .acquire_timeout(Duration::from_millis(500))
        .connect(&std::env::var("DATABASE_URL").context("DATABASE_URL missing")?)
        .await?;
    if args[0] == "query" && args.len() == 2 {
        match find(&pool, saga_id).await? {
            Some(row) => println!(
                "{} {} {} {} {}",
                row.saga_id, row.product_id, row.quantity, row.unit_price_cents, row.state
            ),
            None => println!("not_found"),
        }
    } else if args.len() == 5 {
        let action = match args[0].as_str() {
            "reserve" => Action::Reserve,
            "confirm" => Action::Confirm,
            "release" => Action::Release,
            _ => bail!("unknown action"),
        };
        let command = Command {
            saga_id,
            product_id: args[2].parse().context("invalid product id")?,
            quantity: args[3].parse().context("invalid quantity")?,
            unit_price_cents: args[4].parse().context("invalid price")?,
        };
        println!("{}", execute(&pool, &command, action).await?.as_str());
    } else {
        bail!("invalid argument count for action");
    }
    pool.close().await;
    Ok(())
}
```

这是管理实验工具，直接连接商品库，不校验浏览器用户身份，不能作为公开网络入口。Reserve、Confirm、Release 都要求同一 UUID、商品 id、数量和单价；query 只需 UUID。

### 30.7.7 【精通】向投影观察库存变化

Confirm 不改变商品可售量，因此投影不会因为每次确认或重复调用都多一个商品快照。验证时应比较业务效果和具体版本，而不是用“消息越多越正确”作为标准。

### 30.8.2 【进阶】普通流程只是第一层

测试覆盖预留重试、确认重试、确认后释放不回退；释放只归还一次；取消先到和确认先到都阻止迟到预留。每次除了检查 State，还比较 stock、revision 与 Outbox 数量。

这样能防止某个实现虽然返回 Held，却重复扣了库存；也能发现确认时误增商品事件的问题。只比较返回枚举不足以证明持久化副作用正确。

### 30.8.3 【进阶】两个不同意图抢最后一件

测试通过 tokio::join! 并发执行两个不同 UUID 的 Reserve，初始可售一件。期望一个 Held、一个 Rejected，库存为零，只有成功扣减增加版本和事件。

哪个请求获胜不做固定要求，调度顺序不是业务承诺。测试核对结果集合及最终数据，避免把偶然的先后当成算法条件。

### 30.8.4 【进阶】同一个意图并发重复

另一用例同时执行相同 UUID 和参数，两次都可以观察 Held，但总共只扣一次、只产生一次对应版本变化。区别在于：前一个测试竞争资源，后一个测试汇聚同一意图。

它们覆盖不同的协调位置。只验证同 UUID 幂等，不能证明两个不同订单不会超卖；只验证库存不负，也不能证明相同订单不会被扣两次。

### 30.8.5 【精通】失败注入要核对所有原子成员

Outbox 约束故意拒绝新事件时，预留失败后库存、商品版本和事件数量保持原值，收据也不存在。删除测试约束后，用同一标识重试能够正常 Held。

锁等待测试持有商品行锁，等待超时后检查收据没有残留，再释放锁以相同标识重试。算术溢出测试则检查已存在 Held 收据不被错误改成 Released。失败发生在不同阶段，回滚证据也要对应阶段检查。

### 30.8.6 【精通】旧更新路径的回归测试

新增用例先预留一件使stock=9，再用旧stock=10调用商品更新，必须得到 StockWriteForbidden，版本和Outbox不变。使用当前stock=9修改名称可以成功，随后释放仍正确回到10。

这项测试防止本章只在新模块里自证正确，却保留原入口覆盖预留账的缺陷。应用写入口的闭合是业务不变量的一部分，不能拖到集成时才注意。

## 30.9 排查库存状态而非猜测数字

### 30.9.1 【入门】故障表

| 现象 | 先收集的证据 | 判断与修复 |
| --- | --- | --- |
| Reserve返回Rejected | 收据参数、商品当前状态和价格 | 是这次意图的稳定拒绝，不随补货自动改变 |
| 重试出现IdentityConflict | 同一UUID保存的三项参数 | 恢复原参数，不按新数量释放旧占用 |
| Release先到后Reserve不扣 | 已保存Released收据 | 正确取消屏障，不删除收据绕过 |
| Confirm返回Released | 是否曾成功Held、调用次序 | 当前策略不允许凭空确认，协调方须检查状态 |
| Confirm后Release库存不归还 | 收据是否Confirmed | 正常终态，退款退货需要独立流程 |
| 商品PUT返回409 | 请求stock与锁定后的可售值 | 禁止绝对库存覆盖，重新获取元数据并用库存能力变更数量 |
| 库存变化但投影暂未变化 | 两库revision、Outbox和worker | 异步传播存在延迟，按前章链路排查 |
| SQL锁等待超时 | 阻塞事务、持有锁与用时 | 释放或修复阻塞源，保留同一意图重试 |
| 查询超时或结果未知 | 原UUID、服务错误和持久化收据 | 先查状态，不换新UUID再次占用 |
| 释放溢出失败仍Held | 当前stock、直接写入与审计记录 | 保留占用证据并对账，不能强制改Released |
| Held长时间不消失 | 订单进度与显式业务期限 | 本章没有自动释放任务，不把更新时间当到期时间 |

### 30.9.2 【进阶】对账应看收据与事件

只看 stock=8 无法知道它来自哪笔预留，也无法区分补货、预留和未经允许的直写。诊断时需要对应预留参数、终态、商品修订与事件，必要时结合业务订单状态。

本章还没有完整仓储流水或订单表，因此不能声称只靠现有几列就能恢复全部历史实物流转。已建立的收据和Outbox是后续账目与恢复设计的基础，不能替代尚未实现的业务事实。

### 30.9.3 【精通】锁顺序和未来多商品扩展

当前一个操作只锁一个收据，再更新一个商品。未来若一次持有多个商品，应先定义稳定排序，例如按商品id递增锁定，所有路径一致执行，再考虑死锁检测与有界重试。

把本章函数循环调用多次，每次独立提交，会出现部分商品成功、部分失败。要么设计同库多行事务，要么设计可补偿的多步骤协议；不能把一个 for 循环称作整单原子预留。

## 30.10 分层练习与网络化衔接

### 30.10.1 【入门练习】解释预留与确认

商品可售十件，某意图预留三件，随后确认两次。最终可售量与状态是什么？再收到一次Release会怎样？

参考答案：预留后可售七件，状态Held；确认后Confirmed，两次确认均不再次扣减；Release保持Confirmed，可售仍七。该释放动作不承担已确认交易的退货入库职责。

### 30.10.2 【操作练习】重现一次取消屏障

用新UUID先Release再Reserve，参数完全相同，查询收据并比较商品库存与Outbox数量。

评分要点：Release记录Released，迟到Reserve不再占用；库存、商品修订和商品快照数量不因这两步改变。仅看到CLI两次退出成功不能证明屏障副作用正确。

### 30.10.3 【推理练习】两种并发为何都要测试

说明“两个UUID竞争最后一件”和“同UUID同时请求两次”各自验证什么，并给出只通过其中一种仍会漏掉的错误。

参考答案：前者验证共享商品数量的并发条件更新，后者验证同意图收据与幂等副作用。系统可能不同订单不超卖，却对同一订单重复扣两次；也可能同UUID幂等，但两个不同UUID都通过先读后写拿到最后一件。

### 30.10.4 【推理练习】陈旧商品页面的库存覆盖

管理员页面读到stock=10，随后订单已预留一件；管理员仅想改名称，却提交旧stock=10。为什么不能直接接受？本章如何处理？

参考答案：接受会把已占用的一件重新放进可售池。更新事务先锁商品读取当前stock=9，发现请求不相等，返回StockWriteForbidden并映射公共409。管理员需读取当前值再改元数据，数量变化走库存命令。

### 30.10.5 【扩展练习】为预留增加到期机制

列出引入expires_at需要新增的至少四类判断，说明为什么不能直接按updated_at批量释放。

参考要点：业务明确期限与时钟来源；确认与到期任务竞争；订单或支付进度核对；每次释放幂等且与库存/事件同事务；执行权限与审计；重启恢复和积压扫描。updated_at会被重复操作刷新，不能稳定代表原业务期限。

### 30.10.6 【衔接】下一章把同一状态机放到网络后面

现在库存有可测试规则、持久化收据和数据库并发边界，正常业务更新也不能再覆盖预留数量。已形成的是商品库内部的可靠事务能力，尚未形成跨服务调用协议、完整订单协调与支付补偿。

下一章继续使用这些状态和事务，增加库存RPC与网络故障处理。网络超时不会取消已经提交的库存事实，稳定标识、查询收据和终态语义将成为调用方恢复的依据。

可进一步对照 [PostgreSQL 17并发更新与隔离说明](https://www.postgresql.org/docs/17/transaction-iso.html)、[显式锁规则](https://www.postgresql.org/docs/17/explicit-locking.html) 和 [事务内等待限制配置](https://www.postgresql.org/docs/17/runtime-config-client.html)，结合本章实际事务顺序理解行为，避免把不同数据库的并发机制混用。

# 第 26 章 微服务拆分：商品服务与数据所有权

上一章得到了一份可生成 Rust 类型的商品契约，也用真实网络验证了调用与状态码。但演示服务器没有自己的持久化数据，进程退出后也没有业务可恢复。本章把 RustMall 的商品能力放进独立 catalog 进程，为它建立独立数据库、迁移命令、服务身份检查和健康状态。

这次拆分分两步进行。本章先建立能独立验证的商品服务；第 27 章再把公共 HTTP 请求接到它上面。完成本章时，旧 monolith 仍然连接自己的数据库。不要把两份实验数据同时当成生产商品真相，更不要让两个服务绕过接口共同修改同一张表。我们会把这个过渡状态写清楚，而不是仅凭目录里出现 services 就宣称拆分完成。

学完后，你应能从空数据库启动 catalog，解释一次商品请求经过的校验与事务边界，区分进程存活和业务就绪，并说明保留旧数据时需要怎样安排停写、复制、验证和切换。

## 26.1 从模块边界走到服务边界

### 26.1.1 【入门】先画出现在的调用链

原来的商品请求经过 HTTP 路由、业务校验和 PostgreSQL 仓储，运行在同一个 monolith 进程中。函数参数可以借用内存里的对象，错误可以沿 Rust 调用栈直接返回，数据库连接池也由同一进程管理。

拆分后的目标链路是“外部客户端 → HTTP 网关 → 商品 gRPC → 商品数据库”。本章只实现后两个节点。这样当数据库查询失败时，可以直接验证商品服务，不必先排除网关路由、用户 JWT 和 HTTP 错误转换的影响。

### 26.1.2 【入门】什么叫独立部署

独立部署是指商品服务可以作为自己的程序构建、启动和替换，拥有明确的配置入口与健康状态。它不是“每个函数一个容器”，也不要求所有服务立刻使用不同语言。

例如商品查询吞吐上升，可以单独增加 catalog 实例；但各实例仍会竞争同一个商品数据库的连接与资源。增加进程数量不能无限增加存储容量，本章为每实例设置连接上限，后面的容量规划还要乘上副本数。

### 26.1.3 【进阶】数据所有权到底约束什么

商品服务拥有商品数据，意味着其他服务通过商品接口请求能力，不能直接执行商品表的 UPDATE 来绕过业务规则。接口是授权、校验、事务和演进的共同入口。

数据库地址分开只是帮助落实边界的一种方法。如果两个服务仍拿着彼此数据库的高权限账户，目录拆得再整齐，也没有建立可靠的写入约束。实验使用单一测试账户便于学习；生产权限分工会在 PostgreSQL 深入章节继续落实。

### 26.1.4 【进阶】为什么先选商品能力

商品具有明确的标识、名称、价格、库存和上下架状态，前面的章节已经实现相应领域对象与仓储。用熟悉业务学习新的进程边界，可以看清到底新增了哪些复杂度。

这并不表示商品与库存永远属于同一个边界。本阶段保留既有 stock 字段与更新方法；后面的库存预留、并发扣减和写入口收口会继续调整职责。不能提前把尚未实现的订单一致性归功于本章的商品 CRUD。

### 26.1.5 【精通】拆分会引入新的失败状态

本地调用通常能直接观察函数返回；远程调用可能遇到连接失败、身份拒绝、服务执行超时和响应丢失。尤其是写操作，客户端没有收到成功并不等于数据库没有提交。

设创建商品的 INSERT 已提交，响应在网络中丢失，客户端重试同一个创建请求。本章接口没有业务幂等键，第二次可能创建另一个商品。因此本章不添加“所有失败都重试”的循环，后面会结合幂等记录与可靠消息讨论可重试条件。

### 26.1.6 【精通】何时不应该拆

如果业务边界仍经常一起变化、团队只有一个发布节奏、主要瓶颈是慢 SQL，新增网络服务可能放大排查成本，而没有带来收益。先改善模块结构与查询，往往比部署更多进程更有效。

RustMall 拆分是为了系统学习契约、持久化边界与故障治理。评价这次拆分，应看是否形成清晰的数据入口和可验证行为，而不是看进程数量是否足够多。

## 26.2 先做一个最小的边界练习

### 26.2.1 【入门】从可验证的行为开始

进入第 25 章的完整 RustMall 工作区，先运行已有契约测试。下面的命令在工作区根目录执行：
```bash
cargo +1.92.0 test --locked -p contracts
```

应看到消息编解码与真实本地传输测试通过。这里的演示对象没有数据库，作用是确认契约与工具链。若这一步失败，先修复 contracts，不要把尚未构建成功的协议问题与 PostgreSQL 混在一起。

### 26.2.2 【入门】预测三个输入的结果

在实际编写 SQL 前，先写下预期：id 为零属于输入不合法，返回 InvalidArgument；合法但不存在的 id 返回 NotFound；数据库连接断开属于服务端故障，不应伪装成商品不存在。

这三个状态不是界面文案的同义词。它们决定调用方是否应该改参数、展示未找到，还是记录依赖故障。客户端应比较 tonic::Code，不能搜索错误显示字符串来判断状态。

### 26.2.3 【进阶】建立可单测的输入边界

稍后 lib.rs 中的 validate_id、validate_page 和 validate_draft 都是同步函数。它们不需要数据库与运行时，因此可以在毫秒级单测中检查范围和归一化行为。

validate_draft 复用 common::product::NewProduct::try_new。这里不重新写一份“差不多”的长度与金额判断；否则 HTTP 路径与 gRPC 路径可能对同一名称作出不同结论。复用的是已经学过的业务规则，不是把传输结构当作合法领域对象。

### 26.2.4 【进阶】本章依赖和执行环境

继续使用 Rust 1.92.0、SQLx 0.8 与 tonic 0.14.6。PostgreSQL 实验使用 17 系列，数据库端口为本机 55433，服务监听本机 50051。Docker 必须已启动；端口被占用时要先确认占用者，不能直接删除陌生容器。

本章以原生 Rust 进程连接 Docker 中的数据库，便于观察服务端日志。前面的 Dockerfile 仍构建 monolith；仅增加一个 Rust 包不会自动产生 catalog 容器镜像。完整微服务的镜像、编排与交付会继续补齐。

### 26.3.3 【入门】完整首次迁移

创建 services/catalog/migrations/0001_catalog.sql：
```sql
-- Fresh catalog database only. Never run against monolith migration history.
CREATE TABLE products (
   id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
   name VARCHAR(100) NOT NULL CHECK (char_length(btrim(name)) BETWEEN 1 AND 100),
   price_cents BIGINT NOT NULL CHECK (price_cents >= 0),
   stock INT NOT NULL CHECK (stock >= 0),
   created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
   updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
   delisted_at TIMESTAMPTZ
);
CREATE INDEX products_listed_created_idx ON products(created_at DESC,id DESC)
   WHERE delisted_at IS NULL;
```

它只用于新的 rustmall_catalog 数据库。旧 monolith 的迁移历史可能已经拥有相同序号；把这份文件塞进旧历史会造成校验冲突，或者试图重复创建 products。数据库迁移编号是各自历史中的位置，不是全书统一的章节编号。

### 26.3.4 【进阶】逐段理解约束

GENERATED ALWAYS AS IDENTITY 为普通 INSERT 生成商品编号，主键同时防止重复。金额以 BIGINT 保存最小货币单位“分”，避免浮点数舍入；库存用 INT，与既有契约的 i32 对应。NOT NULL 防止缺失值绕过比较条件。

名称的 CHECK 约束限制 PostgreSQL 字符长度，并拒绝由普通空格组成的空名称。应用的 Rust trim 处理范围更广，因此数据库约束与领域构造器不能互相替代。读取历史数据时还要重新构造领域对象，后文会测试这个差别。

### 26.3.5 【进阶】为什么使用软下架

delisted_at 为 NULL 表示可见，下架写入时间而不删除行。这样商品标识和原始记录仍存在，未来订单可以保存购买快照，运维也能追查状态变化。

当前查询显式过滤 delisted_at IS NULL。软下架不是自动权限机制，也不是数据库会替你过滤的特殊类型；少写一次条件，就可能把下架商品重新暴露给调用者。

### 26.3.6 【进阶】索引与稳定排序

列表按 created_at DESC,id DESC 排序。多个商品可能在同一事务里得到相同时间，仅按时间排序会使它们的相对顺序没有保证。增加唯一 id 作为第二排序键，能使当前数据集中的分页次序明确。

部分索引只覆盖未下架商品，方向与列表排序匹配。但 OFFSET 很大仍需跳过大量行，稳定排序也不能阻止不同请求之间的新插入改变页边界。游标分页与执行计划将在数据库章节进一步讨论。

### 26.3.7 【精通】迁移命令与业务启动分离

build.rs 的完整内容如下：
```rust
fn main() {
    println!("cargo:rerun-if-changed=migrations");
}
```

catalog-migrate.rs 的完整内容如下：
```rust
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let pool = sqlx::PgPool::connect(&std::env::var("DATABASE_URL")?).await?;
    sqlx::migrate!().run(&pool).await?;
    pool.close().await;
    Ok(())
}
```

SQLx migrate! 把对应迁移嵌入二进制。build.rs 提醒 Cargo 迁移目录发生变化，避免只改 SQL 却沿用旧构建结果。业务 main 不执行迁移；部署时先运行迁移并确认成功，再放行业务实例。每个副本自行修改结构，会让失败来源和发布顺序更难判断。

迁移失败必须保留原始证据并停止后续发布，不要删掉 `_sqlx_migrations` 让工具“重新来过”。这个表记录的是已发生的结构变更，删除记录不会撤销真正执行过的 DDL。

## 26.4 在 Rust 类型与 SQL 之间建立边界

### 26.4.1 【入门】完整业务实现

创建 services/catalog/src/lib.rs。先完整录入，再按下面的调用路径逐段阅读。
```rust
use common::ids::ProductId;
use common::product::{NewProduct, Product as DomainProduct};
use contracts::catalog::catalog_server::Catalog;
use contracts::catalog::*;
use sqlx::PgPool;
use std::future::Future;
use std::time::Duration;
use tonic::{Request, Response, Status};

#[derive(Clone)]
pub struct CatalogApi {
    pool: PgPool,
}
impl CatalogApi {
    pub fn new(pool: PgPool) -> Self {
        Self { pool }
    }
}
#[derive(sqlx::FromRow)]
struct Row {
    id: i64,
    name: String,
    price_cents: i64,
    stock: i32,
}
impl Row {
    fn wire(self) -> Result<Product, Status> {
        let product = DomainProduct::try_new(
            ProductId::new(self.id),
            &self.name,
            self.price_cents,
            self.stock,
        )
        .map_err(|_| Status::internal("stored product violates domain rules"))?;
        Ok(Product {
            id: product.id().get(),
            name: product.name().into(),
            price_cents: product.price_cents(),
            stock: product.stock(),
        })
    }
}
fn database_error(error: sqlx::Error) -> Status {
    if let Some(db) = error.as_database_error()
        && matches!(db.code().as_deref(), Some("23505" | "23503"))
    {
        return Status::failed_precondition("product conflicts with stored data");
    }
    tracing::error!(%error, "catalog database failure");
    Status::internal("catalog database failure")
}
async fn bounded<T>(future: impl Future<Output = Result<T, sqlx::Error>>) -> Result<T, Status> {
    tokio::time::timeout(Duration::from_millis(700), future)
        .await
        .map_err(|_| Status::deadline_exceeded("catalog query budget exhausted"))?
        .map_err(database_error)
}
pub fn validate_draft(name: &str, price: i64, stock: i32) -> Result<NewProduct, Status> {
    NewProduct::try_new(name, price, stock).map_err(Status::invalid_argument)
}
pub fn validate_id(id: i64) -> Result<i64, Status> {
    if id <= 0 {
        return Err(Status::invalid_argument("id must be positive"));
    }
    Ok(id)
}
pub fn validate_page(limit: i64, offset: i64) -> Result<(), Status> {
    if !(1..=100).contains(&limit) || offset < 0 {
        return Err(Status::invalid_argument(
            "limit must be 1..100 and offset nonnegative",
        ));
    }
    Ok(())
}

#[tonic::async_trait]
impl Catalog for CatalogApi {
    async fn get_product(
        &self,
        request: Request<GetProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let id = validate_id(request.into_inner().id)?;
        let row = bounded(sqlx::query_as::<_, Row>(
             "SELECT id,name,price_cents,stock FROM products WHERE id=$1 AND delisted_at IS NULL"
         ).bind(id).fetch_optional(&self.pool)).await?
             .ok_or_else(|| Status::not_found("product not found"))?;
        Ok(Response::new(row.wire()?))
    }
    async fn list_products(
        &self,
        request: Request<ListProductsRequest>,
    ) -> Result<Response<ListProductsResponse>, Status> {
        let page = request.into_inner();
        validate_page(page.limit, page.offset)?;
        // One repeatable-read snapshot keeps count and items coherent.
        let result = async {
            let mut tx = self.pool.begin().await?;
            sqlx::query("SET TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY")
                .execute(&mut *tx)
                .await?;
            let items = sqlx::query_as::<_, Row>(
                 "SELECT id,name,price_cents,stock FROM products WHERE delisted_at IS NULL ORDER BY created_at DESC,id DESC LIMIT $1 OFFSET $2"
             ).bind(page.limit).bind(page.offset).fetch_all(&mut *tx).await?;
            let total: i64 =
                sqlx::query_scalar("SELECT count(*) FROM products WHERE delisted_at IS NULL")
                    .fetch_one(&mut *tx)
                    .await?;
            tx.commit().await?;
            Ok::<_, sqlx::Error>((items, total))
        };
        let (rows, total) = bounded(result).await?;
        let items = rows.into_iter().map(Row::wire).collect::<Result<_, _>>()?;
        Ok(Response::new(ListProductsResponse { items, total }))
    }
    async fn create_product(
        &self,
        request: Request<CreateProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let input = request.into_inner();
        let draft = validate_draft(&input.name, input.price_cents, input.stock)?;
        let row = bounded(sqlx::query_as::<_, Row>(
             "INSERT INTO products(name,price_cents,stock) VALUES($1,$2,$3) RETURNING id,name,price_cents,stock"
         ).bind(draft.name()).bind(draft.price_cents()).bind(draft.stock()).fetch_one(&self.pool)).await?;
        Ok(Response::new(row.wire()?))
    }
    async fn update_product(
        &self,
        request: Request<UpdateProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let input = request.into_inner();
        validate_id(input.id)?;
        let draft = validate_draft(&input.name, input.price_cents, input.stock)?;
        let row = bounded(sqlx::query_as::<_, Row>(
             "UPDATE products SET name=$2,price_cents=$3,stock=$4,updated_at=now() WHERE id=$1 AND delisted_at IS NULL RETURNING id,name,price_cents,stock"
         ).bind(input.id).bind(draft.name()).bind(draft.price_cents()).bind(draft.stock()).fetch_optional(&self.pool)).await?
             .ok_or_else(|| Status::not_found("product not found"))?;
        Ok(Response::new(row.wire()?))
    }
    async fn delist_product(
        &self,
        request: Request<GetProductRequest>,
    ) -> Result<Response<DelistProductResponse>, Status> {
        let id = validate_id(request.into_inner().id)?;
        let result = bounded(sqlx::query(
             "UPDATE products SET delisted_at=now(),updated_at=now() WHERE id=$1 AND delisted_at IS NULL"
         ).bind(id).execute(&self.pool)).await?;
        if result.rows_affected() == 0 {
            return Err(Status::not_found("product not found"));
        }
        Ok(Response::new(DelistProductResponse {}))
    }
}

#[cfg(test)]
mod tests {

    #[test]

        assert!(validate_id(1).is_ok());
        assert_eq!(
            validate_id(0).unwrap_err().code(),
            tonic::Code::InvalidArgument
        );
        assert!(validate_id(-1).is_err());
    }
    #[test]

        assert!(validate_page(100, 0).is_ok());
        assert!(validate_page(101, 0).is_err());
        assert!(validate_page(1, -1).is_err());
    }
    #[test]
    fn validation_reuses_the_book_domain() {
        assert_eq!(validate_draft(" 键盘 ", 19900, 10).unwrap().name(), "键盘");
        assert!(validate_draft(" ", 19900, 10).is_err());
        assert!(validate_draft("键盘", -1, 10).is_err());
        assert!(validate_draft("键盘", 19900, -1).is_err());
    }
}
```

CatalogApi 持有 PgPool。clone 池句柄共享连接管理器，不是复制十条新连接；多个请求可以通过池取得不同连接。不要为每次 RPC 重新建立一个连接池，否则连接预算、握手成本与关闭行为都会失去统一管理。

### 26.4.2 【入门】为什么有 Row、领域 Product 和协议 Product

Row 描述数据库查询返回的列。领域 Product 描述符合业务不变量的商品。contracts::catalog::Product 描述发给远端的消息。三个类型名称相近，信任程度和职责不同。

代码把领域 Product 起别名 DomainProduct，避免与通配导入的协议 Product 混淆。Row::wire 先调用领域构造器，再使用只读访问器构造协议对象；数据库里存在一行，不等于这行已经适合对外提供。

### 26.4.3 【进阶】读取也需要防守

普通写路径已使用 NewProduct，为什么读取还要校验？因为数据可能来自早期版本、管理员 SQL、导入脚本或其他未遵守当前规则的路径。例如某个 Unicode 空白在 PostgreSQL 默认 btrim 后仍存在，而 Rust trim 会把它识别为空白。

这种行应返回 Internal，并由服务端诊断，不能包装成正常商品。本章的重建检查覆盖名称、金额和库存等现有领域规则；不要把有限规则误称为对所有历史数据异常的完整审计。

### 26.4.4 【进阶】参数绑定保护哪一层

SQL 中的 $1、$2 等占位符由 bind 提供值，名称中即使含有引号也作为数据传输。把名称用字符串拼接到 SQL 里，会破坏语法边界并可能引入注入。

绑定值不能代替业务校验，也不能随意替换表名或排序关键字。本章排序规则由固定 SQL 给出，limit 与 offset 则在验证后作为参数绑定。若以后允许用户选择排序，需要把有限选项映射到明确的 SQL 片段。

### 26.4.5 【进阶】fetch_optional 与 fetch_one 的选择

按 id 查询可能没有行，因此使用 fetch_optional，再把 None 转为 NotFound。更新也可能没有匹配的未下架商品，处理方式相同。创建使用 INSERT ... RETURNING，一旦 SQL 成功就应得到新行，因此使用 fetch_one。

不能把所有 sqlx::Error 都转换成 NotFound。连接断开、类型解析失败和表不存在都属于另一类问题，把它们隐藏成未找到会诱导用户重复创建，并使监控失去故障信号。

### 26.4.6 【进阶】数据库错误如何跨过服务边界

database_error 将 SQLSTATE 23505 与 23503 映射为 FailedPrecondition，其他数据库错误记录在服务端并向外返回通用 Internal。当前基本表不依赖这些冲突完成正常流程，这个分支为受约束写入保留一致处理。

SQLSTATE 表达错误类别；数据库约束名、SQL 原文、连接地址和堆栈不应直接成为公共状态消息。日志也需要访问控制和脱敏，通用状态并不表示可以把完整数据库错误随意展示给外部调用者。

### 26.4.7 【精通】软下架的成功语义

下架使用 UPDATE 并检查 rows_affected。第一下成功会写时间；第二次请求找不到未下架行，返回 NotFound。数据库不会重复改变结果，但两次响应状态不同。

所以“重复执行后的资源状态相同”与“每次返回同样状态”是两种性质。调用方重试时要理解接口契约；如果业务要求重复下架也返回成功，需要明确调整规则与测试，不能只在网关吞掉 NotFound。

## 26.5 用事务定义一次列表的观察范围

### 26.5.1 【入门】items 与 total 为什么可能矛盾

假设先查询当前页得到十个商品，另一事务下架其中一个，随后查询总数。如果两个查询各自看到不同提交状态，items 与 total 就可能来自不同的数据时刻。

这不是 SQLx 自动排序就能解决的问题。排序控制同一次查询中的行顺序；事务隔离控制多个查询能够观察哪些已提交变化。两者处理的是不同维度。

### 26.5.2 【进阶】READ COMMITTED 的语句快照

PostgreSQL 默认 READ COMMITTED 下，每条命令取得自己的观察快照。把两个 SELECT 简单放进默认事务，也不保证两者读取同一时刻的状态。

例如列表先读到五条，其他事务插入一条，随后 count 读到六条。两条 SQL 都正确执行，却不能共同表示一个一致的分页观察。这类问题经常被误认为分页计算写错。

### 26.5.3 【进阶】REPEATABLE READ READ ONLY

本章在事务的业务查询之前设置 REPEATABLE READ READ ONLY。随后 items 和 count 使用同一个事务，因此基于同一快照。READ ONLY 表达这里只应查询，防止不小心混入数据修改。

代码把 begin、设置隔离级别、两次查询和 commit 放进同一个 async 块，再把整个块交给 bounded。若分别给两次 SELECT 各 700 毫秒，整体等待可能超过设计预算；现在事务整个过程共用本地查询预算。

### 26.5.4 【进阶】为什么执行器写成 &amp;mut *tx

tx 是 SQLx 的 Transaction，不是一个可以随意同时借出的连接。`&mut *tx` 通过解引用取得底层连接的可变借用，给当前查询使用。await 完成后，下一条 SQL 才再次借用它。

不要把同一个事务的两条查询通过 join! 强行并发。一个连接上的事务有明确顺序；Rust 的可变借用限制也提醒我们，不能让两个独立执行过程同时拥有同一连接的独占访问权。

### 26.5.5 【精通】快照一致性的代价与边界

长事务会延长旧版本数据必须保留的时间，因此本章限制列表大小并设置预算。一次列表事务的快照不会跨越后续 RPC，也不保证订单、用户和商品在各自数据库里共享同一时刻。

反例是先调用商品列表，再过五秒调用下一页。即使每次内部都使用 REPEATABLE READ，两次请求仍有不同快照。需要稳定导出整个数据集时，应设计专用导出任务或其他一致性边界，不能依赖普通分页接口的偶然时序。

## 26.6 启动、身份、健康与关闭

### 26.6.1 【入门】完整启动入口

创建 services/catalog/src/main.rs：
```rust
use anyhow::Context;
use contracts::catalog::catalog_server::CatalogServer;
use platform::ShutdownBudget;
use sqlx::postgres::PgPoolOptions;
use std::time::Duration;
use tokio_util::sync::CancellationToken;
use tonic::{Request, Status, transport::Server};
use tonic_health::ServingStatus;

async fn signal() {
    #[cfg(unix)]
    {
        let mut term = tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("install SIGTERM handler");
        tokio::select! { _ = tokio::signal::ctrl_c() => {}, _ = term.recv() => {} }
    }
    #[cfg(not(unix))]
    {
        tokio::signal::ctrl_c()
            .await
            .expect("install ctrl-c handler");
    }
}
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    tracing_subscriber::fmt()
        .with_env_filter("info,catalog=debug")
        .init();
    let key = std::env::var("RUSTMALL_CATALOG_TOKEN").context("catalog token missing")?;
    anyhow::ensure!(
        key.len() >= 32 && key.bytes().all(|byte| byte.is_ascii_graphic()),
        "catalog token must be >=32 visible ASCII bytes"
    );
    let url = std::env::var("DATABASE_URL").context("catalog database missing")?;
    let pool = PgPoolOptions::new()
        .max_connections(10)
        .acquire_timeout(Duration::from_millis(500))
        .connect(&url)
        .await?;
    let api = catalog::CatalogApi::new(pool.clone());
    let auth = move |request: Request<()>| -> Result<Request<()>, Status> {
        match request
            .metadata()
            .get("x-rustmall-service-token")
            .and_then(|v| v.to_str().ok())
        {
            Some(value) if value == key => Ok(request),
            _ => Err(Status::unauthenticated("service identity required")),
        }
    };
    let (reporter, health) = tonic_health::server::health_reporter();
    reporter
        .set_service_status("liveness", ServingStatus::Serving)
        .await;
    reporter
        .set_service_status("readiness", ServingStatus::NotServing)
        .await;
    let token = CancellationToken::new();
    let health_pool = pool.clone();
    let health_token = token.clone();
    let mut checker = tokio::spawn(async move {
        loop {
            let ok = matches!(
                tokio::time::timeout(
                    Duration::from_millis(500),
                    sqlx::query("SELECT 1").execute(&health_pool)
                )
                .await,
                Ok(Ok(_))
            );
            reporter
                .set_service_status(
                    "readiness",
                    if ok {
                        ServingStatus::Serving
                    } else {
                        ServingStatus::NotServing
                    },
                )
                .await;
            tokio::select! {
                () = health_token.cancelled() => break,
                () = tokio::time::sleep(Duration::from_secs(2)) => {}
            }
        }
    });
    let addr = std::env::var("CATALOG_ADDR")
        .unwrap_or_else(|_| "127.0.0.1:50051".into())
        .parse()?;
    let server = Server::builder()
        .add_service(health)
        .add_service(CatalogServer::with_interceptor(api, auth))
        .serve_with_shutdown(addr, token.clone().cancelled_owned());
    tokio::pin!(server);
    let (result, budget) = tokio::select! {
       result = &mut server => {
            token.cancel();
            (result.context("gRPC server failed"), ShutdownBudget::new(Duration::from_secs(20)))
       },
       () = signal() => {
            token.cancel();
            let budget = ShutdownBudget::new(Duration::from_secs(20));
            let result = match budget.wait("gRPC", &mut server).await {
                Ok(result) => result.context("gRPC server failed"),
                Err(error) => { checker.abort(); return Err(error); }
            };
            (result, budget)
       }
    };
    match budget.wait("health checker", &mut checker).await {
        Ok(result) => result?,
        Err(error) => {
            checker.abort();
            return Err(error);
        }
    }
    budget.wait("database", pool.close()).await?;
    result
}
```

配置在启动时读取。数据库缺失、令牌太短或监听地址不合法会使启动失败；不要静默改连默认生产数据库，也不要在缺令牌时退化为允许所有调用。默认监听 127.0.0.1 限制本章原生实验的暴露范围。

### 26.6.2 【入门】连接池上限与获取预算

max_connections(10) 限制每个服务进程的连接池容量，acquire_timeout(500ms) 限制取得连接时的等待。两者不是数据库端的最大连接配置，也不是每条 SQL 的执行超时。

假设部署六个副本，仅这项配置就可能占用六十条连接，迁移、后台任务和管理工具还要另外计算。池等待升高既可能是池太小，也可能是慢查询占住连接，不能只通过不断增大上限解决。

### 26.6.3 【进阶】服务身份与最终用户权限

业务拦截器读取 x-rustmall-service-token，并与启动时加载的令牌比较。值缺失或不匹配返回 Unauthenticated。令牌至少 32 个可见 ASCII 字节，生成器提供随机值，不使用书中统一口令。

这个令牌证明调用者掌握某个服务凭据，不能证明最终用户具有管理员角色。第 27 章还要在 HTTP 边界验证用户身份并保留管理权限检查。拥有服务令牌的调用者当前能访问全部商品 RPC，所以凭据必须只交给需要它的服务。

### 26.6.4 【进阶】明文实验的使用边界

本章默认在本机回环地址使用 HTTP/2 明文传输。令牌不是加密方案，不适合直接通过不可信网络发送。跨主机部署时应结合 TLS、服务身份与网络访问限制，不能把地址改成 0.0.0.0 就视为部署完成。

配置文件同样不是秘密管理系统。它帮助本地复现，生产环境需要控制分发、读取权限、轮换和撤销。当前进程只在启动时读一次令牌；修改文件不会自动更新已经运行的服务。

### 26.6.5 【进阶】liveness 与 readiness 分别回答什么

健康服务使用标准 gRPC Health 协议，查询时需要指定 service 名称。liveness 在进程建立后标记为 Serving；readiness 先是 NotServing，后台实际执行 SELECT 1 成功才改为 Serving。

数据库暂时不可用时，应让流量停止进入未就绪实例，而不是因为依赖故障不断重启仍活着的程序。这里的健康服务没有挂业务拦截器，是为了让受控网络中的探针查询状态；并不表示商品 RPC 可以绕过身份检查。

### 26.6.6 【进阶】健康检查不是数据库正确性证明

SELECT 1 能验证基本查询连通性，却不读取 products。因此表没迁移、特定商品数据损坏或业务查询缺少索引时，readiness 仍可能是 Serving。

后台检查每轮最多等待 500 毫秒，两轮之间休眠两秒，状态存在观察延迟。这些数字是实验预算，不是从业务 SLO 推导的配置。部署验收仍必须运行一次真实业务路径。

### 26.6.7 【精通】多层等待预算如何配合

服务内部 SQL 操作整体预算为 700 毫秒；客户端给每次请求设置一秒 grpc-timeout，并另有连接与本地传输等待上限。通常应给外层留出网络、排队和解码余量，但数值关系不能保证所有调度情况下都按同一顺序超时。

tokio::time::timeout 到时会停止等待被包裹的 future，并不提供“已提交写入一定回滚”的证明。连接上查询取消与事务清理也有各自的执行过程。客户端收到 DeadlineExceeded 后，仍不能安全地无条件重试创建商品。

### 26.6.8 【精通】共享关闭预算

收到正常终止信号后，CancellationToken 通知 gRPC server 停止接收并等待已有工作，后台检查器退出，随后关闭连接池。platform::ShutdownBudget 为这些步骤共享二十秒期限，避免每一步各等二十秒导致总时长不断相加。

主函数也处理 server 自己失败的路径，通知后台任务退出。若等待任务超时，调用 abort；正常路径还检查 JoinHandle 中的任务结果。信号注册异常属于进程级错误，当前入口使用明确失败而不是悄悄继续运行。

不要将“本机 SIGTERM 能退出”推广成“集群发布不会中断请求”。后者还取决于探针、流量摘除、终止宽限时间以及有负载时的真实实验，本章只记录已经执行的范围。

### 26.7.4 【入门】运行真实客户端

创建 services/catalog/examples/smoke.rs：
```rust
use anyhow::{Context, ensure};
use contracts::catalog::{catalog_client::CatalogClient, *};
use std::time::Duration;
use tonic::metadata::{Ascii, MetadataValue};
use tonic::transport::Endpoint;
use tonic::{Code, Request};

fn request<T>(value: T, key: &MetadataValue<Ascii>) -> Request<T> {
    let mut request = Request::new(value);
    request.set_timeout(Duration::from_secs(1));
    request
        .metadata_mut()
        .insert("x-rustmall-service-token", key.clone());
    request
}

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let arguments: Vec<String> = std::env::args().skip(1).collect();
    let expect_unauthenticated = match arguments.as_slice() {
        [] => false,
        [flag] if flag == "--expect-unauthenticated" => true,
        _ => anyhow::bail!("usage: smoke [--expect-unauthenticated]"),
    };
    let endpoint = std::env::var("RUSTMALL_CATALOG_ENDPOINT")
        .unwrap_or_else(|_| "http://127.0.0.1:50051".into());
    let key: MetadataValue<Ascii> = std::env::var("RUSTMALL_CATALOG_TOKEN")
        .context("catalog token missing")?
        .parse()
        .context("token is not valid metadata")?;
    let channel = Endpoint::from_shared(endpoint)?
        .connect_timeout(Duration::from_secs(2))
        .timeout(Duration::from_secs(2))
        .connect()
        .await?;
    let mut health = tonic_health::pb::health_client::HealthClient::new(channel.clone());
    tokio::time::timeout(Duration::from_secs(3), async {
        loop {
            let reply = health
                .check(Request::new(tonic_health::pb::HealthCheckRequest {
                    service: "readiness".into(),
                }))
                .await?
                .into_inner();
            if reply.status
                == tonic_health::pb::health_check_response::ServingStatus::Serving as i32
            {
                break;
            }
            tokio::time::sleep(Duration::from_millis(100)).await;
        }
        Ok::<_, tonic::Status>(())
    })
    .await
    .context("readiness did not become serving")??;
    let mut client = CatalogClient::new(channel);
    if expect_unauthenticated {
        let error = client
            .get_product(request(GetProductRequest { id: 1 }, &key))
            .await
            .expect_err("wrong identity must not succeed");
        ensure!(error.code() == Code::Unauthenticated);
        println!("PASS identity rejection code={}", error.code() as i32);
        return Ok(());
    }
    let created = client
        .create_product(request(
            CreateProductRequest {
                name: "  章节验证键盘  ".into(),
                price_cents: 19_900,
                stock: 10,
            },
            &key,
        ))
        .await?
        .into_inner();
    ensure!(created.id > 0 && created.name == "章节验证键盘");
    ensure!(created.price_cents == 19_900 && created.stock == 10);
    let found = client
        .get_product(request(GetProductRequest { id: created.id }, &key))
        .await?
        .into_inner();
    ensure!(found == created);
    let page = client
        .list_products(request(
            ListProductsRequest {
                limit: 2,
                offset: 0,
            },
            &key,
        ))
        .await?
        .into_inner();
    ensure!(page.total >= 1 && page.items.len() <= 2);
    let updated = client
        .update_product(request(
            UpdateProductRequest {
                id: created.id,
                name: "静音章节键盘".into(),
                price_cents: 20_000,
                stock: 8,
            },
            &key,
        ))
        .await?
        .into_inner();
    ensure!(updated.name == "静音章节键盘" && updated.price_cents == 20_000 && updated.stock == 8);
    client
        .delist_product(request(GetProductRequest { id: created.id }, &key))
        .await?;
    let error = client
        .get_product(request(GetProductRequest { id: created.id }, &key))
        .await
        .expect_err("delisted product must be invisible");
    ensure!(error.code() == Code::NotFound);
    println!("PASS catalog create/get/list/update/delist; integer money and status preserved");

}
```

## 26.9 保留旧数据时怎样切换

### 26.9.1 【入门】空库实验和生产迁移不同

本章新库中的商品由 smoke 创建，旧库中的商品不会自动出现。两个库具有相同表名并不会同步；把旧 HTTP 地址和新 gRPC 地址都打开，也不会产生数据复制。

如果只学习实验，可以保留旧库作为历史检查点。若要保留已积累的商品，必须在下一章接流量前设计并验证迁移流程。没有明确写入所有者之前，不允许两套入口同时成为权威写入路径。

### 26.9.2 【进阶】一次离线迁移的顺序

小规模教学环境可以安排停写窗口：先备份旧库并记录恢复方式，停止旧商品写入，导出产品业务数据，在新库完成本章结构迁移后导入，再核对记录数量、标识、下架状态、金额与抽样内容。最后验证下一次创建生成的编号不会冲突。

之后才把公共调用切到 catalog。切换前旧库仍是权威；切换后新写入只进入新库。如果切换后已经接受新写入，简单把地址切回旧库会丢失这些新事实，回退必须先解决增量数据归并。这个流程不是“改一次环境变量就回滚”。

### 26.9.3 【进阶】保留 id 与修正序列

商品 id 可能已经被其他记录引用，因此不能导入时重新分配。GENERATED ALWAYS 标识列需要采用支持保留标识值的导入方式，并在导入完成后核对关联序列位置。

仅验证现有 id 不重复不够：如果序列仍从一开始，下一次新建就可能冲突。空表、非空表和显式导入过最大 id 的情况要分别检查；序列操作也不能笼统地认为与普通数据事务拥有相同回滚语义。

### 26.9.4 【精通】不要复制迁移历史冒充迁移业务数据

旧库的 `_sqlx_migrations` 描述旧 monolith 怎样演进，新库则由 catalog 的首次迁移建立。业务数据复制应针对明确的业务表与列，不把旧迁移历史覆盖到新库。

本章没有提供一条声称通用的“整库恢复到新服务”命令，因为旧数据库还含有用户等其他能力，且结构版本可能不同。真正执行前应在临时恢复库中演练导出、转换、导入和序列校验；后续总体验收会记录实际执行结果。

### 26.9.5 【精通】为什么暂时不引入双写

把每次商品更新同时写旧库和新库，看起来可以免停机，实际上会出现旧库成功新库失败、响应丢失后重试、删除与更新乱序等问题。两个独立事务不能靠顺序调用自动变成原子事务。

后面的 Outbox、事件版本与重放机制会提供处理跨系统传播的工具，但这些工具也需要明确所有者和幂等规则。现在先用小规模离线流程建立正确边界，比在没有恢复方案时增加隐藏双写更容易理解和验证。

## 26.10 故障排查、练习与后续衔接

### 26.10.1 【入门】按证据排查

| 现象 | 先收集什么 | 判断和修复 |
| --- | --- | --- |
| workspace 找不到 catalog | 根 members 与文件路径 | 加入 services/catalog，确认命令执行目录 |
| 提示多个二进制可运行 | 包清单与完整命令 | 配置 default-run，迁移显式指定 catalog-migrate |
| 缺少 DATABASE_URL | 当前终端是否导出配置 | 在同一终端 set -a 后读取本地配置 |
| 数据库口令失败 | 容器创建时间、配置文件来源 | 使用初始化该实例的口令，避免重新生成后连接旧实例 |
| products 不存在 | 迁移退出码、数据库名称 | 对独立商品库先执行迁移，不靠重启服务修表 |
| 迁移 checksum 冲突 | 迁移文件与历史记录 | 检查是否误连旧库，恢复正确历史，不删记录绕过 |
| readiness 成功但商品 RPC 失败 | 实际状态码和服务端日志 | 健康只验证 SELECT 1，继续检查结构、数据与身份 |
| Unauthenticated | 元数据键与调用终端配置 | 使用相同服务凭据，避免打印凭据排错 |
| 合法查询返回 DeadlineExceeded | 锁等待、池等待和慢 SQL | 先找等待来源，不先删除预算 |
| 更新下架商品返回 NotFound | delisted_at 和既有接口契约 | 确认软下架状态，不误当连接故障 |
| HTTP 仍看到旧商品 | HTTP 当前连接哪个组件 | 本章尚未切网关，下一章统一读取来源 |

### 26.10.2 【入门练习】复述三个边界

解释协议结构、领域对象和数据库行的区别，再回答“SQL 成功读取到一行，为什么还可能返回 Internal”。

参考答案：协议结构保证可编码的数据形状，领域对象保证构造时业务规则，数据库行描述持久化结果。历史写入不一定遵守当前规则；如果重建领域对象失败，应阻止错误数据作为正常商品返回，并记录服务端诊断。

### 26.10.3 【操作练习】从空库复现

新建专用数据库，依次运行迁移、服务和 smoke，再使用错误令牌执行拒绝模式。记录命令、用例数量、状态码和正常关闭结果，不记录任何秘密。

评分要点：迁移先于业务流量；正确请求经过真实网络；错误令牌得到 Code::Unauthenticated；正确令牌运行拒绝模式应失败；停止服务后数据库数据仍存在。仅贴构建成功截图不满足这道练习。

### 26.10.4 【推理练习】两个 SELECT 的反例

事务 T1 查询列表，T2 插入商品并提交，T1 查询 count。分别分析默认 READ COMMITTED 和本章 REPEATABLE READ 下的结果。

参考答案：默认隔离下，T1 后一语句可以观察到 T2 的新提交，因此列表和总数可能来自不同状态；本章事务内两次业务查询共享快照，不会在 count 突然包含这次后来的插入。另一次独立 RPC 仍可以看到新数据。

### 26.10.5 【推理练习】超时后的创建能否重试

服务端 INSERT 提交后，客户端等待响应超时。能否把这个请求当作从未发生，再无条件调用 create_product？

参考答案：不能。客户端缺少提交结果的信息，本章创建契约没有幂等键，重试可能产生第二条商品。可以人工核对或设计业务幂等协议，但不能靠延长超时或统一重试消除这个不确定性。

### 26.10.6 【扩展练习】设计旧数据迁移验收表

假设旧库有一千条商品，其中两百条已下架。为离线迁移列出至少六个检查点，并说明切换后新增了十条商品时为何不能直接回旧库。

参考答案应包含：写入冻结与备份、来源结构版本、总数与下架数、id 集合或摘要、金额与名称抽样、序列下一值与新建测试、旧入口关闭以及失败恢复负责人。新库新增十条以后，两库已分叉，直接切回会丢失或隐藏新增记录，需要先处理增量与引用关系。

### 26.10.7 【衔接】下一章把公共入口接到服务上

现在 catalog 有自己的持久化、协议入口、服务身份、健康状态和生命周期，能够通过独立客户端验证。common 中仍复用既有领域代码，这是本阶段的过渡结构，不应把整个 common 都称为永久跨服务公共模型。

下一章处理 HTTP 网关如何持有 gRPC Channel、如何转换请求与状态、怎样继续执行用户认证与管理员授权，并明确停止旧商品仓储写入的位置。只有公共请求沿新路径读写同一个权威数据源，商品能力的这次切换才真正闭合。

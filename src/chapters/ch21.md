# 第 21 章 Docker Compose：可复现环境

第 20 章已经定义 monolith 镜像，但还需要人工准备数据库地址、Redis、端口与配置。若每位同学用不同命令启动依赖，出现故障时很难确认彼此的拓扑是否相同。本章把这些约定写成一份可以检查、启动和停止的 Compose 配置。

本章继续使用第 18 章的单体业务与第 20 章的镜像。学习重点是网络位置、配置传递、数据生命周期、启动条件和故障后的程序行为。Compose 负责组装进程环境，数据库事务与缓存逻辑仍由程序负责；掌握这个边界，才能避免把所有问题都归因于“容器启动顺序”。

## 21.1 Compose 的模型：项目、服务与容器

### 21.1.1 【入门】为什么不继续手写很多 docker run

手工命令可以启动三个容器，但还要记住共同网络、卷名、映射端口、环境变量和依赖检查。遗漏其中一个参数，表面上仍能看到三个运行中的进程，实际应用却可能访问另一个数据库或把数据写进临时层。

Compose 将这些声明保存在 YAML 中，工具读取后建立对应资源。它的收益是把“我记得当时这样启动过”变成可审查的输入，并能对照实际容器状态检查差异。

它并不因此等同于生产集群调度器，也不会替应用定义数据库事务。先用它建立可靠单机实验，再理解后面的 Kubernetes，会比同时跳到两套模型更清楚。

### 21.1.2 【入门】服务定义与容器实例

services 下的 postgres、redis、app 是逻辑服务。工具根据定义创建对应容器；同一个服务定义在不同项目中可以产生不同实例。配置文件中的服务名还用于相应网络中的服务发现。

不要把服务名与固定容器名混为一谈。本章不设置 container_name，避免不同实验抢占同一个全局名字，也便于以后理解服务扩容。需要操作某个服务时，用 docker compose exec postgres，而不是猜它生成的完整容器名。

### 21.1.3 【入门】项目名形成一组资源边界

同一份 Compose 文件可以用不同项目名建立独立的网络和命名卷。本章显式用 -p rustmall-ch21，所有后续命令都保持一致，减少目录名变化带来的歧义。

项目名不意味着宿主端口也能重复使用。两组资源都想发布 58080 时，仍会冲突。它也不意味着删除项目就删除镜像仓库或所有其他项目，资源范围要按具体命令理解。

### 21.1.4 【进阶】声明与实际状态可能不一致

配置改了，并不代表正在运行的容器已重建。env 文件改了，也不代表已有数据库账号密码已同步变化。排查时分别检查渲染后的配置、容器当前设置和数据库内部事实。

这一点类似第 19 章的多种状态：编辑器中的文件、已提交版本和正在运行的进程可以属于不同时间点。运维过程也需要明确“改了哪一层”。

### 21.1.5 【精通】一个 up 命令包含多个失败阶段

Compose 可能先解析变量、构建或获取镜像、创建卷与网络、创建容器，再启动并等待条件。失败日志来自哪一阶段，决定下一步查哪份输入。

缺少必填变量发生在程序运行之前；数据库口令错误发生在应用或客户端连接阶段；迁移失败又属于建立数据库结构的阶段。不要仅因这些动作由一次 up 触发，就把它们当作一个无法细分的整体。

## 21.2 网络与地址：站在调用者的位置看 localhost

### 21.2.1 【入门】先画本章拓扑
```text
宿主 curl / 浏览器
        |
        | 127.0.0.1:58080
        v
   app:8080
     |     |
     |     +------ redis:6379
     +------------ postgres:5432

宿主调试数据库：127.0.0.1:55432
宿主调试 Redis：127.0.0.1:56379
```

app、postgres 和 redis 在共同的 Compose 网络内使用服务名通信；宿主通过已发布的回环端口访问。图中的每条边都有一个调用者，地址必须从该调用者所在位置解释。

### 21.2.2 【入门】为什么 app 连接 postgres:5432

postgres 是服务名，5432 是数据库容器内的监听端口。宿主发布为 55432，不会把数据库容器内部端口也改成 55432。

如果把 app 的地址写成 localhost:55432，app 通常会连接自身网络环境中的这个端口，既不是宿主映射，也不是 PostgreSQL。先画拓扑再填 URL，能避免大量“密码正确但一直拒绝连接”的误判。

### 21.2.3 【入门】为什么只把宿主端口绑定到回环

-p 或 Compose ports 可以选择宿主监听地址。本章使用 127.0.0.1，使实验端口面向本机访问；不是让任何能够访问这台机器的人都直接连接数据库和 Redis。

应用服务之间走内部网络，不依赖把每个端口都发布给宿主。发布是为了外部入口或本机诊断，服务发现则由内部网络负责。这两种需要应分开决定。

### 21.2.4 【进阶】服务名比固定 IP 更适合替换实例

容器重建后 IP 可能变化，代码不应把某次 inspect 看到的 IP 写死。服务名提供稳定的逻辑地址，客户端仍需要处理已有连接断开和重新建立。

名称稳定不表示连接永远不坏。PostgreSQL 重启会使原连接失效；Redis 的连接管理器也需要经历故障与恢复。网络层的可重新发现，与程序层的正确重试是不同责任。

### 21.2.5 【精通】DNS、端口、认证与数据库结构的四次检查

先确认名称能找到目标，再确认端口接受连接，然后确认账号和数据库可访问，最后确认迁移与查询满足应用契约。TCP 成功只覆盖第二层的一部分，不证明最后两层。

本章的 postgres 健康检查使用 pg_isready 判断服务器是否接受连接，应用 /health/ready 再通过自己的连接路径检查。不要从 pg_isready 成功推导出应用密码、权限和所有业务表都已正确。

## 21.3 YAML 与 Compose 字段：每个值在哪一层生效

### 21.3.1 【入门】缩进表达结构

YAML 通过缩进表达映射与列表。services 与 volumes 是顶层结构，services 下的 app 是一个服务，app 下的 environment 才是该服务的环境。缩进错一层，可能导致语法错误，也可能产生你没有打算配置的结构。

统一使用空格，不用制表符。布尔或数字形态的环境值可以明确写为字符串；程序最终按自己的配置类型解析，YAML 是否先把它当作整数不应成为隐藏假设。

### 21.3.2 【入门】image 与 build

image 为所用或所产出的镜像指定名称；build 提供构建上下文与相关选项。本章 app 由本地 Dockerfile 构建，同时标记为 rustmall-monolith:ch21。postgres 和 redis 使用明确版本系列的上游镜像。

使用现成 image 不等于一定需要每次重新拉取，行为还取决于命令与策略。为了知道某次实验用了什么，应记录实际镜像身份，而不仅是 YAML 中的可变 tag。

### 21.3.3 【入门】ports 与 volumes 的左右两边

本章端口条目 127.0.0.1:55432:5432 从左到右是宿主地址、宿主端口、容器端口。卷条目 postgres-data:/var/lib/postgresql/data 则是卷源与容器挂载目标。它们都带冒号，但不是同一种语义。

先识别字段所属位置，再解释字符串。把宿主目录误当成命名卷，或把数据库 17 与 18 的数据目录约定混用，都可能留下难以观察的数据问题。本阶段固定 PostgreSQL 17，目录也按该镜像版本使用。

### 21.3.4 【进阶】environment 是进入容器的显式环境

app 的 environment 只注入程序实际需要的数据库 URL、JWT 秘密与 Redis 地址等字段。数据库服务使用 POSTGRES_USER 等上游入口变量，RustMall 使用自己的 Settings 变量名；名字不同，不能期待它们自动互相转换。

显式列出映射还有一个好处：避免把生成文件里的所有秘密交给每个服务。Compose 插值知道某个变量，不代表所有容器都应该获得它。

### 21.3.5 【进阶】restart 与 stop_grace_period

restart 指定容器退出后的相关重启策略，不负责修复坏配置，也不能直接替代业务恢复。stop_grace_period 则给正常停止后的等待阶段一个预算，再结合主进程信号与程序自己的排空实现判断。

本章先不依赖自动无限重启掩盖启动失败，保留退出状态方便学习排查；待明确失败类别后，再在后续部署章节设计适当策略。程序应该明确拒绝错误配置，而不是永远处于看似忙碌的重启循环。

### 21.3.6 【精通】配置文件是程序输入，需要校验
```bash
docker compose -p rustmall-ch21 --env-file compose.dev.env config --quiet
```

--quiet 检查并避免把解析后的秘密直接打印出来。普通 config 可能展示环境值，因此在记录或分享完整输出前先判断是否包含密码。语法检查成功仍不证明镜像已构建、挂载目录可访问或数据库已初始化。

## 21.4 三种 env 用法：不要让文件名代替机制

### 21.4.1 【入门】Docker run 的 --env-file

第 20 章 docker run --env-file compose.env 把文件中的环境变量传进一个容器。那份文件直接使用 DATABASE_URL 和 APP_AUTH__JWT_SECRET，因为它面向 RustMall 进程。

该机制不自动为 PostgreSQL 准备账号，也不会对任意 YAML 做插值。它解决的是启动一个进程时传递哪些键值。

### 21.4.2 【入门】Compose 命令的 --env-file

本章 docker compose --env-file compose.dev.env 首先为 Compose 读取插值来源。文件定义 DB_USER、DB_PASSWORD 等构建拓扑所需参数；只有 compose.yaml 中显式使用它们的地方，才进入对应服务或字段。

为了不悄悄覆盖上一章的直接运行配置，本章使用另一个文件名。两个文件都叫 env 并不意味着内容可互换，准确机制由使用它的命令与字段决定。

### 21.4.3 【进阶】服务级 env_file 是另一项声明

服务的 env_file 字段用于向该服务容器注入相应文件中的变量。本章选择 environment 明确列出需要的字段，没有必要再加入服务级 env_file。

以后确实需要使用时，应检查同名环境值的优先级与实际传入结果。不要把 Compose 的插值文件、服务级 env_file、程序自行加载的 dotenv 当成一个不分层次的“配置自动读取”。

### 21.4.4 【进阶】${VAR:?说明} 让缺失尽早失败

必须存在的密码使用必填插值表达式，缺少或为空时，Compose 先报配置错误，避免悄悄使用空口令或错误地址。对允许有默认值的端口等配置，可以另行使用明确默认规则。

shell 已导出的同名变量可能覆盖文件值。若文件看起来正确，渲染结果却不同，检查启动命令的环境与变量来源。处理秘密时不要为排错而一口气输出整个 env。

### 21.4.5 【进阶】为什么健康命令中有两个美元符号

Compose 会处理相应插值语法。如果希望变量由容器里的 shell 展开，就要让它先穿过 Compose 这一层。本章健康命令中的 $${POSTGRES_USER} 在渲染后保留为容器 shell 能读取的 ${POSTGRES_USER}。

这个问题与 Rust 字符串转义类似：同一段文本可能经过多层解释。先写出“谁先读取、谁后读取”，再决定需要在哪一层保留符号，比反复试删美元符号可靠。

### 21.4.6 【精通】随机口令与连接 URL 的编码

数据库 URL 的口令位置属于 URL 语法。真实口令含 @、:、/ 等字符时，不能不编码地直接拼接。本章生成器使用适合本地插值的 URL-safe 随机字符，缩小初学实验中的编码干扰。

这不是“所有密码都只能使用这些字符”的系统要求。生产秘密接入时，应按库和部署方式正确编码并验证。生成文件也要控制访问、拒绝无意覆盖，并排除 Git 与镜像上下文。

## 21.5 启动条件与迁移：谁在等待什么

### 21.5.1 【入门】运行中不等于就绪

数据库进程可能已经启动，仍在创建数据目录或恢复日志；此时 app 立刻连接就会失败。depends_on 的普通启动顺序只解决一部分时序，不会自动证明 SQL 已可执行。

本章 app 等待 postgres 的健康状态，并对 redis 只要求进程启动。后者沿用“缓存不是商品权威数据”的业务边界。首次完整缓存实验会先单独等待两个依赖，再启动 app，以明确验证确实包含 L2。

### 21.5.2 【进阶】三种条件表达不同含义

| 条件 | 要等待的事情 | 典型用途 |
| --- | --- | --- |
| service_started | 依赖实例已启动 | 允许程序处理暂时不可用的依赖 |
| service_healthy | 对应健康检查通过 | 数据库启动前置检查 |
| service_completed_successfully | 一次性任务成功结束 | 独立迁移或初始化任务 |

条件需要匹配服务性质。一个常驻数据库不会为了表达就绪而正常退出；一次性迁移也不应该被要求永远处于 running。后续独立迁移任务会采用第三种条件。

### 21.5.3 【进阶】本阶段的迁移仍沿用已有 main

第 14 章以后 monolith 在启动时建立连接并按已有流程执行迁移。本章不另造第二份 schema.sql 每次覆盖数据库。首个应用启动需要能把空实验库迁移到当前结构；已有数据库则由迁移记录判断还缺哪些步骤。

多人或多副本部署时，迁移需要更明确的权限和发布顺序，第 23 章会把它拆成独立任务。这里先理解本阶段的实际行为，不提前复制未来的作业配置造成两种启动流程混用。

### 21.5.4 【精通】启动成功之后，依赖仍然可能失败

depends_on 不是整个运行期的业务保证。PostgreSQL 可以在一小时后重启，Redis 可以连接断开，应用仍要正确处理错误、恢复连接和拒绝没有事实依据的结论。

也不能看到依赖被重启，就默认所有相关服务一定自动重启。不同字段与显式 Compose 操作有具体规则；本书故障实验会直接观察当前容器与请求，而不是把“有依赖声明”当作推断运行行为的充分证据。

### 21.5.5 【精通】Redis 启动失败与运行时中断要分开

第 18 章组装时若无法建立 Redis，可能选择仅使用进程内缓存；已经持有连接管理器后出现临时故障，则涉及该管理器的恢复行为。二者不是同一个状态。

因此实验记录要包含 app 启动时 Redis 是否已经可用。要验证两级缓存，应先让 Redis 就绪；要验证纯 L1 降级，应明确从相应前提出发，而不是看到一次请求成功就宣称两条路径都测过。

## 21.6 项目进度：按顺序建立完整环境

### 21.6.1 本节文件清单与阶段边界

| 文件 | 状态 | 本章责任 |
| --- | --- | --- |
| compose.yaml | 新建 | 声明 app、PostgreSQL 与 Redis |
| scripts/create-compose-env.py | 新建 | 生成本地随机配置，拒绝覆盖 |
| scripts/check-ch21-http.py | 新建 | 限制大小并配置网络操作超时的只读检查 |
| .gitignore | 追加必要条目 | 排除 compose.dev.env |
| .dockerignore | 追加必要条目 | 排除同一配置文件 |
| docs/compose-lab.md | 新建 | 记录拓扑、启动和故障实验条件 |

应用代码继续使用前章；本章创建新的实验数据库卷，不自动搬迁前面手工启动数据库中的样本数据。先从空库验证迁移与接口，再讨论数据导入。不要让两个数据库实例同时挂载同一份活动数据目录。

### 21.6.2 第 1 步：生成本地配置

文件：rustmall/scripts/create-compose-env.py（完整内容）
```python
"""在 RustMall 根目录生成本地 Compose 插值文件；拒绝覆盖。"""
from pathlib import Path
import os
import secrets

values = {
    "DB_USER": "rustmall",
    "DB_NAME": "rustmall",
    "DB_PASSWORD": secrets.token_urlsafe(36),
    "JWT_SECRET": secrets.token_urlsafe(48),
}
path = Path("compose.dev.env")
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as output:
    for key, value in values.items():
        output.write(f"{key}={value}\n")
print("已生成 compose.dev.env；没有输出秘密值。")
```

在 RustMall 根目录执行：
```bash
python3 scripts/create-compose-env.py
```

第一次成功创建文件，第二次应明确报文件已存在。不是每次 up 都重新生成密码；否则会让配置中的新密码与已有数据卷中旧账号口令不一致。确需轮换时，应对数据库事实和应用连接一起操作。

### 21.6.3 生成器精讲：随机值、文件身份与输出

token_urlsafe 生成随机秘密的文本表示，减少把特殊 URL 字符原样拼入连接地址的麻烦。DB_USER 与 DB_NAME 固定为实验命名，口令与 JWT 秘密独立生成，不能把两种不同权限材料设成同一个值。

os.open 使用 O_CREAT 与 O_EXCL，使文件是否已存在成为明确条件；0o600 请求仅当前用户读写的权限。该权限在不同系统上的最终效果还取决于文件系统与访问控制，应按实际环境检查。程序不打印秘密正文，让通常的终端记录不包含它们。

### 21.6.4 第 2 步：核对两个忽略边界

在已有 .gitignore 与 .dockerignore 中分别增加下面这一行，保留原有内容：
```text
compose.dev.env
```

它们分别保护源码跟踪和构建输入。确认是追加到两份实际使用的文件，不是新建一个名字相近但没有被工具读取的文件。之后可以检查 git status，生成配置不应成为准备提交的新增文件。

### 21.6.5 第 3 步：完整 compose.yaml

文件：rustmall/compose.yaml（完整内容）
```yaml
services:
  postgres:
    image: postgres:17-bookworm
    environment:
      POSTGRES_USER: ${DB_USER:?请先生成本地配置}
      POSTGRES_PASSWORD: ${DB_PASSWORD:?缺少数据库口令}
      POSTGRES_DB: ${DB_NAME:?缺少数据库名}
    ports:
      - '127.0.0.1:55432:5432'
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U "$${POSTGRES_USER}" -d "$${POSTGRES_DB}"']
      interval: 3s
      timeout: 2s
      retries: 20
      start_period: 10s
  redis:
    image: redis:7.4-alpine
    command: ['redis-server', '--appendonly', 'yes', '--maxmemory', '128mb', '--maxmemory-policy', 'allkeys-lru']

      - '127.0.0.1:56379:6379'
```

### 21.6.6 配置精讲一：数据库服务的初始化与权限

POSTGRES_USER、POSTGRES_PASSWORD 和 POSTGRES_DB 由上游镜像入口在初始化空数据目录时使用。本章这个用户用于实验初始化与应用迁移，具有较高数据库权限，不是生产中应直接沿用的最小权限设计。

环境变量改变，不会自动重写已有数据库角色。数据库卷保留时，账号、表和迁移记录都是持久事实。若连接失败，先分清是首次初始化还是已有卷的重新启动。

本阶段使用 PostgreSQL 17 的数据目录约定。未来升级到另一大版本，应按相应镜像与数据库升级流程迁移，不能只改 image 数字继续使用旧目录碰运气。

### 21.6.7 配置精讲二：Redis 的持久化与驱逐

本章 Redis 保存商品缓存，允许采用 allkeys-lru 这样的缓存淘汰策略；128mb 限制的是 Redis 的相应数据内存管理，不等于整个进程所有内存都被精确限制为同一个数字。

AOF 让部分缓存状态可以跨实例重启保留，缓存权威仍来自 PostgreSQL。不要把同一策略直接用于唯一的会话撤销或资产事实；后续用户服务会专门讨论数据后果不同为什么需要不同方案。

### 21.6.8 配置精讲三：只读应用根文件系统

read_only 让应用根文件系统按只读方式运行；tmpfs 给 /tmp 一个有限的临时可写区域。cap_drop 与 no-new-privileges 减少不必要权限，本章 Dockerfile 中的非 root 用户继续生效。

如果程序试图在 /app 写入文件，会明确失败。这是一次检验运行契约的机会：日志应写 stdout/stderr，持久业务数据应进入数据库。确有其他写入需求时，为相应位置建立有目的的权限和存储，不把整个限制关掉了事。

### 21.6.9 配置精讲四：资源与连接总量

app 的内存与 CPU 限制用于本机可控实验。数据库、Redis、Docker Desktop 的 Linux 环境与宿主其他程序也要消耗资源，不能把应用限制直接当整套工程的资源总预算。

第 15 章连接池每个进程最多多少连接，扩容后就要乘以应用副本数，再加迁移与运维预留。Compose 把服务放进一个文件，不会替你把所有池合并成一个共享上限。

### 21.6.12 第 6 步：只读 HTTP 检查器

文件：rustmall/scripts/check-ch21-http.py（完整内容）
```python
"""只读检查第 21 章已启动的 HTTP 契约；失败返回非零。"""
import argparse
import json
import sys
import urllib.error
import urllib.request

parser = argparse.ArgumentParser()
parser.add_argument("--base", default="http://127.0.0.1:58080")
args = parser.parse_args()
base = args.base.rstrip("/")


class NoRedirect(urllib.request.HTTPRedirectHandler):
    def redirect_request(self, request, fp, code, message, headers, new_url):
        return None


opener = urllib.request.build_opener(NoRedirect())


def fetch(path):
    request = urllib.request.Request(base + path, method="GET")
    try:
        response = opener.open(request, timeout=3)
    except urllib.error.HTTPError as error:
        response = error
    with response:
        body = response.read(128 * 1024 + 1)
        if len(body) > 128 * 1024:
            raise ValueError("响应体超过本检查器上限")
        return response.status, json.loads(body)


try:
    for path in ["/health/live", "/health/ready"]:
        status, body = fetch(path)
        if status != 200 or not isinstance(body, dict):
            raise ValueError(f"{path} 未满足健康接口契约")
        print(f"PASS {path}")
    status, body = fetch("/api/v1/products?page=1&page_size=2")
    if status != 200 or not isinstance(body, dict):
        raise ValueError("商品列表没有返回成功 JSON 对象")
    if not isinstance(body.get("items"), list):
        raise ValueError("items 不是数组")
    if type(body.get("total")) is not int or body["total"] < 0:
        raise ValueError("total 不是非负整数")
    print("PASS 商品列表结构")
except (OSError, ValueError, KeyError, TypeError) as error:
    print(f"FAIL {error}", file=sys.stderr)
    raise SystemExit(1)
print("ALL 3 CHECKS PASSED；只验证已列出的只读契约。")
```

运行：
```bash
python3 scripts/check-ch21-http.py
```

它只访问健康与商品列表，不创建账号、不插入商品，因此可以重复检查当前只读契约。列表允许为空，避免验收依赖某个默认 id；本章新数据库不保证有前章人工创建的样本。

### 21.6.13 检查器精讲：状态、类型与边界

urllib 的 HTTPError 仍包含 HTTP 响应，检查器把它作为响应读取，再按状态与 JSON 结构判断，而不是把 503 和连接根本没建立混在一起。网络异常与格式异常最终都明确失败退出。

read 最多读取上限加一字节，识别超大响应；urllib 配置的是连接及相应阻塞 I/O 的超时，并不是整次请求严格共享的三秒截止时间。慢字节持续到达仍可能延长整个读取过程，因此这个小型本地只读检查器不能替代第 20 章的严格截止时间探针或生产入口预算。它也明确拒绝重定向，避免把跳转后的其他接口当成本次目标已成功。type(total) is int 还排除了 Python 中 bool 属于 int 子类的细节，让“总数”必须是本契约要求的整数。

输出 ALL 3 CHECKS PASSED 只证明这三项通过，不表示登录、写权限、缓存恢复和故障演练也已验证。下一节将分别取得这些证据。

## 21.7 数据卷与重建：保存的是事实，不只是文件名

### 21.7.1 【入门】stop、down 与删除卷

stop 停止相应容器，down 通常移除该项目容器与网络；本章声明的命名卷在不选择删除卷时仍保留。重新 up 可以继续使用同一批数据库事实。

带删除卷选项的操作会改变持久数据范围，不能把它当成“让配置刷新一下”的惯常动作。先确认资源属于哪一个项目、里面是什么、是否有可恢复备份，再决定。这里不把数据删除步骤放进日常启动命令串。

### 21.7.2 【进阶】空卷初始化与已有卷重新启动

首次启动时，PostgreSQL 入口建立数据目录、用户和数据库。后续启动检测到已有数据，就继续使用原内容。若你只改 compose.dev.env 中口令，应用会拿新值连接，数据库仍可能保留旧口令。

这不是 Compose 忽略文件，而是两个系统处理不同事实。正确轮换需要在数据库中改变角色秘密，再让应用按新值重建连接，并明确旧连接与失败窗口。初学实验从空卷可复现，不等于生产可以靠删卷重来。

### 21.7.3 【进阶】更换应用与更换数据库是不同风险

应用镜像通常可以在不删除数据库卷的情况下替换，但还要确认迁移与旧新代码兼容。数据库大版本升级涉及数据格式与升级协议，不能简单与应用换镜像等同。

先保留版本、迁移与数据边界，再讨论回滚。源码回到旧提交，不会自动把数据库变回旧结构，也不会撤销已经发生的外部业务。

### 21.7.4 【精通】卷不是备份，缓存不是业务数据库

卷保留了实例替换后的数据，但宿主磁盘损坏、误删和逻辑错误仍可能影响它。备份需要独立恢复点、保留策略与恢复验证。本章建立持久位置，后续 PostgreSQL 与 SRE 章节再展开恢复。

Redis 缓存卷有助于实验重启保留，但它不替代 PostgreSQL 的权威数据。删除商品缓存后应能受控回源；删除订单数据库则无法靠“再请求一次”安全重建所有历史。

## 21.8 故障演练：每次只改变一个前提

### 21.8.1 【入门】演练先写预期，再执行停止

先确认三个服务健康，记录 app 容器是否保持同一实例、当前提交与镜像、样本请求和缓存冷热。然后只停止一个依赖，观察同一请求，再恢复依赖观察是否收敛。

记录“接口没挂”不够。某个热商品可能一直命中 L1，不能由此证明 Redis 失败时回源正确；某个查询返回 404，也不能说明数据库故障被正确处理。

### 21.8.2 演练一：运行时停止 Redis
```bash
docker compose -p rustmall-ch21 --env-file compose.dev.env stop redis
python3 scripts/check-ch21-http.py
docker compose -p rustmall-ch21 --env-file compose.dev.env logs --tail 80 app
```

商品权威仍在 PostgreSQL，按第 18 章设计，Redis 操作错误或超时应退回相应路径。为了观察回源，应选择明确冷热状态并等待或失效 L1，而不是只重读一个永远未过期的热点项。

恢复 Redis 后，还要根据启动时是否建立连接管理器判断当前进程能否重新使用 L2。测试的真正对象是代码路径和事实，不是“Redis 又变绿了”这个单一状态。

### 21.8.3 演练二：运行时停止 PostgreSQL
```bash
docker compose -p rustmall-ch21 --env-file compose.dev.env stop postgres
curl -i http://127.0.0.1:58080/health/ready
```

就绪应体现数据库依赖不可用。某个热缓存读可能暂时成功，不代表可以进行数据库写入或认证查询。数据库异常不能被转换为“商品不存在”并长期缓存，否则恢复后仍可能持续返回假 404。

恢复后应重新检查就绪、冷读、写入与数据内容。连接池恢复不是数据正确性的替代证据。

### 21.8.4 演练三：只重建应用

在保持数据库卷的前提下重建 app，观察进程内缓存重置、业务数据保留与新请求回源。原 token 是否仍有效，还取决于 JWT 签名秘密和声明规则是否保持一致，不能笼统地说“重启会让全部登录失效”。

若同时重新生成了 JWT 秘密，令牌变化与进程重建就混在一起，无法解释原因。控制变量是故障演练的基本方法。

### 21.8.5 演练四：故意缺少一个必填插值值

在另一份临时实验配置中移除 JWT_SECRET，再运行 config --quiet。预期在解析阶段失败，而不是等到 app 开始处理请求才发现密钥不存在。完成后恢复原实验文件，不覆盖保留中的真实秘密。

这个实验验证“尽早拒绝不完整输入”。它不验证秘密强度或签名实现，后两者仍由应用配置校验和认证测试负责。

### 21.8.6 【精通】用时序区分缓存与依赖故障

把一次请求写成时间线：L1 查询、L2 查询、数据库读取、回填、返回。停止 Redis 会影响其中一段，停止 PostgreSQL 会影响另一段；不同缓存冷热状态可能走不同路径。

因此测量时记录每段的命中、错误与耗时，才能解释“同一个接口有时快有时慢”。只记录总耗时，容易把 Redis 超时、数据库回源和连接池等待混为一谈。

## 21.9 常见问题与检查顺序


| 现象 | 应收集的证据 | 修复方向 |
| --- | --- | --- |
| 新口令连接失败 | 已有数据卷与初始化时间 | 环境文件不会自动修改已初始化数据库的角色口令 |
| 解析配置与运行不同 | 插值来源、运行容器环境、项目名 | 区分解析输入与容器环境，确认是否重建正确项目 |
| 热读成功却依赖已停 | L1/L2冷热、回源日志和请求类型 | 用冷读、写入、认证及健康分别判断依赖状态 |
| 端口被占用 | 发布端口与已有监听进程 | 改宿主映射或清理自己的资源，勿删除陌生实例 |


### 21.9.1 配置文件正确，实际值却不同

核对 -p、--env-file、当前目录、可能的 -f 文件和 shell 同名变量。先确定正在解析哪份模型，再查看渲染后的相应字段。秘密只在受控位置核对，不把全量输出发到问题报告。

### 21.9.2 数据库健康，应用仍提示认证失败

健康检查只表明服务器接受连接，不证明 app 使用了正确口令或数据库。重点核对旧卷是否保留旧账号、配置是否重新生成、应用是否已经重建，以及 URL 是否按规则编码。

### 21.9.3 新配置生成成功，启动却看不到新数据库

先确认是不是原命名卷被继续使用。上游入口不会在每次容器重启时重新创建一套业务用户。再检查项目名是否变化；变化可能让你连接另一个项目中的空数据库，看起来像数据消失。

### 21.9.4 HTTP 检查通过，为什么不能证明缓存正确

检查器只覆盖两个健康接口和商品列表结构，没有验证详情的 L1/L2、缺失缓存失效或 Redis 恢复。需要按故障实验与第 18 章测试检查相应行为，不能用三条只读检查支持整个系统的结论。

### 21.9.5 应用无法写临时文件

检查真实写入路径。/tmp 已提供有限 tmpfs；/app 属于只读运行区。确认依赖是否把临时文件错误放到当前目录，必要时为准确路径提供可写位置，并计算容量。先知道要写什么，再调整权限。

### 21.9.6 端口已经被占用

确认占用来自前章手工容器、另一个 Compose 项目还是其他本机服务。可以调整宿主侧发布端口并同步检查器 --base，而容器内部 app:8080 与 postgres:5432 不必因此改变。

只改配置中的某个数字，却忘记命令行、URL 和观察位置，会把一个简单冲突变成多个新错误。

## 21.10 分层练习、参考答案与本章小结

### 21.10.1 基础练习：从调用者解释三个数据库地址

比较宿主的 127.0.0.1:55432、app 中的 postgres:5432 和 app 中的 localhost:55432。

参考答案：前两者按本章映射指向数据库的不同访问路径；第三个通常指向 app 自身，并不自动连接宿主。判断必须同时写出调用者与目标位置。

### 21.10.2 配置练习：解释三种 env 机制

说明 docker run --env-file、docker compose --env-file 和服务 env_file 的不同，并指出本章为什么没有使用最后一种。

答案要点：分别是单容器环境注入、Compose 模型插值来源、服务环境文件声明；本章用 environment 精确注入需要的字段，避免仅凭文件名推断行为。

### 21.10.3 操作练习：让缺失变量在启动前失败

从临时配置中移除 DB_PASSWORD，执行 config --quiet，记录错误阶段。不要在已有真实数据库上轮换口令来完成这项语法实验。

验收要点：尚未构建或创建业务容器就能识别配置不完整；恢复变量后渲染成功；没有把秘密打印到提交内容。

### 21.10.4 推理练习：为什么不能把 sleep 5 当数据库就绪

给出冷启动、恢复日志和宿主高负载三个场景，解释固定等待如何过短或浪费时间。

参考答案：等待具体健康条件并设总预算，成功时尽早继续，超时时明确失败。等待只是启动协调，运行中依赖故障仍需要应用处理。

### 21.10.5 工程练习：修改宿主 HTTP 端口

把发布端口改为另一个空闲值，用检查器 --base 指向新地址，并解释容器内探针为什么继续使用 8080。

验收要点：只改变宿主侧映射与外部调用地址，不误改服务内部端口；能够分别验证宿主入口和容器探针。

### 21.10.6 精通练习：设计可复现的 Redis 故障记录

至少记录 Redis 在 app 启动时是否就绪、连接管理器是否建立、请求的 L1 冷热、停止与恢复时间、接口结果和 app 日志。

参考答案：上述条件决定实际经过哪条代码路径；一次热缓存成功不能证明回源和恢复。能够解释条件与结果的联系，比只写“故障时可用”更接近有效证据。

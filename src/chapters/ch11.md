# 第 11 章 异步编程与 Tokio 详解

后端服务的大部分时间在等待：等数据库返回、等 Redis 返回、等下游服务返回、等客戶端发来下一个字节。异步编程让程序在等待期间去做别的事，用少量线程处理成千上万个并发请求。Tokio 是 Rust 异步生态的事实标准运行时，本书后面使用的 Axum、SQLx、Tonic、redis-rs、reqwest 全部建立在它之上。本章讲清 async/await 的用法与原理、Tokio 的全部常用组件，项目部分创建 RustMall 的第一个可执行程序monolith ，实现信号处理、后台周期任务与优雅停机。

## 11.1 为什么需要异步

### 11.1.1 【入门】餐厅的两种经营方式

一桌一个服务员（每请求一个线程）：服务员点完菜就站在厨房门口等，菜好了端过去，再等客人吃完。服务 1000 桌就要 1000 个服务员，而他们 99% 的时间都在干等。

少数服务员轮流照看（异步任务）：服务员点完菜就去照看别的桌，厨房做好了喊一声，谁有空谁去端。几个服务员就能照看成千上万桌。

| 维度 | 操作系统线程 | Tokio 异步任务 |
| --- | --- | --- |
| 创建代价 | 微秒级，需要系统调用 | 纳秒级，一次小的堆分配 |
| 内存 | 每个线程默认 2~8 MB 栈 | 每个任务只占它实际需要的状态，通常几百字节到几 KB |
| 切换 | 内核上下文切换 | 用户态，在 .await 处主动让出 |
| 可同时存在的数量 | 几千 | 几十万到上百万 |
| 适合 | CPU 密集计算、阻塞调用 | I/O 密集：网络服务、数据库、缓存 |

后端服务是典型的 I/O 密集型程序，所以现代 Rust 后端几乎全部是异步的。

### 11.1.2 【进阶】协作式调度

Tokio 的任务是协作式的：一个任务只有在 .await 一个尚未就绪的操作时才会让出线程。如果任务里写了一个长时间的计算循环或者阻塞调用（std::thread::sleep 、同步读文件、计算密码哈希），它会一直占着工作线程，该线程上的其他任务全部停滞。这是异步编程的第一大陷阱，11.4.4 节给出解决方法。

## 11.2 Future 与 async/await

### 11.2.1 【入门】第一个异步程序
```toml
# Cargo.toml
[dependencies]
# 练习时用 full，项目中按需开启（11.3.3 节）
tokio = { version = "1", features = ["full"] }
```
```rust
use std::time::Duration;

async fn query_stock(product_id: i64) -> i32 {
    // 模拟一次 500ms 的数据库查询
    tokio::time::sleep(Duration::from_millis(500)).await;
    (product_id * 10) as i32
}

#[tokio::main]
async fn main() {
    let stock = query_stock(1).await;
    println!("库存 {stock}");
}
```

三个要点：

1. async fn 调用后不会立即执行，而是返回一个实现了 Future trait 的值--一张“将来会有结果的任务单”。

2. .await 驱动这个 Future 执行，并在它尚未完成时让出线程，而不是阻塞线程。

3. Future 需要一个运行时来驱动。#[tokio::main] 把 async fn main 改写为“创建 Tokio 运行时并执行这个 Future”的普通 main（第 8.8.1 节的属性宏）。

### 11.2.2 【入门】惰性：不 await 就不执行
```rust
#[tokio::main]
async fn main() {
    // 此时什么都没发生
    let fut = query_stock(1);
    println!("还没有开始查询");

    // 这里才真正执行
    let stock = fut.await;
    println!("{stock}");

    // 警告：unused implementer of `Future` that must be used
    query_stock(2);
}
```

和第 6.5.3 节的迭代器一样，Future 是惰性的。忘记 .await 是新手最常见的 bug：代码看起来调用了发送邮件的函数，实际上什么都没做。编译器会给出警告，-D warnings 下会变成错误。

### 11.2.3 【入门】async 块与 async 闭包
```text
let product_id = 42;

// async 块：创建一个匿名 Future，move 把 product_id 移进去
let fut = async move {
    query_stock(product_id).await + 1
};
let n = fut.await;

// async 闭包（Rust

1.85+）
let m = fetch(7).await;
```

### 11.2.4 【进阶】async fn 的真实签名
```rust
async fn query_stock(product_id: i64) -> i32 { ... }
// 等价于
fn query_stock(product_id: i64) -> impl Future<Output = i32> { async move { ... } }
```

参数中的引用会被捕获进返回的 Future：async fn find(name: &amp;str) -&gt; ... 返回的 Future 借用了name ，在 Future 完成前 name 必须有效。这就是为什么把异步函数交给 tokio::spawn （要求'static ）时，参数应当是拥有所有权的类型（第 2.5.6 节）。trait 中也可以直接写 async fn（Rust 1.75+），第 14 章的异步仓储会使用；但含有 async fn 的 trait 不是 dyn 兼容的，需要放进Arc&lt;dyn...&gt; 时仍然使用 async-trait crate 或手写返回 Pin&lt;Box&lt;dyn Future&gt;&gt; （第二卷 5.5.5节）。

## 11.3 Tokio 运行时

### 11.3.1 【入门】#[tokio::main] 做了什么
```rust
#[tokio::main]
async fn main() { app().await }

// 大致展开为：
fn main() {
    // 多线程运行时
    tokio::runtime::Builder::new_multi_thread()
        // 启用 I/O 与定时器驱动
        .enable_all()
        .build()
        .expect("创建运行时失败")
        // 阻塞当前线程，直到这个 Future 完成
        .block_on(async { app().await })
}
```

### 11.3.2 【进阶】两种运行时与配置

| 运行时 | 写法 | 特点 | 适用 |
| --- | --- | --- | --- |
| 多线程 | #[tokio::main] （默认） | 按 CPU 核数创建工作线程，空闲线程会“偷取”忙碌线程的任务（work-stealing） | 服务端程序 |
| 当前线程 | #[tokio::main(flavor="current_thread")] | 所有任务在一个线程上运行 | 命令行工具、测试（#[tokio::test]默认就是它） |
```rust
// 指定工作线程数
#[tokio::main(worker_threads = 4)]
async fn main() {}
```

容器中运行时，工作线程数应与容器的 CPU 配额匹配：available_parallelism() 在新版本的 Rust中会读取 cgroup 限制，但在部分环境中仍可能返回宿主机核数，此时可以通过环境变量TOKIO_WORKER_THREADS 指定（第 23 章）。

### 11.3.3 【进阶】Tokio 的 features

Tokio 默认什么都不开启，按需选择（第 8.4.2 节）：

| feature | 提供 |
| --- | --- |
| rt / rt-multi-thread | 当前线程 / 多线程运行时 |
| macros | #[tokio::main] 、#[tokio::test] 、join! 、select! |
| net | TCP、UDP、Unix socket |
| time | sleep 、timeout 、interval |
| sync | Mutex 、RwLock 、Semaphore 、通道等 |
| signal | 监听 Ctrl+C、SIGTERM |
| fs 、io-util 、process | 异步文件、I/O 辅助、子进程 |
| test-util | 测试中暂停和推进时间（11.9 节） |
| full | 以上全部（不含 test-util） |

## 11.4 任务

### 11.4.1 【入门】tokio::spawn
```rust
use std::time::Duration;

#[tokio::main]
async fn main() {
    let handle = tokio::spawn(async {
        tokio::time::sleep(Duration::from_millis(100)).await;
        "后台任务完成"
    });
    println!("主任务继续执行");

    // JoinHandle 本身也是 Future
    match handle.await {
        Ok(msg) => println!("{msg}"),
        Err(e) => println!("任务 panic 或被取消：{e}"),
    }
}
```

tokio::spawn 把一个 Future 交给运行时作为独立任务并发运行，立即返回 JoinHandle&lt;T&gt; 。

要求 Future 满足 Send + 'static ：任务可能在任何工作线程上运行、可能比创建它的代码活得更久（与第 7.4.2 节 thread::spawn 的要求相同）。

任务中的 panic 不会让进程崩溃，而是体现为 handle.await 返回 Err(JoinError) 。

丢弃 JoinHandle 不会取消任务，任务会继续在后台运行（“分离”）。要取消任务，调用handle.abort() 。

### 11.4.2 【进阶】JoinSet：管理一组任务
```rust
use tokio::task::JoinSet;

#[tokio::main]
async fn main() {
    let mut set = JoinSet::new();
    for id in [1_i64, 2, 3] {
        // 并发查询 3 个商品
        set.spawn(async move { (id, query_stock(id).await) });
    }

    // 按完成顺序取结果
    while let Some(result) = set.join_next().await {
        match result {
            Ok((id, stock)) => println!("商品 {id} 库存 {stock}"),
            Err(e) => println!("任务失败：{e}"),
        }
    }
// JoinSet 被 drop 时，尚未完成的任务会被自动 abort
}
```

JoinSet 是“结构化并发”的基础工具：任务的生命周期绑定在一个值上，不会泄漏到不可控的后台。

### 11.4.3 【进阶】spawn 与共享状态
```rust
use std::sync::Arc;

struct AppState { service_name: String }

#[tokio::main]
async fn main() {
    let state = Arc::new(AppState { service_name: "rustmall".into() });
    let mut handles = Vec::new();
    for i in 0..3 {
        // 每个任务一份 Arc
        let state = Arc::clone(&state);

        // async move 把这份 Arc 移进任务
        handles.push(tokio::spawn(async move {
            println!("{} 处理请求 {i}", state.service_name);
        }));
    }
    for h in handles { h.await.expect("任务不应 panic"); }
}
```

这个“先 clone 再 async move”的模式与第 7.6.1 节的线程版本完全相同。Axum 在内部为每个请求做的就是这件事（第 12 章的 State）。

### 11.4.4 【进阶】阻塞代码：spawn_blocking
```rust
fn hash_password(pwd: &str) -> String {
    // 假设这是一个耗时 50ms 的 CPU 密集计算（第 16 章的 Argon2）
    format!("hashed:{pwd}")
}

async fn register(pwd: String) -> String {
    // 错误：直接在异步函数中调用，会占住工作线程 50ms
    // let h = hash_password(&pwd);

    // 正确：交给专门的阻塞线程池，当前任务在等待期间让出工作线程
    tokio::task::spawn_blocking(move || hash_password(&pwd))
        .await
        .expect("哈希任务不应 panic")
}
```

| 场景 | 做法 |
| --- | --- |
| 短暂的纯计算（微秒级） | 直接写，不必处理 |
| 耗时的 CPU 计算（密码哈希、压缩、大量 JSON 处理） | spawn_blocking ，或 rayon 线程池 |
| 同步的 I/O 库（没有异步版本） | spawn_blocking |
| 睡眠 | tokio::time::sleep ，绝不用std::thread::sleep |
| 文件读写 | tokio::fs （内部就是 spawn_blocking） |

经验法则：两次 .await 之间的代码不应超过 10~100 微秒。

## 11.5 并发组合与时间

### 11.5.1 【入门】join!：同时等待多个
```rust
#[tokio::main]
async fn main() {
    // 顺序执行：约 1 秒
    let a = query_stock(1).await;
    let b = query_stock(2).await;

    // 并发执行：约 0.5 秒
    let (a2, b2) = tokio::join!(query_stock(1), query_stock(2));
    println!("{a} {b} {a2} {b2}");
}
```

商品详情页要同时查询商品信息、库存、评价时，join! 让总耗时从三者之和降到三者中的最大值。第27 章的网关聚合接口就是这样实现的。

join! 与 spawn 的区别：join! 在当前任务内部交替驱动多个 Future，不创建新任务，不需要'static ，可以借用局部变量；但它们始终在同一个线程上轮流运行，不能利用多核并行计算。I/O等待为主时两者效果相同。

### 11.5.2 【入门】try_join!：任一失败即返回
```rust
async fn load_product(id: i64) -> Result<String, String> { Ok(format!("商品{id}")) }async fn load_reviews(id: i64) -> Result<Vec<String>, String> { Err(format!
("评价服务超时：{id}")) }

#[tokio::main]
async fn main() {
    match tokio::try_join!(load_product(1), load_reviews(1)) {
        Ok((p, r)) => println!("{p} {r:?}"),
        // 一个失败，其余尚未完成的会被取消
        Err(e) => println!("失败：{e}"),
    }
}
```

### 11.5.3 【进阶】select!：谁先完成用谁
```rust
use std::time::Duration;

#[tokio::main]
async fn main() {
    tokio::select! {
        stock = query_stock(1) => println!("查到库存 {stock}"),
        _ = tokio::time::sleep(Duration::from_millis(200)) => println!("查询超过 200ms，放弃"),
    }
}
```

所有分支的 Future 同时进行，第一个完成的分支被执行，其余分支的 Future 被丢弃（取消）。

多个分支同时就绪时，默认随机选一个（避免某个分支永远抢不到）。需要固定优先级时（例如“停机信号优先”），在开头写 biased; ，按书写顺序检查。

分支可以带模式和条件：Some(msg) = rx.recv() =&gt; ... ；模式不匹配时该分支被禁用。

select! 最常见的用法是在循环中同时等待“工作”和“停机信号”，11.9 节的周期任务就是这样。

取消安全（精通）：未被选中的分支会在它的任意一个 .await 点被丢弃。如果一个操作“执行到一半被丢弃会丢数据”（例如从流中已经读取了一部分字节），就称为不是取消安全的。Tokio 文档为每个方法标注了是否取消安全：mpsc::Receiver::recv 、sleep 、CancellationToken::cancelled 是安全的；AsyncReadExt::read_exact 不是。

### 11.5.4 【入门】超时、睡眠与定时
```rust
use std::time::Duration;
use tokio::time::{interval, sleep, timeout};

#[tokio::main]
async fn main() {
    // timeout：给任意 Future 加上时限
    match timeout(Duration::from_millis(300), query_stock(1)).await {
        Ok(stock) => println!("库存 {stock}"),
        // 500ms 的查询会在这里超时
        Err(_elapsed) => println!("查询超时"),
    }

    sleep(Duration::from_millis(10)).await;
    // interval：周期性触发，第一次 tick 立即完成
    let mut ticker = interval(Duration::from_secs(1));
    for _ in 0..3 {
        ticker.tick().await;
        println!("心跳");
    }
}
```

interval 与“循环中 sleep”的区别：interval 按固定节拍触发，任务执行耗时不会累积漂移；如果某次执行超时错过了节拍，由 set_missed_tick_behavior 决定是补发（Burst，默认）、顺延（Delay）还是跳过（Skip）。后台清理类任务通常选 Delay，避免恢复后瞬间连续执行多次。

## 11.6 异步同步原语与通道

### 11.6.1 【入门】tokio::sync::Mutex 还是 std::sync::Mutex

第 7.9.2 节已经给出结论，这里给出代码对比：
```rust
use std::collections::HashMap;
use std::sync::{Arc, Mutex};

// 正确：临界区内没有 .await，用标准库 Mutex，更快
async fn record_hit(cache: Arc<Mutex<HashMap<String, u64>>>, key: String) {
    let mut map = cache.lock().expect("锁已中毒");
    *map.entry(key).or_default() += 1;

// 守卫在这里释放，之后才可能有 .await
}

// 需要在持锁期间 .await 时，才用 tokio::sync::Mutex
async fn refresh_token(token: Arc<tokio::sync::Mutex<String>>) {
    // 异步加锁：等待时让出线程
    let mut t = token.lock().await;

    // 持锁期间 await：保证同一时刻只有一个任务在刷新
    *t = fetch_new_token().await;
}
async fn fetch_new_token() -> String { "new-token".into() }
```

| 对比 | std::sync::Mutex | tokio::sync::Mutex |
| --- | --- | --- |
| 加锁 | lock() ，阻塞等待 | lock().await ，异步等待 |
| 守卫能否跨.await | 语法上可能跨越，但会使 Future 通常不满足 Send，且可能造成死锁；应在 await 前释放 | 能 |
| 性能 | 快 | 较慢（内部用信号量实现） |
| 中毒 | 有 | 没有 |
| 推荐 | 默认选择 | 只在持锁期间必须 await 时使用 |

### 11.6.2 【进阶】Semaphore：限制并发数
```rust
use std::sync::Arc;
use tokio::sync::Semaphore;

#[tokio::main]
async fn main() {
    // 最多 3 个并发调用下游
    let limit = Arc::new(Semaphore::new(3));
    let mut set = tokio::task::JoinSet::new();
    for id in 0..10 {
        let limit = Arc::clone(&limit);
        set.spawn(async move {
            // 拿不到许可就等待
            let _permit = limit.acquire_owned().await.expect("信号量未关闭");
            call_downstream(id).await
        // _permit 在任务结束时 drop，归还许可
        });
    }
    while set.join_next().await.is_some() {}
}
async fn call_downstream(_id: i32) {}
```

信号量是“舱壁隔离”（第 39 章）的基础：给每个下游依赖分配固定数量的并发名额，一个依赖变慢最多占满它自己的名额，不会拖垮整个服务。数据库连接池内部也是用信号量限制连接数。

### 11.6.3 【进阶】四种异步通道

| 通道 | 发送者/接收者 | 特点 | 典型用途 |
| --- | --- | --- | --- |
| mpsc::channel(n) | 多 / 一 | 有界队列，满时 send().await 等待（背压） | 任务队列、日志写入、Outbox 投递 |

| 通道 | 发送者/接收者 | 特点 | 典型用途 |
| --- | --- | --- | --- |
| oneshot::channel() | 一 / 一 | 只发送一个值 | 请求-响应：把结果送回发起者（Actor 模式的回复通道） |
| broadcast::channel(n) | 多 / 多 | 每个接收者都收到每条消息；落后太多会丢消息并收到 Lagged 错误 | 事件通知、配置变更广播 |
| watch::channel(v) | 多 / 多 | 只保留最新值，接收者只关心“当前状态” | 停机信号、配置热更新、健康状态 |
```rust
use tokio::sync::{mpsc, oneshot};

enum Command {
    Deduct { product_id: i64, qty: i32, reply: oneshot::Sender<bool> },
}

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel::<Command>(100);

    // Actor：唯一拥有库存数据的任务，无需任何锁
    tokio::spawn(async move {
        let mut stock = std::collections::HashMap::from([(1_i64, 5_i32)]);
        while let Some(cmd) = rx.recv().await {
            match cmd {
                Command::Deduct { product_id, qty, reply } => {
                    let left = stock.entry(product_id).or_insert(0);
                    let ok = *left >= qty;
                    if ok { *left -= qty; }

                    // 请求方可能已经放弃等待，忽略发送失败
                    let _ = reply.send(ok);
                }
            }
        }
    });

    let (reply_tx, reply_rx) = oneshot::channel();
    tx.send(Command::Deduct { product_id: 1, qty: 2, reply: reply_tx }).await.expect("Actor已退出");
    println!("扣减结果：{}", reply_rx.await.expect("Actor 未回复"));
}
```

这是第 7.9.3 节练习 4 的异步版本。

### 11.6.4 【进阶】Notify 与 OnceCell

tokio::sync::Notify ：最轻量的“唤醒”原语，一个任务 notified().await 等待，另一个任务notify_one() 唤醒它，不携带数据。

tokio::sync::OnceCell ：异步的一次性初始化，get_or_init(|| async { 连接数据库}).await ，多个任务同时首次访问时只初始化一次。

## 11.7 取消与优雅停机

### 11.7.1 【入门】drop 即取消

Rust 中取消一个 Future 的方式就是丢弃它：select! 中未被选中的分支、timeout 超时后的Future、被 abort() 的任务、被 drop 的 JoinSet ，都在它们当前的 .await 处停止，并依次执行局部变量的Drop（第 2.2.6 节的 RAII 依然生效：锁守卫释放、事务回滚）。

这带来一个后端中非常重要的现象：客戶端断开连接时，服务端的 handler Future 会被丢弃。如果handler 在“扣了库存、还没写订单”之间被取消，数据库事务会因 drop 而回滚，这正是第 14 章坚持“多步写操作放在一个事务里”的原因。必须执行完的后台工作（发送通知）应当 spawn 成独立任务，与请求的生命周期解耦。

### 11.7.2 【进阶】CancellationToken

tokio-util crate 的 CancellationToken 是协调“一组任务一起停止”的标准工具：
```rust
use std::time::Duration;
use tokio_util::sync::CancellationToken;

#[tokio::main]
async fn main() {
    let token = CancellationToken::new();

    // 克隆的 token 与原 token 联动
    let worker_token = token.clone();
    let worker = tokio::spawn(async move {
        loop {
            tokio::select! {
                // 优先检查取消信号
                biased;
                _ = worker_token.cancelled() => { println!("收到停机信号，清理后退出"); break; }
                _ = tokio::time::sleep(Duration::from_millis(100)) => println!("处理一批任务"),
            }
        }
    });

    tokio::time::sleep(Duration::from_millis(350)).await;

    // 通知所有持有克隆的任务
    token.cancel();
    worker.await.expect("worker 不应 panic");
}
```

token.child_token() 创建子令牌：父令牌取消时子令牌一起取消，子令牌单独取消不影响父令牌，适合“取消整个服务”与“取消某个请求的子任务”两级控制。

### 11.7.3 【进阶】优雅停机的完整流程

Kubernetes 删除 Pod 时（滚动发布、缩容）会先发送 SIGTERM，默认等待 30 秒后再强制杀死进程（第23 章）。一个合格的服务在收到 SIGTERM 后应当：

1. 停止接受新连接 / 新请求（第 12 章 Axum 的 with_graceful_shutdown ）。

2. 等待正在处理的请求完成。

3. 通知后台任务停止（CancellationToken），等待它们完成当前一轮工作。

4. 刷新日志、追踪数据缓冲区，关闭数据库连接池。

5. 在超时时间内退出；超时仍未完成则放弃等待，直接退出。

11.9 节的项目实现第 3~5 步，第 12 章补上第 1、2 步。

## 11.8 原理与陷阱（精通）

### 11.8.1 Future trait 与轮询
```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> { Ready(T), Pending }
```

运行时反复调用任务的 poll ：

返回 Ready(v) ：任务完成。

返回 Pending ：还没好。返回之前，Future 必须安排好“将来某个时刻通过 cx.waker()叫醒我”--例如把 Waker 登记到 socket 的可读事件上。运行时于是把这个任务挂起，去 poll 其他任务；socket 有数据时，操作系统通知（Linux 的 epoll、macOS 的 kqueue）→ Tokio 的 I/O 驱动调用Waker → 任务回到就绪队列 → 再次被 poll。

async fn 被编译成状态机：每个 .await 是一个状态，局部变量是状态机的字段。所以 Future 的大小取决于跨越 .await 存活的局部变量；在 async 函数中声明一个 100 KB 的数组并跨越 await，这个Future 就有 100 KB，spawn 时会被分配到堆上。

### 11.8.2 Pin

状态机中可能出现“字段 A 是对字段 B 的引用”（例如局部变量借用了另一个局部变量，并且跨越await），即自引用结构（第 2.5.7 节）。自引用结构一旦在内存中被移动，内部引用就失效了。Pin&lt;&amp;mutSelf&gt; 保证 Future 在被 poll 之后不会再被移动。日常开发中你几乎不需要直接处理 Pin，只在两种场景会遇到：手动实现 Future、需要 poll 一个 !Unpin 的 Future 的引用时用 tokio::pin!(fut) 或Box::pin(fut) 。

### 11.8.3 “future cannot be sent between threads safely”

这是异步 Rust 最常见的报错。原因是：tokio::spawn 要求 Future 是 Send，而 Future 是 Send 的条件是所有跨越 .await 存活的局部变量都是 Send。
```rust
async fn bad(cache: std::sync::Arc<std::sync::Mutex<Vec<i32>>>) {
    // MutexGuard 不是 Send
    let guard = cache.lock().expect("锁已中毒");

    // guard 跨越了 await
    tokio::time::sleep(std::time::Duration::from_millis(1)).await;
    println!("{}", guard.len());
}
// tokio::spawn(bad(cache)) 报错：future cannot be sent between threads safely

async fn good(cache: std::sync::Arc<std::sync::Mutex<Vec<i32>>>) {
    let len = {
        let guard = cache.lock().expect("锁已中毒");
        guard.len()
    // guard 在 await 之前就释放了
    };
    tokio::time::sleep(std::time::Duration::from_millis(1)).await;
    println!("{len}");
}
```

常见的非 Send 值：std::sync::MutexGuard 、Rc 、RefCell 的借用守卫、某些第三方库的句柄。解决方法：用代码块缩小作用域，让它们在 .await 之前被 drop；或改用 Send 的替代品（Arc、tokio 的锁）。编译器的报错会指出“这个值在这里被持有、在那里跨越了 await”，按它的提示调整即可。

### 11.8.4 work-stealing 调度器

多线程运行时的每个工作线程有自己的本地任务队列，另有一个全局队列。线程空闲时先查本地队列，再查全局队列，最后从其他线程的队列中“偷”一半任务。这保证了负载均衡，也意味着同一个任务在两次poll 之间可能换到另一个线程执行--这正是 spawn 要求 Send 的根本原因。

Tokio 还有一个“协作预算”机制：一个任务连续执行一定数量的操作后，Tokio 的资源（通道、socket）会主动返回 Pending，迫使它让出线程，避免某个永远就绪的任务饿死其他任务。

### 11.8.5 调试工具

tokio-console：类似 top 的实时任务监视器，显示每个任务的 poll 次数、忙碌时间、等待时间，能直接发现“长时间不让出的任务”和“永远不完成的任务”。需要在程序中启用 console-subscriber 并以 --cfg tokio_unstable 编译。

tracing（第 15 章）：为异步函数加 #[instrument] ，在日志中看到每个请求的完整执行链路。

RUSTFLAGS="--cfg tokio_unstable" 还解锁了运行时指标（Handle::metrics() ），可以导出到Prometheus（第 38 章）。

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| E0277 | future cannot be sent between threads safely | 非 Send 的值跨越了.await | 缩小作用域；换用Send 的类型 |

### 11.9.4 第 3 步：信号处理 shutdown.rs

文件：rustmall/monolith/src/shutdown.rs （新建）
```rust
//! 停机信号处理。

use tokio_util::sync::CancellationToken;

/// 等待 Ctrl+C（所有平台）或 SIGTERM（Unix），收到任一信号后取消 `token`。
///
/// 本地开发按 Ctrl+C 发送的是 SIGINT；Docker 停止容器、Kubernetes 删除 Pod 时发送的是 SIGTERM。
/// 某个信号无法监听时只打印错误并忽略它，另一个信号仍然有效。
pub async fn wait_for_signal(token: CancellationToken) {
    let ctrl_c = async {
        if let Err(e) = tokio::signal::ctrl_c().await {
            eprintln!("无法监听 Ctrl+C：{e}");
            std::future::pending::<()>().await;
        }
    };

    #[cfg(unix)]
    let terminate = async {
        match tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate()) {
            Ok(mut sig) => {
                sig.recv().await;
            }
            Err(e) => {
                eprintln!("无法监听 SIGTERM：{e}");
                std::future::pending::<()>().await;
            }
        }
    };

    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        () = ctrl_c => {}
        () = terminate => {}
    }
    token.cancel();
}
```

代码精讲：

std::future::pending::&lt;()&gt;() 是一个永远不会完成的 Future。监听失败时让这个分支“永远等下去”，这样 select! 只会被另一个信号唤醒，而不会因为监听失败就立刻取消、导致服务刚启动就退出。

#[cfg(unix)] / #[cfg(not(unix))] （第 8.6 节）：SIGTERM 是 Unix 概念，Windows 上没有，所以那里用 pending 占位，两个平台都能编译。

两个 let terminate 只有一个会被编译，不存在重复定义。

这个函数依赖操作系统信号，不写单元测试，在 11.9.8 节手动验证。

### 11.9.5 第 4 步：周期任务 background.rs

文件：rustmall/monolith/src/background.rs （新建）
```rust
//! 后台周期任务。

use std::future::Future;
use std::time::Duration;

use tokio::time::MissedTickBehavior;
use tokio_util::sync::CancellationToken;

/// 每隔 `period` 执行一次 `job`，直到 `token` 被取消，返回执行的次数。
///
/// - 第一次执行在启动时立即发生。
/// - 某次执行耗时超过周期时，下一次立即开始并从那时起重新计时，不会连续补跑错过的次数。
/// - 取消优先：已取消时不再开始新的一次；正在执行的那一次会完整结束。
pub async fn run_periodic<F, Fut>(period: Duration, token: CancellationToken, mut job: F) -> u64
where
    F: FnMut() -> Fut,
    Fut: Future<Output = ()>,
{
    let mut ticker = tokio::time::interval(period);
    ticker.set_missed_tick_behavior(MissedTickBehavior::Delay);
    let mut runs = 0;
    loop {
        tokio::select! {
            biased;
            () = token.cancelled() => break,
            _ = ticker.tick() => {
                job().await;
                runs += 1;
            }
        }
    }
    runs
}

#[cfg(test)]
mod tests {
    use super::*;
    use std::sync::Arc;
    use std::sync::atomic::{AtomicU64, Ordering};

    #[tokio::test(start_paused = true)]
    async fn runs_on_schedule_until_cancelled() {
        let token = CancellationToken::new();
        let counter = Arc::new(AtomicU64::new(0));
        let c = Arc::clone(&counter);
        let handle = tokio::spawn(run_periodic(Duration::from_secs(10), token.clone(), move || 
            {
            let c = Arc::clone(&c);
            async move {
                c.fetch_add(1, Ordering::SeqCst);
            }
        }));

        // 暂停的时间会被自动推进，瞬间完成
        tokio::time::sleep(Duration::from_secs(35)).await;
        token.cancel();

        // 第 0、10、20、30 秒各执行一次
        assert_eq!(handle.await.expect("任务不应 panic"), 4);
        assert_eq!(counter.load(Ordering::SeqCst), 4);
    }

    #[tokio::test(start_paused = true)]
    async fn already_cancelled_runs_nothing() {
        let token = CancellationToken::new();
        token.cancel();
        let runs = run_periodic(Duration::from_secs(1), token, || async {}).await;
        assert_eq!(runs, 0, "biased 保证先检查取消，立即就绪的第一次 tick 不会被执行");
    }

    #[tokio::test(start_paused = true)]
    async fn slow_job_delays_next_run() {
        let token = CancellationToken::new();
        let handle = tokio::spawn(run_periodic(Duration::from_secs(10), token.clone(), || 
            async {
            // 每次执行 25 秒，超过 10 秒的周期
            tokio::time::sleep(Duration::from_secs(25)).await;
        }));

        tokio::time::sleep(Duration::from_secs(60)).await;
        token.cancel();

        // 0~25 秒第 1 次；25~50 秒第 2 次（顺延，不补跑）；50~75 秒第 3 次，
        // 第 60 秒取消时第 3 次正在执行，执行完后才退出
        assert_eq!(handle.await.expect("任务不应 panic"), 3);
    }
}
```

代码精讲：

泛型参数 F: FnMut() -&gt; Fut, Fut: Future&lt;Output = ()&gt; ：调用方传入一个“每次调用都返回一个新 Future”的闭包。这是 Rust 中接收“异步回调”的标准写法（第 6.4.5 节的闭包知识 + 本章的 Future）。用 FnMut 而不是 Fn ，允许闭包修改自己捕获的状态（例如计数）。

biased; ：取消分支写在前面并加 biased ，保证“已经取消”时绝不会再开始新的一次执行。没有 biased 时，第一次 tick 立即就绪、取消也已就绪，select! 会随机选择，测试already_cancelled_runs_nothing 就会时好时坏。

job().await 在分支体内执行：一旦进入分支，就不再处于 select! 的等待中，取消信号不会打断它--这符合“正在执行的那一次完整结束”的语义（例如清理过期购物车时，不希望删到一半被打断）。需要可打断的长任务时，把 token 传进 job 内部自行检查。

MissedTickBehavior::Delay ：配合测试 slow_job_delays_next_run 理解：默认的 Burst模式在第 25 秒结束后会连续补跑错过的 10、20 秒两次；Delay 模式只立即执行一次，并从那时起重新计时。

可控时间测试：#[tokio::test(start_paused = true)] 让测试运行时的时钟一开始就是暂停的。当所有任务都在等待定时器时，Tokio 自动把时钟拨到最近的定时器触发时刻。所以测试中 sleep(60秒)和那些 10 秒、25 秒的定时器都会瞬间“完成”，并且执行顺序完全确定，不受机器负载影响。这需要dev-dependencies 中开启的 test-util feature。测试定时、超时、重试逻辑时，这是唯一可靠的方法--用真实时间测试既慢又不稳定。

文件：rustmall/monolith/src/main.rs （替换 cargo 生成的全部内容）
```rust
//! RustMall 单体服务入口。

use std::time::Duration;

use monolith::{background, shutdown};
use tokio_util::sync::CancellationToken;

/// 收到停机信号后，等待后台任务结束的最长时间。
const SHUTDOWN_GRACE: Duration = Duration::from_secs(10);

#[tokio::main]
async fn main() {
    let token = CancellationToken::new();
    tokio::spawn(shutdown::wait_for_signal(token.clone()));

    let cleaner = tokio::spawn(background::run_periodic(
        Duration::from_secs(5),
        token.clone(),
        || async { println!("[后台] 清理过期的购物车") },
    ));

    println!("RustMall 单体服务已启动（第 11 章骨架），按 Ctrl+C 退出");
    token.cancelled().await;
    println!("收到停机信号，等待后台任务结束……");

    match tokio::time::timeout(SHUTDOWN_GRACE, cleaner).await {
        Ok(Ok(runs)) => println!("后台任务已停止，共执行 {runs} 次"),
        Ok(Err(e)) => eprintln!("后台任务异常退出：{e}"),
        Err(_) => eprintln!("后台任务未能在 {SHUTDOWN_GRACE:?} 内停止，强制退出"),
    }
}
```

这就是 11.7.3 节停机流程的第 3~5 步：取消信号通知后台任务；timeout 限定等待时间；cleaner返回的 Result 区分“正常结束”和“任务 panic”。main 返回后运行时被关闭，剩余的任务（例如还在等待信号的 wait_for_signal ）会被丢弃。日志输出暂时用 println! ，第 15 章换成 tracing。

### 11.9.10 本章小结

后端是 I/O 密集型程序，异步任务比线程轻量几个数量级；任务是协作式调度的，只在.await 处让出线程，阻塞操作必须交给 spawn_blocking 。

async fn 返回惰性的 Future，.await 驱动它执行；#[tokio::main] 创建运行时并block_on主 Future。

tokio::spawn 创建独立任务（要求 Send + 'static ），JoinSet 管理一组任务；join! 、try_join! 并发等待，select! 竞争等待，biased 固定优先级。

timeout 、sleep 、interval 处理时间；所有外部调用都应有超时。

临界区无 await 用标准库锁；Semaphore 限制并发；mpsc、oneshot、broadcast、watch 四种通道各有用途；Actor 模式用消息代替锁。

取消就是 drop Future，RAII 保证清理；CancellationToken 协调一组任务停止；优雅停机要响应SIGTERM 并限时等待。

Future 通过 poll 与 Waker 工作，async fn 编译为状态机；跨越 await 的值必须是 Send 才能spawn。

RustMall 有了第一个可执行程序 monolith：信号处理、可取消的周期任务和确定性的时间测试。

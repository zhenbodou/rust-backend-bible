# 第 29 章 Outbox 与 Inbox：可靠事件链路

上一章已经亲手观察：Kafka 可以保存记录，消费组可以独立恢复，确认与提交也有不确定窗口。但商品数据库里的一次 UPDATE，仍不会自动成为一条可靠事件。仅在 SQL 之后调用 send，会留下数据库成功、进程退出、消息尚未发送的空隙。

本章给 RustMall 加上完整的一段异步链路：商品事务同时写 products 和 product_outbox；中继从 Outbox 领取待发送事件并送入 Kafka；投影消费者在另一个数据库中同时写 Inbox 和 catalog_view，业务事务成功后再提交 offset。同时给公共创建商品接口加入幂等键，避免用户因响应不确定而反复创建不同商品。

学完应能解释业务事务与网络确认的边界，重现 Outbox 插入失败时商品也回滚，验证同一创建命令并发重试只产生一个结果，并在事件重复、乱序与下架后仍保持读模型正确。本章不宣称跨 PostgreSQL 和 Kafka 建立了一次原子提交；它通过持久化事实、重试与幂等，让失败变成可以恢复的状态。

## 29.1 先把失败窗口画清楚

### 29.1.1 【入门】先写数据库，再发消息

顺序是 A：提交商品变化；B：发送消息。若进程在 A 后、B 前退出，商品已经改变，消费者却永远不知道。重启程序也无法仅凭内存知道哪些商品变更需要补发。

把 A 和 B 写进同一个 async 函数，并没有增加跨系统事务。即使每一步都有 Result，调用方也没有得到一份持久化的“尚未完成 B”记录。错误处理必须围绕已经发生的状态设计，不能只把日志写得更详细。

### 29.1.2 【进阶】先发消息，再写数据库

颠倒顺序也有问题：消息已经交付，数据库提交却失败，消费者处理了从未形成的商品事实。尝试再发一条撤销消息，本身还会遇到发送失败、乱序与重复的问题。

因此第一步要缩小原子边界：商品和待发送事件都写入同一个 PostgreSQL 事务。网络发送放到事务外，允许重试；消费者也需要在自己的事务中对重复做出可靠判断。

### 29.1.3 【入门】Outbox 是事务内的待办事实

Outbox 是数据库里的待发布事件表，不是进程中的临时队列。商品变化与事件插入共同提交，要么都存在，要么都不存在。服务重启后，中继仍能找到未交付事件。

这保证的是“已提交业务事实有对应待发布记录”，不是“Kafka 已收到”。Outbox 积压、权限错误、坏事件和长期依赖故障仍需观察和处理；如果中继永远不运行，事件不会自行穿过网络。

### 29.1.4 【进阶】Inbox 是消费事务里的证据

Inbox 记录某个逻辑消费者已处理过哪些 event_id，并保存内容摘要。它与投影更新处于同一个数据库事务：不能先记已处理再丢掉业务结果，也不能先改投影而来不及记录去重事实。

消费者崩溃后可能从 Kafka 重读同一事件，Inbox 让它识别重复，随后安全推进 offset。这个能力只覆盖与 Inbox 同事务的数据库副作用，不能自动保护发邮件、调用支付或其他外部动作。

### 29.1.5 【精通】三个“只一次”不能混为一谈

创建命令幂等解决“同一用户重试同一个创建请求”；Outbox 事件身份解决“同一事实多次网络发送”；Inbox 解决“同一消费身份多次处理同一事件”。它们拥有不同的键和持久化位置。

只做其中一种仍会留下其他重复来源。比如客户端每次重试都换创建键，会产生两个合法商品；即使每个商品事件在 Inbox 只处理一次，重复创建本身也没有被消除。

## 29.2 用最小反例验证事务，而非只看成功路径

### 29.2.1 【入门】实验预期

先设想故意让 product_outbox 插入失败。如果商品仍然出现在 products，说明两次写入不在同一个原子事务里；如果商品也没有留下，才符合本章设计。

后面的数据库测试会在专用测试库为 Outbox 加一个拒绝所有合法修订的 CHECK 约束，再调用创建，断言返回失败且商品数量为零。它不会在读者已有数据上执行，也不会把测试约束带到正常迁移。

### 29.2.2 【进阶】失败注入的证据意义

成功创建一条商品和一条事件，只能证明某次正常执行完成，无法排除中间提交。故意让第二步失败，才有机会观察第一步是否被一并撤销。

同样，测试应查询真实数据库行数，而不是只看函数返回 Err。错误可能发生在商品已经独立提交之后；单看返回值无法证明持久化原子性。

## 29.3 增加商品版本与 Outbox 结构

### 29.3.1 【入门】完整第二次商品迁移

在原来的 services/catalog/migrations 中新增 0002_product_outbox.sql，不修改已经执行过的 0001：
```sql
ALTER TABLE products ADD COLUMN revision BIGINT NOT NULL DEFAULT 1 CHECK(revision>0);
CREATE TABLE product_outbox (
   event_id UUID PRIMARY KEY,
   aggregate_id BIGINT NOT NULL,
   revision BIGINT NOT NULL,
   payload JSONB NOT NULL,
   occurred_at TIMESTAMPTZ NOT NULL DEFAULT now(),
   attempts INT NOT NULL DEFAULT 0,
   next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
   lease_token UUID,
   leased_until TIMESTAMPTZ,
   delivered_at TIMESTAMPTZ,
   last_error TEXT,
   UNIQUE(aggregate_id,revision)
);
CREATE INDEX product_outbox_pending_idx ON product_outbox(next_attempt_at,occurred_at)
   WHERE delivered_at IS NULL;
CREATE TABLE product_create_receipts (
   actor_id BIGINT NOT NULL,
   command_id UUID NOT NULL,
   request_hash BYTEA NOT NULL,
   response JSONB,
   PRIMARY KEY(actor_id,command_id)
);
-- Bootstrap unchanged legacy products from the same transaction as this migration.
INSERT INTO product_outbox(event_id,aggregate_id,revision,payload)
SELECT event_id,id,revision,
       jsonb_build_object('schema_version',1,'kind','product.snapshot.v1',
         'event_id',event_id,'aggregate_id',id,'revision',revision,
         'occurred_at_unix_ms',(extract(epoch FROM now())*1000)::bigint,
         'payload',jsonb_build_object('id',id,'name',name,'price_cents',price_cents,
           'stock',stock,'listed',delisted_at IS NULL))
FROM (SELECT p.*,gen_random_uuid() AS event_id FROM products p) AS snapshots;
```

products.revision 从一开始；后续修改与下架在同一 UPDATE 中加一。业务数据与版本一起锁定更新，比应用先读旧数字、再手工计算写回更容易避免并发覆盖。

### 29.3.2 【进阶】唯一约束如何表达事实

product_outbox 的 event_id 是事件主键，(aggregate_id,revision) 还要求同一商品同一修订只对应一个待发布事实。payload 保留整个 Envelope，发送重试从这里读取，而不是每次重新查询当前商品再生成内容。

否则商品已经变化到 revision 5 时，重发 revision 3 却读到最新价格，就会把旧版本编号与新内容错误组合。可靠重试必须重用原事件身份和原始内容。

### 29.3.3 【进阶】交付、重试与租约字段

delivered_at 标识中继已收到 Kafka 交付成功并完成本地记录；attempts 统计领取尝试；next_attempt_at 控制下一次可领取时间；last_error 保存有界诊断文本。

lease_token 与 leased_until 表达中继临时所有权。租约过期后其他实例可以重新领取，避免进程退出后永远占住事件。事件是否真的发到 Kafka 与租约是否仍属于当前中继是两件事，后面会用令牌条件更新隔离旧领取者。

### 29.3.4 【进阶】旧商品如何形成初始快照

迁移末尾为已有产品插入初始 Outbox，包括已经下架的商品。为每行生成的 UUID 同时写进 event_id 列和 Envelope，避免“表里的事件身份”和“发出去的身份”各自生成一次而不匹配。

下架状态同样需要进入初始事件，不能只导出可见商品。否则旧状态重放时，消费者可能重新展示已经下架的产品。迁移创建的是当前快照，不可能凭空恢复从未记录过的每一步历史变化。

### 29.3.5 【精通】大表回填不能照搬小库实验

教学库在迁移事务内一次性回填，便于观察结构与数据共同完成。生产大表可能带来长事务、锁等待、日志体积和发布时间问题，需要分批回填、明确版本边界，并与正在发生的写入协调。

执行前必须估算数据量并在恢复副本演练。本章验证小规模迁移的身份与内容对应，不将两条测试商品的成功推广成亿级数据在线迁移已经安全。

## 29.4 同一事务中的商品与事件写入

### 29.4.1 【入门】完整事务存储模块

新增 messaging/src/store.rs：
```rust
use crate::event::{Envelope, Snapshot, retry_delay_secs};
use serde::Serialize;
use sha2::{Digest, Sha256};
use sqlx::{PgPool, Postgres, Transaction, types::Json};
use uuid::Uuid;

#[derive(Debug, Clone, Serialize)]
pub struct Draft {
    pub name: String,
    pub price_cents: i64,
    pub stock: i32,
}
#[derive(sqlx::FromRow)]
struct Row {
    id: i64,
    name: String,
    price_cents: i64,
    stock: i32,
    listed: bool,
    revision: i64,
}
impl Row {
    fn event(self) -> Envelope {
        Envelope::new(
            Snapshot {
                id: self.id,
                name: self.name,
                price_cents: self.price_cents,
                stock: self.stock,
                listed: self.listed,
            },
            self.revision,
        )
    }
}
fn protocol(error: impl std::fmt::Display) -> sqlx::Error {
    sqlx::Error::Protocol(error.to_string())
}
async fn append(tx: &mut Transaction<'_, Postgres>, event: &Envelope) -> Result<(), sqlx::Error> {
    event.validate().map_err(protocol)?;
    sqlx::query(
        "INSERT INTO product_outbox(event_id,aggregate_id,revision,payload) VALUES($1,$2,$3,$4)",
    )
    .bind(event.event_id)
    .bind(event.aggregate_id)
    .bind(event.revision)
    .bind(Json(event))
    .execute(&mut **tx)
    .await?;
    Ok(())
}
async fn insert(
    tx: &mut Transaction<'_, Postgres>,
    draft: &Draft,
) -> Result<Envelope, sqlx::Error> {
    let row=sqlx::query_as::<_,Row>("INSERT INTO products(name,price_cents,stock) VALUES($1,$2,$3) RETURNING id,name,price_cents,stock,true AS listed,revision")
        .bind(&draft.name).bind(draft.price_cents).bind(draft.stock).fetch_one(&mut **tx).await?;
    let event = row.event();
    append(tx, &event).await?;
    Ok(event)
}
pub async fn create(pool: &PgPool, draft: &Draft) -> Result<Envelope, sqlx::Error> {
    let mut tx = pool.begin().await?;
    let event = insert(&mut tx, draft).await?;
    tx.commit().await?;
    Ok(event)
}
pub async fn update(
    pool: &PgPool,
    id: i64,
    draft: &Draft,
) -> Result<Option<Envelope>, sqlx::Error> {
    let mut tx = pool.begin().await?;
    let row=sqlx::query_as::<_,Row>("UPDATE products SET name=$2,price_cents=$3,stock=$4,updated_at=now(),revision=revision+1 WHERE id=$1 AND delisted_at IS NULL RETURNING id,name,price_cents,stock,true AS listed,revision")
        .bind(id).bind(&draft.name).bind(draft.price_cents).bind(draft.stock).fetch_optional(&mut *tx).await?;
    let Some(row) = row else { return Ok(None) };
    let event = row.event();
    append(&mut tx, &event).await?;
    tx.commit().await?;
    Ok(Some(event))
}
pub async fn delist(pool: &PgPool, id: i64) -> Result<Option<Envelope>, sqlx::Error> {
    let mut tx = pool.begin().await?;
    let row=sqlx::query_as::<_,Row>("UPDATE products SET delisted_at=now(),updated_at=now(),revision=revision+1 WHERE id=$1 AND delisted_at IS NULL RETURNING id,name,price_cents,stock,false AS listed,revision")
        .bind(id).fetch_optional(&mut *tx).await?;
    let Some(row) = row else { return Ok(None) };
    let event = row.event();
    append(&mut tx, &event).await?;
    tx.commit().await?;
    Ok(Some(event))
}

#[derive(Debug, thiserror::Error)]
pub enum CommandError {
    #[error("idempotency key already used with different input")]
    Conflict,
    #[error(transparent)]
    Database(#[from] sqlx::Error),
}
pub async fn create_once(
    pool: &PgPool,
    actor: i64,
    key: Uuid,
    draft: &Draft,
) -> Result<Envelope, CommandError> {
    if actor <= 0 {
        return Err(protocol("trusted actor required").into());
    }
    let hash = Sha256::digest(serde_json::to_vec(draft).map_err(protocol)?).to_vec();
    let mut tx = pool.begin().await?;
    let inserted=sqlx::query("INSERT INTO product_create_receipts(actor_id,command_id,request_hash) VALUES($1,$2,$3) ON CONFLICT DO NOTHING")
        .bind(actor).bind(key).bind(&hash).execute(&mut *tx).await?.rows_affected();
    if inserted == 0 {
        let (stored_hash,response):(Vec<u8>,Option<Json<Envelope>>)=sqlx::query_as("SELECT request_hash,response FROM product_create_receipts WHERE actor_id=$1 AND command_id=$2")
            .bind(actor).bind(key).fetch_one(&mut *tx).await?;
        if stored_hash != hash {
            return Err(CommandError::Conflict);
        };
        let response = response
            .ok_or_else(|| protocol("incomplete command receipt"))?
            .0;
        tx.commit().await?;
        return Ok(response);
    }
    let event = insert(&mut tx, draft).await?;
    sqlx::query(
        "UPDATE product_create_receipts SET response=$3 WHERE actor_id=$1 AND command_id=$2",
    )
    .bind(actor)
    .bind(key)
    .bind(Json(&event))
    .execute(&mut *tx)
    .await?;
    tx.commit().await?;
    Ok(event)
}

#[derive(sqlx::FromRow)]
pub struct Lease {
    pub event_id: Uuid,
    pub payload: Json<Envelope>,
    pub attempts: i32,
    pub lease_token: Uuid,
}
pub async fn claim_one(pool: &PgPool) -> Result<Option<Lease>, sqlx::Error> {
    let token = Uuid::new_v4();
    sqlx::query_as::<_,Lease>(
        "WITH candidate AS (SELECT event_id FROM product_outbox WHERE delivered_at IS NULL AND next_attempt_at<=now() AND (leased_until IS NULL OR leased_until<now()) ORDER BY occurred_at,event_id FOR UPDATE SKIP LOCKED LIMIT 1) UPDATE product_outbox AS o SET lease_token=$1,leased_until=now()+interval '30 seconds',attempts=attempts+1 FROM candidate AS c WHERE o.event_id=c.event_id RETURNING o.event_id,o.payload,o.attempts,o.lease_token"
    ).bind(token).fetch_optional(pool).await
}
pub async fn delivered(pool: &PgPool, lease: &Lease) -> Result<bool, sqlx::Error> {
    Ok(sqlx::query("UPDATE product_outbox SET delivered_at=now(),lease_token=NULL,leased_until=NULL,last_error=NULL WHERE event_id=$1 AND lease_token=$2 AND delivered_at IS NULL")
        .bind(lease.event_id).bind(lease.lease_token).execute(pool).await?.rows_affected()==1)
}
pub async fn failed(pool: &PgPool, lease: &Lease, error: &str) -> Result<bool, sqlx::Error> {
    let bounded: String = error.chars().take(500).collect();
    Ok(sqlx::query("UPDATE product_outbox SET next_attempt_at=now()+($3::bigint*interval '1 second'),lease_token=NULL,leased_until=NULL,last_error=$4 WHERE event_id=$1 AND lease_token=$2 AND delivered_at IS NULL")
        .bind(lease.event_id).bind(lease.lease_token).bind(retry_delay_secs(lease.attempts)).bind(bounded)
        .execute(pool).await?.rows_affected()==1)
}
```

Draft 是已经通过上层领域校验的写入数据。Row 从 RETURNING 取得真正保存的商品 id、内容与 revision，再创建 Envelope。append 先验证事件，再把同一对象插进 Outbox。

### 29.4.2 【进阶】Transaction 的可变借用贯穿两次写入

create 先 pool.begin，insert 接收 `&mut Transaction`，商品 INSERT 和 append 都通过这条事务连接执行，最后外层 commit。`&mut **tx` 在引用事务的辅助函数中取得底层连接，和前面方法内部的 `&mut *tx` 是不同嵌套层数。

任一步返回错误，控制流不会执行 commit。事务对象丢弃时 SQLx 安排回滚，失败注入测试再从数据库验证没有商品留下。不能在辅助函数里偷偷用 pool 执行 Outbox，否则即使签名里有 tx，也未必真的共用事务。

### 29.4.3 【进阶】更新与下架怎样产生修订

update 在一条 UPDATE 中修改业务列、更新时间，并执行 revision=revision+1，再 RETURNING 新状态。delist 同样递增修订，但生成 listed=false 的完整快照。

两者只匹配未下架行，无匹配返回 None，不产生事件。返回 None 时事务没有业务修改，释放事务即可；有匹配时，事件插入与商品更新共同提交。下架重试仍沿用既有 NotFound 语义，不因为有 Outbox 就改变公共接口结果。

### 29.4.4 【进阶】为什么不在事务中发送 Kafka

如果事务持有商品锁时等待网络，broker 故障会使数据库锁和连接长期占用，其他业务一起受阻。即使发送成功，数据库随后提交失败，消费者仍可能观察到不成立的事实。

本章事务只做数据库内的工作。中继在事务结束以后发送，允许重复但避免没有可靠记录的丢失窗口。代价是消费者看到变更存在传播延迟，公共写入成功不等于投影已经更新。

### 29.4.5 【精通】SQL 字符串也必须实际执行

编译器能检查 Rust 类型，却不会替普通 query 字符串验证所有 SQL 语法。原稿中有 WHERE 条件粘成 ANDnext_attempt_at 和占位符后粘着 AND 的错误，本次恢复为明确的 SQL 词法边界，并通过真实 PostgreSQL 领取与失败调度测试。

这类问题不能靠 PDF 看起来对齐就判定修复。对应仓储需要实际执行到该路径，尤其是很少走到的失败重试与租约续领分支。

## 29.5 创建命令的持久化幂等

### 29.5.1 【入门】公共请求携带什么

Remote 模式下，公共 POST /api/v1/products 现在要求恰好一个 Idempotency-Key 请求头，值为 UUID。同一管理员对同一个创建意图重试时复用该值；输入改变或新的创建意图应使用另一个值。

actor_id 从已经校验的 AdminUser 取得，不接受外部 x-user-id 自报。catalog 的服务令牌仍是上游可信边界的一部分：拥有该凭据的内部调用者有能力声明 actor，因此必须控制凭据分发和访问范围。

### 29.5.2 【进阶】协议新增字段

contracts/proto/catalog.proto 的 CreateProductRequest 新增编号四和五，原字段编号与类型不变：
```protobuf
syntax = "proto3";
package rustmall.catalog.v1;

service Catalog {
  rpc GetProduct(GetProductRequest) returns (Product);
  rpc ListProducts(ListProductsRequest) returns (ListProductsResponse);
  rpc CreateProduct(CreateProductRequest) returns (Product);
  rpc UpdateProduct(UpdateProductRequest) returns (Product);
  rpc DelistProduct(GetProductRequest) returns (DelistProductResponse);
}
message Product {
  int64 id = 1;
  string name = 2;
  int64 price_cents = 3;
  int32 stock = 4;
}
message GetProductRequest { int64 id = 1; }
message ListProductsRequest { int64 limit = 1; int64 offset = 2; }
message ListProductsResponse { repeated Product items = 1; int64 total = 2; }
message CreateProductRequest {
  string name = 1;
  int64 price_cents = 2;
  int32 stock = 3;
  string idempotency_key = 4;
  int64 actor_id = 5;
}
message UpdateProductRequest {
  int64 id = 1;
  string name = 2;
  int64 price_cents = 3;
  int32 stock = 4;
}
message DelistProductResponse {}
```

旧调用者没有新字段时，字符串为空、actor 为零。服务端保留空幂等键的普通创建行为以支持直接教学客户端；公共 Remote HTTP 路径则强制使用幂等键。两者的保证范围不同，不能把裸 RPC 的普通创建也称为幂等创建。

所有手写 CreateProductRequest 初始化都必须加入 `idempotency_key: String::new(), actor_id: 0` 或真实命令值。包括原来的 catalog smoke、数据库测试和远程仓储普通 insert，不能只修改服务端后忽略编译失败的旧调用者。完整章节检查点已经包含这些调用点更新。

### 29.5.3 【进阶】并发请求如何汇聚为一个结果

product_create_receipts 以 (actor_id,command_id) 为主键。create_once 在事务中先尝试 INSERT ... ON CONFLICT DO NOTHING，争取命令处理权。并发相同命令在唯一约束上协调，而不是由进程内 HashMap 判断。

赢得插入的事务创建商品、Outbox，并把响应 Envelope 写进收据后一起提交；另一事务在冲突处理完成后读取已提交收据。若输入摘要一致，直接返回同一商品和事件身份，不再插入商品。

### 29.5.4 【精通】同键不同输入必须冲突

request_hash 根据归一化后的 Draft 编码计算。相同键却改变价格、名称或库存，会与保存摘要不一致，返回冲突，不能悄悄执行另一条业务命令。

收据保存的是首次结果。以后商品已经更新，再重放原创建命令，返回的仍是该命令原结果，不是重新查询的当前商品。这能解释为什么“创建重放响应”和随后 GET 的状态可能不同，接口文档应说清这种时间语义。

### 29.5.5 【精通】收据不能随意清理

删除幂等收据会使原键再次被当作新命令，可能创建重复商品。因此收据保留时间必须与客户端允许重试的窗口、审计和数据恢复策略一致。

本章没有后台自动删除收据，也没有承诺无限历史都必须常驻同一张热表。后面的运维章节会讨论归档、保留与恢复；在此之前，不应为了表看起来干净而定期 truncate。

```rust
        name: value.name,

fn database_error(error: sqlx::Error) -> Status {
    if let Some(db) = error.as_database_error()
        && matches!(db.code().as_deref(), Some("23505" | "23503"))
    {
        return Status::failed_precondition("product conflicts with stored data");
    }
    tracing::error!(%error, "catalog database failure");
    Status::internal("catalog database failure")
}
async fn bounded<T>(future: impl Future<Output = Result<T, sqlx::Error>>) -> Result<T, Status> {
    tokio::time::timeout(Duration::from_millis(700), future)
        .await
        .map_err(|_| Status::deadline_exceeded("catalog query budget exhausted"))?
        .map_err(database_error)
}
pub fn validate_draft(name: &str, price: i64, stock: i32) -> Result<NewProduct, Status> {
    NewProduct::try_new(name, price, stock).map_err(Status::invalid_argument)
}
pub fn validate_id(id: i64) -> Result<i64, Status> {
    if id <= 0 {
        return Err(Status::invalid_argument("id must be positive"));
    }
    Ok(id)
}
pub fn validate_page(limit: i64, offset: i64) -> Result<(), Status> {
    if !(1..=100).contains(&limit) || offset < 0 {
        return Err(Status::invalid_argument(
            "limit must be 1..100 and offset nonnegative",
        ));
    }
    Ok(())
}

#[tonic::async_trait]
impl Catalog for CatalogApi {
    async fn get_product(
        &self,
        request: Request<GetProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let id = validate_id(request.into_inner().id)?;
        let row = bounded(sqlx::query_as::<_, Row>(
             "SELECT id,name,price_cents,stock FROM products WHERE id=$1 AND delisted_at IS NULL"
         ).bind(id).fetch_optional(&self.pool)).await?
             .ok_or_else(|| Status::not_found("product not found"))?;
        Ok(Response::new(row.wire()?))
    }
    async fn list_products(
        &self,
        request: Request<ListProductsRequest>,
    ) -> Result<Response<ListProductsResponse>, Status> {
        let page = request.into_inner();
        validate_page(page.limit, page.offset)?;
        // One repeatable-read snapshot keeps count and items coherent.
        let result = async {
            let mut tx = self.pool.begin().await?;
            sqlx::query("SET TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY")
                .execute(&mut *tx)
                .await?;
            let items = sqlx::query_as::<_, Row>(
                 "SELECT id,name,price_cents,stock FROM products WHERE delisted_at IS NULL ORDER BY created_at DESC,id DESC LIMIT $1 OFFSET $2"
             ).bind(page.limit).bind(page.offset).fetch_all(&mut *tx).await?;
            let total: i64 =
                sqlx::query_scalar("SELECT count(*) FROM products WHERE delisted_at IS NULL")
                    .fetch_one(&mut *tx)
                    .await?;
            tx.commit().await?;
            Ok::<_, sqlx::Error>((items, total))
        };
        let (rows, total) = bounded(result).await?;
        let items = rows.into_iter().map(Row::wire).collect::<Result<_, _>>()?;
        Ok(Response::new(ListProductsResponse { items, total }))
    }
    async fn create_product(
        &self,
        request: Request<CreateProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let input = request.into_inner();
        let value = validate_draft(&input.name, input.price_cents, input.stock)?;
        let draft = store::Draft {
            name: value.name().into(),
            price_cents: value.price_cents(),
            stock: value.stock(),
        };
        let event = if input.idempotency_key.is_empty() {
            bounded(store::create(&self.pool, &draft)).await?
        } else {
            if input.actor_id <= 0 {
                return Err(Status::invalid_argument("trusted actor ID required"));
            }
            let key = uuid::Uuid::parse_str(&input.idempotency_key)
                .map_err(|_| Status::invalid_argument("invalid idempotency key"))?;
            tokio::time::timeout(
                Duration::from_millis(700),
                store::create_once(&self.pool, input.actor_id, key, &draft),
            )
            .await
            .map_err(|_| Status::deadline_exceeded("catalog command budget exhausted"))?
            .map_err(|error| match error {
                store::CommandError::Conflict => {
                    Status::already_exists("idempotency key input conflict")
                }
                store::CommandError::Database(error) => database_error(error),
            })?
        };
        Ok(Response::new(snapshot_wire(event.payload)))
    }
    async fn update_product(
        &self,
        request: Request<UpdateProductRequest>,
    ) -> Result<Response<Product>, Status> {
        let input = request.into_inner();
        validate_id(input.id)?;
        let value = validate_draft(&input.name, input.price_cents, input.stock)?;
        let draft = store::Draft {
            name: value.name().into(),
            price_cents: value.price_cents(),
            stock: value.stock(),
        };
        let event = bounded(store::update(&self.pool, input.id, &draft))
            .await?
            .ok_or_else(|| Status::not_found("product not found"))?;
        Ok(Response::new(snapshot_wire(event.payload)))
    }
    async fn delist_product(
        &self,
        request: Request<GetProductRequest>,
    ) -> Result<Response<DelistProductResponse>, Status> {
        let id = validate_id(request.into_inner().id)?;
        bounded(store::delist(&self.pool, id))
            .await?
            .ok_or_else(|| Status::not_found("product not found"))?;
        Ok(Response::new(DelistProductResponse {}))
    }
}
```

```rust
use crate::{
    http::{auth::AdminUser, error::ApiError, extract::AppJson},
    state::AppState,
};
use axum::{
    extract::State,
    http::{HeaderMap, HeaderName, StatusCode},
};
use common::{
    error::{DomainError, ValidationError},
    product::{NewProduct, Product},
};
use serde::Deserialize;
use uuid::Uuid;

#[derive(Deserialize)]
#[serde(deny_unknown_fields)]
pub struct CreateInput {
    name: String,
    price_cents: i64,
    stock: i32,
}
pub async fn create(
    State(state): State<AppState>,
    admin: AdminUser,
    headers: HeaderMap,
    AppJson(input): AppJson<CreateInput>,
) -> Result<(StatusCode, [(HeaderName, String); 1], AppJson<Product>), ApiError> {
    if headers.get_all("idempotency-key").iter().count() != 1 {
        return Err(ApiError::BadRequest(
            "必须提供一个 Idempotency-Key 请求头".into(),
        ));
    }
    let key = headers
        .get("idempotency-key")
        .and_then(|v| v.to_str().ok())
        .and_then(|v| Uuid::parse_str(v).ok())
        .ok_or_else(|| ApiError::BadRequest("Idempotency-Key 必须为 UUID".into()))?;
    let draft =
        NewProduct::try_new(&input.name, input.price_cents, input.stock).map_err(|reason| {
            DomainError::from(ValidationError::Format {
                field: "product",
                reason,
            })
        })?;
    let catalog = state
        .catalog_commands
        .as_ref()
        .ok_or_else(|| DomainError::Internal("幂等商品命令要求远程 catalog 模式".into()))?;
    let product = catalog.insert_once(admin.0.id.get(), key, &draft).await?;
    let location = format!("/api/v1/products/{}", product.id());
    Ok((
        StatusCode::CREATED,
        [(HeaderName::from_static("location"), location)],
        AppJson(product),
    ))
}
```

函数先取得 AdminUser，再验证请求头必须只有一个值，并解析 UUID。业务字段复用 NewProduct::try_new 完成归一化，actor 从 admin.0.id 取得。它不使用外部提供的身份字段，也不把服务令牌当作浏览器登录令牌。

这里仍使用 AppJson，因此 JSON 结构错误与领域错误沿原有错误模型返回。幂等请求成功和重放都返回 201 与原 Location，调用方可以再次读取该 id 的当前状态。

### 29.6.4 【进阶】仓储新增 insert_once

在 RemoteProductRepo 的 impl 中新增 insert_once。它构造 CreateProductRequest 时使用真实 actor_id 与 key.to_string，再沿原 map_status 与 decode 返回领域 Product。

原 ProductRepository::insert 仍会设置空 idempotency_key 和 actor_id=0，作为兼容普通调用路径。公共 Remote 创建处理函数不会调用这个普通 insert。代码审核时必须检查实际调用路径，不能因为某个类型存在 insert_once 方法就宣称所有创建都自动幂等。

新增方法的完整内容如下，放在 RemoteProductRepo 的 impl 内：
```rust
    pub async fn insert_once(
        &self,
        actor: i64,
        key: uuid::Uuid,
        draft: &NewProduct,
    ) -> DomainResult<Product> {
        let response = self
            .client
            .clone()
            .create_product(self.request(wire::CreateProductRequest {
                name: draft.name().into(),
                price_cents: draft.price_cents(),
                stock: draft.stock(),
                actor_id: actor,
                idempotency_key: key.to_string(),
            }))
            .await
            .map_err(|e| map_status(e, None))?;
        decode(response.into_inner())
    }
```

### 29.6.5 【精通】浏览器预检也属于接口契约

原 CORS 允许列表只有 Content-Type 与 Authorization。本章浏览器增加 Idempotency-Key 后，会发生新的预检请求，因此 allow_headers 还要加入 HeaderName::from_static("idempotency-key")。

只在 curl 中验证幂等创建可能遗漏这点：curl 不执行浏览器同源限制，服务端业务正确，页面仍可能因预检拒绝而无法提交。网关保留这个请求头并转发，身份层则继续拒绝伪造角色。

## 29.7 中继租约、重试与旧领取者隔离

### 29.7.1 【入门】完整 Outbox 中继

新增 messaging/src/bin/outbox-relay.rs：
```rust
use anyhow::Context;
use messaging::{kafka, store};
use std::time::Duration;
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let pool = sqlx::postgres::PgPoolOptions::new()
        .max_connections(4)
        .acquire_timeout(Duration::from_secs(1))
        .connect(&std::env::var("CATALOG_DATABASE_URL")?)
        .await?;
    let producer = kafka::producer(&std::env::var("KAFKA_BROKERS")?)?;
    let topic =
        std::env::var("KAFKA_TOPIC").unwrap_or_else(|_| "rustmall.catalog.snapshots.v1".into());
    let shutdown = messaging::signal();
    tokio::pin!(shutdown);
    loop {
        tokio::select! {
            ()=&mut shutdown=>break,
            ()=tokio::time::sleep(Duration::from_millis(200))=>{}
        }
        let lease = tokio::time::timeout(Duration::from_secs(3), store::claim_one(&pool)).await??;
        let Some(lease) = lease else { continue };
        anyhow::ensure!(
            lease.event_id == lease.payload.0.event_id,
            "outbox row and payload event IDs differ"
        );
        match kafka::send(&producer, &topic, &lease.payload.0).await {
            Ok(()) => {
                let owned =
                    tokio::time::timeout(Duration::from_secs(3), store::delivered(&pool, &lease))
                        .await??;
                if !owned {
                    eprintln!(
                        "acknowledged event {}, but lease ownership changed",
                        lease.event_id
                    );
                }
            }
            Err(error) => {
                tokio::time::timeout(
                    Duration::from_secs(3),
                    store::failed(&pool, &lease, &error.to_string()),
                )
                .await
                .context("outbox retry-state write timed out")??;
                eprintln!("event {} retry scheduled: {error}", lease.event_id);
            }
        }
    }
    tokio::time::timeout(Duration::from_secs(5), pool.close()).await?;
    Ok(())
}
```

它使用 CATALOG_DATABASE_URL 连接商品库，Kafka 配置使用 KAFKA_BROKERS 与 KAFKA_TOPIC。一个循环先领取一条，验证表列 event_id 与 payload 身份对应，再发送并根据结果写交付或重试状态。

### 29.7.2 【进阶】FOR UPDATE SKIP LOCKED 怎样分工

claim_one 通过 CTE 找到当前可领取、未交付且租约过期的候选行，使用 FOR UPDATE SKIP LOCKED 跳过其他事务已锁住的行，再在同一语句中设置新 token、租期与尝试次数。

这允许多个中继并行领取不同事件，不需要一个全局进程锁。SKIP LOCKED 也意味着并发时不是严格按 occurred_at 完成发送；本章快照投影仍使用 revision 判断新旧，不能把领取排序当作全局交付顺序保证。

### 29.7.3 【进阶】网络等待不占着领取事务

领取语句结束后，中继拥有租约而不是继续持有数据库行锁。发送时数据库可以服务其他请求。租约三十秒，大于本章单次正常发送与确认记录预算，但进程暂停或机器负载仍可能使它过期。

租约不是绝对排他执行证明。旧中继可能还在发送，新中继又领取同一事件，两者都可能把消息送到 Kafka。所以发送重复仍然需要 Inbox，而不能把租约误叫成“消息绝不重复”的锁。

### 29.7.4 【进阶】token 条件更新挡住什么

delivered 与 failed 都要求 event_id、当前 lease_token 和未交付条件匹配。旧领取者即使后来收到交付成功，也不能用过期 token 覆盖新领取者的状态。

令牌隔离保护的是 Outbox 元数据更新，不会撤销已经向 Kafka 发送的记录。测试让旧租约过期并重新领取，确认旧 token 不能确认，新 token 可以安排退避，从而实际覆盖这个竞争窗口。

### 29.7.5 【进阶】退避与诊断有上限

失败后按照 attempts 计算指数退避，并限制最大三百秒；last_error 最多保存五百个字符，避免一次大错误撑大记录。退避让依赖故障时不至于紧密重复发送，但当前没有随机抖动，多实例故障恢复仍可能同时重试。

本章也没有设置“尝试若干次自动删除事件”。永久格式错误或授权错误必须被发现并处理，不能悄悄丢弃事实。后面的治理章节会加入积压、最老事件年龄、失败分类与人工恢复流程。

### 29.7.6 【精通】先交付、后标记之间仍可能重复

Kafka 已确认，写 delivered_at 之前中继退出，重启后会再次发送同一 Envelope。这正是允许的失败窗口：Outbox 避免没有记录的丢失，Inbox 处理由可靠重试带来的重复。

因此 delivered_at 是中继收到确认并记账的证据，不代表消费者业务已完成。想知道投影是否已经追上，必须观察消费结果与投影版本，不能只看 Outbox 全部打勾。

## 29.8 Inbox 与投影事务

### 29.8.1 【入门】完整独立投影结构

新增 messaging/migrations/0001_projection.sql：
```sql
CREATE TABLE consumer_inbox (
   consumer_name TEXT NOT NULL,
   event_id UUID NOT NULL,
   payload_hash BYTEA NOT NULL,
   processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
   PRIMARY KEY(consumer_name,event_id)

```

consumer_inbox 的主键含 consumer_name，使不同逻辑消费者可以各自处理同一事件。catalog_view 以商品 id 为主键，保存当前修订和完整快照。它是异步读模型，不是新的商品写入权威。

### 29.8.2 【进阶】完整投影函数

新增 messaging/src/projection.rs：
```rust
use crate::event::{Envelope, Snapshot};
use sqlx::{PgPool, types::Json};

#[derive(Debug, PartialEq, Eq)]
pub enum Applied {
    Duplicate,
    Stale,
    Updated,
}
pub async fn apply(pool: &PgPool, consumer: &str, event: &Envelope) -> anyhow::Result<Applied> {
    event.validate()?;
    let hash = event.digest()?;
    let mut tx = pool.begin().await?;
    let inserted=sqlx::query("INSERT INTO consumer_inbox(consumer_name,event_id,payload_hash) VALUES($1,$2,$3) ON CONFLICT DO NOTHING")
        .bind(consumer).bind(event.event_id).bind(&hash).execute(&mut *tx).await?.rows_affected();
    if inserted == 0 {
        let stored: Vec<u8> = sqlx::query_scalar(
            "SELECT payload_hash FROM consumer_inbox WHERE consumer_name=$1 AND event_id=$2",
        )
        .bind(consumer)
        .bind(event.event_id)
        .fetch_one(&mut *tx)
        .await?;
        anyhow::ensure!(stored == hash, "event ID reused with different payload");
        tx.commit().await?;
        return Ok(Applied::Duplicate);
    }
    let changed=sqlx::query("INSERT INTO catalog_view(product_id,revision,payload) VALUES($1,$2,$3) ON CONFLICT(product_id) DO UPDATE SET revision=EXCLUDED.revision,payload=EXCLUDED.payload,updated_at=now() WHERE catalog_view.revision<EXCLUDED.revision")
        .bind(event.aggregate_id).bind(event.revision).bind(Json::<&Snapshot>(&event.payload))
        .execute(&mut *tx).await?.rows_affected();
    if changed == 0 {
        let (revision, payload): (i64, Json<Snapshot>) =
            sqlx::query_as("SELECT revision,payload FROM catalog_view WHERE product_id=$1")
                .bind(event.aggregate_id)
                .fetch_one(&mut *tx)
                .await?;
        anyhow::ensure!(
            revision != event.revision || payload.0 == event.payload,
            "same revision has conflicting snapshot"
        );
    }
    tx.commit().await?;
    Ok(if changed == 1 {
        Applied::Updated
    } else {
        Applied::Stale
    })
}
```

apply 先校验事件并计算摘要，在事务内尝试插入 Inbox。如果已经存在，读取保存摘要；一致返回 Duplicate，不一致直接失败并回滚。相同 event_id 不允许偷偷携带另一份内容。

### 29.8.3 【进阶】只允许更高版本覆盖

投影的 UPSERT 只在现有 revision 小于新 revision 时更新。低版本事件成为 Stale；同版本若内容相同也不必重写，同版本却内容不同则报错，不能根据到达顺序随便选择一个。

Inbox 插入与这次判断共同提交。冲突失败时，本次新插入的 Inbox 也回滚，防止以后把未成功处理的冲突事件误识别为 Duplicate。测试会核对最终 Inbox 数量，而不只比较返回枚举。

### 29.8.4 【进阶】下架墓碑必须保留版本

listed=false 的快照称为本章的下架墓碑。catalog_view 保留它和最新 revision，而不是简单删除投影行。

如果下架 revision 3 删除了整行，随后收到延迟 revision 2，UPSERT 发现没有行就可能重新创建可见商品。保留 revision 3 的墓碑后，旧版本只能成为 Stale，不会复活已下架内容。

```rust
use messaging::{kafka, projection};
use rdkafka::{Message, consumer::Consumer};
use std::time::Duration;
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let pool = sqlx::postgres::PgPoolOptions::new()
        .max_connections(4)
        .acquire_timeout(Duration::from_secs(1))
        .connect(&std::env::var("PROJECTION_DATABASE_URL")?)
        .await?;
    let name = std::env::var("CONSUMER_NAME").unwrap_or_else(|_| "catalog-view-v1".into());
    let topic =
        std::env::var("KAFKA_TOPIC").unwrap_or_else(|_| "rustmall.catalog.snapshots.v1".into());
    let consumer = kafka::consumer(&std::env::var("KAFKA_BROKERS")?, &name, &topic)?;
    let shutdown = messaging::signal();
    tokio::pin!(shutdown);
    loop {
        let message = tokio::select! {()=&mut shutdown=>break,message=consumer.recv()=>message?};
        // Decode errors stop the process; no offset is committed for poison messages.
        let event = kafka::decode_message(&message)?;
        let (topic, partition, offset) = (
            message.topic().to_string(),
            message.partition(),
            message.offset(),
        );
        drop(message);
        let result = tokio::time::timeout(
            Duration::from_secs(5),
            projection::apply(&pool, &name, &event),
        )
        .await??;
        kafka::commit_processed(consumer.clone(), topic, partition, offset).await?;
        println!("event {}: {result:?}", event.event_id);
    }
    consumer.unsubscribe();
    tokio::time::timeout(Duration::from_secs(5), pool.close()).await?;
    Ok(())
}
```

worker 在 apply 事务成功以后提交 Kafka 下一位置。发生解码错误或投影冲突则退出，不提交坏事件，避免静默丢弃。这个保守策略会让分区停在问题记录上，运维必须根据错误证据修复或执行受审查的隔离流程。

### 29.8.6 【精通】消费事务之外的动作仍不受保护

假设在 apply 成功之后发送一封邮件，再提交 Kafka，邮件发送成功后进程退出，恢复重放即使 Inbox 返回 Duplicate，错误实现仍可能再次发邮件。

应把“需要执行的外部通知”也作为本地可靠事实记录，由独立机制落实幂等或重试，而不是在 Duplicate 分支之外无条件执行。Inbox 不是一个可以自动覆盖任意副作用的装饰器。

在专用 PostgreSQL 测试账户下，从根执行 `cargo +1.92.0 test --locked -p messaging --all-features`。测试账户需要创建独立测试数据库；不要连接共享或生产实例。这里为测试方便将两个独立结构装入隔离用例库，不表示运行时应该把权威库和投影库合并。

### 29.9.7 【精通】本轮已执行的范围

本轮实际通过 catalog 三个规则单测、五个数据库回归、messaging 七个事件单测和五个事务数据库测试。真实原生全链路另外通过十一项检查，包含授权边界、同键重放与冲突、三次商品修订经 Kafka 写入独立投影，以及强制重发后 Inbox 返回 Duplicate 且数量不增加。

最后还验证商品服务停机不回退旧库、就绪传播和正常退出，专用 PostgreSQL 与 Kafka 实验资源已清理。没有把单节点消息实验称为多副本高可用，也没有执行外部支付或邮件副作用的恰好一次证明。

## 29.10 故障排查、练习与库存衔接

### 29.10.1 【入门】故障表

| 现象 | 先收集的证据 | 判断与修复 |
| --- | --- | --- |
| 公共创建返回 400 | 幂等头数量、UUID格式、运行模式 | Remote创建要求恰好一个有效键，不能复制出两个同名头 |
| 同键改输入返回 409 | actor、键和归一化输入 | 正确冲突保护，新意图应使用新键 |
| 原样重试返回旧名称 | 收据首次结果与当前GET | 收据重放原结果，不代表当前商品倒退 |
| 浏览器失败而curl成功 | OPTIONS预检与允许请求头 | CORS加入Idempotency-Key，不删除管理员认证 |
| 商品变化却没有Outbox | 实际写入路径和事务版本 | 确认使用新catalog，不直接写旧表 |
| Outbox有行但一直未交付 | next_attempt_at、租约、last_error | 分清退避、被领取、网络或格式问题 |
| 旧中继确认返回false | lease_token与重新领取记录 | 所有权已改变，不能无条件覆盖新租约 |
| delivered全填但投影落后 | 消费组位置、worker日志、Inbox | 交付确认不等于消费者处理完成 |
| worker反复退出同一消息 | event_id、摘要、修订和解析错误 | 修复冲突来源，保留证据，不直接跳过offset |
| 下架商品重放后复活 | 投影是否保留最高版本墓碑 | 保留listed=false与revision，不能只删除行 |
| 测试说表不存在 | 当前DATABASE_URL与迁移入口 | 区分商品库、投影库和SQLx隔离测试库 |

### 29.10.2 【入门练习】解释两个原子事务

说明商品库事务与投影库事务分别包含什么，Kafka offset 为什么不在商品库事务里。

参考答案：商品库事务包括业务写入、修订和 Outbox，幂等创建还含收据；投影库事务包括 Inbox 和版本投影。Kafka 是独立系统，普通 SQLx 事务不能把它的组位置纳入同一 PostgreSQL 提交，必须按业务完成后提交并处理可能重放。

### 29.10.3 【操作练习】注入Outbox失败

在隔离测试库让 Outbox 插入必然失败，再创建商品，检查返回值和产品行数；撤销测试条件后重新验证正常写入。

评分要点：失败时产品数量不变，没有单独成功提交的半条业务；正常时商品与事件一起出现。不得在原有业务库添加拒绝约束，不使用删除迁移历史重置实验。

### 29.10.4 【推理练习】旧租约为何不能确认

中继 A 领取事件并暂停，租约到期后 B 重新领取；A 恢复并收到 Kafka 成功确认。A 能否直接按 event_id 写 delivered_at？

参考答案：不能，只按事件身份会覆盖 B 的当前状态。应比较 A 保存的 token，所有权已变化时返回 false；A 已发送的副本仍可能存在，消费者必须去重。租约隔离不等于撤销网络副作用。

### 29.10.5 【推理练习】墓碑与乱序

先处理 revision 3 的下架事件，再处理 revision 2 的上架快照。如果下架时删除投影行，会出现什么；保留墓碑又怎样？

参考答案：删除行会让旧快照像首次插入一样复活商品；保留最高版本和 listed=false 后，revision 2 被识别为 Stale。完整快照与版本条件共同约束恢复行为。

### 29.10.6 【扩展练习】收据清理策略

如果客户端允许三十天内重试创建，运维却每天清理前一天的收据，系统还能保证这段窗口内幂等吗？设计需要对齐哪些条件？

参考答案：不能。键被清理后重试会变成新命令。需要对齐客户端重试期限、收据保留与归档、备份恢复、事件审计、身份命名空间，以及键冲突的响应语义；还应测试过期边界，而不是只写一个删除任务。

### 29.10.7 【衔接】下一章让库存成为事务状态机

现在商品变更已经能形成可靠发布记录，消费端能识别重复、旧版本和冲突，公共创建也有持久化幂等入口。但 stock 仍是可被整体替换的普通商品字段，尚未表达订单预留、确认和释放。

下一章在现有商品事务与 Outbox 基础上建立库存预留状态机，用条件更新和事务约束防止超卖，并验证重复预留、取消与确认的行为。

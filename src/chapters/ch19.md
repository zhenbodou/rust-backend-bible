# 第 19 章 Git 与 GitHub：协作与工程历史

第 18 章完成了商品详情的两级缓存。现在，一个需求可能同时修改仓储、配置和测试；两个人还可能同时修改 AppState。仅把“能运行的文件夹”复制给别人，已经无法说明哪些改动属于同一件事、哪次修改引入了问题、应该怎样撤销。本章用 Git 把这些问题变成可以观察和操作的工程过程。

学习时先完成小型本地实验，再把协作约定放回 RustMall。本章的小实验只操作新建的 rustmall-git-lab；它帮助观察版本变化，不替代前文项目。本章结束时，你应能解释工作区、暂存区和提交的区别，独立解决一次冲突，选择合适的撤销方式，并把一个 RustMall 修改整理成可评审的提交。

## 19.1 版本控制究竟控制什么

### 19.1.1 【入门】文件存在，不等于变化有记录

假设你上午修改了商品缓存的过期时间，下午修改了管理员权限，晚上发现商品接口返回错误。磁盘上只有“现在的文件”，无法告诉你上午和下午分别改了哪些行。复制成 project-final、project-final2 也只是人工保留几份文件；分支合并、逐行差异和因果关系仍需要自己猜。

版本控制保存的是一组有身份、顺序和说明的状态。一次提交通常表达一个可以独立解释的修改，例如“新增缺失商品缓存失效测试”。之后即使又修改了相同文件，原状态仍可以被定位和比较。

注意，“可以找回提交过的版本”不等于“Git 自动备份计算机上的所有文件”。尚未添加的文件、被忽略的秘密文件、数据库内容和构建缓存不因此得到可靠备份。先明确哪些材料属于源代码历史，再决定如何保护其他数据。

### 19.1.2 【入门】仓库、提交和历史

仓库是 Git 管理一个项目所使用的对象与引用集合。一般工作仓库包含一个 .git 目录和可编辑文件；.git 中保存对象、分支位置、索引和本地配置。不要因为它平时不可见就把它当成可以随意清理的缓存。

提交可以理解成“有身份的项目快照加说明”。它引用该时刻的一棵目录树，记录作者、提交者、时间、说明和父提交。平常的提交有一个父提交，首次提交没有父提交，合并提交可能有多个父提交。

因此，历史不是只能排成一条直线的文件备份列表，而是一张由父关系连接起来的图。后面看到分支与合并图时，应把它读成“这个状态从哪些状态发展而来”。

### 19.1.3 【进阶】快照模型与差异显示

git diff 展示两种状态之间哪些行变化了，这不意味着 Git 的概念模型就是“只记录一串编辑命令”。可以先把每次提交理解为完整快照，未变化的对象能够共享，底层还可能压缩和使用差分表示节约空间。

这一点解释了为什么可以比较任意两次提交，而不必手动重放中间每次编辑；也解释了为什么提交后继续修改工作区，不会改变已有提交。提交是一个已经确定身份的对象，分支位置则可以前移。

在 RustMall 中，一次“修改缓存键并更新测试”的提交，应包含相互对应的代码与测试状态，而不是只留下“曾经执行过替换字符串”这样的操作意图。

### 19.1.4 【进阶】Git 和 GitHub 的分工

Git 是版本控制工具，可以在断网时创建仓库、提交、分支和合并。GitHub 是托管仓库及协作的服务，提供 Pull Request、讨论、权限与自动检查等功能。GitLab 等平台也可以承担类似职责。

在本机 commit 不会自动把代码发到 GitHub；在 GitHub 创建一个远程仓库，也不会自动把本机尚未提交的文件上传。后面要分别操作本地历史和远程分支。先掌握这两层，才能理解 push 被拒绝时到底是哪一层状态不一致。

### 19.1.5 【精通】提交身份能够证明什么

提交号能精确标识一个提交对象；只要对象内容和所引用身份不同，计算出的对象身份也会不同。它方便定位版本，不是程序正确性的证明。错误代码也可以有稳定提交号，作者姓名也不等于经过认证的发布者身份。

工程交付需要把提交号与测试结果、依赖锁文件、构建产物和部署记录关联起来。后续 CI/CD 会继续建立这条联系。本章先确保历史本身可解释，不把“已经提交”写成“已经验收”。

## 19.2 工作区、暂存区与提交：亲手观察三种状态

### 19.2.1 【入门】准备一个不会碰到项目历史的实验目录

以下命令在 Bash 或 Git Bash 中执行。macOS、Linux 可以使用现有终端；Windows 读者可使用 Git Bash。先在普通实验父目录下新建文件夹，不在已有 RustMall 仓库中再执行本节的初始化步骤。
```bash
mkdir rustmall-git-lab
cd rustmall-git-lab
git init -b main
git config user.name "Book Reader"
git config user.email "reader@example.invalid"
printf '%s\n' 'RustMall Git 实验' > README.md
```

init 创建仓库，-b main 指定初始分支名。两条 config 不带 --global，只设置这个实验仓库的提交身份；正式项目应使用团队要求的身份。example.invalid 是演示地址，不是需要发送邮件的联系人。

后文命令没有列出每一步都要重复的 cd：除非明确切换目录，都在 rustmall-git-lab 中执行。命令块中的路径是输入，随后标为“输出示意”的内容用于对照，不要作为命令执行。

### 19.2.2 【入门】工作区是你正在编辑的内容
```bash
git status --short
```

输出示意：
```text
?? README.md
```

问号表示 Git 还没有跟踪这个文件。编辑器能打开它，并不意味着它已进入任何提交。工作区可以包含已跟踪文件、未跟踪文件和被忽略文件；status 只是按规则展示它们的状态。

### 19.2.3 【入门】暂存区保存“准备提交的版本”
```bash
git add README.md
git status --short
git diff --cached
```

status 此时显示 A 和文件名，表示新文件已经暂存。diff --cached 展示暂存区与当前提交之间的差异；首次提交没有原文件，因此会看到新增的一行。

暂存区不是“文件名单”。add 会把当时的文件内容放进索引。如果 add 后再次编辑文件，暂存区仍保留 add 时的版本。理解这一点，就能避免“明明改好了，提交里却还是旧内容”。

### 19.2.4 【入门】第一次提交与干净工作区
```bash
git commit -m "docs: 建立 Git 实验说明"
git status --short
git log --oneline -1
```

提交成功后，status --short 没有输出表示没有待报告变化；log 显示一个短提交号和提交说明。你的提交号和本书不会相同，因为时间、身份等内容参与提交对象的形成。

“干净”表示工作区与索引相对于当前提交没有待报告变化，不表示代码已经测试，也不表示远程分支已包含这个提交。

### 19.2.5 【进阶】同一个文件可以同时有已暂存和未暂存修改
```bash
printf '%s\n' 'RustMall Git 实验' '准备记录协作流程' > README.md
git add README.md
printf '%s\n' 'RustMall Git 实验' '准备记录协作流程' '这一行尚未暂存' > README.md
git status --short
git diff
git diff --cached
```

输出中的 MM 表示索引里有修改，工作区相对于索引又有修改。git diff 看“最后一行尚未暂存”；git diff --cached 看“准备记录协作流程”。若此时 commit，只会提交暂存区的两行版本。

把三个状态写成具体内容会更清楚：HEAD 中是一行，索引中是两行，工作区中是三行。它们是三个可比较的版本，不是同一个文件被 Git “弄乱了”。

### 19.2.6 【进阶】只提交一个文件中的一部分
```bash
git add -p README.md
```

-p 启动交互式补丁选择，Git 会按差异块询问是否暂存。较大的差异块可能需要拆分或编辑补丁；不是任何相邻修改都能自动按意图分开。如果一次改了缓存参数和注释，最好在编辑时就保持清晰边界。

操作后始终用 diff --cached 检查真实结果。暂存一个“看起来相关的块”仍可能遗漏必要导入或测试，导致提交本身不能编译。提交边界以能独立解释和验证为准，不以行数最少为准。

### 19.2.7 【精通】用索引思考撤销，避免记混命令

| 比较 | 命令 | 回答的问题 |
| --- | --- | --- |
| 工作区与索引 | git diff | add 之后还改了什么 |
| 索引与 HEAD | git diff --cached | 下一次准备提交什么 |
| 工作区与 HEAD | git diff HEAD | 当前文件与上次提交总共差什么 |
| 两次提交 | git diff main..feat/cache-note | 两个确定状态差什么 |

本地练习结束前，把三行版本也暂存并提交，让下一节从干净状态开始。不要只复制操作命令而不看 diff；Git 操作的风险通常来自对状态的误判，而不是命令拼写。
```bash
git add README.md
git commit -m "docs: 说明暂存区与工作区"
```

## 19.3 对象、分支、HEAD 与标签

### 19.3.1 【入门】分支不是复制整个项目

分支首先是指向某个提交的可移动引用。创建分支时，不需要为所有文件复制一份新的历史。切换分支后，Git 按目标状态更新可见文件；因此编辑器里文件内容可能变化，而 .git 中仍能找到另一条历史。
```bash
git switch -c feat/cache-note
printf '%s\n' '缓存缺失结果需要在插入后失效' > cache-note.txt
git add cache-note.txt
git commit -m "docs: 记录缺失缓存失效约定"
git switch main
```

回到 main 后，cache-note.txt 不再是该分支提交中的文件。它没有从整个仓库历史消失，切回 feat/cache-note 仍能看到。

### 19.3.2 【入门】HEAD 表示当前检出位置

通常 HEAD 指向当前分支，分支再指向一个提交。新 commit 产生后，当前分支前移，HEAD 继续跟随它。
```bash
git branch --show-current
git log --oneline --graph --decorate --all
```

graph 用线条表达父关系，decorate 标注分支和标签位置，--all 让你看到不只当前分支可达的历史。先看标签落在哪个节点，再看修改内容，能够避免把 main 与另一分支的提交混为一谈。

### 19.3.3 【进阶】分离 HEAD 为什么容易让初学者困惑

按一个历史提交检出时，HEAD 可以直接指向该提交，而不是跟随某个分支。这就是 detached HEAD。它适合检查旧版本，本身不是仓库损坏。

如果你在这里创建了新提交，却直接切走，没有创建分支留住它，常规分支列表中就不容易再找到这条新历史。打算继续修改时，先创建一个有意义的分支；只是查看旧代码时，看完回到原分支即可。

### 19.3.4 【进阶】标签用于标记版本，分支用于继续工作
```bash
git tag -a lab/before-merge -m "标记对象与引用实验"
git show --stat lab/before-merge
```

附注标签带有标签对象与说明，适合标记教材检查点或发布版本。标签不会像分支那样在新提交时自动前移。远程共享标签还需要显式推送；在本章本地实验里先保留为本地标记。

RustMall 的章节检查点应标记“该阶段已形成什么”，不应提前标记未来还没加入的服务。若标签名已经存在，先检查所指对象，不要为了重复运行命令而强制移动他人已使用的标签。

### 19.3.5 【精通】为什么修改提交说明也会产生新身份

提交说明是提交对象内容的一部分。amend 修改说明或文件后，会创建新的提交对象，通常得到新的提交号；旧对象并不是被原地擦写。它的后代若被重建，父引用也会变化。

这解释了为什么改写历史后，远程可能拒绝普通 push：远程分支与本地新分支不再具有原来的快进关系。问题与“代码内容有没有变化”不同，关键还包括提交之间的连接关系。

## 19.4 分支合并与冲突：让两条开发线重新对齐

### 19.4.1 【入门】先认识快进合并

上节 main 没有继续提交，而 feat/cache-note 比它向前多了一次提交。此时合并可以直接把 main 移到后者位置：
```bash
git switch main
git merge --ff-only feat/cache-note
```

--ff-only 要求只能快进，不满足时拒绝，而不是悄悄创建一种你尚未理解的历史形状。它适合实验和需要保持线性更新的场景，不表示所有团队都必须禁止合并提交。

### 19.4.2 【入门】两边都修改时，Git 根据共同祖先合并

若 main 和功能分支从同一提交各自前进，Git 会比较共同祖先与两边的变化。互不重叠的修改通常能够自动合并；修改同一范围时，工具可能无法决定最终内容。

“自动合并成功”仅表示文本合并不需要人工选择，不表示业务一致。一个分支改了函数参数，另一个分支增加调用点，文本可能无冲突但编译失败。数据库迁移版本冲突更可能发生在两个不同文件里。

### 19.4.3 【入门】制造一个能够看见的冲突

本小节从 main 的干净状态开始，两个分支都修改同一个新文件的同一行。
```bash
printf '%s\n' '商品缓存 TTL：300 秒' > cache-policy.txt
git add cache-policy.txt
git commit -m "docs: 建立缓存参数基线"
git switch -c feat/short-cache
printf '%s\n' '商品缓存 TTL：120 秒' > cache-policy.txt
git commit -am "docs: 缩短缓存保留时间"
git switch main
printf '%s\n' '商品缓存 TTL：600 秒' > cache-policy.txt
git commit -am "docs: 延长缓存保留时间"
git merge feat/short-cache
```

最后一步预期出现冲突，这不是本节操作失败。-am 只会暂存已跟踪文件的修改并提交；这里文件已在基线提交中跟踪，所以适用。它不会替你添加全新的未跟踪文件。

### 19.4.4 【进阶】逐行读懂冲突标记

cache-policy.txt 中会出现类似内容：
```text
<<<<<<< HEAD
商品缓存 TTL：600 秒
=======
商品缓存 TTL：120 秒
>>>>>>> feat/short-cache
```

HEAD 部分是当前分支的版本，下半是正在合并的另一侧。标记告诉你两边输入，不替业务决定 120 和 600 哪个更正确。先问修改目的：想减少陈旧、减轻数据库压力，还是改变安全状态的保留？再决定统一策略。

本实验选择一个明确的折中值 300，并说明这是实验决策。真实 RustMall 的 TTL 需要结合第 18 章的陈旧上限与访问负载判断，不能把“折中”当成技术论证。
```bash
printf '%s\n' '商品缓存 TTL：300 秒；调整前先测量回源负载' > cache-policy.txt
git add cache-policy.txt
git diff --cached
git commit -m "docs: 合并缓存策略并记录测量前提"
```

### 19.4.5 【进阶】中止合并与保留现场

如果发现合错了分支，且尚未完成合并提交，可以使用 git merge --abort 退回合并前的状态。它是另一条操作选择，不是在上一小节提交成功后继续执行的步骤。

开始合并前先保持工作区清楚：未提交修改与冲突处理混在一起，回退时更难判断哪些内容属于原工作。重要工作先提交到个人分支或明确存放，再进行整合，能够把恢复问题大幅简化。

### 19.4.6 【精通】从文本冲突走向语义冲突

RustMall 中两人分别添加 0004_product_sku.sql 和 0004_user_profile.sql，Git 不一定报告冲突，因为文件名不同。但同一迁移器可能要求版本唯一；合并后必须检查迁移顺序、空库执行和已部署环境的记录。

再如，一边把 ProductRepository::update 的含义改为只改描述，另一边仍传 stock 覆盖库存。即使类型没变、编译成功，语义已经冲突。评审者应从接口契约、数据库不变量和测试时序检查，不能只看有没有红色冲突标记。

## 19.5 远程仓库与 GitHub：把个人修改接到团队流程

### 19.5.1 【入门】origin 只是远程地址的一个名字
```bash
git remote -v
```

remote -v 显示已配置的远程名与地址。origin 是常见约定，不是 Git 内建的“官方服务器”。同一仓库可以配置多个远程，例如自己的 fork 与原项目；操作前应确认 push 的目标，而不是看到 origin 就默认安全正确。

本节继续用本地磁盘模拟远程，完整观察 fetch 与 push，不要求注册账号或发送代码到外部平台。在 rustmall-git-lab 中执行：
```bash
git init --bare -b main ../rustmall-origin.git
git remote add origin ../rustmall-origin.git
git push -u origin main
```

bare 仓库主要保存 Git 数据，不供日常编辑工作区文件。它适合作为本地共享端。-u 设置当前分支的上游关系，让后续 status 能比较本地 main 与相应远程跟踪分支。

### 19.5.2 【入门】本地 main、origin/main 与服务器 main

这三个名字容易被说成同一个“主分支”，实际上处于不同位置。本地 main 是你继续提交的分支；origin/main 是本地记录的远程跟踪引用；服务器上的 main 是远程仓库中的分支。

origin/main 不会在同事每次推送时自动实时更新。fetch 与部分其他远程操作才会更新本地对远程状态的认识。因此，status 显示“与上游一致”，只针对当前已经掌握的信息，不保证服务器此刻没有新变化。

### 19.5.3 【入门】让第二位开发者提交一次修改

从第一个实验目录切到父目录，再克隆刚才的本地远程：
```bash
cd ..
git clone rustmall-origin.git rustmall-peer
cd rustmall-peer
git config user.name "Peer Reader"
git config user.email "peer@example.invalid"
printf '%s\n' '同事补充的缓存验证清单' > peer-note.txt
git add peer-note.txt
git commit -m "docs: 补充同事的验证说明"
git push origin main
cd ../rustmall-git-lab
```

现在服务器 main 已前进，第一份工作区仍是旧状态。两份工作目录不会因为共用远程而共享未提交文件；这正是分布式版本控制与网络共享文件夹的区别。

### 19.5.4 【进阶】fetch 先获取事实，merge 再改变当前开发线
```bash
git fetch origin
git log --oneline --decorate main..origin/main
git status --short --branch
git merge --ff-only origin/main
```

fetch 下载缺少的对象并更新远程跟踪引用，不把同事文件直接混进你当前的修改。第二条只看远程比本地多出的提交，第三条确认本地状态，第四条才把当前分支推进到已经检查的目标。

pull 通常把获取与后续整合放在一次操作中，具体整合使用 merge 还是 rebase 与选项、配置有关。初学阶段先分开 fetch 与整合，能够更清楚地观察每一步的影响；熟悉团队策略后再选择一致的 pull 配置。

### 19.5.5 【进阶】push 为什么会被拒绝

如果远程分支已有本地没有的新提交，普通 push 往往不能快进，服务器会拒绝覆盖。此时先 fetch，检查两边历史，再按团队策略合并或重建个人分支。拒绝是在保护已经存在的远程历史，不表示网络一定坏了。

权限不足、认证失败、保护规则未满足和非快进是四种不同原因。排查时先读错误信息中的类别，再选择动作。为非快进问题反复修改访问令牌无效；为权限问题使用强制推送也无效。

### 19.5.6 【进阶】Pull Request 是评审载体，不是另一种提交

PR 对比一个来源分支与目标分支，承载问题说明、差异、讨论和自动检查。commit 已经存在于来源历史中；PR 只是请求把这组变化整合进目标，并记录团队如何作出判断。

一个可读的 RustMall PR 可以按三段组织：先描述具体触发与用户行为，再说明实现如何改变，最后给出实际执行的检查与环境。例子：“先查询不存在商品，再创建该商品，详情仍因 missing 缓存返回 404；本修改在创建成功后失效该 id 的缓存；新增测试覆盖该时序。”

“优化代码”“修复一些问题”不够定位行为；粘贴完整机器日志也不等于说明验证。审查者需要从描述进入差异、从差异找到规则、从规则找到证据。

### 19.5.7 【精通】认证方式与权限范围

HTTPS 和 SSH 都可以用于 Git 托管访问，它们的认证材料和配置不同。HTTPS 常使用平台支持的令牌或凭据管理器；SSH 由密钥与服务端公钥校验建立身份。不要把密码、私钥内容或含令牌的远程 URL 写入项目 README。

凭据能够访问仓库，不代表应当拥有所有仓库的写权限。按用途选择权限范围，区分个人开发与自动化发布。后续 CI 会进一步把只读检查和可写镜像发布分开，本章先建立“谁在什么位置有权改变什么”的基本问题意识。

## 19.6 撤销、整理与找回：按状态选择操作

### 19.6.1 【入门】先问修改有没有提交、有没有共享

| 所处状态 | 常见意图 | 优先理解的工具 |
| --- | --- | --- |
| 工作区有未暂存变化 | 恢复某个文件的内容 | restore；先检查 diff |
| 已暂存但尚未提交 | 取消暂存，继续保留编辑 | restore --staged |
| 本地最后一次提交还没共享 | 补入遗漏内容或整理说明 | commit --amend |
| 缺陷提交已进入共享历史 | 产生一个可审查的反向修改 | revert |
| 切换后找不到原提交 | 找到之前的引用位置 | reflog，再建立保留分支 |

工具选择取决于你要改变哪一层状态。不要仅因为几个命令都能让屏幕上的内容“变回去”，就把它们当成等价操作。

### 19.6.2 【入门】取消暂存，保留工作内容

在实验仓库创建一行本地说明，暂存后再取消：
```bash
printf '%s\n' '尚未决定是否提交的说明' > local-note.txt
git add local-note.txt
git restore --staged local-note.txt
git status --short
```

文件仍存在，状态回到未跟踪。对一个已跟踪文件，取消暂存后其工作区修改也仍保留。--staged 指定的是索引这一层，不是在删除文件。

单独的 git restore 某个已跟踪文件会改变工作区内容，通常从索引恢复。它可能丢弃尚未保存进历史的编辑，因此操作前要先看 diff。这里不把它与“取消暂存”的实验连成一个自动执行块。

### 19.6.3 【进阶】amend 是重建最后一个提交

如果个人分支刚提交后发现遗漏一个测试，可以先添加测试并暂存，再执行 commit --amend。新提交包含新的快照；旧的最后一次提交被当前分支的新位置替代，提交号会改变。

这适合尚未共享的个人整理。若其他人已经基于原提交开发，改写会要求他们重新理解分叉关系。不要把“保持提交漂亮”放在团队已经依赖的历史稳定性之上。

### 19.6.4 【进阶】revert 保存“后来做了什么纠正”

revert 不删除原提交，而是根据原改动创建一份反向变更。后续历史能同时看到原缺陷与纠正动作，适合已共享代码的普通撤销。

反向应用仍可能冲突，因为后面的代码可能继续修改同一范围。并且，撤销源码不会撤销数据库迁移造成的事实，也不会取消已发送的消息。遇到数据库、渠道或协议变更时，必须先判断旧应用还能否在当前数据结构上工作。

### 19.6.5 【进阶】stash 是临时保存，不是长期备份策略
```bash
git stash push -u -m "调查缓存参数前暂存本地说明"
git stash list
```

-u 包括未跟踪文件，默认不会把被忽略文件全部收进去。恢复时先 apply，检查内容正确，再根据需要 drop 对应条目。apply 也可能冲突，不能假设 stash 只是一块永远能无损取出的剪贴板。

本实验前面的 local-note.txt 会被纳入保存。RustMall 的 .env 属于忽略的秘密文件，应通过适当的秘密管理方式保护，不因运行了 stash 就认为已有备份。

### 19.6.6 【进阶】rebase 重新安排个人提交的起点

假设功能分支从旧 main 分出，main 后来增加了兼容修改。rebase 会把选定的个人改动重放到新的基础上，通常生成新的提交对象。它可以让短个人分支的差异更容易阅读，但不是把两个现有提交“原地连接一下”。

发生冲突时，解决对应文件并 add 后，再执行 rebase --continue；发现计划不合适则 rebase --abort。它们是根据情况选择的动作，不能连续执行。也不要把 rebase 的“当前一侧”机械等同于 merge 冲突中的同一业务身份，先检查正在重放的提交内容。

### 19.6.7 【精通】force-with-lease 的保护范围

重建过并且已经上传的个人分支，普通 push 可能不再快进。团队允许时可以使用 --force-with-lease，要求远程仍满足相应预期才覆盖。它比无条件覆盖多了一道并发检查，但不能证明没有同事依赖旧历史。

保护规则应限制共享主分支的历史改写。该选项适合明确约定的个人分支整理，不是遇到 push 失败时的万能修复键。参数还可以影响检查的预期引用，使用前应查当前 Git 的具体说明。

### 19.6.8 【精通】reflog 找到的是本地引用移动记录
```bash
git reflog --date=iso
```

可以从记录中找到切换、提交、重建历史之前的位置。找到需要保留的真实提交号后，再创建 rescue/ 开头的分支指向它。该记录属于本地，也有保留与清理策略；不是 GitHub 的永久操作档案，更不是数据库备份。

恢复时先建立新分支查看，而不是一边猜一边移动当前 main。把“找到对象”与“决定继续采用它”分成两步，更容易保住仍然有用的当前工作。

## 19.7 审查与定位：让历史真正帮助工程

### 19.7.1 【入门】一次提交只表达一个可以验证的意图

“一个意图”不等于“一个文件”。修复缓存失效通常需要代码、回归测试和必要说明三个文件，它们可以属于同一提交。相反，同一个配置文件中的行尾规范化和连接池行为修改，风险不同，适合分开。

判断方式是：能否独立说明触发、行为与验证；能否只撤销这一件事；审查者是否需要猜测哪些改动彼此依赖。提交说明的前缀如 feat、fix、docs 是辅助约定，不代替这个判断。

### 19.7.2 【进阶】读懂一个能够编译的错误修改

下面是评审材料，不是要加入 RustMall 的新版本：
```rust
async fn insert(&self, draft: &NewProduct) -> DomainResult<Product> {
    let product = self.inner.insert(draft).await?;
    Ok(product)
}
```

它在 Rust 类型层面没有明显问题，但漏掉了第 18 章的缺失缓存失效。先访问一个不存在的商品，会缓存 missing；稍后创建得到同一 id，数据库已经有行，查询却仍可能从缓存读到“缺失”。

一条合格审查意见应写出该时序，指出创建成功后需要 invalidate(product.id())，并要求检查 insert_clears_a_cached_missing_marker。这样，评论把用户后果、代码位置与测试连接起来，不只是表达个人写法偏好。

### 19.7.3 【进阶】错误转换也会改变业务含义
```rust
let product = self.inner.get(id).await.ok();
```

ok() 会把所有 Err 变成 None。此时数据库连接失败和商品不存在变成同一个结果。如果随后把 None 缓存起来，短暂数据库故障会被放大成持续的 404。

审查不能只问“为什么不用更短的写法”，而要跟踪错误分类。只有明确的 NotFound 才能形成短期缺失结论，其他故障需要继续向上表达，且不应作为业务事实缓存。第 4 章的结构化错误由此转化成真实的服务行为。

### 19.7.4 【进阶】bisect 用一个判定缩小回归范围

已知旧版本正确、新版本错误时，二分定位可以减少检查次数。关键输入不是“两个日期”，而是两个确定提交，以及一个能在区间内正确判定的测试。
```bash
git bisect start
git bisect bad HEAD
git bisect good book/ch18
```

这段用于已经存在真实 book/ch18 标签的 RustMall 历史，不适用于刚创建的小实验。随后每个候选版本执行回归检查，再按结果标记 good、bad 或 skip；结束后执行 git bisect reset 返回原检出状态。

如果标签不存在，先根据自己的已验收提交建立基线，不应捏造一个与当前代码无关的标签。版本控制命令的正确性，始终依赖操作对象确实存在。

### 19.7.5 【精通】“零个测试成功”不能判成业务正确

Cargo 的测试名称过滤没有匹配到测试时，也可能以成功退出。若在 bisect 中跨越了测试尚未加入的版本，直接按退出码判断，会把“没有执行判定”错认成“缺陷不存在”。

因此自动回归脚本先检查目标测试是否存在，再运行判定。构建失败且与正在调查的缺陷无关时，应当返回无法判定，而不是随意标记为好或坏。Git bisect run 约定 0 表示好，1-127 中除 125 外表示坏，125 表示跳过；其他退出码会终止该过程。退出码是这个接口的协议，不能凭感觉选择。

### 19.7.6 【精通】依赖与迁移的冲突要用对应工具核查

Cargo.lock 冲突应先理解 Cargo.toml 中的依赖意图，再使用固定工具链重新解析并检查差异。不能机械选一边，导致另一边需要的版本或原生功能消失。大范围升级会影响 MSRV、原生库、镜像和安全评估，应与普通业务修复区分。

迁移冲突则要看执行历史。尚未在共享环境使用的新迁移可以协调编号；已经执行的迁移不应靠改内容来“修复记录”。Git 能证明文件历史，但实际数据库还保留另一条迁移事实，两者必须对应。

## 19.8 项目进度：给 RustMall 建立协作检查点

### 19.8.1 本节承接的工程状态

第 18 章的商品服务由 ProductService 包装带缓存仓储，状态通过 AppState::new(pool, jwt, cache) 组装。本章不修改商品模型、缓存策略或认证逻辑，新增的是团队能够共同使用的协作材料。

不要把第 15 章只有 pool 的构造调用带回来，也不要为了准备一个 Git 提交而重写 AppState。先从前章的测试与接口确认基线，再加入本节文件。

### 19.8.2 本节要创建或修改的文件

| 文件 | 状态 | 作用 |
| --- | --- | --- |
| .gitattributes | 新建 | 统一文本与脚本行尾规则 |

前文已有 .gitignore，继续保护 target、.env 和本机临时材料。忽略规则只影响相应未跟踪状态，已经进入历史的秘密不会因为后来加入忽略规则就自动从历史消失；若真实秘密泄露，需要先撤销或轮换，再按团队流程处理历史。

### 19.8.3 第 1 步：行尾规则与脚本可执行性

文件：rustmall/.gitattributes（完整内容）
```gitattributes
* text=auto
*.rs text eol=lf
*.toml text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
*.sh text eol=lf
*.py text eol=lf
Dockerfile text eol=lf
```

text=auto 让 Git 判断文本并规范化；eol=lf 明确这些文本检出为 LF。它与 Linux 脚本的可执行权限是两个问题：正确行尾不能替代执行权限，拥有执行权限也不能修复错误解释器或挂载限制。

为已有仓库规范化时，应单独审查这类机械差异，避免和缓存行为修改混在一起。第 20 章还会区分镜像内权限和宿主机挂载权限。

### 19.8.4 第 2 步：PR 模板与具体描述

文件：rustmall/.github/pull_request_template.md（完整内容）
```markdown
## 问题与触发

说明用户怎样触发，原来出现什么结果。

## 修改后的行为

说明现在返回什么、保存什么，以及关键边界。

## 验证

- [ ] 已运行与本次变化有关的检查
- [ ] 已列出真实命令、环境及结果
- [ ] 涉及数据库或契约时，已说明兼容与回滚条件

## 相关事实

关联问题、迁移、日志或测试；不粘贴密码和令牌。
```

模板不是让每次 PR 填一篇形式化报告。很小的文档修改只需少量文字；修改库存事务则应说明并发、幂等和失败窗口。尺度跟随风险，描述始终面向没有看过聊天记录的评审者。

### 19.8.5 第 3 步：可复现的故障报告

```

“创建商品失败”还不能复现；“在某提交上先查询 id 1 得到 404，再创建首个商品，随后详情继续 404”就明确了时序。数据库故障还需要记录依赖是否就绪、错误码与迁移状态，而不是只截取最后一行 panic。

### 19.8.6 第 4 步：把团队实际采用的约定写下来

文件：rustmall/docs/collaboration.md（完整内容）

1. 从已核验的 main 建立短功能分支。

```

后续 CI 可以强制部分规则，例如格式、测试和分支保护；“这个修改是否解决了正确的问题”仍需要人审查。不要期待一个配置文件替代所有协作判断。

## 19.9 常见问题：把现象分到正确层次


| 现象 | 应收集的证据 | 修复方向 |
| --- | --- | --- |
| add后仍漏修改 | git diff与git diff --cached | 区分工作区和索引，重新暂存实际需要的版本 |
| 忽略文件仍在远端 | 跟踪状态、提交历史、凭据实际权限 | 已跟踪内容不受忽略保护，先处理凭据再清理历史 |
| 无文本冲突却测试失败 | 合并结果、接口和迁移差异 | 在合并后的版本验证语义兼容，不能拼接两边旧结果 |
| push被拒绝 | 当前分支、远程引用和错误类别 | 区分网络、认证、写权限与未整合历史 |


### 19.9.1 status 很干净，为什么运行结果仍错

干净只说明当前没有待报告修改。先确认提交号和运行进程对应，检查是否仍在访问旧端口、旧镜像或旧数据库，再运行针对行为的测试。不要把 Git 状态当成程序健康探针。

### 19.9.2 add 过了，为什么提交仍漏一行

先比较 git diff 与 git diff --cached。最常见原因是 add 后再次编辑，新增内容只在工作区。也可能只暂存了部分差异。确认具体层次后重新 add 所需内容，不需要重装 Git。

### 19.9.3 .gitignore 有 .env，为什么远程仍能看见它

检查该文件是否早已被跟踪或提交。忽略规则不会重写历史。真实秘密已经共享时，应先轮换其实际权限，再处理仓库跟踪与历史；仅从最新目录删除不等于旧提交不可读取。

### 19.9.4 合并没有冲突，为什么测试失败

对照接口、依赖和迁移的语义变化。特别检查两个分支各自新增的调用是否还匹配、是否复用了迁移编号、是否遗漏另一分支所需的 feature。测试应在合并结果上运行，不能拼接两边原先的绿色结果。

### 19.9.5 远程失败时先收集哪些信息

至少记录当前分支、目标远程名、错误类别和是否存在未整合提交。排除地址和网络后再看认证，排除认证后再看写权限与保护规则。向别人求助时不提供令牌内容、私钥或带凭据的完整 URL。

## 19.10 分层练习、参考答案与本章小结

### 19.10.1 基础练习：画出三份 README

按 19.2.5 重做一次，写出 HEAD、索引、工作区的具体行数，并分别选择命令观察两组差异。

参考答案：第一次提交为一行，暂存状态为两行，继续编辑为三行；diff 比较工作区与索引，diff --cached 比较索引与 HEAD。若回答成“Git 里有两份文件”，说明还没有区分保存位置和比较对象。

### 19.10.2 操作练习：从另一份克隆取回修改

完成本地 bare 远程与第二份克隆，第二位开发者推送后，先 fetch，确认工作区未立即出现新文件，再快进整合。

验收要点：能够说出三个 main 的位置；fetch 后 origin/main 已更新而当前 main 尚未前进；整合后文件出现；无需访问任何外部托管账号。

### 19.10.3 操作练习：解决冲突并解释选择

重复 120 秒与 600 秒的冲突，不以“保留某一侧”为理由完成。写出两边改变的目标，再给出统一策略或需要补做的测量。

答案要点：TTL 同时影响陈旧上限与数据库回源负载，数值本身没有脱离业务的绝对优劣。正确解决至少应删除冲突标记，保留一致文本，运行相关测试，并记录选择依据。

### 19.10.4 推理练习：选择撤销方式

情景一，已暂存一个文件但想继续编辑；情景二，个人最后一次提交漏了测试且尚未共享；情景三，缺陷已合入主线。

参考答案：一用 restore --staged；二先补测试再按约定 amend；三用新的修复或 revert，保持共享历史。若情景三还涉及不兼容迁移，先分析数据与旧程序的兼容条件，不能只回滚源码。

### 19.10.5 工程练习：给缓存问题写 PR 描述

描述“先查缺失，再创建，仍返回 404”的缓存缺陷，至少包含触发、修改后行为、关键代码位置和测试。

参考写法：插入成功后失效返回商品 id 对应的缺失缓存；正常数据库错误仍向上返回，不能缓存成不存在；分别运行缺失标记失效和错误不缓存的回归测试。评分重点是行为与证据是否对应，不是文字是否华丽。

### 19.10.6 精通练习：为什么二分脚本必须识别无法判定

设历史区间内一个版本尚未加入目标测试，另一个版本因旧依赖暂时不能构建。它们能否直接标记 good？

参考答案：不能。未执行有效判定不支持“缺陷不存在”的结论；与目标无关的不可测试状态应显式跳过或中止调查。先验证回归测试本身的存在与判别能力，才能信任二分结果。

### 19.10.7 本章小结与下一章衔接

本章把个人文件变化变成了可定位、可比较、可评审的历史。工作区、索引与提交负责不同状态；分支与远程引用负责不同位置；合并和撤销需要理解历史关系，也需要理解业务含义。

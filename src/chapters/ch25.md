# 第 25 章 Protobuf 与 gRPC：通信契约与演进

前面几章已经把同一个 RustMall 从本机程序带到镜像、集群对象与可审查的配置。业务仍在 monolith 中，商品服务可以通过普通 Rust 调用访问仓储。下一步要把商品能力放进独立进程，首先必须回答：调用双方怎样约定字段、方法、错误与等待时间，又怎样在不同版本并存时保持兼容。

本章先学习 Protobuf 的数据模型和编码，再学习 gRPC 的调用生命周期，最后为 RustMall 新增 contracts 工作区包。我们会生成真正的客户端和服务端代码，运行本地网络测试，但不在这里提前实现下一章的 PostgreSQL 商品服务。学完应能解释一段编码字节、区分协议类型与领域不变量、定位一次 RPC 失败发生在哪一层，并审查一个协议变更是否影响旧调用方。

## 25.1 本地函数调用跨过网络以后

### 25.1.1 【入门】RPC 的类比与边界

RPC 是 Remote Procedure Call，远程过程调用。客户端代码看起来像调用一个方法，实际却要把输入编码为消息、发送到另一个进程、等待对方处理，再解析结果。方便的调用形式不会消除网络与进程边界。

在 monolith 中，仓储函数返回以后，调用者已经得到该次执行结果；跨网络后，服务端可能完成了写入，响应却在途中丢失。调用者看到超时，无法仅凭这一现象断言“对方没有执行”。后面的重试、幂等与订单流程都建立在这个区别上。

### 25.1.2 【入门】Protobuf 与 gRPC 各负责什么

Protocol Buffers，简称 Protobuf，用于定义结构化消息并编码、解码。gRPC 在通信过程中组织方法调用、请求、响应、元数据和状态。Rust 项目中的 prost 负责消息相关能力，tonic 提供 gRPC 客户端、服务端与传输支持。

两者经常一起使用，但不是同一层。把 Product 编成字节并写到文件，只用到消息编码；把这些字节作为某个远程方法的请求发送，还需要调用协议与传输。不能因为 Protobuf 能解码，就推导出用户身份、方法名与业务权限都正确。

### 25.1.3 【入门】为什么保留 HTTP 公共接口

RustMall 已经有面向外部客户端的 JSON HTTP 接口。引入内部 gRPC，并不要求立即让浏览器直接调用所有内部服务；外部接口与内部契约可以有不同使用者、认证方式和演进节奏。

本章先建立内部商品契约。下一章实现独立商品服务，再由后续网关章节处理 HTTP 与内部 RPC 的转换。这样每一步都有明确对象，避免一边更改对外响应，一边拆数据库，一边猜测网络错误来源。

### 25.1.4 【进阶】契约至少有四个部分

结构契约规定字段与类型；调用契约规定方法与请求响应关系；语义契约规定单位、范围、缺失值和错误含义；演进契约规定哪些修改能与旧版本共存。

例如 price_cents 使用 int64 只说明可以承载一个整数，不自动说明单位是分、币种是什么、是否允许负数。GetProduct 返回 Product，也没有自动规定不存在时应该返回 NotFound 还是一个 id 为零的对象。没有写清这些语义，生成器仍能顺利工作，但调用双方可能理解不同。

### 25.1.5 【进阶】生成代码减少机械差异

从同一份 .proto 生成客户端和服务端，可以让方法名称、消息字段与序列化规则保持一致。修改服务方法后，实现不完整的 Rust trait 会在编译时暴露问题，而不是等到某条字符串路由才发现拼错名称。

生成器只能落实已经声明的规则。业务范围校验、授权、数据库事务和幂等处理仍需要程序实现。因此我们保留 common 中的领域构造器，不把生成的公共字段结构直接当作已经合法的业务对象。

### 25.1.6 【精通】编译一致与运行版本一致

同一 workspace 同时编译双方，能发现当前源码之间的不匹配；真实部署中，新旧客户端和服务端可能并存，单次全量编译并不能证明跨版本兼容。

例如新客户端开始依赖一个新字段，旧服务仍能返回可解码消息，但该字段永远是默认值。若新逻辑把默认值当作有效业务结论，就会出现“协议没报错，行为却错了”的情况。契约审核必须包含混合版本与默认值含义。

## 25.2 从十一字节的小实验理解编码

### 25.2.1 【入门】创建独立 wire-lab

先在 RustMall 目录之外创建 wire-lab，准备 src 子目录。这是只依赖 prost 的独立练习，不加入业务 workspace，也不需要 Docker、数据库或集群。Cargo.toml 完整内容如下：
```toml
[package]
name = "wire-lab"
version = "0.1.0"
edition = "2024"
rust-version = "1.92"

[dependencies]
prost = "=0.14.4"
```

这里与项目后面的 prost 使用相同版本，便于解释同一套行为。首次构建可能下载依赖；下载失败与编码错误属于不同问题。进入 wire-lab 目录后再执行本节命令，避免在另一个 workspace 中意外创建不受管理的成员。

### 25.2.2 【入门】一个最小消息类型

src/main.rs 的完整内容如下：
```rust
use prost::Message;

#[derive(Clone, PartialEq, Message)]
struct Brief {
    #[prost(int64, tag = "1")]
    id: i64,
    #[prost(string, tag = "2")]
    name: String,
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let value = Brief {
        id: 150,
        name: "键盘".to_string(),
    };
    let bytes = value.encode_to_vec();
    println!("{bytes:02x?}");
    let decoded = Brief::decode(bytes.as_slice())?;
    assert_eq!(decoded, value);
    Ok(())
}
```

Brief 只有 id 与 name。prost 属性给出字段类型与编号，Message 派生实现编码能力；这个练习直接写 Rust 属性，是为了缩短观察路径。正式 contracts 包会以 .proto 为来源，不让两套手写定义长期并存。

Message 派生已经提供所需的相关实现，不要机械添加另一份同名 trait 实现。若遇到 conflicting implementations，先看生成或派生已经提供了什么，再判断是否需要自己的实现。

### 25.2.3 【入门】运行并读取输出

在 wire-lab 目录执行：
```bash
cargo +1.92.0 run
```

本章输入应打印以下十六进制字节，并在断言通过后正常退出：
```text
[08, 96, 01, 12, 06, e9, 94, ae, e7, 9b, 98]
```

println 中的 02x 表示按两位十六进制显示；它没有把内部消息改成文本协议。encode_to_vec 返回拥有字节的 Vec，as_slice 临时借用这些字节供 decode 使用，解码得到的 Brief 重新拥有自己的字符串。

### 25.2.4 【进阶】字段键包含编号和线型

Protobuf 字段键把字段编号与 wire type 组合。对本例，第一字段 id 的编号为 1，使用 varint 线型，键为十六进制 08；第二字段 name 编号为 2，使用长度定界线型，键为 12。

这个键不是字段名的哈希，也不包含 Rust 变量名称。把 name 改成 title 而保留编号，二进制仍可能被旧定义读到同一位置；但生成的 Rust API、JSON 名称与业务语义可能已经改变，所以“字节能读”并不代表所有层面都兼容。

### 25.2.5 【进阶】150 为什么使用两个字节

非负整数 150 的 varint 表示是 96 01。每个字节只用低七位承载数据，最高位表示后面是否还有字节；因此它不是把十进制字符 1、5、0 逐个发出去，也不是固定长度八字节。

变长表示能让常见小整数比较紧凑，但不能据此认为所有数据总比 JSON 小很多。消息大小还取决于字段、数值、字符串、压缩与外围协议；性能结论需要针对实际请求测量。

### 25.2.6 【进阶】字符串长度按字节计算

name 的键后面是 06，表示后续 UTF-8 数据长六字节。键与盘各占三个 UTF-8 字节，合起来不是“两个字节”。这与前面 Rust 字符串章节中 len 返回字节数的概念一致。

业务名称长度校验可能按 Unicode 字符计数，而编码长度按字节计算。不要把协议缓冲区长度限制直接解释为允许多少个中文字符；需要分别说明字段语义与传输大小上限。

### 25.2.7 【精通】int 与 sint 的取舍

int64 与 sint64 都可以表达有符号整数，但负数的编码方式不同。sint 使用 ZigZag，使接近零的正负数更适合紧凑 varint；不能因为看到整数就随意更换已发布字段的类型。

RustMall 的商品 ID、价格和库存正常情况下非负，沿用原契约的 int64/int32，不为追求某个负数示例更改线上字段。若未来新设计需要频繁传输有正有负的小增量，应在新字段或新消息中选择合适表示，并审核兼容边界。

### 25.2.8 【精通】不要依赖一份唯一字节序列

本节打印的确定字节用于解释这个输入与实现，不应升级为“所有等价 Protobuf 消息都只有这一种编码”。字段顺序、未知字段等因素可能使语义等价消息出现不同字节形式。

因此不要随手把任意消息的原始编码当作业务签名或去重键。需要签名或事件身份时，先定义明确的规范化与身份协议；后面的事件章节会使用显式事件 ID，而不是依赖碰巧相同的编码输出。

## 25.3 消息类型、默认值与领域不变量

### 25.3.1 【入门】读懂一条字段声明

在 .proto 中，int64 price_cents = 3; 由类型、字段名与编号组成。编号标识二进制位置，名字供人阅读与代码生成，类型决定相应编码及生成语言类型。

字段编号允许从 1 到 536870911，但 19000 到 19999 留给协议实现；常用小编号的键更紧凑。选择编号时首先保持长期身份稳定，不为节省某几个字节重新编号已发布字段。

编号不是 SQL 列顺序，也不要求随着源码行号变化而重新排序。已经使用的字段应保持编号稳定；把字段“整理漂亮”而顺手重编号，是容易造成数据误读的修改。

### 25.3.2 【入门】本章的标量映射

| Protobuf 声明 | 本章生成的 Rust 表示 | 仍需业务说明 |
| --- | --- | --- |
| int64 id | i64 | 是否必须大于零、属于哪种实体 |
| int64 price_cents | i64 | 单位为分、允许范围与币种约定 |
| int32 stock | i32 | 是否允许负数、由谁写入 |
| string name | String | 规范化、长度与空白规则 |
| repeated Product items | Vec&lt;Product&gt; | 排序、分页与返回条数上限 |

生成的 Product 与 common::product::Product 同名，却位于不同模块。前者是传输对象，字段公开以便组装；后者维护领域规则。后面的服务实现会显式转换，不让同名造成职责混淆。

### 25.3.3 【进阶】隐式存在性与默认值

当前 proto3 契约沿用普通标量字段。未出现的数值字段会读到零，字符串读到空字符串，repeated 读到空集合；不能仅凭最终数值判断“发送者明确传了零”还是“消息没有这个字段”。

这会影响更新接口。当前 UpdateProduct 表达整体替换，省略 stock 就会形成默认零，而不是自动保留旧库存。若设计局部更新，应另外表达存在性与允许修改范围，不能把同一请求悄悄改成另一种语义。

### 25.3.4 【进阶】optional 表达的是存在与否

需要区分“未提供”和“提供了默认值”时，可以使用有存在性的字段。例如一个独立练习消息里的 optional int32 stock，在相应 prost 生成代码中可以通过 Option&lt;i32&gt; 区分 None 与 Some(0)。

这段讨论不是让读者立即修改本章已发布字段。改变字段的存在性表示还可能改变 Rust 调用点与业务校验，即使二进制层面存在兼容路径，也应作为协议变更审查，而不是为了消除编译错误到处填默认值。

### 25.3.5 【进阶】嵌套消息与 oneof

消息字段可以表示一个复合对象；oneof 表示多个候选中当前选择一个，例如未来某类结果只能是成功信息或特定拒绝原因。它能帮助表达互斥关系，但通常还要考虑完全未设置的情况。

不要把 oneof 当成任意业务状态机的完整实现。一个“已支付”分支可以包含结构合法但金额不匹配的数据；协议类型减少非法形状，领域逻辑仍要判断非法业务事实。

### 25.3.6 【进阶】枚举零值必须有清楚含义

新设计枚举时，通常给零值一个明确的未指定语义，避免旧调用方缺字段后意外得到一个有业务副作用的状态。未知数值的具体表示还要结合生成库检查，不能假设只能出现源码中已列出的分支。

本章 Catalog 消息暂时没有业务枚举，先保留这条设计原则给后面的订单与库存契约。阅读生成代码时要分清保存的原始数值与转换成枚举的结果，错误转换不能通过 unwrap 变成服务崩溃。

### 25.3.7 【精通】解码成功不代表商品合法

Product 的空消息能够成功解码为 id=0、name 为空、price_cents=0、stock=0。这是格式层面的默认行为，不证明数据库存在这种商品，也不证明空名称满足规则。

contracts 的单元测试会固定这个现象，提醒服务实现调用领域构造器和必要的 ID 校验。不要为了让请求“更友好”，把非法 ID 悄悄改成某个默认商品；InvalidArgument 与 NotFound 应保持不同含义。

### 25.3.8 【精通】JSON 映射与整数精度

Protobuf 的规范 JSON 映射对某些整数类型采用字符串表示，不能把它与任意 serde_json 输出当成同一契约。RustMall 现有 Axum JSON 接口由自己的 DTO 与序列化规则决定，内部 gRPC 不会自动改变它。

跨语言调用还应考虑接收语言的整数精度。JavaScript 常见 number 表示不能精确覆盖整个 i64 范围；如果公开接口要支持任意大 ID 或金额，应明确范围或字符串策略。这里继续保留整数分的业务单位，不使用浮点数绕开类型设计。

## 25.4 协议演进：旧消息会怎样被新版本理解

### 25.4.1 【入门】新增字段与旧解码器

为消息增加一个未使用编号的字段，旧解码器通常可以跳过自己不认识的字段。这个能力让滚动升级有基础，但新增字段的默认值仍必须允许旧发送者缺失。

例如增加 display_name，旧服务没有发送，新客户端得到默认空值。新客户端需要明确回退规则，不能立刻要求所有响应都有非空 display_name，然后声称“只是新增字段，所以没有破坏兼容”。

### 25.4.2 【进阶】删除后保留编号与名称

删除已使用字段后，应该在协议定义中保留相应编号，必要时同时保留名称，避免未来重用。示意写法是 reserved 5; 与 reserved "old_label";，它们用于防止新的定义占用旧身份。

这类声明保护未来源码变更，不会修改已经存储或正在传输的旧字节。若系统还有旧消息日志、缓存或延迟消费，兼容窗口可能比应用滚动发布长得多。

### 25.4.3 【进阶】同线型也可能发生语义灾难

假设编号 3 原来表示价格分，后来重用为折扣百分比。两者都能用整数线型，解码可能成功，却把 19900 分解释成 19900%。协议层未必有足够信息识别这种误用。

这就是不能依赖“没有解析错误”判断兼容的原因。编号、单位、取值规则与业务含义共同形成契约；变更评审应逐项说明，而不是只看生成代码能否编译。

### 25.4.4 【进阶】未知字段能跳过，不代表能原样转发

本章 prost 版本会让生成的普通消息跳过未知字段，但默认结构不保存任意未知字段集合。把消息解码成当前 Product 后再编码，未知字段可能消失。

单元测试会给 Product 字节追加编号 5 的整数，再解码与重编码，观察额外字段被丢弃。若一个中间服务要保留新版本字段，不能把“读取旧字段成功”误认为“透明代理了所有输入”；需要设计原始字节转发或合适的保留机制。

### 25.4.5 【精通】四个方向都要考虑

变更至少检查旧客户端到新服务、新客户端到旧服务，以及旧数据到新读取者、新数据到旧读取者。它们的默认值、错误处理和存活时间可能不同。

例如一个新增必需语义可以先由服务端接受缺省并记录使用情况，再升级调用方，最后逐步收紧；不能一次部署就假设全部旧请求已消失。后面的数据库迁移和事件演进采用同样的兼容窗口思路。

### 25.4.6 【精通】包版本不是自动兼容开关

package rustmall.catalog.v1 构成协议命名空间，也参与 gRPC 方法身份。新增 v2 可以明确建立另一套接口，但服务器、客户端与路由仍需真实支持它；改一个字符串不会自动把旧调用转换过来。

本章保留 v1 与原来的五个方法，给后面拆分建立稳定起点。真正不兼容的改变需要安排共存、迁移和退役，而不是把旧方法删掉后只在文档标题写上升级版本。

## 25.5 gRPC 的调用生命周期与状态

### 25.5.1 【入门】一次 unary 调用包含什么

unary 调用是一条请求消息对应一条响应消息。客户端确定完整方法，建立或复用连接，发送请求元数据和消息，服务端处理后返回响应以及最终状态。

这里“一条消息”不是“一次 TCP read”。底层可以分片与复用，应用不应按网络读取次数推断业务请求边界。tonic 负责相应协议处理，业务方法处理已经解码的类型。

### 25.5.2 【进阶】HTTP/2 与 gRPC 消息边界

常见 gRPC 传输建立在 HTTP/2 上。一个连接可以承载多个流，每个 RPC 使用相应的流；gRPC 消息还有自己的消息封装，不是直接把 Protobuf 字节不加区分地连在一起。

复用减少了某些连接开销，但仍共享底层网络、连接状态和资源。连接中断可能同时影响多次调用，慢消费也会涉及流控。不能因为支持多流，就推导出任意并发都不需要限制。

### 25.5.3 【入门】Request 与 Response 包装

tonic::Request&lt;T&gt; 把业务消息 T 与元数据等信息放在一起，Response&lt;T&gt; 对应成功响应。request.get_ref() 借用内部消息，into_inner() 消耗包装并取得消息所有权。

本章 Demo 先读取元数据，再调用 into_inner 取 ID，顺序清楚地体现了借用与移动。若先消耗 request，再继续访问它的 metadata，Rust 会阻止已移动值被使用。

### 25.5.4 【进阶】成功消息与错误 Status

方法返回 Result&lt;Response&lt;Product&gt;, Status&gt;。成功时返回具体商品，不存在时返回 NotFound，输入不合法返回 InvalidArgument，缺少身份返回 Unauthenticated。不要用一个字段全零的 Product 替代错误。

Status 包含可机器处理的 code 和描述。对外描述应避免泄露数据库密码、内部 SQL 或令牌。服务日志可以记录必要上下文，但不应把完整敏感请求逐字打印。

### 25.5.5 【进阶】状态码为调用者提供分类

| 状态 | 本章语境 | 调用者首先应做什么 |
| --- | --- | --- |
| InvalidArgument | ID 等输入不满足规则 | 修正输入，避免原样重试 |
| Unauthenticated | 缺少或无效调用身份 | 检查认证配置与凭据生命周期 |
| PermissionDenied | 身份已确认但没有权限 | 检查授权规则 |
| NotFound | 合法查询没有对应在售商品 | 按业务不存在处理 |
| Unimplemented | 本章 Demo 没实现该方法 | 核对服务与方法版本 |
| Unavailable | 当前服务或传输不可用 | 结合操作性质和退避决定是否重试 |
| DeadlineExceeded / Cancelled | 期限、取消或特定传输超时路径 | 先确认执行结果是否可能已发生 |

这张表不是无条件重试表。即使 Unavailable 可能是暂时故障，写操作仍需考虑是否已经产生副作用；业务语义决定能否重试，状态码只是证据之一。

### 25.5.6 【精通】HTTP 状态不等于最终 RPC 状态

诊断 gRPC 时，需要检查最终 gRPC 状态与相关 trailers，不能只看到 HTTP 200 就宣布业务成功。普通只会理解 JSON HTTP 的检查器，也不能直接拿来检查本章的 RPC 方法。

第 21 章 HTTP 检查器继续验证 monolith 的既有公共接口；本章用生成的 CatalogClient 验证 RPC。两套工具分别观察两种契约，后面的网关会把它们连接起来。

### 25.5.7 【精通】流式调用先理解消费与背压

gRPC 还支持服务端流、客户端流与双向流，消息可以连续产生与消费。流不是免费无限数组；生产速度超过消费速度时，需要限制缓冲、处理背压，并定义半关闭、取消与错误后的状态。

RustMall 当前商品操作采用 unary，先把单位调用、错误和超时讲透。后续若引入长连接通知或批量传输，应单独定义流内每条消息的身份、顺序和恢复策略，不能只把返回类型换成 Stream 就认为功能完整。

## 25.6 连接、期限、取消与身份元数据

### 25.6.1 【入门】Channel 负责连接，Client 负责调用接口

Endpoint 描述服务地址与连接策略，连接后得到 Channel，生成的 CatalogClient 通过 Channel 发送请求。不要为每一次商品查询都从头建立连接；连接复用与业务并发应有明确设计。

生成客户端的方法通常需要 &amp;mut self，并不表示整个系统只能串行执行 RPC。Channel 可以廉价克隆，客户端也可以按库支持方式克隆共享底层连接；若所有请求都抢一把长期持有的全局互斥锁，反而可能人为制造串行瓶颈。

### 25.6.2 【进阶】连接超时与请求超时

connect_timeout 约束建立连接的等待；Endpoint::timeout 给客户端请求路径加本地超时。前者成功不代表业务会及时返回，后者也不自动告诉服务端自己的剩余等待预算。

本章测试为连接设置两秒上限，为请求设置 150 毫秒本地预算。它们是实验参数，目的在于让永不完成的 Demo 分支可观察，不是实际商品查询延迟目标。生产预算应根据调用链与容量分析确定。

### 25.6.3 【进阶】set_timeout 传递给服务端什么

Request::set_timeout 把相应期限信息写入 grpc-timeout 元数据，使支持该机制的服务端知道这次调用允许等待的时长。Endpoint 的本地 timeout 与它属于不同机制，本章两者都设置，分别约束调用方与通知对方。

如果只有客户端本地超时，调用方放弃等待后，服务端未必能据此取消全部后台工作。如果有多级调用，下游预算也不能每次重置为完整初始时长；应从总期限扣除已用时间，这与前面共享停机预算的思路一致。

### 25.6.4 【精通】超时后的状态码需要看具体路径

协议层的 DeadlineExceeded 与取消类状态都需要正确识别。当前 tonic 0.14.6 的某些本地超时错误会转换为 Cancelled；本章同为 150 毫秒的本地与服务端期限还存在先后竞争，不能断言只会出现其中某一个。

本次运行观察到 Cancelled。测试接受 Cancelled 或 DeadlineExceeded，同时要求两秒的外层保护没有触发，并拒绝 Unauthenticated、NotFound 等无关错误。这样既验证等待有界，也避免把“任何错误都算超时测试通过”。

### 25.6.5 【精通】取消不等于撤销已经提交的动作

客户端 Future 结束、HTTP/2 流取消、服务方法 Future 被丢弃，与数据库事务提交是不同事件。某个写操作可能在取消前已经提交；单独 spawn 的后台任务也可能继续运行。

因此不能在客户端看到 Cancelled 后立即假定库存未扣减，再用一个新请求重复写入。需要幂等身份、持久化状态与查询恢复流程。当前 Demo 的挂起分支没有真实副作用，后面的库存与订单章节会把这个窗口具体化。

### 25.6.6 【进阶】元数据提供上下文，不自动提供信任

metadata 可以携带调用身份、请求 ID 等信息。本章使用 x-demo-token: test-only 观察元数据如何进入服务端，只用于回环网络测试。字符串放进头部，不代表它经过了认证、保密传输或权限审核。

下一章会定义商品服务实际使用的服务身份；外部用户 JWT 与内部服务身份的责任也不同。不能直接相信调用方传来的 x-user-role=admin，更不能把业务授权写成“头里有这个字段就通过”。

### 25.6.7 【精通】TLS、服务身份与业务权限分别处理

TLS 负责相应传输保护与证书校验，双向 TLS 还可以让双方验证证书身份；服务令牌或其他凭据也有独立生命周期。确认调用者身份以后，仍需判断该身份能否执行某个商品写操作。

本章测试明确使用本机回环明文地址，观察协议功能；它没有实现跨主机的 TLS 部署和轮换。后面的服务治理与网络章节再给出实际配置。不要把能连上 Channel 当作已经完成认证，也不要通过关闭证书校验修复名称或信任链错误。

## 25.7 从 .proto 到 Rust：生成链路必须可复现

### 25.7.1 【入门】protoc 与 Rust 生成器

protoc 读取 .proto，生成器把协议描述转换成目标语言代码。Rust 项目中的 prost-build 与 tonic-prost-build 配合生成消息、服务 trait 与客户端适配。生成的内容还要与运行时库匹配。

本章固定 tonic、tonic-prost、tonic-prost-build 为 0.14.6，prost 与 prost-build 为 0.14.4。这是当前教材检查点的输入，不要求所有 crate 使用同一个版本字符串；重要的是这组依赖已经一起编译并执行，而不是把网上不同年代的片段随意拼接。

### 25.7.2 【进阶】构建依赖与运行依赖

build-dependencies 供 build.rs 在构建阶段使用，dependencies 供生成代码及程序运行使用。把 tonic-prost-build 只放进普通 dependencies，不能让构建脚本自动使用它；反过来，运行时需要的 codec 也不能只放进构建依赖。

tokio-stream 的 net feature 为本章测试提供 TcpListenerStream，Tokio 的 net、time 与运行时 feature 支持真实监听和异步等待。缺 feature 时出现找不到类型，不应通过更换一套无关库版本来掩盖。

### 25.7.3 【进阶】为什么使用显式 protoc 路径

protoc-bin-vendored 提供受支持平台对应的编译器路径，build.rs 把它交给 prost_build::Config::protoc_executable。这样实验不依赖读者机器上的任意 protoc，也不需要在构建脚本中修改全局环境变量。

平台支持仍要按所用依赖版本检查；不能从本机成功推导出每种交叉编译环境都受支持。这里编译器是构建机器上运行的工具，最终业务程序的目标架构则是另一维度，交叉编译时尤其要分清。

### 25.7.4 【进阶】OUT_DIR 与 include_proto

Cargo 为构建脚本提供生成输出目录，include_proto! 按协议包名纳入对应生成文件。本章模块叫 contracts::catalog，宏参数仍是 rustmall.catalog.v1，它们分别属于 Rust 路径与 Protobuf 包身份。

不应手工去 target 下改生成文件修复业务错误：下次构建会覆盖，审查者也难以追踪。协议问题改 .proto，生成选项问题改 build.rs，业务逻辑问题改实现服务；每一层保留自己的来源。

### 25.7.5 【精通】重建触发与锁文件

build.rs 输出 cargo:rerun-if-changed=proto/catalog.proto，提醒 Cargo 在契约变化时重新生成。以后增加 import 文件，也要检查对应输入是否被正确追踪，避免修改了协议却继续使用旧生成结果。

加入新工作区成员后先按正常构建更新 Cargo.lock，审查依赖变化，再在验收和 CI 中使用 --locked。生成器、运行时、protoc 分发包与锁文件共同构成构建输入，不能只保留 .proto 就宣称完全可复现。

## 25.8 RustMall 实战：增加 contracts，不提前搬走业务

### 25.8.1 【入门】文件清单与顺序

从第 24 章工程根目录继续。现有 common、monolith、platform、部署文件和 Helm Chart 保留；新增 contracts 包，并把它加入已有 workspace.members。

| 文件 | 操作 | 目的 |
| --- | --- | --- |
| Cargo.toml | 在 members 中追加 contracts | 纳入现有工作区 |
| Cargo.lock | 由构建更新并审查提交 | 固定生成与运行依赖 |
| contracts/Cargo.toml | 新建 | 声明生成、传输与测试依赖 |

wire-lab 是之前独立练习，不复制为当前 workspace 成员。它与项目演示相同编码原理，但不会引入第二份长期维护的商品契约。

### 25.8.2 【进阶】第一步：清单与依赖

在已有 members 数组里追加 "contracts"，保留前面全部成员；下面不是让你覆盖整个根 Cargo.toml。创建 contracts/Cargo.toml：

### 25.8.3 【进阶】第二步：完整商品协议

创建 contracts/proto/catalog.proto：
```protobuf
syntax = "proto3";
package rustmall.catalog.v1;

service Catalog {
  rpc GetProduct(GetProductRequest) returns (Product);
  rpc ListProducts(ListProductsRequest) returns (ListProductsResponse);
  rpc CreateProduct(CreateProductRequest) returns (Product);
  rpc UpdateProduct(UpdateProductRequest) returns (Product);
  rpc DelistProduct(GetProductRequest) returns (DelistProductResponse);
}
message Product {
  int64 id = 1;
  string name = 2;
  int64 price_cents = 3;
  int32 stock = 4;
}
message GetProductRequest { int64 id = 1; }
message ListProductsRequest { int64 limit = 1; int64 offset = 2; }
message ListProductsResponse { repeated Product items = 1; int64 total = 2; }
message CreateProductRequest {
 string name = 1;
 int64 price_cents = 2;
 int32 stock = 3;
}
message UpdateProductRequest {
  int64 id = 1;
  string name = 2;
  int64 price_cents = 3;
  int32 stock = 4;
}
message DelistProductResponse {}
```

五个方法分别是详情、列表、新增、整体更新与下架，沿用已有商品能力。Product 中的金额是整数分，stock 是当前阶段的库存数；未来库存写入职责收口时会专门讨论旧接口如何限制，不能现在假定这一写入口永远合适。

ListProductsRequest 使用 limit、offset，公共 HTTP 的 page/page_size 会在后面的适配层转换。计划的服务语义为 limit 在 1 到 100、offset 非负，非法输入返回 InvalidArgument；排序仍为在售商品创建时间倒序，再按 ID 倒序。本章 Demo 不实现列表，下一章才用数据库证明这些语义。

DelistProductResponse 为空消息，只表示成功的响应形状；错误仍由 Status 表达。不存在的商品与重复下架如何处理，应保持与既有业务约定一致，不能因为空响应就吞掉所有失败。

### 25.8.4 【精通】第三步：构建脚本

创建 contracts/build.rs：
```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut config = prost_build::Config::new();
    config.protoc_executable(protoc_bin_vendored::protoc_bin_path()?);
    tonic_prost_build::configure().compile_with_config(
        config,
        &["proto/catalog.proto"],
        &["proto"],
    )?;
    println!("cargo:rerun-if-changed=proto/catalog.proto");
    Ok(())
}
```

先取得对应平台 protoc 路径，写入 prost 配置，再把完整配置交给 tonic 生成器。proto 文件路径与 import 根目录分开传入；将来增加协议文件时，检查二者对应关系，不要把 package 名当成磁盘目录传入。

函数返回 Result，让编译器查找、协议解析和生成失败直接成为构建失败。这里没有调用 std::env::set_var，也不需要为了配工具路径给 Rust 2024 代码添加未经解释的 unsafe 块。

### 25.8.5 【进阶】第四步：模块与消息语义测试

创建 contracts/src/lib.rs：
```rust
pub mod catalog {
    tonic::include_proto!("rustmall.catalog.v1");
}

#[cfg(test)]
mod tests {
    use super::catalog::Product;
    use prost::Message;
    #[test]
    fn integer_money_and_unicode_round_trip() {
        let value = Product {
            id: 7,
            name: "机械键盘".into(),
            price_cents: 19900,
            stock: 10,
        };
        assert_eq!(
            Product::decode(value.encode_to_vec().as_slice()).unwrap(),
            value
        );
    }
    #[test]
    fn empty_wire_message_does_not_validate_business_rules() {
        let decoded = Product::decode(&[][..]).unwrap();
        assert_eq!((decoded.id, decoded.price_cents, decoded.stock), (0, 0, 0));
        assert!(decoded.name.is_empty());
    }
    #[test]
    fn unknown_field_is_ignored_by_current_decoder() {
        let mut data = Product {
            id: 7,
            ..Default::default()
        }
        .encode_to_vec();
        data.extend_from_slice(&[0x28, 0x01]); // field 5, varint 1
        let decoded = Product::decode(data.as_slice()).unwrap();
        assert_eq!(decoded.id, 7);
        assert_eq!(decoded.encode_to_vec(), [0x08, 0x07]);
    }
}
```

第一个测试验证中文名称与整数金额往返，避免把金额改成浮点；第二个证明空消息解码并不执行业务校验；第三个追加未知字段，再验证当前解码器能读取旧字段，并在重编码时丢掉未保存字段。

这些测试不启动服务器。它们观察的是当前 prost 生成结构的具体行为，不能替代真实 RPC、跨语言互操作或完整的新旧版本兼容矩阵。注意解码输入借用 bytes，解码输出拥有 String，与网络调用中的所有权转移相互衔接。

### 25.8.6 【进阶】第五步：完整传输实验

创建 contracts/tests/transport.rs：
```rust
use contracts::catalog::{
    catalog_client::CatalogClient,
    catalog_server::{Catalog, CatalogServer},
    *,
};
use std::time::Duration;
use tokio_util::sync::CancellationToken;
use tonic::{
    Request, Response, Status,
    transport::{Endpoint, Server},
};

#[derive(Default)]
struct Demo;
#[tonic::async_trait]
impl Catalog for Demo {
    async fn get_product(
        &self,
        request: Request<GetProductRequest>,
    ) -> Result<Response<Product>, Status> {
        if request
            .metadata()
            .get("x-demo-token")
            .and_then(|v| v.to_str().ok())
            != Some("test-only")
        {
            return Err(Status::unauthenticated("demo token required"));
        }
        let id = request.into_inner().id;
        if id <= 0 {
            return Err(Status::invalid_argument("id must be positive"));
        }
        match id {
            1 => Ok(Response::new(Product {
                id: 1,
                name: "键盘".into(),
                price_cents: 19900,
                stock: 10,
            })),
            3 => std::future::pending().await,
            _ => Err(Status::not_found("product not found")),
        }
    }
    async fn list_products(
        &self,
        _: Request<ListProductsRequest>,
    ) -> Result<Response<ListProductsResponse>, Status> {
        Err(Status::unimplemented("transport demo"))
    }
    async fn create_product(
        &self,
        _: Request<CreateProductRequest>,
    ) -> Result<Response<Product>, Status> {
        Err(Status::unimplemented("transport demo"))
    }
    async fn update_product(
        &self,
        _: Request<UpdateProductRequest>,
    ) -> Result<Response<Product>, Status> {
        Err(Status::unimplemented("transport demo"))
    }
    async fn delist_product(
        &self,
        _: Request<GetProductRequest>,
    ) -> Result<Response<DelistProductResponse>, Status> {
        Err(Status::unimplemented("transport demo"))
    }
}
async fn start() -> (
    CatalogClient<tonic::transport::Channel>,
    CancellationToken,
    tokio::task::JoinHandle<()>,
) {
    let listener = tokio::net::TcpListener::bind("127.0.0.1:0").await.unwrap();
    let addr = listener.local_addr().unwrap();
    let token = CancellationToken::new();
    let shutdown = token.clone();
    let task = tokio::spawn(async move {
        Server::builder()
            .add_service(CatalogServer::new(Demo))
            .serve_with_incoming_shutdown(
                tokio_stream::wrappers::TcpListenerStream::new(listener),
                shutdown.cancelled_owned(),
            )
            .await
            .unwrap();
    });
    let channel = Endpoint::from_shared(format!("http://{addr}"))
        .unwrap()
        .connect_timeout(Duration::from_secs(2))
        .timeout(Duration::from_millis(150))
        .connect()
        .await
        .unwrap();
    (CatalogClient::new(channel), token, task)
}
fn request(id: i64, token: bool) -> Request<GetProductRequest> {
    let mut r = Request::new(GetProductRequest { id });
    r.set_timeout(Duration::from_millis(150));
    if token {
        r.metadata_mut()
            .insert("x-demo-token", "test-only".parse().unwrap());
    }
    r
}
#[tokio::test]
async fn unary_round_trip_keeps_integer_money() {
    let (mut client, token, task) = start().await;
    let value = client
        .get_product(request(1, true))
        .await
        .unwrap()
        .into_inner();
    assert_eq!((value.id, value.price_cents, value.stock), (1, 19900, 10));
    stop(token, task).await;
}

}
#[tokio::test]

#[tokio::test]
async fn stalled_rpc_is_bounded_by_the_client() {
    let (mut client, token, task) = start().await;
    let result =
        tokio::time::timeout(Duration::from_secs(2), client.get_product(request(3, true))).await;
    let status = result
        .expect("outer two-second guard must not expire")
        .expect_err("stalled RPC must fail inside the transport budget");
    assert!(matches!(
        status.code(),
        tonic::Code::Cancelled | tonic::Code::DeadlineExceeded
    ));
    println!("bounded RPC status: {:?}", status.code());
    stop(token, task).await;
}

async fn stop(token: CancellationToken, mut task: tokio::task::JoinHandle<()>) {
    token.cancel();
    match tokio::time::timeout(Duration::from_secs(1), &mut task).await {
        Ok(result) => result.expect("demo server task must finish without panic"),
        Err(_) => {
            task.abort();
            match task.await {
                Ok(()) => {} // Completion may race with the abort request.
                Err(error) if error.is_cancelled() => {}
                Err(error) => panic!("demo server failed during cleanup: {error}"),
            }
        }
    }
}

#[tokio::test]
async fn invalid_id_is_distinct_from_an_absent_product() {
    let (mut client, token, task) = start().await;
    assert_eq!(
        client
            .get_product(request(0, true))
            .await
            .unwrap_err()
            .code(),
        tonic::Code::InvalidArgument
    );
    stop(token, task).await;
}
```

Demo 只实现足够观察传输的 GetProduct：缺少演示身份返回 Unauthenticated，非正 ID 返回 InvalidArgument，ID 1 返回固定商品，ID 3 故意永不完成，其他 ID 返回 NotFound。其余方法明确返回 Unimplemented，不伪装成已经完成商品微服务。

这个测试载体没有真实数据库。通过它先排除编码、方法映射与传输配置问题，下一章再把实际仓储接上；否则初学者遇到一次失败时，很难分辨是 SQL、网络还是方法定义出错。

### 25.8.7 【精通】逐段解释服务实现

Catalog trait 由协议生成，#[tonic::async_trait] 让这里按对应异步接口实现。方法接收 Request&lt;GetProductRequest&gt;，先检查 metadata，然后 into_inner 移走消息。合法响应组装传输 Product，和 common 的领域 Product 并不是同一种类型。

ID 3 的 pending 永远不返回，专门用于测试期限。它不是模拟真实业务的推荐方式，也没有生成后台副作用。测试必须有自己的外层保护，避免程序错误导致整个测试进程无限等待。

### 25.8.8 【精通】监听器、连接与有界清理

start 先绑定 127.0.0.1:0，操作系统选择空闲端口，再把已经绑定的监听器交给服务器。客户端使用实际 local_addr 连接，避免固定端口冲突和“先猜一个端口再抢占”的窗口。

服务器 JoinHandle 被保留，取消令牌发出后在有界时间内等待；等待超时则 abort 并回收句柄。abort 与正常完成可能竞争，所以清理接受正常结束或明确取消，但不会忽略任务 panic。这比丢弃 JoinHandle 后假定后台任务已经停止更准确。

测试失败时，所属 Tokio 运行时最终也会结束，但正常路径仍要主动清理。资源管理是实验可靠性的一部分；它不能被当成对真实服务全部停机路径的证明。

### 25.8.9 【进阶】运行与解读五个网络测试

在 RustMall 根目录先运行一次构建以更新锁文件，再执行：
```bash

cargo test --locked -p contracts -- --nocapture
cargo clippy --locked --workspace --all-targets --all-features -- -D warnings
```

预期三个消息单元测试与五个传输测试通过。网络测试分别固定成功整数金额、缺身份、合法但不存在、非法 ID 与挂起调用的有界失败。--nocapture 会显示本次观察到的 bounded RPC status，不能要求所有实现与版本打印完全同一状态。

本章清单没有继承工作区的 unwrap_used 警告设置；测试中的 unwrap 用于让意外结果使实验失败，生产方法通过 Result/Status 表达错误。如果团队统一继承 lints，应像第 22 章一样只在测试范围制定清楚策略，不能整体关闭生产诊断。

## 25.9 常见故障与定位实验

### 25.9.1 【入门】先定位是生成、连接还是业务

| 现象 | 应收集的证据 | 修复方向 |
| --- | --- | --- |
| build.rs 报找不到 protoc | 编译脚本诊断、平台与依赖版本 | 核对 vendored 支持与显式路径 |
| include_proto 找不到文件 | package、生成输出与宏参数 | 保持包身份与生成文件一致 |
| 生成代码找不到 ProstCodec | codec 与生成器版本、清单分段 | 核对 tonic-prost 运行依赖 |
| 缺 TcpListenerStream | tokio-stream feature | 开启本章需要的 net feature |
| 连接拒绝 | 服务监听地址、进程与调用位置 | 先确认端口真实存在，再查协议 |
| Unimplemented | 完整服务名、方法名与服务版本 | 排除接错服务和未实现 Demo 方法 |
| Unauthenticated | 元数据键、值与认证路径 | 区分演示令牌和实际服务身份 |
| NotFound | 合法 ID、在售状态与业务语义 | 按不存在处理，不用空商品代替 |
| 挂起测试触发外层两秒保护 | 本地 timeout、请求期限与库版本 | 修复未生效的预算，不只增大测试等待 |
| 重编码丢失新增字段 | 当前生成结构与未知字段策略 | 不把普通 DTO 当透明字节代理 |

一次只沿对应阶段缩小问题。重新生成全部代码、改端口、关闭认证和增大超时一起做，可能偶然恢复，却失去知道哪一项真正修复问题的机会。

### 25.9.2 【进阶】字段编号冲突的失败实验

在独立协议副本中给两个字段使用相同编号，再触发生成，预期 protoc 拒绝。恢复后再试把已 reserved 的编号重新使用，观察编译器如何保护声明。

这些实验应在临时副本，不修改已经发布的主契约。它们证明生成器会拒绝一些结构错误；前面价格与折扣重用编号的反例则说明，没有保留声明时，某些语义错误并不会自动被工具发现。

### 25.9.3 【进阶】移除身份与伪造空响应

保留相同请求 ID，先不加 x-demo-token，观察 Unauthenticated；加入演示值再请求不存在 ID，观察 NotFound。这两者都不应该返回一个默认 Product 并被客户端当成功。

若实验把所有失败都映射成 NotFound，会掩盖身份故障；把所有失败都返回 Internal，又失去调用者可处理的分类。状态设计应先根据原因分层，再决定哪些细节可以公开。

### 25.9.4 【精通】超时测试不能只断言 Err

故意把演示令牌拼错，若原测试只检查 is_err，挂起测试可能因为立即认证失败而变绿。本章限制错误 code，并保留外层保护，避免这类假通过。

更复杂的服务还应记录请求是否真正进入目标分支、在哪个阶段被取消，以及是否已经产生副作用。本章固定 Demo 的输入分支足够小，可以直接审查；未来多层调用需要更强的故障注入与观测证据。

### 25.9.5 【精通】旧字段可读的兼容实验

给当前 Product 编码追加未知编号字段，旧解码器仍读取 ID，再重编码观察字段丢失。接着思考一个日志转发器：如果它用旧结构读出再写入，新消费者还能否得到新字段？

答案取决于转发是否保留原始信息。本章默认结构没有保存该字段，所以不能得到。兼容性必须按真实数据路径验证，不能只做一次新消息到旧解码器的单向成功测试。

## 25.10 分层练习、答案与下一章

### 25.10.1 【入门练习】解释编码输出

题目：把 wire-lab 的 id 改为 1，再改回 150，观察 varint 占用；把名称改为三个中文字符，长度前缀表达的是字符数还是字节数？

参考答案：ID 1 的相应值只需要一个 varint 字节，150 使用两个；字段键仍按编号和线型生成。长度前缀按 UTF-8 字节数，不按中文字符数。完整操作应同时用 Rust 的字符串 len 与 chars().count() 解释观察。

### 25.10.2 【操作练习】区分默认值与非法业务输入

题目：解码空 Product 后，列出四个字段；说明为什么不能直接把它当作“商品不存在”的成功响应。再运行非法 ID 的传输测试。

参考答案：数值为零、名称为空，是解码默认值；不存在应通过明确状态表达，非法 ID 又属于输入错误。接收业务请求时还要调用校验与领域构造器。不能因为结构能创建就跳过业务不变量。

### 25.10.3 【推理练习】新增字段为什么仍可能破坏业务

题目：新客户端要求一个新增字段非空，旧服务从未发送它。二进制解析成功，为什么仍然可能失败？怎样分阶段演进？

参考答案：旧服务缺失字段会形成默认值，新客户端的语义要求已经变强。应先定义兼容缺省与回退，升级发送方和接收方并观察旧版本使用情况，再决定是否收紧；必要时使用新协议版本或新方法，而不是只声明“新增字段安全”。

### 25.10.4 【推理练习】本地超时与服务端期限

题目：只设置 Endpoint::timeout，没有 set_timeout，会让服务端知道当前预算吗？客户端已经超时，能否认定新增商品没有写入？

参考答案：本地超时不会自动设置 grpc-timeout 元数据；通知服务端与限制本地等待需要分别处理。写入可能已提交而响应丢失，所以不能据此认定没执行。恢复应依赖幂等身份、持久状态查询与具体业务协议。

### 25.10.5 【扩展练习】设计局部更新消息

题目：为一个独立练习协议设计“库存不变”和“库存改为零”两种状态，说明普通 int32 为什么不够，以及 optional 或其他显式更新表示的取舍。

参考要点：必须能区分未提供与提供默认零，还要限制谁能修改库存、校验合法范围并定义并发语义。只把字段改成 Option 并不解决权限与丢失更新；不要直接修改本章已发布的整体替换接口再假定所有调用方兼容。

### 25.10.6 【精通练习】建立新旧版本检查表

题目：给 Product 增加一个字段，列出旧客户端、新客户端、旧服务、新服务与转发器的组合，说明每个组合要观察什么。

参考要点：检查默认值是否可接受、未知字段是否被保留、重编码是否丢失信息、状态码是否仍可识别，以及业务是否依赖新增语义。测试必须覆盖实际转发路径，不能只比较两个生成文件的文本。

### 25.10.7 【小结】契约已经可生成，业务拆分下一步进行

本章形成了 RustMall 的内部商品契约，解释了字节、类型、默认值、演进、状态与期限，并用真实回环网络运行客户端和测试服务。现有单体业务继续存在，没有把未实现方法伪装成完整商品服务。

下一章建立独立 catalog 进程与独立数据库，讨论数据所有权、迁移起点、重复写入口以及如何让契约语义落在 SQL 与事务上。后面的网关再把当前 HTTP 接口接到这个服务。最终验收仍要区分编码单元测试、真实传输、数据库业务、镜像和集群，不能用其中一项替代全书完整项目验证。

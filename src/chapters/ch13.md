# 第 13 章 PostgreSQL 从安装到精通

第 12 章的商品存在内存里，重启就没了。本章学习 RustMall 的持久化存储 PostgreSQL：从安装、命令行工具、SQL 语法，到索引、事务、并发控制与运维。项目部分为 RustMall 设计全部数据库表，把第 3章的业务不变量写成数据库约束--让非法数据连数据库都进不去。第 14 章再用 SQLx 在 Rust 中访问它。

## 13.1 关系型数据库与 PostgreSQL

### 13.1.1 【入门】表、行、列

把数据库想象成一组严格的 Excel 表格：

| 概念 | 类比 | RustMall 示例 |
| --- | --- | --- |
| 数据库（database） | 一个 Excel 文件 | rustmall |
| 模式（schema） | 文件里的文件夹 | 默认的 public |
| 表（table） | 一个工作表 | products |
| 列（column） | 表头，每列有固定类型 | price_cents BIGINT |
| 行（row） | 一条记录 | 商品“机械键盘” |
| 主键（primary key） | 每行的唯一编号 | id |
| 外键（foreign key） | “这一行引用了另一张表的哪一行” | orders.product_id → products.id |
| 约束（constraint） | 不允许写入的数据规则 | CHECK (price_cents &gt;= 0) |
| 索引（index） | 书的目录 | 按用户查订单的索引 |

数据库会执行声明的类型与约束；并发业务是否正确，还取决于事务边界、隔离级别、锁与应用不变量（13.7节）。它不会自动防止所有业务竞态。

### 13.1.2 【入门】为什么选 PostgreSQL

| 数据库 | 特点 |
| --- | --- |
| PostgreSQL | 开源关系型数据库，支持类型与约束、JSONB、全文与模糊搜索、窗口函数及扩展；本书使用SQLx连接 |
| MySQL | 客户端/服务器关系型数据库；类型、约束及SQL方言需按所用版本核对 |
| SQLite | 嵌入式、单文件，适合本地存储与轻量网站；远程访问及并发写入需按其架构设计 |

SELECT、JOIN等基础语法有共通部分；本书使用的identity、类型、RETURNING、索引和JSON能力仍需逐项适配，不能承诺换数据库只需少量修改。

## 13.2 安装与连接

### 13.2.1 【入门】用 Docker 安装（推荐）
```bash
# 创建数据卷：容器删除后数据仍在
docker volume create rustmall-pgdata

docker run -d --name rustmall-pg \
  -p 5432:5432 \
  -e POSTGRES_USER=rustmall \
  -e POSTGRES_PASSWORD=rustmall \
  -e POSTGRES_DB=rustmall \
  -v rustmall-pgdata:/var/lib/postgresql/data \
  postgres:17
```

| 参数 | 含义 |
| --- | --- |
| -d | 后台运行 |
| --name rustmall-pg | 容器名，之后用它启停、进入 |
| -p 5432:5432 | 把宿主机的 5432 端口映射到容器的 5432 |
| -e POSTGRES_USER / PASSWORD / DB | 首次启动时创建的超级用户、密码和数据库（只在数据目录为空时生效） |
| -v rustmall- pgdata:/var/lib/postgresql/data | 数据持久化到命名卷 |
| postgres:17 | 固定大版本号；不要用 latest |

常用管理命令：docker stop rustmall-pg 、docker start rustmall-pg 、docker logs -frustmall-pg 、docker exec -it rustmall-pg psql -U rustmall （在容器内打开命令行客戶端）。第 21 章会用 Docker Compose 把数据库、Redis 和服务放进一个配置文件一键启动。

版本提示：postgres:18 及以后的官方镜像调整了数据目录布局，推荐把卷挂载到/var/lib/postgresql 。使用新版本时请对照镜像页面的说明；本书统一使用 17。

### 13.2.2 【入门】原生安装

macOS：brew install postgresql@17 ，然后 brew services start postgresql@17 。默认超级用户是当前系统用户。也可以使用图形化的 Postgres.app。

Ubuntu：系统自带仓库的版本可能较旧，推荐使用 PostgreSQL 官方的 APT 仓库（PGDG）：按官网“Download → Linux → Ubuntu”页面的步骤添加仓库后执行 sudo apt install postgresql-17 。安装后服务自动启动，超级用户是系统用户 postgres ：sudo -u postgres psql 。

Windows：从官网下载 EDB 提供的安装程序，安装时设置 postgres 用户密码；或者在 WSL2 中按Ubuntu 的方式安装，或者直接用 Docker。

原生安装后创建与 Docker 方式相同的用户和数据库：
```text
CREATE ROLE rustmall WITH LOGIN PASSWORD 'rustmall' CREATEDB;
CREATE DATABASE rustmall OWNER rustmall;
```

### 13.2.3 【入门】连接字符串

所有客戶端和程序都用同一种 URL 格式描述如何连接数据库：
```text
postgres://rustmall:rustmall@localhost:5432/rustmall?sslmode=disable
└─协议─┘ └用户┘ └密码┘ └─主机─┘ └端口┘ └库名┘ └──参数──┘
```

密码中的特殊字符（@ 、: 、/ 、# ）必须百分号编码。第 14 章把它写进环境变量DATABASE_URL ，生产环境的密码绝不提交到 Git（第 15、23 章）。

### 13.2.4 【入门】psql 必会命令
```bash
# 本机有 psql 时

# 没有时进入容器
docker exec -it rustmall-pg psql -U rustmall
```

| 命令 | 作用 |
| --- | --- |
| \l | 列出数据库 |
| \c 库名 | 切换数据库 |
| \dt | 列出表 |
| \d 表名 | 查看表结构、索引、约束 |
| \di | 列出索引 |
| \du | 列出用户 |
| \x | 切换扩展显示（字段多时竖向显示一行） |

| \i 文件.sql | 执行 SQL 文件 |

SQL 语句以分号结束才会执行；忘记分号时提示符会变成 rustmall-# ，补上分号回车即可。图形化工具推荐 DBeaver（第 0.4.3 节）或 pgAdmin。

## 13.3 数据类型与建表

### 13.3.1 【入门】常用数据类型及其 Rust 对应

| PostgreSQL 类型 | 说明 | Rust 类型（SQLx，第 14 章） |
| --- | --- | --- |
| SMALLINT / INTEGER /BIGINT | 2 / 4 / 8 字节有符号整数 | i16 / i32 / i64 |
| NUMERIC(p, s) | 任意精度十进制 | rust_decimal::Decimal |
| REAL / DOUBLE PRECIS ION | 浮点 | f32 / f64 |
| BOOLEAN | 布尔 | bool |
| TEXT / VARCHAR(n) | 字符串（PostgreSQL 中两者性能相同，推荐TEXT + CHECK 约束） | String |
| TIMESTAMPTZ | 带时区的时间戳（内部存 UTC） | chrono::DateTime&lt;Utc&gt;/ time::OffsetDateTime |
| DATE | 日期 | chrono::NaiveDate |
| UUID | 128 位唯一标识 | uuid::Uuid |
| JSONB | 二进制 JSON，可索引 | serde_json::Value 或sqlx::types::Json&lt;T&gt; |
| BYTEA | 二进制 | Vec&lt;u8&gt; |
| TEXT[] | 数组 | Vec&lt;String&gt; |

PostgreSQL 没有无符号整数，这正是第 1.3.1 节让 ID 和金额使用 i64 的原因之一。时间一律使用TIMESTAMPTZ ，不要用不带时区的 TIMESTAMP --后者在服务器迁移时区或跨时区部署时会制造难以排查的混乱。

### 13.3.2 【入门】创建表与约束
```sql
CREATE TABLE products (

    -- 自增主键
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        TEXT        NOT NULL CHECK (char_length(name) BETWEEN 1 AND 100),
    price_cents BIGINT      NOT NULL CHECK (price_cents >= 0),
    stock       INTEGER     NOT NULL DEFAULT 0 CHECK (stock >= 0),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

| 约束 | 作用 |
| --- | --- |
| PRIMARY KEY | 唯一且非空，自动建索引 |
| NOT NULL | 不允许为空--对应 Rust 中的非 Option 字段，默认都应该加 |
| DEFAULT | 插入时没有提供值就用默认值 |
| UNIQUE | 唯一，自动建索引 |
| CHECK (表达式) | 表达式不能为 FALSE；NULL 也会通过，需配合 NOT NULL |
| REFERENCES t(col) | 外键：引用的行必须存在 |

GENERATED ALWAYS AS IDENTITY 是 SQL 标准的自增写法，取代旧的 BIGSERIAL ：它禁止应用程序手工指定 ID，避免与序列冲突。

约束是业务规则的最后一道防线：第 3 章的 Product::try_new 已经保证了价格不为负，为什么数据库还要再检查一遍？因为数据不只是通过 Rust 代码写入的：运维手工修数、数据迁移脚本、将来另一个语言写的服务，都绕开了你的 Rust 类型。两层都检查，应用层给出友好的错误信息，数据库保证绝对不会出现脏数据。

### 13.3.3 【进阶】外键与级联
```sql
CREATE TABLE cart_items (

    -- 用户被删，购物车一起删
    user_id    BIGINT  NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    product_id BIGINT  NOT NULL REFERENCES products (id) ON DELETE CASCADE,
    quantity   INTEGER NOT NULL CHECK (quantity BETWEEN 1 AND 99),

    -- 复合主键：同一用户同一商品只有一行
    PRIMARY KEY (user_id, product_id)
);
```

| 外键行为 | 被引用的行删除时 | 适用 |
| --- | --- | --- |
| NO ACTION（默认）/ RESTRICT | 通常拒绝删除；NO ACTION 在约束可延迟时可延后检查，RESTRICT 不可 | 订单引用的商品：有订单的商品不能物理删除 |
| CASCADE | 一起删除引用行 | 从属数据：购物车、地址 |
| SET NULL | 引用列置为 NULL | 可选关联 |

微服务拆分后，不同服务的表在不同的数据库中，跨库外键不再可能（第 26 章）。

### 13.3.4 【进阶】修改表结构
```sql
ALTER TABLE products ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT now();
ALTER TABLE products ALTER COLUMN name SET NOT NULL;
ALTER TABLE products ADD CONSTRAINT products_stock_limit CHECK (stock <= 1000000);
ALTER TABLE products DROP COLUMN legacy_code;
DROP TABLE IF EXISTS temp_import;
```

生产环境的表结构修改必须通过迁移文件版本化管理（第 14 章 sqlx-cli），绝不手工执行。大表上的某些ALTER 会锁表很久（13.8.4 节）。

## 13.4 增删改查

### 13.4.1 【入门】INSERT 与 RETURNING
```sql
INSERT INTO products (name, price_cents, stock) VALUES ('机械键盘', 19900,
10);

-- 一次插入多行
INSERT INTO products (name, price_cents, stock) VALUES
    ('鼠标', 9900, 50),
    ('耳机', 29900, 20);

-- RETURNING：插入的同时返回数据库生成的字段（PostgreSQL 特有，第 14 章大量使用）
INSERT INTO products (name, price_cents, stock) VALUES ('音箱', 39900, 5)
RETURNING id, created_at;
```

### 13.4.2 【入门】SELECT
```sql
-- 只取需要的列，不要 SELECT *
SELECT id, name, price_cents FROM products;
SELECT * FROM products WHERE price_cents BETWEEN 10000 AND 30000 AND stock > 0;

-- 模糊匹配（ILIKE 不区分大小写）
SELECT * FROM products WHERE name LIKE '%键盘%';
SELECT * FROM products WHERE id IN (1, 3, 5);

-- 排序与分页
SELECT * FROM products ORDER BY price_cents DESC, id LIMIT 20 OFFSET 40;
SELECT count(*) FROM products WHERE stock = 0;
```

NULL 的特殊性：NULL 表示“未知”，任何与 NULL 的比较结果都是 NULL（既不是真也不是假）。判断空值必须用 IS NULL / IS NOT NULL ，写 WHERE tracking_no = NULL 永远查不到任何行。

### 13.4.3 【入门】UPDATE 与 DELETE
```text
UPDATE products SET price_cents = 17900, updated_at = now() WHERE id = 1 RETURNING *;

-- 条件更新：防超卖的关键（13.7.3 节）
UPDATE products SET stock = stock - 2 WHERE id = 1 AND stock >= 2;
DELETE FROM cart_items WHERE user_id = 7 AND product_id = 1;
```

永远先写 WHERE：忘记 WHERE 的 UPDATE / DELETE 会修改或删除整张表。在 psql 中手工操作生产数据时，先 BEGIN; 开启事务，执行后检查影响行数是否符合预期，再 COMMIT; 或 ROLLBACK; 。

### 13.4.4 【进阶】UPSERT：INSERT ... ON CONFLICT
```sql
-- 购物车“设置数量”：不存在则插入，存在则更新（对应 PUT /cart/items/{id}）
INSERT INTO cart_items (user_id, product_id, quantity) VALUES (7, 1, 3)
ON CONFLICT (user_id, product_id) DO UPDATE SET quantity = EXCLUDED.quantity;

-- 幂等插入：已存在就什么都不做
INSERT INTO processed_events (event_id) VALUES ('e-123') ON CONFLICT DO NOTHING;
```

EXCLUDED 表示“本来要插入的那一行”。UPSERT 是原子的，不存在“先查再插”之间被别人抢先的竞态--这就是第 6.3.1 节 entry API 在数据库中的对应物。

## 13.5 查询进阶

### 13.5.1 【进阶】JOIN
```sql
-- 订单列表，带上商品名
SELECT o.id, o.status, o.total_cents, p.name AS product_name
FROM orders AS o
JOIN products AS p ON p.id = o.product_id           -- INNER JOIN：两边都匹配才出现
WHERE o.user_id = 7
ORDER BY o.created_at DESC;

-- 所有商品及其销量（没有订单的商品也要出现）
SELECT p.id, p.name, coalesce(sum(o.quantity), 0) AS sold
FROM products AS p
LEFT JOIN orders AS o ON o.product_id = p.id AND o.status <> 'cancelled'   -- LEFT JOIN：左表全部保留
GROUP BY p.id, p.name
ORDER BY sold DESC;
```

| JOIN 类型 | 结果 |
| --- | --- |
| INNER JOIN | 两边都匹配的行 |
| LEFT JOIN | 左表全部行，右表没有匹配时为 NULL |
| RIGHT JOIN | 与 LEFT 相反（很少用，一般换顺序写成 LEFT） |
| FULL JOIN | 两边全部行 |

### 13.5.2 【进阶】聚合与分组
```sql
SELECT status, count(*) AS orders, sum(total_cents) AS revenue
FROM orders
WHERE created_at >= now() - interval '7 days'
GROUP BY status

-- HAVING 过滤分组后的结果；WHERE 过滤分组前的行ORDER BY revenue DESC;
HAVING count(*) > 10
```

常用聚合函数：count 、sum 、avg 、min 、max 、array_agg 、string_agg 、json_agg 。这就是第 6.7 节用迭代器做的分组统计--数据量大时，应该让数据库来做，只把结果传回应用。

### 13.5.3 【进阶】子查询与 CTE
```sql
-- CTE（WITH）：把复杂查询拆成有名字的步骤
WITH recent AS (
    SELECT product_id, sum(quantity) AS qty
    FROM orders
    WHERE created_at >= now() - interval '30 days' AND status <> 'cancelled'
    GROUP BY product_id
)
SELECT p.name, r.qty
FROM recent AS r JOIN products AS p ON p.id = r.product_id
ORDER BY r.qty DESC
LIMIT 10;

-- EXISTS 子查询：买过商品 1 的用户
SELECT u.id, u.username FROM users AS u
WHERE EXISTS (SELECT 1 FROM orders AS o WHERE o.user_id = u.id AND o.product_id = 1);
```

### 13.5.4 【精通】窗口函数

窗口函数在不合并行的情况下做分组计算：
```sql
-- 每个用户最近的 3 个订单
SELECT * FROM (
    SELECT o.*, row_number() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
    FROM orders AS o
) t
WHERE rn <= 3;

-- 每天销售额及累计值
SELECT day, revenue, sum(revenue) OVER (ORDER BY day) AS running_total
FROM (
    SELECT date_trunc('day', created_at) AS day, sum(total_cents) AS revenue
    FROM orders WHERE status <> 'cancelled' GROUP BY 1
) d
ORDER BY day;
```

常用窗口函数：row_number 、rank 、dense_rank 、lag / lead （前一行 / 后一行的值，算环比）、配合 OVER 的 sum 、avg 。

### 13.5.5 【进阶】两种分页的 SQL
```sql
-- 偏移分页：第 3 页，每页 20 条。OFFSET 越大越慢：数据库要先读取并丢弃前 40 行
SELECT id, name FROM products ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 40;

-- 游标分页：从上一页最后一条 (created_at, id) 之后继续，任何深度都能利用索引直接定位
SELECT id, name FROM products

-- 行比较
WHERE (created_at, id) < ('2026-10-01 08:00:00+00', 1042)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

排序必须包含唯一列（这里的 id ）作为最后一个排序键，否则 created_at 相同的行在翻页时可能重复或丢失（与第 6.7.4 节“排序必须有确定的次序”是同一个道理）。

### 13.5.6 第 13.1~13.5 节常见错误

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| 连接失败 | connection refused | 数据库没启动或端口不对 | docker ps 检查容器；确认端口映射 |
| 认证失败 | password authentication failed for user | 用户名或密码错误；数据卷里是旧密码 | 环境变量只在首次初始化时生效，删除数据卷重建或用 ALTER ROLE 改密码 |
| 23502 | null value in column "name"violates not-null constraint | 插入了 NULL | 提供值或设置 DEFAULT |
| 23505 | duplicate key value violates unique constraint | 唯一约束冲突 | 应用层映射为 409（第 14 章） |
| 23514 | new row violates check constraint | CHECK 约束失败 | 修正数据 |
| 23503 | violates foreign key constraint | 引用的行不存在，或要删除的行仍被引用 | 检查引用关系 |
| 42703 | column "x" does not exist | 列名拼错，或用了双引号导致大小写敏感 | 列名一律用小写 snake_case，不加引号 |
| 42601 | syntax error at or near | SQL 语法错误；字符串用了双引号 | 字符串用单引号，双引号只用于标识符 |

五位的错误码（SQLSTATE）是稳定的，第 14 章会据此把数据库错误转换为领域错误：23505→Conflict，23514 → InvalidInput。

## 13.6 索引与执行计划

### 13.6.1 【入门】索引是什么

没有索引时，SELECT * FROM orders WHERE user_id = 7 要逐行扫描整张表（全表扫描）；一百万行的订单表，每次查询都要读一百万行。索引就像书末的关键词索引：按 user_id 排好序的一份“目录”，直接定位到需要的行，复杂度从 O(n) 降到 O(log n)。

代价：索引占用磁盘与内存，并且每次写入都要同时更新所有相关索引。所以索引不是越多越好，只为真实的查询模式建索引。
```text
CREATE INDEX orders_user_id_created_at_idx ON orders (user_id, created_at DESC);
DROP INDEX orders_user_id_created_at_idx;
```

主键和 UNIQUE 约束会自动创建索引；外键不会，需要按查询需要手动创建（PostgreSQL 与 MySQL 的一个差异）。

### 13.6.2 【进阶】复合索引与最左前缀

复合索引 (user_id, created_at) 先按 user_id 排序，user_id 相同时再按 created_at 排序。它可以服务：

| 查询条件 | 能否使用该索引 |
| --- | --- |
| WHERE user_id = 7 | 能 |
| WHERE user_id = 7 ORDER BY created_at DESC | 能，而且不需要额外排序 |
| WHERE user_id = 7 AND created_at &gt; '2026-10-01' | 能 |
| WHERE created_at &gt; '2026-10-01' | 基本不能（没有用到最左边的列） |

设计原则：等值条件的列放前面，范围条件和排序的列放后面。“我的订单按时间倒序分页”这一查询，(user_id, created_at DESC, id DESC) 是最合适的索引。

### 13.6.3 【进阶】其他索引类型

| 类型 | 写法 | 适用 |
| --- | --- | --- |
| B-tree（默认） | CREATE INDEX ... (col) | 等值、范围、排序 |
| 部分索引 | CREATE INDEX ... (created_at) WHERE status = 'pending' | 只索引一部分行：例如“超时未支付订单”扫描只关心 pending |
| 表达式索引 | CREATE INDEX ... (lower(email)) | 查询条件是表达式时 |
| 唯一索引 | CREATE UNIQUE INDEX ... | 带条件或表达式的唯一性约束 |
| GIN | CREATE INDEX ... USING gin (col) | JSONB、数组、全文检索、pg_trgm 模糊搜索 |
| BRIN | CREATE INDEX ... USING brin (created_at) | 按时间顺序追加的超大日志表，极小的索引体积 |

模糊搜索：name LIKE '%键盘%' 前面有通配符，B-tree 索引无法使用。PostgreSQL 的 pg_trgm扩展把文本拆成三字符片段建立 GIN 索引，让这类查询也能走索引--13.9 节为商品名建立这个索引，第 14章的商品搜索会用到。数据量与搜索需求更大时，应使用专门的搜索引擎（Elasticsearch、Meilisearch）。

### 13.6.4 【进阶】EXPLAIN：看懂执行计划
```sql
EXPLAIN ANALYZE
SELECT id, total_cents FROM orders WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;
```
```text
Limit  (cost=0.42..8.61 rows=20 width=16) (actual time=0.031..0.052 rows=20 loops=1)
  ->  Index Scan using orders_user_id_created_at_idx on orders  (cost=0.42..410.20 rows=1002 
      width=16)
        Index Cond: (user_id = 7)
Planning Time: 0.110 ms
Execution Time: 0.071 ms
```

| 计划节点 | 含义 | 需要警惕吗 |
| --- | --- | --- |
| Seq Scan | 全表扫描 | 应结合估算行数与过滤比例判断；小表或读取大量行时可能更合适 |
| Index Scan | 通过索引定位后回表取行 | 正常 |
| Index Only Scan | 可从索引取所需列；仍可能因可见性检查访问堆，查看 Heap Fetches | 结合可见性映射与实测判断 |
| Bitmap Heap Scan | 先用索引收集行位置，再批量读取 | 正常，命中行较多时出现 |

| 计划节点 | 含义 | 需要警惕吗 |
| --- | --- | --- |
| Sort | 额外排序 | 大量数据排序时考虑用索引提供顺序 |
| Nested Loop / Hash Join / Merge J oin | 三种连接算法 | 由优化器选择 |

EXPLAIN 只显示预估计划；EXPLAIN ANALYZE 会真正执行语句并显示实际耗时与行数（对 UPDATE /DELETE 使用时要包在事务里回滚）。预估行数与实际行数相差悬殊，说明统计信息过期，执行 ANALYZE表名; 更新。

## 13.7 事务与并发控制

### 13.7.1 【入门】事务与 ACID

下单需要“扣库存”和“创建订单”两步。如果扣完库存服务器就崩溃了，订单没创建，库存却少了。事务把多个操作变成一个不可分割的整体：
```sql
BEGIN;
UPDATE products SET stock = stock - 2 WHERE id = 1 AND stock >= 2;
INSERT INTO orders (user_id, product_id, quantity, unit_price_cents, total_cents, 
    idempotency_key)
VALUES (7, 1, 2, 19900, 39800, gen_random_uuid());

-- 两步一起生效；出错时执行 ROLLBACK，两步一起撤销
COMMIT;
```

| 特性 | 含义 |
| --- | --- |
| 原子性 Atomicity | 全部成功或全部撤销 |
| 一致性 Consistency | 事务前后所有约束都成立 |
| 隔离性 Isolation | 并发执行的事务互不干扰（程度由隔离级别决定） |
| 持久性 Durability | 依赖 WAL 刷盘、synchronous_commit、硬件与复制配置；不能只因写了 WAL 就承诺零丢失 |

第 2.2.6 节说过：在 Rust 中，事务对象被 drop 而没有提交时会自动回滚--第 14 章会用到这一点。

### 13.7.2 【进阶】隔离级别与 MVCC

PostgreSQL 使用多版本并发控制（MVCC）：更新一行时不是原地修改，而是写入新版本，旧版本保留给仍在读取它的事务。因此读不阻塞写，写不阻塞读。

| 隔离级别 | 每条语句看到的数据 | 可能出现的问题 | 说明 |
| --- | --- | --- | --- |
| Read Committed（默认） | 该语句开始时已提交的数据 | 同一事务中两次读取结果可能不同 | 绝大多数场景足够，配合条件更新使用 |
| Repeatable Read | 从第一条实际查询或修改语句开始建立的事务快照 | 并发修改同一行时报错40001，需要重试 | 报表、需要一致快照的读取 |
| Serializable | 等价于串行执行 | 冲突时报错 40001，需要重试 | 复杂的不变量；需要应用层重试逻辑 |
```text
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- ...
COMMIT;
```

### 13.7.3 【进阶】防超卖：三种写法

错误写法：先查后改
```sql
-- 读到 1
SELECT stock FROM products WHERE id = 1;
-- 应用判断 1 >= 1，于是：
UPDATE products SET stock = 0 WHERE id = 1;
```

两个请求同时读到库存 1，都认为可以购买，都扣减成功--超卖。这就是第 7.6.2 节 check-then-act 竞态的数据库版本。

写法一：条件更新（推荐）
```text
UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
-- 影响行数为 1：成功；为 0：库存不足（或商品不存在）
```

检查与修改在一条语句中原子完成，数据库对这一行加行锁，第二个请求会等待第一个提交，然后重新检查条件--库存已是 0，更新 0 行。这是 RustMall 下单使用的写法（第 14 章）。

写法二：悲观锁 SELECT ... FOR UPDATE
```sql
BEGIN;

-- 锁住这一行，其他事务的 FOR UPDATE 会等待
SELECT stock, price_cents FROM products WHERE id = 1 FOR UPDATE;
-- 应用中执行复杂的判断……
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

适合判断逻辑复杂、无法写进一条 UPDATE 的场景。代价是持锁时间更长。

写法三：乐观锁（版本号）
```sql
-- 读到 version = 5
SELECT stock, version FROM products WHERE id = 1;
UPDATE products SET stock = 9, version = version + 1 WHERE id = 1 AND version = 5;
-- 影响 0 行：被别人改过，重新读取后重试
```

冲突少时性能最好；第 7.7.2 节的 CAS 与第 9.4.3 节的 ETag 是同一个思想。

### 13.7.4 【进阶】SKIP LOCKED：用表做任务队列
```sql
-- 多个工作进程并发领取待发送的消息，互不重复、互不等待
SELECT id, payload FROM outbox
WHERE sent_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
```

SKIP LOCKED 跳过已被其他事务锁定的行。第 29 章的 Outbox 投递就是用它实现多实例安全并发的。

### 13.7.5 【精通】死锁

事务 A 锁住行 1 后等待行 2，事务 B 锁住行 2 后等待行 1。PostgreSQL 会检测到死锁并让其中一个事务失败（错误码 40P01）。预防方法与第 7.6.5 节相同：所有事务按固定顺序加锁（例如一次下单多个商品时，按商品 ID 升序扣库存）；保持事务短小；在应用层对 40P01 和 40001 进行有限次数的重试。

## 13.8 运维与调优

### 13.8.1 【进阶】用户与权限
```text
CREATE ROLE rustmall_app WITH LOGIN PASSWORD '强密码';
GRANT CONNECT ON DATABASE rustmall TO rustmall_app;
GRANT USAGE ON SCHEMA public TO rustmall_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO rustmall_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO 
    rustmall_app;
```

生产环境遵循最小权限原则：应用程序使用只有读写权限的账号；执行迁移（建表、改表）使用另一个账号；超级用户只供数据库管理员使用。这样即使应用被攻破，攻击者也无法删除表。

### 13.8.2 【进阶】连接数与连接池

PostgreSQL 为每个连接创建一个独立的操作系统进程，每个连接占用数 MB 内存，max_connections默认只有 100。10 个服务实例 × 每实例 20 个连接 = 200 个连接，就会超出上限。

应用层：每个服务实例使用连接池，并合理设置上限（第 14 章PgPoolOptions::max_connections）。经验值：连接数大约是数据库 CPU 核数的 2~4 倍时吞吐最好，连接越多反而越慢。

服务实例很多时，在数据库前部署 PgBouncer 做集中的连接池（事务模式），让成百上千个客戶端连接复用几十个真实连接。

### 13.8.3 【进阶】关键配置参数

| 参数 | 作用 | 参考值 |
| --- | --- | --- |
| shared_buffers | 数据库自身的缓存 | 物理内存的 25% |
| effective_cache_size | 告诉优化器操作系统缓存有多大 | 物理内存的 50%~75% |
| work_mem | 每个排序、哈希操作可用的内存 | 4~64 MB（注意会按操作数倍增） |
| max_connections | 最大连接数 | 100~300，配合连接池 |
| statement_timeout | 单条语句最长执行时间 | 按角色或会话设置，如 30s，防止慢查询拖垮数据库 |
| log_min_duration_statement | 记录慢查询 | 如 500ms |

### 13.8.4 【精通】MVCC 的代价与 VACUUM

MVCC 的旧版本行（“死元组”）不会立刻消失，由后台的 autovacuum 进程清理并回收空间。频繁更新的表如果 autovacuum 跟不上，会出现“表膨胀”：表文件越来越大、查询越来越慢。监控pg_stat_user_tables 中的 n_dead_tup ，必要时调整 autovacuum 参数。

在线修改表结构的风险：大多数 ALTER TABLE 需要短暂的排他锁，如果前面有长事务没结束，ALTER会排队，而它后面的所有查询又排在 ALTER 后面--整个表瞬间不可用。生产环境执行迁移前应设置lock_timeout （如 5 秒，拿不到锁就失败重试）；大表加索引使用 CREATE INDEX CONCURRENTLY。

### 13.8.5 【精通】备份、高可用与监控

逻辑备份：pg_dump -Fc rustmall &gt; rustmall.dump ，用 pg_restore 恢复。适合中小数据库与跨版本迁移。

物理备份与时间点恢复（PITR）：基础备份 + 持续归档 WAL，可以恢复到任意时刻（例如误删数据前一秒），工具有 pgBackRest、WAL-G。定期演练恢复，没有验证过的备份等于没有备份。

高可用：主库 + 流复制的只读从库；主库故障时由 Patroni 等工具自动切换。读多写少的场景可以把查询分流到从库（注意复制延迟）。

托管服务：云厂商的托管 PostgreSQL 内置了备份、高可用、监控，团队没有专职 DBA 时强烈推荐。

监控：pg_stat_statements 扩展记录每类 SQL 的调用次数与总耗时，是定位慢查询的第一工具；连接数、复制延迟、磁盘空间、事务 ID 回卷风险是必须告警的指标（第 38 章接入Prometheus）。

### 13.8.6 第 13.6~13.8 节常见错误

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| 40001 | could not serialize access due to concurrent update | Repeatable Read/Serializable 下的并发冲突 | 应用层重试整个事务 |
| 40P01 | deadlock detected | 死锁 | 固定加锁顺序；重试 |
| 53300 | too many clients already | 连接数超过 max_connections | 减小连接池上限；使用 PgBouncer |
| 57014 | canceling statement due to statement timeout | 语句超时 | 优化查询或索引；调整超时 |
| 55P03 | lock not available /canceling statement due to lock timeout | 拿不到锁 | 找出长事务；稍后重试 |
| 25P02 | current transaction is aborted, commands ignored until end of transaction block | 事务中某条语句失败后继续执行其他语句 | 先 ROLLBACK 再重新开始 |
| 查询很慢 | - | 缺索引、统计信息过期、返回行太多 | EXPLAIN ANALYZE 分析 |

### 13.9.3 第 1 步：开发数据库脚本

文件：rustmall/scripts/dev-db.sh （新建）
```bash
#!/usr/bin/env bash
# 启动（或重新启动）开发用的 PostgreSQL 容器。
# 用法：./scripts/dev-db.sh
set -euo pipefail

NAME=rustmall-pg
VOLUME=rustmall-pgdata
IMAGE=postgres:17

docker volume create "$VOLUME" > /dev/null

if docker ps -a --format '{{.Names}}' | grep -qx "$NAME"; then
    docker start "$NAME" > /dev/null
    echo "已启动已有容器 $NAME"
else
    docker run -d --name "$NAME" \
        -p 5432:5432 \
        -e POSTGRES_USER=rustmall \
        -e POSTGRES_PASSWORD=rustmall \
        -e POSTGRES_DB=rustmall \
        -v "$VOLUME":/var/lib/postgresql/data \
        "$IMAGE" > /dev/null
    echo "已创建并启动容器 $NAME"
fi

# 等待数据库可以接受连接（最多 30 秒）
for _ in $(seq 1 30); do
    if docker exec "$NAME" pg_isready -U rustmall > /dev/null 2>&1; then
        echo "PostgreSQL 已就绪：postgres://rustmall:rustmall@localhost:5432/rustmall"
        exit 0
    fi
    sleep 1
done
echo "等待 PostgreSQL 启动超时" >&2
exit 1
```

逐行说明：

set -euo pipefail ：任何命令失败（-e ）、使用未定义变量（-u ）、管道中任一环节失败（pipefail ）都立即退出，这是编写可靠 Shell 脚本的第一行。

容器已存在就 start ，不存在才 run ：脚本可以反复执行，这种性质称为幂等（第 9.3.1 节）。

pg_isready ：PostgreSQL 自带的就绪检查工具。容器启动后数据库还需要几秒初始化，紧接着执行 SQL 会失败，所以要等待。第 21 章的 Compose 健康检查、第 23 章的 Kubernetes 就绪探针用的是同一个思想。

执行前需要赋予执行权限：chmod +x scripts/dev-db.sh 。Windows 用户在 Git Bash 或 WSL中执行。

### 13.9.4 第 2 步：建表脚本

文件：rustmall/db/schema.sql （新建）
```sql
-- RustMall 单体阶段的数据库结构。
-- 第 14 章起作为 sqlx 迁移文件 monolith/migrations/0001_init.sql 由程序执行。

-- 模糊搜索扩展（商品名搜索，见 13.6.3 节）
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- ---------------------------------------------------------------- 用户
CREATE TABLE users (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username      TEXT        NOT NULL UNIQUE
                              CHECK (char_length(username) BETWEEN 3 AND 20),
    password_hash TEXT        NOT NULL,
    role          TEXT        NOT NULL DEFAULT 'user'
                              CHECK (role IN ('user', 'admin')),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- ---------------------------------------------------------------- 商品
CREATE TABLE products (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name        TEXT        NOT NULL CHECK (char_length(name) BETWEEN 1 AND 100),
    price_cents BIGINT      NOT NULL CHECK (price_cents >= 0),
    stock       INTEGER     NOT NULL CHECK (stock >= 0),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 商品列表按创建时间倒序分页（13.5.5 节）
CREATE INDEX products_created_at_id_idx ON products (created_at DESC, id DESC);
-- 商品名模糊搜索
CREATE INDEX products_name_trgm_idx ON products USING gin (name gin_trgm_ops);

-- ---------------------------------------------------------------- 购物车
CREATE TABLE cart_items (
    user_id    BIGINT      NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    product_id BIGINT      NOT NULL REFERENCES products (id) ON DELETE CASCADE,
    quantity   INTEGER     NOT NULL CHECK (quantity BETWEEN 1 AND 99),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, product_id)
);

-- ---------------------------------------------------------------- 订单
CREATE TABLE orders (
    id               BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id          BIGINT      NOT NULL REFERENCES users (id),
    product_id       BIGINT      NOT NULL REFERENCES products (id),
    quantity         INTEGER     NOT NULL CHECK (quantity BETWEEN 1 AND 99),
    unit_price_cents BIGINT      NOT NULL CHECK (unit_price_cents >= 0),
    total_cents      BIGINT      NOT NULL,
    status           TEXT        NOT NULL DEFAULT 'pending'
                                 CHECK (status IN ('pending', 'paid', 'shipped', 'completed', 'cancelled')),
    paid_at          TIMESTAMPTZ,
    tracking_no      TEXT,
    cancel_reason    TEXT,
    idempotency_key  UUID        NOT NULL,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT orders_total_matches CHECK (total_cents = unit_price_cents * quantity),
    CONSTRAINT orders_tracking_by_status CHECK ((status IN ('shipped', 'completed')) = 
        (tracking_no IS NOT NULL)),
    CONSTRAINT orders_reason_by_status CHECK ((status = 'cancelled') = (cancel_reason IS NOT 
        NULL)),
    CONSTRAINT orders_paid_at_by_status CHECK (status NOT IN ('paid', 'shipped', 'completed') OR paid_at IS NOT NULL),
    CONSTRAINT orders_idempotency UNIQUE (user_id, idempotency_key)
);

-- “我的订单”按时间倒序分页
CREATE INDEX orders_user_created_idx ON orders (user_id, created_at DESC, id DESC);
-- 超时未支付订单的扫描只关心 pending（部分索引，13.6.3 节）
CREATE INDEX orders_pending_created_idx ON orders (created_at) WHERE status = 'pending';
-- 外键列不会自动建索引；按商品统计销量、删除商品前检查引用时需要
CREATE INDEX orders_product_idx ON orders (product_id);
```

设计精讲：

布尔等式约束：(status IN ('shipped','completed')) = (tracking_no IS NOT NULL) 读作“状态是已发货或已完成，当且仅当快递单号不为空”。等号两边都是布尔值，相等即“同真同假”，一条约束同时禁止了“已发货却没单号”和“未发货却有单号”两种非法状态--这正是第3.6.2 节OrderState 枚举在数据库中的表达。

蕴含约束：status NOT IN (...) OR paid_at IS NOT NULL 是“如果已支付，则必须有支付时间”的标准写法（A → B 等价于 ¬A ∨ B）。注意这里不用等式：已取消的订单可能支付过（有paid_at），也可能没支付过。

约束命名：CONSTRAINT orders_total_matches ... 给约束起名，违反时错误信息中会出现这个名字，第 14 章可以据此把数据库错误翻译成清晰的业务错误。

订单中冗余存储 unit_price_cents ：商品价格以后会变，订单必须记录下单时的价格快照（与第

6. 8 节购物车的“价格快照”是同一原则）。

订单不级联删除：orders.product_id 使用默认的 NO ACTION ，有订单的商品无法被物理删除。这意味着 API 中的 DELETE /products/{id} 在第 14 章需要改为“下架”（软删除），这是数据库设计反过来影响 API 实现的例子。

idempotency_key 与唯一约束：第 29 章实现幂等下单时，重复请求插入会触发 23505 唯一冲突，据此返回第一次创建的订单。

### 13.9.6 第 4 步：约束验证脚本

文件：rustmall/db/checks.sql （新建）
```sql
-- 逐条验证约束：每条语句都应当失败，并显示注释中的错误。
-- 用 psql 执行时加 -v ON_ERROR_STOP=0，让失败后继续执行下一条。
-- 1. 负价格 → violates check constraint "products_price_cents_check"
INSERT INTO products (name, price_cents, stock) VALUES ('坏商品', -1, 0);

-- 2. 空商品名 → violates check constraint "products_name_check"
INSERT INTO products (name, price_cents, stock) VALUES ('', 100, 0);

-- 3. 购物车数量 100 → violates check constraint "cart_items_quantity_check"
INSERT INTO cart_items (user_id, product_id, quantity) VALUES (2, 1, 100);

-- 4. 总价不等于单价乘数量 → violates check constraint "orders_total_matches"
INSERT INTO orders (user_id, product_id, quantity, unit_price_cents, total_cents, 
    idempotency_key)
VALUES (2, 1, 2, 19900, 100, gen_random_uuid());
-- 5. 已发货却没有快递单号 → violates check constraint "orders_tracking_by_status"
INSERT INTO orders (user_id, product_id, quantity, unit_price_cents, total_cents, status, 
    paid_at, idempotency_key)
VALUES (2, 1, 1, 19900, 19900, 'shipped', now(), gen_random_uuid());

-- 6. 同一用户重复的幂等键 → duplicate key value violates unique constraint "orders_idempotency"
INSERT INTO orders (user_id, product_id, quantity, unit_price_cents, total_cents, 
    idempotency_key)
VALUES (2, 1, 1, 19900, 19900, '00000000-0000-0000-0000-000000000001');
INSERT INTO orders (user_id, product_id, quantity, unit_price_cents, total_cents, 
    idempotency_key)
VALUES (2, 1, 1, 19900, 19900, '00000000-0000-0000-0000-000000000001');

-- 7. 防超卖：库存为 0 的商品（ID 5），条件更新影响 0 行 → 输出 UPDATE 0
UPDATE products SET stock = stock - 1 WHERE id = 5 AND stock >= 1;
```

注意第 6 组中的第一条 INSERT 是合法的、会成功，第二条才失败。gen_random_uuid() 是PostgreSQL 13 起内置的 UUID 生成函数。

### 13.9.10 常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| port is already allocated | 本机 5432 端口已被占用（例如本地安装的 PostgreSQL） | 停止本地服务，或改为 -p 5433:5432并相应修改连接字符串 |
| relation "users" already exists | schema.sql 已经执行过 | 开发阶段删除数据卷重建；第 14 章起由迁移工具记录执行状态 |
| extension "pg_trgm" isnot available | 使用了不带 contrib 扩展的精简PostgreSQL | 使用官方镜像 postgres:17 |
| permission denied 执行dev-db.sh | 没有执行权限 | chmod +x scripts/dev-db.sh |
| password authenticationfailed | 数据卷是用其他密码初始化的 | 删除数据卷重建 |
| seed.sql 报外键错误 | 执行顺序不对 | 先执行 schema.sql |

### 13.9.11 本章小结

关系型数据库用表、行、列组织数据，用主键、外键、约束保证数据正确；PostgreSQL 功能全面、类型严格，是 Rust 后端的首选。

开发环境用 Docker 一条命令启动 PostgreSQL，数据放在命名卷中；连接信息用 URL 描述；psql 的\d 、\x 、\timing 是日常工具。

类型选择：ID 与金额用 BIGINT，时间用 TIMESTAMPTZ，字符串用 TEXT + CHECK；默认所有列NOT NULL；业务不变量写成约束。

RETURNING 返回生成的字段，ON CONFLICT 实现原子的 UPSERT；JOIN、聚合、CTE、窗口函数让数据库完成统计；游标分页在任何深度都高效。

索引用于真实的查询模式：复合索引遵循最左前缀，部分索引、表达式索引、GIN 索引各有用途；EXPLAIN ANALYZE 验证效果。

事务保证多步操作的原子性；MVCC 让读写互不阻塞；防超卖首选条件更新，复杂判断用 FOR UPDATE，低冲突用乐观锁；SKIP LOCKED 实现表队列；固定加锁顺序防死锁。

运维：最小权限、连接池与 PgBouncer、关键参数、autovacuum、在线 DDL 的锁风险、备份与恢复演练、高可用与监控。

RustMall 有了完整的表结构设计：业务不变量被写成数据库约束，并用验证脚本逐条证明。

下一章是第 14 章“SQLx 详解”：在 Rust 中连接 PostgreSQL，学习连接池、查询、类型映射、事务和编译期检查的 SQL，用迁移工具管理表结构，并把 monolith 的商品仓储从内存换成数据库。

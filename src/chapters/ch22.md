# 第 22 章 CI/CD：把一次提交变成有证据的交付

第 19 章让修改进入可审查的历史，第 20 章定义了应用镜像，第 21 章让应用、PostgreSQL 和 Redis 能按同一份配置组合起来。现在还缺一个环节：每次有人修改代码，都由一个干净环境重新执行约定的检查，并把检查结果关联到确切的提交。

本章沿用现有 monolith 与 common，不提前引入微服务目录。我们将编写 GitHub Actions 工作流，区分格式检查、静态分析、普通测试、真实容器测试与镜像运行检查；只有可信 main 分支的 push 才进入镜像发布任务。学完应能读懂一次流水线的执行图，复现失败步骤，识别“没有测试却显示成功”，并说明仓库里的镜像究竟来自哪次提交、经历过哪些验证。

## 22.1 从手工验收到持续集成

### 22.1.1 【入门】持续集成首先是一种协作方式

持续集成通常写作 CI，即 Continuous Integration。团队频繁把小批修改合入共同代码线，每次集成都执行自动检查，尽早发现不同修改之间的不兼容。自动化服务器承担重复动作，但如果大家长期在互不集成的分支开发，最后一天才运行全部检查，仍然会积累很大的集成风险。

例如，甲把商品列表返回字段改名，乙根据旧字段添加缓存。各自的局部测试可能通过，合并后才出现不一致。CI 的作用是缩短发现时间，并保存发现问题所依据的提交与日志；修复仍需要人理解契约。它既不能代替代码审查，也不能从空缺的断言中推导业务正确性。

### 22.1.2 【入门】持续交付与持续部署

持续交付要求软件持续保持可发布状态，经过验证的产物能够按既定流程进入下一环境；实际投产可以保留人工批准。持续部署则进一步自动把满足条件的修改部署到目标运行环境。两者都常缩写为 CD，阅读文档时必须说明采用哪一种含义。

本章完成自动检查与可信分支镜像发布，为持续交付准备产物。把镜像上传仓库不等于用户请求已切换到新服务，也没有自动完成数据库升级、集群滚动发布与回滚。第 23、24 章先解释应用在集群中的运行模型，后面的整套 DevOps 章节再把这些动作接起来。

### 22.1.3 【入门】一次检查必须绑定一次输入

对 RustMall 而言，输入至少包含提交内容、Cargo.lock、Rust 工具链版本、基础镜像与脚本。若只记录“今天测试通过”，明天就无法确定当时是哪份代码、哪个依赖组合。第 19 章的提交标识在这里成为最基本的关联键。

但提交标识也没有包含一切。ubuntu-24.04 托管 runner 的预装软件会更新，postgres:17-bookworm 标签可指向新的补丁镜像，外部包源也可能变化。因此，本章使用固定工具链与锁文件降低漂移，同时把尚未冻结的环境因素列出来。可追踪和逐位可复现相关，却不是同一个承诺。

### 22.1.4 【进阶】每个关卡应该回答一个具体问题

格式关卡回答代码是否符合统一布局；Clippy 回答是否触发选定的静态诊断；单元测试回答特定输入下的局部行为；数据库测试回答 SQL 与事务能否在实际数据库执行；镜像检查回答装入运行镜像的程序是否能启动并提供指定接口。

这些问题不能互相代替。编译通过的查询可能在运行时违反唯一约束；本机可运行的程序可能在镜像里缺少证书；接口返回 200 可能仍然错误计算金额。设计关卡时，先写下希望得到的证据，再选择工具，避免用一个绿色图标涵盖所有层次。

### 22.1.5 【精通】失败得早与验证得完整

越便宜、越确定的检查通常越适合放在前面。一个格式错误不值得等容器下载和十分钟编译后才报告。本章同一质量任务内依次执行格式、Clippy、测试，再让镜像任务依赖质量任务。

这个顺序也有取舍：前面的失败会阻止后面的诊断，第一次修改可能需要来回修复多轮。大型项目可以把相互独立的关卡并行化，换取更多机器与更复杂的结果聚合。这里先采用易读的串行步骤，等能明确每个检查的职责，再决定哪些并行真正节省时间。

### 22.1.6 【精通】绿色检查也可能针对错误的版本

假设某个 PR 在提交 A 时通过，之后又推送 B。审查页面里 A 的成功记录不能证明 B 正确；合并时还可能与新的 main 组合。需要核对检查关联的 SHA、所用事件与最终合入版本，而不是仅搜索最近一次绿色结果。

本章 PR 检查使用 checkout 对当前事件的默认检出行为，通常对应平台为 PR 准备的合并引用；main 的 push 会再检验合入后的实际提交。若仓库另外启用合并队列，还要按平台规则补充对应事件，不能假定现有 pull_request 触发已经覆盖所有队列流程。

## 22.2 先在本地理解成功、失败与测试选择

### 22.2.1 【入门】退出状态是自动化的第一种协议

人在终端里可能看到错误后继续操作，流水线需要机器可读的判断。通常退出状态 0 表示命令按自身约定成功，非零表示失败。关键是“按自身约定”：一个脚本可以漏掉失败，也可以因为没有选中测试而正常退出。

在临时目录创建下面的实验，不修改 RustMall。若机器上尚未装 Rust，先完成前面工具链章节；Windows 可在已配置的 WSL 环境执行。本节命令是 Bash，不适用于直接粘贴进 PowerShell。
```bash
mkdir ci-exit-lab
cd ci-exit-lab
bash -c 'false; echo "后一句仍然执行"'
echo "$?"
bash -e -c 'false; echo "这一句不会执行"'
echo "$?"
```

第一次看到文本且状态为 0，因为最后的 echo 成功；第二次不应看到内部 echo，状态为非零。这里检查的是 Shell 如何传播状态，和 Rust 业务逻辑无关。若你的终端默认遇错退出，请分别开启独立 Bash 执行两组实验。

### 22.2.2 【入门】管道会引入另一个成功假象

很多人为了保存日志写 command | tee result.log。Bash 默认以管道最后一个命令的状态作为管道状态；tee 成功并不能证明前面的检查成功。下面仍在实验目录执行：
```bash
bash -c 'false | tee result.log; echo "status=$?"'
bash -c 'set -o pipefail; false | tee result.log; echo "status=$?"'
```

前者输出 status=0，后者应为非零。set -euo pipefail 将遇错退出、未定义变量检查和管道失败传播组合使用，但不是所有 Shell 上下文的形式化证明。条件语句与清理动作仍需显式处理；尤其不要给必须通过的测试随手补一个 || true。

### 22.2.3 【入门】最小 Rust 测试与空选择

继续在实验目录创建独立 crate。这个 crate 只用标准库，便于观察测试框架本身；它不加入 RustMall workspace，也不需要数据库。
```bash
cargo +1.92.0 new --lib selection
cd selection
```

用下面的完整内容替换 selection/src/lib.rs：
```rust
pub fn line_total(price: u64, quantity: u64) -> Option<u64> {
    price.checked_mul(quantity)
}

#[cfg(test)]
mod tests {
    use super::line_total;

    #[test]
    fn total_is_price_times_quantity() {
        assert_eq!(line_total(1200, 3), Some(3600));
        assert_eq!(line_total(u64::MAX, 2), None);
    }

    #[test]
    #[ignore = "选择行为实验，不是外部服务测试"]
    fn manual_selection_example() {
        assert_eq!(line_total(500, 2), Some(1000));
    }
}
```

这里金额使用最小货币单位的整数，checked_mul 在溢出时返回 None。assert_eq! 比较 Option 的完整结果；它不是只检查函数能否执行。本节借助这个小例子回忆类型与测试断言，后面再连接真实数据库。

### 22.2.4 【进阶】读懂测试数量，而不只看退出状态

在 selection 目录依次运行，观察每段结果中的 passed、ignored 和 filtered out：
```bash
cargo +1.92.0 test
cargo +1.92.0 test spelling_mistake
cargo +1.92.0 test -- --ignored
cargo +1.92.0 test -- --ignored --list
```

第一次通常执行一个普通测试并忽略一个；第二次按名字筛选，可能一个测试也没有运行，却仍成功；第三次执行被忽略的实验；第四次列出选择结果。不同工具链的输出排版可能变化，但“选中了哪些测试”始终是需要检查的事实。

不要把工具链参数放错位置。cargo +1.92.0 test 中的 +1.92.0 由 rustup 选择工具链；若把字符串误放到测试名称位置，就可能意外变成筛选条件。CI 中一行看起来相似的命令，实际含义可以完全不同。

### 22.2.5 【进阶】Cargo 参数与测试程序参数

cargo test --locked -p monolith --test pg_container -- --ignored --test-threads=1 分成两层。双横线前选择锁文件策略、包与测试目标；双横线后交给测试程序，决定只执行 ignored 测试与测试线程数量。

--test pg_container 指向 monolith/tests/pg_container.rs 对应的集成测试目标，不是随便选一个函数名字。目标文件不存在时 Cargo 会失败；文件存在但其中没有 ignored 测试时，命令仍可能成功而没有执行目标行为。本章增加一个测试清单检查，专门防止后者悄悄变绿。

### 22.2.6 【精通】线程数解决不了所有数据库隔离问题

--test-threads=1 可以使同一个测试程序里的测试顺序执行，但不能替代唯一数据标识、独立 schema 或独立数据库。另一个进程、另一个测试目标、后台任务仍可能接触同一实例。

例如两个测试都注册固定邮箱，即使各自内部只有一个线程，先运行的测试留下记录，后运行仍会触发唯一约束。RustMall 测试应沿用前面章节的隔离策略；遇到冲突先检查数据生命周期，不要无限增加重试，把偶然通过误认为修复。

### 22.2.7 【精通】编译测试与执行测试是两份证据

cargo test --no-run 可以提前检查测试目标能否编译，却不会执行断言。Clippy 使用 --all-targets 也会分析更多目标，但同样不能替代运行。文档中的示例由 rustdoc 负责相应测试，和普通集成测试又有不同入口。

因此，本章列出普通测试、真实容器测试与文档测试，并说明默认 cargo test 已经可能运行文档测试，最后的显式 --doc 是为了让该证据在日志里容易定位，代价是重复执行。以后若追求速度，可以重新划分互不重复的目标，但必须保留相同覆盖范围。

## 22.3 GitHub Actions 的执行模型

### 22.3.1 【入门】工作流、任务与步骤

workflow 是保存在 .github/workflows 下的自动化定义；job 是一组在指定 runner 上执行的步骤；step 是一个命令或一个可复用 Action。一个 job 内的步骤通常按顺序运行，能够看到同一任务里前面步骤写入的工作目录文件。

不同 job 通常获得不同机器环境。quality 中编译得到的 target 目录不会因为 image 写了 needs: quality 就自动出现。needs 表示依赖与结果条件；若要传递文件，应明确使用产物机制。本章 image 重新检出同一次事件的代码，用 Dockerfile 构建，不依赖 quality 的本地文件。

### 22.3.2 【入门】runner 是执行程序的机器

runs-on: ubuntu-24.04 选择 GitHub 托管的 Linux runner 系列。它提供操作系统、Shell 与一组预装工具，仍需由工作流明确安装本书要求的 Rust 版本。不能把自己电脑里缓存的依赖、环境变量与文件当成 runner 默认拥有。

本章采用临时托管 runner，不把不可信 PR 放到长期运行、能访问公司内网的自托管机器上。更换 runner 不只是提速选项，还改变网络、权限、残留状态与清理边界；后续自行部署 runner 时需要重新审查这些假设。

### 22.3.3 【入门】事件决定何时开始

pull_request 用于检查提议的修改，push 的 main 过滤用于合入后检查，workflow_dispatch 提供人工触发入口。本章人工触发只做质量检查，因为发布任务另外要求事件必须是 main 的 push。

这意味着“点了手动运行”不等于发布。事件过滤是工作流入口，job 的 if 是任务入口，两层条件应一起阅读。仓库默认分支、权限或 Actions 策略也会影响是否能够触发，不能仅从 YAML 文件存在推断服务器已经执行过。

### 22.3.4 【进阶】uses 与 run 的职责不同

uses 指向一个 Action，例如检出仓库；run 是交给 Shell 的程序文本。完整提交 SHA 固定的是 Action 源码身份；旁边的版本注释只是帮助维护者理解，实际执行依据仍是 SHA。

本章选用已核对的 checkout v6.1.0 提交，使用 Node 24 的 Action 运行环境。托管 runner 应满足其要求；自托管 runner 必须检查自己的 runner 版本与运行环境。未来升级时重新核对官方发布记录、行为变化和提交身份，不能只改注释。

### 22.3.5 【进阶】表达式先求值，Shell 再执行

${{ github.sha }} 属于 Actions 表达式，$REVISION 属于 Shell 变量。把外部文本直接插进 run 程序体，可能让其中的引号、换行或特殊字符变成代码。应先通过 env 传值，再在 Shell 中以双引号引用变量。

例如处理 PR 标题时，用 TITLE 环境变量配合 printf '%s\n' "$TITLE"，而不是把标题拼进一段双引号包围的 echo 源码。环境传值解决代码与数据混合的一类问题；若把值继续交给 eval，仍会重新引入解释执行风险。

### 22.3.6 【进阶】步骤输出适合传少量受控信息

本章镜像检查步骤把 tested_image_id 写入 GITHUB_OUTPUT，后一个步骤通过 steps.smoke.outputs.tested_image_id 读取。输出文件是平台提供的通信通道，不能把它当作任意日志文件，尤其不要把秘密写进去。

脚本先检查本地镜像 ID 的格式，只输出 sha256 后跟 64 个十六进制字符这一种受控单行值。多行任意数据需要另一套分隔协议，本章无需引入。任务间传输出还需要 job outputs 的显式映射；这里所有镜像动作位于同一 job。

### 22.3.7 【精通】并发控制与取消不是业务回滚

同一 PR 快速推送多个提交，旧检查可以取消，让新提交更快得到结果。本章按工作流与引用分组，仅对 pull_request 设置 cancel-in-progress；main push 不主动取消正在运行的旧任务。

取消能结束执行，却不能撤销已经上传的镜像或已经执行的数据库变更。对部署任务，需要另外设计序列化、环境锁和可恢复步骤。concurrency 也不能当成持久有序消息队列，不应依赖它保证所有中间版本都逐一交付。

## 22.4 Rust 质量关卡如何组成证据

### 22.4.1 【入门】把工具链写进仓库

在 RustMall 根目录新增或按本章统一 rust-toolchain.toml：
```toml
[toolchain]
channel = "1.92.0"
profile = "minimal"
components = ["rustfmt", "clippy"]
```

channel 固定到 1.92.0，profile 选择 minimal，再显式加入 rustfmt 与 Clippy。这样开发者在目录内执行 cargo 时使用记录的工具链；CI 再显式安装它，避免依赖预装状态。工具链升级应作为可审查修改，连同诊断变化与依赖兼容一起验证。

### 22.4.2 【入门】Cargo.lock 与 --locked

RustMall 是可运行应用，提交 Cargo.lock，让团队从同一依赖解析结果开始。--locked 要求命令遵守已有锁文件；如果清单变更需要更新锁文件而锁文件没有对应修改，就应当失败，提醒作者补全输入。

锁文件并不代表完全离线。缺少依赖缓存时仍需获取包；它也不会冻结系统链接库和 Docker 基础镜像。因此，下载失败应和依赖解析冲突分开诊断，不要通过删除 Cargo.lock 来“修复网络”，从而引入一批没有审查的新版本。

### 22.4.3 【入门】格式检查不应该在 CI 偷改提交

cargo fmt --all --check 只检查，发现差异就失败。作者在本地运行 cargo fmt --all，审查差异并提交。若流水线悄悄格式化后继续测试，测试的文件就可能不同于仓库提交，审查者也看不到实际变更。

格式失败先按日志定位文件，不需要启动 PostgreSQL 排查。把格式规范自动化的意义，是让审查把精力放到所有权、错误边界和业务行为，而不是把排版讨论重复交给每个人。

### 22.4.4 【进阶】Clippy 与警告策略

cargo clippy --locked --workspace --all-targets --all-features -- -D warnings 中，workspace 扩大到全部工作区包，all-targets 覆盖相关测试与示例等目标，all-features 启用现阶段可同时成立的功能，最后把警告作为失败。

不能为了让命令变绿，在 crate 顶部整体允许所有诊断。先判断警告是否指出真实问题；若有意保留某种写法，在尽量小的范围加说明。未来出现互斥 feature 时，全开会构造无意义组合，届时应改成明确支持的组合矩阵，而不是机械沿用本章参数。

在第一次启用这个严格关卡之前，还要统一前面章节的测试策略。根清单把 clippy::unwrap_used 设为警告，-D warnings 会把它升级为错误；测试里的 unwrap 刻意让错误输入或夹具准备失败时使测试失败，和长期服务中对用户输入直接 unwrap 的风险不同。本章只为测试范围允许这一项诊断，生产目标仍单独接受严格分析，不允许其他警告。

在 common/src/lib.rs 与 monolith/src/lib.rs 的文件最前面、模块文档之前加入：
```rust
#![cfg_attr(test, allow(clippy::unwrap_used))]
```

在以下独立集成测试文件的最前面加入后面的单行属性：common/tests/json_contract.rs、common/tests/properties.rs，以及 monolith/tests/ 下的 products_api.rs、product_repo.rs、auth_api.rs、catalog_queries.rs、api_contract.rs、pg_container.rs、product_cache.rs。这些文件本身就是测试 crate，不会编译成生产服务。
```rust
#![allow(clippy::unwrap_used)]
```

仅在 tests/ 中的 support 子模块不需要重复添加，它继承所属测试 crate 的限定。也可以把测试断言中的 unwrap 逐个改为带具体失败信息的 expect；不要在生产库顶层写无条件 allow，也不要允许整个 clippy 警告集合。第 20 章探针的独立 tests 模块采用相同的局部策略。

### 22.4.5 【进阶】SQLx 的编译阶段与数据库准备

沿用当前代码的 SQLx 使用方式。需要编译期数据库信息的查询宏，和只在运行时执行的动态查询，对 CI 环境的要求不同。如果宏在编译时需要表结构，必须提前准备对应 schema，或使用按 SQLx 官方流程生成并审查的离线元数据。

本章没有凭空增加 cargo sqlx 命令，也没有把“PostgreSQL 已启动”写成“全部宏都能编译”的保证。当前章节检查点若仅在运行时迁移并执行查询，服务容器可供测试使用；以后引入 query! 时，要同步修改这个顺序，并解释元数据如何更新，避免读者遇到未讲解的准备步骤。

### 22.4.6 【进阶】为什么再显式执行 ignored 测试

前面真实 PostgreSQL 和 Redis 测试依赖 Docker，因此用 ignore 避免普通离线开发每次都启动容器。CI 的托管 Linux runner 能提供 Docker 环境，就应把这些测试列成显式步骤，而不是让它们永远停留在 ignored 状态。

先运行 scripts/check-ignored-tests.py，确认 pg_container 与 product_cache 两个目标确实存在被选择的测试；再真正执行 --ignored。清单检查本身只证明测试被选中，没有执行其断言。两步合起来，才减少“测试文件还在，重要用例却被误删”的漏检。

### 22.4.7 【精通】测试数据与生产配置必须分开

CI 服务容器中的 ci_only 是临时测试环境的公开实验口令，不是生产秘密。测试应连接本任务新建的实例，不读取个人生产 DATABASE_URL。真实容器测试还会按前面章节通过 Testcontainers 建立自己的实例与映射端口，不能把服务容器与所有测试实例混为一谈。

若某个测试删除表、清空数据，这种行为必须只发生在明确隔离的测试资源中。把生产连接串存成仓库 Secret 再交给通用 PR 测试，既扩大权限，也让一个测试清理错误变成真实事故。本章不需要任何生产数据库连接。

## 22.5 服务容器、缓存与运行环境

### 22.5.1 【入门】runner 上的程序怎样访问数据库

quality 的 cargo 直接在 runner 上运行，PostgreSQL 位于服务容器中。通过 ports 映射 5432:5432 后，测试访问 127.0.0.1:5432。这与第 21 章 app 容器内部使用 postgres:5432 的地址不同，原因仍然是调用者所在网络不同。

如果以后给整个 job 增加 container，使命令也在作业容器里运行，就需要按平台的容器网络模型访问服务标签。不要把 localhost 口诀背成固定答案；先画“命令运行在哪、数据库运行在哪、经过什么映射”三点图。

### 22.5.2 【入门】健康条件缩短启动竞争

服务容器配置 pg_isready 和检查间隔，使测试尽量在数据库开始接受连接后执行。它降低进程启动阶段的竞争，但不验证应用账号权限、所有迁移和业务 SQL。

出现健康检查超时，先检查镜像获取、启动日志和服务状态；健康成功后应用认证失败，再检查 URL 与权限。给所有失败统一补 sleep 30，只会在环境快时浪费时间，在环境慢时继续失败，还失去可解释的等待条件。

### 22.5.3 【进阶】镜像任务为什么重新启动依赖

quality 和 image 位于不同 runner，质量任务的 PostgreSQL 不会自动跨机器共享。image 使用第 21 章 Compose，再生成一次仅供本次任务使用的凭据，运行数据库、Redis 与最终镜像。

这让镜像检查更接近读者实际用 Compose 启动应用的路径：配置字段、内网地址、证书、文件权限与健康探针都进入验证范围。它仍是单机实验，无法证明未来集群的网络策略、存储和负载均衡已经正确。

### 22.5.4 【进阶】依赖缓存不是交付产物

缓存用于减少重复下载或编译，允许丢失并重建；交付产物用于让下一阶段获取明确构建结果，必须有可追踪身份与保留规则。镜像仓库保存可分发镜像，也不等同于 cargo 缓存。

本章第一版不增加 Actions 缓存，先建立无缓存也正确的基线。以后优化时，可按操作系统、工具链、目标平台和锁文件等维度设计键，并检查命中后是否仍执行必要验证。缓存命中不能被当成测试通过，也不应把包含令牌的目录打包进去。

### 22.5.5 【精通】一次性 runner 与持久 runner 的清理边界

脚本的 down --volumes 会删除本次 CI 项目的实验卷，因此项目名使用运行编号与尝试次数组成；它不适合用来清理读者第 21 章的持久开发数据。脚本要求 CI 与 GITHUB_ACTIONS 环境，避免误把它作为通用本地启动脚本。

这些环境标记只是防误用，不是防攻击的权限系统。真正边界来自临时 runner、无生产凭据、明确项目范围和平台隔离。如果迁移到共享 Docker daemon，固定端口与镜像标签可能冲突，还要重新设计资源唯一性与访问控制。

### 22.5.6 【精通】超时分布在不同层

job 的 timeout-minutes 限制整项任务，Compose 的 wait-timeout 限制其等待服务条件，容器探针有自身截止时间，Python HTTP 检查器又有单次网络操作超时。这些限制不是一回事。

例如 Python 检查器每次操作 timeout=3，并不保证一个缓慢持续传输的响应必在三秒内结束；外层 job 时间上限才提供更粗的兜底。定位超时时先认出是哪一层中止，再决定收集构建耗时、健康状态还是响应行为，不能盲目把所有时间翻倍。

## 22.6 从拉取请求到镜像发布的权限边界

### 22.6.1 【入门】默认只读，从最小需要开始

顶层 permissions 只给 contents: read，满足检出源码。只有 image 任务增加 packages: write，用于向 GitHub 容器镜像仓库写入。GITHUB_TOKEN 是平台为任务提供的令牌，权限受工作流与仓库策略共同约束，不是一个永远拥有完整权限的万能密码。

本章不申请仓库内容写入、管理权限或云账号凭据。以后要部署到云，也应单独设计身份、短期授权和环境审批，而不是为了省事把长期管理员密钥交给全部步骤。

### 22.6.2 【进阶】不可信源码本身能够执行代码

Rust 的 build.rs、依赖构建脚本、测试和 Shell 辅助脚本都可以运行程序。即使工作流 YAML 没变，检出并编译一个 PR 也已经在执行作者控制的内容。

因此，不能因为“只运行 cargo test”就把生产秘密交给外部 PR。fork PR 的平台限制是一层保护，但仍要阅读事件与权限，防止改用高权限事件后又检出不可信分支。代码审查覆盖业务逻辑，也应覆盖构建与脚本变化。

### 22.6.3 【进阶】为什么这里不采用 pull_request_target

pull_request_target 常用于需要基础仓库上下文的自动化，其信任模型不同于普通 PR 检查。若在更高权限上下文中检出并执行外部提交，就可能把可信令牌交给不可信代码。

本章没有给 PR 贴标签或管理评论的需求，直接用 pull_request 做验证即可。不要为了“让 fork 也能拿到 Secret”更换事件。需要管理元数据时，另建不执行 PR 源码的受限流程，并依据官方安全文档重新审核数据流。

### 22.6.4 【进阶】固定 Action 身份与升级责任

完整提交 SHA 比主版本标签更明确地指定 Action 内容，但“固定过一次”不代表永远安全。项目需要定期检查上游修复，审核升级差异并更新 SHA。依赖更新也属于代码审查的一部分。

本章两处 checkout 使用相同已核对提交，persist-credentials: false 避免检出步骤把认证配置留给后续一般 Git 命令。它不消除工作流其余步骤显式获得的令牌；发布步骤仍通过 env 获得自己需要的 GITHUB_TOKEN。

### 22.6.5 【精通】日志是输出通道，也可能泄漏秘密

不要为了排错输出全部环境变量、完整 Compose 渲染结果或包含密码的数据库 URL。自动遮罩不能保证任意转换、分片或编码后的秘密仍被识别。本章配置检查使用 --quiet，清理只列资源状态，不自动打印应用全部日志。

这会减少失败时的现成细节，所以应让应用错误信息按前面日志约定输出有用而不含凭据的上下文。需要日志时明确收集范围并检查脱敏；既不能把“别打印秘密”理解成完全不记录，也不能为方便把所有状态上传为公开产物。

### 22.6.6 【精通】main 的信任还依赖仓库管理

image 只接受 main push，这表示它信任已经进入 main 的代码。若任何人都能绕过审查直接推送，事件判断不会自动补上缺失的治理。仓库应按团队策略保护 main、要求检查与审查，并控制工作流文件的修改权限。

这些设置位于 GitHub 仓库管理界面，提交 YAML 不会自动配置。记录实施情况时，应分别写“文件已编写”“本地验证”“平台执行记录”“分支规则已配置”，避免把期望行为当成已发生事实。

## 22.7 RustMall 实战：按顺序加入文件

### 22.7.1 【入门】本章文件清单与前置条件

从第 21 章完整项目根目录开始，保留 Cargo.toml、Cargo.lock、monolith、common、Dockerfile 与 compose.yaml。先确认普通测试能在原本约定的开发依赖中通过；没有这些文件时，应回到相应章节，不要拿全书最终微服务目录替代当前检查点。

| 文件 | 操作 | 职责 |
| --- | --- | --- |
| rust-toolchain.toml | 新增或统一 | 固定 Rust、格式与静态分析组件 |
| common/src/lib.rs、monolith/src/lib.rs 与列出的集成测试 | 修改 | 仅为测试编译限定 unwrap 诊断策略 |
| scripts/check-ignored-tests.py | 新增 | 检查真实容器测试的选择清单 |
| scripts/ci-image-smoke.sh | 新增 | 临时 runner 上构建、启动、检查与清理 |
| .github/workflows/ci.yml | 新增或整体替换旧实验版 | 事件、任务、权限与发布条件 |
| scripts/create-compose-env.py | 保留第 21 章版本 | 生成隔离实验凭据并拒绝覆盖 |
| scripts/check-ch21-http.py | 保留第 21 章版本 | 检查健康与商品列表只读契约 |

前面的 Git 忽略规则继续排除 compose.dev.env。CI 不会把临时凭据提交到仓库。当前真实容器测试目标名称仍为 pg_container 与 product_cache；未来改名时必须连同清单脚本和工作流一起修改。

### 22.7.2 【进阶】第一步：增加测试选择清单检查器

创建 scripts/check-ignored-tests.py，完整内容如下。在项目根目录执行 python3 scripts/check-ignored-tests.py；需要 Rust 工具链及可获取的依赖，列测试会编译，但不会主动执行 ignored 测试体。
```python
"""拒绝把没有选中任何 ignored 测试的执行计划当作通过。"""
import re
import subprocess
import sys

for target in ["pg_container", "product_cache"]:
    result = subprocess.run(
        ["cargo", "test", "--locked", "-p", "monolith", "--test", target,
         "--", "--ignored", "--list"],
        text=True, capture_output=True, check=False,
    )
    if result.returncode:
        # 编译器原始诊断保留到 CI 日志；不读取或输出环境变量。
        sys.stdout.write(result.stdout)
        sys.stderr.write(result.stderr)
        raise SystemExit(result.returncode)
    tests = [line for line in result.stdout.splitlines()
             if re.fullmatch(r".+: test", line)]
    if not tests:
        print(f"FAIL {target}: 没有选中 ignored 测试", file=sys.stderr)
        raise SystemExit(1)
    print(f"PASS {target}: 已发现 {len(tests)} 个 ignored 测试")
```

subprocess 使用参数列表，避免再经过 Shell 拼接。capture_output 收集命令输出；失败时保留原编译诊断，成功时只报告目标和数量。正则只识别 libtest 列表中的“名称: test”行，匹配到零个就失败。

它有明确适用范围：本书这两个目标使用标准 libtest，不是自定义 harness。如果未来更换测试框架，需要按其输出协议修改检查器。清单数量大于零也不能保证每个业务场景都还存在，关键用例仍应由审查与覆盖清单维护。

### 22.7.3 【进阶】第二步：增加镜像检查与清理脚本

创建 scripts/ci-image-smoke.sh。工作流用 bash 显式执行，因此不依赖文件可执行位。它仅用于一次性托管 runner；本地开发继续使用第 21 章命令。
```bash
#!/usr/bin/env bash
set -euo pipefail

# 这个脚本只用于一次性 GitHub 托管 runner；不用它清理个人开发环境。
[[ "${CI:-}" == true && "${GITHUB_ACTIONS:-}" == true ]] || {
  echo '请在 GitHub Actions 的临时 runner 中执行。' >&2
  exit 2
}
[[ "${GITHUB_RUN_ID:-}" =~ ^[0-9]+$ && "${GITHUB_RUN_ATTEMPT:-}" =~ ^[0-9]+$ ]] || {
  echo '缺少有效的运行编号。' >&2
  exit 2
}
[[ -n "${GITHUB_OUTPUT:-}" ]] || { echo '缺少步骤输出文件。' >&2; exit 2; }
project="rustmall-ci-${GITHUB_RUN_ID}-${GITHUB_RUN_ATTEMPT}"
compose=(docker compose -p "$project" --env-file compose.dev.env)

# 生成失败时不接管已有文件，也不对已有项目执行清理。
python3 scripts/create-compose-env.py
cleanup() {
  local result=$?
  trap - EXIT
  "${compose[@]}" ps --all || true
  if ! "${compose[@]}" down --volumes --remove-orphans; then
    echo '临时 Compose 资源清理失败。' >&2
    if [[ "$result" == 0 ]]; then result=1; fi
  fi
  if ! rm -f compose.dev.env; then
    echo '临时凭据文件清理失败。' >&2
    if [[ "$result" == 0 ]]; then result=1; fi
  fi
  exit "$result"
}
trap cleanup EXIT

"${compose[@]}" config --quiet
"${compose[@]}" up -d --wait --wait-timeout 90 postgres redis
"${compose[@]}" build app
tested_id=$(docker image inspect rustmall-monolith:ch21 --format '{{.Id}}')
[[ "$tested_id" =~ ^sha256:[0-9a-f]{64}$ ]]
"${compose[@]}" up -d --no-deps --no-build --pull never --wait --wait-timeout 90 app
container_id=$("${compose[@]}" ps -q app)
[[ -n "$container_id" ]]
running_id=$(docker inspect "$container_id" --format '{{.Image}}')
[[ "$running_id" == "$tested_id" ]]
python3 scripts/check-ch21-http.py --base http://127.0.0.1:58080
printf 'tested_image_id=%s\n' "$tested_id" >> "$GITHUB_OUTPUT"
```

脚本先验证环境与运行编号，再调用凭据生成器。生成成功后才安装退出清理函数；如果目录已有 compose.dev.env，生成器拒绝覆盖，脚本直接退出，不接管已有文件和资源。

compose 是 Bash 数组，固定项目名与 env 文件，后面每次调用都通过同一个数组展开。这样既保持参数边界，也降低某个清理命令忘记 -p、误操作另一项目的风险。

### 22.7.4 【精通】清理函数如何保留原始失败

进入 cleanup 的第一句 local result=$? 保存触发退出的状态，再解除 EXIT trap，避免清理退出时重复调用。ps 仅辅助观察，失败不覆盖主结果；down 失败时报告清理问题，如果原本成功，则把最终结果改为失败。

如果业务检查已经失败，后面的成功清理不能把它洗成绿色。反过来，清理失败也不应该使脚本无声地遗留资源。rm 只删除本次生成的凭据文件，down --volumes 的范围由前面独有的 CI 项目名约束。外部强制终止进程时 trap 不一定有机会执行，所以这里还依赖临时 runner 的回收边界。

### 22.7.5 【精通】只构建一次，检查运行中的确切镜像

脚本先启动依赖，再 build app。构建后读取本地镜像 ID，随后使用 --no-build --pull never 启动 app，避免验证期间悄悄重建或从仓库取得另一镜像。再比较容器的 Image 字段与刚刚记录的 ID，确认检查对象一致。

HTTP 检查通过后，只把这个受控 ID 输出给下一步骤。镜像仍留在同一 runner 的本地存储中，down 只清理实验运行资源；发布步骤给该 ID 加远端标签并 push。这里没有第二次 docker build，也没有仅凭可变标签猜测“应该还是同一个”。

### 22.7.6 【进阶】第三步：创建完整工作流

创建 .github/workflows/ci.yml，完整内容如下。注意 jobs 下 quality 与 image 缩进相同；image 是第二个任务，不是 quality 的某个步骤。
```yaml
name: RustMall CI

  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

  contents: read

  group: rustmall-${{ github.workflow }}-${{ github.ref }}

      postgres:

          POSTGRES_DB: rustmall
          POSTGRES_PASSWORD: ci_only
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U rustmall -d rustmall"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 12
    env:
      DATABASE_URL: postgres://rustmall:ci_only@127.0.0.1:5432/rustmall
      CARGO_TERM_COLOR: always
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6.1.0
        with:
          persist-credentials: false
      - name: Install recorded toolchain
        run: rustup toolchain install 1.92.0 --profile minimal --component rustfmt --component clippy
      - name: Format
        run: cargo fmt --all --check
      - name: Clippy
        run: cargo clippy --locked --workspace --all-targets --all-features -- -D warnings
      - name: Unit and database tests
        run: cargo test --locked --workspace -- --test-threads=2
      - name: Confirm ignored test inventory
        run: python3 scripts/check-ignored-tests.py
      - name: Real PostgreSQL container test
        run: cargo test --locked -p monolith --test pg_container -- --ignored --test-threads=1
      - name: Real Redis container tests
        run: cargo test --locked -p monolith --test product_cache -- --ignored --test-threads=1
      - name: Documentation tests
        run: cargo test --locked --workspace --doc
  image:
    name: image
    needs: quality
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    timeout-minutes: 40
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803 # v6.1.0
        with:
          persist-credentials: false
      - name: Build once and check the running image
        id: smoke
        shell: bash
        run: bash scripts/ci-image-smoke.sh
      - name: Publish the checked image
        shell: bash
        env:
          REGISTRY_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          REGISTRY_ACTOR: ${{ github.actor }}
          REPOSITORY: ${{ github.repository }}
          REVISION: ${{ github.sha }}
          TESTED_IMAGE_ID: ${{ steps.smoke.outputs.tested_image_id }}
        run: |
          set -euo pipefail
          trap 'docker logout ghcr.io >/dev/null 2>&1 || true' EXIT
          image="ghcr.io/${REPOSITORY,,}/monolith:${REVISION}"
          printf '%s' "$REGISTRY_TOKEN" | docker login ghcr.io -u "$REGISTRY_ACTOR" --password-stdin
          docker tag "$TESTED_IMAGE_ID" "$image"
          docker push "$image"
          printf 'Published `%s` from local image `%s`. Record the registry digest from the push log.\n' "$image" "$TESTED_IMAGE_ID" >> "$GITHUB_STEP_SUMMARY"
```

顶层定义入口、默认权限与并发策略；quality 配置自己的数据库、环境与顺序检查；image 通过 needs 依赖质量任务，再通过 if 限制可信发布入口。image 的两个步骤共享同一个 runner，因此可以用前一步得到的本地镜像 ID。

不要把书中排版的换行符、行号或解释文字复制进 YAML。安装工具链命令中的 --component clippy 是两个参数；少一个空格就会变成无效选项。配置文件的机器解析与文字校对必须同时做，肉眼看起来相似不代表含义相同。

### 22.7.7 【精通】发布步骤中的五个数据流

REGISTRY_TOKEN 只用于仓库登录，REGISTRY_ACTOR 指定登录身份，REPOSITORY 用于构造小写的仓库路径，REVISION 来自本次提交，TESTED_IMAGE_ID 来自已成功检查的步骤。它们通过 env 进入 Shell，使用时保留引号。

密码从标准输入交给 docker login，不出现在命令行参数里；退出时尝试 logout。docker tag 以 ID 为源，docker push 上传这个标签。仓库的包创建、关联仓库与写入策略仍可能拒绝操作，出现 403 时先查权限与包关系，不要立即申请更大令牌。

### 22.7.8 【精通】提交标签、镜像 ID 与仓库摘要

本地镜像 ID 标识本地镜像配置，提交 SHA 标识源码历史，仓库 manifest digest 标识远端分发对象，三者不是同一个哈希。本章使用提交 SHA 作为远端 tag 便于追踪，但 tag 本身仍是可变引用。

发布日志中的 digest 才适合在后续部署中形成更精确的镜像引用。应保存提交、工作流运行、目标平台、标签和仓库摘要之间的关系。不能把本地 sha256 ID 直接写成 ghcr.io/...@sha256:... 并假定可拉取，也不能把一个 SHA 标签当成已完成签名与来源证明。

### 22.7.9 【入门】第四步：提交与首次运行

在项目根目录先检查文件差异，确认没有凭据，然后按第 19 章流程提交并建立 PR。推送命令使用你已经配置的仓库与分支，本书不编造远端地址。平台 Actions 页面应出现 RustMall CI，PR 上应关联对应检查。

首次运行可能需要下载 Rust、依赖和容器镜像。先阅读实际失败的步骤：若工作流根本未启动，检查事件、分支与仓库策略；若已经启动，进入相应 job 查看日志。不要把“页面暂时没有结果”自动解释为代码测试失败。

### 22.7.10 【进阶】章节末目录与验收顺序

本章新增部分合入后，关键目录如下。省略号仅表示前面已经存在的业务文件，不是待补代码；这份树用于定位本章文件，不替代完整项目。

## 22.8 故障实验：让失败按预期被发现

### 22.8.1 【入门】故意制造格式差异

在自己的练习分支中，把一个简单表达式的空格改乱，先运行 cargo fmt --all --check，确认失败；再运行 cargo fmt --all 并查看差异。不要同时修改业务，才能明确这次失败来自格式。

将练习提交推到 PR 后，预期质量任务停在 Format，后续步骤没有作为成功证据出现。恢复后再次运行。这个实验让你认清流水线是按顺序执行的程序，而不是一次触发就自动验证过所有事项。

### 22.8.2 【进阶】让断言失败，再恢复

在练习分支临时把一个已有纯函数测试的预期值改错，先在本地确认失败，再观察 CI 对应步骤的非零状态。修复后核对新提交的结果，而不是盯着旧运行页面。

不要用删除测试、加 ignore 或把断言变成打印来“修复”。失败告诉你观察到了不符合预期的行为；下一步要区分实现错误、预期错误与测试环境错误。只有解释了差异来源，新的绿色结果才有意义。

### 22.8.3 【进阶】删除 ignored 选择，观察清单保护

在临时副本中移除 pg_container 目标内所有 ignore 标记，然后运行清单检查器。预期脚本报告该目标没有选中 ignored 测试并返回非零。直接执行 --ignored 则可能没有测试运行却成功，这正是保护要捕捉的差异。

实验后恢复文件。这里不是说 ignore 永远不能移除；如果团队决定把这些用例改成普通测试，应该同时重构执行计划与清单检查，保证真实服务场景仍在正确阶段运行，而不是留下一个空壳步骤。

### 22.8.4 【精通】令镜像运行检查失败

在隔离练习分支，把 app 的数据库地址改成一个不存在的服务名，再观察 Compose 等待和应用准备状态。预期镜像检查任务失败，发布步骤不会运行，清理仍尝试执行。恢复后再核对正常路径。

这个实验和质量测试失败不同：代码可能编译且局部测试通过，错误发生在运行配置与网络路径。修复时应对照第 21 章拓扑，不要通过让 /health/ready 无条件返回 200 绕过关卡。那会把可见故障改成更危险的假成功。

### 22.8.5 【精通】验证发布对象没有被重建

阅读正常 image 日志，应只出现一条 app 构建路径，记录的 tested_image_id 与运行容器 Image 相等，后面以该 ID 进行 tag 和 push。若在发布前额外增加 docker build，前面的 HTTP 结果就不能证明新构建对象。

可以在脚本测试中替换 Docker 命令，令镜像 ID 与容器 Image 不同，预期脚本在 HTTP 检查与输出之前失败。替身只验证脚本控制流，不证明真实镜像可以运行；真实运行证据仍需来自实际 Docker 与应用检查。

### 22.8.6 【精通】区分重试构建与恢复部署

外部注册表临时不可达，可以在有边界的策略下重试获取或推送；一个业务断言失败不应该自动重试到偶然成功。即使对同一次提交重新构建，基础镜像标签更新也可能产生不同结果，所以重跑记录需要保留运行尝试与产物身份。

本章没有部署生产服务，不讨论“失败后自动回滚”作为既有能力。后续需要把程序版本、配置、schema 与数据副作用放进同一个恢复分析，才能判断回滚容器是否足够。

## 22.9 故障定位：先找证据所在层

### 22.9.1 【入门】从最早失败步骤开始

任务末尾的红色只说明整体失败。先找到第一个本应成功却失败的步骤，再看其原始诊断；后续的“没有输出”通常是依赖失败后的结果，不是另一个独立错误。

| 现象 | 先收集的证据 | 可能原因与修复方向 |
| --- | --- | --- |
| 工作流完全不出现 | 事件类型、分支、文件位置、仓库 Actions 策略 | 核对触发条件与 .github/workflows 路径 |
| Format 失败 | 格式差异与工具链版本 | 本地按记录版本格式化并提交 |
| Clippy 突然出现新诊断 | 实际 Rust 版本、依赖与命令 | 排除工具链漂移，再修复或局部说明 |
| 数据库连接拒绝 | 服务容器状态、调用者位置、映射端口 | 区分数据库未就绪与地址错误 |
| 认证失败 | 账号、数据库名与脱敏后的 URL 结构 | 核对测试变量，避免输出密码 |
| ignored 步骤零用例 | --list 输出、目标文件、ignore 标记 | 修正执行计划，不能只保留空步骤 |
| 镜像健康超时 | 构建是否完成、容器状态、准备接口 | 检查配置、迁移、文件权限与网络 |
| push 返回 403 | 任务权限、包归属与仓库关系 | 按最小需要修正授权与关联 |
| 清理后任务变绿 | trap 是否保存原状态 | 修正控制流，重新做失败路径实验 |

表中“可能原因”不是最终诊断。先用证据缩小范围，再修改输入；一次改动数据库地址、密码、超时和镜像版本，会让偶然恢复难以解释，也妨碍以后复现。

### 22.9.2 【进阶】本地通过，Linux CI 编译失败

先比较工具链、大小写敏感路径、锁文件与系统依赖。macOS 文件系统上的错误大小写引用，可能到 Linux 才暴露；本机已安装的系统库，也可能不在 runner 或构建镜像里。

把缺失依赖写进对应环境的构建步骤，而不是要求每位同学凭记忆安装。若本机使用更新的 Rust 语法，而本书记录的是 1.92.0，应决定统一升级还是保持当前基线；不要让两种版本继续无声分叉。

### 22.9.3 【进阶】数据库测试有时通过、有时失败

收集失败用例名、唯一约束信息、测试并发与数据库清理时点。固定邮箱、共享表清空、后台任务未停止，都可能导致竞争。先在隔离实例中重复目标测试，确认是数据相互影响还是程序真实并发错误。

把线程数从二改成一可以作为诊断手段，却不应掩盖缺少隔离。若业务事务本身存在竞态，串行测试反而让问题暂时消失；这种情况应增加明确的并发用例，而不是只寻求一次通过。

### 22.9.4 【精通】拿到镜像却无法证明来源

先找仓库 tag 对应的远端 digest，再找发布运行、提交 SHA、目标平台与检查步骤。如果只有别人手动推上的 latest，现有信息不足以重建证据链。不要补写一段“应该来自 main”的说明替代记录。

本章建立基础关联，尚未生成签名、软件物料清单或经过验证的构建证明。后续完善供应链时，应在既有身份链上增加可验证声明与部署验证策略，而不是只增加几个听起来安全的文件名。

### 22.9.5 【精通】如何记录本次验证范围

记录时分四栏：检查对象、执行环境、实际动作、没有覆盖的部分。例如“本地替身检查脚本在 HTTP 失败后不输出镜像 ID，并保留非零状态”，不能简写成“镜像交付全部通过”。

同理，YAML 能解析不代表平台接受所有上下文，平台接受不代表测试执行，测试执行不代表生产发布成功。书稿修订记录应把这些事实分开，读者的项目验收也应沿用同样的方法。

## 22.10 分层练习、参考答案与下一章

### 22.10.1 【入门练习】解释四种绿色结果

题目：格式检查成功、cargo test 不存在的名称成功、镜像启动成功、生产订单成功，分别说明了什么？哪几项不能互相推出？

参考答案：格式成功仅覆盖布局约定；名称筛选为空可能未执行任何测试；镜像启动只证明进程在该环境启动，尚需准备状态与业务断言；订单成功还依赖特定业务输入、数据库与外部路径。四种结果属于不同观察范围，不能靠排在同一张页面就视为等价。

### 22.10.2 【操作练习】补齐测试清单的反例

题目：在临时副本验证“编译失败”“目标存在但零个 ignored 测试”“存在 ignored 测试”三种结果，记录清单检查器退出状态。不要连接生产数据库。

评分要点：编译失败保留非零和原诊断；零选择也非零；有测试时清单检查成功，但需要再执行测试体才算验证行为。若只展示成功截图，没有两种反例，则尚未证明保护逻辑有效。

### 22.10.3 【推理练习】两个任务为什么不能共享 target

题目：quality 已完成编译，image 写了 needs: quality，为什么仍然需要重新构建？如果要避免重复，有哪些额外条件？

参考答案：needs 不搬运文件，不同 job 默认不共享本地工作区。复用必须显式传递产物并核对平台、链接环境、工具链与构建参数。直接把 runner 上的动态链接程序拷进另一个运行镜像，还可能发生第 20 章讲过的 ABI 问题，因此不能仅按“省一次编译”决定方案。

### 22.10.4 【推理练习】检查后重建一次有什么问题

题目：先构建镜像 A 并检查通过，发布步骤又从同一提交构建 B。是否可以说 B 已通过前面的 HTTP 检查？

参考答案：不能。源码相同不保证所有构建输入与输出相同；基础标签、获取资源和构建环境可能变化。应发布经过检查的同一产物，并记录其身份；若有意重新构建，需要对 B 再建立对应验证与来源关系。

### 22.10.5 【扩展练习】设计缓存但保持无缓存可用

题目：为依赖下载引入缓存，说明键包含哪些因素、哪些路径不能缓存、未命中时怎么办，以及缓存命中后仍执行什么检查。

参考要点：至少考虑平台、工具链与锁文件，避免缓存凭据和运行数据；缓存丢失时正常重新获取并构建，不改变程序正确性；命中后仍执行格式、静态分析与行为测试。完整答案还应讨论外部 PR 的缓存信任边界，而不是只追求更高命中率。

### 22.10.6 【精通练习】审查一个危险的 PR 发布设计

题目：有人建议用 pull_request_target，检出外部 PR 分支，执行 cargo test，最后用有写权限的令牌发布镜像。请画出令牌与代码的流向，提出替代设计。

参考答案：外部代码可以在构建脚本与测试中运行，获得高权限环境后存在滥用风险。普通 PR 使用无发布权限的验证；可信 main push 才构建与发布。若需要 PR 元数据管理，将不执行外部源码的管理动作隔离，并避免把未验证产物直接提升为可信发布对象。

### 22.10.7 【小结】本章已经建立的能力

现在 RustMall 有了明确的工具链、可解释的质量关卡、真实容器测试入口、空选择保护，以及按同一镜像 ID 运行检查再发布的路径。各层结果都能关联到提交与任务，失败也有相应的定位步骤。

它尚未完成生产部署、迁移编排、来源签名验证、灾备演练和多服务交付。下一章进入 Kubernetes，先理解声明式对象、Pod 生命周期、Service 与健康探针，再把本章产生的镜像放进清晰的运行模型。业务拆分仍在后续章节逐步发生，保证读者可以沿着同一工程继续前进。

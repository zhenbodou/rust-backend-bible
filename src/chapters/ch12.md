# 第 12 章 Axum 详解

Axum 是 Tokio 官方团队维护的 Web 框架，建立在 hyper（HTTP 实现）和 Tower（中间件抽象）之上，是目前 Rust 后端最主流的选择。它的设计哲学是“没有魔法”：处理函数就是普通的 async 函数，参数的类型决定从请求中提取什么，返回值的类型决定响应长什么样。本章系统讲解路由、提取器、响应、状态、中间件与测试，项目部分在 monolith 中实现第 9 章 API 文档中的商品接口（暂时使用内存仓储）。

版本说明：本章基于 Axum 0.8。与 0.7 相比，最明显的变化是路径参数写法从 /:id 改为/{id}，以及自定义提取器不再需要 #[async_trait] 。网上大量旧教程仍是 0.7 写法，对照时请注意。

## 12.1 Axum 的架构

### 12.1.1 【入门】四个核心概念

| 概念 | 是什么 | 类比 |
| --- | --- | --- |
| Router | 路由表：哪个方法 + 路径交给哪个处理函数 | 大楼导览图 |
| Handler（处理函数） | 处理一类请求的 async 函数 | 各个办事窗口 |
| Extractor（提取器） | 从请求中取出数据的类型，作为处理函数的参数 | 窗口前审核材料的工作人员 |
| IntoResponse | 能转换为 HTTP 响应的类型，作为处理函数的返回值 | 办理结果的回执 |

此外还有两个支撑概念：State（所有请求共享的依赖，如连接池）和 Layer / 中间件（包裹在处理函数外层的通用逻辑，如跨域、日志、超时）。

### 12.1.2 【进阶】分层的生态

| 层 | crate | 职责 |
| --- | --- | --- |
| 框架 | axum | 路由、提取器、响应、状态 |
| 中间件抽象 | tower | Service 与 Layer trait，与 HTTP 无关 |
| HTTP 中间件 | tower-http | 跨域、追踪、压缩、超时、请求 ID、请求体限制…… |
| HTTP 协议 | hyper | HTTP/1.1 与 HTTP/2 的解析和连接管理 |
| HTTP 类型 | http | Request 、Response 、StatusCode 、HeaderMap 等公共类型 |
| 异步运行时 | tokio | 网络 I/O 与任务调度（第 11 章） |

因为中间件层是通用的 Tower，同一个中间件（限流、超时、追踪）可以同时用于 Axum 的 HTTP 服务、Tonic 的 gRPC 服务（第 25 章）和 reqwest 以外的 HTTP 客戶端--这是 Axum 相比其他框架最大的生态优势。

### 12.1.3 【进阶】与其他框架的对比

| 框架 | 特点 | 适合 |
| --- | --- | --- |
| Axum | 与 Tokio / Tower 生态无缝结合，提取器设计优雅，社区最活跃 | 绝大多数新项目（本书选择） |
| Actix-web | 老牌、性能极强、生态成熟，有自己的运行时封装与中间件体系 | 已有 Actix 生态的项目 |
| Rocket | 宏驱动、开发体验好 | 快速原型 |
| Poem /Salvo | 功能丰富，内置 OpenAPI 等 | 希望“开箱即用”的团队 |

## 12.2 第一个 Axum 服务

### 12.2.1 【入门】Hello World
```toml
[dependencies]
axum = "0.8"
tokio = { version = "1", features = ["macros", "rt-multi-thread", "net"] }
```
```rust
use axum::{routing::get, Router};

async fn hello() -> &'static str {
    "你好，RustMall"
}

#[tokio::main]
async fn main() -> std::io::Result<()> {
    // 1. 建路由表
    let app = Router::new().route("/", get(hello));

    // 2. 绑定端口
    let listener = tokio::net::TcpListener::bind("0.0.0.0:8080").await?;
    println!("监听 http://localhost:8080");

    // 3. 启动服务
    axum::serve(listener, app).await
}
```

运行后执行 curl http://localhost:8080/ ，得到“你好，RustMall”。三个步骤就是所有 Axum 服务的骨架：

1. Router::new().route(路径, 方法(处理函数)) 注册路由。

2. TcpListener::bind 绑定地址。0.0.0.0 表示接受所有网卡的连接，放进容器后必须这样写（第

9. 1.2 节）。端口被占用时这里会返回错误 Address already in use 。

3. axum::serve 为每个连接 spawn 一个任务，永不返回（除非出错或优雅停机，12.8.3 节）。

## 12.3 路由

### 12.3.1 【入门】方法路由与路径参数
```rust
use axum::routing::{get, post};
use axum::Router;

let app = Router::new()
    // 同一路径的多个方法链式注册
    .route("/products", get(list_products).post(create_product))
    .route("/products/{id}", get(get_product).put(update_product).delete(delete_product))
    .route("/orders/{id}/cancel", post(cancel_order))
    // 通配：匹配剩余的所有路径段
    .route("/files/{*path}", get(serve_file));
```

{id} 匹配一个路径段，由 Path 提取器取出（12.4 节）。

路径存在但方法不对时，Axum 自动返回 405 Method Not Allowed；路径不存在时返回 404。

同一个路径注册两次会在启动时 panic（overlapping route），这是好事：路由冲突在启动时就暴露，而不是在线上请求时。

### 12.3.2 【进阶】嵌套、合并与兜底
```rust
fn product_routes() -> Router<AppState> {
    Router::new()
        .route("/", get(list_products).post(create_product))
        .route("/{id}", get(get_product))
}

fn order_routes() -> Router<AppState> { Router::new() /* ... */ }

let app = Router::new()
    // 前缀挂载：/api/v1/products/{id}
    .nest("/api/v1/products", product_routes())
    // 合并两个路由表
    .merge(health_routes())
    // 所有未匹配的请求
    .fallback(not_found)
    .with_state(state);
```

按业务模块拆分路由函数，是中大型项目的标准组织方式。Router&lt;AppState&gt; 中的类型参数表示“这个路由还缺少一个 AppState”；调用 with_state 提供状态后，类型变成 Router&lt;()&gt; ，才能交给axum::serve 。

nest("/x", r) 与尾部斜杠：Axum 0.8 中，嵌套路由里的 "/" 对应 /api/v1/products ，不匹配/api/v1/products/ 。本书的 API 统一不使用尾部斜杠。

## 12.4 提取器

### 12.4.1 【入门】常用提取器
```rust
use axum::extract::{Path, Query, State, Json};
use axum::http::HeaderMap;
use serde::Deserialize;

#[derive(Deserialize)]
struct ListQuery { page: Option<u32>, page_size: Option<u32>, q: Option<String> }

#[derive(Deserialize)]
struct CreateProduct { name: String, price_cents: i64, stock: i32 }

// GET /products/42            → Path
async fn get_product(Path(id): Path<i64>) -> String { format!("商品 {id}") }

// GET /products?page=2&q=键盘 → Query：用 serde 反序列化查询字符串（第 10.7.1节）
async fn list_products(Query(q): Query<ListQuery>) -> String { format!("第 {:?} 页", q.page) }

// POST /products，JSON 正文   → Json
async fn create_product(Json(body): Json<CreateProduct>) -> String { format!
("创建 {}", body.name) }

// 任意请求头               → HeaderMap
async fn show_agent(headers: HeaderMap) -> String {
    headers.get("user-agent").and_then(|v| v.to_str().ok()).unwrap_or("未知").to_string()
}
```

参数写法 Path(id): Path&lt;i64&gt; 是第 3.5 节的模式解构：Path 是一个元组结构体，直接把内部值解构到 id 。

| 提取器 | 取什么 | 失败时默认响应 |
| --- | --- | --- |
| Path&lt;T&gt; | 路径参数；多个参数用元组 Path&lt;(i64, i64)&gt;或结构体 | 400 |
| Query&lt;T&gt; | 查询字符串 | 400 |
| Json&lt;T&gt; | JSON 正文（要求 Content-Type: application/json ） | 400 / 415 /422 |
| Form&lt;T&gt; | 表单正文 | 400 / 415 /422 |

| 提取器 | 取什么 | 失败时默认响应 |
| --- | --- | --- |
| State&lt;S&gt; | 共享状态（12.6 节） | 编译期保证存在 |
| HeaderMap/ TypedHeader&lt;T&gt; | 请求头 | - |
| Method 、Uri 、Versio n | 请求行的各部分 | - |
| ConnectInfo&lt;SocketAddr&gt; | 客戶端地址（需要配合into_make_service_with_connect_info ） | - |
| Extension&lt;T&gt; | 中间件放进请求扩展中的值（第 16 章当前用户） | 500 |
| Bytes / String | 原始正文 | 400 |
| Request | 整个请求 | - |

### 12.4.2 【入门】提取器的顺序规则

请求正文是一个只能读一次的流。Axum 把提取器分成两类：

只读请求头部分的（实现 FromRequestParts ）：Path 、Query 、State 、HeaderMap……可以有任意多个、任意顺序。

消耗正文的（实现 FromRequest ）：Json 、Form 、String 、Bytes ……只能有一个，并且必须是最后一个参数。
```rust
// 正确：Json 在最后
async fn update(State(s): State<AppState>, Path(id): Path<i64>, Json(b): Json<CreateProduct>) 
    {}
// 错误：Json 不在最后--编译失败，报错信息很长且难以理解（见 12.4.5 节）
// async fn update(Json(b): Json<CreateProduct>, Path(id): Path<i64>) {}
```

### 12.4.3 【进阶】可选与容错的提取
```rust
use axum::extract::rejection::JsonRejection;

// Option<T>：可选的提取器（如可选的请求头、可选的当前用户）
// Result<T, Rejection>：自己处理提取失败的情况
async fn create(payload: Result<Json<CreateProduct>, JsonRejection>) -> String {
    match payload {
        Ok(Json(p)) => format!("创建 {}", p.name),
        Err(rejection) => format!("请求体有误：{}", rejection.body_text()),
    }
}
```

JsonRejection 是一个枚举，常见变体：MissingJsonContentType （缺少或错误的 Content-Type，415）、JsonSyntaxError （JSON 语法错误，400）、JsonDataError （语法正确但不符合目标类型，包括缺少字段、类型不对、第 10 章 try_from 校验失败，422）、BytesRejection （读取正文失败，如超过大小限制）。默认的拒绝响应是纯文本，不符合第 9.7.4 节的统一错误格式，12.5.3 节用自定义提取器解决。

### 12.4.4 【精通】自定义提取器

为自己的类型实现 FromRequestParts ，就能像内置提取器一样写在参数里：
```rust
use axum::extract::FromRequestParts;
use axum::http::{request::Parts, StatusCode};

/// 客戶端传来的请求编号（第 9.4.2 节），没有则为 None
pub struct ClientRequestId(pub Option<String>);

impl<S: Send + Sync> FromRequestParts<S> for ClientRequestId {
    type Rejection = StatusCode;

    async fn from_request_parts(parts: &mut Parts, _state: &S) -> Result<Self, 
        Self::Rejection> {
        let id = parts.headers.get("x-request-id").and_then(|v| 
            v.to_str().ok()).map(str::to_owned);
        Ok(ClientRequestId(id))
    }
}

async fn handler(ClientRequestId(id): ClientRequestId) -> String { format!("{id:?}") }
```

Axum 0.8 的 trait 直接使用 async fn （第 11.2.4 节）。第 16 章的“当前登录用户” CurrentUser就是这样实现的：从 Authorization 头取出令牌、验证、得到用户 ID；任何需要登录的处理函数只要在参数里写上它就自动受保护。

### 12.4.5 【进阶】看懂 Handler 的编译错误

处理函数写错时（提取器顺序不对、参数不是提取器、返回值没实现 IntoResponse、Future 不是Send），编译器只会说：
```text
error[E0277]: the trait bound `fn(Json<CreateProduct>, Path<i64>) -> ... {update}: Handler<_, _>` is not satisfied
```

这类报错没有指出具体哪里不对。解决办法：给处理函数加上 #[axum::debug_handler] （需要开启axum 的 macros feature），编译器会给出精确的提示，例如“Json consumes the request body and thus must be the last argument”。开发时遇到 Handler 未实现的报错，第一反应就是加这个宏。

## 12.5 响应与错误处理

### 12.5.1 【入门】IntoResponse 的各种形式
```rust
use axum::http::{header, StatusCode};
use axum::response::{IntoResponse, Redirect};
use axum::Json;
use serde_json::json;

// 200 + text/plain
async fn text() -> &'static str { "纯文本" }

// 200 + application/json
async fn json_body() -> Json<serde_json::Value> { Json(json!({"ok": true})) }

// 只有状态码
async fn no_content() -> StatusCode { StatusCode::NO_CONTENT }

// 状态码 + 正文
async fn created() -> (StatusCode, Json<serde_json::Value>) {
    (StatusCode::CREATED, Json(json!({"id": 42})))
}

// 状态码 + 响应头 + 正文
async fn with_headers() -> impl IntoResponse {
    (StatusCode::CREATED, [(header::LOCATION, "/api/v1/products/42")], Json(json!({"id": 
        42})))
}
async fn redirect() -> Redirect { Redirect::permanent("/api/v1/products") }
```

元组形式的规则：可选的 StatusCode 在最前，中间是任意个“响应头部分”（头数组、HeaderMap、扩展），最后是正文。返回类型写不清楚时用 impl IntoResponse 。

### 12.5.2 【入门】Result 作为返回值

Result&lt;T, E&gt; 本身实现了 IntoResponse（只要 T 和 E 都实现），所以处理函数可以返回Result&lt;Json&lt;Product&gt;, ApiError&gt; 并在内部自由使用 ? --这是把第 4 章的错误体系接入 HTTP的关键：
```rust
async fn get_product(State(s): State<AppState>, Path(id): Path<ProductId>) -> 
    Result<Json<Product>, ApiError> {
    // DomainError 通过
    let product = s.products.read(|r| r.get(&id))?;
From 自动转换为 ApiError
    Ok(Json(product))
}
```

### 12.5.3 【进阶】统一的 API 错误类型

定义一个实现了 IntoResponse 的错误类型，把所有错误转换为第 9.10 节约定的 {code, message} 结构：
```rust
impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, code, message) = /* 按错误种类决定 */;
        (status, Json(ErrorBody { code, message })).into_response()
    }
}
```

再用一个自定义的 JSON 提取器替代 axum::Json ，让请求体解析失败也返回同样格式的错误。Axum的macros feature 提供了派生宏，只需几行：
```rust
#[derive(axum::extract::FromRequest)]
// 内部用 axum::Json提取，失败时把拒绝转换为 ApiError
#[from_request(via(axum::Json), rejection(ApiError))]

pub struct AppJson<T>(pub T);
```

完整实现在 12.9 节的项目代码中。

### 12.5.4 第 12.1~12.5 节常见错误

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| E0277 | the trait bound fn(...) {handler}: Handler&lt;_, _&gt; is not satisfied | 提取器顺序、参数类型或返回类型有问题 | 加 #[axum::debug_handler]查看具体原因 |
| 启动panic | Overlapping method route | 同一路径同一方法注册了两次 | 删除重复 |
| 启动panic | Path segments must not start with : | 使用了 0.7 的 /:id写法 | 改为 /{id} |
| 运行时415 | Expected request with Content-Type:application/json | 请求没有带 JSON 类型头 | curl 加 -H 'Content- Typ e: application/json' |
| 运行时422 | Failed to deserialize the JSON body into the target type | 字段缺失或类型不对 | 对照请求结构体 |
| E0308 | expected Router&lt;()&gt; , found Router&lt;AppState&gt; | 忘了 with_state | 在最外层调用.with_state(state) |
| 启动失败 | Address already in use | 端口被占用 | 结束占用进程或换端口（ls of -i :8080 查找） |

## 12.6 State 与依赖注入

### 12.6.1 【入门】共享状态

数据库连接池、配置、缓存客戶端需要被所有请求共享。Axum 的做法是：定义一个状态结构体，在构建路由时用 with_state 注入，处理函数用 State 提取器取出：
```rust
use std::sync::Arc;
use axum::{extract::State, routing::get, Router};

// 必须实现 Clone：Axum 为每个请求克隆一份
#[derive(Clone)]
struct AppState {
    // 只读的大对象放进 Arc，克隆只增加计数
    config: Arc<Config>,
    // db: PgPool,                       // 第 14 章：连接池本身内部就是 Arc，可以直接放
}

struct Config { service_name: String }

async fn whoami(State(state): State<AppState>) -> String {
    state.config.service_name.clone()
}

fn app() -> Router {
    let state = AppState { config: Arc::new(Config { service_name: "rustmall".into() }) };
    Router::new().route("/whoami", get(whoami)).with_state(state)
}
```

为什么要求 Clone：每个请求在各自的任务中处理（第 11.4.3 节），都需要拥有一份状态。所以状态的每个字段都应当“克隆很便宜”：Arc&lt;T&gt; 、连接池、第 7 章的 Shared&lt;R&gt; 、reqwest::Client （内部都是 Arc）。不要在状态里直接放大的 Vec 或 HashMap，否则每个请求都会复制一遍。

### 12.6.2 【进阶】子状态：FromRef

大型应用的状态有很多字段，但每个处理函数只需要其中一两个。实现 FromRef 后，处理函数可以只提取自己关心的部分：
```rust
use axum::extract::FromRef;

#[derive(Clone)]
struct AppState { products: ProductStore, config: Arc<Config> }

impl FromRef<AppState> for ProductStore {
    fn from_ref(state: &AppState) -> Self { state.products.clone() }
}

// 处理函数只依赖 ProductStore，不知道 AppState 的存在，更容易单独测试
async fn list(State(store): State<ProductStore>) -> String { String::new() }
```

也可以在 AppState 上写 #[derive(Clone, FromRef)] （需要 macros feature），为每个字段自动生成 FromRef 实现。

### 12.6.3 【进阶】State、Extension 与全局变量的选择

| 方式 | 类型检查 | 适用 |
| --- | --- | --- |
| State&lt;T&gt; | 编译期：忘了 with_state 无法编译 | 应用级依赖：连接池、仓储、配置（首选） |
| Extension&lt;T&gt; | 运行时：没插入时请求返回 500 | 中间件为单个请求计算出的数据：当前用户、请求ID |
| 全局 static/ LazyL ock | - | 真正全进程唯一且不变的东西（第 7.7.4 节），不用于业务依赖 |

## 12.7 Tower 与中间件

### 12.7.1 【入门】中间件是什么

中间件是包裹在处理函数外层的通用逻辑，每个请求进来时先经过它，响应出去时再经过它：打日志、生成请求 ID、处理跨域、限制请求体大小、超时、压缩、鉴权、限流。把这些写在每个处理函数里会导致大量重复，中间件把它们集中到一处。

### 12.7.2 【进阶】Tower 的 Service 与 Layer
```rust
pub trait Service<Request> {
    type Response;
    type Error;
    type Future: Future<Output = Result<Self::Response, Self::Error>>;

    // 是否能接收新请求（背压）
    fn poll_ready(&mut self, cx: &mut Context<'_>) -> Poll<Result<(), Self::Error>>;

    // 处理请求
    fn call(&mut self, req: Request) -> Self::Future;
}
pub trait Layer<S> {
    type Service;

    // 把一个 Service 包装成另一个 Service
    fn layer(&self, inner: S) -> Self::Service;
}
```

Service：一个“输入请求、异步返回响应”的东西。Axum 的路由、每个处理函数，最终都是Service。

Layer：一个“装饰器工厂”，把内层 Service 包一层，得到增加了某种能力的新 Service。

poll_ready 让 Service 可以表达“我现在忙，先别发请求给我”，是第 39 章限流、负载削减的基础。

### 12.7.3 【入门】tower-http 常用中间件
```text
tower-http = { version = "0.6", features = ["cors", "trace", "request-id", "compression- gzip", "limit"] }
```

| 中间件 | feature | 作用 | 章节 |
| --- | --- | --- | --- |
| CorsLayer | cors | 跨域响应头 | 本章 |
| TraceLayer | trace | 为每个请求生成 tracing span、记录耗时与状态码 | 第 15章 |
| SetRequestIdLayer/ PropagateRe questIdLayer | request-id | 生成并回传 x-request-id | 第 15章 |
| CompressionLayer | compression-gzip 等 | 压缩响应体 | - |
| RequestBodyLimitLayer | limit | 限制请求体大小 | - |
| TimeoutLayer | timeout | 整个请求的超时 | 第 31章 |
| CatchPanicLayer | catch-panic | 处理函数 panic 时返回 500 而不是断开连接 | 第 31章 |

Axum 自带 DefaultBodyLimit ：默认把请求体限制为 2 MB，可以用.layer(DefaultBodyLimit::max(64 * 1024)) 调整（第 10.7.2 节的安全建议）。
```rust
use axum::extract::DefaultBodyLimit;
use tower_http::cors::{Any, CorsLayer};
use axum::http::{Method, HeaderValue};

let cors = CorsLayer::new()
    .allow_origin("https://shop.rustmall.com".parse::<HeaderValue>().expect("合法的源"))
    .allow_methods([Method::GET, Method::POST, Method::PUT, Method::DELETE])
    .allow_headers(Any);
let app = Router::new()
    .route("/api/v1/products", get(list_products))
    .layer(DefaultBodyLimit::max(64 * 1024))
    .layer(cors);
```

开发阶段可以用 CorsLayer::permissive() 允许任意来源；生产配置在第 15 章从配置文件读取允许的域名。

### 12.7.4 【进阶】中间件的顺序
```text
let app = Router::new()
    .route("/", get(handler))
    // 先加的在内层
    .layer(layer_a)
    // 后加的在外层
    .layer(layer_b);
// 请求：layer_b → layer_a → handler；响应：handler → layer_a → layer_b
```

像洋葱一样：.layer() 越靠后调用，越在外层。需要“最先看到请求”的中间件（请求 ID、追踪）应当最后添加；也可以用 tower::ServiceBuilder 按从外到内的自然顺序书写：
```rust
use tower::ServiceBuilder;
let app = Router::new().route("/", get(handler)).layer(
    ServiceBuilder::new()
        // ServiceBuilder 中先写的在外层
        .layer(layer_b)
        .layer(layer_a),
);
```

.layer() 只作用于调用它之前已经注册的路由；.route_layer() 只在路由匹配成功时执行（例如鉴权中间件，不希望对 404 也返回 401）。

### 12.7.5 【进阶】用函数写中间件

不需要实现 Tower trait，axum::middleware::from_fn 让普通的 async 函数成为中间件：
```rust
use axum::{extract::Request, middleware::{self, Next}, response::Response};
use std::time::Instant;

async fn timing(req: Request, next: Next) -> Response {
    let start = Instant::now();
    let path = req.uri().path().to_owned();

    // 交给内层继续处理
    let response = next.run(req).await;
    println!("{path} 耗时 {:?}，状态 {}", start.elapsed(), response.status());
    response
}
let app = Router::new().route("/", get(handler)).layer(middleware::from_fn(timing));
```

需要访问状态时用 middleware::from_fn_with_state(state.clone(), f) ，函数的第一个参数写State&lt;AppState&gt; 。中间件函数中可以像处理函数一样使用提取器（最后一个参数必须是 Next ），也可以直接返回响应、不调用 next.run --这就是鉴权中间件拒绝请求的方式。

### 12.8.1 【入门】不启动服务器就能测试

### 12.9.3 第 2 步：统一错误 error.rs

```rust
//! HTTP 层的统一错误：把领域错误和请求解析错误转换为 `{code, message}` 响应。

use axum::http::StatusCode;
use axum::response::{IntoResponse, Response};
use axum::Json;
use common::error::{DomainError, ErrorKind};
use serde::Serialize;
/// 错误响应体，格式见 `docs/api-v1.md` 第 2 节。
#[derive(Debug, Serialize)]
pub struct ErrorBody {
    pub code: &'static str,
    pub message: String,
}

/// 处理函数返回的错误类型。
#[derive(Debug)]
pub enum ApiError {
    /// 请求无法解析：JSON 语法错误、缺少 Content-Type 等
    BadRequest(String),
    /// 请求体结构不符合要求：缺少字段、类型不对、取值不合法、存在未知字段
    Unprocessable(String),
    /// 领域层返回的错误
    Domain(DomainError),
}

impl From<DomainError> for ApiError {
    fn from(e: DomainError) -> Self {
        ApiError::Domain(e)
    }
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, code, message) = match self {
            ApiError::BadRequest(message) => (StatusCode::BAD_REQUEST, "BAD_REQUEST", 
                message),
            ApiError::Unprocessable(message) => {
                (StatusCode::UNPROCESSABLE_ENTITY, ErrorKind::InvalidInput.code(), message)
            }
            ApiError::Domain(e) => {
                let kind = e.kind();
                let status = match kind {
                    ErrorKind::InvalidInput => StatusCode::UNPROCESSABLE_ENTITY,
                    ErrorKind::NotFound => StatusCode::NOT_FOUND,
                    ErrorKind::Conflict => StatusCode::CONFLICT,
                    ErrorKind::Internal => StatusCode::INTERNAL_SERVER_ERROR,
                };
                let message = if kind == ErrorKind::Internal {
                    // 内部错误的细节只进日志（第 15 章换成 tracing），绝不返回给客戶端
                    eprintln!("内部错误：{e:?}");
                    "服务器内部错误".to_string()
                } else {
                    e.to_string()
                };
                (status, kind.code(), message)
            }
        };
        (status, Json(ErrorBody { code, message })).into_response()
    }
}
```

代码精讲：

错误码复用第 4 章的 ErrorKind::code() ：领域层定义“错误是什么”，HTTP 层只决定“用哪个状态码表达”。领域层完全不知道 HTTP 的存在，第 25 章的 gRPC 服务会把同一个 ErrorKind 映射为gRPC 状态码。

match kind 没有写 _ 分支：将来 ErrorKind 新增分类时，编译器会在这里报错，提醒你决定它对应的状态码（第 3.5.10 节）。

内部错误隐藏细节：对外只返回固定文案，详细的 Debug 信息写到标准错误输出（第 9.7.4 节）。

```rust
//! 自定义 JSON 提取器与响应：解析失败时返回统一格式的错误。

use axum::extract::rejection::JsonRejection;
use axum::extract::FromRequest;
use axum::response::{IntoResponse, Response};
use serde::Serialize;

use crate::error::ApiError;

/// 与 `axum::Json` 用法相同，但提取失败时返回 [`ApiError`]。
#[derive(Debug, FromRequest)]
#[from_request(via(axum::Json), rejection(ApiError))]
pub struct AppJson<T>(pub T);
impl<T: Serialize> IntoResponse for AppJson<T> {
    fn into_response(self) -> Response {
        axum::Json(self.0).into_response()
    }
}

impl From<JsonRejection> for ApiError {
    fn from(rejection: JsonRejection) -> Self {
        match rejection {
            // 语法正确但不符合目标类型：缺少字段、类型错误、try_from 校验失败、未知字段
            JsonRejection::JsonDataError(e) => ApiError::Unprocessable(e.body_text()),
            // 其余：JSON 语法错误、缺少 Content-Type、读取请求体失败
            other => ApiError::BadRequest(other.body_text()),
        }
    }
}
```

#[from_request(via(axum::Json), rejection(ApiError))] 的含义：提取 AppJson&lt;T&gt;时，先用axum::Json&lt;T&gt; 提取，成功则把内部值放进 AppJson ；失败则把 JsonRejection 通过 From转换为ApiError 。同一个类型还实现了 IntoResponse ，所以既可以作为参数、也可以作为返回值，与axum::Json 的用法一致。

```rust
//! 商品接口：`/api/v1/products`。

use axum::extract::{Path, Query, State};
use axum::http::{header, StatusCode};
use axum::response::IntoResponse;
use common::error::{DomainError, ValidationError};
use common::ids::ProductId;
use common::pagination::{self, Page};
use common::product::Product;
use common::repository::Repository;
use serde::Deserialize;

use crate::error::ApiError;
use crate::extract::AppJson;
use crate::state::AppState;

/// 新增、修改商品的请求体：只包含允许客戶端设置的字段（第 10.7.2 节）。
#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct ProductInput {
    pub name: String,
    pub price_cents: i64,
    pub stock: i32,
}

impl ProductInput {
    /// 通过 `Product::try_new` 构造，保证商品的不变量。
    fn into_product(self, id: ProductId) -> Result<Product, ApiError> {
        Product::try_new(id, &self.name, self.price_cents, self.stock).map_err(|reason| {
            ApiError::from(DomainError::from(ValidationError::Format { field: "product", 
                reason }))
        })
    }
}

/// 列表查询参数。
#[derive(Debug, Default, Deserialize)]
pub struct ListQuery {
    pub page: Option<u32>,
    pub page_size: Option<u32>,
}

/// `GET /api/v1/products?page=&page_size=`
pub async fn list(State(state): State<AppState>, Query(query): Query<ListQuery>) -> 
    AppJson<Page<Product>> {
    let (page, page_size) = pagination::normalize(query.page, query.page_size);
    let offset = usize::try_from((page - 1).saturating_mul(page_size)).unwrap_or(usize::MAX);
    let limit = usize::try_from(page_size).unwrap_or(usize::MAX);
    let (items, total) = state.products.read(|r| (r.list(offset, limit), r.count()));
    AppJson(Page::new(items, page, page_size, i64::try_from(total).unwrap_or(i64::MAX)))
}
/// `GET /api/v1/products/{id}`
pub async fn get_one(
    State(state): State<AppState>,
    Path(id): Path<ProductId>,
) -> Result<AppJson<Product>, ApiError> {
    let product = state.products.read(|r| r.get(&id))?;
    Ok(AppJson(product))
}

/// `POST /api/v1/products`
pub async fn create(
    State(state): State<AppState>,
    AppJson(input): AppJson<ProductInput>,
) -> Result<impl IntoResponse, ApiError> {
    let id = ProductId::new(state.product_ids.next_value());
    let product = input.into_product(id)?;
    state.products.write(|r| r.insert(product.clone()))?;
    let location = format!("/api/v1/products/{id}");
    Ok((StatusCode::CREATED, [(header::LOCATION, location)], AppJson(product)))
}

/// `PUT /api/v1/products/{id}`：整体替换
pub async fn update(
    State(state): State<AppState>,
    Path(id): Path<ProductId>,
    AppJson(input): AppJson<ProductInput>,
) -> Result<AppJson<Product>, ApiError> {
    let product = input.into_product(id)?;
    state.products.write(|r| r.update(product.clone()))?;
    Ok(AppJson(product))
}

/// `DELETE /api/v1/products/{id}`
pub async fn remove(State(state): State<AppState>, Path(id): Path<ProductId>) -> 
    Result<StatusCode, ApiError> {
    state.products.write(|r| r.remove(&id))?;
    Ok(StatusCode::NO_CONTENT)
}
```

代码精讲：

Path(id): Path&lt;ProductId&gt; ：路径参数直接反序列化为强类型 ID--第 10 章给 ID 加了#[serde(transparent)] ，在这里得到回报。路径中的值不是数字时，Axum 返回 400。

每个处理函数只做三件事：取参数、调用领域代码（仓储与 Product::try_new ）、组装响应。业务规则全在 common 中，处理函数里没有任何 if 判断--这是第 15 章分层架构的雏形。

? 的两种来源：r.get(&amp;id)? 中是 DomainError → ApiError ；input.into_product(id)? 本身就返回 ApiError 。

[(header::LOCATION, location)] ：响应头数组（12.5.1 节），值是 String，Axum 会转换为HeaderValue 。

list 中的类型转换：页码与每页条数是 u32 ，仓储的 list 接收 usize 、count 返回usize，Page::total 是 i64 ，全部使用 try_from （第 1.3.5 节）。页码已被 normalize限制在合法范围内，saturating_mul 防止乘法溢出。

ID 生成在校验之前：校验失败的请求也会消耗一个序号，导致 ID 不连续。这完全没有问题--数据库自增 ID 也有同样的行为，ID 只要求唯一，不要求连续。

竞态说明：update 是“整体替换”，两个管理员同时修改同一商品时，后提交的会覆盖先提交的（last write wins）。第 9.4.3 节介绍的 ETag / If-Match 可以解决，管理后台通常可以接受这种行为。

### 12.9.7 第 6 步：路由 routes.rs

文件：rustmall/monolith/src/routes.rs （新建）
```rust
//! 路由表与全局中间件。

use axum::extract::DefaultBodyLimit;
use axum::http::StatusCode;
use axum::routing::get;
use axum::{Json, Router};
use tower_http::cors::CorsLayer;

use crate::error::ErrorBody;
use crate::state::AppState;
use crate::{health, products};

/// 请求体大小上限：64 KB。商品、订单等 JSON 请求远小于这个值。
pub const MAX_BODY_BYTES: usize = 64 * 1024;

/// 构建完整的应用路由。测试与 main 共用同一个函数，保证测试的就是线上的路由。
pub fn router(state: AppState) -> Router {
    let api = Router::new()
        .route("/products", get(products::list).post(products::create))
        .route(
            "/products/{id}",
            get(products::get_one).put(products::update).delete(products::remove),
        );

    Router::new()
        .route("/health/live", get(health::live))
        .route("/health/ready", get(health::ready))
        .nest("/api/v1", api)
        .fallback(not_found)
        .layer(DefaultBodyLimit::max(MAX_BODY_BYTES))
        // 开发阶段允许任意来源；第 15 章改为从配置读取允许的域名
        .layer(CorsLayer::permissive())
        .with_state(state)
}

/// 未匹配任何路由时，也返回统一格式的错误。
async fn not_found() -> (StatusCode, Json<ErrorBody>) {
    let body = ErrorBody { code: "NOT_FOUND", message: "接口不存在".to_string() };
    (StatusCode::NOT_FOUND, Json(body))
}
```

“测试与 main 共用同一个 router 函数” 是非常重要的工程习惯：如果测试自己另外拼一套路由，就可能出现“测试通过、线上漏注册了某个路由”的情况。

```rust
//! RustMall 单体服务入口。

use std::time::Duration;

use monolith::state::AppState;
use monolith::{background, routes, shutdown};
use tokio_util::sync::CancellationToken;

/// 监听地址（第 15 章改为从配置读取）。
const ADDR: &str = "0.0.0.0:8080";
/// HTTP 服务停止后，等待后台任务结束的最长时间。
const SHUTDOWN_GRACE: Duration = Duration::from_secs(10);

#[tokio::main]
async fn main() -> std::io::Result<()> {
    let token = CancellationToken::new();
    tokio::spawn(shutdown::wait_for_signal(token.clone()));

    let cleaner = tokio::spawn(background::run_periodic(
        Duration::from_secs(60),
        token.clone(),
        || async { println!("[后台] 清理过期的购物车") },
    ));

    let app = routes::router(AppState::default());
    let listener = tokio::net::TcpListener::bind(ADDR).await?;
    println!("RustMall 单体服务监听 http://{ADDR}");

    // 收到停机信号后：停止接受新连接，等待进行中的请求完成
    axum::serve(listener, app).with_graceful_shutdown(token.clone().cancelled_owned()).await?;
    println!("HTTP 服务已停止，等待后台任务结束……");

    match tokio::time::timeout(SHUTDOWN_GRACE, cleaner).await {
        Ok(Ok(runs)) => println!("后台任务已停止，共执行 {runs} 次"),
        Ok(Err(e)) => eprintln!("后台任务异常退出：{e}"),
        Err(_) => eprintln!("后台任务未能在 {SHUTDOWN_GRACE:?} 内停止，强制退出"),
    }
    Ok(())
}
```

与第 11 章相比：main 返回 std::io::Result&lt;()&gt; ，绑定端口失败时程序以错误退出；后台任务周期改为 60 秒；cancelled_owned() 返回一个拥有 token 的 Future（满足with_graceful_shutdown 对'static 的要求），完整的停机顺序是：信号 → 停止 HTTP →等待后台任务 → 退出。

```rust
//! 商品接口的 HTTP 层测试：不监听端口，直接调用 Router。

use axum::body::Body;
use axum::http::{Request, StatusCode};
use axum::Router;
use http_body_util::BodyExt;
use monolith::routes::router;
use monolith::state::AppState;
use serde_json::{json, Value};
use tower::ServiceExt;

fn app() -> Router {
    router(AppState::default())
}

/// 发送请求，返回状态码与 JSON 响应体（空响应体为 Null）。
async fn send(app: &Router, request: Request<Body>) -> (StatusCode, Value) {
    let response = app.clone().oneshot(request).await.expect("Router 不会返回错误");
    let status = response.status();
    let bytes = response.into_body().collect().await.expect("读取响应体").to_bytes();
    let body = if bytes.is_empty() {
        Value::Null
    } else {
        serde_json::from_slice(&bytes).expect("响应体应当是 JSON")
    };
    (status, body)
}

fn get(uri: &str) -> Request<Body> {
    Request::get(uri).body(Body::empty()).expect("合法的请求")
}

fn json_request(method: &str, uri: &str, body: &Value) -> Request<Body> {
    Request::builder()
        .method(method)
        .uri(uri)
        .header("content-type", "application/json")
        .body(Body::from(body.to_string()))
        .expect("合法的请求")
}

fn keyboard() -> Value {
    json!({ "name": "机械键盘", "price_cents": 19900, "stock": 10 })
}

#[tokio::test]
async fn health_is_ok() {
    let (status, body) = send(&app(), get("/health/live")).await;
    assert_eq!(status, StatusCode::OK);
    assert_eq!(body, json!({ "status": "ok" }));
}

#[tokio::test]
async fn create_then_get() {
    let app = app();
    let (status, created) = send(&app, json_request("POST", "/api/v1/products", 
        &keyboard())).await;
    assert_eq!(status, StatusCode::CREATED);
    assert_eq!(created, json!({ "id": 1, "name": "机械键盘", "price_cents": 19900, "stock": 10 
        }));

    let (status, fetched) = send(&app, get("/api/v1/products/1")).await;
    assert_eq!(status, StatusCode::OK);
    assert_eq!(fetched, created);
}

}
```

### 12.9.10 第 9 步：修订 API 文档

实现时发现，按照 Axum 的错误分类，“缺少必填字段、类型错误”属于“JSON 语法正确但数据不符合类型”，与数量超限一样返回 422 更一致。文件：rustmall/docs/api-v1.md ，把第 2 节错误表中400与 422 两行改为：

### 12.9.13 常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| cannot find derive macro FromRequest | axum 没有开启 macros feature | 按 12.9.2 声明 |
| no method named cancelled_owned | tokio-util 版本过旧 | cargo update -p tokio-util |

### 12.9.14 本章小结

Axum 由路由、处理函数、提取器、IntoResponse 四个核心概念组成，建立在 Tower 与 hyper 之上；中间件可以在 HTTP 与 gRPC 之间复用。

路由用 route 注册、nest 挂载前缀、fallback 兜底，0.8 的路径参数写作 {id} 。

提取器从请求中取数据：只读请求头部分的可以有多个，消耗正文的只能有一个并且必须在最后；Result / Option 提取器处理失败情况；自定义提取器实现 FromRequestParts ；看不懂的Handler 报错用 #[axum::debug_handler] 。

返回值实现 IntoResponse 即可；Result&lt;T, ApiError&gt; 让处理函数中自由使用 ? ；统一的错误类型与自定义 JSON 提取器保证所有错误格式一致。

State 必须能廉价克隆；FromRef 提取子状态；Extension 用于中间件传递每个请求的数据。

Tower 的 Service 与 Layer 是中间件的基础，.layer() 越靠后越在外层；from_fn 用普通函数写中间件。

Router 可以不经网络直接 oneshot 测试；with_graceful_shutdown 实现 HTTP 层的优雅停机。

RustMall 的 monolith 有了健康检查与商品增删改查接口、统一错误响应和 10 个 HTTP 层测试。

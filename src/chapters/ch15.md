# 第 15 章 工程化：配置、日志与分层架构

到第 14 章为止，RustMall 已经能把商品存进 PostgreSQL，但代码里还有不少“玩具痕迹”：

监听地址、数据库地址写死在 main.rs 的常量里；

日志靠 println! / eprintln!，没有级别，不能按模块过滤，也没法被日志系统采集；

处理函数直接调用仓储，业务规则没有固定的“家”；

新增商品时用一个占位 ID 去构造 Product。

本章把这些问题一次性解决：用 dotenvy + config 做分层配置，用 tracing 体系做结构化日志与请求追踪，用 validator 做请求校验，并把 monolith 重构为“HTTP 层 → 服务层 → 仓储层”三层结构。本章结束时，RustMall 的代码组织方式就基本定型了，后面的认证、缓存、微服务拆分都在这个骨架上展开。

| crate | 作用 | 小节 |
| --- | --- | --- |
| dotenvy | 从 .env 文件加载环境变量 | 15.2.2 |
| config | 多来源、分层合并的配置加载 | 15.2.3 |
| tracing | 结构化日志与 span 的“埋点”API | 15.3 |
| tracing-subscriber | 收集、过滤、格式化 tracing 数据 | 15.3.5 |
| tower-http（trace、request-id） | HTTP 请求日志与请求 ID | 15.3.7 |
| validator | 声明式字段校验 | 15.4 |

## 15.1 什么是“工程化”

### 15.1.1 【入门】从“能跑”到“能上线”

一个能在自己电脑上跑起来的程序，和一个能放到生产环境、由团队长期维护的服务，中间隔着一系列工程问题：

| 问题 | 玩具做法 | 工程做法 |
| --- | --- | --- |
| 不同环境地址不同 | 改代码重新编译 | 同一个二进制，配置从外部注入 |
| 出了问题怎么查 | 到处加 println! | 结构化日志，带请求 ID，可按字段检索 |
| 业务规则放哪 | 散落在处理函数里 | 服务层集中表达，可单独测试 |
| 怎么测试 | 只能连真库跑 | 服务层用测试替身，秒级完成 |

### 15.1.2 【进阶】十二要素应用中的三条

“十二要素应用”（The Twelve-Factor App）是云原生服务的经典设计准则，本章落实其中三条：

1. 配置存放在环境中：代码与配置严格分离。判断标准是--这份代码能否立刻开源而不泄露任何凭据？

2. 日志当作事件流：程序只负责把日志写到标准输出，由运行环境（Docker、Kubernetes、日志采集器）决定写到哪里。程序不该自己管理日志文件、轮转、压缩。

3. 开发环境与生产环境尽量一致：同样的配置结构、同样的日志格式（只是开发时更易读），减少“我这里好好的”这类问题。

## 15.2 配置管理：dotenvy 与 config

### 15.2.1 【入门】配置的来源与优先级

一个服务的配置通常来自多个地方，按优先级从低到高：

1. 代码中的默认值 / 默认配置文件：所有环境共享，例如默认端口 8080。

2. 环境专属配置文件：development.toml、production.toml，例如生产环境日志用 JSON。

3. 环境变量：部署时注入，例如 Kubernetes 的 Secret 注入数据库密码。

4. 命令行参数（本书不用）。

高优先级覆盖低优先级。这样，99% 的配置写在文件里、随代码一起评审；少数敏感或随部署变化的值用环境变量覆盖。

### 15.2.2 【入门】dotenvy：本地开发用的 .env 文件

开发时每开一个终端都要 export DATABASE_URL=... 很烦。约定做法是在项目根目录放一个 .env文件（不提交到 Git，第 0 章的 .gitignore 已经忽略它），程序启动时加载：
```toml
[dependencies]
dotenvy = "0.15"
```
```rust
fn main() {
    // 从当前目录（及上级目录）查找 .env 并加载；找不到文件不算错误
    dotenvy::dotenv().ok();
    let configured = std::env::var("DATABASE_URL").is_ok();
    println!("DATABASE_URL configured: {configured}");
}
```

.env 文件格式：
```text
# 注释
DATABASE_URL=postgres://rustmall:rustmall@localhost:5432/rustmall
APP_ENV=development
# 值中有空格时加引号
GREETING="hello world"
```

要点：

已经存在的环境变量不会被 .env 覆盖。这保证了“部署环境注入的值”永远优先于“开发者电脑上的文件”。

dotenvy 是已停止维护的 dotenv crate 的社区继承者，API 基本一致，新项目一律用dotenvy。

生产环境不应该依赖 .env 文件，而是由容器编排平台注入环境变量。.ok() 让“没有 .env 文件”成为正常情况。

其他函数：dotenvy::from_filename(".env.test") 加载指定文件；dotenvy::var("KEY")先加载再读取单个变量。

建议同时提交一个 .env.example，列出所有需要的变量名和示例值，新成员复制一份改名即可。

### 15.2.3 【入门】config crate：分层合并
```toml
[dependencies]
config = { version = "0.15", default-features = false, features = ["toml"] }
serde = { version = "1", features = ["derive"] }
```

config 默认支持 TOML、JSON、YAML、INI 等多种格式，default-features = false 后只开启toml，减少依赖。

最小示例：
```rust
use config::{Config, Environment, File};
use serde::Deserialize;

#[derive(Debug, Deserialize)]
struct Settings {
    port: u16,
    name: String,
}

fn main() -> Result<(), config::ConfigError> {
    let settings: Settings = Config::builder()
        // 优先级低：settings.toml（必须存在）
        .add_source(File::with_name("settings"))
        // 优先级高：APP_PORT、APP_NAME 等环境变量
        .add_source(Environment::with_prefix("APP"))
        .build()?
        .try_deserialize()?;
    println!("{settings:?}");
    Ok(())
}
```

settings.toml：
```text
port = 8080
name = "demo"
```

运行 APP_PORT=9000 cargo run，得到 Settings { port: 9000, name: "demo" }。

工作原理：build() 把所有来源按添加顺序合并成一棵键值树，后添加的覆盖先添加的；try_deserialize() 再用 serde 把这棵树反序列化成你的结构体（第 10 章的所有 serde 知识在这里都适用：#[serde(default)]、rename_all、枚举……）。

### 15.2.4 【进阶】嵌套结构与环境变量命名

真实项目的配置是分组的：
```text
[server]
host = "0.0.0.0"
port = 8080

[database]
url = "postgres://localhost/app"
max_connections = 10
```

对应的环境变量要能表达“database 组下的 max_connections”。约定用双下划线作为层级分隔符，因为键名本身可能含有单下划线：
```text
Environment::with_prefix("APP")
    // 前缀与键之间用单下划线：APP_xxx
    .prefix_separator("_")
    // 层级之间用双下划线：APP_DATABASE__MAX_CONNECTIONS
    .separator("__")
    // 把 "10"、"true" 这类字符串解析为数字、布尔
    .try_parsing(true)
```

| 环境变量 | 覆盖的配置项 |
| --- | --- |
| APP_SERVER__PORT=9000 | server.port |
| APP_DATABASE__MAX_CONNECTIONS=20 | database.max_connections |
| APP_LOG__FORMAT=json | log.format |

注意 prefix_separator：只设置 separator("__") 时，config 会把前缀分隔符也当成 __，变量名就变成了 APP__SERVER__PORT。显式写出 prefix_separator("_") 可以避免这个容易混淆的细节。

### 15.2.5 【进阶】ConfigBuilder 的常用方法

| 方法 | 作用 |
| --- | --- |
| add_source(File::with_name("config/default")) | 加载文件，扩展名自动识别（.toml 等） |
| File::with_name(...).required(false) | 文件不存在时跳过而不是报错 |
| File::from_str(text, FileFormat::Toml) | 从字符串加载（测试中很方便） |
| set_default("server.port", 8080)? | 设置最低优先级的默认值 |
| set_override("server.port", 9000)? | 设置最高优先级的值 |
| set_override_option("database.url", Option&lt;String&gt;)? | 值为 Some 时才覆盖 |

set_override_option 很适合兼容“业界通用”的环境变量名。例如 sqlx-cli、很多部署平台都使用DATABASE_URL，我们可以让它优先于 APP_DATABASE__URL：
```text
builder.set_override_option("database.url", std::env::var("DATABASE_URL").ok())?
```

### 15.2.6 【精通】配置设计的最佳实践

1. 启动时一次性加载、校验，失败就退出。配置错误应该在部署那一刻暴露，而不是在凌晨三点某个请求走到某个分支时暴露。

2. 用强类型表达配置：端口用 u16（负数或 70000 在反序列化时就会失败），日志格式用枚举而不是字符串，时长用整数秒并在名字里写明单位（acquire_timeout_secs）。

3. 配置结构体只在启动时读取，然后把需要的部分传给各组件。不要把整个 Settings 放进全局变量让各处随意读取，那会让组件之间产生看不见的依赖。

4. 敏感值不进日志。#[derive(Debug)] 会把数据库密码打印出来；包含密钥的结构体要手动实现Debug（第 3.3 节），第 16 章会用 secrecy crate 从类型层面解决。

5. 不要支持“运行时热更新配置”，除非真的需要。在容器环境中，改配置 = 滚动重启，简单可靠。

### 15.2.7 常见错误与解读

| 报错 | 原因 | 修复 |
| --- | --- | --- |
| configuration file "config/default" not found | 相对路径以当前工作目录为准，而不是以 Cargo.toml 为准 | 用绝对路径或可配置的目录（15.6 节的做法） |
| missing field 'port' | 所有来源都没有提供该字段 | 补充默认配置，或在字段上加#[serde(default)] |

| 报错 | 原因 | 修复 |
| --- | --- | --- |
| invalid type: string "abc", expected u16 for key 'server.port' | 值类型不对 | 检查环境变量值 |
| 设置了环境变量但没有生效 | 分隔符不对（例如写成了APP_SER VER_PORT） | 层级之间用 __，并确认pr efix_separator |
| 布尔或数字从环境变量读进来是字符串 | 没开 try_parsing | .try_parsing(true) |

## 15.3 结构化日志：tracing 体系

### 15.3.1 【入门】为什么不用 println!

| 需求 | println! | tracing |
| --- | --- | --- |
| 级别（调试 / 信息 / 警告 / 错误） | 无 | trace!、debug!、info!、warn!、error! |
| 按模块、按级别开关 | 无 | RUST_LOG=monolith=debug,sqlx=warn |
| 结构化字段（可检索） | 只能拼字符串 | info!(product_id = 42, "商品已创建") |
| 关联同一请求的所有日志 | 无 | span：自动携带请求 ID 等上下文 |
| 输出格式 | 固定 | 开发时彩色可读，生产时 JSON |
| 性能 | 每次都格式化 | 级别关闭时几乎零开销 |

Rust 生态还有一个更老的 log crate（log::info!），API 类似，但没有 span 的概念。Tokio、Axum、SQLx、tower-http 都使用 tracing，后端项目直接选它；tracing 也能接收 log 产生的日志（tracing-log，tracing-subscriber 默认开启）。

### 15.3.2 【入门】两个 crate 的分工

tracing：埋点 API。库和应用代码只依赖它，负责“产生”事件。

tracing-subscriber：订阅者。只有可执行程序（main 所在的 crate）依赖它，负责“收集、过滤、格式化、输出”。

这种分工和 log 生态一样：库不决定日志去哪里，由最终的应用决定。如果没有安装任何订阅者，所有tracing 调用都是空操作。
```toml
[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }
```

最小示例：
```rust
fn main() {
    // 安装一个默认格式的订阅者：输出到标准输出，级别 INFO 及以上
    tracing_subscriber::fmt::init();

    tracing::info!("服务启动");
    tracing::debug!("这条不会显示：默认级别是 INFO");
    tracing::warn!(retries = 3, "数据库连接不稳定");
}
```

输出形如：
```text
2026-10-11T08:00:00.123456Z  INFO demo: 服务启动
2026-10-11T08:00:00.123500Z  WARN demo: 数据库连接不稳定 retries=3
```

### 15.3.3 【进阶】事件与字段
```rust
use tracing::{error, info, warn};

let product_id = 42_i64;
let name = "机械键盘";
let err = std::io::Error::other("磁盘已满");

// 字段名 = 值：值必须实现 tracing 的 Value（整数、布尔、&str 等）
info!(product_id, "商品已创建");

// 显式命名
info!(id = product_id, "商品已创建");

// % 表示用 Display 记录，? 表示用 Debug 记录
info!(%name, ?err, "写入失败");

// 消息部分支持 format! 语法
warn!(product_id, "库存只剩 {} 件", 3);

// 记录错误的惯用写法：error = %err 记录消息，error = ?err 记录完整结构
error!(error = %err, "保存商品失败");
```

字段 vs 消息：把变化的数据放进字段，消息保持固定文本。这样在日志平台里可以直接按 product_id=42 检索、按“商品已创建”聚合计数；如果把 ID 拼进消息字符串，每条消息都不一样，就失去了这些能力。

### 15.3.4 【进阶】span：给一段时间内的日志加上下文

事件（event）是一个时间点上发生的事；span 是一段持续的时间，例如“处理一个 HTTP 请求”。在span 内产生的所有事件，都会自动带上 span 的字段：
```rust
use tracing::{info, info_span, Instrument};

async fn handle(order_id: i64) {
    info!("开始扣库存");
    info!("扣库存完成");
}

// 给一个 Future 附加 span：Future 每次被轮询时都会进入这个 span handle(1001).instrument(info_span!
    ("place_order", order_id = 1001)).await;
```

输出中两条事件都带有 place_order{order_id=1001} 前缀。

更常用的是 #[instrument] 属性宏，自动为函数创建 span，并把参数记录为字段：
```rust
use tracing::instrument;

// skip(self) 不记录 self；fields 增加自定义字段
#[instrument(skip(self), fields(product_id = %id))]
async fn get(&self, id: ProductId) -> DomainResult<Product> {
    // ……这里的所有日志都带 product_id 字段
}
```

| #[instrument] 参数 | 作用 |
| --- | --- |
| skip(a, b) / skip_all | 不记录某些参数（大对象、敏感数据、没有实现 Debug 的类型） |
| fields(k = v) | 增加字段，可以用 %、? |
| level = "debug" | span 的级别（默认 INFO） |
| err | 函数返回 Err 时自动记录一条 ERROR 事件 |
| ret | 记录返回值 |
| name = "xxx" | span 名称（默认是函数名） |

异步代码中绝对不要用 span.enter() 跨越 .await：
```text
// 错误示范
let span = info_span!("work");
let _guard = span.enter();
some_async_fn().await;   // 在 await 期间任务可能被挂起，别的任务会“继承”这个 span
```

异步代码一律用 .instrument(span) 或 #[instrument]。这是 tracing 文档中特别强调的坑。

### 15.3.5 【进阶】tracing-subscriber：过滤与格式化

EnvFilter 过滤语法（来自环境变量 RUST_LOG 或配置）：

| 写法 | 含义 |
| --- | --- |
| info | 所有模块 INFO 及以上 |
| monolith=debug | 只有 monolith crate 的 DEBUG 及以上，其他不输出 |
| info,monolith=debug,sqlx=warn | 默认 INFO；monolith 放宽到 DEBUG；sqlx 收紧到 WARN |
| tower_http=debug | 查看 tower-http 的请求日志细节 |
| monolith[place_order]=trace | 只在名为 place_order 的 span 内输出 TRACE |

注意模块路径中 crate 名的连字符要写成下划线：tower-http 写作 tower_http。

组合式配置：tracing-subscriber 采用“注册表 + 层”的设计：
```rust
use tracing_subscriber::layer::SubscriberExt;
use tracing_subscriber::util::SubscriberInitExt;
use tracing_subscriber::{fmt, EnvFilter};

tracing_subscriber::registry()
    // 过滤层：决定哪些数据被记录
    .with(EnvFilter::new("info,monolith=debug"))
    // 格式化层：决定怎样输出
    .with(fmt::layer().json())
    // 设为全局默认订阅者
    .init();
```

fmt::layer() 的常用定制：

| 方法 | 作用 |
| --- | --- |
| .json() | 每条日志一行 JSON，供 Loki、ELK 等平台采集 |
| .pretty() | 多行、带颜色、带源码位置，适合调试 |
| .compact() | 单行紧凑格式 |
| .with_target(false) | 不显示模块路径 |
| .with_file(true).with_line_number(true) | 显示源码位置 |
| .with_writer(std::io::stderr) | 输出到标准错误 |

JSON 格式的一条日志：
```text
{"timestamp":"2026-10-11T08:00:00.123Z","level":"INFO","fields":{"message":"商品已创建","product_id":42},"target":"monolith::service::products","span": 
    {"method":"POST","uri":"/api/v1/products","request_id":"3f0c…","name":"http"}}
```

运行时二选一的格式：开发用可读格式、生产用 JSON，两种层的类型不同，不能直接放进同一个match分支。用 .boxed() 把它们装箱成同一个 trait 对象（第 5.5 节）：
```rust
use tracing_subscriber::Layer;

let fmt_layer = match format {
    LogFormat::Json => fmt::layer().json().boxed(),
    LogFormat::Pretty => fmt::layer().boxed(),
};
tracing_subscriber::registry().with(fmt_layer).with(filter).init();
```

### 15.3.6 【精通】tracing 的工作原理与性能

每个 info! 宏展开后都有一个静态的调用点元数据（级别、模块、文件、行号、字段名）。订阅者第一次见到某个调用点时决定“是否感兴趣”，结果被缓存。之后级别被过滤掉的调用点只需要读一个原子变量就返回，几乎零开销。

字段值只有在事件真的被记录时才会被格式化，所以 debug!(?big_struct) 在 DEBUG 关闭时不会执行 Debug 格式化。

编译期还可以通过 tracing 的 feature（如 max_level_debug、release_max_level_info）彻底移除某些级别的代码。

span 的上下文存储在线程本地变量中；异步任务在不同线程间迁移时，Instrument 包装器负责在每次轮询时正确地进入和退出 span。

### 15.3.7 【进阶】HTTP 请求日志：TraceLayer 与请求 ID

tower-http 的 TraceLayer 为每个请求创建一个 span，并在请求开始、响应返回、失败时记录事件：
```text
tower-http = { version = "0.6", features = ["trace", "request-id"] }
```
```rust
use tower_http::trace::{DefaultOnResponse, TraceLayer};
use tracing::Level;

let trace = TraceLayer::new_for_http()
    // 响应日志用 INFO 级别（默认是 DEBUG）
    .on_response(DefaultOnResponse::new().level(Level::INFO));
```

请求 ID 是排查线上问题的关键：用户报告“下单失败”，客服拿到响应头里的请求 ID，开发者在日志平台一搜，这个请求经过的所有日志一目了然。tower-http 提供三个组件：

| 组件 | 作用 |
| --- | --- |
| SetRequestIdLayer::x_request_id(MakeRequestUuid) | 请求头中没有 x-request-id 时生成一个 UUID写入 |
| PropagateRequestIdLayer::x_request_id() | 把请求的 x-request-id 复制到响应头 |

| 组件 | 作用 |
| --- | --- |
| TraceLayer::make_span_with(...) | 在 span 中记录请求 ID |

中间件顺序很重要：生成 ID 必须在 Trace 之前（外层），否则 span 里拿不到 ID。用tower::ServiceBuilder 可以按“从外到内”的自然顺序书写（第 12.7 节）：
```rust
use tower::ServiceBuilder;

let middleware = ServiceBuilder::new()
    // 最外层：先生成请求 ID
    .layer(SetRequestIdLayer::x_request_id(MakeRequestUuid))
    // 然后创建请求 span（此时已经能读到 ID）
    .layer(trace)
    // 最后把 ID 写回响应头
    .layer(PropagateRequestIdLayer::x_request_id());
```

如果上游（网关、负载均衡器）已经带来了 x-request-id，SetRequestIdLayer 不会覆盖它，于是整条调用链共用同一个 ID--第 38 章的分布式追踪会把这个思想推广到 trace ID。

### 15.3.8 常见错误与解读

| 现象 / 报错 | 原因 | 修复 |
| --- | --- | --- |
| 什么日志都没有 | 没有安装订阅者，或过滤级别太高 | 在 main 开头初始化；检查RU ST_LOG |
| a global default trace dispatcher hasalready been set | 初始化了两次（常见于测试中） | 测试中用 try_init() 并忽略错误 |
| the trait `Value` is not implemented for `Product` | 字段值不是基础类型 | 加 ?（Debug）或 %（Display） |
| #[instrument] 报某参数没有实现 Debug | 参数会被自动记录 | skip(参数) |
| 日志中出现了密码、令牌 | 结构体派生了 Debug 并被记录 | skip 掉，或手动实现 Debug（15.2.6） |
| 异步代码中日志的 span 错乱 | span.enter() 跨越了.await | 改用 .instrument() |

## 15.4 validator：声明式校验

### 15.4.1 【入门】在结构体上声明规则
```text
validator = { version = "0.20", features = ["derive"] }
```
```rust
use serde::Deserialize;
use validator::Validate;

#[derive(Debug, Deserialize, Validate)]
struct RegisterRequest {
    #[validate(length(min = 3, max = 20, message = "用户名长度需为 3~20 个字符"))]
    username: String,

    #[validate(email(message = "邮箱格式不正确"))]
    email: String,

    #[validate(range(min = 13, max = 150))]
    age: u8,
}

fn main() {
    let req = RegisterRequest { username: "ab".into(), email: "not-an-email".into(), age: 8 };
    match req.validate() {
        Ok(()) => println!("通过"),
        Err(errors) => println!("{errors}"),
    }
}
```

validate() 返回 Result&lt;(), ValidationErrors&gt;，一次性收集所有字段的错误，而不是遇到第一个就返回--这对表单类接口很友好，前端可以把每个字段的错误同时标红。

### 15.4.2 【进阶】常用规则

| 规则 | 说明 |
| --- | --- |
| length(min, max, equal) | 字符串（按字符计数）、Vec 等的长度 |
| range(min, max, exclusive_min, exclusive_max) | 数值范围 |
| email / url | 邮箱、URL 格式 |
| contains(pattern = "x") / does_not_contain(pattern = "x") | 包含 / 不包含子串 |
| must_match(other = "password") | 两个字段相等（确认密码） |
| regex(path = *RE) | 正则（需要 regex crate 与一个 LazyLock&lt;Regex&gt;静态变量） |

| 规则 | 说明 |
| --- | --- |
| custom(function = "my_fn") | 自定义函数：fn my_fn(v: &amp;str) -&gt; Result&lt;(), V alidationError&gt; |
| nested | 递归校验嵌套的结构体 |
| required | Option 字段必须为 Some |

每个规则都可以加 message = "..." 自定义消息、code = "..." 自定义错误码。Option&lt;T&gt; 字段的规则只在值为 Some 时检查。

### 15.4.3 【进阶】读取错误详情
```text
if let Err(errors) = req.validate() {
    // field_errors()：字段名 → 该字段的错误列表
    let mut fields: Vec<_> = errors.field_errors().into_iter().collect();
    // HashMap 无序：排序后输出才稳定（第 6.3 节）
    fields.sort_by(|a, b| a.0.cmp(&b.0));
    for (field, errs) in fields {
        for e in errs {
            // code 是规则名（如 "length"），message 是自定义消息
            println!("{field}: {} {:?}", e.code, e.message);
        }
    }
}
```

### 15.4.4 【精通】validator 与领域校验的分工

RustMall 已经有领域层的校验（Product::try_new、Quantity::try_new，第 3 章）。那还需要validator 吗？两者解决的问题不同：

|  | validator（HTTP 层） | 领域构造函数（领域层） |
| --- | --- | --- |
| 关注点 | 请求格式是否合理 | 业务不变量是否成立 |
| 错误收集 | 一次返回所有字段的错误 | 遇到第一个就返回 |
| 能否绕过 | 能：不经过 HTTP 的调用（后台任务、消息消费者）不会执行 | 不能：拿到 Product 就一定合法 |
| 例子 | 邮箱格式、分页参数范围、字段长度 | 价格不为负、状态转换合法 |

原则：领域层是唯一可信的防线，validator 是锦上添花的用户体验层。两者规则重叠时（例如商品名长度），领域层必须保留；validator 只是让用户一次看到所有错误。15.6 节会给商品接口加上 validator，并保留 NewProduct::try_new 的校验。

## 15.5 分层架构

### 15.5.1 【入门】三层各管什么

请求自上而下穿过三层，每层只依赖它下面的一层：

| 层 | 职责 | 知道什么 | 不知道什么 | 向下传递 |
| --- | --- | --- | --- | --- |
| HTTP 层（handler） | 解析请求、校验格式、调用服务、组装响应 | HTTP、JSON、状态码 | SQL、业务规则 | 领域类型（Product、ProductI d、命令对象） |
| 服务层（service） | 业务流程与规则：校验不变量、编排多个仓储、事务边界 | 领域模型、仓储 trait | HTTP、SQL | 仓储 trait 的方法调用 |
| 仓储层（repository） | 数据存取：SQL、行与领域对象的转换 | 数据库 | HTTP、业务流程 | - |
```text
HTTP 请求 ──► http::products ──► service::products ──► repo::ProductRepository ──► PostgreSQL
```

依赖方向只能向下：handler 依赖 service，service 依赖仓储的 trait（而不是具体的 PostgreSQL 实现）。服务层因此可以用一个内存实现来测试，几毫秒跑完，不需要数据库。

### 15.5.2 【进阶】为什么要多一层“服务层”

第 14 章的 handler 直接调用仓储，看起来也挺简洁。服务层的价值在后面的章节会越来越明显：

下单（第 26、29 章）要依次：检查商品、扣库存、创建订单、清购物车，并放在一个事务里。这些步骤写在 handler 里，HTTP 接口和将来的 gRPC 接口就要各写一遍。

缓存（第 18 章）：“先查 Redis、没有再查数据库并回填”属于业务策略，放在服务层，handler 和仓储都不用改。

测试：业务规则集中在服务层，可以脱离 HTTP 和数据库进行单元测试。

服务层的方法签名只使用领域类型和简单的“命令对象”，不出现 Json、StatusCode、PgPool。

### 15.5.3 【精通】异步仓储 trait 的写法

Rust 1.75 起可以在 trait 中直接写 async fn。但是对于 Web 服务，有一个关键问题：Axum 的处理函数返回的 Future 必须是 Send 的（Tokio 多线程运行时会在线程之间移动任务，第 11 章），而 trait 中的async fn 无法表达“返回的 Future 一定是 Send”。

解决办法是在 trait 中把返回类型写成 impl Future + Send，实现时仍然可以用 async fn：
```rust
use std::future::Future;

pub trait ProductRepository: Clone + Send + Sync + 'static {
    fn get(&self, id: ProductId) -> impl Future<Output = DomainResult<Product>> + Send;
}

impl ProductRepository for PgProductRepo {
    // 实现时写 async fn 即可；编译器会检查它返回的 Future 确实是 Send
    async fn get(&self, id: ProductId) -> DomainResult<Product> {
        // ……
    }
}
```

| 方案 | 写法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| impl Future + Send（本书采用） | 如上 | 零开销，无额外依赖 | trait 不能做成 dyn ProductReposito ry |
| async-trait crate | #[async_trai t] 宏 | 支持 dyn，老项目常见 | 每次调用一次堆分配 |
| 纯 async fn in trait | 不写 Send | 最简洁 | 无法保证 Send，在 Axum 中会遇到难懂的编译错误 |

不能做成 dyn 怎么办？用泛型：ProductService&lt;R: ProductRepository&gt;。具体类型在 main中确定一次（ProductService&lt;PgProductRepo&gt;），测试中换成ProductService&lt;InMemoryProductRepo&gt;。这就是第 5.2 节的单态化--没有任何运行时开销。

### 15.6.3 第 2 步：common 新增 NewProduct

文件：rustmall/common/src/product.rs。在 impl Product { ... } 块之后、#[cfg(test)]mod tests 之前加入：

```rust
/// 尚未分配 ID 的商品：新增商品时使用。
///
/// 校验规则与 [`Product::try_new`] 完全相同；ID 由存储层分配后，
/// 通过 [`NewProduct::into_product`] 成为正式商品。
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct NewProduct {
    name: String,
    price_cents: i64,
    stock: i32,
}

impl NewProduct {
    /// 校验并创建。复用 `Product::try_new`，规则只写在一个地方。
    pub fn try_new(name: &str, price_cents: i64, stock: i32) -> Result<Self, String> {
        let checked = Product::try_new(ProductId::new(0), name, price_cents, stock)?;
        Ok(Self {
            name: checked.name,
            price_cents: checked.price_cents,
            stock: checked.stock,
        })
    }

    pub fn name(&self) -> &str {
        &self.name
    }

    pub fn price_cents(&self) -> i64 {
        self.price_cents
    }

    pub fn stock(&self) -> i32 {
        self.stock
    }

    /// 分配 ID，成为正式商品。字段已经校验过，不需要再次校验。
    pub fn into_product(self, id: ProductId) -> Product {
        Product {
            id,
            name: self.name,
            price_cents: self.price_cents,
            stock: self.stock,
        }
    }
}
```

在同一文件的 mod tests 末尾追加两个测试：
```rust
#[test]
fn new_product_uses_the_same_rules() {
    assert!(NewProduct::try_new("   ", 100, 1).is_err());
    assert!(NewProduct::try_new("键盘", -1, 1).is_err());
    let draft = NewProduct::try_new("  键盘 ", 100, 2).unwrap();
    assert_eq!(draft.name(), "键盘");
}

#[test]
fn new_product_becomes_product_with_id() {
    let product = NewProduct::try_new("键盘", 100, 
        2).unwrap().into_product(ProductId::new(7));
    assert_eq!(product.id(), ProductId::new(7));
    assert_eq!((product.name(), product.price_cents(), product.stock()), ("键盘", 100, 2));

```

为什么能直接访问 checked.name：Product 的字段是私有的，但私有性的边界是模块（第 8.2 节）。NewProduct 与 Product 在同一个模块里，可以互相访问私有字段；模块外的代码仍然只能通过构造函数。内部用 0 作为占位 ID 只是为了复用校验，它被封装在这一个函数里，调用方再也看不到“占位 ID”这个概念。

```rust
/// 隐藏连接字符串中的账号与密码：`postgres://u:p@host/db` → `postgres://***@host/db`。
```

代码精讲：

模块为什么叫 settings 而不是 config：monolith 依赖了名为 config 的外部 crate。如果自己的模块也叫 config，在某些位置写 use config::... 时编译器会报“名称有歧义”（E0659）。换一个名字最省心。

默认配置目录 concat!(env!("CARGO_MANIFEST_DIR"), "/config")：env! 在编译期读取Cargo设置的环境变量，得到 monolith/Cargo.toml 所在目录的绝对路径。这样无论你在workspace 根目录还是 monolith 目录运行 cargo run，都能找到配置文件（15.2.7 节第一个坑）。部署到容器中时，二进制已经不在编译它的机器上，用 APP_CONFIG_DIR 指定实际目录（第20 章）。

两类错误分开：Load 是“读不出来或类型不对”（文件缺失、format = "xml" 无法解析为枚举），Invalid 是“读出来了但值不合理”（端口为 0）。#[from] 让 ? 自动转换（第 4.5 节）。

#[validate(nested)]：让 Settings::validate() 递归校验子结构。没有校验规则的LogSettings、CorsSettings 不需要派生 Validate，也不需要标注。

测试不碰磁盘和环境变量：环境变量是进程全局的，测试默认并行运行，一个测试设置的变量会影响另一个测试，结果时好时坏。所以测试通过 include_str!（编译期把文件内容嵌入为字符串）加File::from_str 构造来源，直接调用 from_builder。“加载逻辑”与“来源”分离，是让代码可测试的常用手法。

redact_url 中的 rfind('@')：密码中可能出现 @（URL 编码前），从右往左找最后一个 @更稳妥。

```rust
//! 仓储层：数据的存取。服务层只依赖这里的 trait，不依赖具体数据库。

pub mod products;

use std::future::Future;

use common::error::DomainResult;
use common::ids::ProductId;
use common::product::{NewProduct, Product};

/// 商品仓储。
///
/// 返回类型写成 `impl Future + Send` 而不是 `async fn`：保证返回的 Future 可以在线程间移动，
/// Axum 处理函数才能调用它（第 15.5.3 节）。实现时仍然可以直接写 `async fn`。
pub trait ProductRepository: Clone + Send + Sync + 'static {
    /// 新增商品，ID 由存储分配。
    fn insert(&self, draft: &NewProduct) -> impl Future<Output = DomainResult<Product>> + 
        Send;

    /// 按 ID 查询在售商品；不存在或已下架时返回“不存在”。
    fn get(&self, id: ProductId) -> impl Future<Output = DomainResult<Product>> + Send;

    /// 按创建时间倒序分页列出在售商品，并返回在售商品总数。
    fn list(&self, limit: i64, offset: i64) -> impl Future<Output = 
        DomainResult<(Vec<Product>, i64)>> + Send;

    /// 整体替换在售商品的可修改字段。
    fn update(&self, product: &Product) -> impl Future<Output = DomainResult<Product>> + Send;

    /// 下架商品。
    fn delist(&self, id: ProductId) -> impl Future<Output = DomainResult<()>> + Send;
}
```

Clone + Send + Sync + 'static 这组约束的来源：服务要放进 AppState，AppState 要能克隆（第12.6 节）、能在线程间共享，并且不能借用任何局部数据。

```rust
//! 商品仓储的 PostgreSQL 实现。
//!
//! 只有在售商品（`delisted_at IS NULL`）对外可见：下架的商品在查询、修改、再次下架时
//! 都表现为“不存在”。
use common::error::{DomainError, DomainResult};
use common::ids::ProductId;
use common::product::{NewProduct, Product};
use sqlx::PgPool;
use tracing::instrument;

use super::ProductRepository;
use crate::db;

/// 实体名称，用于“不存在”错误信息。
const ENTITY: &str = "商品";

/// 数据库中的一行商品，字段与 SELECT / RETURNING 的列一一对应。
#[derive(Debug, sqlx::FromRow)]
struct ProductRow {
    id: i64,
    name: String,
    price_cents: i64,
    stock: i32,
}

impl ProductRow {
    /// 行 → 领域对象。依然经过 `Product::try_new`，商品的不变量在任何来源下都成立。
    fn into_product(self) -> DomainResult<Product> {
        let id = self.id;
        Product::try_new(ProductId::new(id), &self.name, self.price_cents, self.stock)
            .map_err(|reason| DomainError::Internal(format!("数据库中的商品 {id} 不满足不变量：{reason}")))
    }
}

/// 商品仓储。内部只有一个连接池，克隆的代价是一次引用计数加一。
#[derive(Debug, Clone)]
pub struct PgProductRepo {
    pool: PgPool,
}

impl PgProductRepo {
    pub fn new(pool: PgPool) -> Self {
        Self { pool }
    }
}

impl ProductRepository for PgProductRepo {
    #[instrument(level = "debug", skip_all)]
    async fn insert(&self, draft: &NewProduct) -> DomainResult<Product> {
        sqlx::query_as::<_, ProductRow>(
            "INSERT INTO products (name, price_cents, stock) VALUES ($1, $2, $3) \
             RETURNING id, name, price_cents, stock",
        )
        .bind(draft.name())
        .bind(draft.price_cents())
        .bind(draft.stock())
        .fetch_one(&self.pool)
        .await
        .map_err(db::to_domain)?
        .into_product()
    }

    #[instrument(level = "debug", skip(self))]
    async fn get(&self, id: ProductId) -> DomainResult<Product> {
        sqlx::query_as::<_, ProductRow>(
            "SELECT id, name, price_cents, stock FROM products \
             WHERE id = $1 AND delisted_at IS NULL",
        )
        .bind(id.get())
        .fetch_optional(&self.pool)
        .await
        .map_err(db::to_domain)?
        .ok_or_else(|| DomainError::not_found(ENTITY, id))?
        .into_product()
    }

    #[instrument(level = "debug", skip(self))]
    async fn list(&self, limit: i64, offset: i64) -> DomainResult<(Vec<Product>, i64)> {
        let rows = sqlx::query_as::<_, ProductRow>(
            "SELECT id, name, price_cents, stock FROM products \
             WHERE delisted_at IS NULL \
             ORDER BY created_at DESC, id DESC \
             LIMIT $1 OFFSET $2",
        )
        .bind(limit)
        .bind(offset)
        .fetch_all(&self.pool);

        let total = sqlx::query_scalar::<_, i64>("SELECT count(*) FROM products WHERE delisted_at IS NULL")
            .fetch_one(&self.pool);

        // 两条查询互不依赖：并发执行，各自从池中借一个连接
        let (rows, total) = tokio::try_join!(rows, total).map_err(db::to_domain)?;

        let items = rows
            .into_iter()
            .map(ProductRow::into_product)
            .collect::<DomainResult<Vec<_>>>()?;
        Ok((items, total))
    }

    #[instrument(level = "debug", skip_all, fields(product_id = %product.id()))]
    async fn update(&self, product: &Product) -> DomainResult<Product> {
        sqlx::query_as::<_, ProductRow>(
            "UPDATE products SET name = $2, price_cents = $3, stock = $4, updated_at = now() \
             WHERE id = $1 AND delisted_at IS NULL \
             RETURNING id, name, price_cents, stock",
        )
        .bind(product.id().get())
        .bind(product.name())
        .bind(product.price_cents())
        .bind(product.stock())
        .fetch_optional(&self.pool)
        .await
        .map_err(db::to_domain)?
        .ok_or_else(|| DomainError::not_found(ENTITY, product.id()))?
        .into_product()
    }

    #[instrument(level = "debug", skip(self))]
    async fn delist(&self, id: ProductId) -> DomainResult<()> {
        let result = sqlx::query(
            "UPDATE products SET delisted_at = now(), updated_at = now() \
             WHERE id = $1 AND delisted_at IS NULL",
        )
        .bind(id.get())
        .execute(&self.pool)
        .await
        .map_err(db::to_domain)?;

        if result.rows_affected() == 0 {
            return Err(DomainError::not_found(ENTITY, id));
        }
        Ok(())
    }
}
```

与第 14 章相比：方法从 impl PgProductRepo 移到了 impl ProductRepository forPgProductRepo；insert 接收 &amp;NewProduct；每个方法加了 DEBUG 级别的 span（RUST_LOG=monolith=debug 时能看到每次仓储调用及耗时）。SQL 一个字没变。

#[instrument] 不加 err 的原因：err 会把每个 Err 记录为 ERROR。而“商品不存在”是正常的业务结果，会在每次 404 时产生一条 ERROR 日志，淹没真正的问题。错误日志统一由 HTTP 层的ApiError 按错误分类决定（15.6.9 节）。

```rust
        info!(product_id = %product.id(), "商品已创建");

            let product = draft.clone().into_product(ProductId::new(*next));
            self.items.lock().unwrap().push(product.clone());
            Ok(product)
        }

        async fn get(&self, id: ProductId) -> DomainResult<Product> {
            let items = self.items.lock().unwrap();
            items.iter().find(|p| p.id() == id).cloned().ok_or_else(|| 
                DomainError::not_found("商品", id))
        }

        async fn list(&self, limit: i64, offset: i64) -> DomainResult<(Vec<Product>, i64)> {
            let items = self.items.lock().unwrap();
            let total = i64::try_from(items.len()).unwrap();
            let page = items
                .iter()
                .rev()
                .skip(usize::try_from(offset).unwrap())
                .take(usize::try_from(limit).unwrap())
                .cloned()
                .collect();
            Ok((page, total))
        }

        async fn update(&self, product: &Product) -> DomainResult<Product> {
            let mut items = self.items.lock().unwrap();
            let slot = items
                .iter_mut()
                .find(|p| p.id() == product.id())
                .ok_or_else(|| DomainError::not_found("商品", product.id()))?;
            *slot = product.clone();
            Ok(product.clone())
        }

        async fn delist(&self, id: ProductId) -> DomainResult<()> {
            let mut items = self.items.lock().unwrap();
            let before = items.len();
            items.retain(|p| p.id() != id);
            if items.len() == before {
                return Err(DomainError::not_found("商品", id));
            }
            Ok(())
        }
    }
```

```rust
//! HTTP 层的统一错误：把领域错误和请求解析错误转换为 `{code, message}` 响应。

use axum::http::StatusCode;
use axum::response::{IntoResponse, Response};
use axum::Json;
use common::error::{DomainError, ErrorKind};
use serde::Serialize;

/// 错误响应体，格式见 `docs/api-v1.md` 第 2 节。
#[derive(Debug, Serialize)]
pub struct ErrorBody {
    pub code: &'static str,
    pub message: String,
}

/// 处理函数返回的错误类型。
#[derive(Debug)]
pub enum ApiError {
    /// 请求无法解析：JSON 语法错误、缺少 Content-Type 等
    BadRequest(String),
    /// 请求体结构不符合要求：缺少字段、类型不对、取值不合法、存在未知字段
    Unprocessable(String),
    /// 领域层返回的错误
    Domain(DomainError),
}

impl From<DomainError> for ApiError {
    fn from(e: DomainError) -> Self {
        ApiError::Domain(e)
    }
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, code, message) = match self {
            ApiError::BadRequest(message) => (StatusCode::BAD_REQUEST, "BAD_REQUEST", 
                message),
            ApiError::Unprocessable(message) => {
                (StatusCode::UNPROCESSABLE_ENTITY, ErrorKind::InvalidInput.code(), message)
            }
            ApiError::Domain(e) => {
                let kind = e.kind();
                let status = match kind {
                    ErrorKind::InvalidInput => StatusCode::UNPROCESSABLE_ENTITY,
                    ErrorKind::NotFound => StatusCode::NOT_FOUND,
                    ErrorKind::Conflict => StatusCode::CONFLICT,
                    ErrorKind::Internal => StatusCode::INTERNAL_SERVER_ERROR,
                };
                let message = if kind == ErrorKind::Internal {
                    // 内部错误的细节只进日志（带上当前请求 span 的请求 ID），绝不返回给客戶端
                    tracing::error!(error = ?e, "内部错误");
                    "服务器内部错误".to_string()
                } else {
                    e.to_string()
                };
                (status, kind.code(), message)
            }
        };
        (status, Json(ErrorBody { code, message })).into_response()
    }
}
```

```rust
//! 自定义提取器：
//! - `AppJson`：与 `axum::Json` 用法相同，解析失败时返回统一格式的错误；
//! - `ValidJson`：在 `AppJson` 的基础上再执行 `validator` 校验。

use axum::extract::rejection::JsonRejection;
use axum::extract::{FromRequest, Request};
use axum::response::{IntoResponse, Response};
use serde::de::DeserializeOwned;
use serde::Serialize;
use validator::{Validate, ValidationErrors};

use crate::http::error::ApiError;

/// 与 `axum::Json` 用法相同，但提取失败时返回 [`ApiError`]。
#[derive(Debug, FromRequest)]
#[from_request(via(axum::Json), rejection(ApiError))]
pub struct AppJson<T>(pub T);

impl<T: Serialize> IntoResponse for AppJson<T> {
    fn into_response(self) -> Response {
        axum::Json(self.0).into_response()
    }
}

impl From<JsonRejection> for ApiError {
    fn from(rejection: JsonRejection) -> Self {
        match rejection {
            // 语法正确但不符合目标类型：缺少字段、类型错误、try_from 校验失败、未知字段
            JsonRejection::JsonDataError(e) => ApiError::Unprocessable(e.body_text()),
            // 其余：JSON 语法错误、缺少 Content-Type、读取请求体失败
            other => ApiError::BadRequest(other.body_text()),
        }
    }
}
/// 解析 JSON 并执行 `Validate` 校验；校验失败时一次性返回所有字段的错误（422）。
#[derive(Debug)]
pub struct ValidJson<T>(pub T);

impl<T, S> FromRequest<S> for ValidJson<T>
where
    T: DeserializeOwned + Validate,
    S: Send + Sync,
{
    type Rejection = ApiError;

    async fn from_request(req: Request, state: &S) -> Result<Self, Self::Rejection> {
        let AppJson(value) = AppJson::<T>::from_request(req, state).await?;
        value.validate().map_err(|errors| ApiError::Unprocessable(describe(&errors)))?;
        Ok(ValidJson(value))
    }
}

/// 把校验错误整理成一行可读文字，例如 `name：长度需为 1~100 个字符；price_cents：不能为负数`。
fn describe(errors: &ValidationErrors) -> String {
    let mut parts = Vec::new();
    for (field, errs) in errors.field_errors() {
        for e in errs {
            let detail = e.message.as_deref().unwrap_or(&e.code);
            parts.push(format!("{field}：{detail}"));
        }
    }
    // field_errors() 是 HashMap，顺序不固定；排序让同样的请求总是得到同样的消息
    parts.sort();
    parts.join("；")
}
```

```rust
//! 路由表与全局中间件。

use axum::extract::{DefaultBodyLimit, Request};
use axum::http::{header, HeaderName, HeaderValue, Method, StatusCode};
use axum::routing::get;
use axum::{Json, Router};
use tower::ServiceBuilder;
use tower_http::cors::{AllowOrigin, CorsLayer};
use tower_http::request_id::{MakeRequestUuid, PropagateRequestIdLayer, SetRequestIdLayer};
use tower_http::trace::{DefaultOnResponse, TraceLayer};
use tracing::Level;

use crate::http::error::ErrorBody;
use crate::http::{health, products};
use crate::settings::CorsSettings;
use crate::state::AppState;

/// 请求体大小上限：64 KB。商品、订单等 JSON 请求远小于这个值。
pub const MAX_BODY_BYTES: usize = 64 * 1024;

/// 请求 ID 所在的请求头 / 响应头。
const REQUEST_ID: HeaderName = HeaderName::from_static("x-request-id");

/// 构建完整的应用路由。测试与 main 共用同一个函数，保证测试的就是线上的路由。
pub fn router(state: AppState, cors: &CorsSettings) -> Router {
    let api = Router::new()
        .route("/products", get(products::list).post(products::create))
        .route(
            "/products/{id}",
            get(products::get_one).put(products::update).delete(products::remove),
        );

    // ServiceBuilder 中写在上面的层在外层，请求按从上到下的顺序经过
    let middleware = ServiceBuilder::new()
        // 1. 生成请求 ID（请求已带 x-request-id 时保留原值）
        .layer(SetRequestIdLayer::new(REQUEST_ID, MakeRequestUuid))
        // 2. 为每个请求创建 span，并记录响应状态与耗时
        .layer(
            TraceLayer::new_for_http()
                .make_span_with(make_span)
                .on_response(DefaultOnResponse::new().level(Level::INFO)),
        )
        // 3. 把请求 ID 写回响应头
        .layer(PropagateRequestIdLayer::new(REQUEST_ID))
        // 4. 跨域
        .layer(cors_layer(cors))
        // 5. 请求体大小限制
        .layer(DefaultBodyLimit::max(MAX_BODY_BYTES));

    Router::new()
        .route("/health/live", get(health::live))
        .route("/health/ready", get(health::ready))
        .nest("/api/v1", api)
        .fallback(not_found)
        .layer(middleware)
        .with_state(state)
}

/// 请求 span：方法、路径与请求 ID。之后该请求内产生的所有日志都带有这些字段。
fn make_span(request: &Request) -> tracing::Span {
    let request_id = request
        .headers()
        .get(&REQUEST_ID)
        .and_then(|v| v.to_str().ok())
        .unwrap_or("-");
    tracing::info_span!("http", method = %request.method(), uri = %request.uri(), request_id)
}

/// 按配置构造 CORS 中间件：只允许列出的来源。
fn cors_layer(settings: &CorsSettings) -> CorsLayer {
    let origins: Vec<HeaderValue> = settings
        .allowed_origins
        .iter()
        .filter_map(|origin| match origin.parse() {
            Ok(value) => Some(value),
            Err(_) => {
                tracing::warn!(%origin, "忽略无法解析的 CORS 来源");
                None
            }
        })
        .collect();

    CorsLayer::new()
        .allow_origin(AllowOrigin::list(origins))
        .allow_methods([Method::GET, Method::POST, Method::PUT, Method::DELETE])
        .allow_headers([header::CONTENT_TYPE, header::AUTHORIZATION])
        // 让前端 JavaScript 能读取这两个响应头
        .expose_headers([REQUEST_ID, header::LOCATION])
}

/// 未匹配任何路由时，也返回统一格式的错误。
async fn not_found() -> (StatusCode, Json<ErrorBody>) {
    let body = ErrorBody { code: "NOT_FOUND", message: "接口不存在".to_string() };
    (StatusCode::NOT_FOUND, Json(body))
}
```

```rust
//! 停机信号处理。

use tokio_util::sync::CancellationToken;

/// 等待 Ctrl+C（所有平台）或 SIGTERM（Unix），收到任一信号后取消 `token`。
///
/// 本地开发按 Ctrl+C 发送的是 SIGINT；Docker 停止容器、Kubernetes 删除 Pod 时发送的是 SIGTERM。
/// 某个信号无法监听时只记录错误并忽略它，另一个信号仍然有效。
pub async fn wait_for_signal(token: CancellationToken) {
    let ctrl_c = async {
        if let Err(e) = tokio::signal::ctrl_c().await {
            tracing::error!(error = %e, "无法监听 Ctrl+C");
            std::future::pending::<()>().await;
        }
    };

    #[cfg(unix)]
    let terminate = async {
        match tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate()) {
            Ok(mut sig) => {
                sig.recv().await;
            }
            Err(e) => {
                tracing::error!(error = %e, "无法监听 SIGTERM");
                std::future::pending::<()>().await;
            }
        }
    };

    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        () = ctrl_c => {}
        () = terminate => {}
    }
    tracing::info!("收到停机信号，开始优雅停机");
    token.cancel();
}
```

```rust
//! RustMall 单体服务入口：配置 → 日志 → 数据库 → 组装 → 运行 → 停机。

use std::time::Duration;

use anyhow::Context;
use monolith::settings::Settings;
use monolith::state::AppState;
use monolith::{background, db, http, shutdown, telemetry};
use tokio_util::sync::CancellationToken;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // 0. 本地开发：加载 .env（文件不存在时忽略；已存在的环境变量不会被覆盖）
    dotenvy::dotenv().ok();

    // 1. 配置。此时日志系统还没有初始化，失败时由 anyhow 把错误打印到标准错误
    let settings = Settings::load().context("加载配置失败")?;

    // 2. 日志
    telemetry::init(&settings.log).context("初始化日志失败")?;
    tracing::info!(?settings, "配置已加载");

    // 3. 数据库
    let pool = db::connect(&settings.database).await.context("连接数据库失败")?;
    db::MIGRATOR.run(&pool).await.context("执行数据库迁移失败")?;
    tracing::info!("数据库已连接，迁移已是最新");

    // 4. 信号处理与后台任务
    let token = CancellationToken::new();
    tokio::spawn(shutdown::wait_for_signal(token.clone()));

    let cleaner = tokio::spawn(background::run_periodic(
        Duration::from_secs(60),
        token.clone(),
        || async { tracing::debug!("清理过期的购物车") },
    ));

    // 5. HTTP 服务
    let app = http::routes::router(AppState::new(pool.clone()), &settings.cors);
    let addr = settings.server.addr();
    let listener = tokio::net::TcpListener::bind(&addr)
        .await
        .with_context(|| format!("绑定地址 {addr} 失败"))?;
    tracing::info!(%addr, "RustMall 单体服务已启动");

    axum::serve(listener, app)
        .with_graceful_shutdown(token.clone().cancelled_owned())
        .await
        .context("HTTP 服务异常退出")?;
    tracing::info!("HTTP 服务已停止，等待后台任务结束");

    // 6. 停机
    let grace = settings.server.shutdown_grace();
    match tokio::time::timeout(grace, cleaner).await {
        Ok(Ok(runs)) => tracing::info!(runs, "后台任务已停止"),
        Ok(Err(e)) => tracing::error!(error = %e, "后台任务异常退出"),
        Err(_) => tracing::warn!(?grace, "后台任务未能按时停止，强制退出"),
    }

    pool.close().await;
    tracing::info!("数据库连接池已关闭，服务退出");
    Ok(())
}
```

### 15.6.14 常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 加载配置失败 … configuration file ".../config/default" not found | 设置了错误的 APP_CONFIG_DIR | 取消该变量，或指向包含defa ult.toml 的目录 |
| 改了 .env 不生效 | 终端中已经 export 了同名变量，.env 不会覆盖它 | unset 该变量，或直接修改环境变量 |
| APP_SERVER_PORT=9000 不生效 | 层级之间要用双下划线 | APP_SERVER__PORT=9000 |

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 启动报 初始化日志失败 | log.level / RUST_LOG 的过滤表达式写错 | 对照 15.3.5 节的语法 |
| no method named 'get' found for struct 'PgProductRepo' | 调用 trait 方法时 trait 不在作用域 | use monolith::repo::ProductRepository; |
| future cannot be sent betweenthreads safely，指向某个仓储实现 | 实现中在 .await 期间持有了非Send 的值（如std::sync::MutexGuar d） | 在 await 之前释放锁，或改用tokio::sync::Mutex（第11章） |
| 浏览器报 CORS 错误 | 前端地址不在cors.allowed_origi ns 中 | 修改配置；注意协议、域名、端口都要完全一致 |
| E0659 'config' is ambiguous | 自己的模块与外部 crate 同名 | 本书已命名为 settings，避免同名 |

### 15.6.15 本章小结

配置：默认文件 → 环境文件 → 环境变量，后者覆盖前者；用强类型和 validator 在启动时校验，失败即退出；.env 只用于本地开发；包含密码的配置手动实现 Debug。

日志：tracing 埋点、tracing-subscriber 输出；把变化的数据放进字段；用 span 关联同一请求的日志；异步代码用 .instrument() 或 #[instrument]；开发用可读格式，生产用JSON。

请求 ID：SetRequestIdLayer 生成、TraceLayer 记录、PropagateRequestIdLayer 返回，排查线上问题的第一线索。

校验分工：validator 负责“一次返回所有格式问题”，领域构造函数负责不变量，后者不可省略。

分层：HTTP 层只做转换，服务层表达业务，仓储层只管存取；依赖指向 trait；异步 trait 写成 implFuture + Send；具体类型只在组合根 AppState 中出现一次。

下一章是第 16 章“认证与授权”：用 argon2 存储密码哈希，用 JWT 签发访问令牌，实现注册、登录接口，用提取器从请求中识别当前用户，并给商品管理接口加上“仅管理员”的权限检查；secrecy crate会把密码、密钥包装成“不会被意外打印”的类型。

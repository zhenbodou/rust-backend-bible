# 第 23 章 Kubernetes：理解控制循环，再运行 RustMall

第 22 章回答了“一个镜像从哪次提交来、经过什么检查”。本章继续回答运行阶段的问题：怎样声明两个应用副本，进程退出后由谁补建，地址改变后请求怎样找到服务，数据库暂时不可用时应摘流量还是重启应用。

我们先用一个小实验理解 Kubernetes 的对象与控制循环，再将同一个 RustMall 单体放入隔离教学集群。业务接口与数据库模型保持不变；新增的是迁移命令、严格的迁移开关和共享停机预算。学完后，应能沿着 Deployment、ReplicaSet、Pod、Service 与数据库逐层排查，而不是遇到问题就反复删除 Pod。

## 23.1 先建立对象与控制循环的认识

### 23.1.1 【入门】集群不是一个更长的 docker run

Kubernetes 管理一组机器上的工作负载。你向 API 提交期望状态，控制器持续观察实际状态并尝试缩小差异。例如声明两个副本，其中一个 Pod 消失后，控制器会补建，而不需要你再次手工执行启动命令。

这里最重要的变化是“持续协调”。提交命令成功只表示请求被接收或对象被更新，不表示镜像已下载、进程已启动、业务已就绪。后面的查看状态与等待命令，就是用来观察协调结果，不能省略。

### 23.1.2 【入门】控制平面与工作节点

控制平面保存对象、处理 API 请求、执行调度与控制逻辑；工作节点运行承载应用的 Pod。kubelet 在节点上协调容器运行，容器运行时负责实际创建进程环境。kubectl 是 API 客户端，不是运行应用的服务器。

本章使用本地 kind 集群，节点本身运行在容器环境中，便于学习。生产集群还涉及控制平面可用性、节点维护、网络、存储和权限管理。把本地实验跑通，是理解对象的起点，不等于已经设计了生产集群。

### 23.1.3 【入门】Pod 是调度与生命周期边界

Pod 包含一个或多个需要共同调度的容器及相关配置；同一 Pod 内容器共享相应网络环境。一个 Pod 里的 localhost 指向该 Pod 的网络，和第 21 章中各自独立容器的 localhost 位置不同。

本章每个应用 Pod 只有一个 monolith 容器。不要为了减少 YAML 就把数据库、Redis 和应用全部放到一个 Pod。它们的扩容、升级与数据生命周期不同，绑定在一起会让其中一方重建时牵动所有角色。

### 23.1.4 【进阶】Deployment、ReplicaSet 与 Pod 的关系

Deployment 描述应用副本与更新策略，ReplicaSet 维持某一套 Pod 模板的副本数量，Pod 是最终实例。更新模板时，Deployment 通常通过新旧 ReplicaSet 协调版本替换。

因此要持续运行应用，应修改 Deployment，而不是把管理中的某个 Pod 当作固定主机。直接进入容器改一个配置文件，可能只改变当前实例的临时层；下一次重建就消失，也没有进入审查历史。

### 23.1.5 【进阶】期望状态不会自动消除所有故障

控制器可以尝试补建，但节点容量不足、镜像拉取失败、卷不能挂载、权限不满足，都可能使期望长期无法实现。replicas: 2 表达希望有两个副本，不保证立即得到两个 Ready 实例。

这和 Rust 的 Result 类似：发起动作与获得期望结果不同。运维时需要看 status、事件和日志，把“协调正在进行”“无法继续协调”“业务启动后失败”分开，而不是把 apply 的成功当成最终结果。

### 23.1.6 【精通】声明式管理也需要确定所有者

若 Git 中声明两个副本，另一位同事手工 scale 到五个，而自动化工具随后又应用旧配置，最终数量可能回到二。冲突来自多个管理者同时修改同一字段，而不是 Kubernetes 忘记了某个命令。

本章先由命令行按序管理资源，下一章引入 Helm 与 GitOps 后再明确配置来源和变更入口。不要同时让多个工具互相覆盖同一套对象，然后用“最终一致”解释无法追踪的变化。

## 23.2 kubectl、小实验与对象身份

### 23.2.1 【入门】先确认客户端连接到哪里

安装 Docker、kind 和与服务端兼容的 kubectl，安装来源与当前平台支持以官方说明为准。进入空的实验目录，先查看工具与已有上下文；这些查看命令不会创建业务资源。
```bash
kind version
kubectl version --client
kubectl config current-context
kubectl config get-contexts
```

context 关联集群地址、身份与默认命名空间。不要根据终端标题猜测目标。后面的命令显式指定 kind-rustmall-book，避免另一窗口切换上下文后误操作已有集群。

### 23.2.2 【入门】创建隔离本地集群

确认 Docker 可用且有足够空闲资源后执行：
```bash
kind create cluster --name rustmall-book
kubectl --context kind-rustmall-book get nodes
kubectl --context kind-rustmall-book version
```

预期能看到节点，并等待其 Ready。记录实际 kind、kubectl 与服务端版本，后续使用 apps/v1、batch/v1 等稳定 API，不根据书稿日期猜测“当前最新版”。若创建失败，先查 Docker、镜像下载与资源条件，不要立即重建其他集群。

### 23.2.3 【入门】先观察一个不涉及数据库的 Deployment

这个实验只使用官方 Nginx 镜像观察控制器，不属于 RustMall 的最终依赖。创建独立命名空间后执行：
```bash
kubectl --context kind-rustmall-book create namespace controller-lab
kubectl --context kind-rustmall-book -n controller-lab create deployment web --image=nginx:1.28-alpine --replicas=2
kubectl --context kind-rustmall-book -n controller-lab rollout status deployment/web --timeout=120s
kubectl --context kind-rustmall-book -n controller-lab get deployments,replicasets,pods
```

预期有一个 Deployment、相应 ReplicaSet 与两个可运行 Pod。名称后缀不应写死；若镜像无法下载，实验停在拉取阶段，并不证明控制器机制错误。describe 的事件会提供下一层线索。

### 23.2.4 【进阶】删除一个实例，观察补建

先列出 Pod，再把你自己刚刚看到的一个完整名称代入删除命令。只在 controller-lab 操作，不使用面向所有命名空间的删除。
```bash
kubectl --context kind-rustmall-book -n controller-lab get pods
kubectl --context kind-rustmall-book -n controller-lab delete pod <刚列出的一个Pod名称>
kubectl --context kind-rustmall-book -n controller-lab get pods -w
```

尖括号内容是需要替换的输入提示，不能原样执行。预期旧实例终止，另一个名称的新实例出现；观察完成按 Ctrl-C 退出 watch。删除 Pod 没有把 Deployment 的期望数量改为一，所以控制器继续补足两个。

### 23.2.5 【进阶】读懂 YAML 的四个入口

apiVersion 指定 API 组与版本，kind 指定对象种类，metadata 标识名称、命名空间和标签，spec 表达对象所需配置。status 通常由系统反馈，不能把服务器导出的整份 status 当作需要手工维护的输入。

Deployment 的 spec.template 又是一份 Pod 模板，其中的 metadata.labels 供选择器匹配。spec.selector.matchLabels 与模板标签不一致会出错；Service 的 selector 若写错，则可能创建成功却找不到后端。这两种失败发生在不同边界。

### 23.2.6 【精通】名字不是实例身份

Pod 被删除并以相同名称重建，也会拥有新的 UID；Deployment 管理下的新实例通常连名字也变化。Pod IP 更不能当作永久数据库地址写进代码。名称用于查找，UID 区分对象实例，控制器 ownerReferences 表达归属。

实验结束只删除独立命名空间：kubectl --context kind-rustmall-book delete namespace controller-lab。RustMall 将使用另一个命名空间，保留集群继续学习，不必为了结束小实验删掉整台本地集群。

## 23.3 Service、DNS 与请求真正经过的路径

### 23.3.1 【入门】为什么不能直接保存 Pod IP

Pod 是可替换实例，地址可能随重建变化。Service 为一组匹配选择器的后端提供稳定访问入口，调用者面向服务名与端口，而不是记住某次观察到的 Pod IP。

本章应用通过 postgres:5432 访问同命名空间的数据库 Service。虽然字符串和 Compose 相似，背后的资源与发现机制已经改变；Compose 网络不会因为名字相同就和 Kubernetes 网络连通。

### 23.3.2 【入门】port、targetPort 与 containerPort

Service 的 port 是客户端访问这个 Service 的端口，targetPort 指向后端容器的实际目标端口；containerPort 在 Pod 定义中描述容器端口，并可给予名字。它不会独自让程序开始监听。

RustMall 将容器端口命名 http，Service 的 targetPort 引用 http。应用仍须绑定 0.0.0.0:8080；若程序只监听 Pod 内的回环地址，写再多 containerPort 也不能使其他 Pod 访问它。

### 23.3.3 【进阶】selector 与 EndpointSlice

Service 的 selector 根据标签寻找后端，相关 EndpointSlice 保存后端地址及条件。排查请求不通时，应把 Service 配置与 EndpointSlice 一起看，而不是只确认 Service 对象存在。

例如 Service 选择 app=book-rustmall，而模板误写 app=rustmall，两个对象都可能存在，但没有你期待的匹配后端。再检查后端是否 Ready；匹配到了一个尚未就绪的 Pod，也不意味着它应立即接收正常业务流量。

### 23.3.4 【进阶】ClusterIP 与端口转发

ClusterIP 通常用于集群内部访问；本章不创建公网 LoadBalancer 或 Ingress。读者在本机使用 kubectl port-forward 进入服务，便于实验而不增加外部入口组件。
```bash
kubectl --context kind-rustmall-book -n rustmall-lab port-forward service/book-rustmall 58080:8080
```

保持该终端运行，在另一个终端访问 127.0.0.1:58080。端口转发会选择具体后端建立连接，不能用它证明 Service 负载分配、外部流量入口或跨节点网络都已验证；后端重建后可能需要重新建立转发。

### 23.3.5 【精通】拓扑中的四种 localhost

电脑上的 curl、kind 节点、应用 Pod、数据库 Pod 各有自己的网络位置。即使它们最终都运行在同一台笔记本里，也不能用同一个 localhost 地址互相替代。

本章拓扑是：本机请求经 port-forward 到一个应用 Pod，应用通过 postgres Service 访问数据库 Pod，数据库将数据写入挂载卷。先沿这条路径逐段确认，再判断 DNS、TCP、认证或 SQL 属于哪个阶段。

### 23.3.6 【精通】Service 不提供业务级重试

后端替换时可能有连接断开与观察传播延迟。Service 不知道一个创建订单请求是否已经落库，也不会自动替应用决定能否重试。幂等键、事务与恢复流程仍是业务责任。

不要因为拥有两个副本就假定所有失败都可以重发。一个请求在响应丢失前已经提交，客户端重试可能产生重复副作用；这个问题会在后面的库存与订单章节展开，本章先保留明确边界。

## 23.4 三类探针与故障的分类

### 23.4.1 【入门】Running 不等于能够接业务

Pod phase 为 Running，通常只表示已进入容器运行阶段的状态描述；应用可能仍在连接依赖，或正在反复重启。READY 列、容器状态与事件需要一起阅读。

RustMall 的 /health/live 用于判断进程是否仍能响应基本健康请求，/health/ready 通过应用连接路径检查必要依赖。把二者区分后，数据库短暂故障就不必自动解释为进程必须重建。

### 23.4.2 【入门】startupProbe 给启动过程单独预算

startupProbe 成功之前，相关 liveness 与 readiness 探测不会按正常阶段启动。本章用 /health/live 作为启动探针，给程序加载配置、连接数据库与绑定端口的过程一段有限等待。

failureThreshold 与 periodSeconds 可以帮助估计等待量级，但不能把乘积当成每种运行时都精确到秒的总截止时间。若程序卡在无法完成的初始化，最终仍应失败，而不是把阈值无限调大。

### 23.4.3 【进阶】readiness 控制是否适合接收流量

准备探针失败通常使 Pod 不再作为正常就绪后端使用，不意味着立刻重启容器。本章数据库不可用会影响准备状态，让应用尽量停止接收无法完成的业务请求。

传播不是零延迟，已有连接也可能仍在。因此程序仍要正确返回数据库错误，不能认为探针已替每一次请求兜底。readiness 是流量治理信号，不是事务一致性协议。

### 23.4.4 【进阶】liveness 失败可能导致重启

存活探针应该针对“重启本进程可能恢复”的问题。若把所有外部依赖检查都放进 liveness，数据库一断，所有应用副本同时重启，恢复时又并发建立连接，可能放大故障。

本章沿用 /health/live，不把数据库短暂不可用直接变成应用重启条件。这样做仍需结合实际故障模型：事件循环完全阻塞、进程无响应等情况可能需要重启；一个正常返回数据库错误的进程未必需要。

### 23.4.5 【精通】探针必须便宜且有界

高频探针若扫描业务表、执行复杂 JOIN 或等待无限长连接池，会成为额外负载源。准备检查应选择足够代表必要依赖、又不会明显扰动业务的动作，并设置合理的等待边界。

探针超时、连接池获取超时、数据库语句超时分别约束不同动作。Kubernetes 终止一次探测请求，不一定证明服务端所有关联工作立即停止；应用代码也需要有界等待与取消设计。

### 23.4.6 【精通】Dockerfile HEALTHCHECK 不替代 Pod 探针

第 20 章的 HEALTHCHECK 服务于相应容器工具的检查模型。Kubernetes 中应显式定义 startupProbe、readinessProbe 与 livenessProbe，不能因为镜像有 HEALTHCHECK 就认为三种条件已配置。

本章使用 HTTP 探针直接访问现有接口，保留镜像中的独立探针供 Compose 使用。同一程序可被不同运行平台检查，但每个平台的行为、失败后动作和时间设置都要分别理解。

## 23.5 资源、数据与配置生命周期

### 23.5.1 【入门】requests 与 limits

requests 用于调度时的资源需求判断，limits 约束运行中的资源使用。100m CPU 表示 0.1 个 CPU 的请求量，1 表示一个 CPU 的相应额度；128Mi 与 256Mi 使用二进制内存单位。

本章数值是教学起点，不是容量结论。若多个副本都能被调度却在流量下频繁 OOM，说明“调度成功”没有证明内存足够。应结合测量调整，并在后面的性能与可观测性章节解释工作负载特征。

### 23.5.2 【进阶】CPU 节流与内存终止

CPU 超限常体现为节流与延迟变化，内存超限可能导致 OOM 终止，两者不能用同一张“百分比高了”的图解释。排查重启时查看上次容器退出原因和事件，再判断是资源问题还是程序主动退出。

应用重启后内存暂时下降，也不证明泄漏已修复。测试应覆盖稳定负载与长时间趋势；暂时加大 limits 可以缓解容量不足，但需要说明实际原因和持续预算。

### 23.5.3 【入门】emptyDir、PVC 与数据保留

emptyDir 随 Pod 生命周期存在，适合本章的临时 /tmp；PVC 是对持久存储的申请，绑定的具体卷与存储类决定底层行为。应用 Pod 重建时不应该靠容器临时层保存数据库数据。

本章 PostgreSQL 使用单个 PVC 与单副本 Recreate Deployment，目的是让数据生命周期可观察。PVC 不自动提供备份、主从复制或跨可用区恢复；ReadWriteOnce 也不是防止同节点多个进程写坏数据库的完整锁协议。

### 23.5.4 【进阶】为什么实验数据库选择 Recreate

普通滚动更新可能使新旧实例短暂同时存在。对挂载同一数据库数据目录的单机实验，不能像无状态 HTTP 服务一样随便并行两份进程，因此本章用 Recreate，先停止旧实例再创建新实例。

代价是更新期间数据库可能不可用。这里没有把 Deployment 加 PVC 介绍成生产 PostgreSQL 的通用运维方案；生产需要评估托管数据库或专门的数据库编排、备份与故障切换机制。

### 23.5.5 【入门】ConfigMap 与 Secret

ConfigMap 保存非秘密配置，Secret 用于需要受权限控制的敏感数据。本章 ConfigMap 注入端口、停机时长与迁移开关，Secret 注入数据库 URL 和 JWT 秘密。

Secret 的编码不等于加密，也不是所有能读命名空间的人都天然应该读它。集群的静态加密、API 权限与运维访问策略需要另外配置。本章只建立正确的引用与不把秘密写进 Git 的习惯，不宣称默认集群已经满足生产密钥管理要求。

### 23.5.6 【进阶】环境变量不会自动刷新已有进程

通过环境注入的 ConfigMap 或 Secret 更新后，已启动进程不会因此自动获得新的变量。应明确执行受控重启并观察新 Pod 使用的配置。挂载文件的更新又有另外的传播与应用重载条件，不能与环境变量混为一谈。

本章继续使用镜像内已有 TOML 默认配置，通过环境覆盖少量部署差异，减少重复抄写完整配置。下一章再讨论配置版本如何触发发布以及 Helm 模板怎样表达这些差异。

### 23.5.7 【精通】减少应用不需要的集群权限

monolith 不调用 Kubernetes API，因此设置 automountServiceAccountToken: false。应用以非 root 身份运行，禁止提权、丢弃 capabilities，根文件系统只读，额外提供有限临时目录。

这些设置减少不必要能力，也可能暴露程序此前偷偷写入工作目录的假设。若启动出现 Permission denied，先确认程序到底要写什么，再提供必要挂载；不要为了快速变绿整体恢复 root 与可写根目录。

## 23.6 多副本前先处理迁移与停机

### 23.6.1 【入门】迁移与长期服务是两类工作

单体开发阶段启动时运行迁移很方便；多个副本同时发布时，把结构变更混在每个进程启动里，会使部署顺序、失败原因与权限边界难以观察。本章增加独立迁移命令，由 Job 先执行，应用副本设置迁移开关为 false。

这不意味着数据库迁移锁没有作用，也不意味着只要分离命令就绝对安全。迁移 SQL 仍需考虑旧程序兼容、锁等待与执行时间；本章先建立“迁移成功才继续应用发布”的显式操作顺序。

### 23.6.2 【进阶】严格解析开关，避免拼写错误静默生效

RUSTMALL_RUN_MIGRATIONS 只接受 true 或 false；未设置时保留前面本地与 Compose 的自动迁移行为。FALSE、空字符串等输入报错，而不是随意解释为某个默认值。

读取环境变量时，也区分未设置与无法转换成 Unicode 的异常。前面的普通业务配置已有相应错误传播习惯，这里继续通过 Result 与上下文把错误带到启动失败，不用 .ok() 把所有读取错误都变成“没有设置”。

### 23.6.3 【进阶】SIGTERM 到退出有一段过程

Kubernetes 终止 Pod 时有宽限期，preStop 也占用这段时间，然后程序收到停止信号并结束处理。RustMall 的停止路径要通知 HTTP 与后台任务，等待已有工作在预算内结束，最后关闭数据库连接池。

本章 Pod 宽限期设为 30 秒，preStop 暂停 3 秒，应用停机预算 20 秒，留出一定余量。三秒只是帮助观察传播窗口的实验值，不保证所有流量都已摘除。超时之后平台仍可能强制终止，因此持久化一致性不能依赖进程总能优雅退出。

### 23.6.4 【精通】一个总预算，避免每阶段重新计时

若 HTTP、后台任务和数据库关闭各等 20 秒，总等待可能超过外层 30 秒。ShutdownBudget 保存一个截止 Instant，后续 wait 都使用同一个 deadline，使已消耗的时间不被下一阶段重新补满。

例如 HTTP 用去 8 秒，总预算 10 秒时，数据库阶段只剩约 2 秒；它再申请等待 3 秒应超时。这个机制与第 20 章探针共享总截止时间的思路相同，只是这里处理异步 Future 与 Tokio 时间。

### 23.6.5 【精通】超时是协作取消，不是抢占执行

timeout_at 能限制会把控制权交回运行时的异步等待，但不能把一个永不 yield 的同步死循环按时抢占停止。Future 被丢弃后，独立 spawn 的任务也不会必然跟着消失，所以脚本显式保留并处理后台任务句柄。

因此停机设计仍需避免在异步任务中执行长时间阻塞工作，并为后台循环提供 CancellationToken。达到预算后 abort 是最后的进程内停止措施，不保证已经发往数据库或外部系统的动作被撤销。

### 23.6.6 【精通】为什么不能只 sleep 再退出

直接收到信号后 sleep 20 秒，看起来留下了时间，却没有表达停止接收、取消后台工作和等待已有请求的关系。若时间内继续接受新工作，结束时仍可能丢下正在执行的操作。

优雅停机是一个有状态的协议：发出取消信号，停止入口，等待已接工作，清理资源，再报告结果。超时与错误必须可见；不能为了退出状态漂亮，把所有 JoinError 或数据库关闭失败都吞掉。

```rust
use anyhow::{Context, Result};
use std::future::Future;
use std::time::Duration;
use tokio::time::{Instant, timeout_at};

pub fn migration_enabled(raw: Option<&str>) -> Result<bool> {
    match raw {
        None | Some("true") => Ok(true),
        Some("false") => Ok(false),
        Some(_) => anyhow::bail!("RUSTMALL_RUN_MIGRATIONS must be true or false"),
    }
}

pub struct ShutdownBudget {
    deadline: Instant,
}
impl ShutdownBudget {
    pub fn new(grace: Duration) -> Self {
        Self {
            deadline: Instant::now() + grace,
        }
    }
    pub async fn wait<F: Future>(&self, label: &str, future: F) -> Result<F::Output> {
        timeout_at(self.deadline, future)
            .await
            .with_context(|| format!("shutdown budget exhausted at {label}"))
    }
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn migration_switch_is_strict() {
        assert!(migration_enabled(None).unwrap());
        assert!(migration_enabled(Some("true")).unwrap());
        assert!(!migration_enabled(Some("false")).unwrap());
        assert!(migration_enabled(Some("FALSE")).is_err());
        assert!(migration_enabled(Some("")).is_err());
    }
    #[tokio::test(start_paused = true)]
    async fn stages_share_one_deadline() {
        let budget = ShutdownBudget::new(Duration::from_secs(10));
        budget
            .wait("http", tokio::time::sleep(Duration::from_secs(8)))
            .await
            .unwrap();
        assert!(
            budget
                .wait("database", tokio::time::sleep(Duration::from_secs(3)))
                .await
                .is_err()
        );
    }
    #[tokio::test(start_paused = true)]
    async fn completed_stages_return_their_result() {
        let budget = ShutdownBudget::new(Duration::from_secs(10));
        assert_eq!(budget.wait("stage", async { 42 }).await.unwrap(), 42);
    }
}
```

migration_enabled 通过匹配把输入收敛成 bool 或明确错误。ShutdownBudget 持有截止时间，wait 泛型接受任意 Future，返回其输出；外层 Result 表示预算是否耗尽，Future 自身若也返回 Result，就形成两层结果，调用者需要分别处理。

### 23.7.3 【精通】理解 Future、借用与结果两层

wait 接受 F: Future，不要求 Future 的输出必须是某一种业务类型。因此可以等待 HTTP 服务结果、JoinHandle 结果或连接池关闭。共享 &amp;self 只读取 deadline，不把预算复制成一套新的计时状态。

Tokio 的暂停时间测试让 8 秒加 3 秒的时序可以快速验证，不需要真实等待十秒。它只证明时间组合逻辑，不证明真实操作系统信号与全部业务请求的停机行为；后者还要通过实际进程与集群实验观察。

### 23.7.4 【进阶】第二步：替换 monolith 启动入口

用以下完整内容替换 monolith/src/main.rs，其他业务模块沿用前章：
```rust
use anyhow::Context;
use monolith::auth::jwt::JwtKeys;
use monolith::cache::{ProductCache, connect_redis};
use monolith::settings::Settings;
use monolith::state::AppState;
use monolith::{background, db, http, shutdown, telemetry};
use platform::{ShutdownBudget, migration_enabled};
use std::future::IntoFuture;
use std::time::Duration;
use tokio_util::sync::CancellationToken;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    dotenvy::dotenv().ok();
    let settings = Settings::load().context("load settings")?;
    telemetry::init(&settings.log).context("init logging")?;
    let run_migrations = migration_enabled(match std::env::var("RUSTMALL_RUN_MIGRATIONS") {
        Ok(ref value) => Some(value.as_str()),
        Err(std::env::VarError::NotPresent) => None,
        Err(error) => return Err(error).context("read migration switch"),
    })?;
    let pool = db::connect(&settings.database)
        .await
        .context("connect database")?;
    if run_migrations {
        db::MIGRATOR.run(&pool).await.context("run migrations")?;
    }
    let jwt = JwtKeys::new(
        &settings.auth.jwt_secret,
        &settings.auth.issuer,
        settings.auth.access_token_ttl_secs,
    );
    let redis = connect_redis(&settings.redis).await;
    let cache = ProductCache::new(
        &settings.cache,
        redis,
        Duration::from_millis(settings.redis.op_timeout_ms),
    );
    let state = AppState::new(pool.clone(), jwt, cache);
    let app = http::routes::router(state, &settings.cors);
    let listener = tokio::net::TcpListener::bind(settings.server.addr()).await?;
    let token = CancellationToken::new();
    tokio::spawn(shutdown::wait_for_signal(token.clone()));
    let mut cleaner = tokio::spawn(background::run_periodic(
        Duration::from_secs(60),
        token.clone(),
        || async { tracing::debug!("cart cleanup tick") },
    ));
    let server = axum::serve(listener, app)
        .with_graceful_shutdown(token.clone().cancelled_owned())
        .into_future();
    tokio::pin!(server);
    let (server_result, budget) = tokio::select! {
        result = &mut server => {
            token.cancel();
            (result.context("HTTP server failed"),
                ShutdownBudget::new(settings.server.shutdown_grace()))
        }
        () = token.cancelled() => {
            let budget = ShutdownBudget::new(settings.server.shutdown_grace());
            let result = budget.wait("HTTP", &mut server).await;
            let result = match result {
                 Ok(result) => result.context("HTTP server failed"),
                 Err(error) => {
                     cleaner.abort();
                     return Err(error);
                 }
            };
            (result, budget)
        }
    };
    token.cancel();
    match budget.wait("background", &mut cleaner).await {
        Ok(result) => {
            result.context("background task failed")?;
        }
        Err(error) => {
            cleaner.abort();
            return Err(error);
        }
    }
    budget.wait("database", pool.close()).await?;
    server_result
}
```

读取 Settings、初始化日志、连接数据库仍按原顺序；严格开关决定是否执行 MIGRATOR。JWT、Redis 和 ProductCache 的构造沿用第 18 章的契约，AppState 仍接收 pool、jwt 与 cache，没有在部署章节偷偷改变业务状态类型。

HTTP 服务与后台清理任务共享取消令牌。server 被 pin 后，select 同时观察服务结束与取消信号；如果收到取消，就在预算内等待服务完成。如果服务先失败，也取消后台工作，避免留下无意义循环。

### 23.7.5 【精通】为什么保留句柄与原错误

后台任务以 JoinHandle 保留，超时后可 abort；JoinError 也会带上下文传播。HTTP 的 server_result 在清理阶段之后返回，使服务错误不会因为后续连接池成功关闭就消失。

如果预算耗尽，程序报告错误并结束，不假装所有请求都已完成。此时进程退出会回收资源，但外部数据库事务与已提交行为仍按自身协议处理。后面设计订单与消息消费时，还要结合“动作已发生而响应未送达”的窗口分析。

```python
password = secrets.token_urlsafe(36)
```

```yaml
      maxSurge: 1
  selector:
    matchLabels:
      app: book-rustmall
  template:
    metadata:
      labels:
        app: book-rustmall
    spec:
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: app
          image: rustmall-monolith:ch23
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: book-rustmall-config
          env:
            - name: APP_CONFIG_DIR
              value: /app/config
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: rustmall-runtime
                  key: DATABASE_URL
            - name: APP_AUTH__JWT_SECRET
              valueFrom:
                secretKeyRef:
                  name: rustmall-runtime
                  key: JWT_SECRET
          startupProbe:
            httpGet:
              path: /health/live
              port: http
            periodSeconds: 2
            timeoutSeconds: 1
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /health/ready
              port: http
            periodSeconds: 3
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health/live
              port: http
            periodSeconds: 10
            timeoutSeconds: 1
            failureThreshold: 3
          lifecycle:
            preStop:
              exec:
                command: [/bin/sleep, "3"]
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: "1"
              memory: 256Mi
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: [ALL]
          volumeMounts:
            - name: tmp
              mountPath: /tmp
      volumes:
        - name: tmp
          emptyDir:
            medium: Memory
            sizeLimit: 16Mi
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: book-rustmall
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: book-rustmall
```

ConfigMap 保存部署差异，envFrom 将其注入应用，Secret 则按需要取特定键。Pod 层 securityContext 管身份与 seccomp；容器层 securityContext 管提权、根文件系统与 capabilities。containers 必须位于 template.spec 下，不能与 spec 同级。

Service 选择 app=book-rustmall，与 Deployment 模板一致。三个探针分别对应启动、准备与存活。PDB 说明期望在某些自愿中断中保留至少一个可用副本，但不防节点突然故障，也不把单节点集群变成高可用集群。

### 23.8.4 【精通】滚动策略的容量与失败条件

两个副本、maxUnavailable: 0、maxSurge: 1，表示更新期间尝试保留已有可用数量，并允许临时多一个副本。这要求节点有放下额外实例的资源；若容量不足，新 Pod 可能一直 Pending。

新副本准备失败时，旧版本可能继续提供服务，rollout status 最终报告进展问题。系统不会因为配置了 progressDeadlineSeconds 就自动替你选择正确业务回滚。需要先查新实例失败原因，再决定修复还是回退模板。

### 23.8.5 【入门】构建并装入 kind 节点

确认代码检查通过，在项目根目录执行。本章使用本地实验标签，装入专用 kind 集群，不依赖私有远端仓库登录。
```bash
cargo test --locked -p platform
cargo check --locked -p monolith --bins
docker build -t rustmall-monolith:ch23 .
kind load docker-image rustmall-monolith:ch23 --name rustmall-book
```

kind 节点有自己的镜像存储，宿主能 docker image inspect 不代表节点已经拥有镜像。IfNotPresent 配合本地加载用于本实验；重复使用同一标签时必须确认节点实际镜像身份。正式交付应沿用第 22 章的产物记录，并优先按仓库摘要明确版本。

### 23.8.6 【进阶】建立 Secret，等待数据库

先检查当前目标，所有修改明确指定专用 context 和 namespace：
```bash
kubectl --context kind-rustmall-book apply -f deploy/k8s/namespace.yaml
python3 scripts/lab-secrets.py
kubectl --context kind-rustmall-book -n rustmall-lab create secret generic rustmall-runtime --from-env-file=.env.k8s
kubectl --context kind-rustmall-book -n rustmall-lab apply -f deploy/lab-postgres.yaml
kubectl --context kind-rustmall-book -n rustmall-lab rollout status deployment/postgres --timeout=180s
```

create Secret 如果同名对象已存在会失败，不应删掉后盲目重建。先确认是否在继续原实验、已有数据库实际使用什么口令。不要把 kubectl get secret -o yaml 的完整结果贴到公开问题中，编码后的值仍是秘密。

### 23.8.7 【进阶】迁移成功以后才发布应用

数据库就绪后执行：
```bash
kubectl --context kind-rustmall-book -n rustmall-lab apply -f deploy/k8s/migration.yaml
kubectl --context kind-rustmall-book -n rustmall-lab wait --for=condition=complete job/book-rustmall-migrate --timeout=150s
kubectl --context kind-rustmall-book -n rustmall-lab logs job/book-rustmall-migrate
```

预期 Job Complete；若失败，先读 Job 与 Pod 的状态和脱敏日志，停止后续动作。不要在忽略 wait 失败的情况下继续 apply 应用。成功后再执行：
```bash
kubectl --context kind-rustmall-book -n rustmall-lab apply -f deploy/k8s/application.yaml
kubectl --context kind-rustmall-book -n rustmall-lab rollout status deployment/book-rustmall --timeout=240s
kubectl --context kind-rustmall-book -n rustmall-lab get pods,services
```

这些命令应逐组执行并核对结果，不是一个无条件粘贴全部的脚本。当前没有自动化编排工具替你在失败后阻止下一次手工命令。

### 23.8.8 【精通】为什么重跑迁移需要新一次 Job

已经 Complete 的同名 Job 不会因为再次 apply 就重新执行。部分模板字段也不可直接修改。确认上次执行记录和当前迁移输入后，可以为下一次发布使用新的 Job 名称，或者在明确保留必要记录后删除旧 Job 再创建。

不能把删除 Job 当成撤销迁移；它只删除执行对象，不会回滚数据库结构。SQLx 的已执行版本与 checksum 仍由数据库记录。下一章将把迁移执行身份与发布过程联系起来，但仍需保持这个数据边界。

## 23.9 故障实验与定位方法

### 23.9.1 【进阶】删实例与改期望数量

在 rustmall-lab 列出应用 Pod，删除其中一个，观察新实例补建；再用 scale deployment/book-rustmall --replicas=1 修改期望数量，观察实际收敛为一个。注意命令仍带完整 context 与 namespace。

这两次操作看起来都使实例数量短暂减少，但含义不同：前者没有改变控制器目标，后者改变了 spec。实验后恢复 replicas=2，并核对 PDB 与实际就绪数量。不要长期让手工 scale 与 Git 文件相互矛盾。

### 23.9.2 【进阶】数据库不可用时观察准备状态

仅在隔离实验，把 postgres Deployment 缩到零，观察应用 readiness 与 restartCount；恢复到一后再次观察。预期准备状态受到影响，进程不应仅因数据库不可用就被 liveness 连续重启。

如果应用先在启动阶段就无法连接数据库，可能尚未成功进入 HTTP 服务，这是另一种路径。记录故障发生在启动前还是已运行后，才能判断与预期是否一致。恢复后也要检查业务连接能否重新建立，不只看数据库 Pod 变绿。

### 23.9.3 【进阶】故意写错 Service selector

在临时练习副本把应用 Service selector 改成不存在的标签，再检查 EndpointSlice。预期 Service 对象仍存在，但正常后端不符合预期；修复选择器后再观察。

这个实验说明“API 接受配置”和“配置表达正确意图”不同。YAML 校验可以发现字段类型问题，却无法知道 app=another-name 是你的拼写错误还是有意选择另一组服务。

### 23.9.4 【精通】更新一个无法就绪的模板

在练习分支临时给应用配置错误数据库地址并发布，观察新 ReplicaSet、旧 Pod、新 Pod 与 rollout 状态。maxUnavailable: 0 有助于保留旧的可用副本，但如果旧版本也依赖同一个已坏数据库，就无法凭此保持业务可用。

修复配置后需要重启使用环境变量的 Pod，或者发布新的模板。Deployment 回退只处理相应模板历史，不会自动回退同名 ConfigMap 的当前内容，更不会逆转数据库迁移。回滚范围必须具体说明。

### 23.9.5 【入门】按状态选取证据

| 现象 | 收集证据 | 处理方向 |
| --- | --- | --- |
| Pending | Pod 事件、节点资源、PVC 状态 | 区分调度不足与存储绑定问题 |
| ImagePullBackOff | Pod 事件、镜像名、节点可见镜像 | 核对 kind 加载、仓库权限与目标平台 |
| CreateContainerConfigError | 事件、引用的 Secret/ConfigMap 键 | 补齐正确命名空间中的资源与键 |
| CrashLoopBackOff | 当前与 previous 日志、退出状态 | 排查配置、迁移和启动异常 |
| Running 但不 Ready | 探针响应、数据库路径、应用日志 | 沿准备条件定位，不先改成恒真 |
| Service 无法访问 | selector、Pod 标签、EndpointSlice | 排除无后端与未就绪 |
| 迁移 Job 失败 | Job 条件、迁移日志、数据库记录 | 保留失败证据，停止应用发布 |
| 滚动更新卡住 | 新旧 ReplicaSet、资源与探针 | 判断容量、镜像或配置问题 |
| 删除后数据消失 | PVC、PV 回收策略、实际挂载 | 核对生命周期，不能用重建替代恢复 |

describe 与 logs 必须指向实际失败的对象。CrashLoop 情况下可用 logs --previous 读取上次容器日志；但收集与转发前检查敏感内容。kubectl get events 的显示顺序与保留时间也有边界，不要把它当成永久审计仓库。

### 23.9.6 【精通】数据卷与命名空间的清理

停止 port-forward 不会删除应用。若继续下一章，应保留 rustmall-lab 与凭据；若明确结束一次性实验，再评估命名空间、PVC 与底层 PV 的回收行为，确认所需数据已另有备份。

删除 kind 集群会销毁这套本地环境，不能把节点本地卷视为跨集群备份。本章不提供默认一键删库命令作为日常修复步骤。出现卷挂载问题时，先保存状态证据，再决定恢复、迁移还是清理。

## 23.10 分层练习与参考答案

### 23.10.1 【入门练习】解释四层对象

题目：Deployment、ReplicaSet、Pod、Service 分别解决什么问题？删掉一个 Pod 为什么不等于缩容？

参考答案：Deployment 管模板与更新，ReplicaSet 维持某模板的实例数量，Pod 承载具体容器，Service 为匹配后端提供访问入口。删除实例没有修改副本目标，所以控制器会补建；缩容需要修改相应期望数量。

### 23.10.2 【操作练习】查出三个端口的含义

题目：容器监听 8080，Service port 改为 80，targetPort 仍为 http，本地想用 58080 访问，应该如何转发？程序监听是否需要改？

参考答案：Service 目标继续指向命名容器端口 http，即 8080；本机转发应使用 58080:80。程序监听无需仅因 Service 对外端口变化而改动。完整答案应画出客户端、Service 端口和后端端口三段关系。

### 23.10.3 【推理练习】数据库坏了要不要重启所有应用

题目：外部数据库不可用，但应用进程仍可响应基本健康请求。把 readiness 改成 liveness 能否提高恢复速度？

参考答案：不一定，可能造成所有副本重启和连接风暴。准备状态用于表达暂时不适合接业务，存活状态用于判断进程是否需要重启。恢复策略应对应故障模型，不能靠更激烈动作代替诊断。

### 23.10.4 【推理练习】共享停机预算

题目：外层宽限 30 秒，preStop 用 3 秒，应用预算 20 秒；HTTP 用 15 秒，后台工作再需 8 秒，是否应完整等待？

参考答案：应用预算在本章从停止处理阶段开始共享，HTTP 后只余约 5 秒，后台阶段应超时，而不是重新获得 20 秒。外层还包含信号与调度等开销，不能把所有数字刚好相加等于 30。超时结果应报告并处理句柄。

### 23.10.5 【扩展练习】追踪一个配置变更

题目：修改 ConfigMap 的环境变量后，旧 Pod 仍使用旧值；如何证明新配置真正进入进程？怎样避免把秘密写进日志？

参考要点：核对对象版本与部署动作，受控重启并观察新 Pod 身份，使用非敏感配置或经过专门设计的配置版本信息确认加载；不打印整份环境。若配置来自挂载文件，还需解释更新传播与应用重载，不可套用环境变量结论。

### 23.10.6 【精通练习】设计失败的迁移发布顺序

题目：Job 执行失败，操作者仍更新 Deployment，应用又设置 RUSTMALL_RUN_MIGRATIONS=false。会发生什么？如何改进？

参考答案：新程序可能连接旧 schema，在请求阶段出错；关闭启动迁移并不会自动建立 Job 依赖。必须把“迁移成功”作为继续发布的条件，保留失败记录，并评估新旧程序兼容。自动化时将等待失败传播为非零，不能只按文件顺序 apply 后就认为已建立依赖。

### 23.10.7 【小结】从进程配置走向运行模型

本章建立了控制循环、服务发现、探针分类、资源与存储生命周期，并在同一个 RustMall 中增加独立迁移入口和有预算的停机协议。教学集群仍是单机实验，数据库没有高可用，缓存暂时使用既有降级路径，外部入口也仅通过端口转发。

下一章用 Helm 表达环境差异，再用 GitOps 的思路明确期望状态的来源与发布记录。部署工具会减少重复输入，但不会消除本章解释的迁移、配置刷新、数据与权限边界。审核记录应分别列出本地代码测试、清单检查和真实集群运行；没有执行的阶段保持明确待验证。

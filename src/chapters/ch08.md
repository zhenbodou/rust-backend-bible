# 第 8 章 模块、包与 Cargo 深入

前 7 章的代码都在一个 common 库里。从第 12 章开始，RustMall 会逐步长成十几个 crate 的workspace：单体服务、协议定义、多个微服务、网关。本章系统讲解组织代码的全部工具：模块与可见性决定“谁能看到什么”，Cargo 的包、workspace 与 features 决定“怎样构建、按需启用功能”，条件编译与宏让同一份源码适应不同场景、消除重复代码。项目部分用 macro_rules! 重写第 3 章的 ID 类型，并为 common 增加 prelude 与可供其他 crate 使用的测试夹具。

## 8.1 模块系统

### 8.1.1 【入门】四个层次的概念

| 概念 | 是什么 | 由什么定义 | RustMall 中的例子 |
| --- | --- | --- | --- |
| workspace | 一组共同构建的包 | 根目录的 Cargo.toml 中的 [workspace] | rustmall/ |
| package（包） | 一个 Cargo.toml 描述的项目，可包含一个 lib 和多个 bin | Cargo.toml 的[package] | common ，以后的order-service |
| crate | 一次编译的单元，编译结果是一个库或一个可执行文件 | crate 根文件：lib.rs 或main.rs | common 库 crate |
| module（模块） | crate 内部组织代码的命名空间，形成一棵树 | mod 关键字 | common::money 、common::order |

类比一家公司：workspace 是集团，package 是子公司，crate 是子公司对外发布的一款产品，module是产品内部的部门。

### 8.1.2 【入门】三种定义模块的方式
```rust
// 方式一：内联模块，代码直接写在花括号里（常用于测试模块 mod tests { }）
mod pricing {
    pub fn vip_price(cents: i64) -> i64 { cents * 95 / 100 }
}

// 方式二：同名文件。编译器在当前文件旁边找 billing.rs
mod billing;

// 方式三：同名目录。编译器找 reports.rs 或 reports/mod.rs，子模块放在 reports/ 目录下
mod reports;

fn main() {
    println!("{}", pricing::vip_price(10_000));
}
```

第三种方式有两种文件布局，推荐第一种（Rust 2018 起的写法）：
```text
# 推荐：模块入口与目录同名                # 旧写法：目录里放 mod.rs
src/                                       src/
├── main.rs                                ├── main.rs
├── reports.rs        ← mod daily;         └── reports/
└── reports/                                   ├── mod.rs    ← mod daily;
    └── daily.rs                               └── daily.rs
```

新写法的好处是编辑器标签页里不会出现一堆同名的 mod.rs 。两种写法不能在同一个模块上混用。mod 声明只在父模块中写一次--不要在每个用到它的文件里写 mod xxx; ，那会创建多个不同的模块；其他地方用 use 引入。

### 8.1.3 【入门】路径：crate、self、super

模块形成一棵树，根是 crate 本身。引用其他模块中的项有两种路径：
```rust
// 文件：src/order.rs（common crate 的 order 模块）
// 绝对路径：从当前 crate 的根开始
use crate::ids::OrderId;

// 相对路径：super 表示父模块（这里是 crate 根）
use super::money;

// self 表示当前模块
use self::helpers::round;

mod helpers {
    pub fn round(x: i64) -> i64 { x }

    // 子模块访问父模块的私有函数
    pub fn parent_fn() -> i64 { super::super_level() }
}

fn super_level() -> i64 { 1 }
```

规则：同一个 crate 内部优先使用 crate:: 开头的绝对路径，文件移动位置时更不容易出错；super::主要用于测试模块（use super::*; ）和紧密相关的子模块。引用其他 crate 时直接写crate 名：use thiserror::Error; 、use common::money; 。

### 8.1.4 【进阶】use 的各种写法
```rust
// 引入单个项
use std::collections::HashMap;

// 引入多个
use std::collections::{BTreeMap, HashSet};

// 同时引入 io 模块本身和 io::Write
use std::io::{self, Write};

// 重命名，避免与 std::result::Result 冲突
use std::fmt::Result as FmtResult;

// glob 引入：模块中所有公开项
use crate::error::*;

// 嵌套
use std::sync::{Arc, atomic::{AtomicU64, Ordering}};
```

惯用法（rustfmt 和社区约定）：

函数：引入到它的父模块，调用时写 money::format_yuan(x) ，读代码的人能看出函数来自哪里。

结构体、枚举、trait：直接引入类型本身，use std::collections::HashMap; ，然后写HashMap::new() 。

glob 引入只用于两种场景：测试模块的 use super::*; ，以及专门设计的 prelude（8.9 节）。业务代码中滥用 glob 会让人分不清名字来自哪里，还可能因为上游新增同名项而突然编译失败。

use 语句分组排序：标准库、第三方 crate、本 crate，组之间空一行；rustfmt 会在组内自动按字母排序。

### 8.1.5 【进阶】重导出：pub use

pub use 让一个项在当前模块中以新的路径对外公开，用来设计一个比内部目录结构更友好的公共API：
```rust
// 文件：src/lib.rs
mod internal {
    pub mod deep {
        pub mod nested {
            pub struct Product;
        }
    }
}

// 使用者写 mycrate::Product 即可
pub use internal::deep::nested::Product;
```

标准库到处都在这样做：std::collections::HashMap 实际定义在std::collections::hash::map中。RustMall 在 8.9 节用 pub use 构建一个 common::prelude。

### 8.1.6 【精通】模块树与编译

模块树完全由 mod 声明决定，文件系统中存在但没有被 mod 声明的 .rs 文件不会被编译--新手常见的“我写的代码怎么没生效”就是这个原因。

模块主要组织命名空间。crate 是 Cargo 的依赖和调度边界，但 rustc 还会使用代码生成单元与增量查询缓存；并不是改动一个模块就必然从头编译整个 crate。

#[path = "other.rs"] mod foo; 可以指定模块文件路径，除生成代码外不推荐使用。

cargo modules （第三方工具）可以把模块树打印出来，接手陌生项目时很有用。

## 8.2 可见性

### 8.2.1 【入门】默认私有

Rust 中的所有项（函数、结构体、模块、字段、常量）默认对父模块私有，只有加 pub 才能被外部访问。但子模块可以访问祖先模块中的私有项：
```rust
mod shop {
    // 私有：shop 外部不可见
    fn secret_discount() -> i64 { 50 }

    pub mod cart {
        pub fn total() -> i64 {
            // 子模块可以访问父模块的私有函数
            100 - super::secret_discount()
        }
    }
}

fn main() {
    // 正确
    println!("{}", shop::cart::total());
    // shop::secret_discount();                    // 错误 E0603: function `secret_discount` is private
}
```

规则可以概括为：可见性向下透明、向上封闭。这和公司的保密制度一样：部门内部的事，部门里的小组都知道，但其他部门不知道。

### 8.2.2 【入门】五种可见性修饰

| 写法 | 可见范围 | 典型用途 |
| --- | --- | --- |
| （不写） | 当前模块及其子模块 | 实现细节 |
| pub(self) | 同上（等于不写） | 极少使用 |
| pub(super) | 父模块 | 只给父模块用的辅助函数 |
| pub(crate) | 整个 crate 内部 | crate 内部共享、但不对外公开的工具 |
| pub(in crate::a::b) | 指定的祖先模块 | 精确控制，较少使用 |
| pub | 任何能访问到其父模块的地方 | 公共 API |

注意 pub 的“任何地方”有前提：一个 pub fn 写在私有模块里，外部仍然访问不到，因为路径上的模块不可见。可见性是沿着整条路径逐级检查的。

### 8.2.3 【进阶】结构体与枚举的可见性
```rust
pub mod model {
    pub struct Product {
        // 公开字段
        pub name: String,
        // 私有字段：外部无法读写，也无法用 Product {
        price_cents: i64,
.. } 字面量构造
    }

    impl Product {
        pub fn new(name: &str, price_cents: i64) -> Option<Self> {
            (price_cents >= 0).then(|| Self { name: name.to_string(), price_cents })
        }
        pub fn price_cents(&self) -> i64 { self.price_cents }
    }

    // 枚举的变体自动与枚举本身同样可见
    pub enum Status { Active, Archived }
}
```

结构体的每个字段单独决定可见性。只要有一个私有字段，外部就无法用字面量构造该结构体，只能通过构造函数--第 3 章“构造即合法”的设计正是依靠这一点。

元组结构体同理：pub struct Quantity(i32); 的字段是私有的，所以外部写不出Quantity(1000) 。

枚举的变体和变体字段没有单独的可见性，全部跟随枚举。

#[non_exhaustive] 可以阻止外部 crate 用字面量构造结构体（即使字段全是 pub），也让外部crate 的 match 必须写 _ 分支--给库作者保留以后增加字段或变体的余地。

### 8.2.4 【精通】设计公共 API 的原则

最小公开：先全部私有，确实需要时再逐个开放。公开的东西一旦被别人依赖，修改就是破坏性变更。

用 pub(crate) 表达“内部共享”：例如 crate 内多个模块共用的 SQL 片段、测试辅助函数。

公开类型，不公开字段：通过方法提供只读访问，保持修改内部表示的自由（第 3.7.3 节的 ID 类型就是这样设计的）。

私有类型不能出现在公开 API 中：pub fn f() -&gt; PrivateType 会触发 private_interfaces警告，调用方拿到了一个无法命名的类型。

clippy 和 rustc 提供了 unreachable_pub 、missing_docs 等 lint，可以检查“标了 pub 却实际不可达”和“公开项缺少文档”，适合在发布库时开启。

### 8.2.5 常见编译错误与解读

| 错误码 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| E0583 | file not found for module billin g | mod billing; 找不到billing.rs或 billing/mod.rs | 检查文件名与位置 |
| E0433 | failed to resolve: use of undeclared crate or module | 路径写错，或忘了在父模块 mo d声明 | 检查 mod 声明和路径 |
| E0432 | unresolved import crate::util s | use 的路径不存在 | 用 crate:: 绝对路径核对模块树 |
| E0603 | function xxx is private | 访问了私有项 | 加合适的可见性修饰，或通过公开 API 访问 |
| E0616 | field price_cents of struct Pro duct is private | 读写了私有字段 | 使用方法 |
| E0451 | field price_cents of struct Pro duct is private（构造时） | 外部用字面量构造含私有字段的结构体 | 使用构造函数 |
| E0255/E0252 | the name Result is defined multiple times | 两次 use 引入了同名项 | 用 as 重命名 |
| 警告 | unused import | 引入了却没用 | 删除，cargo fix可以自动处理 |

## 8.3 包、crate 与构建目标

### 8.3.1 【入门】一个包里的五种目标

Cargo 按约定的目录自动发现构建目标（target），不需要配置：

| 目标 | 位置 | 运行方式 | 用途 |
| --- | --- | --- | --- |
| 库（lib） | src/lib.rs | 被其他 crate 依赖 | 业务逻辑、可复用代码；每个包最多一个 |
| 主程序（bin） | src/main.rs | cargo run | 服务的启动入口 |

| 目标 | 位置 | 运行方式 | 用途 |
| --- | --- | --- | --- |
| 额外程序 | src/bin/*.rs | cargo run --bin 文件名 | 数据迁移、管理脚本、压测工具 |
| 示例 | examples/*.rs | cargo run --example 文件名 | 演示 API 用法（第 4 章的 error_report） |
| 集成测试 | tests/*.rs | cargo test | 只能通过公开 API 测试库（第 17 章） |
| 基准测试 | benches/*.rs | cargo bench | 性能测试（第 17 章） |

### 8.3.2 【进阶】库 + 二进制：服务的标准结构

后端服务推荐“薄 main + 厚 lib”的结构：
```text
order-service/
├── Cargo.toml
└── src/
    ├── lib.rs        # 全部业务代码：路由、服务层、仓储……
    ├── main.rs       # 只有十几行：读配置、初始化日志、调用 lib 中的 run()
    └── bin/
        └── migrate.rs  # 单独的数据库迁移工具，同样调用 lib 中的代码
```
```rust
// 文件：order-service/src/main.rs
fn main() -> anyhow::Result<()> {
    // 包名中的 - 在代码中写作 _
    order_service::run()
}
```

好处：集成测试（tests/ 目录）和其他 bin 只能使用库 crate，业务代码放在 lib 中才能被测试和复用。第 12 章的单体服务、第 26 章的每个微服务都采用这个结构。

### 8.3.3 【精通】crate 类型与编译产物

cargo build 后，库编译为 target/debug/libcommon.rlib （Rust 专用的静态库格式），二进制编译为可执行文件。Rust 依赖通常被链接进最终产物，但系统库、TLS 后端或本地库仍可能带来动态依赖；部署前应检查目标平台和实际链接结果，不能一概认为只复制一个文件即可运行。

[lib] crate-type = ["cdylib"] 可以编译为 C 动态库，用于给 Python、Node.js 等语言提供扩展；proc-macro 类型用于过程宏（8.8 节）。

crate 是 Cargo 管理依赖与安排编译任务的重要边界；rustc 的增量编译还会缓存更细粒度的计算。修改 common 后，其下游可能需要重新检查或构建，具体范围取决于变化和缓存，不能把增量缓存简单等同于整 crate 缓存。

## 8.4 Cargo.toml 与 features 深入

### 8.4.1 【入门】依赖的三种来源与三种类型

第 0.2.2 节讲过版本号写法，这里补全依赖声明的全部形式：
```toml
[dependencies]
# crates.io
serde = "1"

# 本地路径
common = { path = "../common" }

# git 仓库，可用 branch / tag / rev 固定
my-sdk = { git = "https://github.com/acme/sdk", rev = "a1b2c3d" }
reqwest = { version = "0.12", default-features = false, features = ["rustls-tls", "json"] }

# 重命名：代码中用 wire:: 引用 wire-protocol 这个包
wire = { package = "wire-protocol", version = "2" }

# 只在测试、示例、基准测试中使用
[dev-dependencies]
proptest = "1"

# 只在构建脚本 build.rs 中使用（第 25 章生成 gRPC 代码）
[build-dependencies]
tonic-prost-build = "0.14"

# 只在类 Unix 系统上使用的依赖
[target.'cfg(unix)'.dependencies]
libc = "0.2"
```

需要可复现构建时，应提交 Cargo.lock，并为 Git 依赖固定经过审核的 rev。tag 也可能被上游移动；branch 依赖在锁文件未更新时不会自动跟随每次推送，但更新锁文件后可能解析到新提交。

### 8.4.2 【入门】features 是什么

feature 是包提供的可选功能开关。例如 tokio 默认几乎什么都不开启，你用 features = ["full"] 打开全部功能，或只开需要的 ["rt-multi-thread", "macros", "net"] ，以减少编译时间和二进制体积。

在自己的包中定义 feature：
```toml
# 文件：某个库的 Cargo.toml
[features]
# 默认开启的 feature
default = ["json"]

# 开启 json 时启用可选依赖 serde_json
json = ["dep:serde_json"]

# 纯代码开关，不引入依赖
metrics = []

# feature 可以组合其他 feature
full = ["json", "metrics"]
[dependencies]
# 可选依赖：只有某个 feature引用它时才会编译
serde_json = { version = "1", optional = true }
```
```rust
// 代码中按 feature 条件编译
#[cfg(feature = "json")]
pub fn to_json(v: &MyType) -> String { serde_json::to_string(v).unwrap_or_default() }
```

dep:serde_json 写法（Rust 1.60+）明确表示“启用这个可选依赖”，并且不会自动生成一个同名的 feature，避免意外暴露。

使用方：my-lib = { version = "1", default-features = false, features =["metrics"]} 。

命令行：cargo build --features metrics 、cargo build --all-features 、cargobuild --no-default-features 。

### 8.4.3 【进阶】feature 必须是“可加”的

Cargo 对同一个依赖在整个依赖图中只编译一份，所有使用者请求的 feature 取并集（feature unification）。例如服务 A 依赖 common 时开了 test-util ，服务 B 没开，但它们在同一个workspace中一起构建时，B 拿到的 common 也会带着 test-util 。因此：

feature 只能增加功能，不能删除或改变已有行为。“开启 no_std 就去掉某些函数”这样的设计会让别人的代码在偶然的组合下编译失败。

互斥的 feature（例如“用 rustls”与“用 openssl”二选一）会出问题，需要在代码中用compile_error! 明确报错，或者设计成优先级规则。

resolver 2 及以上会把“只在 dev-dependencies / build-dependencies 中开启的 feature”与正常依赖分开计算，减少测试代码的 feature 污染正式构建（这也是第 1.6.2 节写 resolver = "3" 的原因之一）。

### 8.4.4 【进阶】构建脚本 build.rs

包根目录下的 build.rs 会在编译这个包之前先被编译并运行，常用于：从 .proto 文件生成 Rust 代码（第 25 章）、编译 C 语言依赖（第 28 章 Kafka 客戶端）、把 Git 提交号嵌入程序。
```rust
// 文件：build.rs -- 把构建时间注入为编译期环境变量
fn main() {
    // 只有 build.rs 变化时才重新运行
    println!("cargo::rerun-if-changed=build.rs");
    let ts = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .map(|d| d.as_secs())
        .unwrap_or(0);
    println!("cargo::rustc-env=BUILD_TS={ts}");
}
// 业务代码中读取：env!("BUILD_TS")
```

构建脚本通过向标准输出打印 cargo::指令=值 与 Cargo 通信（旧写法为单冒号 cargo: ）。不写rerun-if-changed 时，包内任何文件变化都会让它重新运行，拖慢增量编译。

### 8.4.5 【精通】版本解析与 Cargo.lock

同一个 crate 的不兼容版本（如 rand 0.8 和 rand 0.9 ）可以同时存在于依赖图中，各自编译一份；兼容版本会被统一到满足所有约束的最高版本。cargo tree -d 可以找出重复的版本（第0.2.5节）。

两个不同版本的同名类型是不同的类型：A 库返回 http 0.2 的 StatusCode ，B 库需要 http1.x的 StatusCode ，就会出现“expected StatusCode , found StatusCode ”这种令人困惑的报错。解决办法是统一版本。

[patch.crates-io] 可以临时把某个依赖替换为本地路径或 fork 的 git 仓库，用于验证修复或等待上游合并。

cargo update --precise 1.2.3 -p some-crate 可以把锁文件中的某个依赖精确地调整到指定版本。

## 8.5 workspace 深入

### 8.5.1 【入门】回顾与扩展

第 1.6.2 节已经建立了 workspace，第 4 章加入了 [workspace.dependencies] 。完整的能力如下：
```toml
# 文件：rustmall/Cargo.toml（示意，不是本章要修改的内容）
[workspace]
resolver = "3"

# 支持通配符
members = ["common", "services/*", "gateway"]

# 从通配符中排除
exclude = ["services/experimental"]

# 在根目录执行 cargo run / build 时的默认目标
default-members = ["gateway"]

# 成员可继承的元数据
[workspace.package]
version = "0.1.0"
edition = "2024"

# 成员可继承的依赖版本
[workspace.dependencies]
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
# 内部 crate 也可以登记在这里
common = { path = "common" }

# 成员可继承的 lint 规则
[workspace.lints.clippy]
unwrap_used = "warn"
```

成员中的继承写法：
```toml
[dependencies]
# 继承版本与 feature，并额外追加 net
tokio = { workspace = true, features = ["net"] }

# 点号写法与上一行等价
common.workspace = true
```

注意：成员只能追加 feature，不能去掉 workspace 中声明的 feature，也不能在成员中改写版本号。

### 8.5.3 【进阶】内部 crate 之间的依赖

内部 crate 互相依赖时使用路径依赖。依赖关系必须是有向无环的：如果 common 依赖 order-service，order-service 又依赖 common，Cargo 会报 cyclic package dependency 。这在架构上也是好事--它强迫你把共享代码下沉到底层 crate。RustMall 最终的依赖分层是：
```text
gateway    user-service   product-service   order-service
    │            │              │                │
    └────────────┴──────┬───────┴────────────────┘
                        ▼
             proto（gRPC 接口定义）
                        ▼
             common（错误、ID、通用工具）
```

### 8.5.4 【精通】拆分 crate 的时机

拆分 crate 可以让互不依赖的部分并行构建，并明确公共接口边界。单 crate 也能利用增量编译；是否拆分应根据 cargo build --timings 的测量与复用边界决定，不能只凭行数判断。

边界清晰：跨 crate 只能使用 pub 的 API，crate 边界是比模块更强的封装。

不要过早拆分：每多一个 crate 就多一份 Cargo.toml 和一层可见性考虑。经验法则是“先在一个crate 内用模块分层，当某一部分需要被多个服务复用、或编译时间明显变长时再拆”。

cargo build --timings 生成一份 HTML 报告，显示每个 crate 的编译耗时和并行情况，是决定如何拆分的依据。

## 8.6 条件编译

### 8.6.1 【入门】cfg 属性

#[cfg(条件)] 让编译器只在条件成立时编译它标注的项；条件不成立时，那段代码就像不存在一样，不会被类型检查，也不会进入二进制：
```rust
// 只在 cargo test 时编译
#[cfg(test)]
mod tests { /* ... */ }

// 只在开启 metrics feature 时编译
#[cfg(feature = "metrics")]
fn record_metric(name: &str) { println!("metric {name}"); }

// 只在 Linux 上编译
#[cfg(target_os = "linux")]
fn platform_name() -> &'static str { "linux" }

#[cfg(not(target_os = "linux"))]
fn platform_name() -> &'static str { "other" }

// debug 构建（cargo build 默认）时编译，release 时不编译
#[cfg(debug_assertions)]
fn debug_only_check() {}
```

常用条件：test 、debug_assertions 、feature = "名字" 、target_os = "linux"/"macos" / "windows" 、unix 、windows 、target_arch = "x86_64" 。组合：all(a, b)、any(a, b) 、not(a) 。

### 8.6.2 【进阶】cfg! 宏与 cfg_attr
```rust
fn log_level() -> &'static str {
    // cfg! 在编译期求值为 true/false，两个分支都会被编译和类型检查
    if cfg!(debug_assertions) { "debug" } else { "info" }
}
// cfg_attr：条件成立时才附加某个属性
#[cfg_attr(feature = "serde", derive(serde::Serialize))]
pub struct Money { cents: i64 }

// 测试中允许使用 expect（RustMall 用 clippy.toml 统一处理了，这里只演示写法）
#[cfg_attr(test, allow(clippy::expect_used))]
fn helper() {}
```

#[cfg] 与 cfg! 的区别：前者让代码根本不存在（未开启的分支可以引用不存在的依赖）；后者两个分支都必须能编译通过，只是运行时走其中一个，编译器会把常量条件优化掉。

### 8.6.3 【精通】条件编译的陷阱

未启用的代码不会被检查：一段只在 feature = "metrics" 下编译的代码，即使有类型错误，默认构建也发现不了。CI 中应当用 cargo hack check --each-feature （第三方工具）或至少 --all-features 构建一次。

feature 名拼写错误不会报错（旧版本）：#[cfg(feature = "metric")] 少了一个字母，代码会被悄悄地永远排除。新版 Cargo 会对 Cargo.toml 中未声明的 feature 名给出 unexpected_cfgs 警告，-D warnings 下会成为错误。

#[cfg(test)] 只对本 crate 的测试生效：其他 crate 的测试依赖本 crate 时，本 crate 是以普通方式编译的，cfg(test) 中的代码不可见。想把测试辅助代码提供给其他 crate，需要一个 feature--这正是 8.9 节 test-util 的设计动机。

### 8.6.4 常见编译错误与解读

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| E0432/E0433 | unresolved import（只在某些构建中出现） | 代码依赖的 feature 或可选依赖没有开启 | 用 #[cfg(feature=...)] 保护代码，或开启feature |
| 警告 | unexpected cfg condition value:metric | cfg 中的 feature 名未在Cargo.toml 中声明 | 修正拼写或在 [feature s]中声明 |
| Cargo 错误 | feature xxx includes dep:yyy ,but yyy is not an optional dependency | dep: 指向的依赖没有optional = true | 把依赖标为可选 |
| Cargo 错误 | cyclic package dependency | 内部 crate 循环依赖 | 把共享部分下沉到更底层的crate |
| Cargo 错误 | duplicate key dependencies | 同一个表写了两次 | 合并到一个表中 |
| E0308 | expected StatusCode , found Sta tusCode | 依赖图中存在同一 crate的两个不兼容版本 | cargo tree -d 找到并统一版本 |

## 8.7 声明宏 macro_rules!

### 8.7.1 【入门】宏与函数的区别

第 1 章起我们一直在用宏：println! 、vec! 、format! 、assert_eq! 。宏与函数的根本区别是：函数在运行时接收值，宏在编译期接收代码并生成代码。因此宏能做到函数做不到的事：接收数量可变的参数、在编译期检查格式字符串、生成新的类型和 impl 块。

代价是：宏比函数难读、难调试，报错信息也更晦涩。能用函数、泛型、trait 解决的问题就不要用宏；宏适合消除“结构重复”--几段代码只在名字或类型上不同，又无法用泛型表达。

### 8.7.2 【入门】第一个宏
```rust
/// 生成一个返回固定错误码的函数
macro_rules! error_code_fn {
    // 匹配规则 => 展开结果
    ($name:ident, $code:expr) => {
        fn $name() -> &'static str {
            $code
        }
    };
}

error_code_fn!(not_found, "NOT_FOUND");
error_code_fn!(conflict, "CONFLICT");

fn main() {
    println!("{} {}", not_found(), conflict());
}
```

macro_rules! 名字 { (模式) =&gt; { 展开 }; ... } ：可以有多条规则，从上到下匹配第一条成功的。

$name:ident ：一个元变量，ident 是它的片段类型，表示“匹配一个标识符”。

调用时用 名字!(...) ，圆括号、方括号、花括号都可以：vec![] 、println!() 只是习惯写法。

### 8.7.3 【进阶】片段类型

| 片段类型 | 匹配什么 | 例子 |
| --- | --- | --- |
| ident | 标识符 | UserId 、price |
| expr | 表达式 | 1 + 2 、"abc" 、f(x) |
| ty | 类型 | i64 、Vec&lt;String&gt; |
| pat | 模式 | Some(x) 、1..=9 |
| path | 路径 | std::fmt::Display |
| stmt | 语句 | let x = 1 |
| block | 代码块 | { ... } |
| item | 项 | 一个函数、结构体定义 |
| meta | 属性内容 | derive(Debug) 、doc = "..." |
| literal | 字面量 | 42 、"text" |
| lifetime | 生命周期 | 'a |
| vis | 可见性（可以为空） | pub 、pub(crate) |
| tt | 单个 token 树 | 任何东西，最灵活 |

### 8.7.4 【进阶】重复

$( ... ),* 表示“括号里的内容重复零次或多次，用逗号分隔”；+ 表示一次或多次；? 表示零次或一次。展开时用同样的 $( ... )* 写法把对应部分重复输出：
```rust
/// 构造一个 HashMap：hashmap!{ "a" => 1, "b" => 2 }
macro_rules! hashmap {
    // $(,)? 允许最后一项后面多一个逗号
    ($($key:expr => $value:expr),* $(,)?) => {{
        let mut map = ::std::collections::HashMap::new();
        $( map.insert($key, $value); )*
        map
    }};
}

fn main() {
    let stock = hashmap! { "键盘" => 10, "鼠标" => 5, };
    println!("{stock:?}");
}
```

展开结果外层的双花括号 {{ ... }} ：外层是宏规则语法本身的括号，内层是一个代码块表达式，让let mut map 等语句被包在一个块里并返回 map 。

### 8.7.5 【进阶】卫生性与 $crate

卫生性（hygiene）：宏内部定义的局部变量不会与调用处的同名变量冲突。上例中宏里的 map 不会覆盖调用者作用域中名为 map 的变量。

路径要写完整：宏在调用处展开，调用处可能没有 use std::collections::HashMap ，所以宏内部写 ::std::collections::HashMap （开头的 :: 表示从外部 crate 根开始）。

$crate ：宏要引用定义它的 crate 中的项时，写 $crate::module::Item 。无论使用者把你的crate 重命名成什么，$crate 都能正确指向它。

### 8.7.6 【进阶】宏的作用域与导出

macro_rules! 宏遵循“文本顺序”：必须先定义、后使用（在同一个文件中，定义要写在调用之前）。

在模块中定义的宏默认只在该模块（及之后的子模块）中可用。

让其他 crate 使用：在宏定义上加 #[macro_export] ，它会被导出到 crate 根，使用者写 usemycrate::hashmap; 或 mycrate::hashmap!{...} 。

### 8.7.7 【精通】调试宏

cargo expand （第 0.2.7 节）显示宏展开后的完整代码，是调试宏的第一工具。也可以只展开某个模块：cargo expand -p common ids 。

报错时编译器会指出“in this macro invocation”，先看展开后的代码哪里出错，再回到宏定义修改。

复杂的匹配逻辑（递归宏、tt 吞噬）会急剧增加编译时间和理解难度。超过二三十行、需要解析复杂语法的宏，应考虑改写为过程宏，或者干脆写成普通代码。

### 8.7.8 常见编译错误与解读

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| 宏错误 | no rules expected the token xx x | 调用参数不符合任何一条规则 | 对照规则的模式检查分隔符与片段类型 |
| 宏错误 | unexpected end of macro invocation | 参数少了 | 补齐参数 |
| E0425 | cannot find value map in this scope | 卫生性：想在宏外访问宏内部定义的局部变量 | 让宏返回值，或由调用者传入变量名（ident） |
| 宏错误 | cannot find macro define_id in this scope | 宏在定义之前被调用，或没有导出 | 调整定义顺序；跨 crate 使用加#[macro_export] |

| 错误 | 典型信息 | 原因 | 解决 |
| --- | --- | --- | --- |
| 宏错误 | variable x is still repeating at this depth | 展开时重复层数与匹配时不一致 | 让 $( )* 的嵌套层数一致 |
| 宏错误 | $x:expr is followed by { ,which is not allowed | expr 后面只能跟=&gt;、,、; | 调整分隔符 |

## 8.8 过程宏简介、文档与发布

### 8.8.1 【入门】三种过程宏

过程宏是一个特殊的 crate（crate-type = "proc-macro" ），它在编译期运行，接收代码的 token流、输出新的 token 流。我们每天都在使用别人写的过程宏：

| 种类 | 写法 | 例子 |
| --- | --- | --- |
| 派生宏 | #[derive(Xxx)] | Serialize 、thiserror::Error 、sqlx::FromRow |
| 属性宏 | #[xxx] 标在函数或类型上 | #[tokio::main] 、#[tracing::instrument] 、#[sqlx::tes t] |
| 函数式宏 | xxx!(...) | sqlx::query!(...) 、html!{...} |

编写过程宏通常用 syn （解析 Rust 语法）、quote （生成代码）、proc-macro2 三个库。本书不要求你编写过程宏，但理解“ #[tokio::main] 只是把你的 async fn main 改写成创建运行时并block_on的普通 main”会让你在第 11 章看懂报错。可以用 cargo expand 看到这些宏展开后的样子。

### 8.8.2 【进阶】文档注释与 rustdoc

第 1.1.4 节介绍了 /// 和 //! 。补充几个常用技巧：

文档内链接：[`Product`] 、[`crate::money::format_yuan`] ，rustdoc 会生成可点击链接，并在链接失效时给出警告。

约定的小节标题：# Examples 、# Errors （返回 Err 的条件）、# Panics （会 panic 的条件）、# Safety （unsafe 函数的前提）。clippy 的 pedantic 组中有 missing_errors_doc 、missing_panics_doc ，可以在发布库时开启。

文档测试的标记：代码块标 no_run （编译但不运行，例如需要网络）、ignore （不编译）、should_panic 、compile_fail （证明某种误用无法编译--用来给 API 的类型安全写“测试”）。

cargo doc --no-deps --open 只生成本 workspace 的文档；#! [warn(missing_docs)] 要求所有公开项都有文档。

### 8.8.3 【精通】语义化版本与发布

版本号 主.次.修订：修复 bug 升修订号；向后兼容地新增功能升次版本号；破坏兼容升主版本号。1.0 之前，次版本号的变化被视为不兼容。

什么算“破坏兼容”：删除或重命名公开项、给 trait 增加没有默认实现的方法、给公开枚举增加变体（没有 #[non_exhaustive] 时）、提高 MSRV（有争议，很多库视为次版本变化）、去掉某个Copy/Send 实现。cargo semver-checks 可以自动检测。

发布到 crates.io：cargo login 后执行 cargo publish （需要填写 description 、license 等元数据）。发布的版本不可删除，只能 cargo yank 标记为不推荐。

公司内部的共享库通常不发布到 crates.io，而是放在同一个 workspace（RustMall 的做法），或者搭建私有 registry（如 Kellnr、cloudsmith、Artifactory），在.cargo/config.toml 中配置[registries] 。

### 8.9.2 第 1 步：用宏重写 ids.rs

文件：rustmall/common/src/ids.rs （替换全部内容）
```rust
//! 强类型 ID。
//!
//! 每种实体的 ID 都是独立的类型，编译器会阻止把 `UserId` 传给需要 `ProductId` 的地方。
//! 运行时它们与 `i64` 完全相同，没有任何额外开销。
//! 所有 ID 类型由本模块私有的 `define_id!` 宏生成，保证行为一致。

/// 生成一个包装 `i64` 的 ID 类型。
///
/// 生成的内容：
/// - `#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]`
/// - `const fn new(i64) -> Self` 与 `const fn get(self) -> i64`
/// - `Display`：输出内部数字
/// - `From<ID> for i64`：可以写 `i64::from(id)` 或 `let raw: i64 =
/// id.into();`
///
/// 宏调用前写的文档注释会成为生成类型的文档。
macro_rules! define_id {
    ($(#[$meta:meta])* $name:ident) => {
        $(#[$meta])*
        #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
        pub struct $name(i64);

        impl $name {
            pub const fn new(value: i64) -> Self {
                Self(value)
            }

            pub const fn get(self) -> i64 {
                self.0
            }
        }

        impl ::std::fmt::Display for $name {
            fn fmt(&self, f: &mut ::std::fmt::Formatter<'_>) -> ::std::fmt::Result {
                write!(f, "{}", self.0)
            }
        }

        impl ::std::convert::From<$name> for i64 {
            fn from(id: $name) -> i64 {
                id.0
            }
        }
    };
}
define_id!(
    /// 用户 ID。
    UserId
);

define_id!(
    /// 商品 ID。
    ProductId
);

define_id!(
    /// 订单 ID。
    OrderId
);

#[cfg(test)]
mod tests {
    use super::*;
    use std::collections::HashSet;

    #[test]
    fn ids_display_as_plain_numbers() {
        assert_eq!(UserId::new(7).to_string(), "7");
        assert_eq!(format!("订单 {}", OrderId::new(1001)), "订单 1001");
    }

    #[test]
    fn ids_can_be_hash_keys() {
        let set: HashSet<ProductId> = [ProductId::new(1), ProductId::new(1), 
            ProductId::new(2)].into();
        assert_eq!(set.len(), 2);
    }

    #[test]
    fn ids_convert_to_i64() {
        let raw: i64 = ProductId::new(42).into();
        assert_eq!(raw, 42);
        assert_eq!(i64::from(UserId::new(7)), 7);
        assert_eq!(OrderId::new(3).get(), 3);
    }
}
```

代码精讲：

$(#[$meta:meta])* ：匹配零个或多个属性。文档注释 /// 用户 ID。 在编译器眼中就是属性#[doc = " 用户 ID。"] ，所以它会被捕获，并在展开时原样放到生成的结构体上-- cargodoc中每个 ID 类型仍然有自己的文档。

::std::fmt::Display ：开头的 :: 保证无论宏在哪里展开都能找到标准库（8.7.5 节）。这个宏只在本文件内使用，写短路径也能编译，但养成写完整路径的习惯，以后把宏移到别处或导出时不会出问题。

宏定义必须写在调用之前（8.7.6 节）。宏没有加 #[macro_export] ，所以它是 ids 模块的私有实现细节，crate 外部看不到 define_id! 。模块文档中只用代码格式提到它，而不写成[`define_id!`] 链接：公开模块的文档链接到私有项，cargo doc 会给出private_intra_doc_links 警告。

impl From&lt;ProductId&gt; for i64 满足孤儿规则（第二卷 5.6 节）：From 和 i64 都是外部的，但类型参数 ProductId 是本地类型，规则允许。

原来的两个测试原样保留，证明重写没有改变行为；新增 ids_convert_to_i64 测试新功能。重构时先保证旧测试全部通过，再加新测试，这是安全重构的基本纪律。

用 cargo expand -p common ids 查看展开结果，会看到与第 3.7.3 节手写版本几乎相同的代码，外加From 实现。

### 8.9.4 第 3 步：新建 fixtures.rs

文件：rustmall/common/src/fixtures.rs （新建）
````rust
//! 测试夹具：快速构造合法的领域对象。
//!
//! 只在本 crate 的测试中，或者其他 crate 开启 `test-util` feature 时编译。
//! 其他 crate 的用法（写在它们的 `[dev-dependencies]` 中）：
//!
//! ```toml
//! common = { path = "../common", features = ["test-util"] }
//! 
```
//!
//! 夹具函数在参数不合法时直接 panic：测试数据写错属于测试代码的 bug，
//! 应当立即暴露，而不是返回 Result 让每个测试都去处理。

use crate::ids::ProductId;
use crate::product::Product;
use crate::quantity::Quantity;

/// 构造购买数量。
///
/// # Panics
/// `n` 不在 1~99 之间时 panic。
pub fn qty(n: i32) -> Quantity {
    Quantity::try_new(n).expect("夹具中的数量必须合法")
}

/// 构造商品。
///
/// # Panics
/// 名称为空、价格或库存为负时 panic。
pub fn product(id: i64, name: &str, price_cents: i64, stock: i32) -> Product {
    Product::try_new(ProductId::new(id), name, price_cents, stock).expect("夹具中的商品必须合法")
}

/// 一个常用的示例商品：ID 1，机械键盘，199 元，库存 100。
pub fn keyboard() -> Product {
    product(1, "机械键盘", 19_900, 100)
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn fixtures_build_valid_objects() {
        let p = keyboard();
        assert_eq!(p.id(), ProductId::new(1));
        assert_eq!(p.stock(), 100);
        assert_eq!(qty(3).get(), 3);
    }

    #[test]
    #[should_panic(expected = "夹具中的数量必须合法")]
    fn invalid_fixture_panics_with_clear_message() {
        let _ = qty(0);
    }
}
````

设计说明：

#[should_panic(expected = "...")] ：断言测试函数会 panic，并且 panic 信息包含指定文本。只写 #[should_panic] 而不写 expected，任何原因的 panic 都会让测试通过，可能掩盖真正的bug。

第 6、7 章的测试中各自写了 fn qty(...) 、fn product(...) 辅助函数。现在它们可以改用crate::fixtures::qty ，作为练习留给你；不改也完全不影响功能。

夹具中使用 expect 而不是返回 Result，并在文档的 # Panics 小节写明--这是“库代码可以panic 的合理场景”之一（第二卷 4.7 节）：调用者违反了明确写出的前提条件，而且只在测试中使用。

### 8.9.9 常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| cannot find macro define_id inthis scope | 宏定义写在了调用之后 | 把 macro_rules! 移到文件开头 |
| no rules expected the token | 调用宏时文档注释与类型名之间多了逗号等符号 | 按 8.9.2 的格式书写 |
| conflicting implementations oftrait Display | 旧的手写 impl Display 没有删除 | 用 8.9.2 的完整内容替换整个文件 |
| unresolved import crate::fixtures （在其他 crate 中） | 没有开启 test-util feature | 在 dev-dependencies 中写features = ["test-util"] |
| prelude 导致命名冲突（E0659 ambiguous） | 本地定义了与 prelude 同名的类型，同时 glob 导入 | 显式 use 本地类型，或不使用 glob改为逐个导入 |
| unresolved link to fixtures 文档警告 | 在 lib.rs 文档中给 fixtures 加了链接 | 去掉链接，见 8.9.6 的说明 |

### 8.9.10 本章小结

模块树由 mod 声明决定，推荐“同名文件 + 目录”布局；crate 内部用 crate:: 绝对路径，函数引入到父模块、类型直接引入；pub use 设计对外 API。

可见性默认私有、向下透明；pub(crate) 表达内部共享；只要有一个私有字段，外部就只能通过构造函数创建结构体，这是“构造即合法”的基础。

包可以包含一个 lib 与多个 bin、examples、tests、benches；服务采用“薄 main + 厚 lib”结构。

features 是可加的可选功能，同一依赖的 feature 在依赖图中取并集；可选依赖用 dep: 引用；build.rs 在编译前运行，用于代码生成。

workspace 统一管理成员、依赖版本、元数据与 lint；内部 crate 依赖必须无环；按复用与编译速度需要拆分 crate。

#[cfg] 让代码在条件不成立时完全不存在，cfg! 只是编译期常量；#[cfg(test)] 对其他crate不可见，需要通过 feature 提供测试支持。

macro_rules! 在编译期按模式生成代码，适合消除结构重复；注意卫生性、完整路径与$crate；过程宏（派生宏、属性宏、函数式宏）是 serde、tokio 等库的基础。

RustMall 用宏生成 ID 类型、新增 prelude 与 test-util 夹具，单元测试在当前配套检查点中为 67 个。

第 0~8 章完成了 Rust 语言本身的学习。下一章进入 Web 世界：第 9 章“HTTP、REST 与 JSON 全解”，从一次请求的完整旅程讲起，系统讲解 HTTP 协议、REST 设计规范与 JSON，并为 RustMall 编写第一份API 设计文档。

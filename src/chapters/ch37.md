# 第 37 章 端到端事件链路与读模型重建

第36章已经让一笔订单经过用户认证、库存预留、实验支付和库存确认，最终进入completed。现在打开另一个终端查看商品展示库：它能否在不读取订单库、也不参与库存事务的条件下，逐步追上权威商品状态？如果这个展示库丢失，能否在保留原系统的同时建立一个新版本，并证明重建结果正确？

本章从第36章完整工程增量演进。我们继续使用同一份商品、同一笔订单、同一套Outbox，不重新编写一个脱离主线的消息演示。第28章解决客户端如何连接Kafka，第29章解决本地事实怎样可靠传播；本章把它们接进七角色订单实验，并完成新增数据库、积压追赶、重复交付、墓碑保护、并行重建与错误定位。

学完后，应能沿商品id、revision、event_id和Kafka位点追踪一次变化；解释每个崩溃窗口由哪份持久记录恢复；从零启动两个彼此独立的投影；并识别“消费追平”和“数据完整”之间的区别。

## 37.1 先确定谁拥有业务事实

### 37.1.1 【入门】两个数据库可以给出不同的库存吗

短时间内可以。catalog库中的products是库存裁决的权威数据；projection库中的catalog_view是异步副本。预留事务已经把可售库存从10改成8，但消息尚未被消费时，展示库可能还显示10。

因此订单仍向catalog内的Inventory RPC申请预留。不能读到展示库的10，就在订单库自行减2并声称已经获得库存。读模型用于展示、搜索或统计，拥有“允许短暂落后”的业务边界。

### 37.1.2 【入门】本章增加哪几条箭头

完整路径如下。箭头表示信息流，不代表所有节点处在同一事务中。
```text
edge -> orders HTTP -> orders库
                     -> worker -> Inventory / Payment
                                   |
                           catalog本地事务
                           products + product_outbox
                                   |
                             outbox-relay
                                   |
                   Kafka product.snapshot.v1
                         /                   \
             projection-worker        rebuild worker
             projection库             projection_rebuild库
             Inbox + view             Inbox + view
```

只有products与Outbox共享catalog本地事务；只有某个投影的Inbox与view共享该投影本地事务。订单审计、支付收据和库存预留账仍由前章各自服务维护。

### 37.1.3 【进阶】事件表达已经发生的事实

本章继续使用product.snapshot.v1。它包含商品身份、商品版本和该版本完整快照。它没有命令消费者“再扣一次库存”。重复应用快照不会重复扣减权威库存。

订单完成状态也没有通过这个事件传播。它是商品事件协议，不能因为实验中出现了订单，就把订单状态或支付内部字段塞进商品payload。本章证明的是订单引起的商品变化能够进入读模型。

### 37.1.4 【精通】异步不等于放弃正确性

短暂落后是被明确允许的状态；永远丢失、错误复活、重复扣减是协议错误。我们允许重试，却要求身份不变；允许乱序，却要求版本单调；允许崩溃，却要求有足够的持久事实继续处理。

本章采用单broker实验验证应用协议。它没有验证Kafka节点故障下的副本选举、高可用或跨故障域恢复；这些运维机制在第43章继续展开。

## 37.2 用一张表推演双写与崩溃

### 37.2.1 【入门】为什么不在HTTP提交后直接send

假设先提交商品，再发送Kafka。进程在两者之间退出，商品存在而事件永远缺失。反过来先发消息再提交数据库，消费者可能看到一个后来回滚的商品。

Outbox让商品修改和待传播事实在同一个SQL事务内提交。失败时二者一起回滚；提交后即使HTTP连接断开，relay仍能找到待处理事件。

### 37.2.2 【入门】Outbox没有消除所有双写

relay必须先让Kafka确认，再把delivered_at写回catalog库。这仍然是两个系统的操作，不能用一个PostgreSQL事务包住。

| 中断位置 | 持久事实 | 恢复动作 |
| --- | --- | --- |
| 商品事务提交前 | 商品与Outbox均未提交 | 原业务按同一请求身份重试 |
| 商品事务已提交、relay未发送 | Outbox待交付 | relay领取并发送 |
| Kafka已接受、delivered未写回 | broker可能已有事件，Outbox仍待交付 | 再发原event_id，消费者去重 |
| 投影事务提交前 | Inbox与view一起回滚 | 保留原Kafka位置，重新处理 |
| 投影事务提交后、offset提交前 | Inbox与view已存在 | 重读时返回Duplicate，再提交位置 |

第三行是重复交付的来源。Outbox解决本地事实不丢失，Inbox和版本规则解决重复与乱序，二者共同构成恢复协议。

### 37.2.3 【进阶】生产者幂等与业务幂等分工

enable.idempotence=true让Kafka生产者协议能够处理其序列范围内的重试。它不能自动识别“进程重启后从数据库再次取出的同一业务事件”。

因此重发必须保留Outbox里的event_id、revision和payload。本章outbox-replay读取原事件直接重投；它不会新建一个Envelope来冒充原发送尝试。有关幂等生产者范围，参见[librdkafka官方说明](https://docs.confluent.io/platform/current/clients/librdkafka/html/md_INTRODUCTION.html)。

### 37.2.4 【精通】超时无法证明对方没收到

生产者等待超时、网络断开或客户端任务取消，都可能发生在broker接收之后。消费者提交offset等待超时，也可能发生在broker已经保存位置之后。

本书的处理是允许重复、恢复后重查，而非把超时翻译成“从未发生”。这与第31章库存RPC和第35章支付收据的未知结果处理是一致的设计思想。

## 37.3 再读一次事件契约

### 37.3.1 【入门】三个编号各回答什么

| 字段 | 回答的问题 | 重试时是否变化 |
| --- | --- | --- |
| aggregate_id | 哪个商品 | 不变 |
| revision | 这个商品的哪次状态修订 | 不变 |
| event_id | 哪条已提交事件 | 不变 |

发生新的商品修改时，revision递增并建立新的event_id。重发旧事实时两个值都保留。Kafka offset是它在某个分区日志中的位置，同一event_id重投可以拥有另一个offset。

### 37.3.2 【入门】先复习完整结构与校验

use serde::{Deserialize, Serialize};
use sha2::{Digest, Sha256};
use uuid::Uuid;

pub const MAX_EVENT_BYTES: usize = 64 * 1024;
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
#[serde(deny_unknown_fields)]
pub struct Snapshot {
    pub id: i64,
    pub name: String,
    pub price_cents: i64,
    pub stock: i32,
    pub listed: bool,
}
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
#[serde(deny_unknown_fields)]
pub struct Envelope {
    pub schema_version: u32,
    pub kind: String,
    pub event_id: Uuid,
    pub aggregate_id: i64,
    pub revision: i64,
    pub occurred_at_unix_ms: i64,
    pub payload: Snapshot,
}
impl Envelope {
    pub fn new(payload: Snapshot, revision: i64) -> Self {
        Self {
            schema_version: 1,
            kind: "product.snapshot.v1".into(),
            event_id: Uuid::new_v4(),
            aggregate_id: payload.id,
            revision,
            occurred_at_unix_ms: chrono::Utc::now().timestamp_millis(),
            payload,
        }
    }
    pub fn validate(&self) -> anyhow::Result<()> {
        anyhow::ensure!(
            self.schema_version == 1 && self.kind == "product.snapshot.v1",
            "unsupported event schema"
        );
        anyhow::ensure!(
            !self.event_id.is_nil()
                && self.aggregate_id > 0
                && self.aggregate_id == self.payload.id,
            "invalid event identity"
        );
        anyhow::ensure!(self.revision > 0, "invalid revision");
        anyhow::ensure!(
            (1..=100).contains(&self.payload.name.trim().chars().count()),
            "invalid product name"
        );
        anyhow::ensure!(
            self.payload.price_cents >= 0 && self.payload.stock >= 0,
            "invalid product values"
        );
        Ok(())
    }
    pub fn encode(&self) -> anyhow::Result<Vec<u8>> {
        self.validate()?;
        let bytes = serde_json::to_vec(self)?;
        anyhow::ensure!(bytes.len() <= MAX_EVENT_BYTES, "event too large");
        Ok(bytes)
    }
    pub fn decode(bytes: &[u8]) -> anyhow::Result<Self> {
        anyhow::ensure!(bytes.len() <= MAX_EVENT_BYTES, "event too large");
        let value: Self = serde_json::from_slice(bytes)?;
        value.validate()?;
        Ok(value)
    }
    pub fn digest(&self) -> anyhow::Result<Vec<u8>> {
        Ok(Sha256::digest(self.encode()?).to_vec())
    }
}

schema_version与kind共同限定协议，aggregate_id必须等于payload.id，revision为正，金额与库存不能负数，商品名长度受限。64KiB上限在反序列化之前检查，避免把任意大小的正文全部交给JSON解析器。

### 37.3.3 【进阶】摘要检查的是规范结构

digest先把已解码、已校验的Envelope重新编码，再计算SHA-256。发送端增加JSON缩进或调整对象字段顺序，不会产生另一个业务内容身份。

但修改event_id、occurred_at_unix_ms、revision或payload任何实际字段都会改变摘要。不能重发时更新事件发生时间；“本次发送时间”应由独立发送记录表达。

### 37.3.4 【精通】快照与增量事件适用规则不同

当前事件携带完整快照，因此revision 3先到时可以直接覆盖revision 1，随后到达的revision 2按Stale处理。这个规则不能直接搬给“库存减少2”的增量事件：跳过中间增量会丢失业务变化，重复执行又可能多扣。

事件协议的含义决定消费者算法。先弄清事件表示状态还是操作，再讨论乱序、缺口与重建。

## 37.4 投影事务怎样保护三个不变量

### 37.4.1 【入门】Inbox和展示行必须一起提交

每次处理先插入consumer_inbox，再按版本更新catalog_view，最后提交。若版本冲突或数据库错误发生，Inbox插入也回滚。

如果先单独提交Inbox，后续view更新失败，重放会被错误地判断为已处理。只把两个INSERT写在同一个函数里不够，必须确认使用的是同一个tx连接。

### 37.4.2 【进阶】墓碑要保留版本

下架事件把listed变成false。catalog_view保留这行及最新revision，普通展示查询再过滤listed。若消费下架后物理删除行，旧的在售快照可能再次INSERT，造成商品复活。

本章的墓碑是业务快照中的listed=false，payload仍是非空JSON；它与Kafka日志压缩协议中“key加null value”的墓碑机制不同。

### 37.4.3 【进阶】一个物理读模型只绑定一个消费者代次

旧实现允许同一个catalog_view库接收不同consumer_name的Inbox记录。这容易诱发错误重建：只换名称，旧view仍在，验证看似通过，却不能证明新代次从空库恢复。

新增迁移将数据库绑定到一个逻辑消费者。历史Inbox只有一个名称时保留它；出现多个名称时迁移显式失败，需要先审查数据，不替操作者任意选择。空库等待第一次绑定。

文件messaging/migrations/0002_projection_identity.sql：
```sql
-- One physical read model belongs to one logical consumer generation.
-- Preserve an existing unambiguous Inbox identity during the upgrade.
DO $$ BEGIN
    IF (SELECT count(DISTINCT consumer_name) FROM consumer_inbox) > 1 THEN
        RAISE EXCEPTION 'multiple Inbox identities: audit before binding this read model';
    END IF;
END $$;
CREATE TABLE projection_identity (
    singleton BOOLEAN PRIMARY KEY DEFAULT true CHECK(singleton),
    consumer_name TEXT NOT NULL CHECK(length(consumer_name) BETWEEN 1 AND 128)
);
INSERT INTO projection_identity(singleton,consumer_name)
SELECT true,min(consumer_name) FROM consumer_inbox
HAVING count(DISTINCT consumer_name)=1;
```

本章消费者名称同时作为Kafka group.id和Inbox的consumer_name，便于初学者保持对应关系。程序启动绑定一次，apply事务也检查绑定，避免其他调用者绕过启动检查。

### 37.4.4 【精通】完整应用逻辑

更新messaging/src/projection.rs：
```rust
use crate::event::{Envelope, Snapshot};
use sqlx::{PgPool, types::Json};

#[derive(Debug, PartialEq, Eq)]
pub enum Applied {
    Duplicate,
    Stale,
    Updated,
}
async fn bind_in_transaction(
    tx: &mut sqlx::Transaction<'_, sqlx::Postgres>,
    consumer: &str,
) -> anyhow::Result<()> {
    anyhow::ensure!(
        !consumer.trim().is_empty() && consumer.chars().count() <= 128,
        "invalid logical consumer name"
    );
    sqlx::query("INSERT INTO projection_identity(singleton,consumer_name) VALUES(true,$1) ON CONFLICT DO NOTHING")
        .bind(consumer).execute(&mut **tx).await?;
    let stored: String =
        sqlx::query_scalar("SELECT consumer_name FROM projection_identity WHERE singleton=true")
            .fetch_one(&mut **tx)
            .await?;
    anyhow::ensure!(
        stored == consumer,
        "read model belongs to another consumer generation"
    );
    Ok(())
}
pub async fn bind_consumer(pool: &PgPool, consumer: &str) -> anyhow::Result<()> {
    let mut tx = pool.begin().await?;
    bind_in_transaction(&mut tx, consumer).await?;
    tx.commit().await?;
    Ok(())
}
pub async fn apply(pool: &PgPool, consumer: &str, event: &Envelope) -> anyhow::Result<Applied> {
    event.validate()?;
    let hash = event.digest()?;
    let mut tx = pool.begin().await?;
    bind_in_transaction(&mut tx, consumer).await?;
    let inserted=sqlx::query("INSERT INTO consumer_inbox(consumer_name,event_id,payload_hash) VALUES($1,$2,$3) ON CONFLICT DO NOTHING")
        .bind(consumer).bind(event.event_id).bind(&hash).execute(&mut *tx).await?.rows_affected();
    if inserted == 0 {
        let stored: Vec<u8> = sqlx::query_scalar(
            "SELECT payload_hash FROM consumer_inbox WHERE consumer_name=$1 AND event_id=$2",
        )
        .bind(consumer)
        .bind(event.event_id)
        .fetch_one(&mut *tx)
        .await?;
        anyhow::ensure!(stored == hash, "event ID reused with different payload");
        tx.commit().await?;
        return Ok(Applied::Duplicate);
    }
    let changed=sqlx::query("INSERT INTO catalog_view(product_id,revision,payload) VALUES($1,$2,$3) ON CONFLICT(product_id) DO UPDATE SET revision=EXCLUDED.revision,payload=EXCLUDED.payload,updated_at=now() WHERE catalog_view.revision<EXCLUDED.revision")
        .bind(event.aggregate_id).bind(event.revision).bind(Json::<&Snapshot>(&event.payload))
        .execute(&mut *tx).await?.rows_affected();
    if changed == 0 {
        let (revision, payload): (i64, Json<Snapshot>) =
            sqlx::query_as("SELECT revision,payload FROM catalog_view WHERE product_id=$1")
                .bind(event.aggregate_id)
                .fetch_one(&mut *tx)
                .await?;
        anyhow::ensure!(
            revision != event.revision || payload.0 == event.payload,
            "same revision has conflicting snapshot"
        );
    }
    tx.commit().await?;
    Ok(if changed == 1 {
        Applied::Updated
    } else {
        Applied::Stale
    })
}
```

INSERT Inbox冲突后读取旧摘要，相同才返回Duplicate。首次出现的事件进入view UPSERT；只有更高revision才能覆盖。没有更新时，再检查相同revision是否具有相同业务快照。相同版本不同内容意味着生产者协议损坏，不能悄悄选择最后到达的一份。

这些检查对最新view与已见event_id有效；它没有建立所有历史revision内容的永久审计表。已被更高版本覆盖、且event_id从未见过的旧快照按Stale保存Inbox。本章不把它夸大为全历史内容审计。

## 37.5 从数据库提交到Kafka位点

### 37.5.1 【入门】处理42，提交43

Kafka已提交位置表达下次继续读取的位置。成功持久化某分区offset 42后提交43。本书关闭自动提交与自动offset存储，显式执行数据库事务，再提交这个位置。

配置项的准确含义见[Kafka 4.0消费者文档](https://kafka.apache.org/40/configuration/consumer-configs/)与[librdkafka配置参考](https://docs.confluent.io/platform/current/clients/librdkafka/html/md_CONFIGURATION.html)。

### 37.5.2 【进阶】客户端实现与边界

messaging/src/kafka.rs：
```rust

    ClientConfig, Message, Offset, TopicPartitionList,
    consumer::{CommitMode, Consumer, StreamConsumer},
    producer::{FutureProducer, FutureRecord},
};
use std::{sync::Arc, time::Duration};

pub fn producer(brokers: &str) -> anyhow::Result<FutureProducer> {
    Ok(ClientConfig::new()
        .set("bootstrap.servers", brokers)
        .set("enable.idempotence", "true")
        .set("acks", "all")
        .set("delivery.timeout.ms", "5000")
        .set("request.timeout.ms", "3000")
        .set("linger.ms", "5")
        .set("queue.buffering.max.kbytes", "10240")
        .create()?)
}
pub async fn send(producer: &FutureProducer, topic: &str, event: &Envelope) -> anyhow::Result<()> {
    let payload = event.encode()?;
    let key = event.aggregate_id.to_string();
    tokio::time::timeout(
        Duration::from_secs(8),
        producer.send(
            FutureRecord::to(topic).key(&key).payload(&payload),
            Duration::from_millis(250),
        ),
    )
    .await
    .context("producer await budget exhausted; delivery may still happen")?
    .map_err(|(error, _)| anyhow::anyhow!("Kafka delivery failed: {error}"))?;
    Ok(())
}

        .set("enable.auto.commit", "false")
        .set("enable.auto.offset.store", "false")
        .set("auto.offset.reset", "earliest")
        .set("isolation.level", "read_committed")
        .set("max.poll.interval.ms", "30000")
        .set("session.timeout.ms", "10000")
        .set("socket.timeout.ms", "3000")
        .create()?;
    consumer.subscribe(&[topic])?;
    Ok(Arc::new(consumer))
}
pub fn decode_message(message: &impl Message) -> anyhow::Result<Envelope> {
    let event = Envelope::decode(message.payload().context("empty Kafka payload")?)?;
    let key = std::str::from_utf8(message.key().context("missing aggregate key")?)?;
    anyhow::ensure!(
        key == event.aggregate_id.to_string(),
        "Kafka key does not match event aggregate"
    );
    Ok(event)
}
pub async fn commit_processed(
    consumer: Arc<StreamConsumer>,
    topic: String,
    partition: i32,
    offset: i64,
) -> anyhow::Result<()> {
    let mut positions = TopicPartitionList::new();
    positions.add_partition_offset(
        &topic,
        partition,
        Offset::Offset(offset.checked_add(1).context("offset overflow")?),
    )?;
    tokio::time::timeout(
        Duration::from_secs(5),
        tokio::task::spawn_blocking(move || consumer.commit(&positions, CommitMode::Sync)),
    )
    .await
    .context("offset commit wait budget exhausted")???;
    Ok(())
}
```

消息key使用aggregate_id的十进制字符串，解码时检查它与Envelope一致。不能只校验JSON而忽略分区key，否则生产者的路由错误会被隐藏。

生产者使用有界发送队列、交付时限与外层等待预算；消费者对同步offset提交使用spawn_blocking，避免阻塞Tokio执行线程。外层timeout结束等待不保证阻塞任务已经停止；发生这种未知结果时进程退出，由Inbox保护重读。

### 37.5.4 【精通】为什么不能把最后完成的位置直接提交

若并行处理offset 42、43、44，44先完成时提交45，会把仍未持久化的42和43一起跨过。安全的提交水位必须是“此前每条都完成”的连续边界。

## 37.6 relay的责任与重试上限

### 37.6.1 【入门】领取不是删除

relay从product_outbox领取一条尚未交付、重试时间已到、租约可用的事件。SKIP LOCKED让多个relay避开彼此正在领取的行；每次领取生成新lease_token。

broker确认后，delivered更新必须匹配event_id和当前token。旧进程拿着过期token，在新持有者已经领取后不能替新持有者确认。当前delivered条件检查token，没有额外要求租约未到期；若尚未发生接管，同一token仍可确认。不要把它与第36章订单步骤必须同时匹配未过期租约的规则混淆。

### 37.6.2 【进阶】长期失败不能溢出计数器

前章领取SQL采用attempts+1，极长时间反复失败最终可能溢出INT。本章改成先提升到bigint相加，再饱和到i32::MAX。达到计数上限仍能发送，不会因此永久卡死。

messaging/src/store.rs末尾的领取与回写实现更新为：
```rust
#[derive(sqlx::FromRow)]
pub struct Lease {
    pub event_id: Uuid,
    pub payload: Json<Envelope>,
    pub attempts: i32,
    pub lease_token: Uuid,
}
pub async fn claim_one(pool: &PgPool) -> Result<Option<Lease>, sqlx::Error> {
    let token = Uuid::new_v4();
    sqlx::query_as::<_,Lease>(
        "WITH candidate AS (SELECT event_id FROM product_outbox WHERE delivered_at IS NULL AND next_attempt_at<=now() AND (leased_until IS NULL OR leased_until<now()) ORDER BY occurred_at,event_id FOR UPDATE SKIP LOCKED LIMIT 1) UPDATE product_outbox AS o SET lease_token=$1,leased_until=now()+interval '30 seconds',attempts=LEAST(o.attempts::bigint+1,2147483647)::int FROM candidate AS c WHERE o.event_id=c.event_id RETURNING o.event_id,o.payload,o.attempts,o.lease_token"
    ).bind(token).fetch_optional(pool).await
}
pub async fn delivered(pool: &PgPool, lease: &Lease) -> Result<bool, sqlx::Error> {
    Ok(sqlx::query("UPDATE product_outbox SET delivered_at=now(),lease_token=NULL,leased_until=NULL,last_error=NULL WHERE event_id=$1 AND lease_token=$2 AND delivered_at IS NULL")
        .bind(lease.event_id).bind(lease.lease_token).execute(pool).await?.rows_affected()==1)
}
pub async fn failed(pool: &PgPool, lease: &Lease, error: &str) -> Result<bool, sqlx::Error> {
    let bounded: String = error.chars().take(500).collect();
    Ok(sqlx::query("UPDATE product_outbox SET next_attempt_at=now()+($3::bigint*interval '1 second'),lease_token=NULL,leased_until=NULL,last_error=$4 WHERE event_id=$1 AND lease_token=$2 AND delivered_at IS NULL")
        .bind(lease.event_id).bind(lease.lease_token).bind(retry_delay_secs(lease.attempts)).bind(bounded)
        .execute(pool).await?.rows_affected()==1)
}
```

retry_delay_secs仍将等待封顶300秒；last_error截断到500个字符。计数饱和与重试时限分别解决存储溢出和重试频率，不代表允许忽略长期积压。

### 37.6.3 【进阶】运行入口保持简单可复查

messaging/src/bin/outbox-relay.rs：
```rust
use anyhow::Context;
use messaging::{kafka, store};
use std::time::Duration;
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let pool = sqlx::postgres::PgPoolOptions::new()
        .max_connections(4)
        .acquire_timeout(Duration::from_secs(1))
        .connect(&std::env::var("CATALOG_DATABASE_URL")?)
        .await?;
    let producer = kafka::producer(&std::env::var("KAFKA_BROKERS")?)?;
    let topic =
        std::env::var("KAFKA_TOPIC").unwrap_or_else(|_| "rustmall.catalog.snapshots.v1".into());
    let shutdown = messaging::signal();
    tokio::pin!(shutdown);
    loop {
        tokio::select! {
            ()=&mut shutdown=>break,
            ()=tokio::time::sleep(Duration::from_millis(200))=>{}
        }
        let lease = tokio::time::timeout(Duration::from_secs(3), store::claim_one(&pool)).await??;
        let Some(lease) = lease else { continue };
        anyhow::ensure!(
            lease.event_id == lease.payload.0.event_id,
            "outbox row and payload event IDs differ"
        );
        match kafka::send(&producer, &topic, &lease.payload.0).await {
            Ok(()) => {
                let owned =
                    tokio::time::timeout(Duration::from_secs(3), store::delivered(&pool, &lease))
                        .await??;
                if !owned {
                    eprintln!(
                        "acknowledged event {}, but lease ownership changed",
                        lease.event_id
                    );
                }
            }
            Err(error) => {
                tokio::time::timeout(
                    Duration::from_secs(3),
                    store::failed(&pool, &lease, &error.to_string()),
                )
                .await
                .context("outbox retry-state write timed out")??;
                eprintln!("event {} retry scheduled: {error}", lease.event_id);
            }
        }
    }
    tokio::time::timeout(Duration::from_secs(5), pool.close()).await?;
    Ok(())
}
```

领取、确认和失败回写都有等待预算。发送结果不明确时保留重试责任；原事件身份不变。若进程在处理期间被杀，租约到期后其他relay可再次领取。

### 37.6.4 【精通】按key分区仍要检查版本

同一key通常进入同一分区，但多个relay可以先领取不同revision，再以不同速度发送。Kafka分区内有日志追加顺序，不会替业务重建“哪个数据库版本先提交”。

因此本章继续要求消费者按revision单调更新。分区key与版本条件分别解决路由和业务收敛，不能互相替代。

import json
import os

ROOT = Path(__file__).resolve().parents[1]
ROLES = ['catalog', 'users', 'payments', 'orders', 'worker', 'catalog-http', 'edge', 'relay', 'projection', 'projection-rebuild']

            key, value = line.split('=', 1)
            if not key or not all(c.isascii() and (c.isalnum() or c == '_') for c in key):

        for name in read(path): environment.pop(name, None)

    if errors: raise SystemExit('\n'.join(errors))

        print('PASS isolated role profile: ' + args.role); return
    binaries = args.bin_dir or Path(environment.get('CARGO_TARGET_DIR', str(ROOT/'target')))/'debug'
    if args.role in ('relay', 'projection', 'projection-rebuild'):
        if args.migrate and args.role == 'relay':

        binary = 'outbox-relay' if args.role == 'relay' else ('projection-migrate' if args.migrate else 'projection-worker')
        command = [str((binaries/binary).resolve())]

        command = [str((binaries/('catalog-migrate' if args.migrate else 'catalog')).resolve())]
    else:
        if args.migrate and args.role not in ('users', 'payments', 'orders'):

                   'migrate-'+args.role if args.migrate else args.role]
    if not Path(command[0]).is_file():
        raise SystemExit('Build first: cargo build --locked --workspace --all-features --bins')
    os.chdir(ROOT)
    os.execve(command[0], command, environment)

## 37.9 主动重投同一事实

### 37.9.1 【入门】建立可复查的重投工具

新增messaging/src/bin/outbox-replay.rs，并在Cargo.toml中把该bin声明为required-features=["kafka"]。完整工程已包含声明。
```rust
//! Deliberately duplicate an existing immutable event in the isolated lab.
use messaging::{event::Envelope, kafka};
use sqlx::types::Json;
use std::time::Duration;
use uuid::Uuid;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let args: Vec<_> = std::env::args().skip(1).collect();
    anyhow::ensure!(
        args.len() == 2 && args[0] == "--local-lab",
        "usage: outbox-replay --local-lab EVENT_UUID"
    );
    let id = Uuid::parse_str(&args[1])?;
    let pool = sqlx::postgres::PgPoolOptions::new()
        .max_connections(1)
        .acquire_timeout(Duration::from_secs(1))
        .connect(&std::env::var("CATALOG_DATABASE_URL")?)
        .await?;
    let (event_id, aggregate_id, revision, Json(event)): (Uuid, i64, i64, Json<Envelope>) =
        tokio::time::timeout(Duration::from_secs(3), sqlx::query_as(
            "SELECT event_id,aggregate_id,revision,payload FROM product_outbox WHERE event_id=$1")
            .bind(id).fetch_one(&pool)).await??;
    anyhow::ensure!(
        event_id == event.event_id
            && aggregate_id == event.aggregate_id
            && revision == event.revision,
        "outbox row and envelope identity differ"
    );
    let producer = kafka::producer(&std::env::var("KAFKA_BROKERS")?)?;
    kafka::send(&producer, &std::env::var("KAFKA_TOPIC")?, &event).await?;
    pool.close().await;
    println!("replayed original event {id}; no source rows changed");
    Ok(())
}
```

它按UUID读取原Outbox记录，检查行身份与Envelope一致，发送原内容。它不修改商品、delivered标记或事件时间，不生成新event_id。

## 37.10 并行重建，不清空正在服务的数据库

### 37.10.1 【入门】四个对象必须一起思考

| 对象 | 正常重启 | 建立新代次 |
| --- | --- | --- |
| Kafka group.id | 保留 | 使用新名称 |
| Inbox consumer_name | 保留 | 与新group一致 |
| catalog_view物理库 | 保留 | 独立空库 |
| projection_identity | 保留原绑定 | 在新库绑定新名称 |

只清view、保留Inbox会把应重建的事件全部当成Duplicate。只建空库、沿用旧group可能从已提交末尾开始，永久缺少历史。只换group而复用旧库则无法证明独立恢复；本章绑定检查会拒绝它。

### 37.10.3 【进阶】对账命令完整实现

新增messaging/src/bin/projection-audit.rs：
```rust
//! Run only after stopping business writers and draining the relay/consumer.
//! Separate database snapshots cannot prove an atomic live cross-service view.
use messaging::event::Snapshot;
use sqlx::{PgPool, types::Json};
use std::time::Duration;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    anyhow::ensure!(
        std::env::args().nth(1).as_deref() == Some("--writers-stopped"),
        "stop catalog writers and Saga worker; pass --writers-stopped to acknowledge the audit prerequisite"
    );
    let catalog = connect("CATALOG_DATABASE_URL").await?;
    let projection = connect("PROJECTION_DATABASE_URL").await?;
    tokio::time::timeout(Duration::from_secs(10), audit(&catalog, &projection)).await??;
    catalog.close().await;
    projection.close().await;
    Ok(())
}
async fn connect(name: &str) -> anyhow::Result<PgPool> {
    Ok(sqlx::postgres::PgPoolOptions::new()
        .max_connections(1)
        .acquire_timeout(Duration::from_secs(1))
        .connect(&std::env::var(name)?)
        .await?)
}
async fn audit(catalog: &PgPool, projection: &PgPool) -> anyhow::Result<()> {
    let mut source = catalog.begin().await?;
    sqlx::query("SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY")
        .execute(&mut *source)
        .await?;
    let mut target = projection.begin().await?;
    sqlx::query("SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY")
        .execute(&mut *target)
        .await?;
    let pending: i64 =
        sqlx::query_scalar("SELECT count(*) FROM product_outbox WHERE delivered_at IS NULL")
            .fetch_one(&mut *source)
            .await?;
    anyhow::ensure!(pending == 0, "relay not drained: {pending} pending events");
    type Row = (i64, i64, Json<Snapshot>);
    let expected: Vec<Row> = sqlx::query_as("SELECT id,revision,jsonb_build_object('id',id,'name',name,'price_cents',price_cents,'stock',stock,'listed',delisted_at IS NULL) FROM products ORDER BY id LIMIT 100001")
        .fetch_all(&mut *source).await?;
    let actual: Vec<Row> = sqlx::query_as(
        "SELECT product_id,revision,payload FROM catalog_view ORDER BY product_id LIMIT 100001",
    )
    .fetch_all(&mut *target)
    .await?;
    anyhow::ensure!(
        expected.len() <= 100_000 && actual.len() <= 100_000,
        "local audit row limit exceeded; use a paginated production reconciliation job"
    );
    let equal = expected.len() == actual.len()
        && expected
            .iter()
            .zip(&actual)
            .all(|(a, b)| a.0 == b.0 && a.1 == b.1 && a.2.0 == b.2.0);
    anyhow::ensure!(
        equal,
        "projection differs from authoritative products (source={}, target={}); do not cut over",
        expected.len(),
        actual.len()
    );
    source.commit().await?;
    target.commit().await?;
    println!(
        "PASS quiescent read-model audit: {} products including delisted tombstones",
        actual.len()
    );
    Ok(())
}
```

该本地命令要求显式确认写入已经暂停。分别在两个数据库开启只读Repeatable Read事务，检查Outbox已排空，逐行比较商品ID、revision和所有快照字段，包含listed=false。规模超过10万行显式失败，生产应改成分页或分片对账。

两个数据库各自的快照不构成跨库原子快照。因此必须先停catalog写入和Saga worker，并让传播追平；--writers-stopped只是操作前提确认，程序不能通过一个布尔参数强制其他进程停写。

真正上线读路径时，还要约定可接受陈旧度、展示语义、读写后可见性和切回方案。保留原代次至回滚窗口结束，不能在新库刚刚追平时立刻销毁旧库。

## 37.11 毒消息、诊断与恢复责任

### 37.11.1 【入门】停止比静默跳过更容易证明

未知schema_version、损坏JSON、缺少key或身份冲突会使当前消费者退出，不提交该失败消息的位置。这样保持失败证据，但该分区的进度无法继续，需要操作者处理。

本章没有自动死信队列。捕获异常后直接continue，既没有保存修复责任，也可能在提交后续位置时跨过失败事实。

### 37.11.2 【进阶】按身份追踪，而非先清表

排查顺序是：确定商品id和revision；在catalog查Outbox原event_id；确认delivered状态；从日志定位topic/partition/offset；查对应Inbox；最后比较view版本与payload。

last_error用于定位发送失败，消费者上下文用于定位处理失败。未知内容不要直接完整粘贴进共享日志；先保留可复查的位置与错误类别。

### 37.11.3 【进阶】故障现象与具体检查

| 现象 | 先核对 | 处理方向 |
| --- | --- | --- |
| 新投影库不存在 | 是否显式运行extend脚本 | 旧PG卷不会重跑init.sql |
| 初次连上Kafka随后失败 | advertised.listeners与59093 | 同步broker地址与三个profile |
| Outbox一直增加 | broker、relay进程、next_attempt_at | 保留原事件并修复依赖 |
| Outbox为零但view缺行 | 消费进程、错误位点、Inbox | 交付不等于已应用 |
| 更名后启动即失败 | projection_identity绑定 | 正常重启保留身份，重建用空库 |
| 重建消费到末尾仍缺旧商品 | 留存窗口、旧group误复用 | 核查历史缺口，不能宣称重建成功 |
| 同一event_id内容冲突 | 原Outbox与发出内容 | 修复生产者或受控数据损坏 |
| 同版本内容冲突 | catalog版本写入规则 | 禁止任意覆盖，保留失败证据 |
| 重启后反复停在同一offset | 毒消息未解决 | 修复协议或制定审计过的隔离流程 |
| 对账偶发失败 | 是否仍有业务写入 | 暂停写入并等待传播，或设计水位对账 |

### 37.11.4 【精通】监控必须覆盖传播前后

至少观察最老待交付Outbox年龄、待交付量、重试次数、消费者处理错误、提交进度、投影更新时间和业务版本差。lag低可能只是relay没把新事实发出来；Outbox低也可能是消费者一直写失败。

第38章会把这些业务身份与指标接入可观测系统。本章先确保错误中带有足够的事件位置，避免只有一个无法复现的“消费失败”。

### 37.12.3 【入门练习】为什么显示8却不能保证还能买8

题目：投影显示stock8，能否直接按这个数字确认下一笔订单？

参考答案：不能。投影可能落后，其他订单也可能并发预留。它可以辅助展示，最终预留仍由权威库存事务串行裁决。同样，展示0也可能是暂时落后的状态，需按产品体验约定刷新与提示。

### 37.12.4 【进阶练习】设计一次不会复活商品的乱序实验

题目：先应用revision3、listed=false，再应用新event_id的revision2、listed=true，应得到什么？

参考答案：第一条Updated，第二条Stale。两条合法事件可各有Inbox记录，view仍是revision3且listed=false。接着复用第一条event_id但改stock，应失败且不提交新业务修改。数据库回归测试提供这一组合。

### 37.12.5 【进阶练习】为什么清空view不够

题目：为了重建只执行TRUNCATE catalog_view，保留Inbox，再把group offset移到最早，会发生什么？

参考答案：旧事件被Inbox判断为Duplicate，不再恢复展示行。重建应独立准备新group、新Inbox与新view物理库，随后对账。不要在正在服务的旧库中试验清表。

### 37.12.6 【精通练习】不停写的生产对账怎样设计

题目：本章暂停写入获得稳定比较。若业务不能暂停，应如何增强协议？

参考答案：需要确定权威快照边界，保存快照对应的版本或增量水位，再持续消费边界后的变化，并对照同一逻辑时点核查。跨分区不能只保存一个“最新offset”，必须保存分区位置向量或其他有明确语义的边界。还需处理快照期间新增、下架与修改的商品。两个普通SELECT或一句最终一致性，均不足以证明完整。

### 37.12.7 【精通练习】为毒消息隔离补齐责任

题目：若业务要求跳过毒消息继续处理，最少还要保存什么？

参考答案：保存原topic/partition/offset、原始事件或可验证归档引用、错误类别、隔离身份、审批和修复记录，并制定修复后的重放与去重规则。隔离记录提交和offset推进也形成新的原子性边界，必须推演崩溃窗口。没有这些机制，本章选择停止而不是自动跨过。

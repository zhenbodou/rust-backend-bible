# 第 9 章 HTTP、REST 与 JSON 全解

从本章开始进入 Web 后端。后端程序的本质，是一个一直在监听网络端口的进程：收到 HTTP 请求，执行业务逻辑，读写数据库，返回 HTTP 响应。写后端之前必须弄懂这个“协议”本身。本章不写 Rust 代码，而是系统讲解 HTTP 协议、REST 设计规范和 JSON，项目部分为 RustMall 编写一份完整的 API 设计文档--专业团队在写第一行接口代码之前，都会先把接口设计清楚。

## 9.1 一次请求的完整旅程

### 9.1.1 【入门】从输入网址到看到页面

用户在 App 中点开“商品详情”，App 向 https://api.rustmall.com/api/v1/products/42 发起请求。用去餐厅点餐来类比：

| 步骤 | 发生了什么 | 类比 | 典型耗时 |
| --- | --- | --- | --- |
| 1. DNS 解析 | 把域名 api.rustmall.com 翻译成IP地址 | 查餐厅地址 | 几毫秒（有缓存时接近0） |
| 2. TCP 连接 | 三次握手，建立可靠的双向通道 | 走进餐厅坐下 | 1 个往返（RTT） |
| 3. TLS 握手 | 协商加密算法、验证服务器证书 | 拉上包间门帘、确认是真餐厅 | 1 个 RTT（TLS 1.3） |
| 4. 发送 HTTP 请求 | 方法、路径、头部、正文 | 点菜 | 半个 RTT |
| 5. 服务端处理 | 路由、鉴权、查缓存、查数据库、组装响应 | 厨房做菜 | 容易在这里变慢 |
| 6. 返回 HTTP 响应 | 状态码、头部、JSON 正文 | 上菜 | 半个 RTT + 传输时间 |

同一个连接上的后续请求可以跳过第 1~3 步（连接复用，9.5 节）。生产环境中，请求在到达你的 Rust 程序之前通常还会经过负载均衡器、API 网关（第 27 章）、Kubernetes 的 Ingress（第 23 章），HTTPS 往往在这些组件上就被解密了，后端服务之间走内网。

### 9.1.2 【进阶】分层的网络协议

| 层 | 协议 | 负责什么 | 后端开发中的体现 |
| --- | --- | --- | --- |
| 应用层 | HTTP、gRPC、WebSocket、PostgreSQL协议、Redis 协议 | 业务含义的数据格式 | 你写的代码直接面对这一层 |
| 安全层 | TLS | 加密、防篡改、身份验证 | 证书、rustls（第 27 章） |

| 层 | 协议 | 负责什么 | 后端开发中的体现 |
| --- | --- | --- | --- |
| 传输层 | TCP、UDP（QUIC） | 端到端传输；TCP 提供可靠字节流，UDP 不保证可靠与顺序，QUIC 在 UDP 上实现可靠流 | TcpListener::bind("0.0.0.0:8080")（第 11 章） |
| 网络层 | IP | 寻址与路由 | IP 地址、Kubernetes 的 Pod IP |

端口：一台机器上可以运行很多个服务，端口号区分它们。HTTP 默认 80，HTTPS 默认 443，PostgreSQL 5432，Redis 6379，Kafka 9092。服务监听 0.0.0.0:8080 表示接受来自任何网卡的连接；监听 127.0.0.1:8080 则只接受本机连接--放进 Docker 容器后外部就访问不到了，这是第 20章的一个常见坑。

## 9.2 HTTP 报文

### 9.2.1 【入门】请求长什么样

HTTP/1.1 是纯文本协议，可以直接读：
```text
POST /api/v1/orders?source=app HTTP/1.1
Host: api.rustmall.com
Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOjd9.xxxx
Idempotency-Key: 7b1c6e0a-9f1e-4c1d-8a2e-3f0e9d6c5b4a
Content-Length: 39

{"product_id": 42, "quantity": 2}
```

| 部分 | 内容 | 说明 |
| --- | --- | --- |
| 请求行 | POST /api/v1/orders?source=app HTTP/1.1 | 方法、请求目标（路径 + 查询字符串）、协议版本 |
| 头部（headers） | Host: ... 等多行 | 键值对，名称不区分大小写 |
| 空行 |  | 标志头部结束 |
| 正文（body） | JSON | 可选，GET 请求通常没有正文 |

### 9.2.2 【入门】URL 的结构
```text
https://api.rustmall.com:443/api/v1/products?
keyword=%E9%94%AE%E7%9B%98&page=2#reviews
└─┬─┘   └───────┬──────┘ └┬┘└──────┬───────┘ └─────────────┬───────────────┘ └─┬───┘
 协议        主机        端口    路径                  查询字符串              片段
```

路径（path）标识“资源”；查询字符串（query string）用 ? 开始、&amp; 分隔，用于筛选、分页、排序。

片段（# 之后）只在浏览器内使用，不会发送到服务器。

百分号编码：URL 只能包含有限的 ASCII 字符，中文和空格等要编码。“键盘”的 UTF-8 字节是 E994 AE E7 9B 98 ，编码后就是 %E9%94%AE%E7%9B%98 。框架会自动解码，第 12 章 Axum 的Query 提取器拿到的已经是“键盘”。用 curl 手工调试时要小心：curl "...? keyword=键盘" 通常也能工作，但包含空格、&amp; 、# 的值必须编码，可以用 curl -G -- data-urlencode "keyword=机械 键盘" 。

### 9.2.3 【入门】响应长什么样
```text
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/orders/1001
X-Request-Id: 0f8c2a1e7d
Content-Length: 86

{"id": 1001, "status": "pending", "total_cents": 39800, "created_at": "2026-10-10T08:30:00Z"}
```

响应由状态行（协议版本、状态码、原因短语）、头部、空行、正文组成。Location 头告诉客戶端新创建的资源在哪里。

## 9.3 方法与状态码

### 9.3.1 【入门】HTTP 方法

| 方法 | 含义 | 安全 | 幂等 | 有正文 | RustMall 示例 |
| --- | --- | --- | --- | --- | --- |
| GET | 读取资源 | 是 | 是 | 通常不使用；语义不通用 | GET /api/v1/products/42 |
| POST | 创建资源 / 执行动作 | 否 | 否 | 是 | POST /api/v1/orders |
| PUT | 整体替换资源 | 否 | 是 | 是 | PUT /api/v1/products/42 |
| PATCH | 部分修改资源 | 否 | 不一定 | 是 | PATCH /api/v1/products/42 （只改价格） |
| DELETE | 删除资源 | 否 | 是 | 一般没有 | DELETE /api/v1/cart/items/42 |
| HEAD | 只取响应头 | 是 | 是 | 否 | 检查资源是否存在 |
| OPTIONS | 询问支持的能力 | 是 | 是 | 否 | 浏览器跨域预检（9.6 节） |

安全：不修改服务器状态。GET 必须是安全的--网络组件、浏览器预加载、搜索引擎爬虫都可能随意发起 GET。曾经有系统把“删除”做成 GET 链接，结果被爬虫把数据删光。

幂等：同一个请求执行一次和执行多次，服务器状态相同。PUT 把商品价格设为 199 元，执行十次结果一样；POST 下单执行十次就是十个订单。网络超时后客戶端会自动重试，幂等的请求可以放心重试；非幂等的 POST 要通过 Idempotency-Key （9.4 节、第 29 章）变得可以安全重试。

### 9.3.2 【入门】状态码

状态码的第一位表示类别：2xx 成功，3xx 重定向，4xx 客戶端的错，5xx 服务端的错。后端最常用的如下：

| 状态码 | 名称 | 何时返回 |
| --- | --- | --- |
| 200 | OK | 查询成功、修改成功并返回新数据 |
| 201 | Created | 创建成功，配合 Location 头 |
| 202 | Accepted | 已接收但尚未处理完（异步任务） |
| 204 | No Content | 成功且无正文（删除成功） |
| 301 / 308 | 永久重定向 | 接口地址变更（308 保持原方法） |
| 304 | Not Modified | 客戶端缓存仍有效（9.4.3 节 ETag） |
| 400 | Bad Request | 请求格式错误：JSON 解析失败、缺少必填字段 |
| 401 | Unauthorized | 未登录：没有令牌、令牌无效或过期 |
| 403 | Forbidden | 已登录但无权限 |
| 404 | Not Found | 资源不存在（也用于对无权访问者隐藏资源的存在） |
| 405 | Method Not Allowed | 路径存在但不支持该方法 |
| 409 | Conflict | 与当前状态冲突：用户名已存在、库存不足、订单状态不允许此操作 |
| 413 | Content Too Large | 请求体超过限制 |
| 415 | Unsupported Media Type | Content-Type 不是服务端支持的格式 |
| 422 | Unprocessable Content | 格式正确但业务校验失败：价格为负、数量超限 |
| 429 | Too Many Requests | 触发限流，配合 Retry-After 头（第 39 章） |
| 500 | Internal Server Error | 服务端 bug 或未预料的错误 |
| 502 | Bad Gateway | 网关联系不上上游服务 |
| 503 | Service Unavailable | 服务过载、维护、依赖不可用、熔断开启 |
| 504 | Gateway Timeout | 网关等待上游超时 |

400 与 422 的区别：400 是“看不懂”（JSON 语法错误、类型不对），422 是“看得懂但不接受”（数量是1000，超过上限）。401 与 403 的区别：401 是“你是谁”没回答，403 是“知道你是谁，但你不能做”。

### 9.3.3 【进阶】领域错误到状态码的映射

第 4 章的 ErrorKind 把领域错误分成了四类，它们与 HTTP 状态码的对应关系在本章定下来，第 12 章在 Axum 中实现：

| ErrorKind | HTTP 状态码 | 响应体 code 字段 |
| --- | --- | --- |
| InvalidInput | 422（JSON 本身无法解析时由框架返回 400） | INVALID_INPUT |
| NotFound | 404 | NOT_FOUND |
| Conflict | 409 | CONFLICT |
| Internal | 500（响应体不含错误细节） | INTERNAL |

未登录（401）、无权限（403）、限流（429）由认证与网关层产生，不属于领域错误，第 16、31 章加入。

## 9.4 常用头部

### 9.4.1 【入门】内容协商与身份

| 头部 | 方向 | 作用 | 示例 |
| --- | --- | --- | --- |
| Content-Type | 双向 | 正文的格式 | application/json 、multipart/fo rm-data |
| Content-Length | 双向 | 正文字节数 | 86 |
| Accept | 请求 | 客戶端能接受的格式 | application/json |
| Accept-Encoding / Content- E ncoding | 请求 /响应 | 压缩算法 | gzip, br |
| Accept-Language | 请求 | 客戶端语言偏好 | zh-CN,zh;q=0.9 |
| Authorization | 请求 | 身份凭证 | Bearer &lt;JWT&gt; （第 16 章） |
| User-Agent | 请求 | 客戶端类型 | RustMall-iOS/3.2.0 |
| Location | 响应 | 新资源或重定向地址 | /api/v1/orders/1001 |
| Retry-After | 响应 | 多久后再试 | 30 |

### 9.4.2 【进阶】后端工程中的自定义头部

| 头部 | 作用 | 章节 |
| --- | --- | --- |
| X-Request-Id | 一次请求的唯一编号，写进所有日志，并返回给客戶端，用户反馈问题时报这个编号就能定位日志 | 第 15章 |
| traceparent | W3C 链路追踪上下文，在微服务之间传递 | 后续可观测性章节 |
| Idempotency-Key | 客戶端为一次“下单意图”生成的 UUID，服务端据此去重，使 POST 可安全重试 | 第 29章 |
| X-Forwarded-For | 经过代理后的客戶端真实 IP（可被伪造，只信任自己的代理添加的部分） | 第 27章 |

新设计的头部已不推荐加 X- 前缀，但 X-Request-Id 等已经是事实标准，继续使用。

### 9.4.3 【精通】缓存相关头部

Cache-Control: no-store ：不要缓存（订单、个人信息等所有用户相关的响应都应该这样）。

Cache-Control: public, max-age=60 ：任何中间代理和浏览器都可以缓存 60 秒（商品列表、分类树等公共数据）。

ETag / If-None-Match ：服务端给响应一个版本标识，客戶端下次请求时带上，数据没变就返回304 且没有正文，节省带宽。

ETag / If-Match ：反过来用于并发控制--客戶端修改商品时带上它读到的版本，版本已变就返回 412 Precondition Failed，防止“后写覆盖前写”。这是第 7.7.2 节乐观并发在 HTTP 层的体现。

### 9.4.4 第 9.1~9.4 节练习

1. 用 curl -v https://www.rust-lang.org -o /dev/null 观察完整的请求与响应头，标出 TLS握手、请求行、状态行和 3 个你认识的响应头。

2. 判断以下操作应该用什么方法、成功时返回什么状态码：查询订单列表；取消订单；把购物车中某商品数量改为 3；删除收货地址；上传商品图片。

3. 设计题：用户重复提交同一个“修改昵称”请求是否安全？“给账戶充值 100 元”呢？分别说明原因，以及后者应如何改造才能安全重试。

4. 解释为什么不应该用 GET 请求实现“清空购物车”。

## 9.5 HTTP 版本与连接

### 9.5.1 【入门】三个主流版本

| 版本 | 传输 | 主要特点 | 后端中的位置 |
| --- | --- | --- | --- |
| HTTP/1.1 | TCP，纯文本 | 持久连接（keep-alive）；同一连接上的请求必须排队，前一个慢会拖住后一个（队头阻塞） | 仍然是服务间最常见的协议；调试最方便 |
| HTTP/2 | TCP，二进制帧 | 在协议协商的并发流上限内多路复用；使用 HPACK，仍受 TCP 丢包影响 | gRPC 建立在 HTTP/2 之上（第25 章）；浏览器到网关 |
| HTTP/3 | UDP 上的QUIC | 消除 TCP 层的队头阻塞；连接建立更快；切换网络（Wi-Fi 到 4G）时连接不断 | 主要在 CDN、网关一侧；后端服务之间较少使用 |

Rust 生态中，hyper 库同时实现了 HTTP/1.1 和 HTTP/2，Axum（第 12 章）和 reqwest（第 27 章）都建立在 hyper 之上，对你的代码而言版本差异几乎是透明的。

### 9.5.2 【进阶】连接复用与连接池

建立一个 HTTPS 连接需要 TCP 握手和 TLS 握手两到三个往返；跨机房时一个往返就是几十毫秒。所以：

客戶端必须复用连接：在服务里调用其他 HTTP 服务时，整个进程共用一个 reqwest::Client（它内部维护连接池），而不是每次请求都新建一个--这是第 27 章网关最重要的性能要点之一。

服务端要设置合理的空闲超时：长期空闲的连接占用文件描述符和内存。

数据库连接（第 14 章）和 Redis 连接（第 18 章）同样使用连接池，原理完全相同。

### 9.5.3 【精通】超时的分层

一次 HTTP 调用可分别限制连接、请求发送、首字节等待与整体操作。整体必须有有限预算，阶段限制用于更快定位和控制等待；已有整体上界时，不能说少一个独立阶段限制就必然无限等待。第 39 章将根据剩余端到端预算分配下游等待，避免每层都重新获得一份完整总预算。

## 9.6 状态管理与跨域

### 9.6.1 【入门】HTTP 是无状态的

服务器不会记得上一个请求是谁发的。为了“记住登录状态”，有两类方案：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Session+Cookie | 服务端保存会话数据，给浏览器一个随机 ID 放在 Cookie 中 | 可随时让会话失效；Cookie由浏览器自动携带 | 多实例部署要共享会话存储（如Redis）；App 和第三方调用不方便 |

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| Token（如JWT） | 服务端签发一个带签名的令牌，客戶端每次放在Authorizatio n 头中 | 服务端无状态，任何实例都能独立验证；适合 App、微服务 | 令牌签发后到期前难以撤销，需要短有效期 +刷新令牌 |

RustMall 使用 JWT 访问令牌 + 存在 Redis 中的刷新令牌（第 16 章）。

### 9.6.2 【进阶】Cookie 的安全属性

如果使用 Cookie 保存会话，必须设置：HttpOnly （JavaScript 无法读取，防 XSS 窃取）、Secure（只在 HTTPS 下发送）、SameSite=Lax 或 Strict （防跨站请求伪造 CSRF）。

### 9.6.3 【进阶】跨域资源共享 CORS

浏览器的同源策略：https://shop.rustmall.com 页面中的 JavaScript，默认不能读取https://api.rustmall.com 的响应（协议、域名、端口任一不同即为跨域）。要允许跨域，后端必须在响应中明确声明：
```text
# 浏览器先发一个“预检”请求（复杂请求才会发：带自定义头、非简单方法、JSON 正文等）
OPTIONS /api/v1/orders HTTP/1.1
Origin: https://shop.rustmall.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type, authorization

# 后端回答允许
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://shop.rustmall.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, authorization
Access-Control-Max-Age: 600
```

要点：

CORS 是浏览器的限制，curl、App、服务之间的调用不受影响。所以“curl 能调通，前端报跨域错误”是典型现象。

生产环境只允许自己的前端域名，不要用 Access-Control-Allow-Origin: * ，尤其是需要携带Cookie 时（此时 * 本身就是不允许的）。

第 12 章用 tower-http 的 CorsLayer 一行配置完成。

## 9.7 REST 设计规范

### 9.7.1 【入门】核心原则：资源 + 方法

REST 是一套 API 设计风格，核心是：URL 用名词表示资源，HTTP 方法表示动作。

| 好的设计 | 不好的设计 | 问题 |
| --- | --- | --- |
| GET/api/v1/products/42 | GET /api/getProduct?id=42 | 动词进了 URL |
| POST /api/v1/orders | POST /api/v1/createOrder | 同上 |
| GET/api/v1/users/7/orders | GET /api/v1/orders?user=7 （作为唯一入口） | 从属关系不清晰（两者都可以，前者更直观） |
| DELETE/api/v1/cart/items/42 | POST /api/v1/cart/removeItem | 用 POST 表达一切 |

规则：

1. 资源用复数名词：/products 、/orders 。

2. 层级表示从属：/users/{id}/addresses ，层级不超过两三层。

3. URL 全小写，单词用连字符：/order-items （JSON 字段则用 snake_case，见 9.8）。

4. 路径带版本号：/api/v1/ 。不兼容的修改发布为 /api/v2/ ，旧版本并行运行一段时间再下线。

### 9.7.2 【进阶】无法映射为 CRUD 的动作

“取消订单”“支付订单”不是简单的增删改查。两种主流做法：

子资源动作：POST /api/v1/orders/1001/cancel 。直观，被广泛采用（Google API 设计指南称为“自定义方法”，写作 POST /orders/1001:cancel ）。

状态字段修改：PATCH /api/v1/orders/1001 ，正文 {"status": "cancelled"} 。看似纯粹，但取消通常还需要原因、会触发退款等副作用，用状态修改来表达并不自然。

RustMall 采用第一种：状态机的每个转移（第 3.7 节的 pay 、ship 、complete 、cancel ）对应一个 POST /orders/{id}/动作 接口。

### 9.7.3 【进阶】分页、过滤与排序

偏移分页（offset）：GET /products?page=3&amp;page_size=20 。简单，支持跳页；缺点是深页很慢（数据库要先扫描并丢弃前面的行），且翻页时有新数据插入会出现重复或遗漏。

游标分页（cursor / keyset）：GET /products?after=1042&amp;limit=20 ，服务端执行 WHERE id &gt;1042 ORDER BY id LIMIT 20 。在匹配索引和过滤条件下，可以避免随 OFFSET 增大而跳过大量行；不能任意跳页，也不能自动保证跨请求快照一致。适合信息流、订单历史和受控导出。

分页响应的统一结构（RustMall 约定）：
```text
{
  "items": [ { "id": 41, "name": "机械键盘" } ],
  "page": 3,
  "page_size": 20,
  "total": 245
}
```

过滤与排序用查询参数：?category=外设&amp;min_price=10000&amp;sort=-price,id （前缀 - 表示降序）。排序字段必须使用白名单，不能把用户输入直接拼进 SQL 的 ORDER BY（第 14 章会讲到 SQL 注入）。

### 9.7.4 【进阶】统一的错误响应

所有错误使用同一种结构，前端只需要写一套处理逻辑。RustMall 的约定（与第 4 章ErrorKind::code() 对应）：
```text
{
  "code": "INVALID_INPUT",
  "message": "字段 `quantity` 的值 120 超出范围 1~99",
  "request_id": "0f8c2a1e7d"
}
```

code ：稳定的、机器可读的错误码，前端据此做判断（例如 CONFLICT 时提示“库存不足”）。发布后不能修改。

message ：给人看的说明，可以随时调整措辞，前端不应该依赖它做判断。

request_id ：与 X-Request-Id 头相同，方便排查。

5xx 错误的 message 统一为“服务器内部错误”，绝不能把数据库报错、堆栈等内部信息返回给客戶端（安全风险）；详细信息只写进日志（第二卷第 4 章综合练习 5 的答案）。

业界也有标准格式 RFC 9457（Problem Details，application/problem+json ），字段为 type 、title 、status 、detail 、instance 。两种都可以，关键是全系统统一。

### 9.7.5 【精通】API 设计的长期考虑

向后兼容：可以新增字段、新增可选参数、新增接口；不能删除字段、修改字段类型或含义、把可选参数改为必填。客戶端也要“宽容地读”：忽略不认识的字段。

幂等键：所有“创建”类 POST 接口都接受 Idempotency-Key 头，服务端在一段时间内对同一个键返回同样的结果（第 29 章实现）。

批量接口：GET /products?ids=1,2,3 避免前端发起 N 次请求；注意限制最大数量。

长耗时操作：返回 202 和一个任务资源 /jobs/{id} ，客戶端轮询或通过 WebSocket 接收结果。

文档即合同：用 OpenAPI 描述接口（9.9.3 节），让前后端并行开发、自动生成客戶端代码和接口测试。

## 9.8 JSON

### 9.8.1 【入门】语法与类型
```text
{
  "id": 42,
  "name": "机械键盘",
  "price_cents": 19900,
  "on_sale": true,
  "tags": ["数码", "外设"],
  "discount": null,
  "specs": { "switch": "青轴", "keys": 104 }
}
```

JSON 只有六种值：对象 {} 、数组 [] 、字符串（必须双引号）、数字、布尔、null。不支持注释、不允许尾随逗号、键必须是字符串。

### 9.8.2 【进阶】后端必须知道的 JSON 陷阱

| 陷阱 | 说明 | RustMall 的约定 |
| --- | --- | --- |
| 大整数精度 | JavaScript 的数字是 64 位浮点数，超过 2⁵³（约9×10¹⁵）的整数会丢失精度，9007199254740 993 在浏览器中会变成...992 | 整数绝对值超过 2^53-1 时应考虑序列化为字符串；不要假定 ID 或累计金额永远较小 |
| 金额 | 不要用小数表示金额 | 一律用整数“分”，字段名带 _cents 后缀 |
| 时间 | JSON 没有日期类型 | 使用 RFC 3339 字符串，统一 UTC："2026-10- 10 T08:30:00Z" |
| null与缺失 | "discount": null 与没有 discount 字段，含义可能不同（PATCH 时尤其重要：null 表示“清空”，缺失表示“不修改”） | 第 10 章使用嵌套 Option 配合自定义反序列化与 default，单独嵌套 Option 不足以区分 |
| 命名风格 | camelCase 还是 snake_case | 全部 snake_case，与 Rust 字段名一致 |
| 枚举 | 用数字还是字符串 | 用小写字符串："status": "paid" ，可读且不怕增删变体 |
| 未知字段 | 客戶端多传了字段 | 默认忽略；对安全敏感的接口可以拒绝（第 10 章de ny_unknown_fields ） |

### 9.8.3 【精通】JSON 的替代品

Protobuf：二进制、强类型、体积小、解析快，gRPC 使用它（第 25 章）。服务之间的内部调用常用Protobuf，对外的 API 使用 JSON。

MessagePack / CBOR：二进制的 JSON，结构与 JSON 一致，用于缓存序列化（第 18 章）。

NDJSON：每行一个 JSON 对象，适合流式导出和日志（第 15 章的结构化日志就是这种格式）。

| 接口 | 允许的当前状态 | 结果状态 | 请求体 |
| --- | --- | --- | --- |
| `POST /orders/{id}/pay` | pending | paid | 无 |

| `POST /orders/{id}/ship` | paid | shipped | `{ "tracking_no": "SF1234567890" }` |
| `POST /orders/{id}/complete` | shipped | completed | 无 |

### 9.10.7 本章小结

一次请求经过 DNS、TCP、TLS、HTTP 四个阶段；连接复用能省掉前三个阶段的开销。

HTTP 报文由起始行、头部、空行、正文组成；GET 必须安全，PUT / DELETE 应当幂等，POST 通过Idempotency-Key 变得可安全重试。

状态码：2xx 成功、4xx 客戶端错误、5xx 服务端错误；400 与 422、401 与 403 要区分清楚。领域错误按 ErrorKind 映射为 422、404、409、500。

HTTP/2 多路复用是 gRPC 的基础；服务内的 HTTP 客戶端必须复用连接池，所有调用必须设置超时。

HTTP 无状态，用 Session 或 Token 维持登录；CORS 是浏览器的限制，生产环境只允许自己的域名。

REST：名词表示资源、方法表示动作、复数与版本号；状态机动作用 POST /资源/{id}/动作；

统一的分页结构与错误结构，错误码稳定、文案可变，5xx 不泄露内部信息。

JSON：金额用整数分、时间用 RFC 3339 UTC、枚举用小写字符串、超大整数用字符串、区分 null与缺失。

# 第 42 章 Redis 深入：缓存、原子操作与可靠性

第41章沿真实SQL解释了数据库如何读取快照、等待锁与恢复数据。本章将同样的追问带到Redis：数据库已经更新，为什么用户仍可能读到旧商品？登录限流脚本没有被其他请求打断，为什么仍需要检查错误路径？Redis重启以后，哪些数据可以重新生成，哪些事实必须另有权威记录？

先沿第18章的商品缓存复现一次读写交错，再修复回填权限与本地缓存顺序。随后把方法应用到当前微服务的登录计数与会话撤销。本章使用同一个RustMall项目，保留既有库存预留、订单幂等、付款绑定与数据库租约条件。

## 42.1 先确定Redis保存的是什么

### 42.1.1 【入门】副本、协调状态与权威记录

商品名称可以从PostgreSQL重新读取，因此商品缓存丢失后可以回源。登录次数影响当前时间窗是否允许尝试；如果Redis故障时直接放行，限流策略就随故障一起消失。已经注销的会话则关系到身份是否仍有效，不能仅靠一个可能消失的Redis键决定。

三类数据都能保存为字符串，但恢复方式不同。选数据结构之前，先写下丢失后允许发生什么，再选择故障时的响应。

| 数据 | 当前工程中的权威或作用 | Redis不可用时的策略 |
| --- | --- | --- |
| 商品展示缓存 | PostgreSQL商品数据的派生副本 | 尝试权威仓储，缓存操作受超时约束 |
| 登录次数 | 用户名维度的短期准入状态 | 返回服务暂不可用，不变成无限尝试 |
| 注销标记 | 对数据库会话撤销的辅助检查 | 身份校验失败关闭；恢复后仍检查数据库会话 |
| 库存预留 | Inventory数据库中的记录 | 不使用缓存值作最终扣减判断 |
| 付款与订单步骤 | 各自数据库的绑定记录与状态机 | 保留原幂等键和条件更新规则 |

### 42.1.2 【入门】区分早期单体与当前微服务路径

第18章的`monolith`包含`ProductCache`与`CachedProductRepo`，用于学习两级缓存。当前十角色部署中的`catalog-http`通过Catalog RPC读取商品，没有因为工作区里存在这个模块就自动使用它。下单路径也继续取得权威价格，并由Inventory处理库存预留。

本章同时修改两处：单体仓储包装器用于讲清缓存竞态；`services/commerce`中的登录脚本与Redis预算用于当前微服务运行路径。读者检查性能或故障时，应先确认实际启动的是哪一个程序。

### 42.1.3 【进阶】先列出承诺，再写代码

本章要求同一个缓存对象及其克隆在写操作成功返回以后，不会又被该进程先前的旧查询留下旧L1值。跨进程回填则要求：失效操作成功撤销了某次回填许可后，那次旧读取不能再凭旧许可发布Redis值。

这两项承诺都有范围。远端进程已经持有的L1不会收到本地互斥门的通知；Redis操作失败时失效可能没有送达；数据库提交后调用方被取消，也可能未完成失效。TTL仍是这些缓存残留的恢复途径，不能由此宣称全局线性一致。

## 42.2 为什么先更新数据库再删除缓存仍有竞态

### 42.2.1 【入门】把一次请求拆成可以交错的步骤

假设商品名从“旧名称”更新为“新名称”。下面每一行都可能与另一个请求交错：

| 顺序 | 读取请求A | 更新请求B |
| --- | --- | --- |
| 1 | 缓存未命中，数据库读取旧快照 | |
| 2 | 尚未写回缓存 | 数据库提交新名称 |
| 3 | 尚未写回缓存 | 删除缓存并返回 |
| 4 | 将旧名称写进缓存 | |

数据库更新与删除缓存各自都成功，结果仍不符合预期。问题出在A持有旧快照，却没有在回填时证明自己仍有发布资格。给缓存增加更长TTL会扩大残留时间，不能修复这个顺序。

### 42.2.2 【进阶】合并未命中与协调写入是两回事

原实现已经用moka的`try_get_with`合并同一进程的同键未命中，不应把本章写成“首次加入防击穿”。合并读取可以降低同时回源的次数，却不自动约束仓储更新与旧读取的最后一次插入。

stage42改为显式的固定分片互斥门：本地命中仍走快速路径；未命中时取得门、重新检查L1，再加载并插入；写操作先提交数据库，随后取得同一扇门并完成失效。写操作返回前，先前占门的加载已经结束，其留下的值也已经被删除。

### 42.2.3 【精通】固定64扇门的代价

互斥门存放在共享的`Arc`中，缓存克隆使用同一组门。商品ID按固定方式落到64个槽位，不会随着访问的商品数增长而不断分配锁。

槽位碰撞会让不同商品的未命中互相等待。这是限制内存与实现复杂度的代价，不是吞吐无损优化。缓存快速命中不用取得门；外层请求仍需保留总预算。进程内互斥无法协调另一台机器，也不是库存的分布式锁。

## 42.3 用短期许可约束Redis回填

### 42.3.1 【入门】一个商品对应两个同槽键
```text
rustmall:product:v2:{42}:value
rustmall:product:v2:{42}:fill
```

`value`保存展示结果或不存在标记；`fill`保存某一次加载的随机UUID。花括号内相同的部分用于Redis Cluster键槽计算，使这两个键能够交给同一段多键脚本。当前实验仍使用单实例Redis；键名准备不等于已经部署并验收Cluster。

版本号从v1变为v2是键协议升级。当前代码不再读取旧键，旧值随原TTL消失。不要在运行中混用两个版本并期待它们相互失效；滚动迁移时还需要约束旧程序的存活时间。

### 42.3.2 【进阶】在读取数据库之前申请许可

未命中L2后，程序生成随机UUID，执行`SET fill token NX PX 2000`。只有收到了明确成功回复的请求，才携带这个UUID去尝试发布。请求没有拿到许可，仍可以读取数据库并返回结果，但不写L2，也不无限循环抢许可。

许可必须先于数据库读取。如果先读取旧快照、再等更新完成以后申请新许可，旧数据会得到一张看似有效的新通行证。

2000毫秒是本实现的回填许可期限，不是数据库查询的硬截止时间，也不是可随意套用的生产参数。数据库读取超过期限时，返回的数据仍可用于本次查询，但发布脚本会拒绝已经失去许可的写入。

### 42.3.3 【进阶】发布时核对所有者
```lua
if redis.call('GET',KEYS[2]) ~= ARGV[1] then return 0 end
redis.call('SET',KEYS[1],ARGV[2],'EX',ARGV[3])
redis.call('DEL',KEYS[2])
return 1
```

`KEYS[1]`是值键，`KEYS[2]`是许可键，参数分别为UUID、序列化结果和正向或负向TTL。旧许可已经过期、被撤销或被新所有者替换时，脚本返回0，不会删除新所有者的许可。

发布成功后删除的是自己刚验证过的许可。比较与删除需要在同一段脚本中完成，不能先GET，回到客户端判断，再单独DEL。

### 42.3.4 【进阶】失效同时撤销值与许可
```lua
return redis.call('DEL',KEYS[1],KEYS[2])
```

失效早于发布时，旧UUID失去发布权限；发布早于失效时，刚发布的值会被删除。两个操作在同一个Redis实例上按执行顺序观察这两个键，从而堵住“删除完成以后旧加载再写回L2”的路径。

这是缓存发布协议。随机UUID只证明所有者相同，没有可比较的递增顺序。它不能代替数据库中的租约令牌、旧步骤与未过期条件，也不能让付款或外部文件写入自动拒绝迟到进程。

### 42.3.5 【精通】许可丢失与历史状态回退的区别

Redis清空或淘汰许可后，旧发布因找不到UUID而被拒绝。若故障切换把Redis恢复到一个包含旧许可的历史状态，前述单实例顺序论证不能直接覆盖它。这里没有跨数据库和Redis提交的统一事务，也没有把数据库商品修订号带到发布条件中。

因此本章不将这个方案扩展为强一致缓存。若业务要求跨故障切换的单调读取，需要另外设计权威修订号、读取规则和恢复协议，并验证整个链路；不能只把UUID改成长字符串就认为问题解决。

## 42.4 限制缓存输入与陈旧时间

### 42.4.1 【入门】缓存数据也必须经过领域校验

Redis键名与载荷里的商品ID必须相同。载荷还要通过`Product::try_new`验证名称、价格与库存字段；解析失败、错误类型、错误ID都按未命中处理。第18章已经修复ID不匹配，本章继续保留该保护。

读取脚本先检查字符串长度，超过4096字节时不把内容取回应用。错误类型也会产生错误，再由有界缓存操作转为未命中。这个限制针对本工程的小商品载荷，不是Redis所有字符串的通用上限。

### 42.4.2 【进阶】L1与L2的TTL会叠加

一个远端进程可能在L2即将到期时读到旧值，随后给自己的L1设置完整TTL。因此不能把L2配置的TTL单独当成用户看到旧值的最长期限。还应计入L1有效期、读取与加载耗时，以及故障期间的写入和失效是否完成。

正向TTL按商品ID加入稳定偏移，分散同一批键的到期时间。不存在标记也有有限TTL，插入新商品后要同时失效。抖动减少集中回源的概率，不能保证流量尖峰消失，更不能让缓存承担库存最终判定。

## 42.5 先用可控制的交错验证本地承诺

### 42.5.1 【入门】测试不能靠猜测机器调度

新增回归让读取先取得旧快照并停在通知点；随后让更新确实修改权威仓储；最后释放旧读取，让它尝试回填。测试等待更新完成，再读取同一商品，要求得到新名称。

旧读取本身可以返回旧名称，因为它与更新重叠。真正需要验证的是：更新已经成功返回后，随后一次读取不能被旧加载留下的L1值污染。用通知点安排顺序，比随意等待几十毫秒更能说明失败原因。

### 42.5.2 【进阶】验证层次不能混算

本地内存仓储可以验证互斥门与失效顺序，却不能证明Lua实际执行、Redis ACL允许所需命令或断连时符合预算。cargo check只说明相关目标能够编译，不代表测试已经运行。

本章分别记录本地回归、真实Redis并发与错误输入、实际十角色部署和故障恢复。某一层尚未运行时，应明确标为待验证，不能沿用第41章的通过数量。

### 42.6.2 【进阶】完整缓存模块的运行部分

下面是`cache.rs`的运行代码。Lua通过`include_str!`编译进程序；配套检查点包含全部源文件，单独复制Rust文件而遗漏Lua会编译失败。
```rust
//! 商品缓存：进程内缓存（moka，L1）+ Redis（L2）（第 18 章）。
//!
//! Redis 是可选的：没有配置、连接失败、操作出错或超时，都自动降级，
//! 缓存的任何故障都不会让请求失败。

use std::future::Future;
use std::sync::Arc;
use std::time::Duration;
use tokio::sync::{Mutex, MutexGuard};
use uuid::Uuid;

use common::ids::ProductId;
use common::product::Product;
use moka::future::Cache;
use redis::aio::ConnectionManager;
use serde::{Deserialize, Serialize};
use tracing::{info, warn};

use crate::settings::{CacheSettings, RedisSettings};

/// 缓存值格式的版本。修改 `Entry` 的结构时加 1：旧格式的键不再被读取，随过期时间自然消失。
const KEY_VERSION: u32 = 2;
const FILL_LEASE_MS: u64 = 2000;

/// 一次查询的结论：`Some(商品)` 表示存在，`None` 表示确认不存在。两者都会被缓存。
pub type Lookup = Option<Product>;

/// 商品在 Redis 中的键，例如 `rustmall:product:v2:{42}:value`。
pub fn product_key(id: ProductId) -> String {
    format!("rustmall:product:v{KEY_VERSION}:{{{}}}:value", id.get())
}

/// Co-located with the value in Redis Cluster; not an inventory or payment lock.
pub fn fill_key(id: ProductId) -> String {
    format!("rustmall:product:v{KEY_VERSION}:{{{}}}:fill", id.get())
}

/// 正向缓存的过期秒数：基础时间加上按商品 ID 分散的偏移（最多约 10%），
/// 让同一批写入的键在不同时刻过期，避免缓存雪崩（第 18.9.4 节）。
pub fn ttl_with_jitter(base_secs: u64, id: ProductId) -> u64 {
    let spread = (base_secs / 10).max(1);
    base_secs.saturating_add(id.get().unsigned_abs() % spread)
}

/// Redis 中保存的值。“不存在”也要缓存，防止缓存穿透。
///
/// 单独定义而不是直接序列化 `Product`：缓存格式由缓存模块自己掌控，
/// 读回时经过 `Product::try_new` 校验，被改坏的缓存值不会变成非法的领域对象。
#[derive(Debug, PartialEq, Serialize, Deserialize)]
#[serde(tag = "state", rename_all = "snake_case")]
enum Entry {
    Found {
        id: i64,
        name: String,
        price_cents: i64,
        stock: i32,
    },
    Missing,
}

impl Entry {
    fn from_lookup(lookup: &Lookup) -> Self {
        match lookup {
            Some(p) => Entry::Found {
                id: p.id().get(),
                name: p.name().to_string(),
                price_cents: p.price_cents(),
                stock: p.stock(),
            },
            None => Entry::Missing,
        }
    }

    fn into_lookup(self) -> Result<Lookup, String> {
        match self {
            Entry::Found {
                id,
                name,
                price_cents,
                stock,
            } => Product::try_new(ProductId::new(id), &name, price_cents, stock).map(Some),
            Entry::Missing => Ok(None),
        }
    }
}

/// 两级缓存。克隆是廉价的：moka 缓存与 Redis 连接内部都是共享的。
#[derive(Clone)]
pub struct ProductCache {
    local: Cache<ProductId, Lookup>,
    gates: Arc<[Mutex<()>; 64]>,
    redis: Option<ConnectionManager>,
    op_timeout: Duration,
    ttl_secs: u64,
    missing_ttl_secs: u64,
}

impl ProductCache {
    pub fn new(
        settings: &CacheSettings,
        redis: Option<ConnectionManager>,
        op_timeout: Duration,
    ) -> Self {
        let local = Cache::builder()
            .max_capacity(settings.local_capacity)
            .time_to_live(Duration::from_secs(settings.local_ttl_secs))
            .build();
        Self {
            local,
            gates: Arc::new(std::array::from_fn(|_| Mutex::new(()))),
            redis,
            op_timeout,
            ttl_secs: settings.product_ttl_secs,
            missing_ttl_secs: settings.missing_ttl_secs,
        }
    }

    /// 只有进程内缓存：测试、以及没有配置 Redis 的环境使用。
    pub fn local_only(settings: &CacheSettings) -> Self {
        Self::new(settings, None, Duration::from_millis(200))
    }

    pub fn has_redis(&self) -> bool {
        self.redis.is_some()
    }

    pub(crate) fn local(&self) -> &Cache<ProductId, Lookup> {
        &self.local
    }

    /// Fixed memory: collisions serialize unrelated misses, but never grow a lock map.
    pub(crate) async fn gate(&self, id: ProductId) -> MutexGuard<'_, ()> {
        self.gates[(id.get().unsigned_abs() % 64) as usize]
            .lock()
            .await
    }

    pub(crate) async fn begin_fill(&self, id: ProductId) -> Option<Uuid> {
        let mut con = self.redis.clone()?;
        let token = Uuid::new_v4();
        let reply: Option<String> = with_timeout(
            self.op_timeout,
            "SET fill NX",
            redis::cmd("SET")
                .arg(fill_key(id))
                .arg(token.to_string())
                .arg("NX")
                .arg("PX")
                .arg(FILL_LEASE_MS)
                .query_async(&mut con),
        )
        .await?;
        reply.filter(|value| value == "OK").map(|_| token)
    }

    /// 读 Redis。返回 `None` 表示未命中--键不存在、Redis 不可用、值无法解析，都按未命中处理。
    pub(crate) async fn redis_get(&self, id: ProductId) -> Option<Lookup> {
        let mut con = self.redis.clone()?;
        let key = product_key(id);
        let raw: Option<String> = with_timeout(
            self.op_timeout,
            "bounded GET",
            redis::Script::new(include_str!("lua/read_value.lua"))
                .key(key)
                .invoke_async(&mut con),
        )
        .await?;
        let parsed = serde_json::from_str::<Entry>(&raw?)
            .map_err(|err| err.to_string())
            .and_then(Entry::into_lookup);
        match parsed {
            Ok(Some(product)) if product.id() != id => {
                warn!(expected = %id, actual = %product.id(), "Redis key and product identity differ; treating as cache miss");
                None
            }
            Ok(lookup) => Some(lookup),
            Err(reason) => {
                warn!(%id, reason, "Redis 中的缓存值无法解析，按未命中处理");
                None
            }
        }
    }

    /// 写 Redis。失败只记录警告：缓存写不进去，下一次再回源即可。
    pub(crate) async fn redis_put(&self, id: ProductId, lookup: &Lookup, permit: Option<Uuid>) {
        let Some(permit) = permit else { return };
        let Some(mut con) = self.redis.clone() else {
            return;
        };
        let ttl = match lookup {
            Some(_) => ttl_with_jitter(self.ttl_secs, id),
            None => self.missing_ttl_secs,
        };
        let json = match serde_json::to_string(&Entry::from_lookup(lookup)) {
            Ok(json) => json,
            Err(err) => {
                warn!(%id, error = %err, "缓存值序列化失败");
                return;
            }
        };
        let _: Option<i64> = with_timeout(
            self.op_timeout,
            "publish owned fill",
            redis::Script::new(include_str!("lua/publish_fill.lua"))
                .key(product_key(id))
                .key(fill_key(id))
                .arg(permit.to_string())
                .arg(json)
                .arg(ttl)
                .invoke_async(&mut con),
        )
        .await;
    }

    /// 写入数据库之后调用：删除两级缓存中的这个商品。
    pub async fn invalidate(&self, id: ProductId) {
        let _guard = self.gate(id).await;
        self.local.invalidate(&id).await;
        if let Some(mut con) = self.redis.clone() {
            let _: Option<i64> = with_timeout(
                self.op_timeout,
                "invalidate value and fill",
                redis::Script::new(include_str!("lua/invalidate.lua"))
                    .key(product_key(id))
                    .key(fill_key(id))
                    .invoke_async(&mut con),
            )
            .await;
        }
    }
}

/// 给 Redis 操作加上超时；出错或超时时记录警告并返回 `None`（降级）。
async fn with_timeout<T>(
    limit: Duration,
    op: &'static str,
    fut: impl Future<Output = redis::RedisResult<T>>,
) -> Option<T> {
    match tokio::time::timeout(limit, fut).await {
        Ok(Ok(value)) => Some(value),
        Ok(Err(err)) => {
            warn!(op, error = %err, "Redis 操作失败，已降级");
            None
        }
        Err(_) => {
            warn!(op, timeout = ?limit, "Redis 操作超时，已降级");
            None
        }
    }
}

/// 启动时连接 Redis。没有配置、地址无效、连接失败或超时，都返回 `None` 并记录原因。
pub async fn connect_redis(settings: &RedisSettings) -> Option<ConnectionManager> {
    let url = settings
        .url
        .as_deref()
        .filter(|url| !url.trim().is_empty())?;
    let client = match redis::Client::open(url) {
        Ok(client) => client,
        Err(err) => {
            warn!(error = %err, "Redis 地址无效，商品缓存只使用进程内缓存");
            return None;
        }
    };
    let limit = Duration::from_secs(settings.connect_timeout_secs);
    match tokio::time::timeout(limit, ConnectionManager::new(client)).await {
        Ok(Ok(manager)) => {
            info!("已连接 Redis");
            Some(manager)
        }
        Ok(Err(err)) => {
            warn!(error = %err, "连接 Redis 失败，商品缓存只使用进程内缓存");
            None
        }
        Err(_) => {
            warn!(timeout = ?limit, "连接 Redis 超时，商品缓存只使用进程内缓存");
            None
        }
    }
}
```

`with_timeout`的返回值表示本次客户端观察到的结果。写入超时不证明服务器没有执行命令：许可申请可能成功但回复丢失，程序因此放弃发布，许可随后过期；发布可能已经成功但回复丢失，后续失效仍通过同一个协议删除它。不能把超时当成“绝对没有副作用”。

### 42.6.3 【进阶】仓储包装器如何安排本地顺序
```rust
//! 带缓存的商品仓储：按 cache-aside 模式包装任意 `ProductRepository`（第 18.9 节）。
//!
//! 读：进程内缓存 → Redis → 被包装的仓储（数据库）；回源结果写回 Redis。
//! 写：先写被包装的仓储，成功后删除两级缓存。

use common::error::{DomainError, DomainResult, ErrorKind};
use common::ids::ProductId;
use common::product::{NewProduct, Product};
use tracing::debug;

use crate::cache::{Lookup, ProductCache};
use crate::repo::ProductRepository;

const ENTITY: &str = "商品";

#[derive(Clone)]
pub struct CachedProductRepo<R> {
    inner: R,
    cache: ProductCache,
}

impl<R: ProductRepository> CachedProductRepo<R> {
    pub fn new(inner: R, cache: ProductCache) -> Self {
        Self { inner, cache }
    }

    /// 进程内缓存未命中时执行。同一个 ID 同时只有一个任务执行它，其余任务等待结果。
    async fn load(&self, id: ProductId) -> DomainResult<Lookup> {
        if let Some(hit) = self.cache.redis_get(id).await {
            debug!(%id, "商品缓存：Redis 命中");
            return Ok(hit);
        }
        let permit = self.cache.begin_fill(id).await;
        let loaded = match self.inner.get(id).await {
            Ok(product) => Some(product),
            Err(err) if err.kind() == ErrorKind::NotFound => None,
            Err(err) => return Err(err),
        };
        debug!(%id, found = loaded.is_some(), "商品缓存：未命中，已回源");
        self.cache.redis_put(id, &loaded, permit).await;
        Ok(loaded)
    }
}

impl<R: ProductRepository> ProductRepository for CachedProductRepo<R> {
    async fn insert(&self, draft: &NewProduct) -> DomainResult<Product> {
        let product = self.inner.insert(draft).await?;
        // 新分配的 ID 可能已经被缓存为“不存在”（有人提前查询过它）
        self.cache.invalidate(product.id()).await;
        Ok(product)
    }

    async fn get(&self, id: ProductId) -> DomainResult<Product> {
        if let Some(hit) = self.cache.local().get(&id).await {
            return hit.ok_or_else(|| DomainError::not_found(ENTITY, id));
        }
        let _guard = self.cache.gate(id).await;
        let lookup = if let Some(hit) = self.cache.local().get(&id).await {
            hit
        } else {
            let loaded = self.load(id).await?;
            self.cache.local().insert(id, loaded.clone()).await;
            loaded
        };
        lookup.ok_or_else(|| DomainError::not_found(ENTITY, id))
    }

    async fn list(&self, limit: i64, offset: i64) -> DomainResult<(Vec<Product>, i64)> {
        // 列表的组合太多（页码 × 每页数量），任何一次写入都会让它们全部过时，暂不缓存
        self.inner.list(limit, offset).await
    }

    async fn update(&self, product: &Product) -> DomainResult<Product> {
        let updated = self.inner.update(product).await?;
        self.cache.invalidate(updated.id()).await;
        Ok(updated)
    }

    async fn delist(&self, id: ProductId) -> DomainResult<()> {
        self.inner.delist(id).await?;
        self.cache.invalidate(id).await;
        Ok(())
    }
}
```

门保护的是未命中加载、插入与失效的顺序，底层数据库写入不需要持门。写入提交以后再等门，可以让旧加载完成，然后删除其结果；写操作只有完成失效流程才返回成功。Redis失败会记录并降级，因此“成功”并不意味着远端所有实例都已清缓存。

读命中L1时可以直接返回。如果它与更新发生重叠，读到旧值并不违反本章承诺。请求被取消时，持有的Rust互斥门会随guard释放；已经提交的数据库更新却不能因此自动回滚。恢复与TTL策略必须覆盖这段窗口。

### 42.6.4 【精通】错误不能变成永久负缓存

只有领域层明确返回NotFound，才能把结果转为`Missing`。数据库连接失败、查询超时与内部错误必须继续向上传递，不写“不存在”。否则一次短暂故障会把真实商品隐藏到负向TTL结束。

发布许可不是等待其他实例结果的通知机制。本实现竞争失败后仍可能回源，主要保证失效后的发布顺序；它没有承诺跨实例同一时刻只发生一次数据库查询。若引入有限等待或等待通知，还必须处理持有者退出、通知丢失、预算耗尽和回源放大，不能无限自旋。

## 42.7 登录限流：固定窗口也要处理异常状态

### 42.7.1 【入门】先把策略说完整

当前策略按规范化用户名计数：从第一次尝试建立一个60秒窗口，最多允许10次尝试继续进行密码校验。成功登录也消耗一次尝试；第11次返回429。不存在的用户名同样计数，不让攻击者通过响应差异轻易枚举账户。

这不是“任意滚动60秒最多10次”。固定窗口边界两侧可能短时间内出现接近两倍的允许量；它也不是每IP或每设备策略。攻击者知道用户名时可以消耗该用户窗口，造成短期拒绝服务。生产系统需要结合来源、设备、全局容量与风险策略设计，不能把一个计数器称为完整反撞库方案。

### 42.7.2 【进阶】为什么不只写INCR再EXPIRE

客户端分两次发命令时，INCR成功以后进程退出，EXPIRE就不会执行。将两条命令放到Lua中能防止其他客户端插入执行，但仍要考虑第二条命令报错以后第一条是否已经生效。

本实现先读取并验证状态，再做一次带PX的最终SET。正常计数、补TTL与计数饱和共用同一套分支，避免把超大历史计数一直增长到整数溢出。

### 42.7.3 【进阶】实际运行的完整脚本
```lua
-- Fixed window, bounded state, one final write. Atomic execution is not rollback.
local maximum=10
local window=60000
if redis.call('STRLEN',KEYS[1])>18 then
  return redis.error_reply('invalid login counter')
end
local raw=redis.call('GET',KEYS[1])
local count=0
local ttl=window
local repair=false
if raw then
  if not string.match(raw,'^%d+$') or #raw>18 then
    return redis.error_reply('invalid login counter')
  end
  count=tonumber(raw)
  ttl=redis.call('PTTL',KEYS[1])
  if ttl<0 or ttl>window then ttl=window; repair=true end
  if ttl==0 then ttl=1 end
end
if count>=maximum then
  -- Repair old non-expiring or oversized counters, without extending valid windows.
  if count~=maximum or repair then
    redis.call('SET',KEYS[1],maximum,'PX',ttl)
  end
  return {0,maximum,ttl}
end
count=count+1
redis.call('SET',KEYS[1],count,'PX',ttl)
return {1,count,ttl}
```

STRLEN先拒绝过长输入，也让错误类型在写入之前失败。内容只允许十进制数字；18位以内的大数字无需精确恢复其原值，只需确认已经超过10并饱和为10。普通窗口保留剩余PTTL，不因每次尝试续成新的60秒。

没有TTL或TTL异常过长的旧计数会得到一个有限窗口。PTTL为0时使用1毫秒，避免把PX设为0；这只处理到期边界，不将其宣传为精确到微秒的公平调度器。无法理解的计数返回错误，不删除后放行。

### 42.7.4 【精通】Lua原子执行不等于数据库回滚

在隔离实验中先SET字符串，再对同一键LPUSH，后一步因类型错误失败，已经写入的字符串仍存在。这说明“没有其他命令插进来”和“失败时撤销前面所有写入”是不同性质。MULTI/EXEC也不能按PostgreSQL事务的回滚模型理解。

工程因此尽量在修改前完成格式、类型和TTL判断，并压缩最终写入数量。脚本仍需短小有界，不能为了方便把全库扫描或外部等待塞进执行过程。[Redis事务错误处理](https://redis.io/docs/latest/develop/using-commands/transactions/)

## 42.8 在Rust侧约束Redis调用

### 42.8.1 【入门】类型化回复与故障关闭
```rust
//! Authentication Redis is required; it never silently degrades to unlimited attempts.
use crate::runtime::*;
use redis::aio::ConnectionManager;
use std::{future::Future, time::Duration};
pub const LOGIN_SCRIPT: &str = include_str!("lua/login_limit.lua");
#[derive(Debug, PartialEq, Eq)]
pub struct Admission {
    pub allowed: bool,
    pub count: i64,
    pub remaining_ms: i64,
}
pub async fn bounded<T>(future: impl Future<Output = redis::RedisResult<T>>) -> ApiResult<T> {
    tokio::time::timeout(call_duration(Duration::from_millis(150))?, future)
        .await
        .map_err(|_| unavailable())?
        .map_err(|_| unavailable())
}
pub async fn login_attempt(redis: &mut ConnectionManager, username: &str) -> ApiResult<Admission> {
    let values: (i64, i64, i64) = bounded(
        redis::Script::new(LOGIN_SCRIPT)
            .key(format!("users:v1:login:{username}"))
            .invoke_async(redis),
    )
    .await?;
    if !matches!(values.0, 0 | 1)
        || !(1..=10).contains(&values.1)
        || !(1..=60_000).contains(&values.2)
    {
        return Err(unavailable());
    }
    Ok(Admission {
        allowed: values.0 == 1,
        count: values.1,
        remaining_ms: values.2,
    })
}
```

Lua返回三个整数，Rust进一步检查允许标志、计数与TTL的范围。协议异常返回503，不把未知回复解释成允许。调用取150毫秒上限与当前治理预算的较小值，沿用第39章的剩余预算机制。

超时会停止应用等待，不保证已经发给Redis的计数命令被取消。回复丢失可能多消耗一次尝试，策略倾向保守拒绝。不要为了“补回来”再无条件减一次计数，因为原操作可能根本没有成功，也可能已经进入新的窗口。

### 42.8.2 【进阶】脚本缓存消失是正常分支

Redis脚本缓存与业务键不同。服务重启、故障切换或SCRIPT FLUSH都可能使EVALSHA遇到NOSCRIPT。当前代码使用redis crate的`Script`接口；缺失时由脚本接口加载源文本并重试调用，整个等待仍处于外层预算内。

独立实验明确执行SCRIPT FLUSH，再观察NOSCRIPT，随后使用实际应用ACL加载同一份固定脚本并再次调用。实验验证ACL和服务端协议；Rust真实测试覆盖实际`Script`调用，不能将手动命令实验写成另一种客户端的自动恢复已经验收。避免把源文本按用户名动态拼接，否则脚本缓存会出现大量无意义版本。[Redis脚本与缓存](https://redis.io/docs/latest/develop/programmability/eval-intro/)

### 42.8.3 【进阶】ACL必须包含脚本真正调用的命令
```text
~users:v1:*
+strlen +get +pttl +exists +set
+eval +evalsha +script|load
```

这只是与本章相关的权限片段，完整生成器还允许连接握手与必要的连接管理命令。STRLEN、GET和PTTL服务于登录计数，EXISTS与SET服务于会话检查及注销标记。脚本执行权限不会自动授予脚本内部任意命令或越过键范围。

应用身份不获FLUSHDB、CONFIG、任意键空间或管理脚本缓存的权限。独立实验需要SCRIPT FLUSH和CONFIG，因此另外添加只属于实验的管理员；正式生成器不包含它。不要为了让测试方便把实验管理员复制进部署配置。

### 42.8.4 【精通】商品缓存身份应独立规划

当前十角色部署的Redis应用身份只用于users，不允许访问商品v2键。这是因为当前Catalog HTTP没有启用早期单体缓存。若将来确实把商品缓存接入独立服务，需要新增独立ACL、预算、监控和发布方案，不能扩大users身份的键空间后便声称完成架构升级。

两个业务共用一个Redis进程也会共享CPU、内存和故障域。逻辑数据库编号不能提供资源隔离或独立淘汰策略；键前缀与ACL解决的是访问边界，不能代替容量隔离。

## 42.9 会话撤销：恢复以后也不能复活旧身份

### 42.9.1 【入门】数据库会话记录仍是权威

JWT签名与有效期只是校验的一部分。程序还检查已签发会话是否存在、是否撤销、数据库有效期是否结束，并从数据库读取当前角色。Redis撤销键可以快速拒绝，却不能在键丢失时替数据库证明会话有效。

注销先更新数据库的`revoked_at`，再设置Redis标记。Redis写失败时返回503，但数据库撤销可能已经提交；调用方按同一令牌重试注销，仍应得到204。不要把先写Redis、再更新数据库当作等价顺序。

### 42.9.2 【进阶】三种响应分别说明什么

| 场景 | 预期响应 | 已知事实 |
| --- | --- | --- |
| Redis可用且会话有效 | 200 | 签名、Redis检查与数据库会话均通过 |
| Redis不可用 | 503 | 未完成依赖检查，不按有效身份放行 |
| Redis恢复，会话在数据库中已撤销 | 401 | 缓存丢失没有恢复被撤销的会话 |
| 注销数据库已提交，Redis不可用 | 503 | 应重试；不能推断撤销没有发生 |
| 恢复后重复注销同一有效期内令牌 | 204 | 同一会话撤销保持幂等 |

401说明身份不满足要求；503说明暂时不能完成依赖检查。把两者混为一个响应，会让客户端错误地清除令牌或反复登录。

### 42.9.3 【精通】主部署仍使用易失Redis

本书当前Compose明确配置`--save "" --appendonly no`和128MB、noeviction。Redis重启后登录窗口会清空；停机期间请求503，恢复后的新窗口可能再次允许尝试。这一恢复语义必须写出来，不能因为注销在数据库持久化，就推导所有Redis策略都持久化了。

若要求重启后限流额度连续，应为这类状态选择持久化、复制与恢复方案，并考虑历史窗口、时钟和故障切换可能的回退。改变Redis启动参数以后还需重新验证，不属于本章现有Compose已经具备的能力。

## 42.10 从数据结构走到资源预算

### 42.10.1 【入门】按访问方式选择结构

| 结构 | 适合表达的关系 | 需要额外处理的问题 |
| --- | --- | --- |
| String | 小型完整快照、计数、带TTL标记 | 大值、整值改写、类型协议 |
| Hash | 一组字段的局部访问 | 字段与整体生命周期、部分更新一致性 |
| Set | 去重成员关系 | 成员数增长、完整枚举成本 |
| Sorted Set | 分数排序、时间或优先级索引 | 相同分数、清理与成员上限 |
| List | 有序元素与两端操作 | 积压、消费确认与故障恢复 |
| Stream | 追加条目与消费组 | 确认、待处理项、裁剪与重投递 |

本项目登录计数选择String，因为一次脚本需要整体读取计数并设置TTL；商品缓存选择小型完整快照，因为需要一次校验后再转成领域对象。本章不把业务事件从Kafka改写到另一套队列，后续章节仍沿现有Outbox与投影链路深入。

### 42.10.2 【进阶】小对象不代表没有内存开销

键名、对象元数据、过期信息、分配器和连接缓冲都会占内存。某些小集合可以采用紧凑编码，超过阈值后编码可能变化；因此不能只把JSON字节数乘键数当作容量答案。

先对代表性键观察MEMORY USAGE和OBJECT ENCODING，再结合INFO MEMORY、键数量、平均与高分位大小估算，并预留复制、持久化和客户端缓冲空间。阈值应查正在使用版本的配置，不能把某台机器默认值写成所有Redis版本的保证。[Redis内存优化](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

### 42.10.3 【进阶】过期与淘汰解决不同问题

过期由TTL定义数据还能保留多久；淘汰在内存压力下选择删除什么。noeviction会拒绝需要新增内存的写入，不保证业务仍可写。allkeys类策略可以删除未过期键，volatile类策略只在设置过期的键中选择；两者对“标记不存在意味着什么”的业务影响不同。

本项目选择noeviction，使认证状态不会为腾空间被任意淘汰；相应代价是容量不足时可能出现503。商品派生缓存可以接受丢失，但若与认证混用同一资源池，不能分别假定不同淘汰语义。[Redis淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)

### 42.10.4 【精通】热点、雪崩与穿透不能混成一个开关

热点是少数键承受大量访问；同时过期造成集中回源；大量不存在ID持续访问会造成穿透。L1、单进程合并、TTL抖动与有限负缓存分别缓解不同路径。

负缓存也会占容量，任意ID攻击仍可能产生大量不同键。应用层应限制入口速率、请求体与ID格式，并对回源并发设预算。布隆过滤器只能作为可能存在的筛选器，还要处理误判、构建和更新过程；本章没有加入它，不能声称已经阻断所有穿透。

## 42.11 持久化、复制与高可用的责任边界

### 42.11.1 【入门】RDB与AOF先回答恢复到哪里

RDB保存某个时刻的数据集快照，备份间隔之间的写入可能缺失。AOF记录写入并配合刷盘与重写；everysec、always与不主动fsync在延迟和可能损失的窗口上不同。重写与后台保存都需要额外资源，不能只观察平时的used_memory。

恢复方案还要包含文件可读性、版本兼容、ACL与配置来源。把文件复制到新机器但缺少访问策略，并不是恢复服务完成。[Redis持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 42.11.2 【进阶】本章AOF实验具体证明了什么

独立脚本建立新的AOF实验卷，写合成标记和登录计数，使用WAITAOF等待本地AOF刷盘确认，然后优雅停止并启动同一容器。它核对标记、计数和剩余TTL，并确认脚本缓存消失、重新加载以后仍拒绝超额登录。

这里只证明该版本、该配置、该文件系统下的一次优雅重启恢复；没有模拟宿主断电、损坏介质或AOF尾部损坏，也没有复制节点。WAITAOF等待的是这条实验连接此前的写入持久化确认；不能据此证明另一条连接尚未关联的业务写入已经同步。

### 42.11.3 【进阶】复制确认不是跨系统提交

Redis复制通常异步，主节点确认的写入可能尚未到达稍后被提升的副本。WAIT可以请求副本确认此前写入的复制进度，但不把Redis变成与PostgreSQL、支付服务一起提交的分布式事务。

恢复后的缓存、限流窗口与会话标记都可能遇到历史状态。处理方法应分别来自派生数据重建、准入策略与数据库权威检查，不能用“有副本”替代业务语义。[Redis复制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

### 42.11.4 【精通】Sentinel与Cluster不是相同扩容方式

Sentinel围绕非分片Redis提供监测与故障转移，客户端需要发现当前主节点并处理重连。Cluster把键分布到哈希槽，客户端要理解重定向，多键操作受同槽约束；分片不会自动分散单个热点键。

当前工程使用普通ConnectionManager与单实例URL，没有配置和实测Sentinel或Cluster连接管理。v2键的hash tag只是给多键脚本保留同槽条件。上线任何一种高可用拓扑，都需要补足发现、凭据、TLS、网络分区、读写路由和故障演练。[Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)，[Cluster规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

    result = subprocess.run(command, capture_output=True, text=True, timeout=60, input=input)
    if result.returncode and not allowed:
        raise RuntimeError('Redis42 command failed; response values deliberately omitted')

        if test(): return
        if time.monotonic() >= end: raise RuntimeError('timeout: ' + label)
        time.sleep(.1)

    result = run(['docker', 'exec', '-e', 'REDISCLI_AUTH=' + password, name,
                  'redis-cli', '--user', user, '--json', '-e', *map(str, args)], allowed=allowed)
    return result

def value(*args, user='lab_admin'):
    return json.loads(cli(*args, user=user).stdout)

try:
    with tempfile.TemporaryDirectory(prefix='rustmall-redis42-') as tmp:

        secret_dir = profile/'secrets'

        app_password = next(x[1:] for x in line.split() if x.startswith('>'))

             '--maxmemory-policy', 'noeviction']); created = True
        until(lambda: cli('PING', allowed=True).returncode == 0, 'Redis ready')

        script = (ROOT/'services/commerce/src/lua/login_limit.lua').read_text()
        sha = hashlib.sha1(script.encode()).hexdigest()

        assert all(1 <= x[1] <= 10 and 0 < x[2] <= 60000 for x in results)
        assert value('GET', key, user='app_users') == '10'

            assert failure.returncode != 0 and 'NOPERM' in failure.stdout + failure.stderr
        report['checks'].append('actual users Lua: exactly10 of64 admitted, bounded counter/TTL; generated ACL rejects FLUSHDB and out-of-scope key')
        value('SCRIPT', 'FLUSH')
        missing = cli('EVALSHA', sha, 1, key, user='app_users', allowed=True)
        assert missing.returncode and 'NOSCRIPT' in missing.stdout + missing.stderr
        assert value('SCRIPT', 'LOAD', script, user='app_users') == sha
        assert value('EVALSHA', sha, 1, key, user='app_users')[0] == 0
        report['checks'].append('script cache flush produces NOSCRIPT; application ACL can reload exact source and evaluate it')
        partial_key = 'users:v1:lab:partial'
        partial = cli('EVAL', "redis.call('SET',KEYS[1],'already-written'); return redis.call('LPUSH',KEYS[1],'x')", 1, partial_key, allowed=True)
        assert partial.returncode and 'WRONGTYPE' in partial.stdout + partial.stderr
        assert value('GET', partial_key) == 'already-written'
        report['checks'].append('later Lua WRONGTYPE error does not roll back an earlier SET')
        # Existing reads still work; a write requiring new memory must reject.
        value('CONFIG', 'SET', 'maxmemory', 1)
        try:
            failure = cli('EVAL', script, 1, 'users:v1:login:oom42', user='app_users', allowed=True)
            assert failure.returncode and 'OOM' in failure.stdout + failure.stderr
            assert value('EXISTS', 'users:v1:login:oom42') == 0

        run(['docker', 'start', name])

        assert value('GET', key) == '10'
        assert 0 < value('PTTL', key) <= 60000
        assert not value('SCRIPT', 'EXISTS', sha)[0]
        assert value('SCRIPT', 'LOAD', script, user='app_users') == sha
        assert value('EVALSHA', sha, 1, key, user='app_users')[0] == 0
        report['checks'].append('graceful AOF restart retains synthetic data and absolute TTL; Lua cache is absent and reload succeeds')

finally:

## 42.13 运维排查要回答业务问题

### 42.13.1 【入门】从症状找到证据

| 症状 | 优先观察 | 不应直接推断 |
| --- | --- | --- |
| 登录大量503 | Redis连通性、超时、内存写拒绝、脚本ACL | 密码全部错误 |
| 登录429 | 用户名窗口计数与TTL、入口流量 | Redis坏了就该删除键 |
| 商品读到旧名称 | 实际读取路径、实例L1、键协议版本、更新是否完成失效 | 数据库没有提交 |
| 回填经常被拒绝 | 加载耗时、许可期限、更新频率 | 增大锁期限必然正确 |
| Redis内存升高 | 键数、大小分布、缓冲、持久化与复制状态 | JSON小就不会占空间 |
| 重启后注销键消失 | 数据库会话撤销与实际认证响应 | 旧令牌重新有效 |

先核对当前运行角色和镜像身份。若请求走Catalog RPC，却排查monolith的商品键命中率，观察对象已经错了。

### 42.13.2 【进阶】SCAN是增量遍历，不是快照分页

完整遍历要持续携带返回游标，直到返回0。COUNT只是工作量提示，可能返回空页或更多元素；重复键需要按业务需要去重。数据在遍历期间变化时，不能把本次结果当作一个时刻的完整快照。

本章仅在静止的200个合成键上验证完整集合相同。脚本限制总轮数以免实验无限循环，这不是生产扫描固定200条或每批固定17条的保证。[SCAN语义](https://redis.io/docs/latest/commands/scan/)

### 42.13.3 【进阶】诊断本身也消耗资源

INFO、SLOWLOG和延迟工具应由单独运维身份使用，先看低成本汇总，再限定采样范围。慢日志关注服务器命令执行，不一定包含应用等待连接、网络传输和本地排队；它与第38章HTTP耗时要结合分析。

SLOWLOG或MONITOR可能暴露命令参数。不要把包含令牌、密码、个人数据的输出直接归档到共享报告，也不要让应用身份拥有所有诊断权限。本章实验报告只保存断言、版本、脚本摘要与清理状态，不保存原始认证命令。

### 42.13.4 【精通】容量预算应连到故障预算

当Redis拒绝写入，认证选择503意味着可用性下降；商品缓存回源则可能把压力传给数据库。两者都需要监控，但没有必要使用完全相同的恢复动作。

重启可能暂时释放内存，也可能清掉窗口、引发集中回源和数据库排队。应先核对数据语义、配额、峰值与异常键来源，再按演练过的步骤恢复。第46章会把这些局部判断接入跨服务对账与灾难恢复流程。

## 42.14 分层练习与参考答案

### 42.14.1 【入门】写出一次超时的两种可能

问题：申请回填许可超时以后，为什么不能直接当作拿到了许可，也不能证明Redis没有这个键？

答案：服务器可能没有收到请求，也可能已经创建许可但回复丢失。程序没有确认所有权，就不发布；即使存在未确认的许可，也让它在短TTL后自然过期。盲目DEL可能误删后来者，盲目发布则绕过授权条件。

### 42.14.2 【进阶】证明两种失效顺序

问题：发布与失效谁先执行都可能，为什么旧许可不能在失效成功以后再留下L2值？远端L1是否也因此立即更新？

答案：发布先执行时，后续失效删除值和许可；失效先执行时，旧UUID不再匹配，发布不写值。这个论证依赖同一Redis状态上的脚本顺序，不覆盖历史状态回退。远端已有L1没有被通知，仍可能在自己的TTL内返回旧值。

### 42.14.3 【进阶】解释固定窗口与修复分支

问题：计数9、剩余5秒时再来两次，计数100且没有TTL时再来一次，分别发生什么？

答案：第一种第十次允许、计数10，后一次拒绝，正常情况下都保留原窗口剩余时间；第二种拒绝并将计数饱和为10，修复为有限60秒窗口。字符串NaN或错误类型不是上述修复对象，应返回503并保留现场，不能清空后开放。

### 42.14.4 【精通】设计一次不会误报的恢复演练

问题：同一Redis重启后哪些检查能证明注销语义保持，哪些检查只能证明数据恢复？

答案：保留一个未撤销会话和一个在停机期间完成数据库撤销的会话。恢复后前者应可继续使用，后者必须401；重复注销应204，并核对数据库记录。AOF中存在某个字符串只证明该数据可读，不能替代HTTP身份校验，也不能证明六个数据库处于同一恢复时间线。

### 42.14.5 【精通】继续到Kafka之前保留哪些事实

本章将缓存看作有明确权限、期限和错误语义的协议；登录限流与会话撤销则按各自权威状态处理故障。下一章继续检查现有Outbox、Kafka副本与消费恢复：数据库已经提交、事件是否可靠送达、消费位点何时提交，以及积压与保留期如何影响投影重建。不要把Redis脚本成功、Kafka写入成功和订单全流程完成混为同一个“成功”。

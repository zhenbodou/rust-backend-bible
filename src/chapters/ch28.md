# 第 28 章 Kafka：分区日志与消息消费

上一章把商品写入收口到独立服务，公共请求通过明确链路完成同步调用。如果搜索索引、统计或其他服务也需要知道商品发生了变化，让商品接口逐个调用它们，会使响应等待依赖数量与故障一起增长。我们需要一种能够持久保留事件、允许不同使用者独立读取的传播方式。

本章学习 Kafka 的日志模型，建立一个单节点 KRaft 实验，再为同一个 RustMall 增加 messaging 包。你会用 Rust 发送经过校验的商品快照，观察分区与偏移量，亲手验证不提交就可能重放、提交记录的是下一位置、不同消费组拥有独立进度。

本章先独立学习消息链路，不把 catalog 的每次 UPDATE 直接接到生产者。数据库提交与消息发送如何一起可靠发生，是下一章 Outbox 要解决的具体问题。能够发送一条演示消息，与商品变更已经可靠发布，是不同的验收结论。

## 28.1 先理解事件与日志

### 28.1.1 【入门】事件描述已经发生的事实

命令表达希望执行的动作，例如“把价格改为 19900 分”；事件表达已经形成的事实，例如“商品 1 在修订 8 时的价格是 19900 分”。使用者不能把事件当作可以任意拒绝并撤销源事务的远程函数调用。

本章采用商品快照事件。payload 包含该版本的名称、价格、库存与上下架状态，让消费者不必再同步查询商品服务才能了解这个版本。但快照大小、隐私字段和长期演进仍要审核，不能把整行数据库数据毫无选择地发送出去。

### 28.1.2 【入门】Kafka 不是一个会读后删除的队列

Kafka 将记录追加到分区日志中，消费者读取以后通常不会立即删除它。数据何时淘汰由保留策略等机制决定，不由某个消费者是否成功处理决定。

这让新的统计服务可以用自己的进度读取保留的数据，也让故障服务恢复时从已提交位置继续。它同时意味着落后太久的消费者可能错过已被清理的历史，需要重建或其他恢复来源；“消息会保存”不能简化成“永不丢历史”。

### 28.1.3 【入门】主题与分区

Topic 是逻辑主题，例如 rustmall.catalog.demo.v1；Partition 是主题内部的一条有序追加日志。一个主题可以有多个分区，每条记录落在其中一个分区，并取得该分区内的 offset。

offset 只在“主题、分区”这两个坐标下有意义。分区 0 的 offset 15 与分区 1 的 offset 15 不是同一位置，也不能据此比较全局先后。日志清理或控制记录等机制还会影响可见记录，消费者不应假设每个整数位置都必然对应一条可见业务消息。

### 28.1.4 【进阶】key 如何连接业务与分区

本章使用商品 aggregate_id 的十进制字符串作为 Kafka key。默认分区策略在分区数固定时通常将相同 key 路由到同一分区，因此同一商品的事件可以沿一条日志观察顺序。

key 不是唯一索引，Kafka 不会因为两条记录 key 相同就拒绝第二条。它也不保证不同商品之间的全局顺序。增加主题分区数可能改变后续 key 的路由，涉及顺序的系统必须把这类运维修改作为协议变化评估。

### 28.1.5 【进阶】Broker、Leader 与副本

Broker 是保存日志并服务客户端请求的 Kafka 节点。分区有负责读写协调的 leader，也可以有其他副本。acks=all 表达生产者等待当前所需副本确认的策略，还必须结合副本数、同步副本和最小 ISR 等配置理解。

本章只有一个 broker、复制因子一。即使 acks=all，也没有第二台机器保存同一份分区副本，不能抵御该机器或其数据盘丢失。多副本、故障选主和长期运维放在 Kafka 深入章节继续实验。

### 28.1.6 【精通】KRaft 管理什么

KRaft 使用 Kafka 自身的元数据仲裁机制管理集群元数据，不再要求本章额外部署 ZooKeeper。实验节点同时承担 broker 与 controller 角色，缩短准备路径。

元数据仲裁和业务分区副本不是同一份状态。controller 了解主题、分区和集群状态，不表示业务记录已经多副本保存。单节点组合模式适合学习，不应从它推导出生产高可用架构。

## 28.2 先用控制台观察一条日志

### 28.2.1 【入门】本章执行位置与前提

继续使用上一章 RustMall 工作区。Docker 与 Compose 必须可用；本章使用原稿固定的 apache/kafka:4.0.0 镜像和 rdkafka 0.39.0，而不是宣称这些是当前最新版本。Rust 客户端库版本、其依赖的 librdkafka 版本与 broker 版本分别管理，版本数字不要求相同。

默认主机端口为 9092，可通过 KAFKA_LAB_PORT 覆盖。此端口只绑定本机回环地址。已有 Kafka 使用该端口时应改实验端口，不要删除现有服务。所有 Compose 命令在工作区根执行，显式传入同一项目名和文件路径。

### 28.2.2 【入门】完整 Kafka 实验 Compose

创建 deploy/messaging/compose.yaml：
```yaml
name: rustmall-messaging-lab
services:
  volume-init:
    image: busybox:1.37
    user: "0:0"
    command: ["sh", "-c", "chown -R 1000:1000 /data"]
    volumes:
      - kafka-data:/data
  kafka:
    image: apache/kafka:4.0.0
    depends_on:
      volume-init:
         condition: service_completed_successfully
    ports:
      - "127.0.0.1:${KAFKA_LAB_PORT:-9092}:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      KAFKA_LISTENERS: INTERNAL://:19092,EXTERNAL://:9092,CONTROLLER://:9093
      KAFKA_ADVERTISED_LISTENERS: INTERNAL://kafka:19092,EXTERNAL://127.0.0.1:${KAFKA_LAB_PORT:-9092}
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT
      KAFKA_INTER_BROKER_LISTENER_NAME: INTERNAL
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_LOG_DIRS: /tmp/kraft-combined-logs
      CLUSTER_ID: 4L6g3nShT-eMCtK--X86sw
    volumes:
      - kafka-data:/tmp/kraft-combined-logs
    healthcheck:
      test: ["CMD", "/opt/kafka/bin/kafka-topics.sh", "--bootstrap-server", "kafka:19092", "--list"]
      interval: 10s
      timeout: 5s
      retries: 20
volumes:
  kafka-data: {}
```

volume-init 只处理本项目 Kafka 命名卷的目录归属，随后退出；kafka 依赖它成功完成。它使用 root 只是为这个初始化动作，不是要求业务客户端以 root 运行。volumes 中的 kafka-data 缩进必须正确，否则 Compose 不会把它解析为命名卷声明。

### 28.2.3 【进阶】三组监听地址不要混淆

INTERNAL 的 kafka:19092 给同一个 Compose 网络里的工具和后续容器使用；EXTERNAL 广告本机地址与映射端口，给本机 Rust 进程使用；CONTROLLER 的 9093 用于元数据角色通信。

bootstrap.servers 只是初次接触集群的入口。客户端随后会按 broker 返回的 advertised.listeners 继续连接。因此“能连接映射端口，但发送失败”可能来自广告地址不可达，而不是主题不存在。容器里的 127.0.0.1 指向该容器自身，也不能拿来代替 Compose 服务名。

### 28.2.4 【入门】启动并等待健康
```bash
docker compose -p rustmall-ch28 -f deploy/messaging/compose.yaml up -d --wait
docker compose -p rustmall-ch28 -f deploy/messaging/compose.yaml ps
```

首次需要下载镜像，启动还会初始化日志与内部主题。成功后 kafka 应为 healthy，初始化服务正常退出。若失败，先查看同一项目的 logs，再决定修复配置；不要反复带 --volumes 删除数据来掩盖身份或目录问题。

若要使用 19094 主机端口，先在当前终端执行 `export KAFKA_LAB_PORT=19094`，后面的 Compose 命令也要保持这个值；Rust 的 KAFKA_BROKERS 随之改为 127.0.0.1:19094。只改端口映射而不改广告地址会造成不一致，本文件通过同一变量关联两者。

### 28.2.5 【入门】显式创建主题
```bash
docker compose -p rustmall-ch28 -f deploy/messaging/compose.yaml exec -T kafka \
  /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka:19092 \
  --create --topic rustmall.catalog.text-lab.v1 --partitions 3 --replication-factor 1
docker compose -p rustmall-ch28 -f deploy/messaging/compose.yaml exec -T kafka \
  /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka:19092 \
  --describe --topic rustmall.catalog.text-lab.v1
```

预期描述显示 PartitionCount 为 3、ReplicationFactor 为 1。topic 已存在时不要直接假定参数相同，应再次 describe。教学中显式创建有助于发现分区和复制配置，不能把自动创建的默认结果当作设计值。

### 28.2.6 【入门】发送与读取两行文本
```bash
printf 'first\nsecond\n' | \
  docker compose -p rustmall-ch28 -f deploy/messaging/compose.yaml exec -T kafka \
  /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server kafka:19092 \
  --topic rustmall.catalog.text-lab.v1
docker compose -p rustmall-ch28 -f deploy/messaging/compose.yaml exec -T kafka \
  /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:19092 \
  --topic rustmall.catalog.text-lab.v1 --from-beginning --max-messages 2 \
  --property print.partition=true --property print.offset=true
```

应看到两条记录及各自的分区、位置。没有指定 key 的两条输入，不要求按全局输入次序跨分区输出。再次从开头使用独立消费身份读取仍可看到记录，说明读取本身没有从日志删除它们。

这个 text-lab 主题只用于纯文本练习。后面的 Rust 消费者严格解析 Envelope，不要让它去读这两条普通字符串，否则正确行为就是拒绝解析。为实验分开主题，可以避免把数据格式错误误认为客户端连接失败。

### 28.3.3 【入门】完整事件模型

创建 messaging/src/event.rs：
```rust
use serde::{Deserialize, Serialize};
use sha2::{Digest, Sha256};
use uuid::Uuid;

pub const MAX_EVENT_BYTES: usize = 64 * 1024;
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
#[serde(deny_unknown_fields)]
pub struct Snapshot {
    pub id: i64,
    pub name: String,
    pub price_cents: i64,
    pub stock: i32,
    pub listed: bool,
}
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]
#[serde(deny_unknown_fields)]
pub struct Envelope {
    pub schema_version: u32,
    pub kind: String,
    pub event_id: Uuid,
    pub aggregate_id: i64,
    pub revision: i64,
    pub occurred_at_unix_ms: i64,
    pub payload: Snapshot,
}
impl Envelope {
    pub fn new(payload: Snapshot, revision: i64) -> Self {
        Self {
            schema_version: 1,
            kind: "product.snapshot.v1".into(),
            event_id: Uuid::new_v4(),
            aggregate_id: payload.id,
            revision,
            occurred_at_unix_ms: chrono::Utc::now().timestamp_millis(),
            payload,
        }
    }
    pub fn validate(&self) -> anyhow::Result<()> {
        anyhow::ensure!(
            self.schema_version == 1 && self.kind == "product.snapshot.v1",
            "unsupported event schema"
        );
        anyhow::ensure!(
            !self.event_id.is_nil()
                && self.aggregate_id > 0
                && self.aggregate_id == self.payload.id,
            "invalid event identity"
        );
        anyhow::ensure!(self.revision > 0, "invalid revision");
        anyhow::ensure!(
            (1..=100).contains(&self.payload.name.trim().chars().count()),
            "invalid product name"
        );
        anyhow::ensure!(
            self.payload.price_cents >= 0 && self.payload.stock >= 0,
            "invalid product values"
        );
        Ok(())
    }
    pub fn encode(&self) -> anyhow::Result<Vec<u8>> {
        self.validate()?;
        let bytes = serde_json::to_vec(self)?;
        anyhow::ensure!(bytes.len() <= MAX_EVENT_BYTES, "event too large");
        Ok(bytes)
    }
    pub fn decode(bytes: &[u8]) -> anyhow::Result<Self> {
        anyhow::ensure!(bytes.len() <= MAX_EVENT_BYTES, "event too large");
        let value: Self = serde_json::from_slice(bytes)?;
        value.validate()?;
        Ok(value)
    }
    pub fn digest(&self) -> anyhow::Result<Vec<u8>> {
        Ok(Sha256::digest(self.encode()?).to_vec())
    }
}
pub fn retry_delay_secs(attempts: i32) -> i64 {
    2_i64.pow(attempts.clamp(0, 9) as u32).min(300)
}
#[cfg(test)]
mod tests {
    use super::*;
    fn event() -> Envelope {
        Envelope::new(
            Snapshot {
                id: 1,
                name: "键盘".into(),
                price_cents: 19900,
                stock: 10,
                listed: true,
            },
            1,
        )
    }
    #[test]
    fn stable_retries_keep_the_event_identity() {
        let e = event();
        assert_eq!(Envelope::decode(&e.encode().unwrap()).unwrap(), e);
    }
    #[test]
    fn incompatible_versions_are_rejected() {
        let mut e = event();
        e.schema_version = 2;
        assert!(e.encode().is_err());
    }
    #[test]
    fn wrong_aggregate_identity_is_rejected() {
        let mut e = event();
        e.aggregate_id = 2;
        assert!(e.encode().is_err());
    }
    #[test]
    fn negative_money_is_not_a_valid_snapshot() {
        let mut e = event();
        e.payload.price_cents = -1;
        assert!(e.encode().is_err());
    }
    #[test]
    fn structured_digest_ignores_json_layout() {
        let e = event();
        let pretty = serde_json::to_vec_pretty(&e).unwrap();
        assert_eq!(
            e.digest().unwrap(),
            Envelope::decode(&pretty).unwrap().digest().unwrap()
        );
    }
    #[test]
    fn oversized_payload_is_rejected_before_json_parsing() {
        let error = Envelope::decode(&vec![b' '; MAX_EVENT_BYTES + 1]).unwrap_err();
        assert_eq!(error.to_string(), "event too large");
    }
    #[test]
    fn backoff_is_bounded() {
        assert_eq!(retry_delay_secs(1), 2);
        assert_eq!(retry_delay_secs(i32::MAX), 300);
        assert_eq!(retry_delay_secs(-1), 1);
    }
}
```

Snapshot 表达一个商品版本的完整展示状态；Envelope 是包在 payload 外面的事件信封。它提供 schema_version、kind、event_id、aggregate_id、revision 与发生时间，让接收者先识别协议，再解释业务内容。

### 28.3.4 【进阶】三种编号各有用途

event_id 标识某一次已经形成的事件，网络重发时应保持不变；aggregate_id 标识商品实体，多次商品变化共享这个 id；revision 表示同一商品的业务修订次序，必须由权威写入路径管理。

三者不能互换。为每次重试生成新 event_id 会让消费者无法按事件身份识别重复；只使用商品 id 去重则可能把该商品所有后续合法更新误删。UUID 的随机性也不能代替商品版本的单调递增关系。

### 28.3.5 【进阶】schema_version 与 revision 不同

schema_version 描述消息格式版本，例如接收者是否理解当前字段语义。revision 描述同一个商品已经发生到第几次修订。格式版本一的事件可以包含商品修订一百，二者没有大小对应关系。

本章只接受 schema_version=1 且 kind 为 product.snapshot.v1。未知类型明确拒绝，而不是用默认值继续修改业务投影。正式格式升级需要版本并存策略与兼容测试，不只是把常量从一改成二。

### 28.3.6 【进阶】JSON 字段验证与大小约束

serde 负责解析字段类型，validate 再检查业务含义：事件 UUID 不为空、商品 id 正数且与 payload 对应、revision 正数、名称有效、金额与库存非负。deny_unknown_fields 使当前格式严格拒绝未知字段。

严格模式易于发现拼写和意外输入，但也意味着追加字段不是自动兼容。应在演进计划中解释这个取舍。decode 先限制输入 64 KiB 再解析，encode 同样限制结果大小，使生产者和消费者遵守一致上限；broker 的上限配置是另一层约束。

### 28.3.7 【进阶】发生时间不能决定业务次序

occurred_at_unix_ms 使用生产进程的时钟，适合记录和粗略观察延迟，但不同机器时钟可能偏移，也可能被校准。收到较晚时间戳不表示商品版本一定更新。

后面的投影使用 revision 判断新旧，并通过事件身份识别重复。时间戳用于诊断，不用于替代商品修订顺序。这个模型也不会自动校验所有机器的时间可信性。

### 28.3.8 【精通】摘要可以发现什么

digest 对当前结构重新编码后计算 SHA-256，因此同一结构输入的缩进变化不会影响摘要。它可用于识别“同一 event_id 却出现不同业务内容”等异常。

这不是通用跨语言规范 JSON 的证明，也不是消息签名。不同语言的序列化细节与未来字段规则需要共同规范；攻击者若能替换内容，也能重新计算无密钥哈希。身份认证与完整性保护仍应由传输安全和明确的签名协议处理。

## 28.4 Rust 与原生客户端的构建边界

### 28.4.1 【入门】为什么需要 C 工具链

rdkafka 是 Rust 对 librdkafka 的封装。本章开启 cmake-build，从依赖源码构建原生库，因此机器需要可运行的 C/C++ 编译器、CMake 和相应构建工具。Cargo 能下载 Rust crate，不表示它会替你安装系统编译器。

macOS 可使用已配置的 Command Line Tools 与 CMake；Linux 需要对应编译工具。先执行 `cmake --version` 与 `cc --version`，确认命令可用，再进入 cargo build。依赖准备应遵循自己的系统安装方式，不把某个机器上的绝对工具路径写进项目源码。

### 28.4.2 【进阶】可指定临时 CMake 路径

如果工具安装在自定义位置，可在构建终端导出 CMAKE 指向真实可执行文件。它用于构建脚本，不是 Kafka broker 地址。构建日志出现“failed to execute cmake”时，应先修工具路径，而不是尝试更改消息代码。

本轮实际使用工作区内临时 CMake 3.31.10 完成原生构建，没有要求读者覆盖系统工具。默认 feature 下的纯事件测试与启用 kafka 的全功能构建必须分开报告，不能只运行前者就宣称客户端已经编译。

### 28.4.3 【入门】先运行模型测试

在工作区根执行：
```bash
cargo +1.92.0 test -p messaging --lib
cargo +1.92.0 test --locked -p messaging --all-features
```

第一次增加依赖时允许 Cargo.lock 有意更新，审核后后续使用 --locked。事件测试应包含正常往返、未知版本、错误实体标识、负金额、结构摘要、过大输入和有界退避。启用全部 feature 的测试还会编译原生客户端与演示程序。

### 28.4.4 【精通】构建特性与传输安全

本章原生客户端配置服务于回环地址的 PLAINTEXT 实验，没有自动提供 SASL/TLS。Rust 包清单中能看到 rustls 的其他依赖，不表示 librdkafka 已经启用并配置同样的能力。

未来接入受保护集群时，应检查原生库构建特性、security.protocol、证书和认证机制，并实际完成握手验证。把 bootstrap 地址改为远端域名，不能自动完成传输安全迁移。

## 28.5 生产者：入队与确认是不同步骤

### 28.5.1 【入门】完整 Kafka 模块

创建 messaging/src/kafka.rs：
```rust
use crate::event::Envelope;
use anyhow::Context;
use rdkafka::{
    ClientConfig, Message, Offset, TopicPartitionList,
    consumer::{CommitMode, Consumer, StreamConsumer},
    producer::{FutureProducer, FutureRecord},
};
use std::{sync::Arc, time::Duration};

pub fn producer(brokers: &str) -> anyhow::Result<FutureProducer> {
    Ok(ClientConfig::new()
        .set("bootstrap.servers", brokers)
        .set("enable.idempotence", "true")
        .set("acks", "all")
        .set("delivery.timeout.ms", "5000")
        .set("request.timeout.ms", "3000")
        .set("linger.ms", "5")
        .set("queue.buffering.max.kbytes", "10240")
        .create()?)
}
pub async fn send(producer: &FutureProducer, topic: &str, event: &Envelope) -> anyhow::Result<()> {
    let payload = event.encode()?;
    let key = event.aggregate_id.to_string();
    tokio::time::timeout(
        Duration::from_secs(8),
        producer.send(
            FutureRecord::to(topic).key(&key).payload(&payload),
            Duration::from_millis(250),
        ),
    )
    .await
    .context("producer await budget exhausted; delivery may still happen")?
    .map_err(|(error, _)| anyhow::anyhow!("Kafka delivery failed: {error}"))?;
    Ok(())
}
pub fn consumer(brokers: &str, group: &str, topic: &str) -> anyhow::Result<Arc<StreamConsumer>> {
    let consumer: StreamConsumer = ClientConfig::new()
        .set("bootstrap.servers", brokers)
        .set("group.id", group)
        .set("enable.auto.commit", "false")
        .set("enable.auto.offset.store", "false")
        .set("auto.offset.reset", "earliest")
        .set("isolation.level", "read_committed")
        .set("max.poll.interval.ms", "30000")
        .set("session.timeout.ms", "10000")
        .set("socket.timeout.ms", "3000")
        .create()?;
    consumer.subscribe(&[topic])?;
    Ok(Arc::new(consumer))
}
pub fn decode_message(message: &impl Message) -> anyhow::Result<Envelope> {
    let event = Envelope::decode(message.payload().context("empty Kafka payload")?)?;
    let key = std::str::from_utf8(message.key().context("missing aggregate key")?)?;
    anyhow::ensure!(
        key == event.aggregate_id.to_string(),
        "Kafka key does not match event aggregate"
    );
    Ok(event)
}
pub async fn commit_processed(
    consumer: Arc<StreamConsumer>,
    topic: String,
    partition: i32,
    offset: i64,
) -> anyhow::Result<()> {
    let mut positions = TopicPartitionList::new();
    positions.add_partition_offset(
        &topic,
        partition,
        Offset::Offset(offset.checked_add(1).context("offset overflow")?),
    )?;
    tokio::time::timeout(
        Duration::from_secs(5),
        tokio::task::spawn_blocking(move || consumer.commit(&positions, CommitMode::Sync)),
    )
    .await
    .context("offset commit wait budget exhausted")???;
    Ok(())
}
```

producer 创建可复用 FutureProducer；send 将已经形成的事件编码，以 aggregate_id 为 key 发往明确主题。Envelope::new 只用于形成新事实，send 本身不创建新的 event_id，便于后续可靠重发。

### 28.5.2 【进阶】FutureProducer 的两段等待

producer.send 的 queue timeout 限制本地队列满时等待入队的时间。本章为 250 毫秒。消息进入队列以后，还要等待 broker 的交付结果；本地队列接受并不等于远端已经确认保存。

配置 delivery.timeout.ms=5000 约束客户端交付尝试，外层 Tokio 八秒则防止调用方无限等待交付 future。这几种时间预算覆盖不同阶段，不能把“250 毫秒没有报错”解释成消息已经持久化。

### 28.5.3 【进阶】幂等生产者解决哪种重复

enable.idempotence=true 配合 acks=all，让客户端与 broker 使用生产者身份和序号处理特定重传重复。它主要解决生产协议内部的重试情形。

如果应用显式把同一 Envelope 调用 send 两次，这仍然是两次业务发送，不能期待 Kafka 自动按 event_id 或 key 删除第二条。进程重启后的应用重发也需要持久化事件身份和消费者幂等处理，后面 Outbox/Inbox 会继续建立这两端机制。

### 28.5.4 【进阶】队列、批量与吞吐

linger.ms=5 给客户端短暂聚合批次的机会，queue.buffering.max.kbytes 限制本地缓冲。批量减少请求开销，但会增加等待，并且每个生产者实例都拥有自己的缓冲预算。

吞吐调优要同时观察消息体积、批次、压缩、分区、broker 负载与端到端延迟。不能在没有测量时一味调大队列，使依赖故障被隐藏成进程内越来越多的待发送数据。

### 28.5.5 【精通】外层超时不会撤销已经入队的记录

Tokio timeout 停止等待 send future 时，原生客户端可能还在后台执行交付。代码的错误上下文明确写出 delivery may still happen，提醒调用者结果存在不确定性。

因此可靠中继不能在超时后生成另一条新事件，也不能宣称上一条从未到达。它应该保留原 event_id 与内容，允许后续重发，并要求消费者能处理重复；这正是下一章要接上的工程行为。

### 28.5.6 【入门】完整发送程序

创建 messaging/src/bin/send-snapshot.rs：
```rust
use messaging::{
    event::{Envelope, Snapshot},
    kafka,
};
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let producer = kafka::producer(&std::env::var("KAFKA_BROKERS")?)?;
    let topic = std::env::var("KAFKA_TOPIC").unwrap_or_else(|_| "rustmall.catalog.demo.v1".into());
    let event = Envelope::new(
        Snapshot {
            id: 1,
            name: "演示键盘".into(),
            price_cents: 19900,
            stock: 10,
            listed: true,
        },
        1,
    );
    kafka::send(&producer, &topic, &event).await?;
    println!("delivered demo event {}", event.event_id);
    Ok(())
}
```

它生成一个商品 1、revision 1 的演示快照，等待交付确认后打印事件 UUID。每次重新运行都会形成一个新的演示事件，因此不要用反复运行这个程序模拟“同一事件身份的重试”。正式事件身份会在业务事务内生成并持久保存。

## 28.6 消费者：业务完成后再推进位置

### 28.6.1 【入门】消费组保存独立进度

消费组由 group.id 标识。同组的活跃消费者协作分配主题分区，通常同一分区在组内由一个消费者负责；另一个组有自己独立的消费位置，可以读取同一条记录。

三个分区不意味着必须启动三个消费者。一个消费者可以负责多个分区；同组消费者多于分区时，一部分会空闲。分区是组内并行能力的重要边界，不是把进程数加大就无限扩展。

### 28.6.2 【进阶】为什么关闭两种自动行为

enable.auto.commit=false 关闭周期自动提交，enable.auto.offset.store=false 关闭自动在客户端记录可提交位置。这样我们在业务处理成功之后明确提交，而不是刚把消息交给应用就把它当作完成。

关闭自动提交不代表再也不会重复。业务数据库提交以后、Kafka offset 提交以前进程崩溃，恢复后仍会读到相同记录。因此消费者幂等必须处理这个窗口，不能只靠这两个开关解决。

### 28.6.3 【进阶】提交的是下一位置

假设处理的是某个分区 offset=8，提交的恢复位置应为 9。代码使用 checked_add(1) 防止整数溢出，并在 TopicPartitionList 中明确主题与分区。

这并不是要求下一条可见业务消息一定在 9；它表达“从 9 开始继续寻找后续记录”。若把 8 原样提交，恢复后可能再次处理当前记录；若过早提交 10，可能跳过尚未完成的业务记录。

### 28.6.4 【进阶】先验证 key，再处理 payload

decode_message 要求消息有 payload、可以解析为合法 Envelope，并且 Kafka key 与 aggregate_id 对应。只验证 JSON 不检查 key，可能让同一商品被错误分区，破坏依赖按商品顺序处理的假设。

缺少 key、key 不是 UTF-8 或 key 对不上都返回错误。这里不会自动把坏消息提交掉；正式持续消费者需要定义重试、隔离与人工处理策略，否则一条坏记录就可能阻塞整个分区。

### 28.6.5 【进阶】借用消息与拥有业务对象

librdkafka 提供的 BorrowedMessage 借用消费者持有的数据。Envelope::decode 产生拥有 String 等字段的业务对象，因此可以在提取主题、分区、offset 后释放消息，再执行异步后续处理。

不要把借用字节随意移到需要 'static 的后台任务中。需要跨作用域时应明确复制成拥有所有权的对象，计算其内存成本；让编译器接受不代表消息生命周期设计自动合理。

### 28.6.6 【精通】同步提交为何放入 spawn_blocking

CommitMode::Sync 可能等待原生客户端与 broker 协调。直接在 Tokio 异步任务上执行阻塞调用，会占用运行时线程，因此 commit_processed 用 spawn_blocking 隔离它。

外层五秒 timeout 只限制等待 JoinHandle，不能强制取消已经运行的阻塞函数。超时以后实际 offset 提交仍可能完成，所以恢复逻辑仍应允许重放，并避免把“等待超时”当作“提交肯定没发生”。

### 28.6.7 【精通】read_committed 不等于业务恰好一次

isolation.level=read_committed 影响消费者看到 Kafka 事务记录的方式。本章生产者只是幂等发送，没有建立跨 PostgreSQL 与 Kafka 的原子事务。

即便 Kafka 内部事务可以约束某些读写流程，也不能自动把另一数据库里的订单扣款纳入同一原子提交。业务“只生效一次”需要围绕具体副作用、幂等键和事务边界证明，不能从一个客户端配置推导出来。

## 28.7 用一次性消费者观察提交与重放

### 28.7.1 【入门】完整消费程序

创建 messaging/src/bin/consume-once.rs：
```rust
use anyhow::{Context, ensure};
use messaging::kafka;
use rdkafka::{Message, consumer::Consumer};
use std::time::Duration;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let arguments: Vec<String> = std::env::args().skip(1).collect();
    let commit = match arguments.as_slice() {
        [] => true,
        [flag] if flag == "--no-commit" => false,
        _ => anyhow::bail!("usage: consume-once [--no-commit]"),
    };
    let topic = std::env::var("KAFKA_TOPIC").unwrap_or_else(|_| "rustmall.catalog.demo.v1".into());
    let group = std::env::var("KAFKA_GROUP").context("KAFKA_GROUP missing")?;
    let wait: u64 = std::env::var("KAFKA_WAIT_SECS")
        .unwrap_or_else(|_| "20".into())
        .parse()?;
    ensure!((1..=60).contains(&wait), "wait must be 1..60 seconds");
    let consumer = kafka::consumer(&std::env::var("KAFKA_BROKERS")?, &group, &topic)?;
    let message = tokio::time::timeout(Duration::from_secs(wait), consumer.recv())
        .await
        .context("no event arrived within the observation budget")??;
    let event = kafka::decode_message(&message)?;
    let (topic, partition, offset) = (
        message.topic().to_owned(),
        message.partition(),
        message.offset(),
    );
    // The decoded event owns its data; release the borrowed librdkafka message.
    drop(message);
    println!(
        "observed event={} aggregate={} revision={} partition={} offset={}",
        event.event_id, event.aggregate_id, event.revision, partition, offset
    );
    if commit {
        kafka::commit_processed(consumer.clone(), topic, partition, offset).await?;
        println!(
            "committed next offset={}",
            offset.checked_add(1).context("offset overflow")?
        );
    } else {
        println!("not committed; this group may observe the record again");
    }
    consumer.unsubscribe();
    Ok(())
}
```

它只读取一条合法消息，打印身份和位置，默认提交。如果指定 --no-commit 则不推进组位置。KAFKA_WAIT_SECS 限制观察等待，范围一到六十秒，默认二十秒；到时没有消息会返回错误，不把没有观察到事件伪装成处理成功。

### 28.7.2 【入门】建立专用 JSON 主题

保持本章 Compose 项目运行，在工作区根执行：

如果修改了 KAFKA_LAB_PORT，相应调整 KAFKA_BROKERS。预期发送程序打印 delivered demo event 加一个 UUID。这个输出来自等待交付结果之后，而不是在调用 send 之前提前打印。

### 28.7.3 【入门】第一次不提交

为本次实验使用从未运行过的组名，例如自己的 lab-replay-001。下列演示需要该主题只有这次产生的一条测试事件，或者你能明确识别正在观察的事件；不要在已经积累多轮消息后假定下一条就是最新发送的记录。
```bash
export KAFKA_GROUP=lab-replay-001
cargo +1.92.0 run --locked -p messaging --features kafka --bin consume-once -- --no-commit
cargo +1.92.0 run --locked -p messaging --features kafka --bin consume-once -- --no-commit
```

两次应看到相同 event_id、partition、offset，以及 not committed。第一次进程退出不代表组进度已经持久前进。每次重新分配分区可能需要时间，应给正常组协调留足观察预算。

### 28.7.4 【进阶】提交以后再启动同一个组
```bash
cargo +1.92.0 run --locked -p messaging --features kafka --bin consume-once
KAFKA_WAIT_SECS=3 \
  cargo +1.92.0 run --locked -p messaging --features kafka --bin consume-once
```

第一次仍看到该记录，随后打印 committed next offset。若该分区第一条演示记录 offset 为零，提交位置就是一。第二次在没有新消息时应等待后以观察超时退出，不应再次打印同一事件。

三秒只是本机实验的短观察窗口，不证明集群永远不会重放。真实重平衡、提交结果不确定和处理失败都需要恢复设计。本实验成功依赖前一次同步提交已收到确认。

### 28.7.5 【进阶】换一个消费组仍可读取
```bash
KAFKA_GROUP=lab-independent-001 \
  cargo +1.92.0 run --locked -p messaging --features kafka --bin consume-once
```

新组没有已提交位置，auto.offset.reset=earliest 使它从可用的较早记录开始。应重新看到之前的演示事件，说明一个组提交进度并没有删除其他组需要的数据。

earliest 只在没有有效已提交位置等情况下生效。对已经保存进度的组反复设置 earliest，不会自动清空进度；需要重放时应设计明确的组重置或新组流程，并理解重放的业务副作用。

### 28.7.6 【进阶】正常停止和数据清理

一次性客户端执行完会退出。停止 broker 可以使用不带 --volumes 的 down，命名卷继续保留；再次启动会使用相同日志和集群身份。
```bash
docker compose -p rustmall-ch28 -f deploy/messaging/compose.yaml down
```

只有确认本项目是可以丢弃的教学数据，并决定从空日志重新开始时，才使用 `down --volumes`。删除卷会同时丢失日志与组位置，不能把这种操作当作消费者恢复方法。实验的 CLUSTER_ID 也不能在保留旧日志时随意更换。

### 28.7.7 【精通】为什么演示消费者不等于业务消费者

consume-once 把“成功解码并打印”作为处理完成，适合观察协议和偏移量。真正业务处理还要写数据库、核对事件身份与版本，再决定是否提交。

若把打印成功直接替换成网络调用，仍会遇到远端已完成但响应丢失的问题。消费者并发处理多条记录时，还要防止先提交较大 offset 而跳过前面尚未完成的记录。本章串行一次性例子故意保持简单，下一章用持久化投影和 Inbox 建立业务处理边界。

## 28.8 故障窗口与可靠性判断

### 28.8.1 【入门】至少一次意味着可能重复

如果先处理再提交，崩溃可能发生在两者之间。恢复时读取重复记录是正常情况，不是 Kafka 一定违反承诺。系统应把重复变成可识别、可安全处理的输入。

反过来，先提交再处理可以减少重复，却可能在提交后崩溃而永远不再处理该记录。这是两种不同取舍，不能用“自动提交更方便”代替业务语义选择。

### 28.8.2 【进阶】同商品版本如何防止旧状态覆盖新状态

假设消费者先收到商品修订 8，又收到延迟重发的修订 7。若只按到达顺序覆盖，名称和价格会倒退。消费者应比较持久化版本，拒绝旧状态覆盖更新状态。

这里采用完整快照，有机会用更高版本重建最新展示；如果事件是“库存减一”这种增量，跳过中间事件可能直接丢失业务影响。选快照还是增量，需要结合是否允许跳版、审计和恢复要求决定。

### 28.8.3 【进阶】分区顺序不是数据库修订顺序的替代品

同一 key 会帮助记录进入同一分区，但生产方仍可能并发发送、重发旧事件，或在扩分区后改变路由。日志的追加顺序表达 Kafka 接收到记录的顺序，不一定就是业务事务提交的顺序。

因此后面仍保留 revision 和去重标识。不能因为主题有序，就删除业务层版本检查；也不能因为有版本号，就不再关心分区与并发处理策略。

### 28.8.4 【精通】长处理与重平衡

消费者长时间不及时调用所需轮询流程，可能超过 max.poll.interval.ms，失去组内分区分配。之后另一个消费者接手，而旧任务可能还在执行数据库副作用。

设置更大的超时只能延后检测，不能证明不会并发执行旧任务。本章不把长事务或阻塞代码塞进接收循环；后续消费者会将处理、去重、取消和提交边界放在一起审核。

### 28.8.5 【精通】数据库与 Kafka 之间的空隙

如果 catalog 先提交商品 UPDATE，再调用 send，进程可能恰好在两者之间退出：商品已经改了，事件却没有形成可靠发送记录。若反过来先发事件再改数据库，消费者又可能看到根本没有提交成功的商品状态。

这两个时序都不能通过“写在同一个 Rust 函数里”变成原子操作。下一章把业务修改和待发送事件写进同一个 PostgreSQL 事务，再由可重试中继发送；消费端用自己的数据库事务记录已处理事件和投影变化。

### 28.9.4 【精通】不要用删卷替代诊断

日志目录身份不匹配、端口冲突和消费者已有进度是不同问题。一次删卷可能让现象消失，也会销毁恢复时最重要的证据和数据。

正确排查应先确认项目、主题、分区、组和位置，再收集 broker 与客户端错误。在可抛弃教学环境中从空卷重做是允许的实验选择，但应明确记录它重置了哪些状态，而不是把这种方法写成生产恢复流程。

## 28.10 分层练习与 Outbox 衔接

### 28.10.1 【入门练习】解释四个坐标

说明 topic、partition、offset、group.id 分别标识什么，并解释“分区 0 的 offset 10 大于分区 1 的 offset 9，所以前者更晚发生”是否成立。

参考答案：主题组织记录，分区是一条追加日志，offset 定位该分区位置，组记录独立消费进度。不同分区 offset 无法构成全局时间比较，这个推断不成立。

### 28.10.2 【操作练习】保存一次重放证据

从空演示主题发送一条事件，使用同组 --no-commit 运行两次，再提交并重新启动同组，最后换新组读取。只保存事件 id、位置和退出结果，不保存服务凭据。

评分要点：两次未提交看到同一身份和位置；提交值为处理位置加一；同组无新消息时不重放；新组可读取保留记录。若主题已有多条消息，应逐条说明观察对象，不能仅凭出现任意记录就判定成功。

### 28.10.3 【推理练习】为什么幂等生产仍要 Inbox

应用在收到不确定的交付错误后，再次调用 send 发送同一事件。enable.idempotence 是否保证消费者只处理一次？

参考答案：不保证。显式业务重发与生产协议内部重传不是同一层；即使日志只有一条，消费完成后未提交 offset 也可能重放。消费端需要持久化事件身份并使业务副作用与去重记录处于同一事务边界。

### 28.10.4 【推理练习】错误提交顺序

消费者处理 offset 8 失败，却提交了 9；另一个消费者处理 8 成功，只提交了 8。分别有什么问题？

参考答案：前者恢复从 9 开始，可能永久跳过失败记录；后者恢复仍可再次读取 8，必须依靠幂等防止重复副作用。正确常规顺序是处理成功，再提交 9，并继续处理提交失败的不确定性。

### 28.10.5 【扩展练习】设计格式升级

为 Snapshot 增加币种字段。当前 deny_unknown_fields 与 schema_version 检查会怎样影响新旧消费者？你会怎样安排部署？

参考要点：旧消费者会拒绝未知字段或新版本，不能假定追加字段天然兼容。需要选择明确的版本共存策略，例如新类型或主题、先部署兼容读取方、定义缺失币种语义，再切换生产方；完成新旧格式与混合部署测试后才能退出旧版本。

### 28.10.6 【衔接】下一章把事实写进同一个事务

目前我们已经能解释日志位置、组进度、客户端确认和重复窗口，并完成可运行的 Rust 消息实验。仍缺少的是商品变更到事件之间的原子记录，以及消费结果到去重记录之间的原子提交。

下一章新增 Outbox 与 Inbox：业务事务保存待发送事实，中继允许重复发送，消费者在事务中识别重复并更新投影。可靠性来自这些边界共同成立，而不是把一个 Kafka 连接对象放进 AppState。

继续阅读可对照 [Apache Kafka 4.0 实验文档](https://kafka.apache.org/40/getting-started/quickstart/)、[生产者配置说明](https://kafka.apache.org/40/configuration/producer-configs/) 和 [rdkafka 0.39 FutureProducer 文档](https://docs.rs/rdkafka/0.39.0/rdkafka/producer/struct.FutureProducer.html)。本章实际值固定于配套锁文件与镜像，不把官方后续版本示例默认为本实验已经升级。

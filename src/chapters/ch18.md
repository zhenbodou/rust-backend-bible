# 第 18 章 Redis 从安装到精通 + redis-rs

商品详情是 RustMall 中访问量最大的接口：每个浏览商品的用户都会请求它，而商品信息很少变化。每次请求都查一次 PostgreSQL，数据库的连接和 CPU 就会被大量重复查询占满。本章用缓存解决这个问题：

Redis：最常用的缓存与内存数据库。本章从安装讲起，覆盖五种基本数据结构、过期与淘汰、持久化与高可用，以及使用 Redis 时最常见的性能陷阱。

redis crate：在 Rust 中访问 Redis，包括连接管理、命令、管道和错误处理。

moka：进程内缓存，可避免网络往返，但每个服务实例各有一份；具体延迟与内存收益仍须按负载评估。

缓存设计：cache-aside 模式、缓存与数据库的一致性，以及缓存穿透、击穿、雪崩三大问题。

本章涉及的软件与 crate：

| 软件 / crate | 作用 | 小节 |
| --- | --- | --- |
| Redis 7.4 | 内存数据库，用作分布式缓存 | 18.1~18.6 |
| redis-cli | Redis 命令行客戶端 | 18.3 |
| redis | Rust 的 Redis 客戶端 | 18.7 |
| moka | 进程内缓存，支持容量上限、过期和并发去重 | 18.8 |

本章的项目部分（18.10）为商品详情加上“进程内缓存 + Redis”两级缓存。Redis 是可选的：没有配置 Redis 或 Redis 不可用时，服务自动退回为只用进程内缓存，所有已有的测试不需要启动 Redis就能运行。

## 18.1 Redis 是什么

### 18.1.1 【入门】一个“数据结构服务器”

Redis 是一个把数据保存在内存中的键值数据库。和 HashMap 一样，每个值都有一个键；不同的是，Redis 运行在一个独立的进程中，多个服务实例可以通过网络共享同一份数据。

Redis 的值不只是字符串，还可以是列表、哈希、集合、有序集合等数据结构，并且提供直接操作这些结构的命令（例如“给有序集合中某个成员的分数加 1”）。所以它常被称为数据结构服务器。

| 用途 | 做法 | 本书中的位置 |
| --- | --- | --- |
| 缓存 | 把数据库查询结果存一份，设置过期时间 | 本章项目 |
| 计数器、限流 | INCR单次自增原子；与过期组合时需另设协议 | 第42章登录限流；第39章对照本地限流 |

| 用途 | 做法 | 本书中的位置 |
| --- | --- | --- |
| 会话、令牌黑名单 | 带过期时间的键 | 第 16 章练习 |
| 排行榜 | 有序集合 | 18.4.6 节 |
| 分布式锁 | SET key value NX EX 30 | 18.9.4 节 |
| 简单消息队列 | 列表、Stream、发布订阅 | 第 28 章 Kafka 之前的过渡方案 |

### 18.1.2 【入门】为什么快

一次 Redis 命令通常在一毫秒以内完成（大部分时间花在网络往返上），一台普通服务器每秒可以处理十万量级的简单命令。原因有三个：

数据在内存中：读写内存比读写磁盘快几个数量级。持久化在后台进行，不阻塞命令（18.6 节）。

命令执行是单线程的：所有命令在一个线程中依次执行，不需要锁，也没有线程切换的开销。网络读写从 Redis 6 起可以使用多个 I/O 线程，但执行命令的始终只有一个线程。

高效的数据结构：每种类型都根据大小自动选择紧凑或高效的内部编码。

单线程执行有一个直接的推论，贯穿本章：一个慢命令会阻塞所有客戶端。对一个有一百万个成员的集合执行 SMEMBERS，在它返回之前，其他所有请求都在排队。18.6.5 节会专门讲这个问题。

### 18.1.3 【进阶】Redis、Valkey 与许可证

选择 Redis 时你会遇到一个名字：Valkey。2024 年 Redis 公司把 Redis 7.4 起的许可证从 BSD 改为RSALv2 与 SSPLv1 双许可；随后 Linux 基金会基于 Redis 7.2 的代码发起了采用 BSD 许可证的分支Valkey。2025 年发布的 Redis 8 又增加了 AGPLv3 作为可选许可证。

对本书的读者来说，需要知道的是：

协议与命令兼容：本章的命令、redis crate 的代码，对 Redis 7.x、Redis 8 和 Valkey 都适用。

许可证只在“把 Redis 作为服务提供给别人”时才有实际区别。在自己的后端中使用 Redis，这几种许可证都允许。如果你所在的公司对许可证有要求，请咨询法务。

云厂商的托管服务（各大云的“Redis 兼容”缓存服务）多数同时提供 Redis 与 Valkey 引擎，切换时通常不需要修改代码。

本书使用官方镜像 redis:7.4-alpine。如果你更倾向于 Valkey，把镜像换成 valkey/valkey:8-alpine，其余内容不变。

### 18.1.4 【进阶】Redis 与进程内缓存的分工

| 方面 | 进程内缓存（moka） | Redis |
| --- | --- | --- |
| 读取速度 | 纳秒~微秒级，没有网络 | 约 0.1~1 毫秒，一次网络往返 |
| 多实例共享 | 每个实例一份，互相看不到 | 所有实例共享一份 |

| 方面 | 进程内缓存（moka） | Redis |
| --- | --- | --- |
| 容量 | 受单个进程的内存限制 | 可以单独扩容，甚至做成集群 |
| 失效 | 只能失效本实例的副本 | 删除一次，所有实例都看到 |
| 进程重启 | 缓存全部丢失 | 不受影响 |
| 额外依赖 | 无 | 需要部署和运维 Redis |

两者并不冲突。本章项目采用两级缓存：先查进程内缓存（L1），未命中再查 Redis（L2），都没有才查数据库。L1 挡住同一实例上的重复请求，L2 让多个实例共享查询结果，并在实例重启后依然有效。

## 18.2 安装 Redis

### 18.2.1 【入门】Docker（推荐）

和第 13 章的 PostgreSQL 一样，开发环境推荐用 Docker 运行 Redis，四个平台的做法完全相同：
```bash
docker run -d --name rustmall-redis -p 6379:6379 redis:7.4-alpine

# 进入容器中的 redis-cli
docker exec -it rustmall-redis redis-cli
127.0.0.1:6379> PING
PONG
```

-p 6379:6379 把容器的 6379 端口（Redis 的默认端口）映射到本机，之后程序用redis://localhost:6379 连接。18.10.2 节会把启动命令写成脚本 scripts/dev-redis.sh，加上持久化与内存上限等配置。

### 18.2.2 【入门】macOS
```bash
brew install redis
# 作为后台服务启动，开机自动运行
brew services start redis
redis-cli ping
```

配置文件位于 $(brew --prefix)/etc/redis.conf。停止服务用 brew services stop redis。

### 18.2.3 【入门】Linux

各发行版的软件源中的 Redis 版本往往较旧。Redis 官方提供了 APT 和 RPM 软件源，以 Ubuntu /Debian 为例（命令以 Redis 官方文档为准）：
```bash
sudo apt-get install -y lsb-release curl gpg
KEYRING=/usr/share/keyrings/redis-archive-keyring.gpg
curl -fsSL https://packages.redis.io/gpg | sudo gpg --dearmor -o "$KEYRING"
echo "deb [signed-by=$KEYRING] https://packages.redis.io/deb $(lsb_release -cs) main" \
    | sudo tee /etc/apt/sources.list.d/redis.list
sudo apt-get update
sudo apt-get install -y redis

sudo systemctl enable --now redis-server
redis-cli ping
```

配置文件通常在 /etc/redis/redis.conf，日志通过 journalctl -u redis-server 查看。

### 18.2.4 【入门】Windows

Redis 官方不提供 Windows 原生版本。可选的方式：

Docker Desktop（推荐）：即 18.2.1 节的做法。Docker Desktop 本身运行在 WSL2 之上。

WSL2：在 WSL2 的 Ubuntu 中按 18.2.3 节安装。Windows 中的程序可以通过 localhost:6379访问 WSL2 中的 Redis。

网上流传的 “Redis for Windows” 移植版本停留在多年前的版本，不要使用。

redis-cli 也可以不安装在本机，随时通过 docker exec -it rustmall-redis redis-cli 使用。

### 18.2.5 【进阶】关键配置项

Redis 的配置写在 redis.conf 中，也可以作为启动参数传入（redis-server --maxmemory 256mb），或者运行时用 CONFIG SET 修改（重启后失效，除非再执行 CONFIG REWRITE）。

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| port | 6379 | 监听端口 |
| bind | 127.0.0.1 -::1 | 监听地址。不要在公网地址上无密码开放 Redis |
| protected-mode | yes | 没有设置密码且绑定了非本机地址时，拒绝外部连接 |
| requirepass | 无 | 默认用户的密码；Redis 6 起推荐用 ACL 为每个应用建立独立用户 |
| maxmemory | 0（不限制） | 内存上限，作缓存用时必须设置 |
| maxmemory-policy | noeviction | 达到上限后的淘汰策略（18.5 节） |
| appendonly | no | 是否开启 AOF 持久化（18.6 节） |
| save | 有默认规则 | RDB 快照的触发规则 |

安全提示：暴露在公网上、没有密码的 Redis 是最常见的入侵入口之一，攻击者可以利用它写入文件、植入挖矿程序。生产环境的 Redis 必须只监听内网地址，开启密码或 ACL，并用防火墙限制来源。

## 18.3 redis-cli 与键的基础

### 18.3.1 【入门】字符串与过期时间

打开 redis-cli，先熟悉最常用的命令：
```text
127.0.0.1:6379> SET greeting "你好"
OK
127.0.0.1:6379> GET greeting
"\xe4\xbd\xa0\xe5\xa5\xbd"
127.0.0.1:6379> EXISTS greeting
(integer) 1
127.0.0.1:6379> DEL greeting
(integer) 1
127.0.0.1:6379> GET greeting
(nil)
```

redis-cli 默认把非 ASCII 字节显示为转义序列，加上 --raw 参数启动（redis-cli --raw）就能直接显示中文。

过期时间是缓存的基础：
```text
127.0.0.1:6379> SET session:abc "user-7" EX 60      # 60 秒后自动删除
OK
127.0.0.1:6379> TTL session:abc                     # 剩余秒数
(integer) 57
127.0.0.1:6379> PERSIST session:abc                 # 取消过期，变为永久
(integer) 1
127.0.0.1:6379> TTL session:abc
(integer) -1
127.0.0.1:6379> TTL no-such-key
(integer) -2
```

| TTL 返回值 | 含义 |
| --- | --- |
| 正数 | 剩余秒数 |
| -1 | 键存在，但没有过期时间 |
| -2 | 键不存在 |

SET 的常用选项：

| 选项 | 含义 |
| --- | --- |
| EX 秒 / PX 毫秒 | 同时设置过期时间 |
| NX | 只在键不存在时设置（用于分布式锁、去重） |
| XX | 只在键已存在时设置 |
| KEEPTTL | 修改值但保留原来的过期时间 |

| 选项 | 含义 |
| --- | --- |
| GET | 设置新值并返回旧值 |

注意：对一个有过期时间的键执行不带 KEEPTTL 的 SET，过期时间会被清除，键变成永久的。这是一个常见的“缓存永不过期”的原因。

### 18.3.2 【入门】原子计数
```text
127.0.0.1:6379> INCR page:views
(integer) 1
127.0.0.1:6379> INCRBY page:views 10
(integer) 11
127.0.0.1:6379> DECR page:views
(integer) 10
```

INCR 是原子的：一百个客戶端同时执行 INCR，结果一定增加 100。对比“先 GET、在程序中加 1、再 SET”的写法，两个客戶端可能读到同一个旧值，结果只加了 1。这就是第 7 章讲过的“读―改―写”竞争，在分布式环境中同样存在。

### 18.3.3 【进阶】键的命名与查找

Redis 只有一个扁平的键空间（默认有 16 个编号的数据库，但生产中通常只用 0 号，Redis Cluster 也只支持 0 号），所以键名需要约定。常见的约定是用冒号分隔层级：
```text
<应用>:<实体>:<版本>:<ID>
rustmall:product:v1:42
rustmall:ratelimit:ip:203.0.113.7
```

应用前缀：多个应用共用一个 Redis 时避免冲突，也便于按前缀统计和清理。

版本号：缓存值的格式改变时（例如增加了字段），把 v1 改为 v2。新代码只读新键，旧键随过期时间自然消失，不会出现新代码读到旧格式而解析失败的情况。

查找键：
```text
127.0.0.1:6379> SCAN 0 MATCH rustmall:product:* COUNT 100
1) "17"                         # 下一次迭代的游标，为 "0" 时表示结束
2) 1) "rustmall:product:v1:42"
   2) "rustmall:product:v1:7"
127.0.0.1:6379> SCAN 17 MATCH rustmall:product:* COUNT 100
...
```

不要在生产环境使用 KEYS pattern：它一次性遍历全部的键，几百万个键时会阻塞 Redis 数秒，期间所有请求都在等待。SCAN 每次只遍历一小部分，用游标分多次完成。

### 18.3.4 【进阶】批量与类型

| 命令 | 作用 |
| --- | --- |
| MSET k1 v1 k2 v2 / MGET k1 k 2 | 一次设置 / 读取多个键，减少网络往返 |
| TYPE key | 查看值的类型：string、list、hash、set、zset、strea m |
| OBJECT ENCODING key | 查看内部编码，例如 int、embstr、listpack |
| MEMORY USAGE key | 估算一个键占用的内存字节数 |
| EXPIRE key 秒 / PEXPIRE | 为已有的键设置过期时间 |
| RENAME old new | 重命名 |
| UNLINK key | 删除，但在后台线程中释放内存，删除大键时代替 DEL |
| FLUSHDB / FLUSHALL | 清空当前库 / 全部库。只在开发环境使用 |

### 18.3.5 本节练习

1. 用 SET ... NX EX 10 模拟一把锁：在两个 redis-cli 窗口中同时执行，观察只有一个成功；10 秒后再试一次。

2. 先 SET a 1 EX 100，再 SET a 2，用 TTL a 验证过期时间被清除了；然后用 KEEPTTL 重做一遍。

3. 写一个 Shell 循环插入 1000 个键，用 SCAN 分批遍历它们，数一数一共需要几次迭代。

## 18.4 五种基本数据结构

### 18.4.1 【入门】总览

| 类型 | 类比 Rust | 典型用途 |
| --- | --- | --- |
| String | Vec&lt;u8&gt;（可以是文本、数字、序列化后的 JSON） | 缓存对象、计数器、锁 |
| List | VecDeque&lt;String&gt; | 队列、最近浏览记录 |
| Hash | HashMap&lt;String, String&gt; | 对象的各个字段、购物车 |
| Set | HashSet&lt;String&gt; | 标签、去重、共同关注 |
| Sorted Set | 按分数排序的 BTreeMap&lt;分数, 成员&gt;，成员唯一 | 排行榜、延时任务、按时间排序的列表 |

所有类型的值都是二进制安全的字节序列，Redis 不关心编码，也不理解 JSON 的结构。

### 18.4.2 【入门】String

除了 18.3 节的命令，String 还支持部分修改：

| 命令 | 作用 |
| --- | --- |
| APPEND key 文本 | 追加 |
| STRLEN key | 字节长度 |
| GETRANGE key 0 9 | 取一段 |
| INCRBYFLOAT key 1.5 | 浮点数增加 |

缓存一个对象，最常见的做法就是把它序列化为 JSON 存成一个 String。一个 String 最大 512 MB，但缓存值应当远小于这个数（18.6.5 节）。

### 18.4.3 【入门】List

List 是双向链表（内部实现为紧凑的 quicklist），两端的插入和弹出都是 O(1)：
```text
127.0.0.1:6379> LPUSH recent:user:7 101 102 103   # 从左端依次插入
(integer) 3
127.0.0.1:6379> LRANGE recent:user:7 0 -1          # 取全部：0 到最后一个
1) "103"
2) "102"
3) "101"
127.0.0.1:6379> LTRIM recent:user:7 0 49           # 只保留最近 50 个
OK
127.0.0.1:6379> RPOP recent:user:7
"101"
```

| 命令 | 作用 |
| --- | --- |
| LPUSH / RPUSH | 从左 / 右端插入 |
| LPOP / RPOP | 从左 / 右端弹出 |
| BLPOP key 超时秒数 | 阻塞弹出：列表为空时等待，可以做简单的任务队列 |
| LRANGE key start stop | 按下标取一段，负数表示从末尾数 |
| LTRIM key start stop | 只保留一段 |
| LLEN key | 长度 |

“最近浏览的 50 个商品”就是 LPUSH + LTRIM 的典型组合。按下标访问中间的元素（LINDEX）是O(n)，不要把 List 当数组用。

### 18.4.4 【入门】Hash

Hash 存储一个对象的多个字段，可以单独读写某个字段：
```text
127.0.0.1:6379> HSET cart:user:7 101 2 205 1      # 商品 101 买 2 件，205 买 1 件
(integer) 2
127.0.0.1:6379> HINCRBY cart:user:7 101 1          # 商品 101 再加 1 件
(integer) 3
127.0.0.1:6379> HGETALL cart:user:7
1) "101"
2) "3"
3) "205"
4) "1"
127.0.0.1:6379> HDEL cart:user:7 205
(integer) 1
```

| 命令 | 作用 |
| --- | --- |
| HSET key f1 v1 f2 v2 | 设置一个或多个字段 |
| HGET / HMGET | 读一个 / 多个字段 |
| HGETALL | 读全部字段（大 Hash 慎用） |
| HINCRBY | 字段的原子自增 |
| HDEL、HEXISTS、HLEN | 删除字段、判断存在、字段数 |

JSON String 还是 Hash？ 整体读写的对象（如商品详情）用 JSON String 更简单，一次 GET 拿到全部；需要单独修改某个字段的对象（如购物车中某个商品的数量）用 Hash，避免“读出整个对象、修改、写回”的竞争。传统上只能对整个键设置过期时间，Redis 7.4 起新增了 HEXPIRE 等命令，可以为Hash 的单个字段设置过期时间。

### 18.4.5 【入门】Set
```text
127.0.0.1:6379> SADD tags:product:101 机械 键盘 蓝牙
(integer) 3
127.0.0.1:6379> SADD tags:product:205 键盘 有线
(integer) 2
127.0.0.1:6379> SISMEMBER tags:product:101 蓝牙
(integer) 1
127.0.0.1:6379> SINTER tags:product:101 tags:product:205     # 交集
1) "键盘"
```

| 命令 | 作用 |
| --- | --- |
| SADD / SREM | 添加 / 删除成员 |
| SISMEMBER / SMISMEMBER | 判断一个 / 多个成员是否存在 |
| SCARD | 成员数 |
| SMEMBERS | 全部成员（大集合用 SSCAN） |
| SINTER、SUNION、SDIFF | 交集、并集、差集 |

| 命令 | 作用 |
| --- | --- |
| SRANDMEMBER、SPOP | 随机取 / 随机弹出（抽奖） |

### 18.4.6 【入门】Sorted Set

有序集合中的每个成员带有一个分数（浮点数），成员按分数排序。排行榜是它最经典的用途：
```text
127.0.0.1:6379> ZINCRBY sales:2026-10 3 product:101    # 商品 101 卖出 3 件
"3"
127.0.0.1:6379> ZINCRBY sales:2026-10 5 product:205
"5"
127.0.0.1:6379> ZINCRBY sales:2026-10 1 product:101
"4"
127.0.0.1:6379> ZRANGE sales:2026-10 0 9 REV WITHSCORES   # 销量前 10 名，从高到低
1) "product:205"
2) "5"
3) "product:101"
4) "4"
127.0.0.1:6379> ZRANK sales:2026-10 product:101 REV     # 排名，从 0 开始
(integer) 1
```

| 命令 | 作用 |
| --- | --- |
| ZADD key 分数 成员 | 添加或更新分数；NX/XX/GT/LT 控制条件 |
| ZINCRBY | 分数原子增加 |
| ZRANGE key start stop [REV] [WITHSCORES] | 按排名取一段；也可以加 BYSCORE 按分数范围取 |
| ZRANK / ZSCORE | 查排名 / 分数 |
| ZREM、ZCARD | 删除、成员数 |
| ZREMRANGEBYSCORE | 删除分数范围内的成员（清理过期数据） |

以时间戳为分数，有序集合还可以实现延时任务：ZADD delayed &lt;执行时间&gt; &lt;任务 ID&gt;，工作进程定期取出 ZRANGE delayed 0 &lt;当前时间&gt; BYSCORE 的任务执行。

### 18.4.7 【进阶】其他类型一览

| 类型 | 用途 |
| --- | --- |
| Stream | 只追加的日志，支持消费者组和消息确认，是 Redis 中最完整的消息队列 |
| Bitmap | 按位操作的 String，例如用 SETBIT 记录用户每天是否签到，一年只占 46 字节 |
| HyperLogLog | 用约 12 KB 估算海量元素的去重个数（误差约 0.81%），例如统计独立访客数 |
| Geo | 经纬度坐标与按距离搜索，例如“附近的门店” |
| Pub/Sub | 发布订阅，消息不持久化，订阅者不在线时消息丢失（18.9.6 节） |

RustMall 的消息队列在第 28 章使用 Kafka，本书不展开 Stream。

### 18.4.8 【精通】内部编码与内存

每种类型都有两种以上的内部编码，Redis 根据数据大小自动选择：

| 类型 | 小数据时 | 超过阈值后 |
| --- | --- | --- |
| String | int（整数）、embstr（短字符串） | raw |
| List | 小列表可以直接使用 listpack（取决于版本与配置） | quicklist（listpack 组成的链表） |
| Hash | listpack | hashtable |
| Set | intset（全是整数）或 listpack | hashtable |
| Sorted Set | listpack | skiplist + hashtable |

listpack 使用紧凑的连续存储，适合小集合。Redis 7.4 的 hash-max-listpack-entries 默认值为 512，hash-max-listpack-value 默认为 64 字节；以实例的 CONFIG GET 结果为准。按 ID 分桶可能减少顶层键的开销，也会改变访问与过期粒度，应先测量再采用。

2. 用 Sorted Set 实现一个“热搜词”：每次搜索 ZINCRBY，取前 10 名；思考怎样只统计最近 7 天（提示：每天一个键，再用 ZUNIONSTORE 合并）。

## 18.5 过期与淘汰

### 18.5.1 【入门】过期的键什么时候被删除

设置了过期时间的键，到期后并不会在那一刻被立即删除。Redis 结合使用两种方式：

主节点处理普通键读取时会检查逻辑过期，已过期的键通常表现为不存在。但业务事实可能早于 TTL 变化，从节点、进程内缓存和已经取得的值还涉及各自的时序；不能据此保证用户永远看不到业务上的旧数据。

定期删除：后台每秒若干次随机抽查一批设置了过期时间的键，删除其中过期的。如果抽到的过期键比例较高，就继续抽查下一批。

结果是：过期的键在逻辑上立即消失，但它占用的内存可能要稍后才释放。大量的键在同一时刻过期，会让定期删除在短时间内做很多工作，这也是 18.9.5 节建议给过期时间加随机抖动的原因之一。

### 18.5.2 【入门】内存满了怎么办

maxmemory 设置内存上限。达到上限后，新的写入怎么处理由 maxmemory-policy 决定：

| 策略 | 淘汰的范围 | 淘汰谁 |
| --- | --- | --- |
| noeviction（默认） | 不淘汰 | 写入命令直接报错 OOM command not allowed |
| allkeys-lru | 所有键 | 最久没被访问的 |
| allkeys-lfu | 所有键 | 访问频率最低的 |
| allkeys-random | 所有键 | 随机 |
| volatile-lru | 只在设置了过期时间的键中 | 最久没被访问的 |
| volatile-lfu | 只在设置了过期时间的键中 | 访问频率最低的 |
| volatile-random | 只在设置了过期时间的键中 | 随机 |
| volatile-ttl | 只在设置了过期时间的键中 | 剩余时间最短的 |

怎么选：

纯缓存：allkeys-lru 或 allkeys-lfu。缓存中的数据都能从数据库重新加载，被淘汰无所谓。热点明显（少数商品占大部分访问）时 LFU 效果更好。

缓存与持久数据混用：volatile-lru，只淘汰带过期时间的缓存键，不动没有过期时间的重要数据。但更推荐把两类数据放在不同的 Redis 实例中。

只存重要数据（例如作为队列）：noeviction，宁可写入失败也不丢数据，同时监控内存使用。

作缓存用的 Redis 一定要设置 maxmemory 和一个淘汰策略。默认的“不限内存 + 不淘汰”会让Redis 一直增长，直到被操作系统的 OOM killer 杀死。

### 18.5.3 【精通】近似 LRU 与 LFU

Redis 的 LRU 不是精确的：维护一个全局的访问顺序链表开销太大。它为每个对象记录最后访问时间，淘汰时随机抽取 maxmemory-samples（默认 5）个键，淘汰其中最久未访问的，并维护一个候选池让结果更接近精确的 LRU。增大采样数更精确，但更耗 CPU。

LFU 使用一个 8 位的对数计数器记录访问频率，并随时间衰减（由 lfu-log-factor、lfu-decay-time 控制），这样“很久以前很热、现在不再访问”的键也能逐渐被淘汰。

用 INFO stats 中的 evicted_keys 观察淘汰数量。如果它持续快速增长，说明内存不足以容纳热数据，缓存命中率会下降，需要扩容或缩短过期时间。

## 18.6 持久化、高可用与性能

### 18.6.1 【入门】两种持久化方式

Redis 的数据在内存中，进程重启就会丢失，除非开启持久化：

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| RDB 快照 | 定期把全部数据写成一个压缩的二进制文件 dump.rdb | 文件小，恢复快，适合备份 | 两次快照之间的写入会丢失 |
| AOF 日志 | 把每个写命令追加到日志文件，重启时重放 | 丢失窗口取决于 appendfsync 等设置 | 文件大，恢复慢，需要定期重写 |

RDB 的触发规则写成 save &lt;秒&gt; &lt;修改次数&gt;，例如 save 3600 1 300 100 60 10000 表示：一小时内至少 1 次修改，或 5 分钟内至少 100 次，或 1 分钟内至少 1 万次，就做一次快照。手动触发用BGSAVE。

AOF 的关键配置是 appendfsync，决定多久把日志真正写到磁盘一次：

| 值 | 数据安全 | 性能 |
| --- | --- | --- |
| always | 回复前请求刷盘；持久性还依赖操作系统和硬件，不等于最多丢一条 | 最慢 |
| everysec（默认） | 正常情况下约一秒的丢失窗口；刷盘延迟或故障可能扩大窗口 | 推荐的平衡点 |
| no | 由操作系统决定 | 最快，可能丢失较多 |

AOF 文件会越来越大，Redis 会在后台重写它：用当前数据生成一份最短的命令序列。从 Redis 7 起，AOF 由一个基础文件加若干增量文件组成，基础文件默认使用 RDB 格式，兼顾了恢复速度与数据安全。

作缓存用要不要开持久化？ 纯缓存可以都不开：重启后缓存为空，请求会逐渐把它重新填满。但如果缓存很大、数据库扛不住重启后的大量回源，开启 RDB 可以让 Redis 重启后带着数据启动。本书的开发脚本开启了 AOF，主要是为了演示。

### 18.6.2 【精通】fork 与写时复制

BGSAVE 和 AOF 重写都通过 fork() 创建子进程完成。子进程得到父进程内存的一份“快照”，但操作系统并不真的复制内存，而是父子进程共享内存页，只有某一页被修改时才复制那一页（写时复制，copy-on-write）。

由此带来两个运维要点：

内存余量：快照期间写入越频繁，被复制的页越多，最坏情况下内存占用接近翻倍。所以maxmemory 应当明显小于机器内存，常见做法是留出 30%~50% 的余量。

fork 耗时：fork 需要复制页表，几十 GB 的实例 fork 一次可能耗时数百毫秒，这期间 Redis 无法处理命令。INFO stats 中的 latest_fork_usec 记录了最近一次 fork 的耗时。这也是单个 Redis实例不宜过大的原因之一。

### 18.6.3 【进阶】主从复制与 Sentinel

主从复制：一个主节点（master）负责写，若干从节点（replica）通过 REPLICAOF &lt;主节点地址&gt; &lt;端口&gt; 复制主节点的数据。从节点默认只读，可以分担读请求。复制是异步的：主节点执行完写命令就返回，不等从节点确认。主节点宕机时，最后一小段写入可能还没传到从节点。

Sentinel（哨兵）：一组独立的 Sentinel 进程监控主节点，主节点故障时投票选出一个从节点提升为新的主节点，并通知客戶端新的地址。客戶端连接的是 Sentinel，向它查询当前的主节点。

### 18.6.4 【进阶】Redis Cluster

数据量或写入量超过一台机器的能力时，使用 Redis Cluster 分片：

键空间被分成 16384 个槽（slot），每个键根据 CRC16(键) % 16384 落在某个槽上，每个主节点负责一部分槽。

每个主节点可以有从节点，主节点故障时自动切换。

客戶端需要支持 Cluster 协议（redis crate 的 cluster-async feature），它会根据键计算槽，直接把命令发给负责的节点。

Cluster 的主要限制是：一个命令涉及的多个键必须在同一个槽中，否则报 CROSSSLOT 错误。MGET a b、事务、Lua 脚本都受此限制。解决办法是哈希标签：键名中 {} 内的部分才参与槽的计算，{user:7}:cart 和 {user:7}:recent 一定落在同一个槽。

本章使用单实例 Redis 演示缓存。托管产品是否提供 Sentinel、Cluster、代理或多个端点，要以具体服务为准；应用不能把单机客户端直接当成支持所有拓扑的客户端。

### 18.6.5 【精通】性能陷阱：大键、热键与慢命令

命令单线程执行（18.1.2 节），所以 Redis 的性能问题大多来自“某一个操作太慢，阻塞了所有人”：

| 问题 | 表现 | 对策 |
| --- | --- | --- |
| 大键（big key）：几 MB 的 String，几十万个成员的集合 | 读写它的命令耗时长；删除时阻塞；网络流量大 | 拆分；用 UNLINK 代替 DEL；redis-cli --bigkeys 定期扫描 |

| 问题 | 表现 | 对策 |
| --- | --- | --- |
| 热键（hot key）：极少数键承担大部分访问 | 在 Cluster 中这个键所在的节点被打满 | 进程内缓存挡在前面（本章的 L1）；复制多份分散访问 |
| O(n) 命令：KEYS、HGETALL/SMEM BERS 大集合、FLUSHALL | 慢查询日志中出现，延迟抖动 | SCAN 系列命令；只取需要的字段 |
| 每个请求很多次往返 | 单个命令很快，但累加起来很慢 | 批量命令（MGE T）或管道（18.7.6 节） |

诊断工具：

| 命令 | 作用 |
| --- | --- |
| SLOWLOG GET 10 | 最近 10 条执行超过 slowlog-log-slower-than（默认 10 毫秒）的命令 |
| INFO stats | 包括 keyspace_hits、keyspace_misses，可以算出整体命中率 |
| INFO memory | 内存使用、碎片率 |
| redis-cli --bigkeys | 扫描每种类型中最大的键 |
| redis-cli --latency | 持续测量往返延迟 |
| MONITOR | 实时打印所有命令。开销很大，只用于开发调试 |

### 18.6.6 【进阶】事务与 Lua 脚本

MULTI / EXEC：把多个命令打包，EXEC 时依次执行，执行过程中不会插入其他客戶端的命令：
```text
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379(TX)> DECRBY stock:101 1
QUEUED
127.0.0.1:6379(TX)> RPUSH orders:pending 9001
QUEUED
127.0.0.1:6379(TX)> EXEC
1) (integer) 9
2) (integer) 1
```

但它和数据库事务不同：没有回滚。其中一个命令运行时出错（例如对字符串执行 RPUSH），其他命令照样执行。WATCH key 可以实现乐观锁：被监视的键在 EXEC 之前被别人修改了，整个事务不执行。

Lua 脚本执行时不与其他客户端命令交错，适合把读取、判断和写入组成一个操作。但运行错误不会自动回滚此前已执行的写入，因此应在修改前验证参数与类型。下面的解锁脚本只在锁值仍属于自己时删除键。
```text
-- KEYS[1] 锁的键，ARGV[1] 加锁时写入的随机令牌
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

脚本执行期间同样阻塞其他命令，所以脚本必须短小。

### 18.6.7 本节练习

1. 用 redis-server --appendonly yes 启动一个容器，写入几个键后 docker restart，验证数据还在；再用不开持久化的容器重做一遍。

2. 执行 CONFIG SET slowlog-log-slower-than 0（记录所有命令），执行几个命令后查看SLOWLOG GET，然后恢复为 10000。

3. 用 INFO stats 中的 keyspace_hits 和 keyspace_misses 计算当前实例的命中率，写出公式。

## 18.7 redis crate：在 Rust 中访问 Redis

### 18.7.1 【入门】声明依赖与 feature
```toml
[dependencies]
redis = { version = "0.32", features = ["tokio-comp", "connection-manager"] }
```

| feature | 作用 |
| --- | --- |
| tokio-comp | 基于 Tokio 的异步支持（包含 aio） |
| connection-manager | 提供自动重连的 ConnectionManager |
| tokio-rustls-comp | 用 rustls 支持 rediss:// 加密连接 |
| cluster-async | 异步的 Redis Cluster 客戶端 |
| sentinel | 通过 Sentinel 查找主节点 |
| json | RedisJSON 模块的命令 |

默认 feature 已包含脚本、Stream、Geo 等常用命令组。redis crate 的 0.x 版本更新较频繁，写作时为0.32；各版本间的不兼容变化主要集中在连接类型和类型转换上，升级前请阅读 CHANGELOG。

### 18.7.2 【入门】同步客戶端：最小例子
```rust
use redis::Commands;

fn main() -> redis::RedisResult<()> {
    let client = redis::Client::open("redis://127.0.0.1:6379/")?;
    let mut con = client.get_connection()?;

    let _: () = con.set_ex("greeting", "你好", 60)?;
    let value: Option<String> = con.get("greeting")?;
    println!("{value:?}");
    Ok(())
}
```

Client::open 只解析地址，不连接；get_connection 才真正建立连接。

Commands trait 为连接类型添加了与 Redis 命令同名的方法：set_ex、get、incr、hset……返回值类型必须标注：同一个命令可以转换成多种 Rust 类型（GET 的结果可以是 String、Option&lt;String&gt;、i64、Vec&lt;u8&gt;），编译器无法推断。不关心结果时标注为 ()。

连接地址的格式：

| 格式 | 含义 |
| --- | --- |
| redis://host:6379/0 | 普通连接，/0 是数据库编号，可省略 |
| redis://:密码@host:6379 | 带密码（默认用户） |
| redis://用户名:密码@host:6379 | ACL 用户 |
| rediss://host:6380 | TLS 加密连接（需要 TLS feature） |
| redis+unix:///tmp/redis.sock | Unix 套接字 |

### 18.7.3 【入门】异步连接与 ConnectionManager

后端服务中使用异步版本：
```rust
use redis::AsyncCommands;

let client = redis::Client::open("redis://127.0.0.1:6379/")?;
let mut con = client.get_multiplexed_async_connection().await?;

let _: () = con.set_ex("greeting", "你好", 60).await?;
let value: Option<String> = con.get("greeting").await?;
```

redis crate 有几种异步连接，后端最常用的是两种：

| 类型 | 特点 |
| --- | --- |
| MultiplexedConnection | 一个 TCP 连接上同时发送多个请求（多路复用），可以廉价克隆后在多个任务中并发使用。连接断开后不会自动恢复 |
| ConnectionManager | 包装了 MultiplexedConnection，连接断开后自动重连。同样可以廉价克隆。服务中首选 |
```rust
use redis::aio::ConnectionManager;

let manager = ConnectionManager::new(client).await?;
// 每个任务克隆一份；克隆只是增加引用计数，底层共用同一个连接
let mut con = manager.clone();
let n: i64 = con.incr("page:views", 1).await?;
```

命令方法需要 &amp;mut self，所以要先克隆出一个可变的副本再调用，这是 redis crate 代码中最常见的写法。

需要连接池吗？ 多路复用连接已经能在一个 TCP 连接上并发处理大量请求，绝大多数服务一个ConnectionManager 就够了。只有两种情况需要独占的连接：阻塞命令（BLPOP，它会占住连接直到有数据），以及 WATCH 事务（监视状态绑定在连接上）。需要时可以使用 bb8-redis 或 deadpool-redis 连接池。

### 18.7.4 【进阶】类型转换：ToRedisArgs 与 FromRedisValue

命令的参数要实现 ToRedisArgs，返回值要实现 FromRedisValue。常用类型都已经实现：

| Rust 类型 | 作为参数 | 作为返回值 |
| --- | --- | --- |
| &amp;str、String | 字符串 | 字符串；返回 nil 时报错 |
| i64、u64、f64 等 | 数字的十进制文本 | 解析数字 |
| Vec&lt;u8&gt;、&amp;[u8] | 原样的字节 | 原样的字节 |
| Option&lt;T&gt; | - | nil 转为 None |
| bool | - | 1/0 转为 true/false |
| Vec&lt;T&gt; | 多个参数 | 列表 |
| HashMap&lt;K, V&gt; | - | HGETALL 等返回的字段与值 |
| (A, B, …) | 多个参数 | 管道的多个结果 |
| () | - | 忽略结果 |

最常踩的坑是 GET 一个不存在的键却标注为 String：nil 无法转换为 String，返回一个类型错误。可能不存在的值一律用 Option&lt;T&gt;。

存储结构体时，最简单的做法是自己用 serde_json 序列化成字符串：
```text
let json = serde_json::to_string(&product)?;
let _: () = con.set_ex(key, json, 300).await?;

let raw: Option<String> = con.get(key).await?;
let product: Option<Product> = raw.map(|s| serde_json::from_str(&s)).transpose()?;
```

也可以为自己的类型实现 ToRedisArgs/FromRedisValue，让 con.get::&lt;_, Product&gt;(key) 直接工作。但序列化格式、版本兼容这些问题并没有消失，只是被藏了起来，本书选择显式序列化。

### 18.7.5 【进阶】任意命令：redis::cmd

AsyncCommands 没有覆盖的命令或选项组合，用 redis::cmd 手动构造：
```text
// SET lock:order:9001 <令牌> NX EX 30：加锁，成功返回 "OK"，已被占用返回 nil
let acquired: Option<String> = redis::cmd("SET")
    .arg("lock:order:9001")
    .arg(&token)
    .arg("NX")
    .arg("EX")
    .arg(30)
    .query_async(&mut con)
    .await?;
let locked = acquired.is_some();
```

arg 接受任何实现了 ToRedisArgs 的值，命令和参数按顺序拼接，与在 redis-cli 中输入的完全一样。

### 18.7.6 【进阶】管道、事务与脚本

管道（pipeline）：一次发送多个命令，再一次收回所有结果，只需一次网络往返：
```text
let (views, stock): (i64, Option<i64>) = redis::pipe()
    .incr("page:views", 1)
    .get("stock:101")
    .query_async(&mut con)
    .await?;
```

加上 .atomic()，管道会被包在 MULTI/EXEC 中作为一个事务执行。某个命令的结果不需要时，在它后面调用 .ignore()，这样它不会出现在结果元组中。

脚本：
```text
const RELEASE_LOCK: &str = r#"
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
"#;

let released: i64 = redis::Script::new(RELEASE_LOCK)
    .key("lock:order:9001")
    .arg(&token)
    .invoke_async(&mut con)
    .await?;
```

Script 会先尝试用脚本的 SHA1 摘要执行（EVALSHA），Redis 中没有缓存这个脚本时，再自动发送完整脚本（EVAL），节省了每次传输脚本正文的流量。

### 18.7.7 【进阶】错误处理与超时

所有操作返回 RedisResult&lt;T&gt;，即 Result&lt;T, RedisError&gt;。RedisError 提供了一组判断方法：

| 方法 | 含义 |
| --- | --- |
| is_io_error() | 网络层面的错误 |
| is_connection_refusal() | 连接被拒绝（Redis 没有启动） |
| is_connection_dropped() | 连接中断 |
| is_timeout() | 超时 |
| kind() | 错误分类，例如 TypeError（返回值类型转换失败）、ResponseError（Redis返回了错误） |

一定要为缓存操作设置超时。Redis 卡住或网络异常时，没有超时的请求会一直等待，缓存反而拖垮了整个服务。最直接的做法是用 tokio::time::timeout 包住每次调用：
```rust
use std::time::Duration;

let limit = Duration::from_millis(200);
match tokio::time::timeout(limit, con.get::<_, Option<String>>(key)).await {
    Ok(Ok(value)) => { /* 正常结果 */ }
    Ok(Err(err)) => { /* Redis 返回错误 */ }
    Err(_) => { /* 超时 */ }
}
```

ConnectionManager 本身也提供了连接超时、响应超时等配置项（不同版本的配置方式有差别），外层的 timeout 则对任何版本都有效，本章项目采用这种写法。

### 18.7.8 常见错误与解读

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| type annotations needed 指向con.get(...) | 没有标注返回值类型 | let v: Option&lt;String&gt; = ...或 con.get::&lt;_, Option&lt;String&gt;&gt;(...) |
| Response was of incompatibletype ... (response was nil) | 键不存在，却要求返回 Strin g | 改为 Option&lt;String&gt; |
| cannot borrow ... as mutable | 在共享的 ConnectionManager 上直接调用命令 | 先 let mut con = manager.clone(); |
| Connection refused (os error111) | Redis 没有启动，或地址、端口错误 | redis-cli ping 检查；核对连接地址 |

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| NOAUTH Authentication required | Redis 设置了密码，地址中没有带 | 在地址中加入密码，或使用 ACL 用户 |
| WRONGTYPE Operation against akey holding the wrong kind ofvalue | 对一个类型的键执行了另一种类型的命令（如对 String 执行 HG ET） | 检查键名是否冲突；用 TYPE 确认 |
| OOM command not allowed whenused memory &gt; 'maxmemory' | 内存满且策略为 noeviction | 调整淘汰策略或扩容（18.5.2 节） |

## 18.8 moka：进程内缓存

### 18.8.1 【入门】为什么不用 HashMap

最朴素的进程内缓存是 Mutex&lt;HashMap&lt;K, V&gt;&gt;。它很快就会遇到三个问题：

无限增长：只放不删，内存迟早耗尽。需要容量上限和淘汰策略。

数据过期：需要过期时间，到期后重新加载。

并发：一把全局锁会成为瓶颈；而且多个请求同时发现缓存未命中时，会同时去查数据库。

moka 是 Rust 中最常用的进程内缓存库，它解决了上面所有问题：并发安全、容量上限（基于 TinyLFU的高命中率淘汰策略）、过期时间，以及对同一个键的并发加载去重。

### 18.8.2 【入门】声明依赖
```toml
[dependencies]
moka = { version = "0.12", features = ["future"] }
```

| feature | 提供 |
| --- | --- |
| future | moka::future::Cache，方法是 async 的，在异步代码中使用 |

| feature | 提供 |
| --- | --- |
| sync | moka::sync::Cache，在同步（阻塞）代码中使用 |

两个版本的功能基本相同。异步服务中使用 future::Cache：它的加载函数可以是一个 Future，而且等待其他任务加载同一个键时不会阻塞线程。

### 18.8.3 【入门】基本用法
```rust
use std::time::Duration;
use moka::future::Cache;

let cache: Cache<i64, String> = Cache::builder()
    // 最多 10000 个条目
    .max_capacity(10_000)
    // 写入 60 秒后过期
    .time_to_live(Duration::from_secs(60))
    .build();

cache.insert(42, "机械键盘".to_string()).await;
assert_eq!(cache.get(&42).await, Some("机械键盘".to_string()));

cache.invalidate(&42).await;
assert_eq!(cache.get(&42).await, None);
```

值必须实现 Clone：get 返回值的一个克隆，缓存本身仍保留一份。值比较大时，存 Arc&lt;T&gt;，克隆只是增加引用计数。

Cache 本身可以廉价克隆：内部是 Arc，克隆后的副本操作的是同一份缓存，可以直接放进AppState。

键需要 Hash + Eq + Send + Sync + 'static，值需要 Clone + Send + Sync +'static。

构建器的常用选项：

| 方法 | 作用 |
| --- | --- |
| max_capacity(n) | 容量上限（默认按条目数计） |
| weigher(\|k, v\| -&gt; u32) | 自定义每个条目的“重量”，配合 max_capacity 按字节数之类限制容量 |
| time_to_live(d) | 写入后经过 d 过期 |
| time_to_idle(d) | 最后一次访问后经过 d 过期 |
| expire_after(...) | 为每个条目单独计算过期时间 |
| eviction_listener(...) | 条目被淘汰或过期时回调，可用于统计 |

### 18.8.4 【进阶】get_with 与 try_get_with：并发加载去重

缓存最常见的读法是“有就返回，没有就加载并放进去”。moka 把它做成了一个原子操作：
```text
let name = cache
    .get_with(42, async {
        // 只有缓存中没有 42 时才执行
        load_name_from_db(42).await
    })
    .await;
```

get_with 的关键特性是并发加载去重：100 个请求同时发现 42 不在缓存中，只有第一个会执行加载的Future，其余 99 个等待它完成后直接拿到结果。这正是 18.9.4 节“缓存击穿”问题在单个进程内的解决方案。

加载可能失败时用 try_get_with：
```text
let result: Result<String, Arc<DbError>> = cache
    .try_get_with(42, async { load_name_from_db(42).await })
    .await;
```

加载返回 Ok(v)：v 被放进缓存并返回。

加载返回 Err(e)：错误不会被缓存，下一次请求会重新尝试加载。等待中的其他请求也收到同一个错误。因为同一个错误要交给多个等待者，所以它被包在 Arc&lt;E&gt; 中返回，E 需要满足 Send +Sync + 'static。

还有一个 optionally_get_with，加载返回 None 时不缓存。

### 18.8.5 【精通】淘汰策略与观测

moka 的淘汰策略参考了 Java 的 Caffeine：新条目进入缓存前要经过 TinyLFU 准入判断，用一个紧凑的频率草图估计“新条目”和“将被淘汰的条目”谁更常被访问，只有新条目更热时才替换。对于少数热点占大部分访问、偶尔有大量一次性访问（例如爬虫扫过所有商品）的场景，它的命中率明显高于单纯的LRU。

需要知道的细节：

维护工作是批量进行的：淘汰、过期等维护任务在读写操作中顺带批量执行，所以 entry_count()等统计值是近似的。测试中需要精确值时，先调用 run_pending_tasks().await。

过期条目不会被返回：即使维护任务还没把它清理掉，get 也不会返回已过期的条目。

每个实例一份：多个服务实例各有自己的 moka 缓存。一个实例执行了失效，其他实例的副本不受影响，直到过期。这是两级缓存设计中最需要权衡的地方（18.9.6 节）。

## 18.9 缓存设计：模式、一致性与三大问题

### 18.9.1 【入门】cache-aside：最常用的缓存模式

读：

1. 先查缓存，命中就直接返回。

2. 未命中，查数据库。

3. 把结果写入缓存（设置过期时间），再返回。

写：

1. 先更新数据库。

2. 再删除缓存中对应的键。

下一次读取时缓存未命中，自然会加载最新的数据。这个模式也叫“旁路缓存”：缓存不知道数据库的存在，由应用代码负责两者的协调。

其他模式了解即可：

| 模式 | 做法 | 特点 |
| --- | --- | --- |
| read-through | 缓存组件自己负责从数据库加载 | 应用代码更简单，moka 的 get_with 就是这种风格 |
| write-through | 写入时同时更新缓存和数据库 | 成功路径容易理解；双写失败与并发仍可能导致不一致 |
| write-behind | 只写缓存，异步批量写入数据库 | 写入极快，但缓存故障会丢数据，后端业务很少用 |

### 18.9.2 【进阶】为什么写操作是“删缓存”而不是“更新缓存”

直觉上，更新数据库之后直接把新值写进缓存，下一次读取就不用回源了。但在并发下它会出错：
```text
时间  请求 A（改价为 100）     请求 B（改价为 200）
 1    更新数据库：100
 2                            更新数据库：200
 3                            写缓存：200
 4    写缓存：100              ← 网络慢了一点
结果：数据库是 200，缓存是 100，直到过期之前一直错
```

删除缓存就没有这个问题：无论两个删除谁先谁后，结果都是“缓存中没有”，下一次读取从数据库加载最新值。另外，很多写入之后并没有人读，删除也避免了无用的计算。

### 18.9.3 【精通】先更新数据库再删缓存，就一致了吗

不完全是。还有一个时间窗口很小的竞争：
```text
时间  读请求 R                      写请求 W
 1    缓存未命中，读数据库：旧值
 2                                   更新数据库：新值
 3                                   删除缓存
 4    把旧值写入缓存                 ← R 在 W 删除之后才写入
结果：缓存中是旧值，直到过期
```

它要求“读数据库”在写请求之前完成，“写缓存”又在写请求删除缓存之后才发生，而读数据库后写缓存通常只需要几毫秒，所以实际中很少出现。常见的补救措施：

过期时间兜底：所有缓存都设置过期时间，最坏情况下，旧值也只存在一个过期周期。这是最重要、也是最简单的保障。

延迟双删：写请求删除缓存后，过一小段时间（如 500 毫秒）再删一次。

基于数据库变更日志失效：订阅 PostgreSQL 的逻辑复制流（CDC），由一个独立组件负责删除缓存，删除失败可以重试。这是最可靠也最复杂的方案。

还要正视另一种失败：数据库已经更新，删除缓存这一步却失败了（Redis 超时）。缓存会保持旧值到过期为止。

所以要先明确业务能接受的不一致时长。商品名称、描述晚几分钟更新，用户几乎无感；库存、价格这类影响下单的数据，下单时必须以数据库为准（第 29 章），缓存中的值只用于展示。本章项目的缓存过期时间为 5 分钟，并在每次写入后删除缓存，这对商品详情页来说是合适的。

### 18.9.4 【进阶】三大问题：穿透、击穿、雪崩

| 问题 | 现象 | 原因 |
| --- | --- | --- |
| 缓存穿透 | 请求查询不存在的数据，每次都打到数据库 | 数据不存在就不会被缓存；恶意请求可以用随机 ID 持续攻击 |
| 缓存击穿 | 一个热点键过期的瞬间，大量请求同时打到数据库 | 所有请求同时发现未命中，同时回源 |
| 缓存雪崩 | 大量键在同一时间过期，或者 Redis 整体不可用，数据库被瞬间压垮 | 批量写入时设置了相同的过期时间；缓存服务故障 |

穿透的对策：

缓存空值：查询结果为“不存在”时，也缓存一个“不存在”标记，过期时间较短（如 30 秒）。之后新建了这个 ID 的数据时，删除对应的缓存。本章项目采用这种做法。

布隆过滤器：用一个位数组记录“所有存在的 ID”，查询前先判断。它可能误判“存在”，但绝不会误判“不存在”。适合 ID 集合大且相对稳定的场景。

参数校验：ID 为负数或明显超出范围的请求，在接口层直接拒绝。

击穿的对策：

单飞（single flight）：同一个键同时只允许一个请求回源，其余等待结果。在单个进程内，moka 的get_with 正好做到这一点。

分布式锁：多个实例之间也要去重时，用 SET lock:key token NX EX 5 加锁，拿到锁的实例回源，其余实例稍等后重试读缓存。代价是复杂度和延迟。

逻辑过期：缓存值中记录一个“逻辑过期时间”，Redis 中的键本身不过期。读到逻辑过期的值时，仍然先返回旧值，同时在后台刷新。用短暂的旧数据换取永远不回源。

雪崩的对策：

过期时间加随机抖动：基础时间加上一个随机或分散的偏移量，让同一批写入的键在不同时间过期。

多级缓存：Redis 不可用时，进程内缓存仍能挡住大部分热点请求。

降级：Redis 故障时不要让请求失败，直接回源数据库（同时依靠连接池上限保护数据库）。

高可用：主从 + Sentinel，或托管服务，降低 Redis 整体故障的概率。

### 18.9.5 【进阶】本章项目的选择

| 问题 | RustMall 的做法 |
| --- | --- |
| 穿透 | 缓存“不存在”标记，Redis 中 30 秒，进程内 10 秒；新建商品时删除该 ID 的缓存 |
| 击穿 | 进程内用 moka 的 try_get_with 单飞。多个实例之间不去重：实例数量有限，最多每个实例回源一次，可以接受 |
| 雪崩 | 给回源增加并发限制与熔断；直接降级查库只是教学路径，高流量下会压垮数据库 |
| 一致性 | 写数据库后删除两级缓存；过期时间兜底（Redis 5 分钟，进程内 10 秒） |

为什么抖动按 ID 分散，而不是用随机数：两者都能把过期时间打散，按 ID 计算的结果是确定的，测试可以精确断言，也不需要额外引入随机数依赖。

### 18.9.6 【精通】两级缓存的一致性

两级缓存引入了一个新问题：实例 A 更新了商品，删除了 A 自己的 L1 和共享的 L2，但实例 B 的 L1 中还有旧值。B 会一直返回旧值，直到它的 L1 过期。

常见的解决方法：

| 方法 | 做法 | 代价 |
| --- | --- | --- |
| L1 短过期 | L1 的过期时间远小于 L2（本章：10 秒对 5 分钟） | 其他实例可能继续读自己的 L1；十秒只是 L1 这一级的正常 TTL，并非全链路陈旧上限 |
| 广播失效 | 写入的实例通过 Redis 的 Pub/Sub 发布“商品 42 已修改”，所有实例订阅后删除自己的 L1 | Pub/Sub 不保证送达，仍需短过期兜底；多一个后台任务 |
| 版本号 | 每次读取 L1 前先查一次 Redis 中的版本号 | 每次请求仍有一次 Redis 往返，L1 的意义大打折扣 |

本章选择“L1 短过期”：实现最简单，10 秒的不一致对商品详情页完全可以接受。广播失效作为 18.10.13节的练习。

还有一点容易忽略：L1 能挡住热点键。一个爆款商品每秒被请求一万次，没有 L1 时这一万次都落在Redis 中同一个键上（18.6.5 节的热键问题）；有了 L1，每个实例每 10 秒最多访问 Redis 一次。

### 18.9.7 【精通】缓存的观测

上线后要能回答“缓存是否有效”：

命中率：L1、L2 各自的命中次数和未命中次数。命中率很低的缓存只是在增加延迟和复杂度。

回源次数与耗时：数据库查询是否真的减少了。

Redis 错误与超时次数：降级在发生，说明 Redis 有问题。

Redis 端的指标：内存使用、evicted_keys、keyspace_hits/misses（18.6.5 节）。

本章项目先用 tracing 在 DEBUG 级别记录命中情况，在 WARN 级别记录 Redis 错误。第 38 章接入Prometheus 后，再把它们变成计数器指标。

## 18.10 项目进度：商品详情的两级缓存

本节为 GET /api/v1/products/{id} 加上“进程内缓存（L1）+ Redis（L2）”两级缓存。设计要点在18.9.5 节已经列出，这里再从代码结构的角度概括一遍：

装饰器：新增 CachedProductRepo&lt;R&gt;，它本身实现 ProductRepository，内部包着真正的仓储。服务层、HTTP 层一行都不用改：ProductService 只依赖 trait，并不知道仓储外面多了一层缓存。这就是第 15 章坚持“服务层只依赖 trait”带来的回报。

测试不需要 Redis：HTTP 集成测试使用只有进程内缓存的配置，缓存的读取、回源、失效逻辑照样被已有的 HTTP 测试覆盖；真实 Redis 的测试用 testcontainers 启动，默认忽略。

### 18.10.4 第 3 步：缓存模块 cache.rs

文件：rustmall/monolith/src/cache.rs（新建）
```rust
//! 商品缓存：进程内缓存（moka，L1）+ Redis（L2）（第 18 章）。
//!
//! Redis 是可选的：没有配置、连接失败、操作出错或超时，都自动降级，
//! 缓存的任何故障都不会让请求失败。

use std::future::Future;
use std::time::Duration;

use common::ids::ProductId;
use common::product::Product;
use moka::future::Cache;
use redis::aio::ConnectionManager;
use redis::AsyncCommands;
use serde::{Deserialize, Serialize};
use tracing::{info, warn};

use crate::settings::{CacheSettings, RedisSettings};

/// 缓存值格式的版本。修改 `Entry` 的结构时加 1：旧格式的键不再被读取，随过期时间自然消失。
const KEY_VERSION: u32 = 1;

/// 一次查询的结论：`Some(商品)` 表示存在，`None` 表示确认不存在。两者都会被缓存。
pub type Lookup = Option<Product>;

/// 商品在 Redis 中的键，例如 `rustmall:product:v1:42`。
pub fn product_key(id: ProductId) -> String {
    format!("rustmall:product:v{KEY_VERSION}:{}", id.get())
}

/// 正向缓存的过期秒数：基础时间加上按商品 ID 分散的偏移（最多约 10%），
/// 让同一批写入的键在不同时刻过期，避免缓存雪崩（第 18.9.4 节）。
pub fn ttl_with_jitter(base_secs: u64, id: ProductId) -> u64 {
    let spread = (base_secs / 10).max(1);
    base_secs + id.get().unsigned_abs() % spread
}

/// Redis 中保存的值。“不存在”也要缓存，防止缓存穿透。
///
/// 单独定义而不是直接序列化 `Product`：缓存格式由缓存模块自己掌控，
/// 读回时经过 `Product::try_new` 校验，被改坏的缓存值不会变成非法的领域对象。
#[derive(Debug, PartialEq, Serialize, Deserialize)]
#[serde(tag = "state", rename_all = "snake_case")]
enum Entry {
    Found { id: i64, name: String, price_cents: i64, stock: i32 },
    Missing,
}

impl Entry {
    fn from_lookup(lookup: &Lookup) -> Self {
        match lookup {
            Some(p) => Entry::Found {
                id: p.id().get(),
                name: p.name().to_string(),
                price_cents: p.price_cents(),
                stock: p.stock(),
            },
            None => Entry::Missing,
        }
    }

    fn into_lookup(self) -> Result<Lookup, String> {
        match self {
            Entry::Found { id, name, price_cents, stock } => {
                Product::try_new(ProductId::new(id), &name, price_cents, stock).map(Some)
            }
            Entry::Missing => Ok(None),
        }
    }
}

/// 两级缓存。克隆是廉价的：moka 缓存与 Redis 连接内部都是共享的。
#[derive(Clone)]
pub struct ProductCache {
    local: Cache<ProductId, Lookup>,
    redis: Option<ConnectionManager>,
    op_timeout: Duration,
    ttl_secs: u64,
    missing_ttl_secs: u64,
}

impl ProductCache {
    pub fn new(
        settings: &CacheSettings,
        redis: Option<ConnectionManager>,
        op_timeout: Duration,
    ) -> Self {
        let local = Cache::builder()
            .max_capacity(settings.local_capacity)
            .time_to_live(Duration::from_secs(settings.local_ttl_secs))
            .build();
        Self {
            local,
            redis,
            op_timeout,
            ttl_secs: settings.product_ttl_secs,
            missing_ttl_secs: settings.missing_ttl_secs,
        }
    }

    /// 只有进程内缓存：测试、以及没有配置 Redis 的环境使用。
    pub fn local_only(settings: &CacheSettings) -> Self {
        Self::new(settings, None, Duration::from_millis(200))
    }

    pub fn has_redis(&self) -> bool {
        self.redis.is_some()
    }

    pub(crate) fn local(&self) -> &Cache<ProductId, Lookup> {
        &self.local
    }

    /// 读 Redis。返回 `None` 表示未命中--键不存在、Redis 不可用、值无法解析，都按未命中处理。
    pub(crate) async fn redis_get(&self, id: ProductId) -> Option<Lookup> {
        let mut con = self.redis.clone()?;
        let key = product_key(id);
        let get = con.get(key);
        let raw: Option<String> = with_timeout(self.op_timeout, "GET", get).await?;
        let parsed = serde_json::from_str::<Entry>(&raw?)
            .map_err(|err| err.to_string())
            .and_then(Entry::into_lookup);
        match parsed {
            Ok(Some(product)) if product.id() != id => {
                warn!(expected = %id, actual = %product.id(), "Redis key and product identity differ; treating as cache miss");
                None
            }
            Ok(lookup) => Some(lookup),
            Err(reason) => {
                warn!(%id, reason, "Redis 中的缓存值无法解析，按未命中处理");
                None
            }
        }
    }

    /// 写 Redis。失败只记录警告：缓存写不进去，下一次再回源即可。
    pub(crate) async fn redis_put(&self, id: ProductId, lookup: &Lookup) {
        let Some(mut con) = self.redis.clone() else {
            return;
        };
        let ttl = match lookup {
            Some(_) => ttl_with_jitter(self.ttl_secs, id),
            None => self.missing_ttl_secs,
        };
        let json = match serde_json::to_string(&Entry::from_lookup(lookup)) {
            Ok(json) => json,
            Err(err) => {
                warn!(%id, error = %err, "缓存值序列化失败");
                return;
            }
        };
        let set = con.set_ex(product_key(id), json, ttl);
        let _: Option<()> = with_timeout(self.op_timeout, "SET", set).await;
    }

    /// 写入数据库之后调用：删除两级缓存中的这个商品。
    pub async fn invalidate(&self, id: ProductId) {
        self.local.invalidate(&id).await;
        if let Some(mut con) = self.redis.clone() {
            let del = con.del(product_key(id));
            let _: Option<()> = with_timeout(self.op_timeout, "DEL", del).await;
        }
    }
}

/// 给 Redis 操作加上超时；出错或超时时记录警告并返回 `None`（降级）。
async fn with_timeout<T>(
    limit: Duration,
    op: &'static str,
    fut: impl Future<Output = redis::RedisResult<T>>,
) -> Option<T> {
    match tokio::time::timeout(limit, fut).await {
        Ok(Ok(value)) => Some(value),
        Ok(Err(err)) => {
            warn!(op, error = %err, "Redis 操作失败，已降级");
            None
        }
        Err(_) => {
            warn!(op, timeout = ?limit, "Redis 操作超时，已降级");
            None
        }
    }
}

/// 启动时连接 Redis。没有配置、地址无效、连接失败或超时，都返回 `None` 并记录原因。
pub async fn connect_redis(settings: &RedisSettings) -> Option<ConnectionManager> {
    let url = settings.url.as_deref().filter(|url| !url.trim().is_empty())?;
    let client = match redis::Client::open(url) {
        Ok(client) => client,
        Err(err) => {
            warn!(error = %err, "Redis 地址无效，商品缓存只使用进程内缓存");
            return None;
        }
    };
    let limit = Duration::from_secs(settings.connect_timeout_secs);
    match tokio::time::timeout(limit, ConnectionManager::new(client)).await {
        Ok(Ok(manager)) => {
            info!("已连接 Redis");
            Some(manager)
        }
        Ok(Err(err)) => {
            warn!(error = %err, "连接 Redis 失败，商品缓存只使用进程内缓存");
            None
        }
        Err(_) => {
            warn!(timeout = ?limit, "连接 Redis 超时，商品缓存只使用进程内缓存");
            None
        }
    }
}
```

代码精讲：

Lookup = Option&lt;Product&gt; 同时缓存“存在”与“不存在”：None 是一个明确的查询结论（防穿透），而“缓存未命中”由外面再包一层 Option 表示，所以 redis_get 返回Option&lt;Lookup&gt;。两层 Option 各有含义，类型别名让签名读起来更清楚。

Entry 使用内部标签 #[serde(tag = "state")]：Redis 中的值是 {"state":"found",...}或 {"state":"missing"}，用 redis-cli 查看时一目了然。第三个测试把这个格式固定下来：格式变了，就要同时修改 KEY_VERSION。

读回的值经过 Product::try_new 校验：Redis 中的数据可能被人手动改过、被旧版本程序写入。校验失败按未命中处理，最坏情况只是多一次回源，绝不会把非法的商品交给业务层。

with_timeout 把降级集中在一处：所有 Redis 操作都经过它，出错和超时统一记录 WARN 日志并返回 None。调用方只需要处理“有结果”和“没有结果”两种情况。

ttl_with_jitter 使用 unsigned_abs：商品 ID 不会是负数，但 i64 % u64 不能直接计算，转为无符号数的同时也避免了负数取余的边界问题。

connect_redis 永远不会让启动失败：与数据库不同，Redis 不是必需的依赖。注意一个取舍：启动时连不上 Redis，这次运行就一直不使用它，即使 Redis 之后恢复了也一样，需要重启服务。连接建立之后的断线则由 ConnectionManager 自动重连。18.10.13 节的练习 2 会改进这一点。

```rust
//! 带缓存的商品仓储：按 cache-aside 模式包装任意 `ProductRepository`（第 18.9 节）。
//!
//! 读：进程内缓存 → Redis → 被包装的仓储（数据库）；回源结果写回 Redis。
//! 写：先写被包装的仓储，成功后删除两级缓存。

use std::sync::Arc;

use common::error::{DomainError, DomainResult, ErrorKind};
use common::ids::ProductId;
use common::product::{NewProduct, Product};
use tracing::debug;

use crate::cache::{Lookup, ProductCache};
use crate::repo::ProductRepository;

const ENTITY: &str = "商品";

#[derive(Clone)]
pub struct CachedProductRepo<R> {
    inner: R,
    cache: ProductCache,
}

impl<R: ProductRepository> CachedProductRepo<R> {
    pub fn new(inner: R, cache: ProductCache) -> Self {
        Self { inner, cache }
    }

    /// 进程内缓存未命中时执行。同一个 ID 同时只有一个任务执行它，其余任务等待结果。
    async fn load(&self, id: ProductId) -> DomainResult<Lookup> {
        if let Some(hit) = self.cache.redis_get(id).await {
            debug!(%id, "商品缓存：Redis 命中");
            return Ok(hit);
        }
        let loaded = match self.inner.get(id).await {
            Ok(product) => Some(product),
            Err(err) if err.kind() == ErrorKind::NotFound => None,
            Err(err) => return Err(err),
        };
        debug!(%id, found = loaded.is_some(), "商品缓存：未命中，已回源");
        self.cache.redis_put(id, &loaded).await;
        Ok(loaded)
    }
}

impl<R: ProductRepository> ProductRepository for CachedProductRepo<R> {
    async fn insert(&self, draft: &NewProduct) -> DomainResult<Product> {
        let product = self.inner.insert(draft).await?;
        // 新分配的 ID 可能已经被缓存为“不存在”（有人提前查询过它）
        self.cache.invalidate(product.id()).await;
        Ok(product)
    }

    async fn get(&self, id: ProductId) -> DomainResult<Product> {
        let lookup = self
            .cache
            .local()
            .try_get_with(id, self.load(id))
            .await
            .map_err(unshare)?;
        lookup.ok_or_else(|| DomainError::not_found(ENTITY, id))
    }

    async fn list(&self, limit: i64, offset: i64) -> DomainResult<(Vec<Product>, i64)> {
        // 列表的组合太多（页码 × 每页数量），任何一次写入都会让它们全部过时，暂不缓存
        self.inner.list(limit, offset).await
    }

    async fn update(&self, product: &Product) -> DomainResult<Product> {
        let updated = self.inner.update(product).await?;
        self.cache.invalidate(updated.id()).await;
        Ok(updated)
    }

    async fn delist(&self, id: ProductId) -> DomainResult<()> {
        self.inner.delist(id).await?;
        self.cache.invalidate(id).await;
        Ok(())
    }
}

/// `try_get_with` 把加载错误包在 `Arc` 中交给所有等待者。
/// 只剩一个持有者时直接取出原错误；否则保留错误信息，转为内部错误。
fn unshare(err: Arc<DomainError>) -> DomainError {
    Arc::try_unwrap(err)
        .unwrap_or_else(|shared| DomainError::Internal(shared.to_string()))
}

#[cfg(test)]
mod tests {
    use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
    use std::sync::Mutex;

    use super::*;
    use crate::settings::CacheSettings;

    /// 最多保存一个商品的内存仓储，记录 `get` 被调用（即回源）的次数。
    #[derive(Clone, Default)]
    struct CountingRepo {
        product: Arc<Mutex<Option<Product>>>,
        gets: Arc<AtomicUsize>,
        fail_next_get: Arc<AtomicBool>,
    }

    impl CountingRepo {
        fn with(product: Product) -> Self {
            let repo = Self::default();
            *repo.product.lock().unwrap() = Some(product);
            repo
        }

        fn gets(&self) -> usize {
            self.gets.load(Ordering::SeqCst)
        }
    }

    impl ProductRepository for CountingRepo {
        async fn insert(&self, draft: &NewProduct) -> DomainResult<Product> {
            let product = draft.clone().into_product(ProductId::new(1));
            *self.product.lock().unwrap() = Some(product.clone());
            Ok(product)
        }

        async fn get(&self, id: ProductId) -> DomainResult<Product> {
            self.gets.fetch_add(1, Ordering::SeqCst);
            // 让出执行权，模拟一次数据库往返，让并发的请求有机会同时到达
            tokio::task::yield_now().await;
            if self.fail_next_get.swap(false, Ordering::SeqCst) {
                return Err(DomainError::Internal("数据库暂时不可用".to_string()));
            }
            let current = self.product.lock().unwrap().clone();
            current
                .filter(|p| p.id() == id)
                .ok_or_else(|| DomainError::not_found(ENTITY, id))
        }

        async fn list(
            &self,
            _limit: i64,
            _offset: i64,
        ) -> DomainResult<(Vec<Product>, i64)> {
            unreachable!("缓存测试不使用 list")
        }

        async fn update(&self, product: &Product) -> DomainResult<Product> {
            *self.product.lock().unwrap() = Some(product.clone());
            Ok(product.clone())
        }

        async fn delist(&self, _id: ProductId) -> DomainResult<()> {
            *self.product.lock().unwrap() = None;
            Ok(())
        }

    }
```

代码精讲：

装饰器模式：CachedProductRepo&lt;R&gt; 对外和任何仓储没有区别，内部把 get 转成“先查缓存”，把三个写方法转成“写入后删缓存”。泛型参数 R 让它能包装任何仓储：生产中包装PgProductRepo，测试中包装 CountingRepo。

try_get_with(id, self.load(id))：L1 未命中时才执行 load，并且对同一个 ID 只执行一次（18.8.4 节）。load 内部再依次尝试 Redis 和数据库。concurrent_misses_load_once 测试验证了这一点：8 个任务同时请求，CountingRepo 只被调用一次。

只有 NotFound 被当作结论缓存：数据库的内部错误原样返回，并且不会被缓存（moka 不缓存Err）。errors_are_not_cached 验证了“故障恢复后立即可用”，而不是在缓存的过期时间内一直返回错误。

insert 也要删缓存：这是最容易遗漏的一处。insert_clears_a_cached_missing_marker 描述了这个场景：有人先查询了 ID 1（得到“不存在”并被缓存），随后管理员新建的商品恰好分配到ID 1。如果不删缓存，新商品在“不存在”标记过期之前都查不到。

list 不缓存：列表的键要包含页码和每页数量，任何一次商品写入都会让所有列表缓存过时，失效逻辑复杂而收益有限。真正需要时，常见做法是只缓存第一页，或者给列表一个很短的过期时间。

unshare：moka 把错误包在 Arc 中，因为同一个错误可能要交给多个等待的任务。只有一个持有者时 Arc::try_unwrap 能直接取回原错误，保留它的分类；多个持有者时保留错误信息转为内部错误。实际中能走到 load 的错误本来就只有内部错误（NotFound 已转为 Ok(None)），所以这里不会丢失分类。

故意制造不一致：直接用 SQL 修改名称，绕过了缓存失效。B 读到旧名字，说明缓存确实在工作；这也直观地展示了 18.9.3 节的结论--任何绕过仓储的写入（手工 SQL、数据迁移脚本、其他服务直接写库）都会造成缓存不一致，只能等过期时间兜底。

检查 Redis 中的原始值：第二个测试直接读取键的内容和剩余过期时间，确认“不存在”标记的格式与短过期，这是只看仓储返回值无法验证的。

redis.stop() 模拟宕机：停止容器后，读写都应当继续成功，并且有时间上限。如果把with_timeout 去掉，这个测试会因为请求长时间等待而失败或超时。

### 18.10.11 本章小结

Redis 基础：内存中的数据结构服务器，命令单线程执行，所以快，但一个慢命令会阻塞所有人。作缓存用时必须设置 maxmemory 和淘汰策略，不要在生产中使用 KEYS。

数据结构：String 存对象与计数，List 做队列与最近记录，Hash 存可单独修改字段的对象，Set 做去重与集合运算，Sorted Set 做排行榜与延时任务。

持久化与高可用：RDB 快照、AOF 日志及其取舍；fork 与写时复制带来的内存余量要求；主从复制是异步的；Cluster 用槽分片，多键操作需要哈希标签。

redis crate：服务中使用 ConnectionManager，克隆后调用命令；返回值必须标注类型，可能不存在的值用 Option；任意命令用 redis::cmd，批量用管道，原子的“读―判断―写”用 Lua 脚本；每次操作都要有超时。

moka：并发安全的进程内缓存，支持容量上限和过期时间；try_get_with 对同一个键的并发加载去重，并且不缓存错误。

缓存设计：cache-aside 读时回填、写时删除；“先写数据库再删缓存”仍有小窗口，过期时间是最后的兜底；穿透用空值缓存，击穿用单飞，雪崩用过期抖动、多级缓存和降级。

项目：CachedProductRepo 以装饰器的方式加在仓储外面，服务层与 HTTP 层没有任何改动；Redis 是可选依赖，任何故障都降级而不是报错。

下一章是第 19 章“Git 与 GitHub 协作”：在 RustMall 的仓库上实践提交规范（Conventional Commits）、分支策略、Pull Request 与代码审查流程，配置分支保护、CODEOWNERS 与 Issue/PR 模板，并学会处理合并冲突、rebase、cherry-pick、bisect 等日常与救急操作，为第 22 章的CI/CD 打好基础。

### 18.10.12 本章练习

1. 广播失效：在 ProductCache::invalidate 中，删除 Redis 键之后再 PUBLISHrustmall:product:invalidated &lt;ID&gt;；在 main.rs 中启动一个后台任务订阅这个频道，收到消息后删除本实例的进程内缓存。之后把 local_ttl_secs 调大到 60 秒，验证多个实例之间仍能快速一致。为什么仍然需要过期时间兜底？

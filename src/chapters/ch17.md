# 第 17 章 测试

到目前为止，RustMall 已经有 130 个测试：第 1~8 章为 common 写的单元测试，第 15 章服务层用内存仓储写的测试，第 14、16 章用 #[sqlx::test] 写的 HTTP 测试。它们是“边写功能边补”出来的。本章把测试当作一门独立的手艺来学：

体系：Rust 的三种测试分别放在哪里、怎样编译运行，以及怎样让几百个测试跑得又快又稳。

工具：每种工具解决一类问题--mockall 检查“调用了谁、传了什么”，testcontainers 在测试中自动启动数据库，insta 把 API 的 JSON 形状固定下来，proptest 用成千上万个随机输入寻找边界情况，cargo-llvm-cov 告诉你哪些代码从来没被测过。

本章涉及的 crate 与工具：

| crate / 工具 | 作用 | 小节 |
| --- | --- | --- |
| cargo test、cargo-nextest | 运行测试 | 17.1 |
| sqlx::test | 每个测试一个临时数据库、SQL 夹具 | 17.3 |
| tower::ServiceExt | 不启动服务器，直接把请求交给 Router | 17.4 |
| mockall | 自动生成测试替身（mock） | 17.5 |
| testcontainers、testcontainers-modules | 在测试中启动 Docker 容器 | 17.6 |
| insta、cargo-insta | 快照测试 | 17.7 |
| proptest | 性质测试（基于属性的测试） | 17.8 |
| cargo-llvm-cov | 测试覆盖率 | 17.9 |

本章的项目部分（17.10）不新增任何业务功能，只增加测试和测试工具。业务代码只有一处变化：服务层文件末尾追加一个测试模块。这样你可以放心地按自己的节奏完成本章，不会影响后续章节。

## 17.1 Rust 的测试体系

### 17.1.1 【入门】三种测试放在哪里

Rust 把测试分成三种，区别在于写在哪里和能看到什么：

| 种类 | 写在哪里 | 能访问 | 典型用途 |
| --- | --- | --- | --- |
| 单元测试 | 被测代码同一个文件的 #[cfg(tes t)] mod tests 中 | 本模块的私有函数和私有字段 | 一个函数、一个类型的规则 |

| 种类 | 写在哪里 | 能访问 | 典型用途 |
| --- | --- | --- | --- |
| 集成测试 | crate 根目录下的 tests/*.rs | 只能访问 crate 的公开 API，就像外部用户一样 | 多个模块合作、HTTP 接口、数据库 |
| 文档测试 | 文档注释 /// 中的代码块 | 只能访问公开 API | 保证文档里的示例代码一直能运行 |

用 RustMall 中已有的代码各举一例：
```rust
// 单元测试：common/src/pagination.rs 末尾
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn normalize_handles_edges() {
        assert_eq!(normalize(None, None), (1, DEFAULT_PAGE_SIZE));
    }
}
```
```rust
// 集成测试：monolith/tests/products_api.rs，只用到 monolith 的公开 API
mod support;

use support::*;

#[sqlx::test]
async fn get_missing_is_404(pool: PgPool) {
    let (status, _) = send(&app(pool), get("/api/v1/products/999")).await;
    assert_eq!(status, StatusCode::NOT_FOUND);
}
```
````rust
/// 计算 SQL 需要的 `(limit, offset)`。
///
/// 
```
/// use common::pagination::limit_offset;
/// assert_eq!(limit_offset(Some(3), Some(20)), (20, 40));
/// 
```
pub fn limit_offset(page: Option<u32>, page_size: Option<u32>) -> (i64, i64) {
    // ...
}
````

#[cfg(test)] 的意思是“只在编译测试时才编译这个模块”。cargo build 产出的程序里完全没有测试代码，也不会因为测试多而变大。

### 17.1.2 【入门】cargo test 的常用用法

| 命令 | 作用 |
| --- | --- |
| cargo test | 运行当前 crate（在 workspace 根目录则是默认成员）的全部测试 |
| cargo test --workspace | 运行 workspace 中所有 crate 的测试 |

| 命令 | 作用 |
| --- | --- |
| cargo test -p common | 只测 common 这个 crate |
| cargo test login | 只运行名字中包含 login 的测试（子串匹配） |
| cargo test -- --exact tests::login | 名字必须完全等于给定值 |
| cargo test --lib | 只运行单元测试 |
| cargo test --test products_api | 只运行 tests/products_api.rs 这一个集成测试文件 |
| cargo test --doc | 只运行文档测试 |
| cargo test -- --nocapture | 测试中的 println! 直接输出（默认被捕获，只在失败时显示） |
| cargo test -- --test-threads=1 | 单线程依次运行（排查测试之间互相干扰时用） |
| cargo test -- --ignored | 只运行被 #[ignore] 标记的测试 |
| cargo test -- --include-ignored | 普通测试和被忽略的测试都运行 |
| cargo test -- --list | 只列出测试名，不运行 |
| cargo test --no-fail-fast | 某个测试程序失败后，继续运行其余的测试程序 |

命令中的 -- 是一条分界线：前面的参数给 Cargo，后面的参数给测试程序本身。cargo test --help 列出 Cargo 的参数，cargo test -- --help 列出测试程序的参数。

### 17.1.3 【进阶】测试函数的属性与返回值

#[should_panic]：断言函数会 panic。务必写上 expected，它要求 panic 信息包含指定文字，否则任何原因的 panic 都会让测试通过（第 8.9 节的夹具测试就是这样写的）：
```rust
#[test]
#[should_panic(expected = "夹具中的数量必须合法")]
fn invalid_fixture_panics_with_clear_message() {
    let _ = qty(0);
}
```

#[ignore]：默认不运行，需要 -- --ignored 才运行。适合依赖外部环境（Docker、网络）或特别慢的测试。可以在等号后写上原因，原因会显示在测试输出中：
```rust
#[test]
#[ignore = "需要本机运行 Docker"]
fn starts_a_real_container() { /* ... */ }
```

返回 Result 的测试：测试函数可以返回 Result&lt;(), E&gt;（E 需要实现 Debug），于是函数体里可以使用 ?。返回 Err 等同于测试失败：
```rust
#[test]
fn parses_price() -> Result<(), String> {
    let cents = parse_yuan("199.50").ok_or("解析失败")?;
    assert_eq!(cents, 19_950);
    Ok(())
}
```

这种写法有两个限制：返回 Result 的测试不能再加 #[should_panic]；失败时只打印 Err 的Debug 输出，没有行号。RustMall 的测试大多直接用 unwrap()/expect()--panic 信息自带文件和行号，定位更快。工作区的 clippy.toml 中 allow-unwrap-in-tests = true 已经允许在测试函数中使用 unwrap（第二卷衔接说明）。

断言宏：

| 宏 | 用途 |
| --- | --- |
| assert!(cond, "说明 {x}") | 条件为真 |
| assert_eq!(left, right,"说明") | 相等，失败时打印两边的 Debug 输出 |
| assert_ne!(left, right) | 不相等 |
| matches!(value, Pattern) | 配合 assert! 判断枚举变体：assert!(matches!(err, DomainError::N otFound { .. })) |
| debug_assert! | 只在 debug 构建中检查，属于业务代码中的“内部自检”，不是测试工具 |

给断言加上说明文字，失败时你能直接看到“当时在检查什么、实际值是什么”，而不必回到代码里猜。第 16 章 support::login 中的 assert_eq!(status, StatusCode::OK, "登录失败：{token}")就是这样：登录失败时，响应体会直接显示在失败信息里。

### 17.1.4 【进阶】异步测试与时间控制

普通 #[test] 函数不能是 async fn。#[tokio::test] 为每个测试创建一个独立的 Tokio 运行时，再在其中运行测试函数：
```rust
#[tokio::test]
async fn create_then_get() { /* ... */ }

// 等价于：
#[test]
fn create_then_get() {
    tokio::runtime::Builder::new_current_thread()
        .enable_all()
        .build()
        .unwrap()
        .block_on(async { /* ... */ })
}
```

常用参数：

| 写法 | 含义 |
| --- | --- |
| #[tokio::test] | 单线程运行时（current_thread），测试中 spawn 的任务也在这一个线程上轮流执行 |
| #[tokio::test(flavor = "multi_thread", worker_threads = 2)] | 多线程运行时，用于测试真正的并行行为 |
| #[tokio::test(start_paused = true)] | 时间从“暂停”状态开始，需要 tokio 的 test-util feature |

start_paused 是测试超时、重试、定时任务的利器。时间暂停后，tokio::time::sleep 不会真的等待：当所有任务都在等待计时器时，Tokio 会把虚拟时钟直接拨到最近的到期时间。下面的测试“等待”了一小时，实际只用了几毫秒：
```rust
use std::time::Duration;
use tokio::time::{self, Instant};

#[tokio::test(start_paused = true)]
async fn timeout_fires_after_deadline() {
    let start = Instant::now();
    let one_hour = time::sleep(Duration::from_secs(3600));
    let result = time::timeout(Duration::from_secs(5), one_hour).await;
    assert!(result.is_err(), "5 秒后应当超时");
    // 虚拟时钟恰好前进了 5 秒
    assert_eq!(start.elapsed(), Duration::from_secs(5));
}
```

monolith 的 [dev-dependencies] 从第 11 章起就为 tokio 开启了 test-util，这个功能可以直接使用。注意 start_paused 只支持单线程运行时；涉及真实网络或数据库的测试不要暂停时间，否则连接超时之类的计时也会被“快进”。

### 17.1.5 【精通】测试是怎样编译和运行的

理解编译模型，才能解释很多“奇怪”的现象。

单元测试：cargo test 用 --test 参数把 src/lib.rs 重新编译一遍，此时 cfg(test) 为真，所有 #[cfg(test)] 代码都参与编译，标准库的测试框架（libtest）生成一个 main 函数，依次调用每个 #[test] 函数。所以一个库 crate 实际上会编译两次：一次是正常版本，一次是带测试的版本。

集成测试：tests/ 下的每个 .rs 文件都被编译成一个独立的 crate，它像外部用户一样依赖你的库。关键在于：它依赖的是正常版本的库，其中 cfg(test) 为假。因此：

库中 #[cfg(test)] 的辅助函数，集成测试看不到。这正是第 8.9 节为 common 设计 test-util feature 的原因：fixtures 模块用 #[cfg(any(test, feature = "test-util"))] 控制，其他 crate 在 [dev-dependencies] 中开启这个 feature 就能使用。

只有库 crate 才能做集成测试。二进制 crate（只有 main.rs）无法被 use，这就是第 12 章把monolith 拆成 lib.rs + main.rs 的原因：main.rs 只做组装，其余逻辑都在库里。

tests/ 下的子目录不会被当作测试程序编译，所以共享代码放在 tests/support/mod.rs，由各测试文件 mod support; 引入（第 16 章）。

dev-dependencies：只在编译测试、示例（examples）和基准测试（benches）时可用。mockall、insta、proptest 这些测试工具都放在这里，不会进入生产程序。

运行方式：同一个测试程序内，测试默认在多个线程上并行运行（线程数等于 CPU 核数）；不同的测试程序之间依次运行。因此，测试之间不能依赖执行顺序，也不能共享可变的全局状态（17.2.5 节）。

链接时间：每个集成测试文件都要单独链接一次，链接带着 sqlx、axum 等大依赖的程序要几秒钟。测试文件很多时，有一种常见的组织方式：把它们放进一个测试程序：
```text
tests/
└── it/
    ├── main.rs          ← mod products_api; mod auth_api; mod support;
    ├── products_api.rs
    ├── auth_api.rs
    └── support.rs
```

Cargo 可以把 tests/it/main.rs 自动发现为名为 it 的多文件集成测试目标，再由这个入口通过 mod 引入子模块。辅助文件不会因此各自变成独立测试程序。若关闭 autotests，或采用其他路径，应在 Cargo.toml 中用 [[test]] 显式登记。RustMall 当前保留分文件测试，便于使用 cargo test --test auth_api 单独运行。

文档测试：每个文档示例原本是一个独立的小程序，单独编译，所以文档测试往往是整个测试套件中最慢的部分。Rust 2024 edition 会尽量把同一个 crate 的文档测试合并成一个程序编译，速度好了很多。文档代码块可以加标注：

| 标注 | 含义 |
| --- | --- |
| ```ignore | 不编译也不运行 |

| 标注 | 含义 |
| --- | --- |
| ```no_run | 只编译，不运行（例如示例会发起网络请求） |
| ```should_panic | 运行时应当 panic |
| ```compile_fail | 应当编译失败（用于演示“这样写是错的”） |
| ```text | 不是 Rust 代码，原样显示 |

示例代码中以 # 开头的行参与编译，但不会显示在生成的文档中，常用来隐藏 use 语句和 main 函数等样板代码。

### 17.1.6 【进阶】cargo-nextest：更快、更清晰的测试运行器

cargo-nextest 是一个可以替代 cargo test 的测试运行器，生态中被广泛使用。它和 cargo test 运行的是同样的测试，区别在于运行方式：

| 方面 | cargo test | cargo nextest run |
| --- | --- | --- |
| 隔离 | 同一程序中的测试共享一个进程 | 每个测试一个独立进程，一个测试 panic 或修改全局状态不会影响别人 |
| 并行 | 程序内并行，程序之间串行 | 所有程序的所有测试放进同一个调度池并行，充分利用 CPU |
| 输出 | 按程序分段，失败信息在最后 | 每个测试一行（含耗时），失败的测试立刻显示输出 |
| 重试、超时 | 不支持 | 支持重试不稳定的测试、标记慢测试、设置超时 |
| 文档测试 | 支持 | 不支持，需要另外运行 cargo test --doc |

安装与使用：
```bash
cargo install cargo-nextest --locked

# 运行全部测试（不含文档测试）
cargo nextest run --workspace
# 文档测试仍然用 cargo test
cargo test --workspace --doc

# 按名字过滤，与 cargo test 相同
cargo nextest run login
# 过滤表达式：只运行 monolith 中名字含 product 的测试
cargo nextest run -E 'package(monolith) & test(product)'
# 只列出，不运行
cargo nextest list --workspace
```

输出示例：
```text
Starting 149 tests across 11 binaries (1 test skipped)
    PASS [   0.012s] common money::tests::line_total_rejects_invalid_input
    PASS [   0.284s] monolith::products_api create_then_get
    ...
 Summary [   4.120s] 149 tests run: 149 passed, 1 skipped
```

nextest 的配置文件是 workspace 根目录下的 .config/nextest.toml，可以定义多个 profile（例如本地用 default，CI 用 ci）。17.10 节会为 RustMall 加上这个文件。本书后续章节的命令仍然写cargo test，安装了 nextest 的读者可以随时替换。

### 17.1.7 常见错误与解读

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 集成测试中 use monolith::...报 unresolved import | crate 没有 lib.rs，或者被引用的模块不是 pub | 二进制 crate 拆出 lib.rs；需要被测试的模块声明为 pub mod |
| 集成测试找不到库中 #[cfg(tes t)] 的辅助函数 | 集成测试依赖的是不带 cfg(tes t) 的正常版本 | 用 feature 控制（如 common 的 tes t-util），或把辅助函数放进 tests/support/ |
| error: test functions cannot be async 一类的报错（措辞因版本而异） | 普通 #[test] 不能是 asyncfn | 改用 #[tokio::test] |
| #[should_panic] 测试意外通过 | 没写 expected，其他原因的panic 也算通过 | 加上 expected = "..." |
| 测试单独运行通过，一起运行偶尔失败 | 测试之间共享了状态（全局变量、同一个数据库、同一个文件、同一个端口） | 每个测试使用独立的资源（17.2.5节）；临时用 --test-threads=1 确认 |
| start_paused 报需要 test-ut il | tokio 没开启 test-util feature | 在 [dev-dependencies] 中为 tokio开启 |
| cargo nextest run 后文档测试没有运行 | nextest 不运行文档测试 | 另外执行 cargo test --doc |

## 17.2 写出好测试

### 17.2.1 【入门】一个测试只验证一个行为

测试的名字就是它的说明书。好的名字描述“在什么情况下，应当发生什么”，读到失败的测试名就能大致知道哪里坏了：

| 不好的名字 | 好的名字 |
| --- | --- |
| test_create | create_rejects_negative_price |
| test1 | delisted_product_is_hidden_from_list |
| login_works | wrong_password_and_unknown_user_look_identical |

一个测试只验证一个行为。如果一个测试同时验证“创建成功”“名称被修剪”“列表数量增加”三件事，失败时你要先弄清是哪一件出了问题；拆成三个测试，失败信息本身就是答案。这条规则说的是“一个行为”，不是“一个断言”：验证一个行为可能需要好几个断言，例如检查状态码之后再检查响应体。

### 17.2.2 【入门】准备―执行―断言

几乎所有测试都可以写成三段，段与段之间空一行（英文称为 Arrange‒Act‒Assert）：
```rust
#[tokio::test]
async fn delist_hides_product() {
    // 准备：一个已有商品的服务
    let svc = service();
    let p = svc.create(cmd("键盘", 100)).await.unwrap();

    // 执行：被测的操作只有这一步
    svc.delist(p.id()).await.unwrap();

    // 断言：可观察到的结果
    assert_eq!(svc.get(p.id()).await.unwrap_err().kind(), ErrorKind::NotFound);
}
```

“执行”最好只有一行。如果准备部分很长，就把它提取成辅助函数（如第 16 章的 admin_token、create_product），让测试正文只剩下与本测试有关的内容。

### 17.2.3 【进阶】测试金字塔与 RustMall 的测试分层

不同种类的测试，在速度、稳定性和“发现问题的能力”上各有取舍：

| 层次 | 速度 | 稳定性 | 能发现的问题 |
| --- | --- | --- | --- |
| 单元测试 | 微秒~毫秒 | 极稳定 | 一个函数、一条业务规则写错 |
| 集成测试（数据库、HTTP） | 几十~几百毫秒 | 稳定，需要数据库 | SQL 写错、约束不一致、路由与中间件配置错误 |

| 层次 | 速度 | 稳定性 | 能发现的问题 |
| --- | --- | --- | --- |
| 端到端测试（真实进程与依赖） | 秒级 | 最容易受环境影响 | 部署配置、组件之间的衔接 |

“测试金字塔”的建议是：底层的单元测试最多，越往上越少。原因很简单：底层测试又快又稳，能在几秒内给出反馈；上层测试慢，失败时还要先排除环境问题。但上层测试也不能没有，因为很多问题只在组件真正连接起来时才会出现。

本章结束时 RustMall 的测试分层如下，括号中是 17.10 节之后的数量：

| 层次 | 位置 | 测什么 |
| --- | --- | --- |
| 单元测试（100） | 各 src/ 文件中的 mod tests | 金额、分页、订单状态机等领域规则；服务层流程（Fake 与 Mock） |
| 性质测试（6） | common/tests/properties.rs | 对所有输入都应成立的规律 |
| 契约测试（common 6+ 快照 6） | common/tests/json_contract.rs、monolith/tests/api_contract.rs | JSON 的形状不被意外改变 |
| 数据库集成测试（9） | monolith/tests/product_repo.rs、catalog_queries.rs | SQL、约束、排序 |
| HTTP 集成测试（22） | monolith/tests/products_api.rs、auth_api.rs | 路由、提取器、权限、状态码 |
| 端到端测试（1，默认忽略） | monolith/tests/pg_container.rs | 在全新的 PostgreSQL 容器中跑通迁移与主流程 |

### 17.2.4 【进阶】测试数据：夹具、构造器与“只写关心的字段”

测试数据的写法会严重影响测试的可读性。看两个版本：
```text
// 版本 A：每个字段都写出来，读者分不清哪个值重要
let p = Product::try_new(ProductId::new(1), "机械键盘", 19_900, 100).unwrap();
let line = CartLine::from_product(&p, Quantity::try_new(3).unwrap());
assert_eq!(line.subtotal_cents(), Some(59_700));

// 版本 B：用夹具，只写出与本测试有关的值
let line = CartLine::from_product(&keyboard(), qty(3));
assert_eq!(line.subtotal_cents(), Some(19_900 * 3));
```

常用的三种手段：

夹具函数：返回一个“典型的合法对象”，如 common 的 fixtures::keyboard()。适合大多数测试都需要、但不关心细节的数据。

带参数的辅助函数：只暴露测试关心的参数，如服务层测试的 cmd(name, price_cents)，库存固定为 1。

构造器（builder）：字段很多时，用 ProductBuilder::default().price(0).build() 的形式只改动需要的字段。RustMall 的类型字段不多，暂时不需要。

数据库测试还有第四种手段：SQL 夹具，用一个 .sql 文件一次性准备好精确的数据（17.3.3 节）。

### 17.2.5 【精通】确定性：时间、随机数、顺序与并行

一个测试在代码没有变化的情况下时而通过、时而失败，称为不稳定测试（flaky test）。它比没有测试还糟糕：团队会逐渐习惯“再跑一次就好了”，真正的失败也会被忽略。不稳定的根源几乎都是下面几类：

| 来源 | 例子 | 对策 |
| --- | --- | --- |
| 当前时间 | 断言“创建时间是今天”，在午夜前后运行就失败 | 时间作为参数传入；异步代码用 start_paused；快照中脱敏时间字段（17.7.4 节） |
| 随机数 | 随机生成的数据偶尔触发边界情况 | 固定种子（StdRng::seed_from_u64(42)）；或者干脆把随机变成系统化的性质测试（17.8 节） |
| 遍历顺序 | HashMap 的遍历顺序每次运行都不同 | 比较前先排序，或改用 BTreeMap |
| 共享资源 | 两个测试写同一张表、同一个文件、同一个端口 | 每个测试一个独立数据库（#[sqlx::test]）、临时目录、端口 0（由系统分配） |
| 全局状态 | 测试修改环境变量，影响同时运行的其他测试 | 不修改全局状态，把配置作为参数传入 |
| 真实的等待 | sleep(100ms) 后断言后台任务已完成，机器慢时就失败 | 等待明确的信号（channel、JoinHandle）；或者暂停时间 |

关于环境变量，Rust 2024 edition 有一个直接的约束：std::env::set_var 变成了 unsafe 函数，因为在多线程程序中修改环境变量可能导致未定义行为，而测试正是在多线程中并行运行的。RustMall 的workspace 设置了 unsafe_code = "forbid"，测试中根本无法调用它。第 15 章的配置测试因此采用了“把配置来源作为参数传入”的设计，而不是在测试中设置 APP_* 环境变量。这就是可测试性影响设计的一个例子。

## 17.3 数据库测试进阶：#[sqlx::test]

### 17.3.1 【入门】回顾：每个测试一个新数据库

第 14.9.6 节已经介绍过 #[sqlx::test] 的基本用法。它为每个测试做了这些事：读取DATABASE_URL 连接到 PostgreSQL 服务器，新建一个临时数据库，执行 ./migrations 中的全部迁移，把连接到这个库的 PgPool 传给测试函数，测试结束后再删除临时库。

这个设计带来三个好处：

隔离：每个测试都从一个“结构完整、没有数据”的库开始，测试之间互不干扰，可以放心地并行运行。

可预测：自增 ID 总是从 1 开始，所以第 16 章的测试可以直接断言 "id": 1。

真实：测试运行在真正的 PostgreSQL 上，约束、索引、事务的行为与生产环境完全一致。用 SQLite或内存仓储模拟数据库，永远会有细节对不上。

代价是：运行测试前必须有一个可连接的 PostgreSQL（./scripts/dev-db.sh），并且该用户有建库权限。17.6 节的 testcontainers 会去掉这个前提。

### 17.3.2 【进阶】参数与测试函数签名

#[sqlx::test] 支持以下参数：

| 写法 | 作用 |
| --- | --- |
| #[sqlx::test] | 执行 crate 根目录下 ./migrations 中的迁移 |
| #[sqlx::test(migrations = "../db/migrations")] | 指定迁移目录（相对于 crate 根目录） |
| #[sqlx::test(migrator = "monolith::db::MIGRATOR")] | 使用一个已有的 Migrator 静态变量 |
| #[sqlx::test(migrations = false)] | 不执行迁移，得到一个空库 |
| #[sqlx::test(fixtures("users", "catalog"))] | 迁移之后，依次执行 fixtures/users.sql、fixt ures/catalog.sql |
| #[sqlx::test(fixtures(path = "../seed", scripts("catalog")))] | 指定夹具目录 |

测试函数的参数决定了你拿到什么：

| 参数 | 说明 |
| --- | --- |
| pool: PgPool | 最常用：连接到临时库的连接池 |
| conn: PoolConnection&lt;Postgres&gt; | 只需要一个连接时 |
| (opts: PgPoolOptions, conn_opts: PgConnectOptions) | 想自己创建连接池（例如测试连接池参数）时 |

测试函数可以返回 sqlx::Result&lt;()&gt;，函数体中就可以对数据库操作使用 ?。

### 17.3.3 【进阶】SQL 夹具 fixtures

有些测试需要一批精确的数据，例如“三个商品，创建时间分别是某年某月某日，其中一个已下架”。通过 HTTP 接口一个个创建做不到--接口不允许客戶端指定创建时间，也不能直接创建一个已下架的商品。这时就用 SQL 夹具：一个普通的 .sql 文件，在迁移之后、测试开始之前执行。

夹具文件放在测试文件所在目录下的 fixtures/ 中，参数中只写文件名，不写 .sql 后缀：
```text
monolith/tests/
├── catalog_queries.rs      ← #[sqlx::test(fixtures("catalog"))]
└── fixtures/
    └── catalog.sql
```

写夹具时有一个必踩的坑，与第 13 章的建表方式有关。products.id 定义为 GENERATED ALWAYS ASIDENTITY，PostgreSQL 默认不允许手动指定它的值：
```sql
INSERT INTO products (id, name, price_cents, stock) VALUES (1, '键盘', 100, 1);
-- ERROR:  cannot insert a non-DEFAULT value into column "id"
-- DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
-- HINT:  Use OVERRIDING SYSTEM VALUE to override.
```

按提示加上 OVERRIDING SYSTEM VALUE 就能插入。但还有第二个坑：手动指定 ID 不会推进序列，下一次由数据库自动分配 ID 时，序列仍然从 1 开始，结果与夹具中的数据冲突：
```sql
INSERT INTO products (name, price_cents, stock) VALUES ('鼠标', 100, 1);
-- ERROR:  duplicate key value violates unique constraint "products_pkey"
-- DETAIL:  Key (id)=(1) already exists.
```

所以夹具末尾要把序列推进到当前的最大 ID：
```sql
SELECT setval(pg_get_serial_sequence('products', 'id'), (SELECT max(id) FROM products));
```

pg_get_serial_sequence 返回该列背后的序列名，对 SERIAL 列和 IDENTITY 列都适用。17.10.5节的夹具完整地演示了这两点，并用一个测试验证“夹具之后新建的商品 ID 从 5 开始”。

夹具的使用原则：

一个夹具描述一个场景，名字说明场景（catalog、users_with_admin），而不是“所有测试数据”。几个夹具可以组合使用。

夹具中的数据必须满足所有约束。它绕过了领域层的校验，只有数据库约束在把关--这也说明了第13 章在数据库中同样定义 CHECK 约束的价值。

能通过接口准备的数据，优先通过接口准备。接口会随业务演进，夹具中的 SQL 不会自动跟着变；表结构变了，夹具可能悄悄失效。

### 17.3.4 【精通】工作原理、清理与连接数

#[sqlx::test] 展开后，大致相当于：
```rust
#[test]
fn create_then_get() {
    // 1. 用 DATABASE_URL 连接“主库”，在其中登记并创建临时库 _sqlx_test_<编号>
    // 2. 在临时库上执行迁移，再依次执行夹具
    // 3. 创建连接临时库的 PgPool，在新建的 Tokio 运行时中运行测试函数体
    // 4. 测试结束后关闭连接池，删除临时库
}
```

几个值得知道的细节：

登记表：SQLx 在主库中创建一个名为 _sqlx_test 的 schema，记录它创建过的临时库。进程被强行终止（例如在调试器中停止）而遗留下来的临时库，会在下一次运行测试时被清理。用 psql 执行 \l 能看到正在使用的临时库。

运行时：#[sqlx::test] 自己创建 Tokio 运行时，所以不要再叠加 #[tokio::test]。

连接数：每个正在运行的测试都持有自己的连接池。并行的测试很多时，可能超过 PostgreSQL 的max_connections（默认 100），报 sorry, too many clients already。解决办法是减少并行度（-- --test-threads=4），或者提高开发库的 max_connections（第 13.8 节）。

速度：建库和执行迁移通常需要几十毫秒。对一般的项目，这完全可以接受；如果迁移非常多、非常慢，可以考虑“模板库”方案：先建一个执行过迁移的库，再用 CREATE DATABASE ...TEMPLATE 复制它。这超出了本书的范围。

### 17.3.5 常见错误与解读

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| DATABASE_URL must be set 一类的 panic | 运行测试时没有设置环境变量 | 确认 .env 存在，或在命令前设置 DATAB ASE_URL=... |
| permission denied to create database | 连接用户没有建库权限 | 给该用户 CREATEDB 权限，或使用超级用户 |
| cannot insert a non-DEFAULT value into column"id" | 夹具给 GENERATED ALWAYS 列指定了值 | 加 OVERRIDING SYSTEM VALUE |

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 夹具之后插入数据报 duplic ate key ... products_pkey | 序列没有推进 | 夹具末尾 SELECT setval(...) |
| 编译报找不到夹具文件 | 夹具路径相对于测试文件所在目录，或者写了 .sql 后缀 | 放在测试文件旁边的 fixtures/ 目录，参数只写文件名 |

## 17.4 HTTP 层测试：tower::ServiceExt

### 17.4.1 【入门】Router 就是一个 Service

第 12.7 节讲过，Tower 的核心是 Service trait：给它一个请求，它返回一个 Future，Future 完成时得到响应。Axum 的 Router 也实现了 Service&lt;Request&lt;Body&gt;&gt;。这意味着测试 HTTP 接口时不需要启动服务器：直接构造一个 Request，交给 Router 处理，拿到 Response 后检查即可。这样的测试没有网络开销，也不会因为端口被占用而失败。

最小的例子：
```rust
use axum::body::Body;
use axum::http::{Request, StatusCode};
use axum::routing::get;
use axum::Router;
use tower::ServiceExt;

#[tokio::test]
async fn hello_returns_200() {
    let app = Router::new().route("/hello", get(|| async { "你好" }));

    let response = app
        .oneshot(Request::get("/hello").body(Body::empty()).unwrap())
        .await
        .unwrap();

    assert_eq!(response.status(), StatusCode::OK);
}
```

oneshot 来自 tower::ServiceExt，需要 tower 的 util feature，所以 monolith 的开发依赖中写的是 tower = { workspace = true, features = ["util"] }（第 15 章）。

### 17.4.2 【进阶】oneshot 与 ready/call

Service 的协议分两步：先调用 poll_ready 等待服务准备好（例如限流中间件可能让你等待），再调用 call 处理请求。ServiceExt 提供了把这两步包装好的方法：

| 方法 | 作用 |
| --- | --- |
| svc.oneshot(req) | 等待就绪，然后处理一个请求。消耗 svc 本身 |
| svc.ready().await? | 只等待就绪，返回 &amp;mut svc，之后可以 .call(req) |

oneshot 会消耗服务，所以第 16 章的 support::send 每次都先 app.clone()。Router 内部用Arc 共享路由表，克隆只是增加引用计数，非常便宜。

如果想对同一个服务实例连续发送多个请求（例如测试一个计数型的限流中间件，它的状态保存在服务实例中），就用 ready + call：
```rust
use tower::{Service, ServiceExt};

let mut svc = app;
for _ in 0..3 {
    // Router 对多种请求体类型都实现了 Service，所以这里要标明请求类型
    let response = ServiceExt::<Request<Body>>::ready(&mut svc)
        .await
        .unwrap()
        .call(Request::get("/hello").body(Body::empty()).unwrap())
        .await
        .unwrap();
    assert_eq!(response.status(), StatusCode::OK);
}
```

读取响应体用 http_body_util::BodyExt::collect，第 12 章起的测试一直这样写：
```rust
use http_body_util::BodyExt;

let bytes = response.into_body().collect().await.unwrap().to_bytes();
let json: serde_json::Value = serde_json::from_slice(&bytes).unwrap();
```

### 17.4.3 【进阶】只测一部分：最小路由与懒连接池

集成测试不一定要组装整个应用。有两个常用技巧。

技巧一：为一个处理函数或一个中间件单独搭建最小路由。 例如只验证“请求 ID 中间件会在响应头中返回 x-request-id”，不需要商品路由，也不需要数据库：
```text
let app = Router::new()
    .route("/ping", get(|| async { "pong" }))
    .layer(/* 只挂上要测的那一层中间件 */);
```

技巧二：懒连接池。 AppState 需要一个 PgPool，但有些测试根本不会访问数据库。例如“不带令牌访问管理接口返回 401”：AdminUser 提取器在访问数据库之前就拒绝了请求。这时可以用connect_lazy 创建一个不立即连接的连接池：
```rust
use sqlx::postgres::PgPoolOptions;

#[tokio::test]
async fn missing_token_is_rejected_before_touching_database() {
    // connect_lazy 只解析连接串，第一次真正执行查询时才会去连接
    let pool = PgPoolOptions::new()
        .connect_lazy("postgres://nobody@127.0.0.1:1/unused")
        .unwrap();
    let app = support::app(pool);

    let body = json!({ "name": "键盘", "price_cents": 100, "stock": 1 });
    let (status, _) = send(&app, json_request("POST", "/api/v1/products", &body)).await;

    assert_eq!(status, StatusCode::UNAUTHORIZED);
}
```

这个测试不需要数据库就能运行，速度和单元测试相当。它同时也是一个断言：如果将来有人把某个数据库查询挪到了权限检查之前，连接失败会让这个测试得到 500 而不是 401，问题马上就会暴露。

### 17.4.4 【精通】三种 HTTP 测试方式的比较

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| ServiceExt::oneshot | 把 Request 直接交给 Router | 最快，不占端口，可以测单个中间件 | 跳过了 hyper 的HTTP 解析和连接处理 |
| axum-test 等测试crate | 对上一种方式的封装，提供 server.get("/x").await 之类更简洁的 API | 测试代码更短 | 多一个依赖，API 随版本变化 |
| 启动真实服务器 | TcpListener::bind("127.0.0.1:0") 让系统分配端口，tokio::spawn(axum::serve(...))，再用HTTP 客戶端（如第 27 章的 reqwest）发请求 | 与生产环境最接近，能测超时、连接关闭、HTTP/2 等 | 较慢，需要管理服务器的启动与关闭 |

RustMall 目前用第一种方式就够了：它覆盖了路由、提取器、中间件和错误映射，这些正是我们自己写的代码；hyper 的协议解析已经由 hyper 自己的测试保证。第 27 章写 API 网关时，网关需要真正转发HTTP 请求，那时再使用第三种方式。

## 17.5 mockall：自动生成测试替身

### 17.5.1 【入门】测试替身的五种角色

测试一个组件时，常常要把它依赖的其他组件换成“替身”（test double），就像拍电影时的替身演员。替身按用途分为五种：

| 角色 | 做什么 | RustMall 中的例子 |
| --- | --- | --- |
| Dummy（占位） | 只是为了凑齐参数，根本不会被用到 | 懒连接池（17.4.3 节） |
| Stub（桩） | 对调用返回预先设定的结果 | 让仓储的 get 固定返回“连接池耗尽” |
| Spy（间谍） | 记录自己被怎样调用，测试结束后再检查 | 记录发送过的通知 |
| Mock（模拟对象） | 事先声明“应当被怎样调用”，调用不符合时测试失败 | “校验失败时 insert一次都不能被调用” |
| Fake（伪实现） | 一个能真正工作的简化实现 | 第 15 章服务层测试中的 FakeRepo（内存仓储） |

第 15、16 章的服务层测试用的都是手写的 Fake。Fake 适合测试“结果”：创建之后能查到，下架之后查不到。但有两类问题 Fake 不擅长：

错误注入：想看服务层在仓储返回“数据库内部错误”时的表现，要让内存仓储返回这个错误，就得给 Fake 加上“出错开关”之类的额外代码。

交互验证：想确认“校验失败时根本没有访问仓储”“传给仓储的名称已经去掉了首尾空格”，Fake只能间接推断。

这两类问题正是 Mock 的用武之地。mockall 是 Rust 中最常用的 mock 库，它根据 trait 或结构体的定义自动生成 Mock 类型，不需要手写。

### 17.5.2 【入门】声明依赖
```toml
[dev-dependencies]
mockall = "0.13"
```

mockall 只在测试中使用，所以放在 [dev-dependencies]。它只有一个可选 feature：nightly，在nightly 编译器上提供更好的错误信息，稳定版不需要。写作时的版本是 0.13；mockall 的 0.x 版本之间可能有不兼容的变化，升级前请阅读它的 CHANGELOG。

### 17.5.3 【入门】#[automock]：第一个 mock

以一个“库存不足时发通知”的小功能为例：
```rust
#[cfg(test)]
use mockall::automock;

/// 发送通知（邮件、短信、即时消息……）。
#[cfg_attr(test, automock)]
pub trait Notifier {
    fn send(&self, to: &str, text: &str) -> Result<(), String>;
}

/// 库存低于 5 时通知运营，返回是否发送了通知。
pub fn notify_low_stock(
    notifier: &dyn Notifier,
    product: &str,
    stock: i32,
) -> Result<bool, String> {
    if stock >= 5 {
        return Ok(false);
    }
    notifier.send("ops@rustmall.dev", &format!("{product} 库存仅剩 {stock} 件"))?;
    Ok(true)
}
```

#[cfg_attr(test, automock)] 的意思是：只在编译测试时给这个 trait 加上 #[automock]。automock 会生成一个名为 MockNotifier 的结构体，它实现了 Notifier，每个方法都有一个对应的 expect_方法名() 用来设定期望。生产构建中这些代码完全不存在。
```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn sends_when_stock_is_low() {
        let mut notifier = MockNotifier::new();
        notifier
            .expect_send()
            .withf(|to: &str, text: &str| {
                to == "ops@rustmall.dev" && text.contains("仅剩 2 件")
            })
            .times(1)
            .returning(|_, _| Ok(()));

        assert_eq!(notify_low_stock(&notifier, "机械键盘", 2), Ok(true));
    }

    #[test]
    fn stays_silent_when_stock_is_enough() {
        let mut notifier = MockNotifier::new();
        notifier.expect_send().never();

        assert_eq!(notify_low_stock(&notifier, "机械键盘", 10), Ok(false));
    }

    #[test]
    fn notifier_failure_is_reported() {
        let mut notifier = MockNotifier::new();
        notifier.expect_send().returning(|_, _| Err("邮件服务不可用".to_string()));

        let result = notify_low_stock(&notifier, "机械键盘", 1);
        assert_eq!(result, Err("邮件服务不可用".to_string()));
    }
}
```

逐行解读第一个测试：

expect_send()：声明“send 会被调用”，返回一个期望对象，后面的方法都在配置它。

withf(...)：参数必须满足这个条件，期望才算匹配。方法参数是引用（&amp;str）时，闭包拿到的也是引用。

times(1)：恰好被调用一次。

returning(...)：被调用时执行这个闭包，返回它的结果。闭包的参数与方法参数相同。

Mock 对象被丢弃（drop）时，mockall 会检查每个期望的调用次数，不满足时 panic，测试失败。调用了一个没有任何期望能匹配的方法，也会立即 panic，信息大致是 MockNotifier::send("…", "…"):No matching expectation found。

### 17.5.4 【进阶】期望：参数匹配、次数、返回值、顺序

参数匹配：

| 写法 | 含义 |
| --- | --- |
| （不写） | 任何参数都匹配 |
| .with(eq(7), always()) | 每个参数一个谓词。eq、ne、always、lt、gt 等来自 mockal l::predicate |
| .with(function(\|x: &amp;i64\| *x&gt; 0)) | 用闭包作为某一个参数的谓词 |
| .withf(\|a, b\| ...) | 用一个闭包同时检查所有参数，最灵活 |

调用次数：.times(2)、.times(1..=3)、.never()；不写时为“任意次数，包括 0 次”。

返回值：

| 写法 | 用途 |
| --- | --- |
| .returning(\|args\| ...) | 每次调用执行闭包，最常用 |
| .return_const(value) | 每次返回同一个值的克隆，要求类型实现 Clone |
| .return_once(\|args\| ...) | 闭包只能调用一次，适合返回不能克隆的值 |

返回值的闭包必须是 Send 的，因为 mock 对象可能被移到别的线程上使用。

调用顺序：默认不检查不同方法之间的先后顺序。需要时用 Sequence：
```rust
use mockall::Sequence;

let mut seq = Sequence::new();
repo.expect_get().times(1).in_sequence(&mut seq).returning(|_| Ok(keyboard()));
repo.expect_update().times(1).in_sequence(&mut seq).returning(|p| Ok(p.clone()));
// 如果 update 在 get 之前被调用，测试失败
```

中途检查：mock.checkpoint() 立即检查到目前为止的所有期望，然后清空它们，适合把一个长测试分成几个阶段。

同一个方法可以设定多个期望（例如不同参数返回不同结果）。多个期望都能匹配同一次调用时，选择哪一个有明确的规则，但依赖这个规则会让测试难以阅读。最好让各个期望的参数条件互不重叠。

### 17.5.5 【进阶】mock! 宏

#[automock] 直接写在 trait 定义上，所以只能用于自己定义的 trait。另外几种情况要用 mock! 宏，在测试代码中“描述”要模拟的类型：
```rust
use mockall::mock;

mock! {
    // 生成名为 MockStore 的结构体（名字前自动加上 Mock）
    pub Store {
        // 结构体自身的方法
        fn get(&self, id: i64) -> Option<String>;
    }

    // 还可以实现若干个 trait，包括标准库和第三方 crate 中的 trait
    impl Clone for Store {
        fn clone(&self) -> Self;
    }
}
```

| 场景 | 选择 |
| --- | --- |
| 自己定义的 trait | #[cfg_attr(test, automock)] |

| 场景 | 选择 |
| --- | --- |
| 别人 crate 中的 trait（不能修改它的源代码） | mock! |
| 一个 Mock 要同时实现多个 trait | mock! |
| 想让 Mock 的方法签名与 trait 不同（例如同步版本） | mock! 加一个手写的适配器（17.10.4 节） |

### 17.5.6 【精通】mock 用在哪里：与手写 Fake 的取舍

mock 很强大，也很容易被滥用。一个过度使用 mock 的测试大概是这样：
```text
// 反面例子：测试的不是“行为”，而是“实现细节”
repo.expect_get().with(eq(id)).times(1).returning(...);
repo.expect_update().withf(...).times(1).returning(...);
cache.expect_invalidate().with(eq(id)).times(1).return_const(());
// …… 断言与被测代码几乎一行对一行
```

这样的测试把被测代码的写法“复制”了一遍。将来只是调整了内部实现（例如把 get + update 合并成一条 SQL），业务行为完全没变，测试却全部失败。测试变成了重构的阻力。

经验法则：

| 情况 | 推荐 |
| --- | --- |
| 关心“结果”：创建后能查到、下架后查不到 | Fake（或真实数据库） |
| 关心“交互本身就是需求”：必须发一次通知、绝不能在校验失败时写库 | Mock |
| 需要注入难以真实触发的错误：连接池耗尽、第三方超时 | Mock（Stub） |
| 依赖是纯计算、速度很快 | 直接用真实实现，不要替身 |

RustMall 两种都用：第 15 章的 FakeRepo 继续承担大部分服务层测试，17.10.4 节新增的 mock 测试只做 Fake 不擅长的三件事--验证仓储没有被调用、检查传给仓储的参数、注入数据库内部错误。

在 Rust 中还有一个影响取舍的因素：trait 的形状。RustMall 的仓储 trait 要求 Clone + Send + Sync+ 'static，方法返回 impl Future + Send（第 15.5.3 节）。mockall 生成的 Mock 类型本身不能克隆，而且它对“返回 Future 的 trait 方法”的支持细节在不同版本中有所变化。为了不受这些细节影响，17.10.4 节采用一种稳定可靠的写法：用 mock! 生成一个同步的 MockStore，再写一个十几行的适配器 MockedRepo(Arc&lt;MockStore&gt;) 实现仓储 trait，每个 async fn 只是把调用转发给 mock。Arc解决了克隆的问题，同步的 mock 不涉及任何异步细节。

### 17.5.7 常见错误与解读

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| cannot find type MockXxx | 忘了 #[automock]，或者在非测试代码中使用了只在测试中生成的 Mock | 检查 cfg_attr(test, automoc k)；Mock 只能在 #[cfg(test)] 代码中使用 |
| No matching expectation found | 调用的参数不满足任何一个期望，或者根本没有设定期望 | 打印出的实际参数与 with/withf 对照 |
| Drop 时 panic：called 0 time(s)which is fewer than expected 1 | 期望的调用没有发生 | 被测代码走了另一个分支，或者提前返回了错误 |
| the trait bound ...: Send is not satisfied（指向 returning的闭包） | 闭包捕获了非 Send 的值（如Rc） | 改用 Arc；只在单线程中使用时可以改用 returning_st |
| eq(10) 报类型不匹配 | 整数字面量默认推断为 i32，而参数是 i64 | 写 eq(10_i64) |
| 期望写在了 Arc::new(mock) 之后，报借用错误 | expect_* 需要 &amp;mut，放进Arc 后只能共享借用 | 先设置好全部期望，再放进 Arc |

2. 用 Sequence 写一个测试，要求先调用 send 通知运营、再调用一个新方法 log 记录日志，顺序颠倒时测试失败。

## 17.6 testcontainers：在测试中启动容器

### 17.6.1 【入门】它解决什么问题

到目前为止，运行 RustMall 的测试有一个前提：先执行 ./scripts/dev-db.sh 启动开发数据库。这个前提带来几个问题：

新同事克隆仓库后直接 cargo test，得到一堆连接失败，需要先读文档。

开发库的版本、配置、扩展可能和生产环境不一致，测试通过不代表线上没问题。

开发库是长期运行的，里面可能残留着手动修改过的数据或结构。

testcontainers 让测试代码自己负责启动依赖：测试开始时通过 Docker 启动一个全新的 PostgreSQL 容器，等它就绪后把连接地址交给测试，测试结束时自动删除容器。唯一的前提是本机有 Docker，这在第 0章已经安装好了。

它不只能启动数据库。后续章节的 Redis、Kafka 等中间件，都可以用同样的方式在测试中启动。

### 17.6.2 【入门】声明依赖与 feature

testcontainers 由两个 crate 组成：

testcontainers：核心库，负责与 Docker 通信、启动和删除容器、等待就绪。

testcontainers-modules：常用镜像的现成配置（PostgreSQL、Redis、Kafka……），每种镜像一个 feature。它会重新导出核心库，路径为 testcontainers_modules::testcontainers。

只依赖 testcontainers-modules，再通过它的重新导出使用核心库，可以保证两者的版本一定匹配：
```toml
[dev-dependencies]
testcontainers-modules = { version = "0.12", features = ["postgres"] }
```

| feature | 作用 |
| --- | --- |
| postgres、redis、kafka…… | 启用对应镜像的模块，按需开启 |
| blocking | 提供同步的 SyncRunner，用于非异步的测试 |

写作时 testcontainers-modules 的版本是 0.12。这两个 crate 更新较快，0.x 版本之间的 API 时有调整；本节用到的都是最核心的几个方法，如果你使用的版本更新，请对照它的文档和 CHANGELOG。

### 17.6.3 【入门】启动一个 PostgreSQL
```rust
use sqlx::postgres::PgPoolOptions;
use testcontainers_modules::postgres::Postgres;
use testcontainers_modules::testcontainers::runners::AsyncRunner;
use testcontainers_modules::testcontainers::ImageExt;

#[tokio::test]
async fn talks_to_a_fresh_postgres() {
    // 1. 启动容器：拉取镜像（第一次较慢），创建并启动容器，等待数据库就绪
    let container = Postgres::default()
        .with_tag("17-alpine")
        .start()
        .await
        .expect("启动 PostgreSQL 容器");

    // 2. 容器的 5432 端口被映射到宿主机上一个随机的空闲端口
    let host = container.get_host().await.expect("容器主机");
    let port = container.get_host_port_ipv4(5432).await.expect("映射后的端口");
    let url = format!("postgres://postgres:postgres@{host}:{port}/postgres");

    // 3. 之后就和连接普通数据库一样
    let pool = PgPoolOptions::new().connect(&url).await.expect("连接数据库");
    let one: i32 = sqlx::query_scalar("SELECT 1").fetch_one(&pool).await.unwrap();
    assert_eq!(one, 1);

    // 4. container 在函数结束时被丢弃，容器随之被停止并删除
}
```

逐项说明：

Postgres::default()：PostgreSQL 模块的默认配置，用户名、密码、数据库名都是postgres。可以用 with_user、with_password、with_db_name 修改。

.with_tag("17-alpine")：来自 ImageExt trait，指定镜像版本。模块的默认版本可能比较旧，一定要显式指定，并与生产环境保持一致。第 13 章开发库使用的是 PostgreSQL 17。

.start()：来自 AsyncRunner trait。它会一直等到模块定义的“就绪条件”满足才返回--PostgreSQL 模块等待日志中出现数据库可以接受连接的信息。返回的 ContainerAsync 代表这个正在运行的容器。

get_host_port_ipv4(5432)：查询容器端口映射到了宿主机的哪个端口。端口是随机分配的，所以多个测试同时启动各自的容器也不会冲突。

生命周期：ContainerAsync 被丢弃时会删除容器。所以要把它保存在一个变量中，直到测试结束。如果写成 let _ = Postgres::default().start().await;，容器会被立刻删除，后续连接全部失败。

### 17.6.4 【进阶】任意镜像：GenericImage

没有现成模块的镜像，用 GenericImage 自己描述：镜像名、版本、暴露的端口和就绪条件。以后面第18 章要用的 Redis 为例：
```rust
use testcontainers_modules::testcontainers::core::{IntoContainerPort, WaitFor};
use testcontainers_modules::testcontainers::runners::AsyncRunner;
use testcontainers_modules::testcontainers::{GenericImage, ImageExt};

let redis = GenericImage::new("redis", "7.4-alpine")
    .with_exposed_port(6379.tcp())
    .with_wait_for(WaitFor::message_on_stdout("Ready to accept connections"))
    .with_env_var("TZ", "Asia/Shanghai")
    .start()
    .await
    .expect("启动 Redis 容器");
let port = redis.get_host_port_ipv4(6379).await.unwrap();
```

就绪条件是最关键的配置。容器“启动了”不等于里面的服务“准备好了”：PostgreSQL 启动后要先初始化数据目录，这期间连接会被拒绝。常用的等待方式：

| 写法 | 含义 |
| --- | --- |
| WaitFor::message_on_stdout("...") | 标准输出中出现指定文字 |
| WaitFor::message_on_stderr("...") | 标准错误中出现指定文字（PostgreSQL 的日志写在这里） |
| WaitFor::seconds(n) | 固定等待 n 秒，最后的手段，既慢又不可靠 |
| 容器的健康检查 | 镜像定义了 HEALTHCHECK 时，等待它变为 healthy |

### 17.6.5 【精通】工作原理、速度与 CI

工作原理：testcontainers 通过 Docker Engine 的 HTTP API（Linux 上是 /var/run/docker.sock，Docker Desktop 也提供同样的接口）完成所有操作，与在命令行执行 docker run -d -P ... 再轮询日志是一回事。它读取 DOCKER_HOST 环境变量，所以也能连接远程的 Docker 或 Podman。

速度：拉取镜像只在第一次发生；之后启动一个 PostgreSQL 容器通常需要一到几秒。与 #[sqlx::test] 建一个临时库的几十毫秒相比，慢了两个数量级。所以不要给每个测试都启动一个容器。常见的组织方式有三种：

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| 少量端到端测试各启动一个容器 | 每个测试函数内 start() | RustMall 的选择：只有一个“全新环境冒烟测试” |
| 一个测试程序共享一个容器 | 在 static 中懒加载容器，所有测试共用 | 测试很多、又不想依赖外部数据库时。注意每个#[tokio::test] 有自己的运行时，共享异步资源要格外小心，一般配合 SyncRunner |
| 容器只负责提供“服务器” | 测试程序启动前用容器起一个 PostgreSQL，导出 DATABASE_URL，然后 #[sqlx::tes t] 照常为每个测试建库 | CI 中最常见，第 22 章会用 GitHub Actions 的服务容器做同样的事 |

为什么 RustMall 不把所有测试都换成 testcontainers？ #[sqlx::test] 已经提供了“每个测试一个干净数据库”，缺的只是“服务器从哪里来”。开发时，一个长期运行的开发库加上 #[sqlx::test]，速度最快；容器测试则用来回答另一个问题：在一个全新的、指定版本的 PostgreSQL 上，迁移能否从零执行成功，主流程能否跑通。这正是 17.10.7 节那个测试的职责。它用 #[ignore] 标记，平时不运行，需要时（例如升级 PostgreSQL 版本前）和在 CI 中显式运行。

清理：正常结束和测试失败（panic）时，容器都会随 ContainerAsync 的丢弃而删除。但如果测试进程被强行终止（kill -9、调试器中直接停止），丢弃逻辑来不及执行，容器会残留。用 docker ps检查，docker rm -f 清理即可。

### 17.6.6 常见错误与解读

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| Cannot connect to the Docker daemon 一类的错误 | Docker 没有运行，或当前用户没有访问Docker 的权限 | 启动 Docker Desktop；Linux 上把用户加入 docker 组 |
| 第一次运行测试很慢，像卡住了一样 | 正在拉取镜像 | 预先 docker pull postgres:17-alpine |
| 连接被拒绝或 connection res et | 没有等到服务就绪；或者容器已经被丢弃 | 检查就绪条件；确认 Container Async 保存在变量中 |

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 多个 testcontainers 相关 crate版本冲突，类型不匹配 | 同时直接依赖了 testcontainers 和testcontainers-modules，且版本不配套 | 只依赖 modules，使用它重新导出的 testcontainers |
| CI 中报找不到 Docker | CI 环境没有 Docker（或在没有特权的容器中运行） | 使用带 Docker 的执行环境；或用CI 的服务容器代替（第 22 章） |
| 测试结束后 docker ps 中仍有容器 | 测试进程被强行终止 | docker rm -f &lt;容器 ID&gt; |

## 17.7 insta：快照测试

### 17.7.1 【入门】什么是快照测试

普通断言需要你把期望值写在代码里：
```text
assert_eq!(body, json!({ "code": "NOT_FOUND", "message": "商品 999 不存在" }));
```

期望值很长时（一整页商品列表、一份复杂的报表），手写期望值既费力又容易抄错。快照测试换了一种做法：第一次运行时，把实际输出保存到一个文件中，由人审阅确认“这就是正确的输出”；以后每次运行都与这个文件比较，不一致就失败，并显示差异。

快照特别适合守护契约：API 的 JSON 形状一旦对外发布，字段的增删、改名、类型变化都会影响客戶端。有了快照，任何这样的变化都会出现在代码审查的 diff 中，必须有人明确地接受它。

### 17.7.2 【入门】安装与声明
```toml
[dev-dependencies]
insta = { version = "1", features = ["json", "redactions"] }
```

| feature | 作用 |
| --- | --- |
| json | 提供 assert_json_snapshot!，把实现了 Serialize 的值序列化为 JSON 保存 |

| feature | 作用 |
| --- | --- |
| yaml | 提供 assert_yaml_snapshot!，序列化为 YAML |
| redactions | 脱敏：把每次都变化的字段（时间、令牌）替换为固定文字 |
| glob | 对一批输入文件分别生成快照 |
| filters | 用正则表达式替换快照中的文字 |

assert_snapshot!（字符串）和 assert_debug_snapshot!（Debug 输出）不需要任何feature。

配套的命令行工具用来审阅快照：
```bash
cargo install cargo-insta --locked
```

insta 的官方文档建议在开发构建中为 insta 开启优化，以加快快照比较。RustMall 的 workspace 已经为所有依赖设置了 [profile.dev.package."*"] opt-level = 2（第 11 章），不需要额外配置。

### 17.7.3 【入门】第一个快照与审阅流程
```rust
#[test]
fn price_breakdown_debug() {
    let mut cart = Cart::new();
    cart.add(CartLine::from_product(&keyboard(), qty(2))).unwrap();
    let rule = Promotion::FullReduction { threshold_cents: 30_000, off_cents: 5_000 };

    insta::assert_debug_snapshot!(cart.price(&[rule]).unwrap());
}
```

完整的工作流程：

1. 第一次运行 cargo test：还没有快照文件，测试失败，insta 写出一个待审阅的文件snapshots/&lt;模块&gt;__price_breakdown_debug.snap.new。

2. 审阅 cargo insta review：在终端中逐个显示待审阅的快照，按 a 接受（.snap.new 改名为.snap）、r 拒绝、s 跳过。

3. 提交 .snap 文件和代码一起提交到 Git。快照是测试的一部分，没有提交快照，别人的机器上测试会失败。

4. 以后每次运行：输出与 .snap 一致则通过；不一致则失败，终端中显示差异，同时再写出一个.snap.new。如果变化是预期的，再次 cargo insta review 接受；否则修复代码。

快照文件的格式：
```text
---
source: common/src/cart.rs
expression: "cart.price(&[rule]).unwrap()"
---
PriceBreakdown {
    subtotal_cents: 39800,
    discount_cents: 5000,
    payable_cents: 34800,
    applied: Some(
        FullReduction {
            threshold_cents: 30000,
            off_cents: 5000,
        },
    ),
}
```

两行 --- 之间是 insta 自动生成的元数据，不要手工修改；之后才是快照内容。

常用命令：

| 命令 | 作用 |
| --- | --- |
| cargo insta test | 运行测试并收集所有快照变化（不会在第一个失败处停止） |
| cargo insta test --review | 运行后立即进入审阅 |
| cargo insta review | 审阅待处理的快照 |
| cargo insta accept / reject | 一次接受或拒绝全部待处理快照 |
| cargo insta pending-snapshots | 列出待处理的快照 |

环境变量 INSTA_UPDATE 控制 insta 写文件的行为：默认 auto 写出 .snap.new；always 直接覆盖 .snap（慎用）；no 不写任何文件。insta 检测到 CI 环境（CI 环境变量）时自动按 no 处理，所以 CI 中快照不一致只会失败，不会悄悄更新。

### 17.7.4 【进阶】JSON 快照与脱敏

HTTP 响应中总有一些每次都不同的值：创建时间、访问令牌、随机生成的 ID。直接快照会导致每次运行都不一致。脱敏（redaction）把这些字段替换成固定的占位文字：
```text
insta::assert_json_snapshot!(body, {
    ".created_at" => "[timestamp]",
    ".items[].updated_at" => "[timestamp]",
    ".**.request_id" => "[uuid]",
});
```

| 选择器 | 匹配 |
| --- | --- |
| .created_at | 顶层的 created_at 字段 |
| .body.access_token | 嵌套字段 |
| .items[] | 数组中的每一个元素 |
| .items[].id | 数组每个元素的 id 字段 |

| 选择器 | 匹配 |
| --- | --- |
| .**.id | 任意深度的 id 字段 |

脱敏的原则：只替换“值本身不确定”的字段，而且替换后仍然保留“这个字段存在”这一事实。快照里的 "created_at": "[timestamp]" 依然在守护契约：如果有人删掉了这个字段，或者把它改名为createdAt，快照照样会失败。

除了替换为固定文字，还有两种常用的脱敏方式：insta::sorted_redaction() 把一个顺序不确定的数组排序后再比较；insta::dynamic_redaction(|value, path| ...) 用闭包检查原值，例如先断言它是一个合法的 RFC 3339 时间，再替换掉。

### 17.7.5 【进阶】内联快照与设置

快照内容很短时，可以直接写在代码中，称为内联快照：
```text
insta::assert_snapshot!(format_yuan(19_950), @"199.50");
```

@ 后面的字符串就是快照。第一次运行时可以只写 @""，审阅接受后，cargo-insta 会把实际内容填进源代码。内联快照让读者在测试中直接看到期望值，适合一两行的输出。

with_settings! 临时修改设置：
```text
insta::with_settings!({
    // 对 Map 按键排序，使快照与遍历顺序无关
    sort_maps => true,
    // 在快照元数据中记录一段说明，审阅时能看到
    description => "未登录用户访问管理接口",
}, {
    insta::assert_json_snapshot!(body);
});
```

sort_maps 用于 HashMap 等遍历顺序不确定的类型。serde_json::Value 默认使用按键排序的BTreeMap（除非依赖树中某个 crate 开启了 serde_json 的 preserve_order feature），所以RustMall 的 JSON 快照中键总是按字母顺序排列。

### 17.7.6 【精通】快照测试的适用边界

快照测试成本低、覆盖面大，但它有一个根本弱点：它只知道“和上次一样”，不知道“是不是对的”。第一次接受快照时，如果输出本身就是错的，错误就被固定成了“标准答案”。之后每个人都会习惯性地按a 接受变化，快照就变成了橡皮图章。

适合快照的：

对外的数据格式：API 响应、错误体、事件消息、导出文件。

复杂但人能看懂的输出：报表、生成的 SQL、编译器式的错误信息。

不适合快照的：

核心业务规则：“满 300 减 50”应当写成明确的断言 assert_eq!(payable, 34_800)。审阅者一眼就能看出它在检查什么，一个大快照里的某个数字则很容易被忽略。

大量的、频繁变化的输出：每次改动都产生上百行的快照 diff，没人会认真看。

一个实用的组合：用普通断言测试规则，用快照测试形状。17.10.6 节的 API 契约测试只做后者--状态码、字段名、错误码这些“客戶端会依赖的东西”。

### 17.7.7 常见错误与解读

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 测试第一次运行就失败，提示有新快照 | 正常现象：还没有快照文件 | cargo insta review 审阅并接受 |
| 本地通过，CI 中失败，提示快照缺失 | .snap 文件没有提交 | 提交 snapshots/ 目录中的 .snap 文件 |
| .snap.new 文件被提交到了Git | 审阅之前就执行了 git add. | 在 .gitignore 中加入 *.snap.new 和*.pending-snap |
| 每次运行快照都不一样 | 快照中有时间、随机值，或Map 的顺序不确定 | 脱敏；sort_maps =&gt; true |
| assert_json_snapshot! 中的脱敏选择器报错 | 没有开启 redactions feature | 在依赖声明中加上 |
| 修改测试函数名后，旧快照文件残留 | 快照文件名由测试函数名决定 | cargo insta test --unreferenced=delete 删除不再被引用的快照 |

## 17.8 proptest：性质测试

### 17.8.1 【入门】从“举例”到“性质”

到目前为止的测试都是举例测试：挑几个输入，断言对应的输出。
```text
assert_eq!(parse_yuan(&format_yuan(19_950)), Some(19_950));
assert_eq!(parse_yuan(&format_yuan(5)), Some(5));
```

例子是人挑的，人挑的例子往往会避开自己没想到的情况：0、负数、i64::MAX、恰好 100 个字符的名字、全是空格的字符串……性质测试换一个角度：不写具体的例子，而是描述一条对所有输入都应当成立的规律（性质，property），由工具随机生成成百上千个输入来检验它：

对任意非负的金额 c，parse_yuan(format_yuan(c)) == Some(c)。

一旦发现反例，工具还会自动收缩（shrink）：不断尝试更简单的输入，最终报告一个最小的反例，例如“c = 100 时失败”，而不是“c = 7_394_011_828_315 时失败”。

### 17.8.2 【入门】声明依赖与第一个性质
```toml
[dev-dependencies]
proptest = "1"
```

默认 feature 就能满足本书的全部用法。
```rust
use common::money::{format_yuan, parse_yuan};
use proptest::prelude::*;

proptest! {
    #[test]
    fn yuan_round_trip(cents in 0..=i64::MAX) {
        prop_assert_eq!(parse_yuan(&format_yuan(cents)), Some(cents));
    }
}
```

逐项解读：

proptest! { ... }：在宏里面写测试函数。每个函数仍然要标注 #[test]。

cents in 0..=i64::MAX：参数的写法是“名字 in 策略”。策略（strategy）描述怎样生成输入，这里是一个整数范围。

prop_assert_eq!：与 assert_eq! 相同，但失败时不直接 panic，而是把失败报告给proptest，让它开始收缩。在 proptest! 中应当使用 prop_assert! 系列宏。

默认每个性质运行 256 个随机输入。失败时的输出大致是：
```text
thread 'yuan_round_trip' panicked at ...:
Test failed: assertion failed: `(left == right)`
  left: `Some(10)`,
 right: `Some(100)` at common/tests/properties.rs:12.
minimal failing input: cents = 100
    successes: 3
    local rejects: 0
    global rejects: 0
```

（这是假设 format_yuan 有 bug 时的样子。）minimal failing input 就是收缩后的最小反例。

### 17.8.3 【进阶】策略：生成什么样的输入

| 策略 | 生成 |
| --- | --- |
| any::&lt;i64&gt;()、any::&lt;Option&lt;u32&gt;&gt;() | 该类型的任意值，偏向边界值（0、最大值、最小值） |
| 0..100、1..=99_i64 | 范围内的整数 |
| "[a-z_]{3,20}" | 符合该正则表达式的字符串 |
| "\\PC{0,50}" | 0~50 个任意“可见”Unicode 字符（中文、表情、空格都可能出现） |
| prop::collection::vec(策略, 0..10) | 长度在范围内的 Vec |
| (策略A, 策略B) | 元组，各分量独立生成 |
| 策略.prop_map(\|x\| ...) | 对生成的值做转换 |
| prop_oneof![策略A, 策略B] | 从几个策略中随机选一个 |
| Just(值) | 总是生成这个值 |

组合起来生成领域对象，例如“任意一条优惠规则”：
```rust
fn any_promotion() -> impl Strategy<Value = Promotion> {
    prop_oneof![
        (any::<i64>(), any::<i64>()).prop_map(|(threshold_cents, off_cents)| {
            Promotion::FullReduction { threshold_cents, off_cents }
        }),
        any::<i64>().prop_map(|percent| Promotion::Discount { percent }),
    ]
}
```

注意这里故意生成包括负数在内的任意字段值。Promotion 的文档承诺“规则本身不合法时返回 0”，这也是需要验证的性质。

过滤：prop_assume!(条件) 丢弃不满足条件的输入。过滤掉的输入太多，proptest 会报 Too manyglobal rejects 并失败。能用策略直接生成合法输入时，就不要先生成再过滤。

配置：
```rust
proptest! {
    #![proptest_config(ProptestConfig::with_cases(10_000))]

    #[test]
    fn slow_but_thorough(x in any::<u32>()) { /* ... */ }
}
```

也可以用环境变量 PROPTEST_CASES=10000 cargo test 临时加大次数，适合在 CI 的夜间任务中运行。

### 17.8.4 【进阶】收缩与回归文件

每个策略都知道怎样把一个值“变简单”：整数向 0 靠近，字符串变短，Vec 减少元素，prop_oneof!倾向于前面的分支。发现反例后，proptest 不断尝试更简单的值，只要仍然失败就继续，直到无法再简化。所以 prop_oneof! 中应当把最简单的分支放在前面。

发现反例时，proptest 还会把生成这个反例的随机种子写入一个回归文件（文件名以 .proptest-regressions 结尾，位置取决于测试文件所在目录，运行时会在输出中提示）。以后每次运行，都会先用这些种子重现历史上的反例，再生成新的随机输入。回归文件应当提交到 Git：它保证一个修复过的 bug不会悄悄回来，即使这个反例很难被随机再次碰到。

### 17.8.5 【精通】怎样找到好性质

刚开始写性质测试时，最难的是想出性质。下面几种模式可以覆盖大部分场景：

| 模式 | 说明 | RustMall 中的例子 |
| --- | --- | --- |
| 往返 | 编码后再解码，回到原值 | parse_yuan(format_yuan(c)) == Some(c)；serde 序列化后再反序列化 |
| 幂等 | 做一次和做两次结果相同 | normalize_username 的结果再规范化一次，不变 |
| 不变量 | 输出总满足某个约束 | 优惠金额总在 0 和小计之间；分页参数总在合法范围内 |
| 等价实现 | 与一个简单但慢的实现比较 | 优化过的搜索函数与逐个比较的朴素实现结果相同 |
| 已知结论 | 在特殊输入上结果可以直接推出 | 折扣为 100% 时应付金额等于小计 |
| 合法性判定 | 构造函数接受的输入恰好是规则允许的输入 | Product::try_new 接受当且仅当名称、价格、库存都合法 |

还要警惕两个陷阱：

把实现再写一遍：如果性质的计算过程和被测代码一模一样，被测代码有 bug，性质也有同样的bug。性质应当从“需求”出发，而不是从“代码”出发。

异步代码：proptest! 中的测试函数是同步的。要测试异步函数，在函数体中创建一个运行时并block_on；涉及数据库时，每个用例都建库会非常慢，通常不值得。性质测试最适合纯函数，这也是 RustMall 把它用在 common 上的原因。

性质测试的近亲是模糊测试（fuzzing，cargo-fuzz），它用覆盖率引导的方式生成输入，擅长发现解析器中的崩溃。对于处理不可信输入的代码（如第 2 章的搜索词解析器），值得一试。

### 17.8.6 常见错误与解读

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 在 proptest! 中用了 assert!，失败后没有收缩 | 普通断言直接 panic，proptest无法收缩 | 使用 prop_assert!、prop_assert_eq! |

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| Too many global rejects | prop_assume! 过滤掉了大部分输入 | 改进策略，直接生成合法输入 |
| 测试非常慢 | 每个用例都做了昂贵的操作，乘以 256 次 | 减少 cases，或只对纯函数做性质测试 |
| 修复 bug 后，旧反例的种子仍在回归文件中 | 正常现象，它会继续作为回归测试运行 | 保留，不要删除 |
| 正则策略生成了意料之外的字符 | \s、\w 等类别在 Unicode下范围很大 | 用明确的字符集，如 [ \t]、[A-Za-z0-9_] |
| prop_assert_eq! 报类型没有实现Debug | 失败时需要打印两边的值 | 为类型派生 Debug |

## 17.9 覆盖率：cargo-llvm-cov

### 17.9.1 【入门】覆盖率衡量什么

测试覆盖率回答一个问题：运行测试时，哪些代码被执行过。它有几种粒度：

| 指标 | 含义 |
| --- | --- |
| 行覆盖率（Lines） | 被执行过的代码行占比，最直观 |
| 函数覆盖率（Functions） | 被调用过的函数占比 |
| 区域覆盖率（Regions） | LLVM 把代码分成更细的“区域”，例如 a &amp;&amp; b 中的 b 是一个单独的区域，只有 a为真时才会被执行 |
| 分支覆盖率（Branches） | 每个 if/match 的每个分支是否都走到过（目前需要 nightly 编译器） |

覆盖率最大的价值不在于那个百分比，而在于没被覆盖的那几行：它们是测试的盲区，往往正是错误处理分支。

### 17.9.4 【精通】覆盖率的局限与变异测试

覆盖率只说明代码被执行过，不说明它被检查过。下面这个测试让 apply_discount 达到了 100% 覆盖，却什么也没验证：
```rust
#[test]
fn covers_everything() {
    let _ = apply_discount(19_950, 90);
    let _ = apply_discount(19_950, 0);
}
```

所以：

不要把覆盖率当作目标。一旦把“覆盖率达到 90%”写进考核，就会出现大量这样的测试。门槛只用来防止覆盖率明显下降，例如在 CI 中设置一个略低于当前水平的值。

100% 既不现实也不必要。main.rs 中的组装代码、unreachable!() 分支、日志初始化，由端到端测试或代码审查来保证更合适。

关注未覆盖的错误分支。“数据库返回内部错误时服务层怎么处理”这类分支，正是 17.10.4 节用mock 补上的。

想知道测试是否真的在“检查”，可以用变异测试（mutation testing）。工具 cargo-mutants 自动对代码做小修改（把 &gt; 改成 &gt;=、把函数体替换为返回默认值……），然后运行测试。如果某个修改之后测试仍然全部通过，说明测试没能发现这个“bug”：
```bash
cargo install cargo-mutants --locked
cargo mutants -p common
```

它的报告会列出“存活的变异”（MISSED），每一条都指向一个测试不够严格的地方。变异测试很慢（每个变异都要重新编译和运行测试），适合对核心模块偶尔运行一次。

### 17.10.3 第 2 步：common 的性质测试

文件：rustmall/common/tests/properties.rs（新建）
```rust
//! common 的性质测试：用大量随机输入验证“对所有输入都成立”的规律（第 17.8 节）。
//!
//! 每个性质默认运行 256 个随机输入；临时加大次数：`PROPTEST_CASES=10000 cargo test -p common`。

use common::cart::Promotion;
use common::ids::ProductId;
use common::money::{format_yuan, parse_yuan};
use common::pagination::{limit_offset, normalize, MAX_PAGE_SIZE};
use common::product::Product;
use common::text::{normalize_username, USERNAME_MAX_CHARS, USERNAME_MIN_CHARS};
use proptest::prelude::*;

/// 任意一条优惠规则。字段故意取任意值（包括负数和超出范围的百分比），
/// 因为 `Promotion::discount_for` 承诺对不合法的规则返回 0。
fn any_promotion() -> impl Strategy<Value = Promotion> {
    prop_oneof![
        (any::<i64>(), any::<i64>()).prop_map(|(threshold_cents, off_cents)| {
            Promotion::FullReduction { threshold_cents, off_cents }
        }),
        any::<i64>().prop_map(|percent| Promotion::Discount { percent }),
    ]
}

proptest! {
    /// 往返：任意非负金额，格式化为“元”再解析，回到原值。
    #[test]
    fn yuan_round_trip(cents in 0..=i64::MAX) {
        prop_assert_eq!(parse_yuan(&format_yuan(cents)), Some(cents));
    }

    /// 负数金额可以格式化（用于退款展示），但用户输入中的负数一律被拒绝。
    #[test]
    fn negative_yuan_is_rejected_by_parser(cents in i64::MIN..0) {
        prop_assert!(format_yuan(cents).starts_with('-'));
        prop_assert_eq!(parse_yuan(&format_yuan(cents)), None);
    }

    /// 不变量：无论客戶端传什么，分页参数都被规范到合法范围，且 offset 与 limit 一致。
    #[test]
    fn pagination_is_always_in_range(
        page in any::<Option<u32>>(),
        size in any::<Option<u32>>(),
    ) {
        let (page_no, page_size) = normalize(page, size);
        prop_assert!(page_no >= 1);
        prop_assert!((1..=MAX_PAGE_SIZE).contains(&page_size));

        let (limit, offset) = limit_offset(page, size);
        prop_assert_eq!(limit, i64::from(page_size));
        prop_assert_eq!(offset, i64::from(page_no - 1) * limit);
    }

    /// 幂等：规范化后的用户名再规范化一次，结果不变；长度不合法时一定被拒绝。
    #[test]
    fn username_normalization_is_idempotent(
        input in "[ \t]{0,2}[A-Za-z0-9_]{0,25}[ \t]{0,2}",
    ) {
        let trimmed_chars = input.trim().chars().count();
        let allowed = USERNAME_MIN_CHARS..=USERNAME_MAX_CHARS;
        let length_ok = allowed.contains(&trimmed_chars);

        match normalize_username(&input) {
            Ok(name) => {
                prop_assert!(length_ok);
                prop_assert_eq!(&name.to_lowercase(), &name);
                prop_assert_eq!(normalize_username(&name), Ok(name));
            }
            // 字符集只包含合法字符，所以失败的唯一原因是长度
            Err(_) => prop_assert!(!length_ok),
        }
    }

    /// 不变量：对任意规则和任意非负小计，优惠金额总在 0 与小计之间（最多减到 0 元）。
    #[test]
    fn discount_never_exceeds_subtotal(
        rule in any_promotion(),
        subtotal in 0..=i64::MAX,
    ) {
        let discount = rule.discount_for(subtotal);
        prop_assert!(
            (0..=subtotal).contains(&discount),
            "rule = {:?}, subtotal = {}, discount = {}",
            rule,
            subtotal,
            discount
        );
    }

    /// 合法性判定：构造函数接受的输入，恰好是规则允许的输入；接受时名称已去除首尾空白。
    #[test]
    fn product_accepts_exactly_the_valid_inputs(
        name in "\\PC{0,110}",
        price_cents in any::<i64>(),
        stock in any::<i32>(),
    ) {
        let name_chars = name.trim().chars().count();
        let valid = (1..=Product::NAME_MAX_CHARS).contains(&name_chars)
            && price_cents >= 0
            && stock >= 0;

        match Product::try_new(ProductId::new(1), &name, price_cents, stock) {
            Ok(product) => {
                prop_assert!(valid);
                prop_assert_eq!(product.name(), name.trim());
                prop_assert_eq!(product.price_cents(), price_cents);
                prop_assert_eq!(product.stock(), stock);
            }
            Err(_) => prop_assert!(!valid),
        }
    }
}
```

代码精讲：

六个性质对应 17.8.5 节的几种模式：往返（金额格式化）、不变量（分页、优惠）、幂等（用户名）、合法性判定（商品）。每个性质都从需求出发描述规律，而不是把实现再写一遍。

0..=i64::MAX 覆盖了极端值：format_yuan(i64::MAX) 得到 "92233720368547758.07"，parse_yuan 必须先乘 100 再加分，任何一步溢出都会被发现。第 1 章写这两个函数时用了checked_mul、checked_add，这个性质证明了它们确实起了作用。

用户名的字符集是精确选择的：[A-Za-z0-9_] 加首尾的空格和制表符。如果改用 \\PC 生成任意字符，失败的原因就不只是长度（还有非法字符），断言要复杂得多。生成器只负责一个维度，性质才清晰。

商品的 \\PC{0,110} 有意超出上限 100：这样才能生成“恰好 100 个字符”“101 个字符”这类边界情况；字符串中也会出现各种 Unicode 空白，检验 trim 的行为与“名称长度按字符计”的规则。

prop_assert! 的说明文字：性质失败时，收缩后的规则、小计、优惠金额会直接显示出来。

### 17.10.4 第 3 步：服务层的 mock 测试

第 15 章的 FakeRepo 保留不动，它继续负责“结果”类的测试。新增的 mock 测试只做 Fake 不擅长的事。

文件：rustmall/monolith/src/service/products.rs。在文件末尾（已有的 mod tests 之后）追加：
```rust
/// 用 mockall 测试服务层与仓储之间的“交互”（第 17.5 节）：
/// 仓储是否被调用、收到了什么参数、仓储的错误是否被原样传递。
#[cfg(test)]
mod mock_tests {
    use std::sync::Arc;

    use common::error::{DomainError, ErrorKind};
    use mockall::mock;
    use mockall::predicate::eq;

    use super::*;

    // 与 `ProductRepository` 一一对应的同步版本。
    // 同步的 mock 不涉及任何异步细节；异步与 `Clone` 由下面的适配器负责。
    mock! {
        Store {
            fn insert(&self, draft: &NewProduct) -> DomainResult<Product>;
            fn get(&self, id: ProductId) -> DomainResult<Product>;
            fn list(&self, limit: i64, offset: i64) -> DomainResult<(Vec<Product>, i64)>;
            fn update(&self, product: &Product) -> DomainResult<Product>;
            fn delist(&self, id: ProductId) -> DomainResult<()>;
        }
    }

    /// 适配器：`Arc` 让它满足仓储 trait 的 `Clone` 约束，每个方法只是转发给 mock。
    #[derive(Clone)]
    struct MockedRepo(Arc<MockStore>);

    impl ProductRepository for MockedRepo {
        async fn insert(&self, draft: &NewProduct) -> DomainResult<Product> {
            self.0.insert(draft)
        }

        async fn get(&self, id: ProductId) -> DomainResult<Product> {
            self.0.get(id)
        }

        async fn list(
            &self,
            limit: i64,
            offset: i64,
        ) -> DomainResult<(Vec<Product>, i64)> {
            self.0.list(limit, offset)
        }

        async fn update(&self, product: &Product) -> DomainResult<Product> {
            self.0.update(product)
        }

        async fn delist(&self, id: ProductId) -> DomainResult<()> {
            self.0.delist(id)
        }
    }

    /// 期望必须在放进 `Arc` 之前设置好：设置期望需要 `&mut`。
    fn service(store: MockStore) -> ProductService<MockedRepo> {
        ProductService::new(MockedRepo(Arc::new(store)))
    }

    fn cmd(name: &str, price_cents: i64) -> ProductCommand {
        ProductCommand { name: name.to_string(), price_cents, stock: 3 }
    }

    #[tokio::test]
    async fn invalid_input_never_reaches_repository() {
        let mut store = MockStore::new();
        store.expect_insert().never();

        let err = service(store).create(cmd("   ", 100)).await.unwrap_err();

        assert_eq!(err.kind(), ErrorKind::InvalidInput);
    }

    #[tokio::test]
    async fn create_passes_trimmed_draft_to_repository() {
        let mut store = MockStore::new();
        store
            .expect_insert()
            .withf(|draft: &NewProduct| {
                draft.name() == "机械键盘" && draft.price_cents() == 19_900
            })
            .times(1)
            .returning(|draft| Ok(draft.clone().into_product(ProductId::new(42))));

        let created = service(store).create(cmd("  机械键盘  ", 19_900)).await.unwrap();

        assert_eq!(created.id(), ProductId::new(42));
        assert_eq!(created.name(), "机械键盘");
    }

    #[tokio::test]
    async fn repository_errors_pass_through_unchanged() {
        let mut store = MockStore::new();
        store
            .expect_get()
            .with(eq(ProductId::new(7)))
            .times(1)
            .returning(|_| Err(DomainError::Internal("连接池耗尽".to_string())));

        let err = service(store).get(ProductId::new(7)).await.unwrap_err();

        assert_eq!(err.kind(), ErrorKind::Internal);
    }

    #[tokio::test]
    async fn list_translates_page_into_limit_and_offset() {
        let mut store = MockStore::new();
        // 第 3 页、每页 10 条 → LIMIT 10 OFFSET 20
        store
            .expect_list()
            .with(eq(10_i64), eq(20_i64))
            .times(1)
            .returning(|_, _| Ok((Vec::new(), 25)));

        let page = service(store).list(Some(3), Some(10)).await.unwrap();

        assert_eq!((page.page, page.page_size, page.total), (3, 10, 25));
        assert!(page.items.is_empty());
    }
}
```

代码精讲：

为什么不直接给 ProductRepository 加 #[automock]：仓储 trait 要求 Clone，方法返回impl Future + Send（第 15.5.3 节）。mockall 生成的类型不能克隆，对返回 Future 的方法的支持细节也因版本而异。“同步 mock + 异步适配器”的写法只依赖 mockall 最基本、最稳定的功能，适配器也只有十几行。

四个测试各自验证一件 Fake 做不到（或做起来别扭）的事：

invalid_input_never_reaches_repository 验证“没有发生的调用”。never() 期望在调用发生时立即让测试失败。第 15 章的 create_validates_before_saving 只能通过“列表仍为空”来间接推断。

create_passes_trimmed_draft_to_repository 检查传给仓储的参数：名称已经去掉首尾空格，价格原样传递。

repository_errors_pass_through_unchanged 是错误注入：让仓储返回“连接池耗尽”，确认服务层不会把它吞掉或改成别的错误。HTTP 层依靠错误分类决定返回 500 并记录 ERROR 日志（第15.6.9 节），这条链路的第一环就在这里。

list_translates_page_into_limit_and_offset 验证分页参数的换算：第 3 页、每页 10 条，仓储必须收到 LIMIT 10 OFFSET 20。

eq(10_i64) 的类型后缀：不写后缀时整数字面量推断为 i32，与参数类型 i64 不匹配（17.5.7节）。

mock 测试不需要数据库，也不需要 Docker：四个测试加起来只需几毫秒，属于测试金字塔的最底层。

### 17.10.5 第 4 步：SQL 夹具与列表查询测试

商品列表按 created_at DESC, id DESC 排序。第 16 章的list_excludes_delisted_and_paginates_newest_first 通过接口依次创建商品，只能依赖“后创建的时间更晚”；“创建时间相同时按 ID 倒序”这条规则从来没被测试过。用夹具可以精确地构造这种情况。

//! 端到端冒烟测试：在一个全新的 PostgreSQL 17 容器中执行全部迁移并跑通主流程（第 17.6 节）。
//!
//! 它回答的问题是“从零开始的环境能否工作”，而不是测试某条业务规则。
//! 需要本机运行 Docker，默认被忽略。运行方式：
//!
//! ```text
//! cargo test -p monolith --test pg_container -- --ignored
//! 
```

mod support;

use axum::http::StatusCode;
use sqlx::postgres::PgPoolOptions;
use support::*;
use testcontainers_modules::postgres::Postgres;
use testcontainers_modules::testcontainers::runners::AsyncRunner;
use testcontainers_modules::testcontainers::ImageExt;

/// 与 `scripts/dev-db.sh`、生产环境保持一致的 PostgreSQL 版本。
const POSTGRES_TAG: &str = "17-alpine";

#[tokio::test]
#[ignore = "需要 Docker：cargo test -p monolith --test pg_container -- --ignored"]
async fn migrations_and_main_flow_on_fresh_postgres() {
    // 容器必须保存在变量中直到测试结束：它被丢弃时容器随之删除
    let container = Postgres::default()
        .with_tag(POSTGRES_TAG)
        .start()
        .await
        .expect("启动 PostgreSQL 容器（Docker 是否在运行？）");
    let host = container.get_host().await.expect("容器主机");
    let port = container.get_host_port_ipv4(5432).await.expect("映射后的端口");
    let url = format!("postgres://postgres:postgres@{host}:{port}/postgres");

    let pool = PgPoolOptions::new()
        .max_connections(5)
        .connect(&url)
        .await
        .expect("连接容器中的数据库");
    // 与服务启动时执行的是同一组迁移（第 14.10 节）
    monolith::db::MIGRATOR.run(&pool).await.expect("在全新数据库上执行迁移");

    // 主流程：注册管理员 → 登录 → 创建商品 → 匿名浏览 → 下架
    let app = app(pool.clone());
    let token = admin_token(&app, &pool).await;
    let id = create_product(&app, &token, "容器里的键盘").await;

    let uri = format!("/api/v1/products/{id}");
    let (status, product) = send(&app, get(&uri)).await;
    assert_eq!(status, StatusCode::OK);
    assert_eq!(product["name"], "容器里的键盘");

    let (status, _) = send(&app, with_token(delete(&uri), &token)).await;
    assert_eq!(status, StatusCode::NO_CONTENT);
    assert_eq!(send(&app, get(&uri)).await.0, StatusCode::NOT_FOUND);
}
````

代码精讲：

不使用 #[sqlx::test]：这个测试的数据库服务器由容器提供，迁移也由测试显式执行，这正是要验证的内容。所以它用普通的 #[tokio::test]，自己创建连接池。

migrations_and_main_flow_on_fresh_postgres 能发现的问题：迁移依赖开发库中“手动做过的某个操作”（例如某个扩展只在开发库中手动创建过）；迁移脚本在新版本 PostgreSQL 上语法不兼容；pg_trgm 扩展在目标镜像中不可用。这些问题在开发库上永远测不出来，因为开发库早已处于“迁移完成”的状态。

复用 tests/support：app、admin_token、create_product 与其他集成测试完全相同，端到端测试并不需要一套单独的工具。

#[ignore] 而不是 feature 开关：被忽略的测试仍然参与编译，代码不会悄悄“烂掉”；只是平时不运行。第 22 章的 CI 会用 -- --ignored 专门运行它。

```bash
#!/usr/bin/env bash
# 生成测试覆盖率报告（第 17.9 节）。需要先运行 ./scripts/dev-db.sh 启动开发数据库。
#
# 用法：
#   ./scripts/coverage.sh            终端摘要 + HTML 报告（target/llvm-cov/html/index.html）
#   ./scripts/coverage.sh --lcov     生成 lcov.info，供编辑器插件或 CI 使用
#
# 环境变量：
#   COVERAGE_MIN=80                  行覆盖率低于该值时以失败状态退出（默认不检查）
set -euo pipefail
cd "$(dirname "$0")/.."

if ! cargo llvm-cov --version > /dev/null 2>&1; then
    echo "未安装 cargo-llvm-cov，请先执行：cargo install cargo-llvm-cov --locked" >&2
    exit 1
fi

# main.rs 只做组装，由端到端测试与手动验证覆盖，不计入统计
IGNORE='monolith/src/main\.rs'

# 清除旧数据，运行全部测试并收集覆盖率（只收集，不生成报告）
cargo llvm-cov clean --workspace
cargo llvm-cov --workspace --no-report

# 从同一份数据生成报告
threshold=()
if [[ -n "${COVERAGE_MIN:-}" ]]; then
    threshold=(--fail-under-lines "$COVERAGE_MIN")
fi
cargo llvm-cov report --ignore-filename-regex "$IGNORE" --summary-only "${threshold[@]}"

if [[ "${1:-}" == "--lcov" ]]; then
    cargo llvm-cov report --ignore-filename-regex "$IGNORE" --lcov --output-path lcov.info
    echo "已生成 lcov.info"
else
    cargo llvm-cov report --ignore-filename-regex "$IGNORE" --html
    echo "HTML 报告：target/llvm-cov/html/index.html"
fi
```

脚本说明：

先收集、后报告：--no-report 只运行测试并保存原始数据，之后的几次 report 都从这份数据生成，测试只运行一次。

"${threshold[@]}"：用数组保存可选参数。COVERAGE_MIN 未设置时数组为空，展开后什么都没有；如果用普通字符串变量，空值会变成一个空参数，让命令报错。

门槛默认关闭：覆盖率门槛应当在团队对当前水平达成共识之后再设置（17.9.4 节），第 22 章接入 CI时再决定具体数值。

````bash
# RustMall 测试约定

## 测试分层

| 层次 | 位置 | 依赖 | 何时写 |
| --- | --- | --- | --- |
| 单元测试 | `src/` 中的 `#[cfg(test)] mod tests` | 无 | 每条业务规则、每个分支 |
| mock 测试 | `src/service/*.rs` 中的 `mod mock_tests` | 无 | 交互验证、错误注入 |
| 性质测试 | `common/tests/properties.rs` | 无 | 纯函数的往返、幂等、不变量 |
| 数据库与 HTTP 集成测试 | `monolith/tests/*.rs` | 开发数据库 | 每个接口的成功与主要错误路径 |
| 契约快照 | `monolith/tests/api_contract.rs` | 开发数据库 | 新增接口或修改响应格式时 |
| 端到端测试 | `tests/pg_container.rs` | Docker | 修改迁移、升级数据库前 |

## 常用命令

```bash
./scripts/dev-db.sh                       # 启动开发数据库
cargo test --workspace                    # 全部测试（不含被忽略的）
cargo test -p monolith --test pg_container -- --ignored   # 端到端测试
cargo insta review                        # 审阅快照变化
./scripts/coverage.sh                     # 覆盖率报告
```

## 规则

1. 测试名描述“情况与结果”，例如 `create_rejects_negative_price`。
2. 一个测试只验证一个行为；正文按“准备-执行-断言”分为三段。
3. 测试之间不共享状态：数据库测试一律使用 `#[sqlx::test]`，不修改环境变量。
4. 不使用 `sleep` 等待异步结果；需要时间的测试使用 `start_paused`。
5. 快照只用于 API 形状；业务规则用明确的断言。
6. `.snap` 文件和 proptest 的回归文件都要提交；`.snap.new` 不提交。
7. 覆盖率用来寻找盲区，不作为考核指标。
````

### 17.10.12 常见问题排查

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| api_contract 的测试全部失败，提示有新快照 | 还没有接受快照 | cargo insta test -p monolith --test api_contract --review |

### 17.10.13 本章小结

体系：单元测试与代码同文件、能访问私有项；集成测试在 tests/ 中、每个文件一个独立程序、只能使用公开 API；文档测试保证示例可运行。集成测试依赖的是不带 cfg(test) 的库，所以测试工具要用 feature 或 tests/support/ 共享。

好测试：名字描述“情况与结果”，一个测试一个行为，“准备―执行―断言”三段式；消除时间、随机数、遍历顺序和共享状态带来的不确定性。

数据库：#[sqlx::test] 每个测试一个临时库；SQL 夹具构造接口无法构造的数据，注意OVERRIDING SYSTEM VALUE 与 setval。

HTTP：Router 就是 Service，oneshot 不启动服务器即可测试；懒连接池让不访问数据库的测试脱离数据库。

替身：Fake 测“结果”，Mock 测“交互”与错误注入；仓储 trait 的形状使 RustMall 采用“同步mock + 异步适配器”。

容器：testcontainers 在测试中启动一次性的依赖，用于“从零开始的环境”这类端到端验证；它与#[sqlx::test] 分工而不是替代。

快照：insta 固定 API 的形状，时间、令牌等字段用脱敏处理；快照只管形状，规则用明确的断言。

性质：proptest 用随机输入检验往返、幂等、不变量等规律，失败时自动收缩出最小反例；回归文件要提交。

覆盖率：cargo-llvm-cov 找出测试盲区；覆盖率不等于质量，变异测试才能回答“测试是否真的在检查”。

下一章是第 18 章“Redis 从安装到精通 + redis-rs”：从 Windows、macOS、Linux 和 Docker 四种方式安装 Redis，讲解五种基本数据结构、过期与淘汰策略、持久化和主从复制；再用 redis crate 和进程内缓存 moka 为商品详情加上两级缓存，处理缓存穿透、击穿与雪崩，并用本章学到的 testcontainers 为缓存层编写测试。

### 17.10.14 本章练习

1. 为认证服务补 mock 测试：用同样的“同步 mock + 异步适配器”写法，为 AuthService 写两个测试：注册时用户名已存在，仓储返回 AlreadyExists，服务原样返回 Conflict；登录时仓储返回内部错误，服务返回 Internal 而不是 Unauthorized（为什么后者很重要？）。

2. 夹具组合：新建夹具 users.sql，插入一个普通用户（密码哈希可以通过注册接口生成后从数据库中复制）。写一个同时使用 fixtures("users", "catalog") 的测试。思考夹具之间的依赖顺序。

3. 契约快照扩展：为 GET /api/v1/users/me、PUT /api/v1/products/{id} 的 422 响应（例如负价格）各加一个快照。422 的 message 中包含什么信息？它应该成为契约的一部分吗？

4. 共享容器：把 pg_container.rs 改造为“一个测试程序共享一个容器，容器只提供服务器，每个测试仍然新建自己的数据库”。提示：容器用 std::sync::OnceLock 保存，用 SyncRunner（blocking feature）启动；每个测试在共享服务器上 CREATE DATABASE。

5. 性质测试找 bug：把 common::money::format_yuan 中格式化分的 {:02} 故意改成 {}，运行cargo test -p common --test properties，观察 proptest 收缩出的最小反例（应当是cents = 1：格式化为 "0.1"，再解析成了 10 分）。为什么 cents = 10 不是反例？然后撤销修改，并删除回归文件中因这次实验产生的那一行。

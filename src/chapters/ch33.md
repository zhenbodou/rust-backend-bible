# 第 33 章 工程检查点：契约与配置

第32章把补货与盘亏接入原有库存和事件模型。现在源码已经包含多个crate、三个业务数据库、多个原生进程，以及Kafka和Redis相关能力。继续增加用户、支付和订单之前，我们要回答一个具体问题：读者当前启动的程序，是否真是书中描述的那一套工程？

本章将第0-32章的累积工程整理为一个可检查的基线，新增Protobuf契约账本、描述符兼容检查、运行角色清单与本地配置检查器。它们直接加入当前workspace和CI。商品更新、库存RPC和调整事务继续沿用已验证实现；本章主要增加约束与操作证据，为后续服务演进提供稳定起点。

学完应能区分crate、二进制、进程、服务和数据所有权，能发现“代码都能编译但配置连错数据库”的问题，能说明协议兼容检查证明了什么，并按层次收集编译、事务、网络与部署证据。

## 33.1 先确认当前已经做到哪一步

### 33.1.1 【入门】从零基础章节走到当前工程

第1-8章建立Rust语言基础与common领域模型；第9-18章实现HTTP、PostgreSQL、日志、认证、测试和缓存；第19-24章展开协作、容器、CI与部署方法；第25-29章建立商品服务边界和事件链路；第30-32章实现库存预留、RPC恢复和可审计调整。

这些能力一直沿同一个RustMall工程推进。旧章节的小程序仍用于理解机制，当前运行入口则以本章角色清单为准。把早期练习的main函数与后期服务main函数同时粘到一个文件，会产生结构错误，不能通过随意删除函数来修补。

### 33.1.2 【入门】当前与后续目标分开理解

| 能力 | 当前第33章检查点 | 后续继续实现 |
| --- | --- | --- |
| 商品 | catalog gRPC、独立商品库、HTTP远程适配 | 后续统一服务入口与管理契约 |
| 库存 | 预留状态机、内部RPC、受控调整、持久化收据 | 持久化订单协调与跨服务恢复 |
| 身份 | 过渡HTTP接口层内的注册、登录和JWT | 第34章独立users与会话生命周期 |
| 事件 | 商品Outbox、Kafka、Inbox、独立投影 | 订单全链路与重建验收 |
| 支付 | 尚未形成分布式订单支付流程 | 第35章实验账本与退款屏障 |
| 订单 | common中的早期领域练习 | 第36章UUID订单、步骤持久化与Saga |
| 交付 | 前章容器、CI、Helm等学习材料和本地证据 | 全套服务交付与实际部署验收 |

本章不把common里一个Order结构体当作已上线的订单系统。语言层面的订单帮助学习所有权与状态；后续分布式订单还要保存身份、步骤、重试和补偿事实。

### 33.1.3 【进阶】三个“通过”回答不同问题

cargo check回答当前源文件能否通过类型检查；数据库测试回答所覆盖的SQL与事务断言是否成立；真实网络链路回答指定进程、依赖与故障场景能否协同。Linux应用镜像、Kubernetes升级回滚和远端流水线还需要各自运行证据。

排版可读也不是代码正确性的替代。跨页恢复的字符串可能把ORDER BY拼成ORDERBY，Rust仍认为它是合法String；只有执行相应SQL才能发现。这正是本书同时保留源码、测试日志与版式检查的原因。

### 33.1.4 【精通】先冻结不变量，再继续增加功能

当前需要保留：金额以分为单位；商品可售量不能被普通PUT覆盖；同意图重试使用同身份与参数；库存和商品事件同事务；投影不反向写商品；未知传输结果不能自动变成业务拒绝。

以后任何服务拆分都要重新验证这些规则。更换文件目录、进程名或网络协议，不应悄悄改变已经成立的业务含义。

## 33.2 把源码、进程与数据归属画清楚

### 33.2.1 【入门】crate不是运行进程

common、platform和contracts主要提供库能力；inventory也同时提供库存库与CLI。messaging一个包提供多个二进制；catalog一个进程同时注册商品Catalog和库存Inventory两个gRPC服务。

因此“有八个workspace成员”不能推出“部署八个微服务”。crate决定编译与代码依赖，二进制决定可执行入口，进程决定运行实例，业务服务与数据库归属决定谁维护不变量。

### 33.2.2 【入门】当前请求与事件路径

公开路径为：浏览器或CLI → gateway → 过渡HTTP接口层monolith → Catalog gRPC → 商品数据库。用户注册、登录和JWT校验当前仍在接口层及其身份数据库中。

可信库存调用方 → Inventory RPC → 同一个catalog进程与商品数据库。库存调整CLI是持有商品库写凭据的受控管理工具。另一路为商品Outbox → relay → Kafka → projection-worker → 独立投影数据库。

缓存是第18章本地商品仓储路径的能力；当前Remote商品模式直接通过catalog适配器读取权威商品，不能看到源码里有Redis依赖，就声称所有远程商品请求都经过Redis。

### 33.2.3 【进阶】数据库归属与例外写者

| 运行角色 | 业务责任 | 数据写入范围 |
| --- | --- | --- |
| catalog | 商品与库存事务 | 商品、预留、调整、商品Outbox |
| facade，即monolith | 过渡HTTP/身份、远程商品适配 | 身份库；Remote商品请求不写本地商品表 |
| gateway | HTTP边界与转发 | 无业务数据库 |
| relay | 事件可靠发送 | 商品Outbox认领、交付、失败重试字段 |
| projection | 去重和商品读模型 | 投影库的Inbox与catalog_view |
| inventory-client | 可信库存业务调用 | 经RPC间接请求，不持商品库凭据 |
| inventory-admin | 受控管理调整 | 经调整模块操作商品库 |

relay需要更新投递元数据，是明确的技术写入例外；它不能随意更新商品或决定库存。迁移程序又是独立高权限角色，日常运行账号不应自然继承全部DDL权限。

### 33.2.4 【精通】独立数据库和独立权限不是同一证据

当前本地实验可在一个PostgreSQL容器中建立三个数据库，也可能为方便测试使用同一个实验管理员。逻辑上已分库，不代表账号权限隔离已经验证。超级用户可以跨库管理对象，也可以绕过应用写入口。

后续完整部署应提供不同运行账号、最小授权、独立迁移账号与拒绝越权测试。当前检查器只核对角色清单和配置形状，不查询数据库授权，也不把数据库名称不同当成权限安全证明。

### 33.2.5 【精通】服务拆分应跟随事务边界

库存与商品留在同一个服务和数据库，是为了让价格、上下架、可售量、预留收据和Outbox共同参与本地事务。把库存搬到另一台机器，需要先设计这些判断跨网络后怎样成立。

订单与支付则有各自的持久化状态和独立业务决定，后面通过协调和恢复协作。服务数目不是质量指标；明确所有权和失败恢复才让拆分可推理。

## 33.3 固定当前代码与构建来源

### 33.3.1 【入门】始终从当前工作区根运行

当前目录应包含Cargo.toml、Cargo.lock、contracts、inventory、messaging和services。使用配套第33章完整检查点时，进入其中的rustmall工作区；自行逐章演进时，继续原目录并应用本章增量。

不要把不同阶段的target目录当作已经编译了当前源码的证据。检查多个同名包阶段时，可为每个阶段设置独立CARGO_TARGET_DIR。作者本轮验证使用独立检查点目录，避免把早章同名包产物误当后章结果。

### 33.3.2 【入门】工具链与锁文件分别固定什么

工具链固定为Rust1.92.0，edition为2024；Cargo.lock固定实际依赖解算结果。清单中的版本范围与锁文件承担不同职责，日常检查用--locked，防止边检查边无意改动依赖版本。

本章为契约测试增加prost-types和serde_json直接测试依赖；它们的版本已在工程依赖图中，仍需更新并提交锁文件的成员依赖记录。首次应用这一明确变更时允许cargo更新锁文件，完成后所有验证恢复--locked。

### 33.3.3 【进阶】先执行最小编译与契约实验

在contracts/Cargo.toml的dev-dependencies追加以下两项，保留原测试依赖：


原第25章的编码与传输测试继续保留。本章新增的描述符检查不替换它们，因为结构保持不代表服务器一定按原语义处理请求。

## 33.4 把协议变成可以核对的账本

### 33.4.1 【入门】生成编译器实际理解的描述符

用以下完整内容替换contracts/build.rs：
```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut config = prost_build::Config::new();
    config.file_descriptor_set_path(
        std::path::PathBuf::from(std::env::var("OUT_DIR")?).join("catalog_descriptor.bin"),
    );
    config.protoc_executable(protoc_bin_vendored::protoc_bin_path()?);
    tonic_prost_build::configure().compile_with_config(
        config,
        &["proto/catalog.proto"],
        &["proto"],
    )?;
    println!("cargo:rerun-if-changed=proto/catalog.proto");
    Ok(())
}
```

protoc继续由protoc-bin-vendored定位，生成Rust服务代码的同时，在OUT_DIR写出catalog_descriptor.bin。它是构建产物，跟随本次.proto编译，不由人手编辑。

在contracts/src/lib.rs原有pub mod catalog之前增加：
```rust
pub const FILE_DESCRIPTOR_SET: &[u8] = tonic::include_file_descriptor_set!("catalog_descriptor");
```

其余模块和三个原单元测试保持不变。include_file_descriptor_set在编译时把当前描述符嵌入库，供兼容测试读取；没有新增对外反射服务或HTTP接口。

### 33.4.3 【进阶】兼容检查读取实际描述符

新建contracts/tests/compatibility.rs，完整内容如下：
```rust
use contracts::FILE_DESCRIPTOR_SET;
use prost::Message;
use prost_types::{
    FileDescriptorSet,
    field_descriptor_proto::{Label, Type},
};
use serde_json::{Map, Value, json};

fn describe(bytes: &[u8]) -> Value {
    let descriptor = FileDescriptorSet::decode(bytes).expect("valid protoc descriptor");
    let file = descriptor
        .file
        .iter()
        .find(|f| f.package.as_deref() == Some("rustmall.catalog.v1"))
        .expect("catalog v1 package");
    let mut messages = Map::new();
    for message in &file.message_type {
        let mut fields = Map::new();
        for field in &message.field {
            let kind = Type::try_from(field.r#type.unwrap())
                .unwrap()
                .as_str_name()
                .trim_start_matches("TYPE_")
                .to_lowercase();
            let label = Label::try_from(field.label.unwrap())
                .unwrap()
                .as_str_name()
                .trim_start_matches("LABEL_")
                .to_lowercase();
            fields.insert(
                field.name.clone().unwrap(),
                json!({
                    "number":field.number, "type":kind, "label":label,
                    "type_name":field.type_name.as_deref().unwrap_or(""),
                    "oneof_index":field.oneof_index,
                    "proto3_optional":field.proto3_optional.unwrap_or(false)
                }),
            );
        }
        messages.insert(message.name.clone().unwrap(), Value::Object(fields));
    }
    let mut enums = Map::new();
    for enumeration in &file.enum_type {
        let values: Map<String, Value> = enumeration
            .value
            .iter()
            .map(|v| (v.name.clone().unwrap(), json!(v.number)))
            .collect();
        enums.insert(enumeration.name.clone().unwrap(), Value::Object(values));
    }
    let mut methods = Map::new();
    for service in &file.service {
        for method in &service.method {
            methods.insert(
                format!(
                    "{}.{}",
                    service.name.as_deref().unwrap(),
                    method.name.as_deref().unwrap()
                ),
                json!({
                    "input":method.input_type, "output":method.output_type,
                    "client_streaming":method.client_streaming.unwrap_or(false),
                    "server_streaming":method.server_streaming.unwrap_or(false)
                }),
            );
        }
    }
    json!({"package":file.package,"syntax":file.syntax,"messages":messages,"enums":enums,"methods":methods})
}

// Existing entries are immutable; new fields/types/methods may be added.
// This is the book's conservative v1 rule, not a complete Protobuf compatibility checker.
fn preserves(expected: &Value, actual: &Value, path: &str) -> Result<(), String> {
    if let Value::Object(entries) = expected {
        for (key, value) in entries {
            let next = actual
                .get(key)
                .ok_or_else(|| format!("removed: {path}/{key}"))?;
            preserves(value, next, &format!("{path}/{key}"))?;
        }
        return Ok(());
    }
    if expected == actual {
        Ok(())
    } else {
        Err(format!("changed: {path}"))
    }
}

fn baseline() -> Value {
    serde_json::from_str(include_str!("../compat/catalog-v1.json")).unwrap()
}
```

测试先用prost_types解码protoc产生的描述符，构造可读结构，再按基准递归检查。实际结构允许增加条目，基准中已有条目的名字和内容必须保留。缺失会报告removed路径，变化会报告changed路径。

它比较编译器实际产物，不用正则表达式解释.proto语法。新协议若自身不合法，protoc编译就先失败；合法但违反本书v1约定的变更，再由账本检查拒绝。

### 33.4.4 【精通】二进制可解码不代表业务兼容

把price_cents从int64改成uint64，在某些值上可能仍能按相近线格式解码，但会改变负数、范围与生成API。我们采用保守规则：既有字段类型、名称、编号与方法形态都不静默改变。

[Protobuf官方协议演进指南](https://protobuf.dev/programming-guides/proto3/#updating)区分了线格式安全和条件兼容的变更。本章账本是针对当前教学工程的更保守约定，并不实现所有Protobuf语言特性的兼容规则。

### 33.4.5 【精通】允许增加字段也需要业务审阅

添加字段通过结构检查，不代表旧客户端会使用它；新增ReservationState也不代表旧InventoryRemote能解释它。第31章已明确拒绝未知枚举，而不是把它当成成功。

当前describe只覆盖本协议的顶层消息、枚举与服务，不递归审计未来的嵌套类型，也未覆盖全部options、JSON映射和新增字段的业务含义。增加这些特性时，要扩展检查器或引入成熟的协议检查工具，并设计混合版本测试。

第一条只检查本章账本及四组回归规则；第二条还执行原编码与真实回环gRPC测试。五个新增测试包含实际描述符保持、金额类型变化、字段移除/编号变化、枚举/RPC形态变化和允许增量字段。

若看到price_cents/type，不要首先重写JSON；先查这次变更是否误改金额类型。若确需不兼容升级，应设计新的协议版本、迁移与并行运行计划。

[Cargo metadata官方文档](https://doc.rust-lang.org/cargo/commands/cargo-metadata.html)规定了机器可读的目标信息。本章使用--format-version 1固定输出格式，--no-deps只获取当前检查所需的包信息，并用--locked --offline避免诊断时意外改锁或联网解算。

## 33.6 实现不泄露秘密的配置检查器

### 33.6.1 【入门】完整脚本

新建scripts/check-checkpoint.py，使用Python3.11及以上：
```python
"""Check chapter structure and optional local role configuration; never print values.

Python 3.11+ and Cargo are required. This is not a deployment or privilege audit.
"""
import argparse
import ipaddress
import json
import os
from pathlib import Path
import subprocess
import sys
from urllib.parse import urlsplit

ROOT = Path(__file__).resolve().parents[1]


def local_http(value):
    try:
        url = urlsplit(value)
        if url.scheme != "http" or not url.hostname or url.username or url.password:
            return False
        if url.path not in ("", "/") or url.query or url.fragment:
            return False
        if url.port is None or not 1 <= url.port <= 65535:
            return False
        if url.hostname == "localhost":
            return True
        return ipaddress.ip_address(url.hostname).is_loopback
    except ValueError:
        return False


def postgres(value):
    try:
        url = urlsplit(value)
        return (url.scheme in ("postgres", "postgresql") and bool(url.hostname)
                and bool(url.path.strip("/")) and bool(url.username)
                and (url.port is None or 1 <= url.port <= 65535))
    except ValueError:
        return False


def check_environment(role, spec, environment):
    errors = [f"missing {name}" for name in spec["required"] if not environment.get(name)]
    for name in spec["postgres"]:
        if environment.get(name) and not postgres(environment[name]):
            errors.append(f"invalid PostgreSQL URL in {name}")
    for name in spec["http"]:
        if environment.get(name) and not local_http(environment[name]):
            errors.append(f"{name} must be an explicit loopback HTTP endpoint with port")
    for name in ("RUSTMALL_CATALOG_TOKEN", "RUSTMALL_INVENTORY_TOKEN"):
        if name not in spec["required"] or not environment.get(name):
            continue
        value = environment[name]
        if not 32 <= len(value) <= 256 or not all(33 <= ord(c) <= 126 for c in value):
            errors.append(f"invalid service credential format in {name}")
        elif name == "RUSTMALL_INVENTORY_TOKEN" and not all(
                c.isascii() and (c.isalnum() or c in "-_") for c in value):
            errors.append(f"invalid inventory credential alphabet in {name}")
    if role == "catalog" and environment.get("RUSTMALL_CATALOG_TOKEN") == environment.get("RUSTMALL_INVENTORY_TOKEN"):
        errors.append("catalog and inventory credentials must differ")
    if role == "facade":
        if environment.get("APP_ENV") != "production":
            errors.append("APP_ENV must be production for this checkpoint")
        if len(environment.get("APP_AUTH__JWT_SECRET", "").encode()) < 32:
            errors.append("APP_AUTH__JWT_SECRET must contain at least 32 bytes")
    if role == "inventory-client" and environment.get("DATABASE_URL"):
        errors.append("inventory-client should not receive DATABASE_URL")
    return errors


def check_structure(ledger, metadata):
    packages = {p["name"]: p for p in metadata["packages"]}
    errors = []
    for role, spec in ledger["roles"].items():
        for package_name, binary in [(spec["package"], spec["binary"])] + (
            [(spec["migration_package"], spec["migration_binary"])] if "migration_binary" in spec else []
        ):
            package = packages.get(package_name)
            if package is None or not any(t["name"] == binary and "bin" in t["kind"] for t in package["targets"]):
                errors.append(f"{role}: missing binary {package_name}/{binary}")
        if "migration_path" in spec and not list((ROOT / spec["migration_path"]).glob("*.sql")):
            errors.append(f"{role}: no SQL migration files")
    return errors


def main():
    ledger = json.loads((ROOT / "docs/runtime-boundaries.json").read_text())
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("--role", choices=sorted(ledger["roles"]))
    args = parser.parse_args()
    result = subprocess.run([os.environ.get("CARGO", "cargo"), "metadata", "--locked",
        "--offline", "--no-deps", "--format-version", "1", "--manifest-path", str(ROOT / "Cargo.toml")],
        text=True, capture_output=True)
    if result.returncode:
        print("FAIL cargo metadata; run cargo metadata separately for compiler diagnostics", file=sys.stderr)
        return 1
    errors = check_structure(ledger, json.loads(result.stdout))
    if args.role:
        errors += check_environment(args.role, ledger["roles"][args.role], os.environ)
    if errors:
        for error in errors:
            print("FAIL " + error, file=sys.stderr)
        return 1
    print(f"PASS chapter {ledger['chapter']} structure" + (f" and local {args.role} configuration" if args.role else ""))
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

不带--role只检查工程结构，不读取配置文件、不连接数据库。带角色时检查当前进程环境，不自动source任何.env文件。成功只输出阶段与角色，失败只指出变量名和错误类别，不回显凭据值。

### 33.6.2 【进阶】分清配置形状与连通性

PostgreSQL URL检查只确认协议、主机、数据库路径、用户名与合法端口。它不登录数据库，不证明密码有效，也不证明账号拥有期望权限。HTTP检查只确认符合回环实验策略，不发送请求。

因此PASS应理解为“这份本地角色配置通过预检查”。下一步仍要启动对应依赖、执行迁移、检查readiness并发送实际业务请求。

### 33.6.3 【进阶】不同凭据表达不同能力

catalog角色要求商品令牌与库存令牌不同。商品令牌遵守当前服务的可见ASCII长度规则；库存令牌遵守第31章URL安全字母表。接口层JWT密钥是另一项身份，不拿内部服务令牌替代它。

facade还要求APP_ENV=production并显式提供至少32字节JWT密钥，防止在这个工程检查点无意依赖开发默认值。这里的production配置用于暴露缺失配置；程序仍运行在回环实验环境，不因此成为生产部署。

### 33.6.4 【精通】错误信息本身也属于接口

URL解析失败可能来自非法端口等问题，脚本只返回固定类别，不打印输入。cargo metadata失败时也给出固定提示，要求操作者单独运行Cargo诊断；脚本不会枚举整个环境或输出.env内容。

这减少误把秘密写入报告的机会，不是完整的秘密防泄漏系统。程序日志、shell调试、进程参数和CI权限仍各需管理；不要在真实凭据终端启用set -x后批量运行实验。

### 33.9.3 【精通】阶段检查点如何接受后续变更

第34章引入users后，运行清单应增加新角色及迁移，并准确标注过渡身份入口的处理。新增支付与订单时同样更新清单和验证链，而不是一次把最终全书文件覆盖到当前目录，让读者遇见尚未介绍的模块。

旧v1账本保留既有契约；新字段有新编号，新业务有新持久化证据。确需替换契约时，应说明并行运行和迁移步骤，使读者知道此刻有哪些版本真实存在。

## 33.10 分层练习与下一章

### 33.10.1 【入门练习】一个crate有几个进程

messaging同时提供relay与projection-worker，这意味着它们共享一个SQL事务吗？

参考答案：没有。源码同包只共享编译与库代码，两个进程分别连接对应数据库；它们通过Kafka与事件身份协作，没有跨进程共享事务。

### 33.10.2 【操作练习】验证检查会正确失败

在专用实验终端让两种服务令牌使用同一测试值，再运行catalog预检查；恢复不同测试值后再次检查。报告只保存通过/失败类别，不写入值。

评分要点：相同值被拒绝，恢复后接受，错误输出没有秘密；随后仍需通过实际身份拒绝与正常RPC实验。

### 33.10.3 【推理练习】账本和协议一起改是否更方便

参考答案：方便却消除了历史参照。普通协议演进应保持旧账本并审阅差异；不兼容变更需要明确版本计划，不能把检查通过作为改写已发布结构的理由。

### 33.10.4 【推理练习】角色检查为何不能证明账号隔离

参考答案：它只读清单、Cargo信息与当前环境，没有以每个运行账号连接数据库执行授权测试。独立库名、正确URL甚至成功登录都不能证明越权写入会被拒绝。

### 33.10.5 【精通练习】添加一个新ReservationState

新增枚举通过账本检查，旧客户端会自动理解吗？

参考答案：不会。旧InventoryRemote明确拒绝未知state，必须设计混合版本行为、发布顺序与兼容处理。结构可增加和业务可恢复是两项不同要求。

### 33.10.6 【衔接】开始独立用户与会话服务

现在工程拥有可核对的角色入口、配置预检查与协议基准。第34章将把身份决策从过渡HTTP接口层迁入独立users，继续沿用common的用户规则，并补上持久会话、退出撤销与Redis故障语义。

后面的支付、订单和DevOps都以这一检查点继续演进。每一步既写清概念与完整文件，也说明真实请求怎样进入、状态保存在哪里、失败后由什么事实恢复。

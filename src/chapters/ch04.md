# 第 4 章 错误处理

后端程序每天都在和失败打交道：参数不合法、数据库连不上、库存不足、下游服务超时。本章讲 Rust怎样把“可能失败”写进类型里，让编译器逼着你处理每一种失败，以及生产项目里怎样组织错误类型。读完本章，RustMall 的 common 库会有一套统一的领域错误，后面 Axum 章节直接把它映射成HTTP 状态码。

## 4.1 两类错误：panic 与 Result

本章先区分可预期的失败和程序不变量被破坏的情况。参数、网络、数据库等业务与运行失败通常应通过 Result 表达；panic 的使用必须结合捕获边界与恢复前提判断，不能把它当成普通业务错误处理。

### 4.1.1【入门】什么是“可恢复”和“不可恢复”

先看一个后端里每天都会发生的场景：用户在下单接口里填了购买数量 "abc" 。这不是程序的 bug，而是用户输入不合法。正确做法是返回 400 并告诉用户“数量必须是数字”，服务本身继续运行。这叫可恢复错误。

再看另一个场景：代码里写了 let item = cart\[3\]; ，而购物车只有 2 件商品。这说明程序逻辑本身写错了，继续跑下去只会产生更离谱的结果。这叫不可恢复错误。

| 维度 | 可预期的失败 | 程序不变量被破坏 |
| --- | --- | --- |
| 例子 | 参数不合法、记录不存在、库存不<br>足、网络超时 | 代码越界、内部断言不成立 |
| 表达方式 | Result&lt;T, E&gt;，由调用方匹配或传<br>播 | 必要时 panic；先检查能否转成明确错误 |
| 处理边界 | 调用者选择返回错误、重试或其他<br>恢复动作 | 取决于 panic 策略与实际捕获边界 |
| HTTP 响应 | 按错误含义映射 4xx、5xx 等状态 | 不会自动形成规范 500；需要明确捕获与响应处<br>理 |

```rust
use std::num::ParseIntError;
 
// 可恢复：解析可能失败，失败信息交给调用者
fn parse_quantity(raw: &str) -> Result<u32, ParseIntError> {
    raw.trim().parse::<u32>()
}
 
fn main() {
    match parse_quantity("abc") {
        Ok(q) => println!("数量 = {q}"),
        // 输入不合法：invalid digit found in string
        Err(e) => println!("输入不合法：{e}"),
    }
 
    // 不可恢复：越界访问直接 panic
    let cart = vec!["键盘", "鼠标"];
 
    // thread 'main' panicked at ... index out of bounds: the len is 2 but the index is 2
    let third = cart[2];
    println!("{third}");
}
```

### 4.1.2【入门】Result 是一个普通的枚举

Result 没有任何魔法，它就是标准库里定义的一个枚举，和第 3 章写的枚举完全一样：

```rust
pub enum Result<T, E> {
    // 成功，携带结果值
    Ok(T),
    // 失败，携带错误值
    Err(E),
}
```

因为它是枚举，第 3 章学的 match 、if let 、let-else 全部可以用：

```rust
fn handle(raw: &str) -> u32 {
    // let-else：失败就给默认值并提前返回
    let Ok(q) = raw.parse::<u32>() else {
        return 1;
    };
    q
}
```

### 4.1.3【进阶】为什么 Rust 不用异常

Java、Python、C# 用 try/catch 异常。异常的问题在于函数签名不告诉你它会不会失败。int parse(String s) 看上去永远返回整数，实际上可能抛出异常；调用者忘了 catch，错误就会一路冒到最顶层。

Rust 的做法是把失败写进返回类型。fn parse\_quantity(raw: &amp;str) -&gt;Result&lt;u32,ParseIntError&gt; 这个签名本身就在说：“我可能失败，失败时给你一个 ParseIntError ”。这带来三个好处：

1. 编译器能提醒遗漏处理。Result 带有 #\[must\_use\] 标记；直接丢弃结果通常会产生警告。开启 -D warnings 后，相关警告会作为错误处理。显式忽略结果仍然可能发生，所以还需要代码审查。

2. 错误路径肉眼可见。代码里每个可能失败的地方都有 ? 或 match ，读代码时一眼能看到哪里会提前返回。

3. 成本可分析。Result 是普通枚举返回值，传播 Err 本身不要求触发 panic 式栈展开。成功与失败的实际耗时仍取决于分支、数据构造、日志和 I/O，不能声称两条路径总是一样快。

### 4.1.4【进阶】panic 时到底发生了什么

panic! 被触发后，默认行为是栈展开（unwind）：

1. 打印 panic 信息（消息、文件、行号）到标准错误。

2. 沿调用栈逐层往回走，对每一层的局部变量执行 Drop 。所以第 2 章讲的 RAII 在 panic 时依然生效：文件句柄和锁守卫会按析构机制清理；异步事务依驱动安排回滚，不等于已经等待并确认回滚完成。

3. 当前线程结束。如果是主线程，整个进程以退出码 101 结束。

设置环境变量 RUST\_BACKTRACE=1 再运行，会额外打印调用栈，定位 bug 时非常有用：

```text
RUST_BACKTRACE=1 cargo run
```

### 4.1.5【精通】unwind 与 abort，以及对后端服务的影响

在 Cargo.toml 的 profile 里可以把 panic 策略改成 abort：

```text
[profile.release]
panic = "abort"
```

| 策略 | 主要行为 | 注意事项 |
| --- | --- | --- |
| unwind | 沿栈展开，在相应边界执行清理 | 能否保持服务可用还取决于捕获位置和共享状态 |
| abort | 终止整个进程，不进行通常的栈展<br>开 | 不能依赖 Drop 清理；其他在途请求也会中断 |

Axum 配合 CatchPanicLayer 还能把 panic 转成 500 响应。如果改成 abort，一个请求里的 bug 会让整个 Pod 重启，正在处理的所有请求都会失败。

还有一个关键点：panic 不是错误处理机制。不要用 std::panic::catch\_unwind 去模拟 try/catch，它只适合在框架边界（线程池、FFI 边界）兜底。

常见编译错误与解读

| 诊断 | 常见触发原因 | 修正方向 |
| --- | --- | --- |
| unused Result that must be<br>used | 调用返回 Result 的函数后忽略结果 | 处理结果；确实需要忽略时明确写 let \_ = ... |
| E0308 类型不匹配 | 把 Result&lt;u32, E&gt; 直接赋给 u32 | 用 match、? 或适当组合子取出成功值 |
| E0004 分支不完整 | match Result 时只覆盖 Ok | 同时处理 Err，或明确传播错误 |

本节练习

1. 把下面五种情况分成“可恢复”和“不可恢复”两类，并说明理由：用户密码错误；配置里的端口号写成了 "80a" （发生在服务启动时）；Redis 连接超时；订单状态机进入了代码里声明“不可能”的状态；上传文件超过 10 MB。

2. 写一个程序故意让 vec!\[1, 2\]\[5\] panic，分别在设置和不设置 RUST\_BACKTRACE=1 的情况下运行，对比输出差异。

3. 新建一个结构体并为它实现 Drop （在 drop 里打印一行字），在它的作用域内触发 panic，验证 unwind 时 Drop 仍会执行。再在 Cargo.toml 里设置 \[profile.dev\] panic = "abort" 重跑，观察区别。

## 4.2 Result 与 Option 全解：常用组合子方法

Result 和 Option 上有几十个方法，本节按四组介绍：取值、变换、链式调用、两者互转。用好它们，可以少写一大半的 match 。

### 4.2.1【入门】取值：从 Result 里拿出值

| 方法 | 成功时 | 失败时 | 用途 |
| --- | --- | --- | --- |
| match / if let | 按模式读取成功值 | 按模式处理失败值 | 明确选择两类分支 |
| unwrap() | 取出值 | panic | 只用于有可说明前提的位置 |
| expect("说明") | 取出值 | panic，并附说明 | 说明为什么这里本应成功 |
| unwrap\_or(value) | 取出值 | 使用给定默认值 | 默认值会提前求值 |
| unwrap\_or\_else(f) | 取出值 | 调用闭包构造默认值 | 按需构造或依据错误恢复 |
| unwrap\_or\_default() | 取出值 | 使用 T::default() | T 实现 Default |
| ? | 继续使用成功值 | 从当前函数或闭包传播<br>失败 | 返回类型需要支持相应失败传播 |

```rust
fn page_size(raw: Option<&str>) -> u32 {
    // 解析失败当作没传
    raw.and_then(|s| s.parse::<u32>().ok())
        // 没传就用 20
        .unwrap_or(20)
        // 再限制在 1..=100
        .clamp(1, 100)
}
 
assert_eq!(page_size(None), 20);
assert_eq!(page_size(Some("50")), 50);
assert_eq!(page_size(Some("abc")), 20);
assert_eq!(page_size(Some("9999")), 100);
```

### 4.2.2【入门】变换：map 与 map\_err

map(f) ：只改成功值，错误原样透传。Result&lt;T, E&gt; 变成 Result&lt;U, E&gt; 。

map\_err(f) ：只改错误值，成功值原样透传。Result&lt;T, E&gt; 变成 Result&lt;T, F&gt; 。后端里最常用来把底层错误换成业务错误。

```rust
#[derive(Debug, PartialEq)]
enum ApiError {
    BadRequest(String),
}
 
fn parse_price_yuan(raw: &str) -> Result<i64, ApiError> {
    raw.parse::<f64>()
        // 元 → 分
        .map(|yuan| (yuan * 100.0).round() as i64)
        .map_err(|e| ApiError::BadRequest(format!("价格格式错误：{e}")))
}
```

注意：这里为了演示用了 f64 。真实项目中金额绝不能用浮点数解析，第 1 章的 money 模块已经用整数“分”存储，第 4.8 节会把校验接进去。

### 4.2.3【进阶】链式调用：and\_then、or\_else、ok\_or

map 的闭包返回普通值；如果闭包本身也可能失败（返回 Result ），用 map 会得到嵌套的 Result&lt;Result&lt;U, E&gt;, E&gt; 。这时要用 and\_then ，它会把嵌套“拍平”。

```rust
fn parse_positive(raw: &str) -> Result<u32, String> {
    raw.parse::<u32>()
        .map_err(|e| e.to_string())
        .and_then(|n| if n > 0 { Ok(n) } else { Err("必须大于 0".to_string()) })
}
```

| 方法 | 处理哪种分支 | 结果或作用 |
| --- | --- | --- |
| map | Ok / Some | 变换成功值 |
| map\_err | Err | 变换错误类型或错误内容 |
| and\_then | Ok / Some | 继续执行返回 Result / Option 的动作 |
| or\_else | Err / None | 在失败或缺失时尝试补救 |
| ok\_or / ok\_or\_else | Option | 将 None 转成指定错误 |
| ok / err | Result | 分别保留成功值或错误值，转换成 Option |
| transpose | Option&lt;Result&lt;T,E&gt;&gt; 或<br>Result&lt;Option&lt;T&gt;,E&gt; | 交换两层容器的位置 |
| inspect\_err | Err | 借用错误作观察，不改变结果 |
| is\_ok\_and / is\_some\_and | Ok / Some | 对内部值作条件判断 |

ok\_or\_else 在后端中很常见：

```rust
fn find_user(users: &[(u64, &str)], id: u64) -> Result<String, String> {
    users
        .iter()
        // Option<&(u64, &str)>
        .find(|(uid, _)| *uid == id)
        // Option<String>
        .map(|(_, name)| name.to_string())
        // Result<String, String>
        .ok_or_else(|| format!("用户 {id} 不存在"))
}
```

transpose 解决“参数可以不传，但传了就必须合法”：

```rust
fn parse_min_price(raw: Option<&str>) -> Result<Option<i64>, std::num::ParseIntError> {
    // Option<Result<i64, _>>
    raw.map(|s| s.parse::<i64>())
        // Result<Option<i64>, _>
        .transpose()
}
 
assert_eq!(parse_min_price(None), Ok(None));
assert_eq!(parse_min_price(Some("100")), Ok(Some(100)));
assert!(parse_min_price(Some("x")).is_err());
```

### 4.2.4【进阶】迭代器里的 Result：collect 的妙用

一个 Vec&lt;Result&lt;T, E&gt;&gt; 可以直接 collect 成 Result&lt;Vec&lt;T&gt;, E&gt; ：全部成功得到 Ok(Vec)，遇到第一个错误就停下并返回这个错误。批量校验请求参数时非常好用：

```rust
fn parse_ids(raw: &str) -> Result<Vec<u64>, std::num::ParseIntError> {
    raw.split(',').map(|s| s.trim().parse::<u64>()).collect()
}
 
assert_eq!(parse_ids("1, 2,3"), Ok(vec![1, 2, 3]));
assert!(parse_ids("1,x,3").is_err());
```

如果想收集所有错误而不是第一个，就用 partition ：

```text
let (oks, errs): (Vec<_>, Vec<_>) = ["1", "x", "3", "y"]
    .iter()
    .map(|s| s.parse::<u64>())
    .partition(Result::is_ok);
let values: Vec<u64> = oks.into_iter().map(Result::unwrap).collect();
assert_eq!(values, vec![1, 3]);
assert_eq!(errs.len(), 2);
```

这里的 unwrap 是安全的：partition 已经保证 oks 里全是 Ok 。这正是 4.7 节说的“由不变量保证不会失败”的合法 unwrap。

### 4.2.5【精通】as\_ref、as\_deref 与所有权

第 2 章的所有权规则在这里同样适用：map 、unwrap\_or 等方法都按值接收 self ，会消耗这个Result/ Option 。如果你只有引用，或者之后还要用原值，先转成引用版本：

| 方法 | Option 示例 | 用途 |
| --- | --- | --- |
| as\_ref | &amp;Option&lt;T&gt; → Option&lt;&amp;T&gt; | 借用内部值 |
| as\_mut | &amp;mut Option&lt;T&gt; →<br>Option&lt;&amp;mut T&gt; | 可变借用内部值 |
| as\_deref | &amp;Option&lt;String&gt; →<br>Option&lt;&amp;str&gt; | 借用并应用 Deref |
| take | &amp;mut Option&lt;T&gt; → Option&lt;T&gt; | 取走值，原位置留下 None |
| copied / cloned | Option&lt;&amp;T&gt; → Option&lt;T&gt; | 满足 Copy 或 Clone 条件时获得拥有所有权的<br>值 |

```rust
struct Query {
    keyword: Option<String>,
}

fn describe(q: &Query) -> &str {
    // q.keyword.unwrap_or(...) 会报 E0507：不能从借用中移出
    q.keyword.as_deref().unwrap_or("（全部商品）")
}
```

这些组合子通常可以被内联和优化，不必为了少写一层方法调用就改成重复的 match；是否生成相同机器码以及实际性能，仍取决于具体代码与编译配置。

常见编译错误与解读

| 诊断 | 原因 | 修正 |
| --- | --- | --- |
| E0507 不能从共享引用移动值 | 对借用字段调用消耗所有权的方法 | 先 as\_ref 或 as\_deref |
| 嵌套 Result 与预期不符 | 闭包返回 Result，却使用 map | 需要扁平串联时使用 and\_then |
| 两步错误类型不一致 | and\_then 的各步使用不同错误类型 | 用 map\_err 统一边界类型 |
| E0282 无法推断类型 | collect 可生成多种集合 | 标注目标类型，如 Result&lt;Vec&lt;u64&gt;, E&gt; |

1. 不用 match ，只用组合子实现 fn parse\_page(raw: Option&lt;&amp;str&gt;) -&gt;Result&lt;u32,String&gt;：不传返回 1；传了必须是 1..=1000 的整数，否则返回带说明的错误。

2. 用 collect 实现 fn parse\_skus(raw: &amp;str) -&gt; Result&lt;Vec&lt;String&gt;, String&gt; ：逗号分隔，任何一项去掉空格后为空就报错，错误里写明是第几项。

3. 给定 struct User { nickname: Option&lt;String&gt; } ，写 fn display\_name(u: &amp;User)-&gt;&amp;str ，昵称为空字符串时也当作未设置。提示：as\_deref 加 filter 。

## 4.3 ? 运算符与 From 转换

? 的意思是：成功就取出值继续往下走，失败就把错误转换成当前函数的错误类型并立即返回。它是Rust 后端代码里出现频率最高的符号，一个 Axum 处理函数里常常有五六个。

### 4.3.1【入门】从 match 到 ?

不用 ? 时，每一步可能失败的操作都要写一个 match ：

```rust
use std::num::ParseIntError;
 
fn total_cents(price: &str, qty: &str) -> Result<u64, ParseIntError> {
    let price = match price.parse::<u64>() {
        Ok(v) => v,
        Err(e) => return Err(e),
    };
    let qty = match qty.parse::<u64>() {
        Ok(v) => v,
        Err(e) => return Err(e),
    };
    Ok(price * qty)
}
```

用 ? 改写后，意思完全一样：

```rust
fn total_cents(price: &str, qty: &str) -> Result<u64, ParseIntError> {
    let price = price.parse::<u64>()?;
    let qty = qty.parse::<u64>()?;
    Ok(price * qty)
}
```

还能链式写在一行：let n = raw.trim().parse::&lt;u64&gt;()?.checked\_mul(2).ok\_or(...)?; 。

### 4.3.2【入门】? 能用在哪里

? 只能写在返回类型“可以表示失败”的函数里：

| 当前返回类型 | 典型允许的 ? 输入 |
| --- | --- |
| Result&lt;T,E&gt; | Result&lt;U,X&gt;，并能将 X 转为 E |
| Option&lt;T&gt; | Option&lt;U&gt; |
| () 或普通值 | 不能直接使用通常的 Result / Option 传播形式 |

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let port: u16 = "8080".parse()?;
    println!("监听端口 {port}");
    Ok(())
}
```

main 返回 Err 时，程序会用错误的 Debug 格式打印 Error: ... 并以退出码 1 结束。

### 4.3.3【进阶】? 背后的真实展开

下面这段伪代码就是编译器对 expr? 做的事情（适用于返回 Result 的函数）：

```text
match expr {
    Ok(v) => v,
    // 关键：自动调用 From 转换
    Err(e) => return Err(From::from(e)),
}
```

关键在 From::from(e) 。只要当前函数的错误类型 E 实现了 From&lt;X&gt; ，类型为 X 的错误就能自动转换成 E 。这就是“错误一层层向上传，每一层换成更高层的错误类型”的机制：

```rust
use std::num::ParseIntError;
 
#[derive(Debug)]
enum OrderInputError {
    BadNumber(ParseIntError),
    ZeroQuantity,
}
 
// 告诉编译器：ParseIntError 可以变成 OrderInputError
impl From<ParseIntError> for OrderInputError {
    fn from(e: ParseIntError) -> Self {
        OrderInputError::BadNumber(e)
    }
}
 
fn parse_qty(raw: &str) -> Result<u32, OrderInputError> {
    // ParseIntError 自动转成 OrderInputError::BadNumber
    let q: u32 = raw.parse()?;
    if q == 0 {
        return Err(OrderInputError::ZeroQuantity);
    }
    Ok(q)
}
```

手写 From 很繁琐，4.5 节的 thiserror 用一个 #\[from\] 属性就能自动生成。

### 4.3.4【进阶】? 用在 Option 上，以及两者不能混用

返回 Option 的函数里，? 遇到 None 就直接返回 None ：

```rust
struct Order { address: Option<Address> }
struct Address { city: Option<String> }
fn city_of(o: &Order) -> Option<&str> {
    Some(o.address.as_ref()?.city.as_deref()?)
}
```

但 Option 和 Result 之间不会自动转换。在返回 Result 的函数里对 Option 用 ? 会报 E0277。正确写法是先用 ok\_or / ok\_or\_else 把 None 变成一个有意义的错误：

```rust
fn city_or_err(o: &Order) -> Result<&str, String> {
    let addr = o.address.as_ref().ok_or("缺少收货地址")?;
    let city = addr.city.as_deref().ok_or_else(|| "地址缺少城市".to_string())?;
    Ok(city)
}
```

第一行 ok\_or 给的是 &amp;str ，函数错误类型是 String ，能通过编译是因为标准库实现了 implFrom&lt;&amp;str&gt; for String ，? 自动调用了它。

### 4.3.5【精通】Box&lt;dyn Error&gt; 与 ? 的类型推断

Box&lt;dyn std::error::Error + Send + Sync + 'static&gt; 是“任何错误”的通用容器。标准库为它实现了 impl&lt;E: Error + Send + Sync + 'static&gt; From&lt;E&gt; for Box&lt;dyn Error +Send +Sync&gt; ，所以任何标准错误都能 ? 进去。它适合示例程序和脚本，但有两个缺点：调用者无法用 match 区分错误种类；每个错误多一次堆分配。生产项目里，库代码用 4.4/4.5 的具体枚举类型，应用顶层用 4.6 的 anyhow。

第二个精通点是类型推断。? 的转换方向是“从表达式的错误类型到函数的错误类型”，编译器要同时知道这两个类型。在闭包里用 ? 时，闭包的返回类型经常推断不出来：

```text
// E0282：编译器不知道闭包返回什么 Result
let parse = |s: &str| {
    let n: u32 = s.parse()?;
    Ok(n)
};
 
// 修复：给闭包写返回类型
let parse = |s: &str| -> Result<u32, std::num::ParseIntError> {
    let n: u32 = s.parse()?;
    Ok(n)
};
```

第三个精通点：? 在 async fn 里行为完全相同。后面的异步与数据库章节里，sqlx::query(...).fetch\_one(&amp;pool).await? 这种写法就是先 .await 拿到 Result ，再用 ?展开。

常见编译错误与解读

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| 在返回 () 的 main 中使用 ? | 返回类型不能承接失败 | 将 main 改成适当的 Result 返回类型 |
| 不能将源错误转成目标错误 | 缺少 From 转换 | 实现 From，或显式 map\_err |
| 在 Result 函数中直接对<br>Option 使用 ? | 两种失败表达不同 | 先 ok\_or 或 ok\_or\_else |

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| 闭包返回类型不明确 | ? 所在闭包自身需要可传播的返回<br>类型 | 标注闭包的 Result 返回类型 |
| 期待 Result 却返回普通值 | 末尾没有包装成功值 | 返回 Ok(value) |

本节练习

1. 把 4.3.3 的 parse\_qty 扩展为 parse\_line(raw: &amp;str) -&gt; Result&lt;(u64,u32),OrderInputError&gt; ，输入形如 "1001:3" （商品 ID:数量）。缺少冒号时新增变体 MissingColon。全程只用 ? 和 ok\_or ，不写 match 。

2. 写一个 fn main() -&gt; Result&lt;(), Box&lt;dyn std::error::Error&gt;&gt; ，依次解析"8080"、"80a"，观察程序在哪一步退出、退出码是多少（Linux/macOS 用 echo $? ，WindowsPowerShell 用$LASTEXITCODE ）。

3. 解释为什么 let a: Result&lt;u8, String&gt; = Err("x")?; 这种写法在返回 Result&lt;(),String&gt;的函数里能编译，而在返回 Result&lt;(), u32&gt; 的函数里不能。

## 4.4 手写自定义错误类型：Display、Error、source

一个合格的错误类型要满足三件事：实现 Debug （给开发者看）、实现 Display （给人看的一句话）、实现 std::error::Error （接入标准错误生态，能被 Box&lt;dyn Error&gt; 、anyhow、日志框架识别）。本节先全部手写一遍，理解原理后，4.5 节再用 thiserror 一行搞定。

### 4.4.1【入门】用枚举表示“一组可能的错误”

业务错误几乎总是用枚举表示：每个变体是一种失败原因，变体里携带定位问题需要的数据。

```rust
// 文件：示例，不属于项目
#[derive(Debug)]
pub enum StockError {
    /// 商品不存在
    ProductNotFound { product_id: u64 },
    /// 库存不足
    Insufficient { product_id: u64, requested: u32, available: u32 },
}
```

设计原则：变体按调用者需要做出的不同反应来划分，而不是按底层原因划分。调用者对“不存在”要返回404，对“库存不足”要返回 409 并提示剩余数量，所以它们是两个变体。

### 4.4.2【入门】实现 Display

Display 决定 {} 和 to\_string() 的输出。约定：小写开头、不带句号、只描述本层发生了什么（中文项目同理，不加句号）。

```rust
use std::fmt;
 
impl fmt::Display for StockError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            StockError::ProductNotFound { product_id } => {
                write!(f, "商品 {product_id} 不存在")
            }
            StockError::Insufficient { product_id, requested, available } => {
                write!(f, "商品 {product_id} 库存不足：需要 {requested}，剩余 {available}")
            }
        }
    }
}
```

逐行解读：

fmt::Formatter&lt;'\_&gt; 是输出目标，'\_ 是第 2 章讲过的匿名生命周期。

write!(f, ...) 和 format! 语法相同，但写入 f 而不是新建字符串，返回 fmt::Result 。

match self 时，self 是 &amp;StockError ，按第 3 章讲的绑定规则，product\_id 等变量都是引用&amp;u64 ，{} 能直接格式化引用。

### 4.4.3【入门】实现 Error

有了 Debug 和 Display ，实现 Error 只需要一行，因为它的方法都有默认实现：

```rust
impl std::error::Error for StockError {}
```

Error trait 的定义（简化）：

```rust
pub trait Error: Debug + Display {
    fn source(&self) -> Option<&(dyn Error + 'static)> { None }
    // description()、cause() 已废弃，不要实现
}
```

冒号后面的 Debug + Display 叫父 trait（supertrait）：想实现 Error ，必须先实现这两个。第 5 章会系统讲 trait。

### 4.4.4【进阶】source：把错误串成一条链

真实错误往往有多层原因。例如“创建订单失败”是因为“扣减库存失败”，而后者又因为“数据库连接超时”。每一层只描述自己这层的事，再通过 source() 指向下一层，这就是错误链。

```rust
use std::error::Error;
use std::fmt;
 
#[derive(Debug)]
pub enum CreateOrderError {
    Stock(StockError),
    InvalidQuantity(std::num::ParseIntError),
}
 
impl fmt::Display for CreateOrderError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            // 只描述本层，不把下层的信息拼进来
            CreateOrderError::Stock(_) => write!(f, "扣减库存失败"),
            CreateOrderError::InvalidQuantity(_) => write!(f, "购买数量格式错误"),
        }
    }
}
 
impl Error for CreateOrderError {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            CreateOrderError::Stock(e) => Some(e),
            CreateOrderError::InvalidQuantity(e) => Some(e),
        }
    }
}
 
impl From<StockError> for CreateOrderError {
    fn from(e: StockError) -> Self { CreateOrderError::Stock(e) }
}
impl From<std::num::ParseIntError> for CreateOrderError {
    fn from(e: std::num::ParseIntError) -> Self { CreateOrderError::InvalidQuantity(e) }
}
```

遍历错误链并打印：

```rust
fn report(err: &dyn Error) -> String {
    let mut out = err.to_string();
    let mut cur = err.source();
    while let Some(cause) = cur {
        out.push_str(&format!("\n  原因：{cause}"));
        cur = cause.source();
    }
    out
}
 
// 输出：
// 扣减库存失败
//   原因：商品 1001 库存不足：需要 5，剩余 2
```

### 4.4.5【进阶】黄金规则：Display 和 source 二选一

这是错误设计里最常见、也最容易被忽视的错误：下层错误的信息要么拼进本层 Display，要么通过source 暴露，不能两者都做。

如果 Display 写成 "扣减库存失败：{e}" ，同时 source() 又返回 e ，若报告工具同时展示本层 Display 与 source 链，就可能把同一条底层信息展示两遍，例如：

```text
扣减库存失败：商品 1001 库存不足：需要 5，剩余 2: 商品 1001 库存不足：需要 5，剩余 2
```

| 组织方式 | Display | source | 适用场景 |
| --- | --- | --- | --- |
| 包装 | 说明本层上下文 | 返回底层错误 | 保留可遍历的错误原因 |
| 透明 | 按透明包装规则转发 | 按透明包装规则转发 | 本层不增加独立上下文 |
| 封装并隐藏 | 输出受控摘要 | 可以不暴露内部来源 | 明确选择不把内部错误交给调用方 |

### 4.4.6 【精通】Error 的约束：Send、Sync、'static

在多线程和异步代码里，错误会跨线程传递（Tokio 任务可能在任意工作线程上恢复执行）。所以后端代码里的错误类型经常需要满足目标 API 指定的 Send、Sync 与 'static 约束；Error trait 本身不自动要求这些条件。常见约束分别表示：

Send ：可以移动到另一个线程。错误里放了 Rc&lt;T&gt; 就会失去 Send 。

Sync ：可以被多个线程同时借用。放了 RefCell&lt;T&gt; 、Cell&lt;T&gt; 就会失去 Sync 。

'static ：不含非 'static 的引用。错误里存 &amp;str 字段（除非是 &amp;'static str ）就不满足，source() 返回的 dyn Error + 'static 也要求这一点。

实践规则：错误类型的字段只用拥有所有权的数据（String 、u64 、Uuid ）和 &amp;'static str，不要在错误里借用请求数据。4.8 节的项目代码会用 &amp;'static str 表示字段名，因为字段名都是代码里写死的字面量。

另一个精通点是错误的大小。Result&lt;T, E&gt; 的实际布局受对齐和可能的布局优化影响，不应只按“较大 变体加判别值”推算精确大小；可以用 size\_of 观察具体实例。如果错误枚举某个变体特别大（比如内

嵌一个 200 字节的结构体），所有返回它的函数都要搬运这么大的返回值，Clippy 的 result\_large\_err 会按所用版本及配置的阈值提示较大的错误值。修复方法是把大变体装进 Box 。

常见编译错误与解读

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| 错误类型未实现 Display | Error 要求相应父 trait | 提供 Display 实现或适当派生宏 |
| 错误类型未实现 Debug | 遗漏 Debug | 派生或实现 Debug |
| source 的引用类型不匹配 | 对已经借用的错误又增加了一层引<br>用 | 返回适当的错误引用，按需转换为 trait 对象 |
| 来源错误生命周期不足 | source 引用了短于要求的值 | 让错误拥有数据，或使用满足条件的静态引用 |
| result\_large\_err | 某个错误变体很大 | 评估用 Box 保存较大的内部错误 |

本节练习

1. 给 4.3 节练习里的 OrderInputError 手写 Display 和 Error ，其中 BadNumber 通过 source 暴露内部的 ParseIntError 。

2. 故意违反“二选一”规则，在 Display 里拼上内层错误，再用 4.4.4 的 report 打印，观察重复。然后改回正确写法。

3. 写一个函数 fn root\_cause(e: &amp;dyn Error) -&gt; &amp;dyn Error ，返回错误链最底层的错误。提示：循环调用 source() 直到返回 None 。

4. 用 std::mem::size\_of::&lt;Result&lt;u64, CreateOrderError&gt;&gt;() 打印大小；给 CreateOrderError 加一个包含 \[u8; 256\] 的变体再打印，体会错误大小对返回值的影响。

## 4.5 thiserror 全解

thiserror 是一个派生宏 crate：你写枚举并加上属性，它在编译期替你生成 4.4 节手写的 Display 、Error 、source() 和 From 。生成的代码和手写的一样，运行时零开销，而且 thiserror 不会出现在你的公开 API 里；在保持公开类型与行为一致的前提下，也可以改成手写实现。它是 Rust 生态里库代码定义错误类型的事实标准。

### 4.5.1【入门】安装与版本

本章示例以 thiserror 2.x 为基准，实际依赖版本应保存在 Cargo.lock 中。在 RustMall 的 workspace里统一管理版本，4.8 节会正式加入。单独试验时：

```bash
cargo new thiserror-demo && cd thiserror-demo
cargo add thiserror@2
```

Cargo.toml 中会出现：

```toml
[dependencies]
thiserror = "2"
```

版本说明："2" 表示 &gt;=2.0.0, &lt;3.0.0 ，Cargo 会选其中最新的版本并写入 Cargo.lock 。thiserror 1.x 的代码在 2.x 下绝大部分不用改，主要差异见 4.5.6。

### 4.5.2【入门】第一个例子：用 thiserror 重写 StockError

```rust
use thiserror::Error;
 
#[derive(Debug, Error)]
pub enum StockError {
    #[error("商品 {product_id} 不存在")]
    ProductNotFound { product_id: u64 },
 
    #[error("商品 {product_id} 库存不足：需要 {requested}，剩余 {available}")]
    Insufficient { product_id: u64, requested: u32, available: u32 },
}
```

对比 4.4 节，二十多行的 impl Display 和 impl Error 全部消失了。逐项解读：

#\[derive(Error)\] ：生成 impl std::error::Error for StockError 。注意 Debug 仍需你自己派生，thiserror 不会替你做。

#\[error("...")\] ：写在每个变体上，生成该变体的 Display 。字符串里的{product\_id} 直接引用该变体的同名字段。

### 4.5.3【入门】#\[error\] 格式字符串的全部写法

| 写法 | 含义 | 示例 |
| --- | --- | --- |
| {field} | 按 Display 输出命名字段 | #\[error("用户 {user\_id} 不存在")\] |
| {0} / {1} | 按编号引用元组字段 | #\[error("无效邮箱：{0}")\] |
| {field:?} | 按 Debug 输出 | #\[error("未知状态 {raw:?}")\] |
| {field:.2} | 使用支持的格式参数 | #\[error("金额 {yuan:.2} 元超限")\] |
| 额外表达式参数 | 在属性参数中计算所需值 | #\[error("名称有 {len} 个字符", len = .<br>name.chars().count())\] |
| {{ / }} | 输出字面花括号 | #\[error("期望 {{id}} 格式")\] |

结构体错误也可以使用相同派生方式：

```rust
use thiserror::Error;

#[derive(Debug, Error)]
#[error("配置项 {key} 缺失")]
pub struct MissingConfig {
    pub key: &'static str,
}
 
#[derive(Debug, Error)]
pub enum NameError {
    #[error("名称过长：{len} 个字符，最多 {max} 个", len = .name.chars().count())]
    TooLong { name: String, max: usize },
}
```

### 4.5.4【进阶】#\[source\]、#\[from\] 与 transparent

这三个属性对应 4.4.4〜4.4.5 讲的错误链：

| 属性或约定 | 作用 | 示例 |
| --- | --- | --- |
| #\[source\] | 把相应字段作为错误链来源 | Io { #\[source\] cause: std::io::Error } |
| 字段名 source | 按约定识别来源错误 | Io { source: std::io::Error } |
| #\[from\] | 生成来源信息与 From 转换 | Parse(#\[from\] ParseIntError) |
| #\[error(transparent)\] | 按透明包装规则转发 Display 与来<br>源 | Other(#\[from\] OtherError) |

```rust
use std::num::ParseIntError;
use thiserror::Error;

#[derive(Debug, Error)]
pub enum StockError {
    #[error("商品 {product_id} 不存在")]
    ProductNotFound { product_id: u64 },
    #[error("商品 {product_id} 库存不足：需要 {requested}，剩余 {available}")]
    Insufficient { product_id: u64, requested: u32, available: u32 },
}

#[derive(Debug, Error)]
pub enum CreateOrderError {
    // 包装：本层说“扣减库存失败”，原因通过 source 暴露
    #[error("扣减库存失败")]
    Stock(#[from] StockError),
 
    // 包装 + 额外上下文：带上原始输入，方便排查
    #[error("购买数量 {raw:?} 格式错误")]
    InvalidQuantity { raw: String, #[source] cause: ParseIntError },
 
    // 透明：本层没有新信息，原样转发
    #[error(transparent)]
    Io(#[from] std::io::Error),
}
 
fn parse_qty(raw: &str) -> Result<u32, CreateOrderError> {
    // InvalidQuantity 没有 #[from]（因为多了 raw 字段），只能 map_err 手动构造
    raw.parse().map_err(|cause| CreateOrderError::InvalidQuantity { raw: raw.to_string(), 
       cause })
}
 
fn reserve(product_id: u64, qty: u32) -> Result<(), StockError> {
    Err(StockError::Insufficient { product_id, requested: qty, available: 2 })
}
 
fn create_order(raw_qty: &str) -> Result<(), CreateOrderError> {
    let qty = parse_qty(raw_qty)?;
 
    // StockError 经 #[from] 自动转成 CreateOrderError::Stock
    reserve(1001, qty)?;
    Ok(())
}
```

#\[from\] 的两条限制要记牢：

1. 带 #\[from\] 的变体只能有这一个字段（外加可选的 backtrace 字段）。要附带额外上下文就不能用#\[from\] ，改用 #\[source\] 加 map\_err ，正如上例的 InvalidQuantity 。

2. 同一个枚举里，同一种源错误类型只能有一个 #\[from\] ，否则会生成两个冲突的 From 实现（E0119）。

### 4.5.5【进阶】thiserror 到底生成了什么

用 cargo install cargo-expand 安装宏展开工具，然后运行 cargo expand 可以看到展开后的代码。Stock(#\[from\] StockError) 这一个变体，大致展开为：

```rust
impl std::fmt::Display for CreateOrderError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            CreateOrderError::Stock(_0) => f.write_str("扣减库存失败"),
            // ...其余变体
        }
    }
}
 
impl std::error::Error for CreateOrderError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            CreateOrderError::Stock(source) => Some(source),
            // ...
        }
    }
}
 
impl From<StockError> for CreateOrderError {
    fn from(source: StockError) -> Self {
        CreateOrderError::Stock(source)
    }
}
```

和 4.4 节手写的版本一模一样。这就是“零成本抽象”：宏只是替你打字。

### 4.5.6【精通】2.x 相对 1.x 的变化与高级用法

| 主题 | 说明 |
| --- | --- |
| 直接依赖 | 使用派生宏的包应明确声明 thiserror 依赖 |
| no\_std | 需要按所用版本配置特性；本书后端示例使用 std |
| 原始标识符 | 字段含 r#type 等名字时，按当前宏版本支持的格式引用 |
| 额外参数与字段名 | 避免歧义；按编译器提示使用明确表达式 |
| 回溯 | 稳定工具链不依赖仍受特性限制的自动回溯集成；错误链与追踪上下文分别设计 |

设计要点：错误枚举应属于明确的 crate 或模块边界；避免整个系统共用一个不断膨胀的错误枚举。

2. 公开错误枚举考虑加 #\[non\_exhaustive\] 。这样以后新增变体不算破坏性变更，外部 crate 的match 必须写 \_ 分支。RustMall 的 common 是内部库，我们不加，好让编译器在新增变体时提醒所有 match 更新。

3. 不要为了 ? 方便而滥用 #\[from\] 。如果同一种底层错误在不同调用点代表不同含义（比如两个不同的ParseIntError ：一个是数量，一个是价格），就应该用 #\[source\] 加 map\_err 分别构造，而不是一个#\[from\] 吞掉所有。

常见编译错误与解读

| 诊断 | 原因 | 修正 |
| --- | --- | --- |
| 缺少 #\[error\] | 未提供 Display 规则 | 补充 #\[error("...")\] 或透明包装 |
| 未实现 Debug | 没有派生 Debug | 添加 Debug 派生 |
| From 实现冲突 | 同一种源错误标了两次 #\[from\] | 只保留一个自动转换，其余显式 map\_err |
| transparent 字段数量不符 | 透明包装没有唯一目标 | 使用受支持的单字段包装 |
| #\[from\] 与额外上下文字段冲突 | 无法由一个源错误自动构造全部字<br>段 | 改用 #\[source\] 与显式构造 |

## 4.6 anyhow 全解

anyhow 提供一个“能装下任何错误”的类型 anyhow::Error ，外加给错误追加上下文的 Contexttrait。它和 thiserror 是同一位作者（dtolnay）写的，二者分工明确：库用 thiserror 定义具体错误，应用顶层用 anyhow 汇总并报告错误。

### 4.6.1【入门】安装与第一个例子

```rust
cargo add anyhow@1
// 等价于 Result<T, anyhow::Error>
use anyhow::Result;
 
fn read_port() -> Result<u16> {
    // VarError 自动装进 anyhow::Error
    let raw = std::env::var("APP_PORT")?;
 
    // ParseIntError 也一样
    let port: u16 = raw.trim().parse()?;
    Ok(port)
}
 
fn main() -> Result<()> {
    let port = read_port()?;
    println!("监听 {port}");
    Ok(())
}
```

不用定义任何错误类型，任何实现了 std::error::Error + Send + Sync + 'static 的错误都能?进 anyhow::Error 。

### 4.6.2【入门】Context：给错误加上“在做什么”

上面的程序如果没设置环境变量，只会打印 Error: environment variable not found ，你不知道是哪个变量。context 和 with\_context 用来补充这条信息：

```rust
use anyhow::{Context, Result};
 
fn read_port() -> Result<u16> {
    let raw = std::env::var("APP_PORT").context("读取环境变量 APP_PORT 失败")?;
    let port: u16 = raw
        .trim()
        .parse()
        .with_context(|| format!("APP_PORT 的值 {raw:?} 不是合法端口"))?;
    Ok(port)
}
```

| 方法 | 上下文何时构造 | 适用场景 |
| --- | --- | --- |
| context(message) | 调用方法前先求值 message | 静态文字或构造便宜的值 |
| with\_context(\|\| message) | 需要错误上下文时调用闭包 | 包含 format! 等较昂贵的构造 |

Context 也为 Option 提供上下文转换：对 None 增加说明后可形成 anyhow 错误；对 Some 则继续取得值。下面的片段需位于返回 anyhow::Result 的函数中，并导入 anyhow::Context。

```text
let user = users.get(&id).context("用户不存在")?;
```

### 4.6.3【进阶】四种打印格式

anyhow::Error 内部是一条错误链：最外层是最后加的 context，往里依次是更底层的原因。不同格式化方式打印不同的内容：

| 格式 | 主要内容 | 用途 |
| --- | --- | --- |
| {} | 当前层显示文字 | 向用户或日志输出当前摘要 |
| {:#} | 按链输出多层上下文 | 单行诊断 |
| {:?} | 调试报告，可包含原因链与可用回<br>溯 | main 返回错误等排查场景 |
| {:#?} | 美化的 Debug 表示 | 调试具体格式与结构 |

```text
Error: 读取配置失败
 
Caused by:
    0: APP_PORT 的值 "80a" 不是合法端口
    1: invalid digit found in string
```

这正是 4.4.5 强调“Display 和 source 二选一”的原因：如果每层 Display 都拼了下一层，Caused by列表会出现大量重复。

### 4.6.4【进阶】创建错误：anyhow!、bail!、ensure!

| 宏 | 作用 | 示例 |
| --- | --- | --- |
| anyhow! | 构造 anyhow::Error | anyhow!("未知环境 {env}") |
| bail! | 提前返回一个错误 | bail!("端口 {port} 不允许使用") |
| ensure! | 条件不成立时提前返回错误 | ensure!(port &gt;= 1024, "练习配置要求端口不<br>小于 1024") |

```rust
use anyhow::{bail, ensure, Result};

fn check_env(env: &str, port: u16) -> Result<()> {
    ensure!(port >= 1024, "练习配置要求端口 {port} 不小于 1024");
    match env {
        "dev" | "test" | "prod" => Ok(()),
        other => bail!("未知环境 {other:?}，只允许 dev/test/prod"),
    }
}
```

### 4.6.5【进阶】downcast：从 anyhow::Error 里找回具体类型

装进 anyhow::Error 后类型信息并没有丢，可以用 downcast\_ref 取回：

```rust
fn http_status(err: &anyhow::Error) -> u16 {
    if let Some(e) = err.downcast_ref::<StockError>() {
        return match e {
            StockError::ProductNotFound { .. } => 404,
            StockError::Insufficient { .. } => 409,
        };
    }
    500
}
```

| 方法 | 结果 | 用途 |
| --- | --- | --- |
| downcast\_ref::&lt;E&gt;() | Option&lt;&amp;E&gt; | 按受支持的类型转换规则借用错误 |
| downcast::&lt;E&gt;() | Result&lt;E, anyhow::Error&gt; | 尝试取走特定错误，失败时保留原错误 |
| chain() | 来源链迭代器 | 逐层查看或搜索来源 |
| root\_cause() | 最底层原因的引用 | 查看链末端原因 |

如果业务逻辑需要频繁按错误种类分支，优先在该边界使用具体错误枚举，而不是把大量 downcast 当作常规控制流程。

### 4.6.6【精通】thiserror 还是 anyhow：分层决策

| 位置 | 通常选择 | 理由 |
| --- | --- | --- |
| 可复用库或领域边界 | 具体错误枚举 | 调用方需要匹配错误种类 |
| 服务启动流程 | anyhow::Result | 汇总上下文并在启动失败时退出 |
| 迁移工具与 CLI | anyhow::Result | 便于输出可诊断报告 |
| HTTP 错误边界 | 实现 IntoResponse 的具体错误类<br>型 | 稳定映射状态码与响应协议 |
| 未知内部故障 | 由具体边界错误包装内部报告 | 对外控制信息，内部保留诊断 |

```rust
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error(transparent)]
    // 4.8 节定义，按 kind 映射 4xx
    Domain(#[from] DomainError),
    #[error("服务器内部错误")]
    // 对外只说“内部错误”，详细链写进日志
    Internal(#[from] anyhow::Error),
}
```

性能与实现细节：anyhow::Error 只有一个指针大小（8 字节），内部把错误和 vtable 一起放在堆上。所以 Result&lt;T, anyhow::Error&gt; 很小，传递很快；代价是创建错误时有一次堆分配。错误路径本来就是少数情况，这点开销可以忽略。还有一点：anyhow::Error 自身没有实现 std::error::Error（为了避免和 From&lt;E: Error&gt; 冲突），需要时用.into\_boxed\_dyn\_error() 或通过 AsRef&lt;dyn Error&gt; 转换。

## 4.7 panic 的正确用法

预期内的业务失败应通过 Result 返回，让调用方决定怎样回复用户或重试。panic 用于指出程序进入了无法按既定逻辑继续处理的状态。它不等于 HTTP 500，也不是输入校验工具：用户购买数量写错、商品不存在或库存不足，都不应该直接触发 panic。

本节修复原第 179-182 页的错列表格，并补充原文过于绝对的说法。下面分别讨论“什么会触发panic”“发生后影响哪里”与“共享数据能否继续使用”，不要把这三个问题混成一个结论。

### 4.7.1 【入门】哪些写法可能触发 panic

对 Result::Err 或 Option::None 调用 unwrap、expect，会触发 panic。expect 允许补充失败说明，但不会把失败变成可恢复错误。处理外部输入时，通常应使用 match、?、ok\_or\_else 等方法把错误交给调用方。

使用 v\[i\] 访问不存在的元素会 panic。字符串使用 &amp;s\[a..b\] 切片时，越界或边界不在 UTF-8 字符边界上也会 panic。可用 v.get(i) 或 s.get(a..b) 得到 Option，再明确处理不存在或不合法的情况。

HashMap 的索引 map\[&amp;key\] 在键不存在时会 panic；map.get(&amp;key) 则返回 Option。整数除数为零会 panic，某些有符号整数除法还存在溢出情况；checked\_div 能把无法表示的结果变成 None，随后由业务代码选择错误。

普通整数加减乘的溢出行为受构建配置中的 overflow-checks 影响。常见默认配置是调试构建检查、发布构建不检查，但不能把这个默认习惯写成语言中永远不变的规则。金额和库存应使用 checked\_add、checked\_sub 等显式方法，不依赖构建模式改变业务含义。

RefCell::borrow\_mut 在已有冲突借用时会 panic；try\_borrow\_mut 可以返回错误。Mutex::lock 本身返回 Result；对中毒结果再 unwrap 才会继续触发 panic。不要把“锁等待”“锁中毒”和“unwrap中毒结果”当成同一个动作。

todo!、unimplemented! 和 unreachable! 执行到时都会 panic。assert! 只有条件为假时才 panic，assert\_eq! 和 assert\_ne! 也仅在相应比较不成立时 panic。原文将这些宏统一写成“执行到即 panic”并不准确。

### 4.7.2 【入门】unwrap 与 expect 的使用边界

第一类是测试。测试里的断言或 unwrap 失败，通常意味着本次测试失败；但这不代表把相同写法放到请求处理代码也合适。测试要验证的是业务行为，不是要求所有业务错误都终止执行。

第二类是能够说明的不变量，例如程序中写死的合法监听地址。使用 expect 时，把说明写成“为什么这里应当成功”，便于未来修改代码的人判断这个前提是否还成立。

```rust
use std::net::SocketAddr;

fn main() {
    let addr: SocketAddr = "127.0.0.1:8080"
        .parse()
        .expect("硬编码的监听地址必须是合法 SocketAddr");
    println!("{addr}");
}
```

第三类是服务启动时的关键失败。配置缺失、数据库连接失败或端口绑定失败，可以使启动流程退出；更清楚的写法往往是 main 返回 Result，并增加上下文，而不是在许多位置散布 unwrap。启动失败与已经开始服务后的单次请求失败，有不同的恢复边界。

不要把 expect 的文字当作失败不会发生的证明。只有前置校验、类型约束或明确的不变量才能支撑这个判断。对于来自环境变量或用户输入的地址，应返回解析错误，而不是套用上面的硬编码示例。

### 4.7.3 【进阶】请求处理中的 panic 会影响哪里

在 panic=unwind 且运行时能在相应任务边界捕获展开的情况下，Tokio 任务中的 panic 通常使该任务失败；等待对应 JoinHandle 时，可以观察 JoinError 并判断它是否来自 panic。不能因此推导出“每个HTTP 请求都固定对应一个独立 Tokio 任务”。请求、连接、HTTP/2 流和服务执行边界取决于服务器实现。

如果没有适合的捕获与响应转换，客户端可能看到连接中断、流错误或其他传输失败，而不是格式统一的 500 JSON。即使进程继续运行，共享状态也可能已被部分修改，所以“其他请求完全不受影响”同样不是普遍保证。

CatchPanicLayer 可以在它覆盖的服务调用范围内把捕获到的展开转换成响应。它不能捕获 panic=abort 导致的进程终止，也不能被描述为覆盖任意后台任务、所有响应体错误或进程中的一切 panic。要结合实际中间件位置和库版本验证边界。tower-http：CatchPanic

对于 panic=abort、双重 panic 或运行时之外的致命故障，整个进程仍可能退出。服务需要健康检查、重启策略、幂等和持久化恢复；不能因为选了 unwind 就省略这些设计。

### 4.7.4 【精通】锁中毒与断言：先看清数据是否仍然有效

标准库 Mutex 的中毒机制是一种提醒：持锁期间发生的 panic 可能破坏了受保护数据的不变量。lock 返回 PoisonError 时，并不代表数据必然损坏，也不代表可以无条件继续使用。中毒是建议性机制，某些特殊情况还可能无法被识别，不能把它当成内存安全或业务一致性的证明。Rust 标准库：Mutex 的中毒机制

处理方式一：拒绝继续使用当前数据。若没有可靠恢复办法，应把问题传到明确的故障边界，停止相关操作并记录原因。lock().expect("共享状态已中毒，当前操作不能安全继续") 会继续 panic；在业务服务里，也可以把中毒转换成明确的内部错误，由请求边界统一处理。

处理方式二：取得数据，检查并修复后继续。PoisonError::into\_inner() 只取回保护数据的 guard，既不会自动修复数据，也不会自动清除中毒标记。只有恢复逻辑确实重建了不变量，才考虑 clear\_poison。不能仅凭“它只是计数器或缓存”就认定更新一半也无害。

下面的例子故意让工作线程在持锁时 panic，然后由主线程将练习计数器恢复到预先约定的安全值。归零是这个实验明确选择的恢复策略，不是订单、金额或真实库存的一般恢复方案。

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let count = Arc::new(Mutex::new(0_i32));
    let worker_count = Arc::clone(&count);

    let worker = thread::spawn(move || {
        let mut guard = worker_count.lock().unwrap();
        *guard = 10;
        panic!("实验：模拟持锁期间失败");
    });

    assert!(worker.join().is_err());
    assert!(count.is_poisoned());

    let mut guard = match count.lock() {
        Ok(guard) => guard,
        Err(poisoned) => {
            let mut guard = poisoned.into_inner();
            *guard = 0;
            count.clear_poison();
            guard
        }
    };
    *guard += 1;
    assert_eq!(*guard, 1);
    drop(guard);
    assert!(!count.is_poisoned());
}
```

处理方式三：选择符合并发模型的其他锁。parking\_lot::Mutex 与 tokio::sync::Mutex 没有标准库Mutex 的同一种中毒策略，但换锁不会自动撤销已发生的部分写入。异步锁主要解决等待方式和持锁跨await 的问题，不是数据一致性修复工具。

再看断言。assert!(cond)、assert\_eq!(a,b)、assert\_ne!(a,b) 用来检查程序应当维持的不变量；默认调试和发布构建都会执行相应检查。不要把有副作用的必要业务操作藏进 debug\_assert!，因为它是否执行检查受 debug\_assertions 配置影响。

debug\_assert! 默认在非优化构建启用，常见发布配置中不启用；也可以通过编译配置显式改变。它适合辅助开发者检查较昂贵的不变量，而不是做认证、参数校验或必须执行的库存扣减。Rust 标准库：debug\_assert!

例如用户输入 qty=0，应返回校验错误。若写成 assert!(qty&gt;0)，就把一个正常可预见的输入问题变成了程序 panic。正确逻辑是先验证数量，再进入领域计算；即使以后关闭调试断言，业务约束仍然必须成立。

### 4.7.5 【精通】panic 钩子：保留定位信息，不手拼 JSON

panic 钩子用于记录 panic 发生时的消息与位置。它不是恢复点，也不能把 panic 变成 Result。安装自定义钩子时，可以保存原钩子，再在记录后调用它，保留默认的定位与回溯行为。

本例只使用标准库输出一条普通文本诊断。原文通过拼接字符串制造 JSON，遇到消息中包含引号、换行或反斜杠时可能得到非法 JSON；这里移除这种容易被复制到工程中的写法。第 15 章再用日志框架进行结构化记录。

```rust
fn install_panic_hook() {
    let default_hook = std::panic::take_hook();
    std::panic::set_hook(Box::new(move |info| {
        let location = info
            .location()
            .map(|location| format!("{}:{}", location.file(), location.line()))
            .unwrap_or_else(|| "未知位置".to_owned());
        let message = info
            .payload()
            .downcast_ref::<&str>()
            .copied()
            .or_else(|| info.payload().downcast_ref::<String>().map(String::as_str))
            .unwrap_or("非字符串 panic 信息");

        eprintln!("PANIC at {location}: {message}");
        default_hook(info);
    }));
}

fn main() {
    install_panic_hook();
    panic!("实验：消息里可以包含引号 \" 和反斜杠 \\");
}
```

运行此程序预期以失败状态退出，因为最后一行有意触发 panic。先看到自定义的 PANIC 诊断，再看到默认钩子信息，是本实验要观察的现象。不要把程序退出误判成“日志钩子没有生效”。

钩子本身应尽量简单，避免再次 panic、无限等待或获取可能已经被当前线程持有的锁。日志记录成功也不代表部分业务写入已被修复；后端恢复仍需要事务、幂等和可追溯事实。

常见错误与定位：clippy::unwrap\_used 提醒你检查业务代码中的 unwrap；不要机械替换成同样会panic 的 expect。clippy::expect\_fun\_call 提醒你可能在成功路径也构造了说明字符串，可改成按需构造的错误处理。库存减法失败时，应检查业务数量与 checked\_sub 的结果，不能只依靠发布模式的溢出设置。

本节练习：第一，找出自己的 unwrap，分别说明它依赖哪条前提；来自外部输入的失败改走 Result。第二，运行中毒实验，去掉 clear\_poison 后观察标记仍然存在；再说明为什么取得 guard 不等于恢复一致性。第三，运行 panic 钩子示例，核对两类诊断的顺序。第四，解释为什么鉴权和库存副作用不能放在 debug\_assert! 的条件表达式中。

//! RustMall 领域层统一错误类型。
//!
//! - [`ValidationError`]：输入校验失败的具体原因。
//! - [`DomainError`]：领域层对外暴露的唯一错误类型，所有领域函数都返回 [`DomainResult`]。
//! - [`ErrorKind`]：与传输协议无关的错误分类，HTTP 层和 gRPC 层据此映射状态码。

use thiserror::Error;

use crate::order::OrderError;

/// 输入校验失败的具体原因。
///
/// 字段名用 `&'static str`：字段名都是代码里写死的字面量，
/// 这样既不分配内存，又满足 `'static` 约束（见 4.4.6）。
#[derive(Debug, Clone, PartialEq, Eq, Error)]
pub enum ValidationError {
    #[error("字段 `{field}` 不能为空")]
    Empty { field: &'static str },

    #[error("字段 `{field}` 长度应为 {min}〜{max} 个字符，实际为 {actual} 个")]
    Length {
        field: &'static str,
        min: usize,
        max: usize,
        actual: usize,
    },
    #[error("字段 `{field}` 的值 {value} 超出范围 {min}〜{max}")]
    OutOfRange {
        field: &'static str,
        value: i64,
        min: i64,
        max: i64,
    },

    #[error("字段 `{field}` 格式不正确：{reason}")]
    Format { field: &'static str, reason: String },
}

/// 与传输协议无关的错误分类。
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum ErrorKind {
    /// 调用方传入的数据不合法。
    InvalidInput,
    /// 要操作的对象不存在。
    NotFound,
    /// 请求本身合法，但与当前业务状态冲突。
    Conflict,
    /// 服务端自身的问题。
    Internal,
}

impl ErrorKind {
    /// 稳定的机器可读错误码，会出现在 API 响应体里，发布后不要修改。
    pub const fn code(self) -> &'static str {
        match self {
            ErrorKind::InvalidInput => "INVALID_INPUT",
            ErrorKind::NotFound => "NOT_FOUND",
            ErrorKind::Conflict => "CONFLICT",
            ErrorKind::Internal => "INTERNAL",
        }
    }
}

/// 领域层统一错误。
#[derive(Debug, Error)]
pub enum DomainError {
    /// 输入校验失败。本层没有新信息，透明转发。
    #[error(transparent)]
    Validation(#[from] ValidationError),

    /// 订单状态机拒绝了某个操作。
    #[error(transparent)]
    Order(#[from] OrderError),

    #[error("{entity} {id} 不存在")]
    NotFound { entity: &'static str, id: String },

    #[error("商品 {product_id} 库存不足：需要 {requested}，剩余 {available}")]
    InsufficientStock {
        product_id: String,
        requested: u32,
        available: u32,
    },

    /// 不应该发生、但又不值得 panic 的情况。对外只显示“内部错误”，详情进日志。
    #[error("内部错误：{0}")]
    Internal(String),
}

impl DomainError {
    /// 构造“不存在”错误的便捷函数，`id` 接受任何能显示的类型。
    pub fn not_found(entity: &'static str, id: impl std::fmt::Display) -> Self {
        DomainError::NotFound {
            entity,
            id: id.to_string(),
        }
    }

    /// 返回错误分类，传输层据此决定状态码。
    pub fn kind(&self) -> ErrorKind {
        match self {
            DomainError::Validation(_) => ErrorKind::InvalidInput,
            DomainError::Order(OrderError::InvalidInput(_) | OrderError::AmountOverflow) => {
                ErrorKind::InvalidInput
            }
            DomainError::Order(OrderError::IllegalTransition { .. })
            | DomainError::InsufficientStock { .. } => ErrorKind::Conflict,
            DomainError::NotFound { .. } => ErrorKind::NotFound,
            DomainError::Internal(_) => ErrorKind::Internal,
        }
    }
}
/// 领域函数的统一返回类型。
pub type DomainResult<T> = Result<T, DomainError>;

逐段讲解：

ValidationError 派生了 Clone, PartialEq, Eq ：校验错误只含简单数据，可以比较，测试里能直接assert\_eq! 。DomainError 没有派生它们，因为将来会包装数据库错误等不可比较、不可克隆的类型。

ErrorKind 与 HTTP 解耦：common 不依赖 Axum，不认识状态码。后面 Axum 章节的 AppError 会写 ErrorKind::NotFound =&gt; StatusCode::NOT\_FOUND ；gRPC 章节则映射成 tonic::Code::NotFound 。同一个领域错误，两种协议各自映射。

code() 是 const fn ：可以在编译期求值。错误码是给前端和其他服务做程序判断的，所以要稳定；Display 文案是给人看的，可以随时改。

两个 transparent 变体：按 4.4.5 的规则，DomainError 在这两处没有补充任何信息，只是换了个类型，所以透明转发，打印错误链时不会出现重复。

ID 用 String 存储：NotFound 和 InsufficientStock 要能装下用户、商品、订单任何一种 ID，用String 最简单。你也可以把 product\_id 改成第 3 章的 ProductId ，前提是给它实现 Display 。

最后一个测试只有类型检查：assert\_bounds::&lt;DomainError&gt;() 能编译通过就说明满足 Send+Sync + 'static 。以后谁往错误里加了 Rc 之类的字段，这个测试会编译失败，提前暴露问题。

### 4.8.5 第四步：新建 common/src/validate.rs

完整内容如下：

````rust
//! 通用输入校验函数。
//!
//! 每个函数只检查一件事，失败时返回带字段名的 [`ValidationError`]。
//! 多个检查用 `?` 串联，遇到第一个失败就返回。

use crate::error::ValidationError;

/// 去掉首尾空白后不能为空。
pub fn non_empty(field: &'static str, value: &str) -> Result<(), ValidationError> {
    if value.trim().is_empty() {
        Err(ValidationError::Empty { field })
    } else {
        Ok(())
    }
}

/// 按字符数（而不是字节数）检查长度，闭区间 `[min, max]`。
///
/// ```
/// use common::validate::char_len;
/// assert!(char_len("name", "机械键盘", 1, 4).is_ok()); // 4 个字符，12 个字节
/// ```
pub fn char_len(
    field: &'static str,
    value: &str,
    min: usize,
    max: usize,
) -> Result<(), ValidationError> {
    let actual = value.chars().count();
    if (min..=max).contains(&actual) {
        Ok(())
    } else {
        Err(ValidationError::Length {
            field,
            min,
            max,
            actual,
        })
    }
}

/// 整数范围检查，闭区间 `[min, max]`。
pub fn in_range(
    field: &'static str,
    value: i64,
    min: i64,
    max: i64,
) -> Result<(), ValidationError> {
    if (min..=max).contains(&value) {
        Ok(())
    } else {
        Err(ValidationError::OutOfRange {
            field,
            value,
            min,
            max,
        })
    }
}

/// 只允许 ASCII 字母、数字、`-` 和 `_`，用于 SKU 编码等。
/// 空字符串会通过本检查，需要时先调用 [`non_empty`]。
pub fn ascii_code(field: &'static str, value: &str) -> Result<(), ValidationError> {
    let is_allowed = |c: char| c.is_ascii_alphanumeric() || c == '-' || c == '_';
    match value.chars().find(|&c| !is_allowed(c)) {
        None => Ok(()),
        Some(bad) => Err(ValidationError::Format {
            field,
            reason: format!("包含不允许的字符 {bad:?}"),
        }),
    }
}

mod tests {

讲解要点：

长度按字符计：第 1 章讲过 Rust 字符串是 UTF-8，一个汉字占 3 个字节。用户眼里“机械键盘”是 4个字，len() 却是 12。面向用户的长度限制必须用 chars().count() 。

(min..=max).contains(&amp;x) ：比 x &gt;= min &amp;&amp; x &lt;= max 更不容易写错边界，clippy 的 manual\_range\_contains 也会建议这种写法。

find(|&amp;c| ...) ：闭包参数用 &amp;c 模式直接解构出 char （第 3 章 3.5 节的引用匹配规则）。

文档测试：char\_len 上方 /// 里的代码块会被 cargo test 当作测试运行，所以它既是文档又是测试。

为什么校验函数返回 ValidationError 而不是 DomainError ：函数只可能产生校验错误，签名就应该精确地说明这一点。调用方需要 DomainError 时，? 会经 #\[from\] 自动转换，见 error.rs 的第一个测试。

//! 订单领域模型与订单状态机。

use crate::ids::{OrderId, ProductId, UserId};
use crate::money;
use crate::quantity::Quantity;

/// 订单的简单状态，用于存储到数据库和对外展示。
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum OrderStatus {
    Pending,
    Paid,
    Shipped,
    Completed,
    Cancelled,
}

impl OrderStatus {
    /// 全部状态，便于遍历和测试。
    pub const ALL: [OrderStatus; 5] = [
        OrderStatus::Pending,
        OrderStatus::Paid,
        OrderStatus::Shipped,
        OrderStatus::Completed,
        OrderStatus::Cancelled,
    ];

    /// 数据库中存储的字符串。
    pub fn as_str(self) -> &'static str {
        match self {
            Self::Pending => "pending",
            Self::Paid => "paid",
            Self::Shipped => "shipped",
            Self::Completed => "completed",
            Self::Cancelled => "cancelled",
        }
    }

    /// 从数据库字符串解析；未知值返回 `None`，由调用方决定如何报错。
    pub fn parse(s: &str) -> Option<Self> {
        match s {
            "pending" => Some(Self::Pending),
            "paid" => Some(Self::Paid),
            "shipped" => Some(Self::Shipped),
            "completed" => Some(Self::Completed),
            "cancelled" => Some(Self::Cancelled),
            _ => None,
        }
    }

    /// 是否为终态（不能再发生任何转移）。
    pub fn is_terminal(self) -> bool {
        matches!(self, Self::Completed | Self::Cancelled)
    }
}

/// 订单的完整运行时状态：每个状态携带且只携带它需要的数据。
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum OrderState {
    Pending,
    Paid { paid_at: i64 },
    Shipped { paid_at: i64, tracking_no: String },
    Completed { paid_at: i64, tracking_no: String },
    Cancelled { reason: String },
}
impl OrderState {
    pub fn status(&self) -> OrderStatus {
        match self {
            Self::Pending => OrderStatus::Pending,
            Self::Paid { .. } => OrderStatus::Paid,
            Self::Shipped { .. } => OrderStatus::Shipped,
            Self::Completed { .. } => OrderStatus::Completed,
            Self::Cancelled { .. } => OrderStatus::Cancelled,
        }
    }
}

/// 订单操作可能出现的错误。
#[derive(Debug, Clone, PartialEq, Eq, thiserror::Error)]
pub enum OrderError {
    /// 输入不合法
    #[error("订单参数不合法：{0}")]
    InvalidInput(&'static str),
    /// 金额计算溢出或超过单笔上限
    #[error("订单金额溢出或超过单笔上限")]
    AmountOverflow,
    /// 当前状态不允许该操作
    #[error("订单当前为 {} 状态，不允许执行 {action}", .from.as_str())]
    IllegalTransition {
        from: OrderStatus,
        action: &'static str,
    },
}

/// 订单。
///
/// ```
/// use common::ids::{OrderId, ProductId, UserId};
/// use common::order::{Order, OrderStatus};
/// use common::quantity::Quantity;
///
/// let qty = Quantity::try_new(2).expect("示例数量应当合法");
/// let mut order = Order::new(OrderId::new(1), UserId::new(7), ProductId::new(42), 19_900,
///     qty).expect("示例订单应当合法");
/// assert_eq!(order.total_cents(), 39_800);
/// order.pay(1_760_000_000).expect("待支付订单应允许支付");
/// assert_eq!(order.status(), OrderStatus::Paid);
/// ```
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Order {
    id: OrderId,
    user_id: UserId,
    product_id: ProductId,
    quantity: Quantity,
    unit_price_cents: i64,
    total_cents: i64,
    state: OrderState,
}

impl Order {
    /// 创建待支付订单，自动计算总价。
    pub fn new(
        id: OrderId,
        user_id: UserId,
        product_id: ProductId,
        unit_price_cents: i64,
        quantity: Quantity,
    ) -> Result<Self, OrderError> {
        if unit_price_cents < 0 {
            return Err(OrderError::InvalidInput("单价不能为负数"));
        }
        let total_cents = money::line_total(unit_price_cents, i64::from(quantity.get()))
            .ok_or(OrderError::AmountOverflow)?;
        Ok(Self {
            id,
            user_id,
            product_id,
            quantity,
            unit_price_cents,
            total_cents,
            state: OrderState::Pending,
        })
    }

    // ---------- 只读访问 ----------

    pub fn id(&self) -> OrderId {
        self.id
    }

    pub fn user_id(&self) -> UserId {
        self.user_id
    }

    pub fn product_id(&self) -> ProductId {
        self.product_id
    }

    pub fn quantity(&self) -> Quantity {
        self.quantity
    }
    pub fn unit_price_cents(&self) -> i64 {
        self.unit_price_cents
    }

    pub fn total_cents(&self) -> i64 {
        self.total_cents
    }

    pub fn state(&self) -> &OrderState {
        &self.state
    }

    pub fn status(&self) -> OrderStatus {
        self.state.status()
    }

    // ---------- 状态转移 ----------

    /// 支付：待支付 → 已支付。
    pub fn pay(&mut self, paid_at: i64) -> Result<(), OrderError> {
        match self.state {
            OrderState::Pending => {
                self.state = OrderState::Paid { paid_at };
                Ok(())
            }
            _ => Err(self.illegal("pay")),
        }
    }

    /// 发货：已支付 → 已发货。
    pub fn ship(&mut self, tracking_no: &str) -> Result<(), OrderError> {
        let tracking_no = tracking_no.trim();
        if tracking_no.is_empty() {
            return Err(OrderError::InvalidInput("快递单号不能为空"));
        }
        match self.state {
            OrderState::Paid { paid_at } => {
                self.state = OrderState::Shipped {
                    paid_at,
                    tracking_no: tracking_no.to_string(),
                };
                Ok(())
            }
            _ => Err(self.illegal("ship")),
        }
    }

    /// 确认收货：已发货 → 已完成。快递单号从旧状态“搬”到新状态，不复制。
    pub fn complete(&mut self) -> Result<(), OrderError> {
        // 先用占位值把旧状态整体取出，拿到其中 String 的所有权
        match std::mem::replace(&mut self.state, OrderState::Pending) {
            OrderState::Shipped {
                paid_at,
                tracking_no,
            } => {
                self.state = OrderState::Completed {
                    paid_at,
                    tracking_no,
                };
                Ok(())
            }
            other => {
                // 不允许转移：把旧状态原样放回
                self.state = other;
                Err(self.illegal("complete"))
            }
        }
    }

    /// 取消：待支付或已支付 → 已取消。
    pub fn cancel(&mut self, reason: &str) -> Result<(), OrderError> {
        let reason = reason.trim();
        if reason.is_empty() {
            return Err(OrderError::InvalidInput("取消原因不能为空"));
        }
        match self.state {
            OrderState::Pending | OrderState::Paid { .. } => {
                self.state = OrderState::Cancelled {
                    reason: reason.to_string(),
                };
                Ok(())
            }
            _ => Err(self.illegal("cancel")),
        }
    }

    fn illegal(&self, action: &'static str) -> OrderError {
        OrderError::IllegalTransition {
            from: self.status(),
            action,
        }
    }
}

要点：

.from.as\_str() 是 4.5.3 讲过的“额外参数”写法：格式字符串后面的表达式里用 .字段名访问字段。这里调用第 3 章为状态枚举写的 as\_str 方法，因为 OrderStatus 没有实现 Display 。如果你的状态类型实现了 Display ，直接写 {from} 即可。

第 3 章没有手写 OrderError 的 Display 实现；这里由 thiserror 生成。重复添加手写实现会产生E0119 冲突。

这里的字段是 OrderStatus 和 &amp;'static str，满足 Send + Sync + 'static ，所以 error.rs 的最后一个测试能通过。

### 4.8.8 第七步：新建 common/examples/error\_report.rs

这个示例演示应用层怎样用 anyhow 汇总 common 的错误并打印完整错误链。完整内容如下：

文件：rustmall/common/examples/error\_report.rs （本节修改后的完整内容）

```rust
//! 运行：cargo run -p common --example error_report

use anyhow::{Context, Result};
use common::validate;

/// 把用户输入的价格字符串解析为“分”，并做范围校验。
fn load_price(raw: &str) -> Result<i64> {
    let cents: i64 = raw
        .trim()
        .parse()
        .with_context(|| format!("无法把 {raw:?} 解析为价格（单位：分）"))?;
    // ValidationError 实现了 Error + Send + Sync + 'static，可以直接 ? 进 anyhow::Error
    validate::in_range("price_cents", cents, 1, 100_000_000)?;
    Ok(cents)
}
fn main() -> Result<()> {
    for raw in ["1999", "abc", "0"] {
        match load_price(raw).context("读取商品价格失败") {
            Ok(cents) => println!("{raw} -> {cents} 分"),
            Err(e) => println!("{raw} -> 错误：{e:#}"),
        }
    }
    Ok(())
}
```

预期输出：

```text
1999 -> 1999 分
abc -> 错误：读取商品价格失败: 无法把 "abc" 解析为价格（单位：分）: invalid digit found in string
0 -> 错误：读取商品价格失败: 字段 `price_cents` 的值 0 超出范围 1〜100000000
```

对照输出理解错误链：{:#} 从外到内用 : 连接每一层。第二行有三层：context 加的外层、with\_context 加的中间层、ParseIntError 本身。第三行只有两层，因为 ValidationError 是最底层，没有 source 。

## 本章小结与综合练习

本章的核心结论：可预料的失败写进返回类型 Result ，用 ? 向上传播；库用 thiserror 定义可 match的具体错误，应用顶层用 anyhow 汇总报告；panic 只留给 bug。

| 知识点 | 要点 | 小节 |
| --- | --- | --- |
| Result 与 panic | 可预期失败通过返回类型处理；<br>panic 边界需要明确 | 4.1 |
| 组合子 | 区分变换、串联和容器互转 | 4.2 |
| ? | 传播失败，并满足相应转换条件 | 4.3 |

| 知识点 | 要点 | 小节 |
| --- | --- | --- |
| 自定义错误 | Debug、Display、Error 与来源链 | 4.4 |
| thiserror | 在编译期生成重复实现 | 4.5 |
| anyhow | 在应用边界汇总错误上下文 | 4.6 |
| panic 纪律 | 明确捕获与恢复边界，不以断言校<br>验外部输入 | 4.7 |
| 项目文件 | DomainError、ErrorKind 与校验<br>函数 | 4.8 |

综合练习

1. 注册校验：在 validate.rs 中新增 pub fn email(field: &amp;'static str, value: &amp;str)-&gt;Result&lt;(), ValidationError&gt; ，要求恰好一个 @ 、@ 两侧非空、域名部分含. ，失败时 reason 写明具体哪条不满足。为它写至少 4 个测试。

2. 库存扣减：在 common 里写 pub fn reserve(stock: u32, requested:u32,product\_id:&amp;str) -&gt; DomainResult&lt;u32&gt; ，返回扣减后的库存。requested 为 0 时返回 ValidationError::OutOfRange ，库存不足返回 DomainError::InsufficientStock 。要求用 checked\_sub ，不能出现可能溢出的减法。

3. 错误码表：写一个测试，遍历 ErrorKind 的全部变体并断言 code() 两两不同。思考：以后新增变体时，怎样保证这个测试不会漏掉新变体？（提示：用一个不带 \_ 分支的 match 构造变体列表。）

4. 错误链报告：把 4.4.4 的 report 函数改造成泛型的 fn report(err:&amp;(dynstd::error::Error+ 'static)) -&gt; String ，用它打印一个 DomainError::Order(...) ，再用 anyhow 的 {:?} 打印同一个错误，对比两者的输出。

5. 思考题：DomainError::Internal 的 Display 里包含了详细信息，但 4.6.6 说对外只显示“内部错误”。应该在哪一层把详细信息挡住？为什么不在 DomainError 这一层就把 Display 写成固定的“内部错误”？（这道题的答案会在 Axum 章节实现 IntoResponse 时揭晓。）

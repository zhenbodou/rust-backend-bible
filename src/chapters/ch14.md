# 第 14 章 SQLx 详解

第 13 章我们在 psql 里设计并验证了 RustMall 的全部表结构。本章让 Rust 程序真正和 PostgreSQL 对话：连接池、执行 SQL、把结果行变成 Rust 结构体、事务、迁移、把数据库错误翻译成业务错误。章末项目把 monolith 的商品接口从内存仓储切换到 PostgreSQL，并把“删除商品”改成“下架商品”。

版本说明：本章基于 SQLx 0.8（写作时的稳定版本）。SQLx 的 API 多年来相当稳定，但 Cargo feature 的名称（尤其是 TLS 相关的几个）在小版本之间改过名。如果你安装到更新的版本、编译器提示某个 feature 不存在，以 docs.rs 上 sqlx 页面的 “Feature flags” 列表为准。

本章用到的 crate 与工具：

| 名称 | 作用 | 首次出现 |
| --- | --- | --- |
| sqlx | 异步 SQL 工具包：连接池、查询、事务、迁移、编译期检查 | 14.2 |

## 14.1 SQLx 是什么，为什么选它

### 14.1.1 【入门】程序访问数据库的四个层次

不管用什么语言，程序访问关系型数据库都绕不开四件事：

1. 建立连接：通过 TCP 与数据库服务器握手、认证（第 13.2 节的连接字符串里那些信息）。

2. 发送 SQL、接收结果：结果是一行一行的数据，每列都有数据库类型（BIGINT、TEXT、TIMESTAMPTZ……）。

3. 类型转换：把数据库类型转换为语言里的类型，例如 BIGINT → i64、TEXT → String、可空列→ Option&lt;T&gt;。

4. 管理连接：连接的建立很贵（一次握手加认证要几毫秒），所以要复用--这就是“连接池”。

不同的 Rust 库把这四件事做到不同的抽象程度：

| 库 | 定位 | 你写什么 | 特点 |
| --- | --- | --- | --- |
| tokio- postgres | 底层驱动 | 原生 SQL | 只做协议，不带连接池（要配 deadpool-postgres 或bb8） |
| sqlx | SQL 工具包 | 原生 SQL | 自带连接池、迁移；可以在编译期连接数据库检查 SQL |

| 库 | 定位 | 你写什么 | 特点 |
| --- | --- | --- | --- |
| diesel | ORM + 查询构建器 | Rust DSL | 类型安全极强；以同步为主（异步需 diesel-async），学习曲线陡 |
| sea-orm | 异步 ORM | 实体 + 链式API | 基于 sqlx，适合 CRUD 很多的管理后台 |

### 14.1.2 【进阶】本书选择 SQLx 的理由

写的就是 SQL。第 13 章学的 JOIN、窗口函数、FOR UPDATE、ON CONFLICT 可以原样使用，不用再学一套 DSL，也不会遇到“ORM 生成的 SQL 不是我想要的”这类问题。后端工程师迟早要直接面对 SQL 和执行计划，SQLx 让这件事从第一天就发生。

纯异步、与 Tokio 无缝配合。查询返回 Future，在 Axum 处理函数里直接 .await。

编译期检查（14.5 节）：sqlx::query! 宏在编译时连接数据库，让 PostgreSQL 自己解析你的SQL，列名写错、类型不匹配会变成编译错误。

自带迁移（14.7 节）与 测试支持（#[sqlx::test] 为每个测试创建独立数据库，14.9.6 节）。

生态位置：sea-orm 底层就是 sqlx，学会 sqlx 以后切换到 ORM 也毫无障碍。

### 14.1.3 【精通】SQLx 的内部结构

SQLx 由几个 crate 组成，你只需要依赖门面 crate sqlx：

| crate | 内容 |
| --- | --- |
| sqlx-core | 与数据库无关的抽象：Pool、Executor、Encode/ Decod e、Error |
| sqlx-postgres / sqlx-mysql / sqlx-sqlite | 各数据库的协议实现 |
| sqlx-macros | query!、#[derive(FromRow)]、#[sqlx::test]、mig rate! 等宏 |

PostgreSQL 驱动是纯 Rust 实现的线协议（wire protocol），不依赖 C 语言的 libpq，所以交叉编译、做静态链接的 Docker 镜像（第 20 章）都很省心。

SQLx 发给 PostgreSQL 的查询默认走扩展查询协议（Parse / Bind / Execute 三步）：SQL 文本与参数分开传输，参数永远不会被拼进 SQL，这从协议层面杜绝了 SQL 注入（14.4.3 节）。每个连接还会缓存已经解析过的语句（prepared statement），同一条 SQL 第二次执行时跳过解析。

2. 对比 sqlx::query! 的编译期检查与“写完 SQL 跑测试才发现错误”，各有什么代价？

### 14.2.2 【入门】在 Cargo.toml 中声明 sqlx

练习时可以新建一个独立的二进制项目（不要放在 rustmall 里）：
```bash

```

```toml

    "macros", "migrate"] }
```

### 14.2.3 【进阶】feature 逐项说明

SQLx 几乎所有能力都靠 feature 开关，选错是新手最常见的编译错误来源：

| feature | 含义 | RustMall 是否开启 |
| --- | --- | --- |
| runtime-tokio | 使用 Tokio 运行时（另一个选项是 runtime-async-std，二选一） | 是 |
| postgres | PostgreSQL 驱动（另有 mysql、sqlite） | 是 |
| macros | query! 系列宏、#[derive(FromRow)]、#[s qlx::test] | 是 |
| migrate | 迁移：sqlx::migrate! 宏与 Migrator | 是 |
| chrono | TIMESTAMPTZ ↔ chrono::DateTime&lt;Utc&gt; 等时间类型映射 | 订单章节开启 |

| feature | 含义 | RustMall 是否开启 |
| --- | --- | --- |
| time | 同上，但使用 time crate（与 chrono 二选一即可） | 否 |
| uuid | UUID ↔ uuid::Uuid | 订单章节开启 |
| json | JSON/ JSONB ↔ serde_json::Value 与sq lx::types::Json&lt;T&gt; | 按需 |
| rust_decimal / bigdec imal | NUMERIC ↔ 十进制数 | 否（金额用“分”存BIGIN T） |
| tls-rustls、tls- nat ive-tls 等 | 与数据库之间使用 TLS 加密连接 | 本地开发不需要；连接云数据库时开启 |
| any | 运行时才决定连接哪种数据库的 AnyPool | 否 |

两点说明：

为什么写 default-features = false：sqlx 的默认 feature 包含 any、json 等本项目用不到的功能。显式列出需要的 feature，编译更快，依赖树更小，也让读代码的人一眼看出“这个服务用到了数据库的哪些能力”（第 8.4 节 features 的“只增不减”原则同样适用）。

TLS：连接云厂商托管的 PostgreSQL（AWS RDS、阿里云 RDS 等）时，通常要求加密连接，需要在feature 中开启一种 TLS 实现，并在连接字符串加上 ?sslmode=require（或更严格的 verify-full）。TLS feature 的名字在 0.8 的小版本间有过调整，开启前请查 docs.rs 上的当前列表。

### 14.2.4 【入门】安装 sqlx-cli

sqlx-cli 是一个独立的命令行程序，用来建库、管理迁移、生成离线查询数据：
```bash
# 只编译 PostgreSQL 支持，使用纯 Rust 的 TLS 实现，安装更快
cargo install sqlx-cli --no-default-features --features rustls,postgres

# 验证
sqlx --version
```

常用命令一览（14.7 节详解迁移）：

| 命令 | 作用 |
| --- | --- |
| sqlx database create | 按 DATABASE_URL 创建数据库（已存在则什么也不做） |
| sqlx database drop | 删除数据库（会二次确认，-y 跳过） |
| sqlx database reset | 删除、重建并执行全部迁移 |
| sqlx migrate add &lt;名称&gt; | 新建迁移文件 |
| sqlx migrate run | 执行尚未执行的迁移 |

| 命令 | 作用 |
| --- | --- |
| sqlx migrate revert | 回滚最近一次迁移（需要可逆迁移） |
| sqlx migrate info | 列出每个迁移及其是否已执行 |
| cargo sqlx prepare | 为 query! 宏生成离线数据（14.5.5 节） |

sqlx-cli 会自动读取当前目录（及上级目录）中 .env 文件里的 DATABASE_URL，所以很多项目会在根目录放一个只用于本地开发、不提交到 Git 的 .env 文件。

## 14.3 连接池 PgPool

### 14.3.1 【入门】第一次连接

文件：sqlx-lab/src/main.rs
```rust
use sqlx::postgres::PgPoolOptions;

#[tokio::main]
async fn main() -> Result<(), sqlx::Error> {
    let url = std::env::var("DATABASE_URL").expect("请先设置 DATABASE_URL");

    // 建立连接池：最多 5 个连接
    let pool = PgPoolOptions::new().max_connections(5).connect(&url).await?;

    // 执行一条最简单的查询，取出第一列
    let (one,): (i32,) = sqlx::query_as("SELECT 1").fetch_one(&pool).await?;
    println!("数据库返回：{one}");

    // 查询服务器版本，演示返回 TEXT
    let version: String = sqlx::query_scalar("SELECT version()").fetch_one(&pool).await?;
    println!("{version}");

    pool.close().await;
    Ok(())
}
```

运行：
```bash
cargo run
# 数据库返回：1
# PostgreSQL 17.x on x86_64-pc-linux-gnu, compiled by gcc ...
```

逐行解读：

PgPoolOptions::new()：连接池的 Builder（第 3.2 节的 Builder 模式），链式设置参数，最后connect 建立池并立刻建立一个连接来验证地址、账号是否正确。连不上时这里就返回错误，程序在启动阶段失败，而不是等第一个请求到来时才失败--这正是我们想要的“快速失败”。

fetch_one(&amp;pool)：从池中借一个连接执行查询，取第一行，执行完自动把连接还给池。你几乎从不需要手动“借”和“还”。

query_as("SELECT 1") 的结果类型写成元组 (i32,)：PostgreSQL 中整数字面量 1 的类型是INTEGER，对应 i32；如果写成 (i64,) 会在运行时报类型不匹配（14.4.6 节的类型表）。

pool.close().await：关闭池，等待所有借出的连接归还后断开。程序退出前调用是好习惯，第

14. 10 节的优雅停机会用到。

### 14.3.2 【进阶】PgPoolOptions 参数全解
```rust
use std::time::Duration;
use sqlx::postgres::PgPoolOptions;

let pool = PgPoolOptions::new()
    // 池中最多同时存在多少个连接
    .max_connections(10)
    // 池中至少保持多少个空闲连接（0 表示按需建立）
    .min_connections(0)
    // 借连接时最多等多久：池满且没有空闲连接时排队，超时返回 PoolTimedOut
    .acquire_timeout(Duration::from_secs(3))
    // 空闲超过这么久的连接会被关闭，把资源还给数据库
    .idle_timeout(Duration::from_secs(600))
    // 无论是否空闲，一个连接最多存活这么久，然后重建
    .max_lifetime(Duration::from_secs(1800))
    // 借出前先 ping 一次，确认连接没断（默认开启）
    .test_before_acquire(true)
    .connect(&url)
    .await?;
```

| 参数 | 默认值 | 作用与调优建议 |
| --- | --- | --- |
| max_connections | 10 | 最重要的参数。所有实例的总和必须小于数据库的 max_connections（第 13.8 节，默认 100），还要给运维工具、迁移留余量。经验值：每个实例 CPU 核数 × 2~4 |
| min_connections | 0 | 大于 0 时池会在后台预先建立连接，减少流量突增时的建连延迟 |
| acquire_timeout | 30 秒 | 默认值对 Web 服务太长。用户不会等 30 秒；设成 2~5 秒，让过载尽早暴露为错误而不是请求堆积 |
| idle_timeout | 10 分钟 | 低峰期释放连接 |
| max_lifetime | 30 分钟 | 定期重建连接，避免长连接在数据库侧积累内存、或者在负载均衡器/代理（如PgBouncer）切换后失效 |
| test_before_acquire | true | 借出前探活，代价是每次借出多一次往返；在极端追求延迟的场景可关闭 |

除了 connect，还有两种建池方式：

connect_lazy(&amp;url)：不立刻连接，第一次使用时才连。返回 Result（只校验 URL 语法）。适合“数据库暂时不可用也要先把服务启动起来”的场景，例如让就绪探针报告未就绪而不是让进程反复崩溃重启。

connect_with(options)：传入 PgConnectOptions 而不是字符串，适合连接参数来自多个配置项的情况（第 15 章配置管理会用到）。
```rust
use sqlx::postgres::{PgConnectOptions, PgPoolOptions};

let options = PgConnectOptions::new()
    .host("localhost")
    .port(5432)
    .username("rustmall")
    .password("rustmall")
    .database("rustmall")
    // 连接建立后对会话生效，便于在 pg_stat_activity 中识别是谁的连接
    .application_name("rustmall-monolith");
let pool = PgPoolOptions::new().max_connections(10).connect_with(options).await?;
```

application_name 非常实用：第 13.8 节查看 pg_stat_activity 时，能直接看到每个连接来自哪个服务。

### 14.3.3 【进阶】Pool 可以随便克隆

PgPool（即 Pool&lt;Postgres&gt;）内部是一个 Arc，clone() 只是增加引用计数，所有克隆共享同一组连接。因此：

在 Axum 中把 PgPool 放进 AppState（第 12.6 节），每个请求拿到的 State 克隆都指向同一个池。

整个进程只建一个池。在处理函数里调用 PgPoolOptions::new().connect(...) 是严重的错误：每个请求都建一个新池、新连接，数据库很快被连接数打满。

### 14.3.4 【精通】连接池的工作方式与“池耗尽”

把连接池想象成停车场：max_connections 是车位数，请求是来停车的车。

1. 请求调用 fetch_one(&amp;pool) → 池中有空闲连接则直接借出；

2. 没有空闲连接但未达到上限 → 新建一个连接；

3. 已达上限 → 排队等待，最多等 acquire_timeout，超时返回 sqlx::Error::PoolTimedOut。

池耗尽的典型原因：

持有连接期间做了慢操作。例如开启事务后调用一个耗时 2 秒的外部 HTTP 接口，事务期间连接一直被占着。原则：事务里只做数据库操作，外部调用放在事务之前或之后。

慢查询：缺索引导致一条查询几百毫秒，连接周转变慢（第 13.6 节的 EXPLAIN ANALYZE）。

连接泄漏：把 PoolConnection 或 Transaction 存进长期存活的结构里不释放。

观察池的状态：
```text
// 当前池中连接总数（含借出与空闲）
println!("size = {}", pool.size());
// 当前空闲连接数
println!("idle = {}", pool.num_idle());
```

第 38 章会把这两个值导出为 Prometheus 指标，池耗尽一目了然。

| --- | --- | --- |

## 14.4 执行查询：query、query_as、query_scalar

### 14.4.1 【入门】三个函数与五种取结果方式

SQLx 的运行时查询 API 由“构造查询”和“取结果”两部分组成：

| 构造函数 | 每一行变成什么 |
| --- | --- |
| sqlx::query(sql) | PgRow（通用行，按列名或下标取值） |
| sqlx::query_as::&lt;_, T&gt;(sql) | T：元组，或实现了 FromRow 的结构体 |
| sqlx::query_scalar::&lt;_, T&gt;(sql) | 第一列的值 T |

| 取结果方法 | 返回 | 适用场景 |
| --- | --- | --- |
| .execute(e) | PgQueryResult（rows_affected()） | INSERT / UPDATE / DELETE 不需要返回行 |
| .fetch_one(e) | T；没有行时返回Error::RowNotFoun d | 预期至少有一行；多行时只取首行，不验证唯一性 |
| .fetch_optional(e) | Option&lt;T&gt; | 按主键查询：可能不存在 |
| .fetch_all(e) | Vec&lt;T&gt; | 列表（务必配合 LIMIT） |
| .fetch(e) | Stream&lt;Item = Result&lt;T&gt;&gt; | 大结果集逐行处理（14.9.3 节） |

参数 e 是“执行器”（Executor）：&amp;PgPool、&amp;mut PgConnection 或事务 &amp;mut *tx 都可以（14.6.4节）。

### 14.4.2 【入门】绑定参数

PostgreSQL 的占位符是 $1、$2……，用 .bind() 按顺序绑定：
```text
let row: (i64, String) = sqlx::query_as("SELECT id, name FROM products WHERE id = $1")
    .bind(1_i64)
    .fetch_one(&pool)
    .await?;
println!("{} {}", row.0, row.1);

// 同一个参数可以在 SQL 中出现多次
let n: i64 = sqlx::query_scalar("SELECT count(*) FROM products WHERE price_cents BETWEEN $1 AND $1 * 2")
    .bind(10_000_i64)
    .fetch_one(&pool)
    .await?;
```

绑定值的 Rust 类型必须与数据库期望的类型兼容：products.id 是 BIGINT，绑定 i64；如果绑定i32，PostgreSQL 会做隐式转换，多数情况下能工作，但养成“类型完全对应”的习惯能避免很多意外（例如索引失效）。

### 14.4.3 【进阶】为什么绑定参数能防 SQL 注入

反面教材--用 format! 拼 SQL：
```text
// 危险！永远不要这样写
let name = "'; DROP TABLE products; --";
let sql = format!("SELECT * FROM products WHERE name = '{name}'");
```

拼出来的 SQL 变成了两条语句，第二条把表删掉了。使用 .bind(name) 时，SQL 文本 ... WHEREname= $1 和参数值在协议层分开发送，数据库先把 SQL 解析成执行计划，再把参数当作纯数据填进去，参数里写什么都不会被当成 SQL 执行。

bind 只能代替“值”，不能代替表名、列名、ORDER BY 的列、ASC/DESC 这类 SQL 结构。需要动态排序时，用 match 把用户输入映射成固定的白名单字符串：
```rust
fn order_clause(sort: &str) -> &'static str {
    match sort {
        "price" => "price_cents ASC, id ASC",
        "-price" => "price_cents DESC, id DESC",
        // 未知值一律使用默认排序，而不是报错或拼接
        _ => "created_at DESC, id DESC",
    }
}
```

这样拼进 SQL 的只可能是代码里写死的几个字符串之一。14.9.1 节的 QueryBuilder 是更系统的做法。

### 14.4.4 【入门】FromRow：把行映射为结构体
```rust
#[derive(Debug, sqlx::FromRow)]
struct ProductRow {
    id: i64,
    name: String,
    price_cents: i64,
    stock: i32,
}

let rows: Vec<ProductRow> = sqlx::query_as::<_, ProductRow>(
    "SELECT id, name, price_cents, stock FROM products ORDER BY id LIMIT $1",
)
.bind(10_i64)
.fetch_all(&pool)
.await?;

for p in &rows {
    println!("{:>3} {:<12} {:>6} 分 库存 {}", p.id, p.name, p.price_cents, p.stock);
}
```

规则：

按列名匹配字段名，与 SELECT 中列的顺序无关。

结构体的每个字段都必须在结果中找到同名列，否则运行时报 ColumnNotFound；结果中多出来的列会被忽略。

不要写 SELECT *。表以后新增一列不会影响已有代码，但会多传输数据；更重要的是，显式列名让读代码的人一眼看到依赖了哪些列。

query_as::&lt;_, ProductRow&gt; 中的 _ 是数据库类型（Postgres），让编译器推断。

### 14.4.5 【进阶】FromRow 的属性
```rust
#[derive(Debug, sqlx::FromRow)]
struct OrderSummary {
    id: i64,
    // 列名与字段名不同
    #[sqlx(rename = "total_cents")]
    amount_cents: i64,
    // 结果中没有该列时使用 Default（这里是 None）
    #[sqlx(default)]
    tracking_no: Option<String>,
    // 把同一行中的多列组装成一个嵌套结构体
    #[sqlx(flatten)]
    buyer: Buyer,
    // 先按 i32 读出，再用 TryFrom 转换为 u32（负数会报错）
    #[sqlx(try_from = "i32")]
    quantity: u32,
    // 该字段不来自数据库，使用 Default
    #[sqlx(skip)]
    note: String,
}

#[derive(Debug, sqlx::FromRow)]
struct Buyer {
    user_id: i64,
    username: String,
}
```

| 属性 | 作用 |
| --- | --- |
| #[sqlx(rename = "列名")] | 字段名与列名不同 |
| #[sqlx(rename_all ="camelCase")]（写在结构体上） | 统一转换命名风格 |
| #[sqlx(default)] | 列不存在时使用 Default::default()（注意：列存在但值为NULL是另一回事，要用 Option） |
| #[sqlx(flatten)] | 嵌套结构体，其字段从同一行读取 |
| #[sqlx(try_from = "类型")] | 先按指定类型解码，再 TryFrom 转换 |
| #[sqlx(json)] | 该列是 JSON，用 serde 反序列化为字段类型（需 json feature） |
| #[sqlx(skip)] | 不从数据库读取 |

列名冲突的处理：JOIN 两张都有 id 列的表时，用 AS 起别名：SELECT o.id AS order_id, u.idAS user_id ...。

### 14.4.6 【进阶】PostgreSQL ↔ Rust 类型对照表

| PostgreSQL | Rust | 需要的 feature |
| --- | --- | --- |
| BOOLEAN | bool | - |
| SMALLINT | i16 | - |
| INTEGER / SERIAL | i32 | - |
| BIGINT / BIGSERIAL / IDE NTITY | i64 | - |
| REAL / DOUBLE PRECISION | f32 / f64 | - |
| NUMERIC | rust_decimal::Decimal 或bigdecimal::BigDecimal | rust_decimal / bigde cimal |
| TEXT / VARCHAR / CHAR | String（绑定时也可用 &amp;str） | - |
| BYTEA | Vec&lt;u8&gt;（绑定时也可用 &amp;[u8]） | - |
| UUID | uuid::Uuid | uuid |
| TIMESTAMPTZ | chrono::DateTime&lt;Utc&gt; 或time::OffsetDateTime | chrono / time |

| PostgreSQL | Rust | 需要的 feature |
| --- | --- | --- |
| TIMESTAMP（无时区） | chrono::NaiveDateTime 或time::Primit iveDateTime | chrono / time |
| DATE | chrono::NaiveDate 或 time::Date | chrono / time |
| INTERVAL | sqlx::postgres::types::PgInterval | - |
| JSON / JSONB | serde_json::Value 或sqlx::types::Jso n&lt;T&gt; | json |
| INET / CIDR | ipnetwork::IpNetwork | ipnetwork |
| T[] 数组 | Vec&lt;T&gt;（绑定时也可用 &amp;[T]） | - |
| 可空列 | Option&lt;T&gt; | - |

三个最容易踩的坑：

1. 整数宽度必须一致。count(*) 返回 BIGINT，必须用 i64 接收；用 i32 会在运行时报mismatched types; Rust type i32 (as SQL type INT4) is not compatible with SQL typeINT8。

2. 无符号整数不受支持。PostgreSQL 没有无符号类型，所以 u32、u64 都不能直接绑定或解码。处理方式：数据库中用有符号类型，进入领域层时用 try_from 转换（第 1.3.5 节）--这就是RustMall的 Quantity 内部用 i32 的原因之一。

3. 可空列必须用 Option。列值为 NULL 而字段是 String 时，运行时报 unexpected null。用LEFT JOIN 时，右表的所有列都可能为 NULL。

### 14.4.7 【进阶】执行写操作与 RETURNING
```text
// INSERT ... RETURNING：一次往返完成插入并取回数据库生成的值
let (id,): (i64,) = sqlx::query_as(
    "INSERT INTO products (name, price_cents, stock) VALUES ($1, $2, $3) RETURNING id",

.bind(10_i32)

    .bind(id)
    .bind(3_i32)

```

第二段就是第 13.7 节“条件更新防超卖”的 Rust 写法：检查和扣减在同一条 SQL 中原子完成。

### 14.4.8 【精通】query 的生命周期与借用
```text
let name = String::from("鼠标");
let q = sqlx::query("SELECT id FROM products WHERE name = $1").bind(&name);
```

bind(&amp;name) 借用了 name，q 的生命周期因此不能超过 name--SQL 文本是 &amp;'q str，绑定的参数也被约束在 'q 之内。这在函数内顺序执行时从不成问题；但如果你想把“构造好的查询”存进结构体或从函数返回，就要让参数拥有所有权（bind(name.clone()) 或直接 bind(name)）。编译器给出的E0597/E0505 错误按第 2.6 节的修复套路处理即可。

## 14.5 编译期检查的查询宏

### 14.5.1 【入门】query! 宏

运行时查询的问题是：SQL 写错、列名拼错、类型不匹配，都要等到程序运行到那一行才发现。query!系列宏把这些检查提前到编译期：
```text
// 编译时，宏会连接 DATABASE_URL 指向的数据库，让 PostgreSQL 解析这条 SQL
let row = sqlx::query!(
    "SELECT id, name, price_cents FROM products WHERE id = $1",
    1_i64
)
.fetch_one(&pool)
.await?;

// 宏自动生成一个匿名结构体，字段名、类型都来自数据库
println!("{} {} {}", row.id, row.name, row.price_cents);
```

把 price_cents 写成 price，cargo build 直接报错：
```text
error: error returned from database: column "price" does not exist
 --> src/main.rs:10:15
```

参数直接写在宏里（不再 .bind()），宏还会检查参数类型：把 1_i64 换成 "1"，编译器报expected i64, found &amp;str。

### 14.5.2 【进阶】宏家族

| 宏 | 结果 | 说明 |
| --- | --- | --- |
| query!(sql, 参数...) | 匿名结构体 | 最常用的探索方式 |
| query_as!(类型, sql, 参数...) | 指定的结构体 | 结构体不需要派生 FromRow，宏直接按字段名构造 |
| query_scalar!(sql, 参数...) | 第一列的值 |  |
| query_file!("queries/x.sql", ...)等 | 同上 | SQL 放在单独文件中，适合很长的语句 |
| query_unchecked! 等 | 同上 | 只做语法转换、不做类型检查，极少使用 |

### 14.5.3 【进阶】可空性推断与覆盖

宏根据表结构推断每列能否为 NULL：NOT NULL 的列得到 T，否则得到 Option&lt;T&gt;。但对于表达式和函数结果，PostgreSQL 无法告诉宏是否可能为 NULL，宏只能保守地推断为 Option：
```text
let n = sqlx::query_scalar!("SELECT count(*) FROM products").fetch_one(&pool).await?;
// n 的类型是 Option<i64>，尽管 count(*) 永远不会返回 NULL
```

用列别名中的特殊后缀覆盖推断：

| 写法 | 含义 |
| --- | --- |
| AS "total!" | 强制非空：类型为 i64 |
| AS "total?" | 强制可空：类型为 Option&lt;i64&gt; |
| AS "total: i32" | 指定 Rust 类型（必须兼容） |
| AS "total!: i32" | 两者组合 |
| AS "status: OrderStatus" | 解码为自定义类型（14.9.4 节） |
```text
let n = sqlx::query_scalar!(r#"SELECT count(*) AS "total!" FROM products"#)
    .fetch_one(&pool)
    .await?;
// n: i64
```

因为别名里有双引号，SQL 字符串用 raw string r#"..."# 书写（第 1.4.4 节）。

! 是你对编译器的承诺。如果写了 "x!" 而数据库实际返回了 NULL，运行时会报 unexpectednull 错误。LEFT JOIN 右侧的列尤其要小心。

### 14.5.4 【进阶】宏需要的环境

宏在编译时需要两样东西之一：

1. 环境变量 DATABASE_URL 指向一个已经执行过迁移的数据库（宏会读取 .env 文件）；

2. 或者离线数据（14.5.5 节）。

这带来实际的工程问题：CI 机器、Docker 构建环境、新同事的电脑上，编译代码之前都要先有一个结构正确的数据库。

### 14.5.5 【精通】离线模式
```bash
# 在 workspace 根目录执行：对所有 crate 中的宏查询生成元数据，写入 .sqlx/ 目录
cargo sqlx prepare --workspace

# 检查 .sqlx/ 是否与代码一致（CI 中使用，不一致则失败）
cargo sqlx prepare --workspace --check
```

.sqlx/ 目录中每条查询一个 JSON 文件，记录参数和结果列的类型。把它提交到 Git，之后：
```text
# 强制使用离线数据，不连接数据库
SQLX_OFFLINE=true cargo build
```

没有设置 DATABASE_URL 时宏也会自动使用离线数据。工作流程是：改了 SQL → 本地连库编译 → 运行cargo sqlx prepare → 一起提交代码与 .sqlx/。CI 中用 --check 防止有人忘记更新。

### 14.5.6 【精通】RustMall 的选择：运行时查询 + 集成测试

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| query! 宏 + 离线数据 | SQL 错误在编译期暴露 | 每次改 SQL 都要连库编译并重新 prepare；构建流程多一个环节 |
| query_as + FromRow + 集成测试 | 编译不依赖数据库，构建简单 | SQL 错误要靠测试发现 |

两种方案在业界都很常见。本书项目选择第二种，原因有三：一是到第 17 章为止，你会频繁修改表结构，每次都要重新生成离线数据会分散注意力；二是第 20 章的 Docker 构建、第 22 章的 CI 都更简单；三是每一条 SQL 都有 #[sqlx::test] 集成测试覆盖（14.10.8 节），SQL 写错在 cargo test 时就会暴露，实际效果接近编译期检查。

本节练习 3 会让你把项目中的一个查询改写成 query_as!，亲手体验两种方式的差别；如果你的团队更偏好编译期检查，完全可以全面采用宏。

## 14.6 事务

### 14.6.1 【入门】开启、提交、回滚

第 13.7 节在 psql 中用 BEGIN / COMMIT / ROLLBACK 体验了事务。在 SQLx 中：
```text
// 从池中借一个连接并执行 BEGIN
let mut tx = pool.begin().await?;

// 事务中的每条语句都用 &mut *tx 作为执行器
sqlx::query("UPDATE products SET stock = stock - 1 WHERE id = $1")
    .bind(1_i64)
    .execute(&mut *tx)
    .await?;

sqlx::query("UPDATE products SET stock = stock + 1 WHERE id = $1")
    .bind(2_i64)
    .execute(&mut *tx)
    .await?;

// 执行 COMMIT，连接归还给池
tx.commit().await?;
```

没有显式回滚的写法：如果中间任何一个 ? 提前返回，tx 在离开作用域时被 drop，SQLx 会自动回滚。这就是第 2.2 节讲的 RAII：资源（这里是“进行中的事务”）的生命周期与变量绑定，任何退出路径都不会遗漏清理。需要主动放弃时，调用 tx.rollback().await?。

### 14.6.2 【进阶】为什么写 &amp;mut *tx

tx 的类型是 Transaction&lt;'static, Postgres&gt;。执行器参数需要 &amp;mut PgConnection，而Transaction 实现了 DerefMut&lt;Target = PgConnection&gt;：

*tx 解引用得到 PgConnection；

&amp;mut *tx 再取可变引用，得到 &amp;mut PgConnection。

每条语句都重新借用一次，借用在语句执行完后结束，所以可以连续执行多条语句。如果写成.execute(&amp;mut tx)，旧版本可以编译、新版本会报 trait 未实现的错误，统一写 &amp;mut *tx 即可。

### 14.6.3 【进阶】隔离级别与行锁

事务默认使用 READ COMMITTED。需要更高隔离级别时，在事务的第一条语句设置：
```text
let mut tx = pool.begin().await?;
sqlx::query("SET TRANSACTION ISOLATION LEVEL SERIALIZABLE")
    .execute(&mut *tx)
    .await?;
// ……业务语句……
tx.commit().await?;
```

第 13.7 节的“先锁后改”在 Rust 中的样子：
```text
let mut tx = pool.begin().await?;

// 锁住这一行，其他事务对它的修改会等待我们提交
let stock: Option<i32> = sqlx::query_scalar("SELECT stock FROM products WHERE id = $1 FOR 
    UPDATE")
    .bind(product_id)
    .fetch_optional(&mut *tx)
    .await?;

let Some(stock) = stock else {
    // 提前返回：tx 被 drop，自动回滚并释放锁
    return Ok(Outcome::NotFound);
};
if stock < qty {
    return Ok(Outcome::Insufficient { available: stock });
}

sqlx::query("UPDATE products SET stock = stock - $2 WHERE id = $1")
    .bind(product_id)
    .bind(qty)
    .execute(&mut *tx)
    .await?;
tx.commit().await?;
```

注意 let ... else（第 3.5 节）在这里的作用：不满足条件时直接返回，事务自动回滚，不需要在每个分支里手写 rollback。

### 14.6.4 【精通】编写既能用池、也能用事务的函数

一个 insert_product 函数，有时单独调用，有时作为更大事务的一部分。SQLx 提供两种抽象：

方式一：PgExecutor--函数内只执行一条语句
```rust
use sqlx::PgExecutor;

async fn count_products<'e>(executor: impl PgExecutor<'e>) -> Result<i64, sqlx::Error> {
    sqlx::query_scalar("SELECT count(*) FROM products").fetch_one(executor).await
}

// 两种调用方式都可以
let a = count_products(&pool).await?;
let b = count_products(&mut *tx).await?;
```

执行器在执行时被消耗（按值传入），所以函数内只能用它执行一次。

方式二：Acquire--函数内执行多条语句
```rust
use sqlx::{Acquire, Postgres};

async fn restock_two<'a>(
    conn: impl Acquire<'a, Database = Postgres>,
    a: i64,
    b: i64,
) -> Result<(), sqlx::Error> {
    // 如果传入的是池，这里借一个连接；如果是事务，就使用事务所在的连接
    let mut conn = conn.acquire().await?;
    sqlx::query("UPDATE products SET stock = stock + 10 WHERE id = $1").bind(a).execute(&mut 
        *conn).await?;
    sqlx::query("UPDATE products SET stock = stock + 10 WHERE id = $1").bind(b).execute(&mut 
        *conn).await?;
    Ok(())
}
```

调用时传 &amp;pool 或 &amp;mut tx。在第 15 章的分层架构中，仓储方法大量使用这两种写法，让“是否在事务中”由上层的服务决定。

### 14.6.5 【精通】保存点：嵌套事务

在一个事务内部再次调用 begin，SQLx 会创建保存点（SAVEPOINT）：
```rust
use sqlx::Connection;

let mut tx = pool.begin().await?;
sqlx::query("INSERT INTO products (name, price_cents, stock) VALUES ('A', 100, 1)").execute(&mut *tx).await?;

{
    // 实际执行 SAVEPOINT
    let mut inner = tx.begin().await?;
    sqlx::query("INSERT INTO products (name, price_cents, stock) VALUES ('', 100, 1)")
        .execute(&mut *inner)
        .await
        // 空名称违反 CHECK 约束；inner 被 drop 时只回滚到保存点
        .ok();
}

// A 仍然会被提交
tx.commit().await?;
```

保存点适合“批量导入时跳过坏数据、其余照常提交”这类场景。

### 14.6.6 【精通】事务的四条纪律

1. 事务越短越好。事务持有连接，可能还持有行锁；事务里不要调用外部 HTTP 接口、不要 sleep、不要等待用户输入。

2. 加锁顺序一致。需要锁多行时，按主键升序加锁（ORDER BY id FOR UPDATE），避免第 13.7 节演示的死锁。

3. 可串行化事务要准备重试。SERIALIZABLE 下冲突的事务会收到错误码 40001（serialization_failure），正确做法是整个事务重来，第 29 章会封装一个带退避的重试函数。

4. 能用一条 SQL 完成的，不用事务。“条件更新 + rows_affected”（14.4.7 节）本身就是原子的，比“先查再改”的事务更快、更不容易出错。

### 14.6.7 常见错误与解读

| 报错 | 原因 | 修复 |
| --- | --- | --- |
| the trait `Executor<'_>` is not implemented for `&mut Transaction<...>` | 写成了 &amp;mut tx | 写 &amp;mut *tx |
| borrow of moved value: `executor` | impl PgExecutor 被第一条查询消耗，又用于第二条 | 改用 Acquire（14.6.4） |
| current transaction is aborted, commandsignored until end of transaction block（25P02） | 事务中某条语句已失败，后续语句全部被拒绝 | 出错后不要继续使用该事务；需要“部分失败继续”时用保存点 |
| could not serialize access due to concur rent update（40001） | 可串行化冲突 | 整个事务重试 |
| deadlock detected（40P01） | 两个事务以相反顺序加锁 | 统一加锁顺序 |

## 14.7 迁移：用代码管理表结构

### 14.7.1 【入门】为什么需要迁移

第 13 章我们手动在 psql 中执行 schema.sql。到了团队协作和多环境部署时，这种方式很快失控：

同事拉下最新代码，不知道要执行哪些 SQL；

测试环境执行过某个改动，生产环境忘了执行；

想知道“生产数据库现在是哪个版本的结构”，没有答案。

迁移（migration）把每一次表结构变化写成一个带版本号的 SQL 文件，并在数据库中用一张表记录“已经执行到哪个版本”。程序启动（或部署流水线）时自动执行尚未执行的迁移，所有环境的结构因此保持一致。

### 14.7.2 【入门】创建与执行迁移
```text
# 在 sqlx-lab 目录下（DATABASE_URL 已设置）
sqlx migrate add create_notes
# Creating migrations/20261011093000_create_notes.sql
```

编辑生成的文件：
```sql
CREATE TABLE notes (
    id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    body TEXT NOT NULL
);
```

执行并查看状态：
```text
sqlx migrate run
# Applied 20261011093000/migrate create notes (8.1ms)

sqlx migrate info
# 20261011093000/installed create notes
```

再执行一次 sqlx migrate run，什么也不会发生：已经执行过的迁移不会重复执行。

### 14.7.3 【进阶】文件命名与版本号

迁移文件名的格式是 &lt;版本号&gt;_&lt;描述&gt;.sql。版本号是一个整数，SQLx 按版本号从小到大执行：

| 风格 | 示例 | 适合 |
| --- | --- | --- |
| 时间戳（默认） | 20261011093000_create_notes.sql | 多人并行开发，不容易撞号 |
| 顺序号 | 0001_init.sql、0002_xxx.sql | 小团队、教学项目，一眼看出先后顺序 |

两种都合法，但同一个项目只用一种。较新版本的 sqlx-cli 支持 sqlx migrate add --sequential &lt;名称&gt; 自动生成顺序号；也可以直接手动创建文件，效果完全相同。RustMall 使用顺序号。

### 14.7.4 【进阶】可逆迁移
```text
sqlx migrate add -r add_note_title
# Creating migrations/20261011094500_add_note_title.up.sql
# Creating migrations/20261011094500_add_note_title.down.sql
```

.up.sql 写正向变更，.down.sql 写如何撤销：
```sql
-- up
ALTER TABLE notes ADD COLUMN title TEXT NOT NULL DEFAULT '';
```
```sql
-- down
ALTER TABLE notes DROP COLUMN title;
```

sqlx migrate revert 执行最近一次迁移的 .down.sql。注意：一个项目中的迁移要么全部是可逆的，要么全部是简单的（只有 .sql），不能混用。

生产环境几乎从不执行 down 迁移：删除列会丢数据，回滚程序版本通常比回滚表结构更安全。所以很多团队只写“只进不退”的简单迁移，出问题时再写一个新的正向迁移来修正。RustMall 采用这种做法。

### 14.7.5 【进阶】在程序中嵌入并执行迁移
```text
// 编译时读取 ./migrations 目录（相对于 Cargo.toml 所在目录），把所有 SQL 嵌入二进制
static MIGRATOR: sqlx::migrate::Migrator = sqlx::migrate!();

// 启动时执行尚未执行的迁移
MIGRATOR.run(&pool).await?;
```

也可以直接写 sqlx::migrate!().run(&amp;pool).await?，或者指定目录 sqlx::migrate!("./db/migrations")。

嵌入意味着部署时只需要一个二进制文件，不必把 SQL 文件一起复制到服务器或 Docker 镜像中。

让 Cargo 感知迁移文件的变化：migrate! 是在编译时读取文件的，如果你只新增了一个迁移文件而没有改任何 Rust 代码，Cargo 可能认为不需要重新编译，新迁移就不会被嵌入。解决办法是在 crate 中加一个构建脚本：
```text
# 自动生成 build.rs
sqlx migrate build-script
```

生成的 build.rs 只有一行有效内容：println!("cargo:rerun-if-changed=migrations");，告诉Cargo 该目录变化时重新编译（第 8.4 节的构建脚本）。

### 14.7.6 【精通】迁移的内部机制

执行迁移后，数据库中会多出一张表：
```sql
SELECT version, description, success, execution_time FROM _sqlx_migrations ORDER BY version;
```

| 列 | 含义 |
| --- | --- |
| version | 版本号 |

| 列 | 含义 |
| --- | --- |
| description | 文件名中的描述部分 |
| installed_on | 执行时间 |
| success | 是否成功 |
| checksum | 文件内容的 SHA-384 摘要 |
| execution_time | 耗时（纳秒） |

几条必须牢记的规则：

1. 已经执行过的迁移文件永远不要修改。SQLx 每次启动都会比对 checksum，发现内容变了会拒绝运行：migration 1 was previously applied but has been modified。要改表结构，写一个新的迁移。（唯一的例外是本地开发、迁移还没推送给任何人时：可以 sqlx database reset 后重来。）

2. 每个迁移默认在一个事务中执行：要么全部成功，要么全部回滚，不会留下“执行了一半”的结构。PostgreSQL 的 DDL 是事务性的，这是它相对 MySQL 的一大优势。

3. 有些语句不能放在事务中，例如 CREATE INDEX CONCURRENTLY。在迁移文件的第一行写 -- no-transaction，SQLx 就不会为它包事务。

4. 多实例并发启动是安全的：执行迁移前 SQLx 会获取一个 PostgreSQL 咨询锁（advisory lock），第二个实例会等第一个执行完，然后发现已经没有待执行的迁移。

5. 线上改表要考虑锁：第 13.8 节讲过 ALTER TABLE 可能锁表。给大表加带默认值的列、加 NOTNULL约束、建索引时，要先评估锁的时长，必要时拆成多个迁移（先加可空列 → 回填数据 → 再加约束；索引用 CONCURRENTLY）。

### 14.7.7 【精通】谁来执行迁移

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 服务启动时执行（MIGRATOR.run） | 简单，不会忘 | 服务账号需要 DDL 权限；多实例同时启动时会排队等锁 |
| 部署流水线中单独执行（sqlx migrate r un 或专用迁移程序） | 权限分离；迁移失败时不会启动新版本 | 流程更复杂 |

单体阶段 RustMall 在启动时执行；第 23 章部署到 Kubernetes 时会改为用一个 Job 先执行迁移，再滚动更新服务。

### 14.7.8 常见错误与解读

| 报错 | 原因 | 修复 |
| --- | --- | --- |
| migration N was previously applied buthas been modified | 修改了已执行的迁移 | 撤销修改，改写新迁移；本地可s qlx database reset |
| migration N was previously applied butis missing in the resolved migrations | 数据库执行过的迁移在代码中被删除了 | 恢复该文件；或者确认连错了数据库 |
| while executing migrations: error returned from database: ... | 迁移 SQL 本身有错 | 修正后重新执行（失败的迁移已回滚） |
| CREATE INDEX CONCURRENTLY cannot run inside a transaction block | 迁移默认包在事务中 | 文件第一行写 -- no-transaction，并自行处理部分执行后的恢复 |
| 新增迁移文件后程序没执行它 | Cargo 没有重新编译 | 加 build.rs（14.7.5），或tou ch 一下 Rust 源文件 |

## 14.8 错误处理：从 sqlx::Error 到业务错误

### 14.8.1 【入门】sqlx::Error 的主要变体

| 变体 | 何时出现 | 一般应如何对外表现 |
| --- | --- | --- |
| Database(Box&lt;dyn DatabaseError&gt;) | 数据库返回了错误（约束冲突、语法错误、死锁……） | 视具体错误码而定（14.8.2） |
| RowNotFound | fetch_one 没有结果 | 通常是 404；更好的做法是用fetch_o ptional 显式处理 |
| PoolTimedOut | 借连接超时 | 500 或 503，并告警 |
| PoolClosed | 池已关闭（正在停机） | 503 |
| Io / Tls / Protocol | 网络或协议问题 | 500，告警 |
| ColumnNotFound / ColumnD ecode / Decode | 代码与表结构不匹配 | 500：这是程序缺陷 |
| Configuration | 连接字符串有误 | 启动失败 |

| 变体 | 何时出现 | 一般应如何对外表现 |
| --- | --- | --- |
| Migrate | 迁移失败 | 启动失败 |

### 14.8.2 【进阶】识别数据库错误：错误码、约束名、错误分类
```rust
use sqlx::error::ErrorKind;

match sqlx::query("INSERT INTO products (name, price_cents, stock) VALUES ($1, $2, $3)")
    .bind("坏商品")
    .bind(-1_i64)
    .bind(0_i32)
    .execute(&pool)
    .await
{
    Ok(_) => println!("插入成功"),
    Err(err) => {
        if let Some(db) = err.as_database_error() {
            // SQLSTATE 错误码，例如 23514
            println!("code = {:?}", db.code());
            // 违反的约束名，例如 products_price_cents_check
            println!("constraint = {:?}", db.constraint());
            // 与数据库种类无关的分类
            match db.kind() {
                ErrorKind::UniqueViolation => println!("唯一约束冲突"),
                ErrorKind::ForeignKeyViolation => println!("外键约束冲突"),
                ErrorKind::NotNullViolation => println!("非空约束冲突"),
                ErrorKind::CheckViolation => println!("检查约束冲突"),
                // ErrorKind 是 non_exhaustive 枚举，必须有兜底分支
                _ => println!("其他数据库错误：{}", db.message()),
            }
        } else {
            println!("非数据库错误：{err}");
        }
    }
}
```

第 13.4 节的错误码表在这里派上用场：

| SQLSTATE | ErrorKind | 含义 | RustMall 中的处理 |
| --- | --- | --- | --- |
| 23505 | UniqueViolation | 唯一约束冲突 | 409 Conflict（例如用户名已存在、幂等键重复） |
| 23503 | ForeignKeyViolation | 外键约束冲突 | 409 Conflict（引用的数据不存在，或仍被引用） |
| 23502 | NotNullViolation | 非空约束冲突 | 500：程序没有提供必填列，是缺陷 |
| 23514 | CheckViolation | 检查约束冲突 | 500：上层校验本应先拦住，是缺陷（见 14.8.3） |
| 40001 | Other | 可串行化冲突 | 重试 |
| 40P01 | Other | 死锁 | 重试 |

需要 PostgreSQL 特有的详细信息（例如冲突的具体值）时，向下转型为 PgDatabaseError：
```rust
use sqlx::postgres::PgDatabaseError;

if let Some(pg) = err.as_database_error().and_then(|db| db.try_downcast_ref:: 
    <PgDatabaseError>()) {
    // 例如：Key (username)=(alice) already exists.
    println!("detail = {:?}", pg.detail());
    println!("table = {:?}, column = {:?}", pg.table(), pg.column());
}
```

### 14.8.3 【精通】检查约束冲突为什么算“内部错误”

RustMall 的商品有两道防线：第一道是 Product::try_new 的校验（第 3 章），第二道是数据库的CHECK 约束（第 13 章）。正常情况下，非法数据在第一道防线就被拦下并返回 422，根本到不了数据库。

如果数据库的 CHECK 约束被触发，说明第一道防线有漏洞：代码和约束的规则不一致了（例如有人把数据库的名称上限改成 50，却忘了改 Product::NAME_MAX_CHARS）。这是程序缺陷，应当记录日志、触发告警，让开发者修复，而不是当成用户输入错误返回 422--用户也无从知道如何改正。

唯一约束和外键约束则不同：它们检查的是“与其他数据的关系”，应用层无法在不加锁的前提下预先判断（检查“用户名是否存在”和插入之间，别人可能已经插入了），所以由数据库裁决并返回 409 是正确的设计。这与第 13.7 节“不要先查后改”是同一个道理。

### 14.8.4 【进阶】把转换集中在一个地方

每个仓储方法都写一遍 match db.kind() 会非常啰嗦。14.10.5 节会在 monolith/src/db.rs 中写一个转换函数，所有仓储统一调用：
```text
sqlx::query(...).execute(&self.pool).await.map_err(db::to_domain)?;
```

为什么不直接写 impl From&lt;sqlx::Error&gt; for DomainError？因为 DomainError 在 common中，而 common 不应该依赖 sqlx（领域层不知道数据库的存在，第 12.9.3 节的原则）；sqlx::Error和DomainError 对 monolith 来说又都是外部类型，孤儿规则（第 5.6 节）不允许在 monolith 中为它们实现 From。普通函数加 map_err 是最直接的解法。

## 14.9 进阶主题

### 14.9.1 【进阶】QueryBuilder：安全地构造动态 SQL

商品搜索的过滤条件是可选的：可能有关键词、可能有价格区间、也可能都没有。手动拼字符串容易出错，QueryBuilder 负责维护 $n 编号：
```rust
use sqlx::{Postgres, QueryBuilder};

struct Filter {
    keyword: Option<String>,
    min_price: Option<i64>,
    max_price: Option<i64>,
}

async fn search(pool: &sqlx::PgPool, f: &Filter) -> Result<Vec<ProductRow>, sqlx::Error> {
    let mut qb: QueryBuilder<Postgres> =
        QueryBuilder::new("SELECT id, name, price_cents, stock FROM products WHERE TRUE");

    if let Some(kw) = &f.keyword {
        // push 追加 SQL 文本；push_bind 追加一个占位符并绑定参数
        qb.push(" AND name ILIKE ").push_bind(format!("%{kw}%"));
    }
    if let Some(min) = f.min_price {
        qb.push(" AND price_cents >= ").push_bind(min);
    }
    if let Some(max) = f.max_price {
        qb.push(" AND price_cents <= ").push_bind(max);
    }
    qb.push(" ORDER BY id LIMIT 50");

    qb.build_query_as::<ProductRow>().fetch_all(pool).await
}
```

生成的 SQL 形如 ... WHERE TRUE AND name ILIKE $1 AND price_cents &gt;= $2 ...。

WHERE TRUE 是常用技巧：后面每个条件都以 AND 开头，不用判断“是不是第一个条件”。

push 只能放代码中写死的文本；任何来自用户的值都必须走 push_bind。

build_query_as / build_query_scalar / build 分别对应 14.4.1 节的三个函数。

### 14.9.2 【进阶】批量插入

方式一：push_values 生成多行 VALUES
```text
let items = vec![("键盘", 19_900_i64, 10_i32), ("鼠标", 9_900, 20), ("耳机", 29_900, 5)];

let mut qb: QueryBuilder<Postgres> = QueryBuilder::new("INSERT INTO products (name, price_cents, stock) ");qb.push_values(items.iter(), |mut row, (name, price, stock)| {
    row.push_bind(*name).push_bind(*price).push_bind(*stock);
});
qb.build().execute(&pool).await?;
```

PostgreSQL 单条语句最多 65535 个参数，3 列的表一次最多约 2 万行，超过时要分批（items.chunks(1000)，第 6.2 节）。

方式二：UNNEST 绑定数组（PostgreSQL 特有，推荐）
```sql
let names: Vec<String> = vec!["键盘".into(), "鼠标".into()];
let prices: Vec<i64> = vec![19_900, 9_900];
let stocks: Vec<i32> = vec![10, 20];

sqlx::query(
    "INSERT INTO products (name, price_cents, stock)
     SELECT * FROM UNNEST($1::TEXT[], $2::BIGINT[], $3::INT[])",)
.bind(&names)
.bind(&prices)
.bind(&stocks)
.execute(&pool)
.await?;
```

无论多少行都只有 3 个参数，SQL 文本固定（能命中语句缓存），也不受参数个数上限的限制。

### 14.9.3 【进阶】流式读取大结果集

fetch_all 会把所有行读进一个 Vec。导出十万条订单时，用 fetch 逐行处理，内存占用恒定：
```rust
use futures::TryStreamExt;

let mut rows = sqlx::query_as::<_, ProductRow>("SELECT id, name, price_cents, stock FROM products ORDER BY id")
    .fetch(&pool);

// try_next 来自 TryStreamExt：逐行取出，出错时返回 Err
while let Some(row) = rows.try_next().await? {
    println!("{}", row.name);
}
```

注意：流在被完全消费（或 drop）之前一直占用一个连接，处理每一行时不要做慢操作。

### 14.9.4 【进阶】自定义类型映射

枚举 ↔ TEXT 列：订单状态在数据库中是带 CHECK 约束的 TEXT（第 13.9.4 节），可以让枚举直接参与绑定和解码：
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, sqlx::Type)]
#[sqlx(type_name = "text", rename_all = "snake_case")]
enum OrderStatus {
    Pending,
    Paid,
    Shipped,
    Completed,
    Cancelled,
}

let pending: i64 = sqlx::query_scalar("SELECT count(*) FROM orders WHERE status = $1")
    .bind(OrderStatus::Pending)
    .fetch_one(&pool)
    .await?;
```

newtype ↔ 底层类型：#[derive(sqlx::Type)] #[sqlx(transparent)] struct Sku(String);让Sku 和 String 一样被编码、解码。

RustMall 为什么不给 ProductId 派生 sqlx::Type：ProductId 定义在 common 中，如果在那里派生，common 就必须依赖 sqlx，领域层被数据库绑架；而在 monolith 中又不能为外部类型实现外部trait（孤儿规则）。所以项目在仓储里用 id.get() 和 ProductId::new(row.id) 显式转换--多写两个方法调用，换来 common 的纯净。第 26 章拆分微服务时，common 会被多个服务共享，这一点更加重要。

JSONB 列（需要 json feature）：

### 14.9.5 【精通】性能要点

| 要点 | 说明 |
| --- | --- |
| 语句缓存 | 每个连接默认缓存 100 条预处理语句（PgConnectOptions::statement_cache_capacity 可调）。SQL 文本固定、参数通过 bind 传入，才能命中缓存--这也是 UNNEST 优于“按行数生成不同 SQL”的原因 |
| 减少往返 | 用 RETURNING 代替“插入后再查询”；用一条 UPDATE ... WHERE 代替“先查再改” |
| 并发查询 | 互不依赖的两条查询可以用 tokio::try_join! 并发执行，它们会各自借用一个连接（14.10.4的列表接口） |
| 只取需要的列 | 不写 SELECT *，大字段（长文本、JSONB）只在详情接口查询 |
| 分页 | 深分页用 keyset 而非 OFFSET（第 13.5.5 节） |

| 要点 | 说明 |
| --- | --- |
| PgBouncer | 使用事务模式的 PgBouncer 时，预处理语句可能失效，需要查阅其版本对预处理语句的支持情况，或在 SQLx 侧关闭语句缓存 |

### 14.9.6 【进阶】#[sqlx::test]：每个测试一个独立数据库
```rust
#[sqlx::test]

    sqlx::query("INSERT INTO products (name, price_cents, stock) VALUES ('键盘', 100, 1)")
        .execute(&pool)
        .await
        .unwrap();
    let n: i64 = sqlx::query_scalar("SELECT count(*) FROM products").fetch_one(&pool).await.unwrap();

}
```

#[sqlx::test] 做了这些事：

1. 读取环境变量 DATABASE_URL，连接到该服务器；

2. 为这个测试新建一个数据库（名字形如 _sqlx_test_123）；

3. 执行 crate 下 ./migrations 中的全部迁移（开启 migrate feature 时）；

4. 把连接到新数据库的 PgPool 作为参数传给测试函数；

5. 测试结束后由 SQLx 负责清理这些临时数据库，不会污染开发库。

因此每个测试都从一个结构完整、数据为空的数据库开始，测试之间互不干扰，可以并行运行，自增 ID也总是从 1 开始。常用参数：

| 写法 | 作用 |
| --- | --- |
| #[sqlx::test(migrations ="../other/migrations")] | 指定迁移目录 |
| #[sqlx::test(migrations = false)] | 不执行迁移 |
| #[sqlx::test(fixtures("products"))] | 迁移后再执行测试文件所在目录下fixtures/products.s ql 中的数据 |

运行要求：执行 cargo test 时必须设置 DATABASE_URL，且该用户有创建数据库的权限（开发容器中的 rustmall 用户是超级用户，满足要求）。第 17 章会系统讲解测试，包括 testcontainers 自动启动数据库容器。

-- 有订单引用的商品不能物理删除（orders.product_id 外键，第 13.9.4 节），

设计说明：

为什么用时间戳而不是布尔值：delisted_at IS NULL 表示在售，非空表示下架，并且同时记录了下架时间，运营排查时很有用。一个列表达两个信息，且不可能出现“标记为下架却没有时间”的不一致状态（第 3.6 节“让非法状态无法表示”）。

### 14.10.5 第 4 步：连接池、迁移器与错误转换 db.rs

文件：rustmall/monolith/src/db.rs（新建）
```rust
//! 数据库基础设施：连接池、迁移器、`sqlx::Error` 到 `DomainError` 的转换。

use std::time::Duration;

use common::error::DomainError;
use sqlx::error::ErrorKind;
use sqlx::migrate::Migrator;
use sqlx::postgres::{PgConnectOptions, PgPoolOptions};
use sqlx::PgPool;

/// 编译时嵌入 `monolith/migrations` 下的全部迁移文件。
pub static MIGRATOR: Migrator = sqlx::migrate!();

/// 按连接字符串创建连接池。会立即建立一个连接，地址或账号错误时在启动阶段就失败。
pub async fn connect(url: &str) -> Result<PgPool, sqlx::Error> {
    // 先解析为结构化选项，再追加 application_name，便于在 pg_stat_activity 中识别
    let options: PgConnectOptions = url.parse()?;
    PgPoolOptions::new()
        .max_connections(10)
        // Web 服务不应让请求等太久：池满 3 秒仍借不到连接就报错
        .acquire_timeout(Duration::from_secs(3))
        .idle_timeout(Duration::from_secs(600))
        .max_lifetime(Duration::from_secs(1800))
        .connect_with(options.application_name("rustmall-monolith"))
        .await
}

/// 把数据库错误转换为领域错误。
///
/// - 唯一约束、外键约束冲突：数据之间的关系由数据库裁决，属于业务冲突，对应 409；
/// - 其余错误（含 CHECK 约束冲突）：说明程序有缺陷或基础设施故障，作为内部错误处理，
///   详情只进日志，不返回给客戶端（见 14.8.3 节）。
pub fn to_domain(err: sqlx::Error) -> DomainError {
    if let Some(db_err) = err.as_database_error() {
        let constraint = db_err.constraint().unwrap_or("未知约束");
        match db_err.kind() {
            ErrorKind::UniqueViolation => {
                return DomainError::Conflict(format!("数据已存在（违反唯一约束{constraint}）"));
            }
            ErrorKind::ForeignKeyViolation => {
                return DomainError::Conflict(format!("关联的数据不存在或仍被引用（{constraint}）"));
            }
            // ErrorKind 是 non_exhaustive 枚举，必须有兜底分支
            _ => {}
        }
    }
    DomainError::Internal(format!("数据库错误：{err}"))
}
```

代码精讲：

pub static MIGRATOR：sqlx::migrate!() 在编译期读取迁移文件，生成一个常量表达式，所以可以放进 static。不写参数时默认目录是 ./migrations（相对于monolith/Cargo.toml）。

url.parse()?：PgConnectOptions 实现了 FromStr，错误类型正是 sqlx::Error，所以? 可以直接使用。解析成结构化选项后，可以在代码中追加连接字符串里没有的设置。

为什么返回 sqlx::Error 而不是 DomainError：connect 只在启动时调用，失败了程序就该退出；它不是业务操作，没必要转换成领域错误。main 中用 anyhow 加上下文即可。

to_domain 中的借用：db_err 借用了 err，在两个 return 分支中借用随函数返回结束；走到最后一行时借用已经结束，err 可以再次使用。这是第 2.4 节 NLL 的又一个例子。

format!("数据库错误：{err}")：内部错误的文字只会被第 12 章的 ApiError 写进标准错误输出（第 15 章换成 tracing 日志），对外统一显示“服务器内部错误”。

### 14.10.6 第 5 步：商品仓储 product_repo.rs

第 5 章的 Repository trait 是同步的（fn get(&amp;self, ...)），而数据库访问是异步的。异步 trait涉及 Send 约束和对象安全等问题（第 11 章讲过 Future 的 Send 要求），留到第 15 章分层重构时统一设计。本章先写一个具体类型的仓储，方法签名就是将来 trait 的雏形。

文件：rustmall/monolith/src/product_repo.rs（新建）
```rust
//! 商品仓储的 PostgreSQL 实现。
//!
//! 只有在售商品（`delisted_at IS NULL`）对外可见：下架的商品在查询、修改、再次下架时
//! 都表现为“不存在”。

use common::error::{DomainError, DomainResult};
use common::ids::ProductId;
use common::product::Product;
use sqlx::PgPool;

use crate::db;

/// 实体名称，用于“不存在”错误信息。
const ENTITY: &str = "商品";

/// 数据库中的一行商品，字段与 SELECT / RETURNING 的列一一对应。
#[derive(Debug, sqlx::FromRow)]
struct ProductRow {
    id: i64,
    name: String,
    price_cents: i64,
    stock: i32,
}

impl ProductRow {
    /// 行 → 领域对象。依然经过 `Product::try_new`，商品的不变量在任何来源下都成立。
    fn into_product(self) -> DomainResult<Product> {
        let id = self.id;
        Product::try_new(ProductId::new(id), &self.name, self.price_cents, self.stock)
            .map_err(|reason| DomainError::Internal(format!("数据库中的商品 {id} 不满足不变量：{reason}")))
    }
}

/// 商品仓储。内部只有一个连接池，克隆的代价是一次引用计数加一。
#[derive(Debug, Clone)]
pub struct PgProductRepo {
    pool: PgPool,
}

impl PgProductRepo {
    pub fn new(pool: PgPool) -> Self {
        Self { pool }
    }

    /// 新增商品，ID 由数据库生成。
    ///
    /// `draft` 必须已经通过 `Product::try_new` 校验；它的 ID 会被忽略
    /// （`products.id` 是 `GENERATED ALWAYS`，INSERT 中不能也不需要写入）。
    pub async fn insert(&self, draft: &Product) -> DomainResult<Product> {
        sqlx::query_as::<_, ProductRow>(
            "INSERT INTO products (name, price_cents, stock) VALUES ($1, $2, $3) \
             RETURNING id, name, price_cents, stock",
        )
        .bind(draft.name())
        .bind(draft.price_cents())
        .bind(draft.stock())
        .fetch_one(&self.pool)
        .await
        .map_err(db::to_domain)?
        .into_product()
    }

    /// 按 ID 查询在售商品。
    pub async fn get(&self, id: ProductId) -> DomainResult<Product> {
        sqlx::query_as::<_, ProductRow>(
            "SELECT id, name, price_cents, stock FROM products \
             WHERE id = $1 AND delisted_at IS NULL",
        )
        .bind(id.get())
        .fetch_optional(&self.pool)
        .await
        .map_err(db::to_domain)?
        .ok_or_else(|| DomainError::not_found(ENTITY, id))?
        .into_product()
    }

    /// 按创建时间倒序分页列出在售商品，同时返回在售商品总数。
    pub async fn list(&self, limit: i64, offset: i64) -> DomainResult<(Vec<Product>, i64)> {
        let rows = sqlx::query_as::<_, ProductRow>(
            "SELECT id, name, price_cents, stock FROM products \
             WHERE delisted_at IS NULL \
             ORDER BY created_at DESC, id DESC \
             LIMIT $1 OFFSET $2",
        )
        .bind(limit)
        .bind(offset)
        .fetch_all(&self.pool);

        let total = sqlx::query_scalar::<_, i64>("SELECT count(*) FROM products WHERE delisted_at IS NULL")
            .fetch_one(&self.pool);

        // 两条查询互不依赖：并发执行，各自从池中借一个连接
        let (rows, total) = tokio::try_join!(rows, total).map_err(db::to_domain)?;

        let items = rows
            .into_iter()
            .map(ProductRow::into_product)
            .collect::<DomainResult<Vec<_>>>()?;
        Ok((items, total))
    }

    /// 整体替换在售商品的可修改字段，返回修改后的商品。
    pub async fn update(&self, product: &Product) -> DomainResult<Product> {
        sqlx::query_as::<_, ProductRow>(
            "UPDATE products SET name = $2, price_cents = $3, stock = $4, updated_at = now() \
             WHERE id = $1 AND delisted_at IS NULL \
             RETURNING id, name, price_cents, stock",
        )
        .bind(product.id().get())
        .bind(product.name())
        .bind(product.price_cents())
        .bind(product.stock())
        .fetch_optional(&self.pool)
        .await
        .map_err(db::to_domain)?
        .ok_or_else(|| DomainError::not_found(ENTITY, product.id()))?
        .into_product()
    }

    /// 下架商品。商品不存在或已下架时返回“不存在”。
    pub async fn delist(&self, id: ProductId) -> DomainResult<()> {
        let result = sqlx::query(
            "UPDATE products SET delisted_at = now(), updated_at = now() \
             WHERE id = $1 AND delisted_at IS NULL",
        )
        .bind(id.get())
        .execute(&self.pool)
        .await
        .map_err(db::to_domain)?;

        if result.rows_affected() == 0 {
            return Err(DomainError::not_found(ENTITY, id));
        }
        Ok(())
    }
}
```

代码精讲：

SQL 字符串里的行尾反斜杠：Rust 字符串中，行尾的 \ 会吃掉换行符和下一行开头的空白（第

1. 4.4 节），所以多行写的 SQL 实际上是一行，每段末尾要留一个空格，否则 $3) 和RETURNING 会粘在一起。

ProductRow 是私有的：数据库的行结构是仓储的实现细节，对外只暴露领域对象 Product。将来表结构变化（例如拆列、改名），影响范围止于这个文件。

从数据库读出的数据也经过 try_new：数据库有 CHECK 约束，正常情况下不会失败；万一失败（例如有人手工改了数据、约束和代码规则不一致），返回内部错误而不是 panic--一条坏数据不应该让整个服务崩溃。

链式调用读法：get 中的链条依次是：执行查询 → 把 sqlx::Error 转成 DomainError 并用? 提前返回 → 得到 Option&lt;ProductRow&gt; → None 转成“不存在”错误并 ? → 得到ProductRow →转成 Product（本身返回 DomainResult，作为函数结果）。每个 ? 都是一个提前退出点，第 4.3节的内容在这里集中体现。

update 和 delist 一条 SQL 完成“检查 + 修改”：WHERE id = $1 AND delisted_at ISNULL同时检查了“存在”和“在售”，再根据返回的行数（或 RETURNING 是否有结果）判断，没有“先查再改”的竞态窗口（14.6.6 节第 4 条）。

list 的并发查询：fetch_all 和 fetch_one 返回的是还没执行的 Future（第 11 章：Future是惰性的），tokio::try_join! 同时推动两者，任何一个失败就立即返回错误。两条查询各用一个连接，不在同一个事务中，所以在高并发写入时，total 与 items 可能对应略微不同的瞬间--对分页列表来说完全可以接受。

为什么 insert 接收 &amp;Product：调用方传入已经校验过的商品，仓储只负责存储，不重复校验。“用占位 ID 构造 Product 来完成校验”只是过渡写法，第 15 章分层重构时会引入专门的“新建商品”类型。

use std::time::Duration;

use axum::extract::State;

/// 存活检查：进程能响应即可，不访问任何依赖。

    Json(json!({ "status": "ok" }))

/// 就绪检查：数据库在 1 秒内可用才返回 200，否则返回 503。
pub async fn ready(State(state): State<AppState>) -> (StatusCode, Json<Value>) {
    let ping = sqlx::query("SELECT 1").execute(&state.pool);

        // 超时或数据库错误：暂时不要把流量分给本实例

//! 商品接口：`/api/v1/products`，数据存放在 PostgreSQL。

use axum::extract::{Path, Query, State};
use axum::http::{header, StatusCode};
use axum::response::IntoResponse;
use common::error::{DomainError, ValidationError};
use common::ids::ProductId;
use common::pagination::{self, Page};
use common::product::Product;
use serde::Deserialize;

use crate::error::ApiError;
use crate::extract::AppJson;
use crate::state::AppState;

/// 新增商品时尚未分配 ID：用 0 占位完成校验。INSERT 语句不写入 id 列，占位值不会进入数据库。
const UNASSIGNED_ID: ProductId = ProductId::new(0);

/// 新增、修改商品的请求体：只包含允许客戶端设置的字段（第 10.7.2 节）。
#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct ProductInput {
    pub name: String,
    pub price_cents: i64,
    pub stock: i32,
}

impl ProductInput {
    /// 通过 `Product::try_new` 构造，保证商品的不变量。
    fn into_product(self, id: ProductId) -> Result<Product, ApiError> {
        Product::try_new(id, &self.name, self.price_cents, self.stock).map_err(|reason| {
            ApiError::from(DomainError::from(ValidationError::Format { field: "product", 
                reason }))
        })
    }
}

/// 列表查询参数。
#[derive(Debug, Default, Deserialize)]
pub struct ListQuery {
    pub page: Option<u32>,
    pub page_size: Option<u32>,
}

/// `GET /api/v1/products?page=&page_size=`
pub async fn list(
    State(state): State<AppState>,
    Query(query): Query<ListQuery>,
) -> Result<AppJson<Page<Product>>, ApiError> {
    let (page, page_size) = pagination::normalize(query.page, query.page_size);
    let (limit, offset) = pagination::limit_offset(query.page, query.page_size);
    let (items, total) = state.products.list(limit, offset).await?;
    Ok(AppJson(Page::new(items, page, page_size, total)))
}

/// `GET /api/v1/products/{id}`
pub async fn get_one(
    State(state): State<AppState>,
    Path(id): Path<ProductId>,
) -> Result<AppJson<Product>, ApiError> {
    Ok(AppJson(state.products.get(id).await?))
}

/// `POST /api/v1/products`
pub async fn create(
    State(state): State<AppState>,
    AppJson(input): AppJson<ProductInput>,
) -> Result<impl IntoResponse, ApiError> {
    let draft = input.into_product(UNASSIGNED_ID)?;
    let product = state.products.insert(&draft).await?;
    let location = format!("/api/v1/products/{}", product.id());
    Ok((StatusCode::CREATED, [(header::LOCATION, location)], AppJson(product)))
}

/// `PUT /api/v1/products/{id}`：整体替换
pub async fn update(
    State(state): State<AppState>,
    Path(id): Path<ProductId>,
    AppJson(input): AppJson<ProductInput>,
) -> Result<AppJson<Product>, ApiError> {
    let product = input.into_product(id)?;
    Ok(AppJson(state.products.update(&product).await?))
}

/// `DELETE /api/v1/products/{id}`：下架（软删除）
pub async fn remove(State(state): State<AppState>, Path(id): Path<ProductId>) -> 
    Result<StatusCode, ApiError> {
    state.products.delist(id).await?;
    Ok(StatusCode::NO_CONTENT)
}
```

与第 12 章对比，变化集中在三处：

调用变成 .await：仓储方法是异步的。state.products.write(|r| ...) 这种“闭包里操作被锁住的内存数据”的写法消失了--并发控制交给了数据库。

列表直接用 limit_offset：第 1 章写 pagination::limit_offset 时就说过返回 i64“以便直接绑定到 PostgreSQL 的 BIGINT”，现在终于用上了；之前那几行 usize::try_from 转换全部删除。

create 不再生成 ID，Location 头中的 ID 来自数据库返回的商品。

ProductId::new 是 const fn（第 8.9 节的 define_id! 宏生成），所以可以用来初始化常量UNASSIGNED_ID。

//! RustMall 单体服务入口。

use std::time::Duration;

use anyhow::Context;
use monolith::state::AppState;
use monolith::{background, db, routes, shutdown};
use tokio_util::sync::CancellationToken;

/// 监听地址（第 15 章改为从配置读取）。
const ADDR: &str = "0.0.0.0:8080";
/// 未设置 `DATABASE_URL` 时使用的开发数据库（第 13.9.3 节的容器）。第 15 章改为从配置读取。
const DEV_DATABASE_URL: &str = "postgres://rustmall:rustmall@localhost:5432/rustmall";
/// HTTP 服务停止后，等待后台任务结束的最长时间。
const SHUTDOWN_GRACE: Duration = Duration::from_secs(10);

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // 1. 连接数据库并执行迁移：任何一步失败，程序都带着清晰的原因退出
    let database_url = std::env::var("DATABASE_URL").unwrap_or_else(|_| 
        DEV_DATABASE_URL.to_string());
    let pool = db::connect(&database_url).await.context("连接数据库失败")?;
    db::MIGRATOR.run(&pool).await.context("执行数据库迁移失败")?;
    println!("数据库已连接，迁移已是最新");

    // 2. 信号处理与后台任务（第 11 章）
    let token = CancellationToken::new();
    tokio::spawn(shutdown::wait_for_signal(token.clone()));

    let cleaner = tokio::spawn(background::run_periodic(
        Duration::from_secs(60),
        token.clone(),
        || async { println!("[后台] 清理过期的购物车") },
    ));

    // 3. HTTP 服务
    let app = routes::router(AppState::new(pool.clone()));
    let listener = tokio::net::TcpListener::bind(ADDR)
        .await
        .with_context(|| format!("绑定地址 {ADDR} 失败"))?;
    println!("RustMall 单体服务监听 http://{ADDR}");
    // 收到停机信号后：停止接受新连接，等待进行中的请求完成
    axum::serve(listener, app)
        .with_graceful_shutdown(token.clone().cancelled_owned())
        .await
        .context("HTTP 服务异常退出")?;
    println!("HTTP 服务已停止，等待后台任务结束……");

    match tokio::time::timeout(SHUTDOWN_GRACE, cleaner).await {
        Ok(Ok(runs)) => println!("后台任务已停止，共执行 {runs} 次"),
        Ok(Err(e)) => eprintln!("后台任务异常退出：{e}"),
        Err(_) => eprintln!("后台任务未能在 {SHUTDOWN_GRACE:?} 内停止，强制退出"),
    }

    // 4. 最后关闭连接池：此时已经没有任何请求或任务在使用数据库
    pool.close().await;
    println!("数据库连接池已关闭");
    Ok(())
}
```

代码精讲：

anyhow::Result&lt;()&gt; 与 .context(...)：启动阶段可能失败的步骤很多，错误类型各不相同（sqlx::Error、MigrateError、io::Error）。main 不需要区分它们，只需要把“哪一步失败、为什么失败”打印出来--这正是第 4.6 节说的 anyhow 的适用场景。数据库没启动时，输出形如：
```text
Error: 连接数据库失败

Caused by:
    0: error communicating with database: Connection refused (os error 111)
    1: Connection refused (os error 111)
```

不打印连接字符串：它包含密码。日志中出现密钥是常见的安全事故来源（第 16 章的 secrecy crate 会从类型层面防止这类泄漏）。

停机顺序：信号 → 停止 HTTP → 等待后台任务 → 关闭连接池 → 退出。连接池必须最后关闭，否则还在处理的请求会收到 PoolClosed 错误。

先迁移再监听端口：如果迁移失败，服务根本不会开始接收请求，不会出现“新代码跑在旧表结构上”的情况。

### 14.10.15 本章小结

连接池是数据库访问的核心：整个进程一个池，max_connections 和 acquire_timeout 两个参数决定了服务在压力下的表现。

查询：query / query_as / query_scalar 加五种取结果方法；参数一律 bind，动态 SQL 用QueryBuilder；类型宽度、可空性必须与数据库一致。

编译期检查宏能把 SQL 错误变成编译错误，代价是构建依赖数据库或离线数据；RustMall 选择运行时查询配合 #[sqlx::test] 全覆盖。

事务依靠 RAII 自动回滚，&amp;mut *tx 作为执行器；事务要短、加锁顺序要一致、能用一条 SQL 完成的不用事务。

迁移让表结构进入版本控制：已执行即冻结，结构变化写新迁移，服务启动时自动执行。

错误分层：唯一与外键冲突是业务冲突（409），CHECK 冲突和其他数据库错误是内部错误（500）；转换集中在 db::to_domain，领域层不依赖 sqlx。

项目：RustMall 的商品数据第一次真正持久化，删除改为下架，就绪检查开始反映数据库状态，所有HTTP 测试都运行在真实的 PostgreSQL 上。

下一章是第 15 章“工程化：配置、日志、分层”：用 config 与 dotenvy 取代代码里写死的地址和连接字符串，用 tracing 取代 println!，并把处理函数、业务服务、仓储分成清晰的三层，为异步仓储设计 trait。

# 第 16 章 认证与授权

到目前为止，任何人都能新增、修改、下架 RustMall 的商品。本章给系统装上“门禁”：

认证（Authentication）：你是谁？--注册、登录、在后续请求中证明身份。

授权（Authorization）：你能做什么？--普通用户只能浏览，管理员才能管理商品。

本章涉及的 crate：

| crate | 作用 | 小节 |
| --- | --- | --- |
| argon2 | 密码哈希（当前推荐的算法） | 16.2 |
| jsonwebtoken | 签发与校验 JWT 访问令牌 | 16.3 |
| secrecy | 把密码、密钥包装成“不会被意外打印”的类型 | 16.4 |
| rand | 生成密码学安全的随机数 | 16.4.4 |
| chrono | 时间类型（用户的注册时间） | 16.6 |

安全提示：本章讲的是业界成熟的标准做法，但安全是一个需要持续投入的领域。上线真实系统前，请阅读 OWASP 的《Authentication Cheat Sheet》《Password Storage Cheat Sheet》等资料，并让有经验的人审查代码。

## 16.1 认证与授权基础

### 16.1.1 【入门】一次登录的完整流程
```text
1. 注册：客戶端 → POST /auth/register {username, password}
         服务端：校验 → 计算密码哈希 → 存入 users 表（只存哈希，不存密码）

2. 登录：客戶端 → POST /auth/login {username, password}
         服务端：查出哈希 → 校验密码 → 签发访问令牌（access token）

3. 访问：客戶端 → GET /users/me   请求头 Authorization: Bearer <令牌>
         服务端：校验令牌签名与有效期 → 得知“这是用户 7，角色 user” → 处理请求
```

HTTP 是无状态的：每个请求都是独立的，服务端不会“记得”你刚刚登录过。所以登录之后，客戶端必须在每个请求中带上能证明身份的凭证。

### 16.1.2 【进阶】会话与令牌两种方案

|  | 服务端会话（Session） | 自包含令牌（JWT） |
| --- | --- | --- |
| 凭证内容 | 随机的会话 ID | 签名过的用户信息（ID、角色、过期时间） |
| 服务端存储 | 需要（内存、Redis、数据库） | 不需要：校验签名即可 |
| 主动注销 / 封禁 | 删除会话即可，立即生效 | 令牌在过期前一直有效，需要额外机制 |
| 横向扩展 | 所有实例共享会话存储 | 任意实例都能独立校验 |
| 典型载体 | Cookie | Authorization: Bearer 请求头 |
| 适合 | 传统网站 | API、移动端、微服务 |

RustMall 是面向前端和移动端的 API，并且会在第 26 章拆分成多个服务--每个服务都要能独立识别用户，所以选择 JWT。JWT 的主要缺点（无法立即吊销）在 16.3.6 节讨论应对方法。

### 16.1.3 【入门】401 与 403

| 状态码 | 名称 | 含义 | RustMall 错误码 |
| --- | --- | --- | --- |
| 401 | Unauthorized | 没有认证：没带令牌、令牌无效或过期、用户名密码错误 | UNAUTHORIZED |
| 403 | Forbidden | 认证了但无权限：普通用户尝试管理商品 | FORBIDDEN |

401 的名字有历史包袱（字面意思是“未授权”，实际含义是“未认证”）。按 HTTP 规范，401 响应应带上WWW-Authenticate 头，告诉客戶端该用什么方式认证，对令牌认证来说就是 WWW-Authenticate:Bearer。

2. 列出 RustMall 第 9 章 API 文档中的每个接口，标出它需要“无需登录 / 登录用户 / 管理员”哪一级权限。

## 16.2 密码存储：argon2

### 16.2.1 【入门】为什么不能存明文、也不能只做普通哈希

明文存储：数据库一旦泄露（SQL 注入、备份文件外流、内部人员），所有用户的密码直接暴露；而很多人在不同网站使用同一个密码。

普通哈希（MD5、SHA-256）：哈希是单向的，看起来安全，但它们太快了。一块显卡每秒可以计算数十亿次 SHA-256，配合常见密码字典，大部分弱密码几分钟内就能被反推出来。

只做哈希不加盐：相同密码得到相同哈希，攻击者可以预先计算“密码 → 哈希”的大表（彩虹表）批量查找。

正确做法是使用专门的密码哈希函数：

1. 加盐：每个用户生成一个随机的“盐”，与密码一起哈希。相同密码的两个用户，哈希完全不同，预计算的大表失效。

2. 故意很慢、并且消耗大量内存：计算一次需要几十毫秒、几十 MB 内存。对正常登录毫无影响，但让暴力破解的成本提高几个数量级--尤其是“消耗内存”这一点，让显卡和专用芯片难以大规模并行。

Argon2 是 2015 年密码哈希竞赛的优胜者，其中的 Argon2id 变体是 OWASP 当前的首选推荐。

### 16.2.2 【入门】argon2 crate 的基本用法
```toml
[dependencies]
argon2 = "0.5"
```
```rust
use argon2::password_hash::rand_core::OsRng;
use argon2::password_hash::{PasswordHash, PasswordHasher, PasswordVerifier, SaltString};
use argon2::Argon2;

fn main() -> Result<(), argon2::password_hash::Error> {
    let password = "S3cure-Passw0rd";

    // 1. 生成随机盐（OsRng：操作系统提供的密码学安全随机数）
    let salt = SaltString::generate(&mut OsRng);

    // 2. 计算哈希；Argon2::default() 是 Argon2id 加推荐参数
    let hash = Argon2::default().hash_password(password.as_bytes(), &salt)?.to_string();
    println!("{hash}");

    // 3. 校验：解析存储的哈希字符串，再验证
    let parsed = PasswordHash::new(&hash)?;
    let ok = Argon2::default().verify_password(password.as_bytes(), &parsed).is_ok();
    let bad = Argon2::default().verify_password(b"wrong", &parsed).is_ok();
    println!("{ok} {bad}");
    Ok(())
}
```

输出形如：
```text
$argon2id$v=19$m=19456,t=2,p=1$k7mXo3HhP1Yw6eT6vjzP5A$8c0yV4Vh…（省略）
true false
```

### 16.2.3 【进阶】PHC 字符串格式

哈希结果是一个自描述的字符串（PHC 格式），用 $ 分隔：

| 部分 | 示例 | 含义 |
| --- | --- | --- |
| 算法 | argon2id | 算法变体 |
| 版本 | v=19 | Argon2 版本 0x13 |
| 参数 | m=19456,t=2,p=1 | 内存 19 MiB、迭代 2 次、并行度 1 |
| 盐 | k7mX… | Base64 编码的随机盐 |
| 哈希 | 8c0y… | Base64 编码的哈希值 |

因为盐和参数都写在字符串里，数据库只需要一个 password_hash TEXT 列（第 13 章已经这样设计）。将来提高参数强度时，旧哈希仍能用它自己记录的参数验证；用户下次登录成功时，再用新参数重新计算并保存即可（“登录时升级哈希”）。

### 16.2.4 【进阶】参数选择

Argon2::default() 使用 OWASP 推荐的最低配置之一：Argon2id、m = 19 MiB、t = 2、p = 1。需要自定义时：
```rust
use argon2::{Algorithm, Argon2, Params, Version};

// 内存 64 MiB、迭代 3 次、并行度 1、输出 32 字节
let params = Params::new(64 * 1024, 3, 1, Some(32))?;
let argon2 = Argon2::new(Algorithm::Argon2id, Version::V0x13, params);
```

调参原则：在生产服务器上测量，让一次哈希耗时在几十毫秒到几百毫秒之间。注意内存参数会乘以并发登录数：64 MiB × 100 个同时登录 = 6.4 GB，要结合机器内存和登录接口的限流（第 39 章）一起考虑。

### 16.2.5 【精通】在异步服务中计算哈希

Argon2 是故意很慢的 CPU 密集型计算。在 Tokio 的工作线程上直接执行，会让这个线程几十毫秒内无法处理任何其他任务（第 11 章“不要阻塞运行时”）。正确做法是交给阻塞线程池：
```text
let hash = tokio::task::spawn_blocking(move || {
    let salt = SaltString::generate(&mut OsRng);
    Argon2::default().hash_password(password.as_bytes(), &salt).map(|h| h.to_string())
})
.await??;
```

spawn_blocking 的闭包必须是 'static 的，所以用 move 把密码的所有权移进去。两个 ?：第一个处理“阻塞任务本身 panic 或被取消”（JoinError），第二个处理哈希函数自己的错误。

调试构建很慢：Argon2 在未优化的 debug 构建中可能慢上几十倍。第 11 章给 workspace 加的[profile.dev.package."*"] opt-level = 2 让所有依赖（包括 argon2）在 debug 构建中也被优化，测试速度因此正常。

### 16.2.6 【精通】登录接口的时序攻击

一个看起来合理的登录实现：
```text
let Some(user) = repo.find_by_username(&username).await? else {
    // 用户不存在：立即返回
    return Err(unauthorized());
};
// 用户存在：计算 Argon2（约 50 毫秒）
if !verify(&password, &user.password_hash) { return Err(unauthorized()); }
```

两种失败返回的是同样的 401 和同样的消息，但耗时不同：用户不存在时 1 毫秒返回，存在时 50 毫秒返回。攻击者测量响应时间，就能判断某个用户名是否注册过。

用户不存在时，也执行一次预先准备的假哈希校验，减少明显的快速失败路径。它不能保证总耗时严格相同：首次初始化、数据库查询、调度和负载仍会造成差异；还需限流与监测。

### 16.2.7 常见错误与解读

| 报错 / 现象 | 原因 | 修复 |
| --- | --- | --- |
| no function or associated item named 'generate' found for struct'SaltString' | 关闭了默认 feature，缺少ran d | 保留 argon2 的默认 feature |
| password hash string invalid | 数据库中的哈希不是 PHC 格式（例如测试数据里的placeho lder） | 用程序生成的哈希；第 13 章的示例用户无法登录是预期行为 |
| 测试中注册、登录非常慢 | debug 构建未优化 argon2 | 确认[profile.dev.packag e."*"] opt-level = 2 |
| 登录接口拖慢了其他请求 | 在异步线程上直接计算哈希 | spawn_blocking |
| the method `hash_password` exists... but trait bounds were not sa tisfied / 找不到方法 | 没有导入 PasswordHasher /PasswordVerifier trait | use argon2::password_hash::{PasswordHasher, PasswordVerifier}; |

## 16.3 JWT：jsonwebtoken

### 16.3.1 【入门】JWT 的结构

JWT（JSON Web Token）是用 . 连接的三段 Base64URL 字符串：
```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI3Iiwicm9sZSI6InVzZXIiLCJleHAiOjE3NjAxNzA0MD 
    B9.Xk3f…
└──────────── 头部 ────────────────┘ └───────────────────── 载荷 ─────────────────────────┘ └签名┘
```

| 部分 | 解码后 | 说明 |
| --- | --- | --- |
| 头部 | {"alg":"HS256","typ":"JWT"} | 签名算法 |
| 载荷 | {"sub":"7","role":"user","exp":1760170400} | 声明（claims） |
| 签名 | 二进制 | 用密钥对“头部.载荷”计算的签名 |

关键认识：载荷只是 Base64 编码，任何人都能解码查看（把令牌粘贴到 jwt.io 试试）。JWT 保证的是不可篡改，而不是保密：改动载荷中的任何一个字符，签名就对不上了。所以载荷里不要放密码、手机号等敏感信息。

### 16.3.2 【入门】标准声明

| 声明 | 全称 | 含义 |
| --- | --- | --- |
| sub | subject | 主体，通常是用户 ID（规范要求是字符串） |
| exp | expiration | 过期时间（Unix 秒），过期后令牌无效 |
| iat | issued at | 签发时间 |
| nbf | not before | 在此时间之前无效 |
| iss | issuer | 签发者，例如 rustmall |
| aud | audience | 接收方，例如某个具体服务 |
| jti | JWT ID | 令牌唯一 ID，用于吊销名单 |

除标准声明外可以加入自定义声明，RustMall 加入 role。

### 16.3.3 【进阶】签名算法

| 算法 | 类型 | 密钥 | 适用 |
| --- | --- | --- | --- |
| HS256 | 对称（HMAC-SHA256） | 签发与校验共用一个密钥 | 单体服务，或签发方与校验方是同一个团队 |

| 算法 | 类型 | 密钥 | 适用 |
| --- | --- | --- | --- |
| RS256 / ES256 /EdDSA | 非对称 | 私钥签发，公钥校验 | 多服务：只有认证服务持有私钥，其他服务只拿公钥 |

单体阶段 RustMall 使用 HS256。HS256 密钥必须足够长且随机：至少 32 字节（256 位）的随机数据，绝不能是 secret、rustmall123 这类可猜测的字符串--攻击者拿到任意一个令牌，就可以离线暴力猜测密钥，猜中后能伪造任何用户（包括管理员）的令牌。第 26 章拆分微服务后会讨论改用非对称算法。

### 16.3.4 【入门】jsonwebtoken 的基本用法
```toml
[dependencies]
jsonwebtoken = "9"
serde = { version = "1", features = ["derive"] }
```

版本说明：jsonwebtoken 10 开始要求在 feature 中显式选择一个加密后端（如 rust_crypto 或aws_lc_rs），API 基本不变。本书使用 9.x；升级到 10 时，按其文档在 Cargo.toml 中加上后端feature 即可。
```rust
use jsonwebtoken::{decode, encode, get_current_timestamp, Algorithm, DecodingKey, EncodingKey, Header, Validation};
use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Claims {
    sub: String,
    role: String,
    exp: u64,
}

fn main() -> Result<(), jsonwebtoken::errors::Error> {
    let secret = b"a-very-long-random-secret-of-at-least-32-bytes!!";

    // 签发：15 分钟后过期
    let claims = Claims { sub: "7".into(), role: "user".into(), exp: get_current_timestamp() + 15 * 60 };
    let token = encode(&Header::new(Algorithm::HS256), &claims, 
        &EncodingKey::from_secret(secret))?;
    println!("{token}");

    // 校验：签名、算法、exp 都会检查
    let data = decode::<Claims>(&token, &DecodingKey::from_secret(secret), 
        &Validation::new(Algorithm::HS256))?;
    println!("{:?}", data.claims);
    Ok(())
}
```

### 16.3.5 【进阶】Validation：校验什么

Validation::new(Algorithm::HS256) 默认会检查：签名正确、头部中的算法属于允许的列表、exp存在且未过期（带 60 秒容差）。常用设置：
```text
let mut validation = Validation::new(Algorithm::HS256);
// 只接受由 rustmall 签发的令牌
validation.set_issuer(&["rustmall"]);
// 这些声明必须存在，否则校验失败
validation.set_required_spec_claims(&["exp", "sub", "iss"]);
// 时钟误差容忍：秒
validation.leeway = 30;
// 如果使用 aud：validation.set_audience(&["rustmall-api"]);
```

为什么必须限定算法：历史上出现过严重的 JWT 漏洞--服务端读取令牌头部的 alg 字段来决定怎么校验，攻击者把 alg 改成 none（不签名），或者在使用 RS256 的系统中改成 HS256 并用公开的公钥当作HMAC 密钥，从而伪造令牌。jsonwebtoken 要求你在 Validation 中明确指定允许的算法，从根本上杜绝了这类问题。

校验失败时可以查看具体原因：
```rust
use jsonwebtoken::errors::ErrorKind;

match decode::<Claims>(&token, &key, &validation) {
    Ok(data) => println!("用户 {}", data.claims.sub),
    Err(e) => match e.kind() {
        ErrorKind::ExpiredSignature => println!("令牌已过期"),
        ErrorKind::InvalidSignature => println!("签名不正确：令牌被篡改或密钥不对"),
        ErrorKind::InvalidIssuer => println!("签发者不对"),
        _ => println!("其他错误：{e}"),
    },
}
```

对 API 调用方，这些原因统一返回 401 和同一条消息即可；具体原因记在 DEBUG 日志里供排查。

### 16.3.6 【精通】过期、吊销与刷新令牌

JWT 无需查库就能校验，代价是签发后无法收回。常用的组合方案：

1. 访问令牌短有效期：例如 15 分钟。泄露后的危害窗口有限。

2. 刷新令牌（refresh token）：一个长有效期（如 30 天）的随机字符串，存在数据库中、可以吊销。访问令牌过期后，客戶端用刷新令牌换一个新的访问令牌；用户“退出登录”或被封禁时，删除其刷新令牌即可。

3. 令牌版本号：用户表加一个 token_version 列并写入令牌；修改密码时加一，旧令牌在下次校验时被拒绝（需要查一次库或缓存）。

4. 吊销名单：把要吊销的令牌的 jti 放进 Redis，直到它自然过期（第 18 章）。

本章实现第 1 条；刷新令牌的完整设计作为章末练习（16.6.16 节练习 1），第 9 章 API 文档中的refresh_token 字段因此暂时移除。

浏览器若把令牌存入 localStorage，页面中的恶意脚本可能读取它。HttpOnly Cookie 能阻止脚本直接读取 Cookie，但不能防止 XSS 代用户发请求；还须处理 CSRF、SameSite、Secure 与页面脚本安全。移动端应使用系统安全存储。服务端应缩短令牌有效期、使用 HTTPS，并避免把令牌写入日志。

### 16.3.7 常见错误与解读

| 错误 | 原因 | 修复 |
| --- | --- | --- |
| ExpiredSignature | 令牌过期 | 重新登录（或用刷新令牌） |
| InvalidSignature | 密钥不一致：例如多个实例配置了不同的密钥，或者重启后随机生成了新密钥 | 所有实例使用同一个固定的密钥，从配置读取 |
| MissingRequiredCla im("exp") | 签发时没有写 exp | 签发时必须设置过期时间 |
| InvalidAlgorithm | 令牌的算法不在允许列表中 | 签发与校验使用同一算法 |
| Json(...) / InvalidT oken | 令牌格式不对、被截断，或者带了 Bearer 前缀 | 只传入令牌本身 |
| 令牌被前端解码后能看到角色 | JWT 本来就不加密 | 不要在载荷中放敏感数据 |

## 16.4 secrecy 与 rand

### 16.4.1 【入门】秘密值为什么需要专门的类型

密码、JWT 密钥一旦出现在日志中，就等于泄露了。而泄露常常是无意的：
```rust
#[derive(Debug)]
struct LoginRequest {
    username: String,
    password: String,
}

// 某天有人为了排查问题加了这一行
tracing::info!(?req, "收到登录请求");
// 日志：LoginRequest { username: "alice", password: "S3cure-Passw0rd" }
```

secrecy 用类型系统阻止这种事故：被包装的值，Debug 输出固定为 [REDACTED]，想读取原值必须显式调用 expose_secret()--在代码评审中一眼就能看到“这里读取了秘密值”。

### 16.4.2 【入门】基本用法
```toml
[dependencies]
secrecy = "0.10"
```
```rust
use secrecy::{ExposeSecret, SecretString};

fn main() {
    let password = SecretString::from("S3cure-Passw0rd".to_string());

    // 输出：SecretBox<str>([REDACTED])
    println!("{password:?}");

    // 显式读取
    let len = password.expose_secret().len();
    println!("密码长度 {len}");
}
```

| 类型 | 说明 |
| --- | --- |
| SecretString | 秘密字符串（SecretBox&lt;str&gt;） |
| SecretBox&lt;T&gt; | 任意秘密值，堆上存储 |
| ExposeSecret trait | 提供 expose_secret()，读取原值 |

secrecy 还会在值被丢弃时用 zeroize 把内存清零，缩短秘密在内存中停留的时间。

### 16.4.3 【进阶】在配置与请求中使用

从配置反序列化：可以开启 secrecy 的 serde feature 直接反序列化；本书采用更直白的办法--先按String 反序列化再包装，不依赖额外的 feature：
```rust
use secrecy::SecretString;
use serde::{Deserialize, Deserializer};

fn deserialize_secret<'de, D: Deserializer<'de>>(deserializer: D) -> Result<SecretString, 
    D::Error> {
    String::deserialize(deserializer).map(SecretString::from)
}

#[derive(Debug, Deserialize)]
struct AuthSettings {
    #[serde(deserialize_with = "deserialize_secret")]
    jwt_secret: SecretString,
}
```

在请求处理中：HTTP 层把请求体中的密码字符串立刻转成 SecretString，之后在服务层、哈希函数之间传递的都是 SecretString，只在真正计算哈希的那一行调用 expose_secret()。

secrecy 会隐藏 Debug 输出，并在受管内存被释放时尽力清零；它不能阻止业务显式复制秘密。SecretString 是否实现 Clone 应以所用版本为准，0.10 系列允许克隆。这里选择在启动时构造签名密钥，并用 Arc 共享，目的是减少副本，而非依赖一个不存在的禁止克隆规则。

### 16.4.4 【入门】rand：生成随机密钥

生成 JWT 密钥这类数据，必须使用密码学安全的随机数生成器：
```toml
[dependencies]
rand = "0.9"
```
```rust
fn main() {
    // rand 的默认生成器是密码学安全的，由操作系统的随机源定期重新播种
    let key: [u8; 32] = rand::random();
    let hex: String = key.iter().map(|b| format!("{b:02x}")).collect();
    println!("{hex}");
}
```

命令行中同样可以生成：
```text
openssl rand -base64 48
```

不要用 rand 的“小型”或“可预测”生成器（如 SmallRng）生成任何与安全相关的数据，也不要用当前时间、进程 ID 当随机源。

## 16.5 在 Axum 中实现认证与授权

### 16.5.1 【入门】用提取器表达“需要登录”

第 12 章讲过，实现 FromRequestParts 的类型可以作为处理函数参数。把“当前用户”做成提取器：
```rust
pub struct CurrentUser {
    pub id: UserId,
    pub role: Role,
}

// 处理函数声明了 CurrentUser 参数 → 自动要求登录
async fn me(user: CurrentUser) -> String {
    format!("你是用户 {}", user.id)
}
```

提取器内部读取 Authorization 头、校验令牌；失败时返回 401，处理函数根本不会被调用。

授权同理：再定义一个 AdminUser 提取器，内部先提取 CurrentUser，再检查角色。“这个接口需要管理员”就体现在函数签名上：
```rust
async fn create_product(_admin: AdminUser, ValidJson(input): ValidJson<ProductInput>) { /* ... */ }
```

### 16.5.2 【进阶】提取器与中间件的比较

另一种做法是用中间件（axum::middleware::from_fn）保护整组路由：

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 提取器（本书采用） | 权限写在函数签名上，一目了然；忘了加参数就拿不到用户信息，不容易漏 | 每个处理函数都要声明 |
| 中间件 | 一处配置保护一批路由 | 处理函数签名上看不出权限要求；路由调整时容易漏掉保护 |

两者可以组合：中间件负责“整组路由都必须登录”，提取器负责细粒度的角色检查。

### 16.5.3 【进阶】可选登录

有些接口登录与否都能访问，但登录后返回更多信息（例如商品详情中显示“你是否收藏过”）。Axum 0.8中，Option&lt;T&gt; 作为提取器要求 T 实现 OptionalFromRequestParts，用来区分“没有凭证”（返回None）和“凭证有误”（返回错误）。RustMall 目前没有这种接口，需要时再实现。

### 16.5.4 【精通】授权模型

| 模型 | 说明 | RustMall |
| --- | --- | --- |
| RBAC（基于角色） | 用户拥有角色，角色决定能做什么 | user / admin 两个角色 |
| 资源归属检查 | “只能看自己的订单”：比较资源的所有者与当前用户 | 第 26 章订单接口 |
| ABAC（基于属性） | 规则可以引用用户、资源、环境的任意属性 | 超出本书范围 |

一个常被忽视的原则：访问他人的资源返回 404 而不是 403（第 9 章 API 文档已经这样约定），不让攻击者通过状态码探测资源是否存在。

2. 用 axum::middleware::from_fn 写一个中间件版本的登录检查，保护一组路由，与提取器版本对比。

```rust
//! 认证基础设施：用户模型、密码哈希、访问令牌。

pub mod jwt;
pub mod password;

use chrono::{DateTime, Utc};
use common::error::{DomainError, DomainResult};
use common::ids::UserId;
use serde::{Deserialize, Serialize};

/// 用户角色。数据库中以小写文本存储（第 13.9.4 节的 CHECK 约束）。
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum Role {
    User,
    Admin,
}

impl Role {
    /// 数据库中的文本表示。
    pub const fn as_str(self) -> &'static str {
        match self {
            Role::User => "user",
            Role::Admin => "admin",
        }
    }

    /// 从数据库文本解析。数据库有 CHECK 约束，出现未知值说明数据被破坏，按内部错误处理。
    pub fn from_db(text: &str) -> DomainResult<Self> {
        match text {
```

```rust
//! 密码哈希（Argon2id）。计算在阻塞线程池中进行，不占用异步工作线程（第 16.2.5 节）。

use std::sync::LazyLock;

use argon2::password_hash::rand_core::OsRng;
use argon2::password_hash::{PasswordHash, PasswordHasher, PasswordVerifier, SaltString};
use argon2::Argon2;
use common::error::{DomainError, DomainResult};
use secrecy::{ExposeSecret, SecretString};

/// 用户不存在时用于校验的假哈希，让“用户不存在”与“密码错误”耗时一致（第 16.2.6 节）。
static DUMMY_HASH: LazyLock<String> = LazyLock::new(|| {
    let salt = SaltString::generate(&mut OsRng);
    Argon2::default()
        .hash_password(b"rustmall-dummy-password", &salt)
        .map(|h| h.to_string())
        .expect("对固定输入计算 Argon2 哈希不会失败")
});

/// 计算密码哈希，返回 PHC 格式字符串。
pub async fn hash(password: SecretString) -> DomainResult<String> {
    tokio::task::spawn_blocking(move || {
        let salt = SaltString::generate(&mut OsRng);
        Argon2::default()
            .hash_password(password.expose_secret().as_bytes(), &salt)
            .map(|h| h.to_string())
    })
    .await
    .map_err(|e| DomainError::Internal(format!("密码哈希任务失败：{e}")))?
    .map_err(|e| DomainError::Internal(format!("密码哈希失败：{e}")))
}

/// 校验密码。`stored` 为 `None`（用户不存在）时与假哈希比较，结果一定是 `false`，但耗时相同。
pub async fn verify(password: SecretString, stored: Option<String>) -> DomainResult<bool> {
    tokio::task::spawn_blocking(move || {
        let user_exists = stored.is_some();
        let hash = stored.unwrap_or_else(|| DUMMY_HASH.clone());
        let parsed = PasswordHash::new(&hash)?;
        let matches = Argon2::default()
            .verify_password(password.expose_secret().as_bytes(), &parsed)
            .is_ok();
        Ok::<bool, argon2::password_hash::Error>(user_exists && matches)
    })
    .await
    .map_err(|e| DomainError::Internal(format!("密码校验任务失败：{e}")))?
    .map_err(|e| DomainError::Internal(format!("存储的密码哈希格式不正确：{e}")))
}
```

代码精讲：

LazyLock（第 7.8 节）：假哈希在第一次需要时计算一次，之后复用。expect 在这里是合理的：输入是固定的，失败意味着 argon2 库本身坏了，属于第 4.7 节说的“不可能发生的情况”。

user_exists &amp;&amp; matches：用户不存在时无论如何返回 false。如果只看 matches，攻击者输入假哈希对应的那个固定密码，就能让“不存在的用户”校验成功--虽然后面查不到用户，但这类“碰巧正确”的逻辑漏洞要在源头堵死。

Ok::&lt;bool, argon2::password_hash::Error&gt;(...)：闭包中用了 ?，编译器需要知道闭包返回的 Result 的错误类型，这种写法叫“涡轮鱼”（turbofish）标注。

密码以 SecretString 按值传入：spawn_blocking 需要 'static 的闭包，按值移动正好满足；闭包结束时密码被丢弃，内存被清零。

```rust
//! JWT 访问令牌：HS256 签名。

use common::error::{DomainError, DomainResult};
use common::ids::UserId;
use jsonwebtoken::{decode, encode, get_current_timestamp, Algorithm, DecodingKey, EncodingKey, Header, Validation};
use secrecy::{ExposeSecret, SecretString};
use serde::{Deserialize, Serialize};

use super::{Role, User};

/// 令牌载荷。只放身份与角色，不放任何敏感信息（载荷可以被任何人解码）。
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Claims {
    /// 用户 ID（JWT 规范要求 sub 为字符串）
    pub sub: String,
    pub role: Role,
    pub iss: String,
    pub iat: u64,
    pub exp: u64,
}

impl Claims {
    /// 解析出用户 ID。签名正确但 sub 不是数字，只可能是签发逻辑有缺陷，按“令牌无效”处理。
    pub fn user_id(&self) -> DomainResult<UserId> {
        self.sub.parse::<i64>().map(UserId::new).map_err(|_| invalid_token())
    }
}

/// 登录接口的响应体。
#[derive(Debug, Serialize)]
pub struct AccessToken {
    pub access_token: String,
    pub token_type: &'static str,
    /// 有效期（秒）
    pub expires_in: u64,
}

/// 签名与校验所需的一切。启动时由配置构造一次，之后只读共享。
pub struct JwtKeys {
    encoding: EncodingKey,
    decoding: DecodingKey,
    validation: Validation,
    issuer: String,
    ttl_secs: u64,
}

impl JwtKeys {
    pub fn new(secret: &SecretString, issuer: &str, ttl_secs: u64) -> Self {
        let bytes = secret.expose_secret().as_bytes();
        let mut validation = Validation::new(Algorithm::HS256);
        validation.set_issuer(&[issuer]);
        validation.set_required_spec_claims(&["exp", "sub", "iss"]);
        validation.leeway = 30;
        Self {
            encoding: EncodingKey::from_secret(bytes),
            decoding: DecodingKey::from_secret(bytes),
            validation,
            issuer: issuer.to_string(),
            ttl_secs,
        }
    }

    /// 为用户签发访问令牌。
    pub fn issue(&self, user: &User) -> DomainResult<AccessToken> {
        let now = get_current_timestamp();
        let claims = Claims {
            sub: user.id.to_string(),
            role: user.role,
            iss: self.issuer.clone(),
            iat: now,
            exp: now + self.ttl_secs,
        };
        let token = self.sign(&claims)?;
        Ok(AccessToken { access_token: token, token_type: "Bearer", expires_in: self.ttl_secs 
            })
    }

    /// 校验令牌，返回载荷。任何失败都统一为“令牌无效”，具体原因只写 DEBUG 日志。
    pub fn verify(&self, token: &str) -> DomainResult<Claims> {
        decode::<Claims>(token, &self.decoding, &self.validation)
            .map(|data| data.claims)
            .map_err(|e| {
                tracing::debug!(error = %e, "访问令牌校验失败");
                invalid_token()
            })
    }

    fn sign(&self, claims: &Claims) -> DomainResult<String> {
        encode(&Header::new(Algorithm::HS256), claims, &self.encoding)
            .map_err(|e| DomainError::Internal(format!("签发令牌失败：{e}")))
    }
}

fn invalid_token() -> DomainError {
    DomainError::Unauthorized("登录已过期或令牌无效，请重新登录".to_string())
}
```

```rust
//! 用户仓储的 PostgreSQL 实现。

use chrono::{DateTime, Utc};
use common::error::{DomainError, DomainResult};
use common::ids::UserId;
use sqlx::PgPool;
use tracing::instrument;

use super::{UserCredentials, UserRepository};
use crate::auth::{Role, User};
use crate::db;

#[derive(Debug, sqlx::FromRow)]
struct UserRow {
    id: i64,
    username: String,
    role: String,
    created_at: DateTime<Utc>,
}

impl UserRow {
    fn into_user(self) -> DomainResult<User> {
        Ok(User {
            id: UserId::new(self.id),
            username: self.username,
            role: Role::from_db(&self.role)?,
            created_at: self.created_at,
        })
    }
}

/// 用户信息 + 密码哈希：`flatten` 让 UserRow 的字段从同一行中读取（第 14.4.5 节）。
#[derive(Debug, sqlx::FromRow)]
struct CredentialsRow {
    #[sqlx(flatten)]
    user: UserRow,
    password_hash: String,
}

#[derive(Debug, Clone)]
pub struct PgUserRepo {
    pool: PgPool,
}

impl PgUserRepo {
    pub fn new(pool: PgPool) -> Self {
        Self { pool }
    }
}

impl UserRepository for PgUserRepo {
    #[instrument(level = "debug", skip(self, password_hash))]
    async fn insert(&self, username: &str, password_hash: &str) -> DomainResult<User> {
        let result = sqlx::query_as::<_, UserRow>(
            "INSERT INTO users (username, password_hash) VALUES ($1, $2) \
             RETURNING id, username, role, created_at",
        )
        .bind(username)
        .bind(password_hash)
        .fetch_one(&self.pool)
        .await;

        match result {
            Ok(row) => row.into_user(),
            // 用户名唯一约束：翻译成比通用 Conflict 更具体的错误
            Err(err) if is_unique_violation(&err) => {
                Err(DomainError::AlreadyExists { entity: "用户名", id: username.to_string() })
            }
            Err(err) => Err(db::to_domain(err)),
        }
    }

    #[instrument(level = "debug", skip(self))]
    async fn find_credentials(&self, username: &str) -> DomainResult<Option<UserCredentials>> 
        {
        let row = sqlx::query_as::<_, CredentialsRow>(
            "SELECT id, username, role, created_at, password_hash FROM users WHERE username = $1",
        )
        .bind(username)
        .fetch_optional(&self.pool)
        .await
        .map_err(db::to_domain)?;

        row.map(|r| Ok(UserCredentials { user: r.user.into_user()?, password_hash: 
            r.password_hash }))
            .transpose()
    }

    #[instrument(level = "debug", skip(self))]
    async fn get(&self, id: UserId) -> DomainResult<User> {
        sqlx::query_as::<_, UserRow>("SELECT id, username, role, created_at FROM users WHERE 
            id = $1")
            .bind(id.get())
            .fetch_optional(&self.pool)
            .await
            .map_err(db::to_domain)?
            .ok_or_else(|| DomainError::not_found("用户", id))?
            .into_user()
    }
}

fn is_unique_violation(err: &sqlx::Error) -> bool {
    err.as_database_error()
        .is_some_and(|db_err| matches!(db_err.kind(), 
            sqlx::error::ErrorKind::UniqueViolation))
}
```

代码精讲：

Option&lt;Result&lt;T&gt;&gt; → Result&lt;Option&lt;T&gt;&gt;：row.map(...) 得到Option&lt;DomainResult&lt;UserCredentials&gt;&gt;，.transpose() 把它翻转成DomainResult&lt;Option&lt;...&gt;&gt;，正好是函数的返回类型。这是处理“可能不存在、存在时转换可能失败”的标准写法（第 4.2 节）。

```rust
//! 认证服务：注册、登录、令牌校验。

use std::sync::Arc;

use common::error::{DomainError, DomainResult, ValidationError};
use common::ids::UserId;
use common::text::normalize_username;
use secrecy::{ExposeSecret, SecretString};
use tracing::{info, instrument};

use crate::auth::jwt::{AccessToken, Claims, JwtKeys};
use crate::auth::{password, User};
use crate::repo::UserRepository;

/// 密码长度范围（按字符计）。上限防止超长输入拖慢哈希计算。
pub const PASSWORD_MIN_CHARS: usize = 8;
pub const PASSWORD_MAX_CHARS: usize = 64;

/// 注册或登录的输入。密码以 `SecretString` 保存，Debug 输出不会泄露。
#[derive(Debug)]
pub struct Credentials {
    pub username: String,
    pub password: SecretString,
}

#[derive(Clone)]
pub struct AuthService<R> {
    repo: R,
    jwt: Arc<JwtKeys>,
}
impl<R: UserRepository> AuthService<R> {
    pub fn new(repo: R, jwt: JwtKeys) -> Self {
        Self { repo, jwt: Arc::new(jwt) }
    }

    /// 注册普通用户。
    #[instrument(skip_all, fields(username = %input.username))]
    pub async fn register(&self, input: Credentials) -> DomainResult<User> {
        let username = normalize_username(&input.username)
            .map_err(|reason| DomainError::from(ValidationError::Format { field: "username", 
                reason }))?;

        let chars = input.password.expose_secret().chars().count();
        if !(PASSWORD_MIN_CHARS..=PASSWORD_MAX_CHARS).contains(&chars) {
            return Err(ValidationError::Length {
                field: "password",
                min: PASSWORD_MIN_CHARS,
                max: PASSWORD_MAX_CHARS,
                actual: chars,
            }
            .into());
        }

        let hash = password::hash(input.password).await?;
        let user = self.repo.insert(&username, &hash).await?;
        info!(user_id = %user.id, "用户已注册");
        Ok(user)
    }

    /// 登录。用户不存在与密码错误返回完全相同的错误，耗时也相同。
    #[instrument(skip_all, fields(username = %input.username))]
    pub async fn login(&self, input: Credentials) -> DomainResult<AccessToken> {
        // 用户名格式不合法时，按“用户不存在”处理，不返回 422（不泄露注册规则以外的信息）
        let credentials = match normalize_username(&input.username) {
            Ok(name) => self.repo.find_credentials(&name).await?,
            Err(_) => None,
        };

        let stored_hash = credentials.as_ref().map(|c| c.password_hash.clone());
        let password_ok = password::verify(input.password, stored_hash).await?;

        match credentials {
            Some(c) if password_ok => {
                let token = self.jwt.issue(&c.user)?;
                info!(user_id = %c.user.id, "登录成功");
                Ok(token)
            }
            _ => {
                info!("登录失败：用户名或密码错误");
                Err(DomainError::Unauthorized("用户名或密码错误".to_string()))
            }
        }
    }

    /// 校验访问令牌。纯计算，不访问数据库，所以是同步函数。
    pub fn verify_token(&self, token: &str) -> DomainResult<Claims> {
        self.jwt.verify(token)
    }

    /// 当前用户的信息。
    #[instrument(skip(self))]
    pub async fn me(&self, id: UserId) -> DomainResult<User> {
        self.repo.get(id).await
    }
}
```

```rust
/// 当前登录用户。作为处理函数参数时，请求必须带有效的 `Authorization: Bearer <令牌>`。
#[derive(Debug, Clone, Copy)]
pub struct CurrentUser {
    pub id: UserId,
    pub role: Role,
}

impl FromRequestParts<AppState> for CurrentUser {
    type Rejection = ApiError;

    async fn from_request_parts(parts: &mut Parts, state: &AppState) -> Result<Self, 
        Self::Rejection> {
        let token = bearer_token(parts)
            .ok_or_else(|| DomainError::Unauthorized("缺少访问令牌，请先登录".to_string()))?;
        let claims = state.auth.verify_token(token)?;
        Ok(CurrentUser { id: claims.user_id()?, role: claims.role })
    }
}

/// 管理员。作为处理函数参数时，请求者必须已登录且角色为管理员。
#[derive(Debug, Clone, Copy)]
pub struct AdminUser(pub CurrentUser);

impl FromRequestParts<AppState> for AdminUser {
    type Rejection = ApiError;

    async fn from_request_parts(parts: &mut Parts, state: &AppState) -> Result<Self, 
        Self::Rejection> {
        let user = CurrentUser::from_request_parts(parts, state).await?;
        if user.role != Role::Admin {
            return Err(DomainError::Forbidden("需要管理员权限".to_string()).into());
        }
        Ok(AdminUser(user))
    }
}

/// 从 `Authorization` 头中取出 Bearer 令牌。方案名不区分大小写（RFC 7235）。
fn bearer_token(parts: &Parts) -> Option<&str> {
    let value = parts.headers.get(header::AUTHORIZATION)?.to_str().ok()?;
    let (scheme, token) = value.split_once(' ')?;
    let token = token.trim();
    (scheme.eq_ignore_ascii_case("bearer") && !token.is_empty()).then_some(token)
}
```

代码精讲：

impl FromRequestParts&lt;AppState&gt;：直接为具体的状态类型实现，提取器内部可以访问state.auth。通用库会写成 impl&lt;S&gt; FromRequestParts&lt;S&gt; 再配合 FromRef，应用内部的提取器没必要那么抽象。

? 在提取器中的两次转换：ok_or_else 产生 DomainError，? 借助 From&lt;DomainError&gt;for ApiError 转换；verify_token 返回 DomainResult，同理。

AdminUser 复用 CurrentUser：先认证（401），再授权（403），两步的顺序与错误码的含义一致。

bearer_token 返回借用：令牌是请求头中字符串的切片，没有任何复制。then_some 把布尔条件转换为 Option（第 3.4 节）。

请求体结构没有 Debug：ValidJson&lt;T&gt; 只在 T: Debug 时才实现 Debug，所以不派生也不影响使用；这样就不可能有人把整个请求体打印到日志中。

```rust
fn into_response(self) -> Response {
    let (status, code, message) = match self {
        ApiError::BadRequest(message) => (StatusCode::BAD_REQUEST, "BAD_REQUEST", 
            message),
        ApiError::Unprocessable(message) => {
            (StatusCode::UNPROCESSABLE_ENTITY, ErrorKind::InvalidInput.code(), message)
        }
        ApiError::Domain(e) => {
            let kind = e.kind();
            let status = match kind {
                ErrorKind::InvalidInput => StatusCode::UNPROCESSABLE_ENTITY,
                ErrorKind::Unauthorized => StatusCode::UNAUTHORIZED,
                ErrorKind::Forbidden => StatusCode::FORBIDDEN,
                ErrorKind::NotFound => StatusCode::NOT_FOUND,
                ErrorKind::Conflict => StatusCode::CONFLICT,
                ErrorKind::Internal => StatusCode::INTERNAL_SERVER_ERROR,
            };
            let message = if kind == ErrorKind::Internal {
                // 内部错误的细节只进日志（带上当前请求 span 的请求 ID），绝不返回给客戶端
                tracing::error!(error = ?e, "内部错误");
                "服务器内部错误".to_string()
            } else {
                e.to_string()
            };
            (status, kind.code(), message)
        }
    };

    let mut response = (status, Json(ErrorBody { code, message })).into_response();
    if status == StatusCode::UNAUTHORIZED {
        // RFC 7235：401 响应应当告诉客戶端使用哪种认证方式
        response.headers_mut().insert(header::WWW_AUTHENTICATE, 
            HeaderValue::from_static("Bearer"));
    }
    response
}
```

### 16.6.16 本章小结

密码：Argon2id 配合随机盐，使用 PHC 格式存储；哈希计算放入 spawn_blocking。用户不存在时执行假哈希校验，减少明显的时序差异，并结合登录限流。

令牌：JWT 只防篡改不保密；HS256 密钥至少 32 字节随机值；Validation 中固定算法、签发者与必需声明；访问令牌短有效期，刷新与吊销需要额外机制。

秘密值：SecretString 让密码和密钥在日志中显示为 [REDACTED]，读取必须显式expose_secret()；危险的配置缺失应当让服务无法启动。

Axum：CurrentUser、AdminUser 两个提取器把“需要登录”“需要管理员”写在函数签名上；401 与 403 各有含义，401 响应带 WWW-Authenticate: Bearer。

工程：认证依旧遵循三层结构，服务层用内存仓储测试；集成测试的公共代码放进tests/support/mod.rs。

下一章是第 17 章“测试”：系统讲解 Rust 的测试体系--单元测试、集成测试、文档测试的组织方式，#[sqlx::test] 的进阶用法与夹具，用 mockall 自动生成测试替身，用 testcontainers 在测试中自动启动数据库容器，用 insta 做快照测试，用 proptest 做性质测试，并为 RustMall 建立完整的测试套件与覆盖率报告。

### 16.6.17 本章练习

1. 刷新令牌：新建 refresh_tokens 表（token_hash、user_id、expires_at、revoked_at），登录时额外签发一个 32 字节随机刷新令牌（数据库中只存它的 SHA-256 哈希），实现 POST/api/v1/auth/refresh 与 POST /api/v1/auth/logout。思考：刷新令牌为什么也要存哈希而不是原文？

2. 登录时升级哈希：把 Argon2 参数提高到 m = 64 MiB；用户登录成功时，如果其哈希中的参数低于当前参数，就重新计算并保存。

3. 初始化管理员：增加一个命令行子程序 cargo run -p monolith --bin create-admin -- &lt;用户名&gt;（src/bin/create-admin.rs，第 8.3 节），从标准输入读取密码，直接创建管理员账号，替代手动执行 SQL。

4. 修改密码：PUT /api/v1/users/me/password，需要旧密码。修改成功后，如何让该用户已签发的访问令牌全部失效？（提示：16.3.6 节的令牌版本号。）

5. 为 CurrentUser 实现 OptionalFromRequestParts，写一个“登录与否都能访问、登录后多返回一个字段”的示例接口。

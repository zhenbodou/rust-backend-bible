# 第 44 章 Linux、网络、TLS与性能诊断

第43章已经用真实Kafka副本与消费者观察故障，但这些进程仍共享宿主机的CPU、内存、磁盘与网络。现在把视角拉回一次请求：域名是否正确，连接到了谁，证书是否证明了目标身份，代理有没有重复发送写请求，程序是否在资源耗尽之前拒绝新工作？

本章沿用同一套RustMall十角色部署，在edge外增加独立的TLS入口，再把操作系统资源、网络步骤和性能测量连到实际工程。先理解层次，再运行受控实验，最后根据证据决定要改程序、数据库还是部署。

## 44.1 进程取得的资源都有边界

### 44.1.1 【入门】Tokio不会替代操作系统

Tokio调度Rust异步任务，操作系统调度线程并提供CPU、内存、文件描述符与网络。一个异步任务可以等待socket就绪而不独占线程，但CPU计算、同步文件访问或阻塞锁仍可能占住执行线程。

所以“用了async”不等于所有工作都有界。检查每个入口的请求名额、连接池、队列容量和等待时间，才知道下游变慢时内存与在途工作会如何增长。第39章的治理预算在本章继续保留。

### 44.1.2 【进阶】容器共享内核，资源限制不互相替代

命名空间改变进程看到的网络、挂载和进程视图；cgroup约束CPU与内存等资源。CPU配额不足可能造成调度等待和尾延迟，内存达到限制则可能触发OOM终止。只读根文件系统与去除capability限制的是另一组操作权限。

扩大CPU不能直接解除数据库行锁；扩大连接池也不能让一个热点行同时完成多个互斥更新。必须先找到等待发生在哪一层，再选择改变哪种资源。

### 44.1.3 【精通】文件描述符与连接生命周期

文件、监听socket、已建立连接和部分事件设施都需要描述符。连接泄漏、过多空闲连接或配置不合理的连接池可能耗尽进程限制。应观察打开对象类型和增长趋势，而不是看到错误后只把上限改成一个很大的数。

本项目复用reqwest客户端、限制SQLx池与并发；新增TLS代理也设置有限worker_connections、keepalive与临时目录。它们不能证明永不耗尽，但使容量和故障可以被测量。

## 44.2 将一次网络调用拆开观察

### 44.2.1 【入门】DNS、TCP、TLS和HTTP

客户端先决定名称对应哪个地址，再建立传输连接；HTTPS还进行TLS协商与目标身份校验，随后才有HTTP请求和应用鉴权。某一步失败，后面的步骤可能根本没有发生。

“连接不上”可以是名称无法解析、目标没有监听、网络过滤、握手失败或应用返回503。诊断时保留错误类别，不能把所有结果都归成同一个接口超时。

### 44.2.2 【进阶】连接超时与总等待预算

connect timeout针对连接建立；socket读等待、代理空闲读取与应用总预算又有各自语义。比如Nginx的proxy_read_timeout限制相邻读取之间的等待，不是无论响应如何分段都恰好在六秒终止的统一墙钟预算。

当前业务服务仍有外层请求预算，HTTP客户端也保留连接和调用限制。TLS代理增加的边界需要与它们一起理解，不能只看到几个相同数字就认为已经传播了严格跨机deadline。

### 44.2.3 【精通】环境代理会改变观察路径

诊断工具若自动使用HTTP_PROXY或HTTPS_PROXY，请求可能先去另一个代理。项目内部客户端显式no_proxy；新TLS探针直接使用http.client，也不会读取环境代理设置。

代理路径有时是组织网络的必要组成，但应作为明确配置记录。不能在不知情的情况下把代理返回的证书、延迟或错误归因于本地Rust服务。

## 44.3 对照实际部署理解地址

### 44.3.1 【入门】localhost指向当前网络空间

| 调用位置 | 地址示例 | 实际目标 |
| --- | --- | --- |
| 宿主机，原开发入口 | 127.0.0.1:18086 | 发布的edge容器8080 |
| 同一Compose网络 | users:8080 | users服务的内部HTTP监听 |
| edge容器内部 | 127.0.0.1:8080 | edge自己 |
| TLS配置下的宿主机 | localhost:18443 | TLS入口容器8443 |
| TLS代理内部上游 | edge:8080 | 原有edge入口 |

服务名后面的端口是容器监听端口，不是宿主机发布端口。数据库、Redis和Kafka在当前主交付配置中没有公开宿主端口；旧稿把调试端口写成当前主部署能力，需要按实际文件纠正。

### 44.3.2 【进阶】新增HTTPS不能留下明文绕过入口

TLS覆盖配置用`ports: !reset []`取消edge原宿主发布，只由TLS容器发布回环18443。普通Compose列表合并可能保留两个端口，不能把增加一个HTTPS端口当作已经关闭HTTP入口。

运行前应检查合并后的Compose模型，再从宿主实际连接两个端口确认。配置中的!reset语义来自[Docker Compose合并规则](https://docs.docker.com/reference/compose-file/merge/)，只看覆盖文件本身不足以证明最终网络边界。

### 44.3.3 【精通】外部TLS与内部传输分开记录

本章新增配置在TLS代理终止HTTPS，然后通过私有网络连接edge。其他HTTP、gRPC、PostgreSQL、Redis和Kafka连接仍沿原配置。此时可以证明客户端到代理的加密与身份验证，不能声称全链路已经启用TLS或mTLS。

若进一步要求内部服务证书认证，需要逐类配置客户端信任、服务名称、证书轮换与连接恢复，并重新验收。网络标记internal也不等于密码学加密。

## 44.4 先生成可验证的本地证书

### 44.4.1 【入门】证书链与目标名称是两个检查

客户端既要相信签发者，也要确认目标名称出现在证书允许的名称中。本实验叶证书仅包含DNS名称localhost；同一台机器上的127.0.0.1不能据此自动通过IP名称校验。

工具只为当前进程加载指定CA，不向系统或浏览器安装根证书。关闭验证不是本章的排错步骤，错误的根、名称或时间应产生可见失败。

### 44.4.2 【进阶】目录与使用范围

在检查点根目录运行，OpenSSL需3或更新版本：
```sh
python3 scripts/create-tls-lab.py \
  --openssl /absolute/path/to/openssl \
  --output-dir /tmp/rustmall-tls44-private
```

目标目录必须不存在。CA有效30天、叶证书有效7天，仅适合本地实验；生成器使用明确SAN、serverAuth用途和密钥权限。CA私钥不挂载给代理，也不进入源代码或镜像。

本地Docker非root进程需要读取挂载的叶证书与私钥，因此这两个文件在0700私有父目录中设为0444，与第40章文件秘密约定相同。它没有把文件加密；正式系统应使用受控秘密分发与证书生命周期管理。

### 44.4.3 【精通】已经验证与尚未验证的范围

当前验证包含真实TLS1.2和TLS1.3握手、正确CA与localhost成功、错误DNS名称、未列出的IP名称和不受信根失败；还用OpenSSL在未来第八天验证七天叶证书已经过期。

未来时间验证不等同于使用过期证书的在线握手，Python测试端点也不等于Nginx或Rust业务链路。后续实验必须分别证明代理启动、真实业务、故障响应与证书更新，不能把这三组证书检查外推为整个部署已经安全完成。
## 44.5 将TLS接在原有edge外侧

### 44.5.1 【入门】保持原业务边界

TLS代理不验证商品库存、不生成用户身份，也不替代JWT与内部服务token。它负责客户端到入口的传输与服务器身份，收到HTTP以后仍把请求交给原edge，再沿原鉴权、订单、支付、库存与事件链路执行。

因此本章验收必须通过HTTPS完成注册、登录、商品操作和幂等下单，并核对真实数据库效果。只对一个静态欢迎页完成握手，不能证明这条业务链路没有改变。

### 44.5.2 【进阶】完整代理配置
```nginx
worker_processes 1;
pid /tmp/nginx.pid;
error_log /dev/stderr warn;
events { worker_connections 256; }
http {
    # Disable access logs; error logs may include URI. Keep credentials out of URI.
    access_log off;
    client_body_temp_path /tmp/client_body;
    proxy_temp_path /tmp/proxy;
    fastcgi_temp_path /tmp/fastcgi;
    uwsgi_temp_path /tmp/uwsgi;
    scgi_temp_path /tmp/scgi;
    client_max_body_size 4k;
    client_header_timeout 5s;
    client_body_timeout 5s;
    keepalive_timeout 15s;
    send_timeout 5s;
    server_tokens off;
    upstream edge44 { server edge:8080; keepalive 16; }
    server {
        listen 8443 ssl;
        server_name localhost;
        ssl_certificate /run/secrets/tls_server_cert;
        ssl_certificate_key /run/secrets/tls_server_key;
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_session_cache shared:TLS44:1m;
        ssl_session_timeout 5m;
        ssl_session_tickets off;
        error_page 413 = @too_large;
        error_page 502 = @unavailable;
        error_page 504 = @deadline;
        location @too_large {
            default_type application/json;
            add_header Cache-Control no-store always;
            return 413 '{"code":"PAYLOAD_TOO_LARGE","message":"request body too large"}';
        }
        location @unavailable {
            default_type application/json;
            add_header Cache-Control no-store always;
            return 503 '{"code":"UNAVAILABLE","message":"upstream unavailable"}';
        }
        location @deadline {
            default_type application/json;
            add_header Cache-Control no-store always;
            return 504 '{"code":"DEADLINE_EXCEEDED","message":"upstream timeout; result may be unknown"}';
        }
        location / {
            proxy_pass http://edge44;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_set_header Host edge;
            proxy_set_header X-Forwarded-For "";
            proxy_set_header Forwarded "";
            proxy_set_header X-Forwarded-Proto "";
            proxy_set_header X-Rustmall-Budget-Ms "";
            proxy_connect_timeout 500ms;
            proxy_send_timeout 6s;
            proxy_read_timeout 6s;
            proxy_next_upstream off;
        }

```

代理固定上游edge:8080，不接受用户指定目标。清理客户端Forwarded与内部预算提示，Host也由受信配置指定；业务鉴权头继续交给edge按白名单处理。关闭自动上游重试，避免代理在不知道写请求是否已产生效果时自行再发送。

413由代理返回统一JSON；连接拒绝等上游不可用情况映射503，超时映射504，并提示结果可能未知。已有上游业务JSON错误继续按原响应返回。HTTPS握手失败发生在HTTP之前，不能要求它返回业务JSON。

关闭access_log不代表错误日志也不含URI。实测413和上游超时日志含请求行，因此凭据仍应放在规定的请求头或正文中，采集报告还需脱敏；不能把这一配置称为绝不记录请求路径。

### 44.5.3 【进阶】只读容器仍需要临时空间

首次真实启动失败于Nginx尝试创建默认fastcgi_temp目录。虽然本工程没有使用FastCGI，该构建中的模块仍初始化了相应路径。修复将client、proxy、fastcgi、uwsgi和scgi临时目录明确放到16MB tmpfs，保留只读根与非root身份。

这说明“设置read_only”是约束，不是自动修复文件写入行为。应让失败暴露出未声明的写路径，再确认哪些临时写入确实必要，而不是直接把整个根文件系统改回可写。

## 44.6 证书工具与只读探针

### 44.6.1 【进阶】完整实验生成器
```python
"""Create NEW local-only CA and server certificate. Never installs a trusted root.

Use an explicit --openssl executable if needed. Keep this private directory with
its deployment. Files mounted into a non-root container are readable only via
this0700 parent directory, as in chapter40; this is not an encrypted secret store.
"""
from pathlib import Path
import argparse,os,re,shutil,subprocess
p=argparse.ArgumentParser(description=__doc__)
p.add_argument('--output-dir',type=Path,required=True)
p.add_argument('--openssl',default='openssl')
a=p.parse_args();root=a.output_dir.resolve()
exe=shutil.which(a.openssl)
if not exe:raise SystemExit('OpenSSL executable not found')
version=subprocess.run([exe,'version'],capture_output=True,text=True,timeout=5)
match=re.match(r'OpenSSL (\d+)\.',version.stdout)
if version.returncode or not match or int(match[1])<3:
 raise SystemExit('OpenSSL3 or newer required; pass --openssl /absolute/path/to/openssl')
root.mkdir(mode=0o700)
os.umask(0o077)
def openssl(*args):
 result=subprocess.run([exe,*map(str,args)],cwd=root,text=True,capture_output=True)
 if result.returncode:raise RuntimeError('certificate generation failed; incomplete private directory retained')
(root/'ca.cnf').write_text('''[req]
distinguished_name=dn
x509_extensions=ca
prompt=no
[dn]
CN=RustMall44 Local Lab CA
[ca]
basicConstraints=critical,CA:TRUE,pathlen:0
keyUsage=critical,keyCertSign,cRLSign
subjectKeyIdentifier=hash
''')
(root/'server.cnf').write_text('''[req]
distinguished_name=dn
prompt=no
[dn]
CN=localhost
[server]
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:localhost
subjectKeyIdentifier=hash
authorityKeyIdentifier=keyid,issuer
''')
openssl('req','-x509','-newkey','rsa:3072','-noenc','-sha256','-days','30','-config','ca.cnf','-keyout','ca.key','-out','ca.pem')
openssl('req','-new','-newkey','rsa:3072','-noenc','-config','server.cnf','-keyout','server.key','-out','server.csr')
openssl('x509','-req','-in','server.csr','-CA','ca.pem','-CAkey','ca.key','-CAcreateserial','-days','7','-sha256','-extfile','server.cnf','-extensions','server','-out','server.pem')
openssl('verify','-CAfile','ca.pem','-verify_hostname','localhost','server.pem')
for name in ['server.pem','server.key']:(root/name).chmod(0o444)
print('Created local-only CA and7-day localhost certificate. Root trust was NOT installed. Keep private files outside source control.')
```

生成器先验证OpenSSL版本再创建目录；已有目录拒绝且内容保持不变。签发过程失败时保留未完成的私有目录，供操作者检查，不能再次运行时静默覆盖已有私钥。命令输出不打印私钥或密码。

### 44.6.2 【进阶】客户端探针仍然验证身份
```python
"""Read-only HTTPS readiness probe. No insecure bypass, no proxy environment.

Certificate verification is mandatory. --ca supplies a private trust bundle only
for this client process; it does not install trust into the OS or browser.
"""
import argparse,hashlib,http.client,json,ssl,urllib.parse
p=argparse.ArgumentParser(description=__doc__)
p.add_argument('--url',required=True)
p.add_argument('--ca')
a=p.parse_args();url=urllib.parse.urlsplit(a.url)
if url.scheme!='https' or not url.hostname or url.username or url.password or url.path not in ('','/') or url.query or url.fragment:
 p.error('HTTPS origin required, without credentials/path/query/fragment')
context=ssl.create_default_context(cafile=a.ca)
context.minimum_version=ssl.TLSVersion.TLSv1_2
connection=http.client.HTTPSConnection(url.hostname,url.port or 443,context=context,timeout=2)
try:
 connection.connect()
 protocol=connection.sock.version()
 certificate=connection.sock.getpeercert(binary_form=True)
 connection.request('GET','/readyz',headers={'Connection':'close'})
 response=connection.getresponse();response.read(4097)
 result={'status':response.status,'tls':protocol,'certificate_sha256':hashlib.sha256(certificate).hexdigest()}
 print(json.dumps(result))
 if response.status!=200:raise SystemExit('readiness not200')
finally:connection.close()
```

在TLS覆盖环境运行以后：
```sh
python3 scripts/tls-probe.py \
  --url https://localhost:18443 \
  --ca .tls44.local/ca.pem
```

探针只接受HTTPS origin，拒绝URL内凭据、额外路径和查询参数；它读取readyz并记录协商版本与公开证书指纹。提供CA仅改变该客户端进程的信任，没有把浏览器或操作系统变成信任此实验CA。

### 44.6.3 【精通】存活、就绪与TLS入口各看一层

进程存在只能证明它还没有退出；内部readyz检查依赖；外部TLS探针还验证入口端口、证书和代理路径。某层成功不自动证明其他层成功。

当前Nginx基础镜像没有本项目的Rust探针，不能伪称它已经在容器中运行同一种HTTPS健康程序。完整验收由外部可信客户端检查TLS入口；内部edge探针继续按原路径工作。

## 44.7 在同一CA下更新叶证书

### 44.7.1 【入门】先分清根信任与叶身份

客户端相信CA，代理使用叶证书与叶私钥。叶证书更新可以继续由同一CA签发，使客户端无需为了普通续期替换根信任；若CA本身需要轮换，就必须另设计新旧根的信任重叠与退役流程。

JWT签名密钥、数据库密码和TLS私钥也各自有生命周期。本章更换叶私钥不会注销已经签发且数据库仍有效的用户会话。

### 44.7.2 【进阶】完整本地续期工具
```python
"""Issue a NEW localhost leaf under the existing LAB CA. Does not modify old files.

The new directory contains no CA private key. Recreate only the TLS proxy with
its new secret mounts; this simple local procedure does not promise zero downtime.
"""
from pathlib import Path
import argparse,os,re,secrets,shutil,subprocess
p=argparse.ArgumentParser(description=__doc__)
p.add_argument('--ca-dir',type=Path,required=True)

if r.returncode or not m or int(m[1])<3:raise SystemExit('OpenSSL>=3 required')
for name in ['ca.pem','ca.key','server.cnf']:
 if not (ca/name).is_file():raise SystemExit('original lab CA directory required')
check=subprocess.run([exe,'x509','-in',str(ca/'ca.pem'),'-checkend',str(8*86400),'-noout'],capture_output=True,text=True)
if check.returncode:raise SystemExit('CA needs more than8days validity for this lab leaf')
os.umask(0o077);out.mkdir(mode=0o700)
def run(*args):
 r=subprocess.run([exe,*map(str,args)],cwd=out,capture_output=True,text=True)
 if r.returncode:raise RuntimeError('leaf rotation failed; incomplete new directory retained')
shutil.copyfile(ca/'ca.pem',out/'ca.pem')
run('req','-new','-newkey','rsa:3072','-noenc','-config',ca/'server.cnf','-keyout','server.key','-out','server.csr')
run('x509','-req','-in','server.csr','-CA',ca/'ca.pem','-CAkey',ca/'ca.key','-set_serial',str(secrets.randbits(127)+1),'-days','7','-sha256','-extfile',ca/'server.cnf','-extensions','server','-out','server.pem')

print('Created new local leaf under unchanged CA; old deployment and CA files untouched.')
```

工具要求原实验CA还有足够有效期，用新的随机序列号签发新的七天叶证书。新目录含公开CA、叶证书与叶私钥，不复制CA私钥，不修改旧证书，也不更新原CA序列号文件。

### 44.7.3 【进阶】新挂载与旧连接

Compose单文件秘密通常通过文件绑定提供给容器。宿主机原子替换文件名，不一定让已绑定的旧inode变成新内容；只对Nginx发送reload不能自动证明它读到了新证书。

本地实验采用明确的新目录与新挂载，仅重建TLS代理。外部新连接核对线上证书指纹发生变化，再用原会话令牌查询身份。它会有单实例重建窗口，本章不称其为零停机更新。[Nginx证书配置](https://nginx.org/en/docs/http/configuring_https_servers.html)

### 44.7.4 【精通】实验CA不是公网证书流程

正式部署还需要域名控制、受信签发流程、续期告警、秘密分发与回退安排。实验不会替读者注册域名，也没有执行ACME、生产CA轮换或mTLS客户端证书授权。

本地明确保留短有效期与独立目录，是为了让失效和更新可以被观察。不要把这份自建根长期装到日常系统里，冒充已经完成公网发布。

## 44.8 让Linux故障与HTTP结果相互印证

### 44.8.1 【入门】STOP和TERM的实验目标不同

TERM用于请求进程按处理程序退出；STOP暂停进程执行，监听socket和进程记录仍可能存在。对暂停的进程建立TCP连接有时仍能完成，因为内核负责部分连接过程，应用却不能及时读取与响应。

因此“端口能连通”不等于应用能完成请求。当前SIGSTOP实验只请求readyz，不对有副作用接口随机注入暂停，避免把观察故障与制造未知订单结果混成一件事。

### 44.8.2 【进阶】实际暂停后的超时分类

完整实验暂停edge，TLS代理在读取上游时耗尽等待并返回JSON504；随后发送CONT，外部readyz恢复200。另一项实验真正停止edge容器，可能表现为连接拒绝或连接超时，对应503或504，并要求代码与HTTP状态一致。

首次验收曾只接受停止后的503，但本机网络实际返回连接超时504。修正依据是实际失败阶段与已经配置的错误分类，不是把任意HTTP结果都当通过。响应仍必须有界、为预期JSON，并在恢复后重新可用。

### 44.8.3 【进阶】只读采集cgroup与描述符

通过`docker compose exec -T edge sh -s`把脚本作为标准输入执行，可以在不安装额外工具的情况下读取该容器的PID1限制与cgroup信息。它不读取进程环境，也不导出命令行中的潜在秘密。

memory.max与memory.current帮助判断配额与使用，memory.events记录相关事件；cpu.max和cpu.stat提供CPU约束与计费信息；描述符数量要结合/proc/1/limits观察。容器内看到的内核来自Linux运行环境，在Docker Desktop中不是macOS内核。[Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

### 44.8.4 【精通】快照不等于根因证明

某一刻内存接近上限不直接证明发生过OOM；出现503也可能是数据库、Redis或本地容量拒绝。需要结合事件计数、进程退出原因、时间线与应用指标。

本章保存两个容器的只读快照，并核对代理实际限制；没有故意制造生产数据丢失或将内存耗尽当作容量测试。若要做资源故障注入，应另建可丢弃环境与明确停止条件。

## 44.9 性能观测先定义分母

### 44.9.1 【入门】请求、成功响应与业务完成

一个客户端收到429的请求也有响应耗时，但它不是成功查询；HTTP202接收订单也不是订单已经付款并完成。每秒响应数、每秒200、订单完成数应分别命名。

本章选择有一件可见商品的只读GET链路，包含TLS、edge、身份检查、Catalog HTTP与RPC。它不会把这条观测解释为库存写入、下单事务或支付系统的容量。

### 44.9.2 【进阶】有界、复用连接的观测程序
```python
"""Bounded, read-only HTTPS GET observations with one reusable connection/worker.

Includes client waiting andTLS costs. Reports all statuses, never treats429/503
as successful business throughput. Closed-loop fixture, not a production SLO.
"""
import argparse,collections,concurrent.futures,http.client,json,os,ssl,threading,time,urllib.parse
from pathlib import Path
p=argparse.ArgumentParser(description=__doc__)
p.add_argument('--url',required=True)
p.add_argument('--ca',type=Path,required=True)
p.add_argument('--token-file',type=Path,required=True)
p.add_argument('--output',type=Path,required=True)
p.add_argument('--requests',type=int,default=120)
p.add_argument('--concurrency',type=int,default=8)
a=p.parse_args();url=urllib.parse.urlsplit(a.url)
if url.scheme!='https' or not url.hostname or url.username or url.password or url.path not in ('','/') or url.query or url.fragment:p.error('HTTPS origin without credentials/path required')
if not (1<=a.requests<=2000 and 1<=a.concurrency<=128):p.error('requests1..2000 concurrency1..128')
if a.output.exists():p.error('output already exists')
if a.token_file.stat().st_size>8192:p.error('token file too large')
token=a.token_file.read_text().strip()
if not token or any(c in token for c in '\r\n'):p.error('single token required')
context=ssl.create_default_context(cafile=str(a.ca));context.minimum_version=ssl.TLSVersion.TLSv1_2
local=threading.local();connections=[];lock=threading.Lock()
def one(_):
 if not hasattr(local,'connection'):
  local.connection=http.client.HTTPSConnection(url.hostname,url.port or 443,timeout=3,context=context)
  with lock:connections.append(local.connection)
 start=time.monotonic()
 try:
  local.connection.request('GET','/api/v1/products',headers={'Authorization':'Bearer '+token})
  response=local.connection.getresponse();data=response.read(65537)
  if len(data)>65536:raise ValueError('response too large')
  status=str(response.status)
 except (OSError,http.client.HTTPException,ValueError):
  local.connection.close();status='transport_error'
 return status,(time.monotonic()-start)*1000
started=time.monotonic()
try:
 with concurrent.futures.ThreadPoolExecutor(max_workers=a.concurrency) as pool:
  rows=list(pool.map(one,range(a.requests)))
finally:
 for connection in connections:connection.close()
elapsed=time.monotonic()-started;counts=collections.Counter(s for s,_ in rows)
times=sorted(t for _,t in rows)
def percentile(p):return times[max(0,min(len(times)-1,int((len(times)*p+99)//100)-1))]
report={'requests':a.requests,'concurrency':a.concurrency,'elapsed_seconds':elapsed,'status_counts':dict(counts),'all_response_rps':len(rows)/elapsed,'http200_rps':counts['200']/elapsed,'latency_ms_all_responses':{'p50':percentile(50),'p95':percentile(95),'p99':percentile(99),'max':max(times)},'scope':'closed-loop GET products, bounded samples, connection reuse per worker; no order capacity or production SLO claim'}
success_times=sorted(t for status,t in rows if status=='200')
if success_times:
 def successful_percentile(p):return success_times[max(0,min(len(success_times)-1,(len(success_times)*p+99)//100-1))]
 report['latency_ms_http200']={'p50':successful_percentile(50),'p95':successful_percentile(95),'p99':successful_percentile(99),'max':max(success_times)}
else:report['latency_ms_http200']=None
fd=os.open(a.output,os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o600)
with os.fdopen(fd,'w') as out:json.dump(report,out,indent=2);out.write('\n')
print(json.dumps(report))
```

每个工作线程复用一条连接，全部样本数与线程数都有限。单次计时从工作线程开始执行调用时启动，包含连接和响应等待，不包含此前在线程池队列中的等待；整组耗时则包含所有任务完成的实际时间。首个请求包含TLS建立成本，后续请求可能复用连接；连接关闭或错误时会重新建立。输出按状态分类，成功吞吐只计200，并分别记录全部响应与200响应的延迟分位数。

令牌从私有文件读取，不出现在命令行参数或报告中。报告文件必须不存在，程序拒绝覆盖旧观测。输出中的transport_error不会被忽略，也不会被算成业务成功。

### 44.9.3 【进阶】读懂三组短实验

第一轮实测每组120次，线程数1、8、32；200分别为69、65、65，429分别为51、55、55。它们展示了第39章实例级令牌桶的短期突发作用，不能用短于一秒的观测外推出持续吞吐。

例如8线程那组全部响应约1712次/秒，200约927次/秒；这不表示持续每秒能完成927次业务查询。初始burst64允许短时突发，稳定补充率仍是已配置的32次/秒。不同组之间等待让桶有机会恢复，但没有把每一组都变成稳态测量。

后续最终复验会生成自己的报告，数值可以不同。读者应核对状态计数之和、窗口长度、成功比例与环境负载，而不是要求自己的p95与书中某个毫秒数相同。

### 44.9.4 【精通】闭环压测的局限

本程序完成一个请求后再开始下一项工作，属于闭环模型。服务变慢时，客户端自然减少发送速率；它不能完整显示固定到达率持续施压时的排队情况，也可能隐藏协调遗漏造成的尾延迟偏差。

长期容量测试还需要受控到达率、预热、稳定窗口、足够样本、独立发压机、资源与业务指标，以及明确结束条件。不能为了得到更高数字，在书中删掉鉴权、关闭证书检查或把所有错误都过滤掉。

## 44.10 从容量估算走向故障预算

### 44.10.1 【入门】用在途量解释排队

稳定条件下，平均在途量可以用到达率乘平均停留时间估算：100次/秒、每次50毫秒，平均约5个在途；同样流量下停留时间升到1秒，约变成100个。

这个算例帮助理解慢依赖为何消耗连接和内存，不直接决定并发上限。突发、尾延迟、重试与多段调用会改变实际分布，还必须结合第39章的剩余预算与名额约束。

### 44.10.2 【进阶】连接复用与连接数不是同一指标

复用连接减少握手，但空闲连接仍消耗资源，也可能被代理或对端关闭。HTTP/2还允许同一连接承载多个流；不能用连接数直接当活跃请求数。

当前Nginx上游明确HTTP/1.1并复用到edge的连接，本章没有将其写成全链路HTTP/2或gRPC over TLS验收。后端gRPC仍沿原配置运行。

### 44.10.3 【精通】找到热点再选择剖析工具

CPU、数据库锁、网络等待与分配压力需要不同证据。对CPU热点可在有权限的隔离环境使用采样剖析；对异步延迟应检查阻塞工作与执行器占用；对数据库等待继续使用第41章的计划和锁诊断。

本章没有实际生成火焰图，也没有让非root业务容器额外获得剖析权限。工具名称只能说明可用方向，不能替代已采集的证据；生产临时提权需要独立运维流程和范围。

## 44.11 从进程到内核再深入一层

### 44.11.1 【入门】线程、任务与可运行工作

进程保存地址空间与打开的资源，线程是操作系统调度执行的单位；Tokio任务则由运行时安排在线程上推进。任务等待网络时可以让出执行机会，线程等待同步锁或执行长时间CPU工作时却不能凭async关键字自动让出。

把一个计算循环写成async函数，再在其中连续计算几秒，仍可能拖慢同一执行器上的其他任务。项目将密码哈希放进有界阻塞工作，而不是让注册请求占住普通异步工作线程；同时有信号量，避免每个请求都无限创建新计算工作。

### 44.11.2 【进阶】虚拟内存、常驻内存与容器计费

虚拟地址空间是进程能够寻址的范围，不等于已经占用同样大小的物理内存。RSS观察进程当前常驻页面；cgroup计费又可能包含文件缓存等与整个组有关的内存。它们描述不同对象，数值不必相等。

本章读取memory.current与memory.max，是为了核对容器的资源边界；它没有提供Rust分配器按对象分类的分析。若RSS持续增长，应同时检查在途任务、连接缓冲、缓存上限、引用保留与分配器行为，不能只凭“没有GC”就排除内存问题。

### 44.11.3 【进阶】CPU配额、调度与上层限制

cpu.max中的max不表示独占无限CPU，只说明该层没有以同样方式给出有限配额。它仍受宿主竞争、虚拟机配置与上层资源约束影响。cpu.stat中的节流计数也不能代替整个调度等待时间。

Docker Desktop里的应用、Kafka和代理共同使用Linux虚拟机资源。压测时另一个构建进程占CPU，可能改变TLS握手和尾延迟；报告应写清观测条件，而不是把所有差异归因于Rust版本或线程数。

### 44.11.4 【精通】描述符计数要找对进程

本章快照读取PID1。Rust服务通常由启动器exec后成为PID1，Tokio线程共享它的描述符表；Nginx则有master与worker，master的FD数量不能直接表示worker当前处理了多少连接。

因此代理连接压力还应结合worker、连接指标与响应情况观察。nofile限制、worker_connections与代理上下游各占用连接的关系也要同时计算：一个正在代理的请求可能关联客户端与上游两个socket，而不是只占一个。

### 44.11.5 【精通】优雅退出保留了哪些工作

本项目HTTP服务接到停止信号后触发CancellationToken，等待在途服务在既有预算内结束，再退出；容器停止宽限期为30秒，应用等待上限为20秒。这些时间需要有一致关系，不能让容器在应用尚未获得清理时间时直接强制终止。

优雅退出也不是跨系统事务。若请求已经提交数据库、回复尚未送到客户端就断开，客户端仍可能不知道结果，必须使用原幂等键查询或重试。第35-36章的绑定与状态机不能因为本章加入TLS而省略。

## 44.12 TCP与连接池的诊断思路

### 44.12.1 【入门】监听socket与已连接socket

服务先bind地址并listen，随后accept取得新的连接socket。监听端口只表示有接收入口，后续每条连接还有自己的状态、缓冲与生命周期。Linux socket接口与等待就绪机制使异步框架能够复用执行线程。[Linux socket手册](https://man7.org/linux/man-pages/man7/socket.7.html)

暂停应用时，监听socket仍可能存在；因此本章同时验证TCP能建立与HTTP是否及时返回，而不只用“进程在、端口在”判断健康。

### 44.12.2 【进阶】TCP是字节流，应用协议负责消息边界

一次write不保证对方的一次read正好收到相同长度。HTTP框架负责根据协议解析请求与响应，gRPC还在HTTP/2上定义消息格式。应用不能用“read返回了些数据”代替完整JSON或完整消息到达。

本项目使用Axum、reqwest和tonic处理这些协议细节，再为请求体与消息长度设置限制。自行拼接HTTP头、透传所有上游头或假定一次读取就是一个请求，会把框架已经解决的问题重新带回来。

### 44.12.3 【进阶】用状态区分连接建立与关闭

| 状态或现象 | 可以提出的问题 | 单凭它不能证明什么 |
| --- | --- | --- |
| SYN-SENT较多 | 对端或路径是否及时回应 | 业务数据库一定慢 |
| ESTABLISHED较多 | 活跃还是空闲，是否复用过多连接 | 每条连接都在做有效工作 |
| CLOSE-WAIT持续增长 | 应用是否及时关闭已被对端关闭的连接 | 只调内核参数就能修好 |
| TIME-WAIT较多 | 连接创建/关闭速率与复用情况 | 一定发生了应用资源泄漏 |

状态名来自TCP的连接状态机。TIME-WAIT与关闭协议有关，不应见到它就批量修改重用参数；先确认哪一端在创建和关闭连接、流量是否符合预期。[TCP规范](https://www.rfc-editor.org/rfc/rfc9293.html)

### 44.12.4 【精通】不要把三类等待合成一个数字

连接池名额等待发生在应用本地；TCP建立等待发生在传输路径；收到请求以后数据库或上游处理又有另一段等待。请求计时通常包含多段，服务端命令耗时未必包含客户端排队。

第38章的调用span、第41章的连接池/SQL错误分类与本章TLS探针应连起来看。若先耗尽等待预算再发送请求，扩大远端超时并不会归还已经花掉的本地时间。

## 44.13 TLS协商与身份为什么要分开解释

### 44.13.1 【入门】一次握手协商什么

TLS需要协商支持的协议与算法，建立用于保护后续数据的密钥，并让客户端按预期身份验证服务端。证书中的长期公钥与每次连接保护数据的会话密钥不是同一个概念。[TLS1.3规范](https://www.rfc-editor.org/rfc/rfc8446.html)

本实验使用RSA证书，不意味着客户端把每个HTTP报文都直接用RSA加密。应用应调用成熟TLS库处理协商、随机数和认证，不能因读懂几步握手就自行实现一套加密传输。

### 44.13.2 【进阶】名称选择、协议选择与证书校验

SNI帮助服务器根据客户端请求的名称选择站点证书；ALPN用于协商应用层协议。它们不能替代客户端的证书链和目标名称验证。客户端发出localhost名称后，仍要确认收到的证书确实允许localhost。

Python探针在本章实际协商TLS1.2与TLS1.3，但没有宣称已验证HTTP/2或HTTP/3。Nginx上游配置明确使用HTTP/1.1；内部gRPC则继续按原路径，不能把这几种协议名混成一个版本号。

### 44.13.3 【进阶】根证书、链与时间

签发者受信、叶证书用途允许、名称匹配与有效期正常，都要成立。本地生成器使用一个明确的CA与叶证书，避免把一堆来源不明的证书全部加入信任库后无法判断到底信任了谁。

正式链条可能还包含中间证书；服务端应发送适当的链，客户端按照自己的根信任验证。服务器和客户端时钟异常也会影响有效期判断。遇到过期错误，先检查证书与时间，不将忽略时间或名称验证写成常规启动参数。

### 44.13.4 【精通】单向TLS、mTLS与用户授权

当前入口证明服务器身份，客户端不需要提交客户端证书。mTLS会增加对客户端证书的验证，但证书中的服务身份如何映射权限，仍需应用或治理层定义。

JWT表达的用户身份与客户端服务证书身份也不同。拿到一个合法服务证书，不代表可以代替任意用户下单；某个用户令牌有效，也不赋予它数据库或Kafka管理员权限。本项目保持这些独立凭据与数据库授权边界。

### 44.13.5 【精通】会话复用、更新与可见信息

连接复用减少握手次数，TLS会话恢复是另外一层机制。当前代理关闭会话票据并设置有限会话缓存；轮换验收强制建立新连接读取线上证书，不用一个早先建立的长连接推断更新是否生效。

本章没有开启或验证0-RTT早期数据，也没有证明请求具备抗网络重放能力。HTTPS并不隐藏所有流量元数据；数据库幂等与付款绑定继续承担业务重复处理的责任。

## 44.14 不经过自动清理脚本的手动操作

### 44.14.1 【入门】建立自己的长期实验环境

自动验收会在结束时清理自己的数据卷。若要保留手动环境，先完成镜像构建，在不存在的目录生成证书与新的业务配置：
```sh
python3 scripts/create-tls-lab.py --output-dir .tls44.local
python3 scripts/create-delivery-env.py
RUSTMALL_IMAGE=rustmall/book:ch44-candidate \
RUSTMALL_TLS_DIR="$PWD/.tls44.local" \
docker compose -p rustmall44-reader \
  --env-file .delivery.local/compose.env \
  -f deploy/delivery40/compose.yaml \
  -f deploy/tls44/compose.yaml \
  up -d --wait --wait-timeout 240
```

这是单独选择的项目名。已有业务配置应按第40章规则复用，不能重新生成密码后期待旧卷自动接受新密码；也不能把自动验收的新数据集当成已经迁移过来的旧用户和订单。

### 44.14.2 【进阶】核对入口，再访问业务
```sh
python3 scripts/tls-probe.py \
  --url https://localhost:18443 --ca .tls44.local/ca.pem
```

探针应返回200并包含协商版本与证书指纹。浏览器仍可能提示不受信，因为该进程的CA选项没有替浏览器安装信任。API客户端可以使用显式CA设置；本章工具不会修改读者系统的全局信任状态。

证书只包含localhost，不把URL改成127.0.0.1来绕过DNS问题；这一改动会改变被验证的目标名称。实际应用鉴权仍使用原用户接口，未登录请求不会因为TLS握手成功就获得管理员身份。

### 44.14.3 【进阶】更新叶证书与回退

在原CA目录内创建一个新的叶证书目录：
```sh
python3 scripts/rotate-tls-lab.py \
  --ca-dir .tls44.local --output-dir .tls44.local/leaf-v2
RUSTMALL_IMAGE=rustmall/book:ch44-candidate \
RUSTMALL_TLS_DIR="$PWD/.tls44.local/leaf-v2" \
docker compose -p rustmall44-reader \
  --env-file .delivery.local/compose.env \
  -f deploy/delivery40/compose.yaml \
  -f deploy/tls44/compose.yaml \
  up -d --no-deps --force-recreate tls
```

再用原CA建立新连接，核对指纹已更新。若新代理无法工作，保留错误记录，将TLS目录指回原目录，仅重新创建代理；不要通过重建数据库或改变JWT密钥来回退证书问题。这是有短暂停机窗口的本地操作流程。

### 44.14.4 【精通】停止与数据保留

手动环境停止时仍使用同一个项目、配置与TLS目录：`docker compose ... down`。是否附带volumes选项决定是否删除该项目的数据卷；删除前必须明确这些数据是否还需要保留。

私有证书和业务配置是两组材料。容器删除不一定删除它们；它们也不应随源码打包发送给他人。第46章会继续区分配置备份、业务数据恢复与可验证切换，而不是把“目录还在”当作恢复成功。

## 44.16 排错表与分层练习

### 44.16.1 【入门】按失败阶段找证据

| 症状 | 优先核对 | 不应直接采取的动作 |
| --- | --- | --- |
| 名称解析失败 | 调用端命名空间与DNS | 关闭证书验证 |
| TCP连通但没有HTTP | TLS、应用是否暂停、请求读取预算 | 宣布服务健康 |
| 证书不受信 | CA来源、链与当前客户端配置 | 永久接受任意证书 |
| 127.0.0.1名称失败 | SAN是否包含该IP | 只改证书CN |
| 代理启动只读报错 | 明确的临时写路径与权限 | 整个根目录改可写 |
| TLS轮换后仍旧指纹 | 挂载inode、进程与实际新连接 | 认为文件名改变即生效 |
| RPS很高但429很多 | 成功分母、突发桶与窗口 | 宣称业务容量变高 |

### 44.16.2 【入门】解释两个localhost

问题：宿主localhost:18443与TLS容器localhost:8080分别指向什么？

答案：前者通过发布端口进入TLS容器8443；后者指向TLS容器自己，并不指向edge。代理上游使用同网络中的edge:8080。

### 44.16.3 【进阶】为什么同CA续期不注销会话

问题：叶证书和私钥更新以后，原JWT仍可使用是否说明证书轮换没成功？

答案：两者生命周期不同。新连接应验证新叶指纹与原CA信任；JWT还需通过既有签名、有效期和数据库会话检查。只有同时核对线上证书和业务响应，才能证明两种事实都成立。

### 44.16.4 【进阶】区分连接与读取超时

问题：停止容器与SIGSTOP进程为什么都可能让readyz失败，却不能固定解释为同一种故障？

答案：停止可能表现为连接拒绝或连接超时；暂停的进程可能仍有可连接socket，却不能响应。应按实际连接/读取阶段返回503或504并保存分类，恢复后再次验证。超时不能证明此前写请求绝无副作用。

### 44.16.5 【精通】审查一张漂亮的性能表

问题：某组全部响应1700次/秒，其中900次/秒是200，观测不到一秒且初始burst64，能否宣称稳定成功吞吐900次/秒？

答案：不能。先区分200和错误响应，再考虑短期突发、持续补充率、闭环发送和样本窗口。长期结论还需要稳态、资源与真实业务完成指标；本章只报告这一次有界观测。

# 第 31 章 库存 RPC：超时后的查询与恢复

上一章在商品数据库内建立了库存收据、状态机与事务，可信 CLI 已能预留、确认和释放。现在订单流程将运行在另一个进程，不能直接借用 PgPool。我们要把同一业务能力放到 RPC 后面，同时保留相同意图只产生一次库存效果的规则。

本章新增 Inventory gRPC 契约，在 catalog 进程中注册库存服务，并编写 InventoryRemote。它们继续使用第 30 章的事务模块，没有新增另一份库存数据库，也没有把网络发送塞进数据库事务。商品查询凭据与库存命令凭据分开，防止普通商品调用者自然获得预留权限。

学习重点是网络引入的不确定性：客户端不再等待，不代表服务器没有提交。学完应能区分业务拒绝、身份拒绝、依赖故障和未知结果，能通过同一 UUID 查询恢复，能解释客户端、服务端与数据库各自的预算，并能审查一次“超时重试”是否可能重复占用库存。

## 31.1 同一事务能力跨过进程边界

### 31.1.1 【入门】本地调用能得到什么

第 30 章 execute 返回 State，调用者与库存逻辑在同一个程序里。调用失败时依然可能涉及提交结果未知，但传递参数、错误和所有权不需要序列化或网络连接。

跨进程后，输入要编码成消息，另一个运行时取得请求，再执行数据库事务，最后发回响应。每个新增步骤都可能失败，调用方得到的 Status 与数据库最终状态不再总是一一对应。

### 31.1.2 【入门】本章实际拓扑

路径是“可信业务调用方 → InventoryRemote → catalog进程中的Inventory服务 → 同一个商品数据库”。商品Catalog服务与库存Inventory服务共享进程和数据库，拥有不同gRPC服务名与凭据。

它不是两台独立服务通过分布式事务同时改库存。这样安排是因为商品可售量、预留收据与商品Outbox仍须共用一个PostgreSQL事务。按业务边界拆分能力，不要求把每个crate都部署成独立进程。

### 31.1.3 【进阶】网络边界不改变状态表

Reserve、Confirm、Release仍使用原UUID、商品、数量与单价。Held、Confirmed、Released、Rejected的含义也不改变，迟到取消和重复调用继续由持久化收据决定。

如果RPC层重新实现一份“先查库存再扣”的逻辑，就会绕开上一章已经验证的边界。本章RPC只做身份、资源与协议转换，然后调用原execute/find，保持一个业务实现来源。

### 31.1.4 【进阶】业务拒绝可以是成功的RPC响应

库存不足时，服务器正确执行检查并保存Rejected，调用本身成功完成，应返回正常ReservationReply，其state为Rejected。它不是网络连接失败，也不应变成可以无条件重试的Unavailable。

调用方必须同时理解传输结果和业务状态。只要RPC返回Ok就把订单标记成功，会把“正确拒绝了预留”错误解释成“拿到库存”。

### 31.1.5 【精通】先列四种结果

第一种，有明确Held等业务结果；第二种，输入或身份被拒绝，业务没有按正常入口开始；第三种，数据库明确报告冲突或事务错误；第四种，调用方在提交附近失去响应，无法知道最终结果。

恢复策略必须由这些事实决定。把所有错误统一改成Rejected会掩盖未知的已提交占用；把所有错误统一重试且换新UUID，则可能多占一份库存。

## 31.2 为状态机定义网络契约

### 31.2.1 【入门】完整Protobuf定义

替换contracts/proto/catalog.proto，保留原商品字段编号与幂等创建字段，追加Inventory服务：
```protobuf
syntax = "proto3";
package rustmall.catalog.v1;

service Catalog {
  rpc GetProduct(GetProductRequest) returns (Product);
  rpc ListProducts(ListProductsRequest) returns (ListProductsResponse);
  rpc CreateProduct(CreateProductRequest) returns (Product);
  rpc UpdateProduct(UpdateProductRequest) returns (Product);
  rpc DelistProduct(GetProductRequest) returns (DelistProductResponse);
}
message Product {
  int64 id = 1;
  string name = 2;
  int64 price_cents = 3;
  int32 stock = 4;
}
message GetProductRequest { int64 id = 1; }
message ListProductsRequest { int64 limit = 1; int64 offset = 2; }
message ListProductsResponse { repeated Product items = 1; int64 total = 2; }
message CreateProductRequest {
  string name = 1;
  int64 price_cents = 2;
  int32 stock = 3;
  string idempotency_key = 4;
  int64 actor_id = 5;
}
message UpdateProductRequest {
 int64 id = 1;
 string name = 2;
 int64 price_cents = 3;
 int32 stock = 4;
}
message DelistProductResponse {}

// Chapter 31: inventory participates in the same catalog service boundary.
service Inventory {
  rpc Reserve(ReservationCommand) returns (ReservationReply);
  rpc Confirm(ReservationCommand) returns (ReservationReply);
  rpc Release(ReservationCommand) returns (ReservationReply);
  rpc GetReservation(GetReservationRequest) returns (ReservationReply);
}
message ReservationCommand {
  string saga_id = 1;
  int64 product_id = 2;
  int32 quantity = 3;
  int64 unit_price_cents = 4;
}
message GetReservationRequest { string saga_id = 1; }
enum ReservationState {
  RESERVATION_STATE_UNSPECIFIED = 0;
  RESERVATION_STATE_HELD = 1;
  RESERVATION_STATE_CONFIRMED = 2;
  RESERVATION_STATE_RELEASED = 3;
  RESERVATION_STATE_REJECTED = 4;
}
message ReservationReply {
  string saga_id = 1;
  int64 product_id = 2;
  int32 quantity = 3;
  int64 unit_price_cents = 4;
  ReservationState state = 5;
}
```

Inventory是新的服务名，原Catalog的五个方法继续保留。不要删除上一章创建请求中的actor_id和idempotency_key，也不要把库存命令错误塞进商品UpdateProduct方法里。

### 31.2.2 【入门】命令为什么重复携带参数

ReservationCommand每次都包含UUID、商品、数量和单价，不只在Reserve时提供。这样Confirm和Release也能核对调用方说的是不是同一份收据，避免拿同一个标识配另一商品或数量执行反向操作。

这些字段不是可以在重试时“顺便刷新”的最新商品状态。已经Held的价格与数量属于原意图；商品后来涨价，不应改变这份收据的参数。

### 31.2.3 【进阶】UUID在协议中为什么用字符串

Protobuf没有直接的UUID标量，本章使用string，进入领域前通过Uuid::parse_str解析，并拒绝nil UUID。字段能被解码为String，只证明它是字符串，不证明它具有合法身份。

同一UUID可以有不同文本写法，服务端解析后用统一UUID类型比较；返回时使用标准字符串形式。客户端也解析再比较，不依赖大小写、连字符文本完全一致来判断是否属于同一意图。

### 31.2.4 【进阶】保留UNSPECIFIED，拒绝默认成功

枚举零值是ReservationState::Unspecified，不能当作Held。未设置字段、旧版本没有提供状态，或未来出现当前客户端不认识的整数，都应被明确拒绝解释。

生成的Rust字段仍保存i32。客户端使用ReservationState::try_from检查，不把未知整数强制转换成一个看似成功的State。这样新旧版本并存时，不会因为默认值而悄悄确认不存在的库存。

### 31.2.5 【进阶】为什么没有公开Pending

正常execute在一个事务内从Pending走到确定状态，再提交。Pending不是本章对外宣告的已完成结果，所以协议没有为它提供可被调用方当作成功的业务状态。

如果查询遇到异常持久化Pending，服务端返回内部状态异常，而不是编造Held。未来若业务改为真正异步处理，需要另行定义“已接收但未完成”的协议与查询期限，不能偷偷复用当前语义。

### 31.2.6 【精通】查不到不等于业务已被撤销

GetReservation对不存在收据返回NotFound，客户端把它转换为Ok(None)。这个结果描述查询观察到的当前数据库事实，不是对其他在途请求未来行为的保证。

例如另一个请求仍在执行，它可能在查询之后提交。恢复流程需要结合稳定标识、原动作和业务期限安排下一步；本章持久化取消屏障可以关闭同一意图，但“查询为空”本身不会创建屏障。

### 31.3.5 【进阶】完整独立实验服务器

创建inventory/examples/rpc_lab.rs：
```rust
use anyhow::Context;
use inventory::rpc::{ServiceKey, service};
use sqlx::postgres::PgPoolOptions;
use std::{net::SocketAddr, time::Duration};
use tokio_util::sync::CancellationToken;
use tonic::transport::Server;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let address: SocketAddr = std::env::var("INVENTORY_LAB_ADDR")
        .unwrap_or_else(|_| "127.0.0.1:50052".into())
        .parse()?;
    anyhow::ensure!(
        address.ip().is_loopback(),
        "lab must listen on loopback only"
    );
    let key = ServiceKey::parse(
        &std::env::var("RUSTMALL_INVENTORY_TOKEN").context("inventory token missing")?,
    )?;
    let pool = PgPoolOptions::new()
        .max_connections(10)
        .acquire_timeout(Duration::from_millis(500))
        .connect(&std::env::var("DATABASE_URL").context("database missing")?)
        .await?;
    let stop = CancellationToken::new();
    let server = Server::builder()
        .add_service(service(pool.clone(), key))
        .serve_with_shutdown(address, stop.clone().cancelled_owned());
    tokio::pin!(server);
    let result = tokio::select! {
        result = &mut server => result.context("lab server failed"),
        result = tokio::signal::ctrl_c() => {
            result?;
            stop.cancel();
            tokio::time::timeout(Duration::from_secs(20), &mut server).await
                 .context("lab shutdown budget exhausted")?
                 .context("lab server failed")
        }
    };
    tokio::time::timeout(Duration::from_secs(2), pool.close())
        .await
        .context("lab pool close budget exhausted")?;
    result
}
```

它只允许回环地址，默认50052端口，单独注册Inventory服务，适合先排除商品主进程组装问题。它不是另一份库存存储，也不新增数据库；同一实验期间避免把两个服务实例误当作两套权威库存。

### 31.3.6 【入门】启动并理解生命周期
```bash
cargo +1.92.0 run --locked -p inventory --example rpc_lab
```

程序会占用终端。它不自动运行迁移，若缺表应回到catalog-migrate。停止时用Ctrl-C，让服务器停止接收并等待，再有界关闭连接池；本实验入口只专门处理Ctrl-C，正式catalog入口继续处理正常SIGTERM。

## 31.4 RPC服务端：在业务之前建立边界

### 31.4.1 【入门】完整服务模块

创建inventory/src/rpc.rs：
```rust
use crate::{
    Error, Reservation, execute, find,
    model::{Action, Command, State},
};
use contracts::catalog::{
    GetReservationRequest, ReservationCommand, ReservationReply, ReservationState,
    inventory_server::Inventory,
};
use sqlx::PgPool;
use std::sync::Arc;
use subtle::ConstantTimeEq;
use tokio::sync::{OwnedSemaphorePermit, Semaphore};
use tonic::{
    Request, Response, Status,
    metadata::{Ascii, MetadataValue},
    service::Interceptor,
};
use uuid::Uuid;

pub const MAX_MESSAGE_BYTES: usize = 64 * 1024;
pub const SERVICE_TOKEN_HEADER: &str = "x-rustmall-service-token";

pub fn service(
    pool: PgPool,
    key: ServiceKey,
) -> tonic::service::interceptor::InterceptedService<
    contracts::catalog::inventory_server::InventoryServer<InventoryApi>,
    ServiceKey,
> {
    let server =
        contracts::catalog::inventory_server::InventoryServer::new(InventoryApi::new(pool))
            .max_decoding_message_size(MAX_MESSAGE_BYTES)
            .max_encoding_message_size(MAX_MESSAGE_BYTES);
    tonic::service::interceptor::InterceptedService::new(server, key)
}

#[derive(Clone)]
pub struct ServiceKey {
    value: MetadataValue<Ascii>,
}

impl ServiceKey {
    pub fn parse(raw: &str) -> anyhow::Result<Self> {
        anyhow::ensure!(
            (32..=256).contains(&raw.len())
                && raw
                    .bytes()
                    .all(|b| b.is_ascii_alphanumeric() || b == b'-' || b == b'_'),
            "service token must contain 32..256 ASCII letters, digits, '-' or '_'"
        );
        Ok(Self {
            value: raw.parse()?,
        })
    }

    pub fn attach<T>(&self, request: &mut Request<T>) {
        request
            .metadata_mut()
            .insert(SERVICE_TOKEN_HEADER, self.value.clone());
    }
}

impl Interceptor for ServiceKey {
    fn call(&mut self, request: Request<()>) -> Result<Request<()>, Status> {
        let mut values = request.metadata().get_all(SERVICE_TOKEN_HEADER).iter();
        let Some(received) = values.next() else {
            return Err(Status::unauthenticated("service identity required"));
        };
        if values.next().is_some()
            || !bool::from(
                received
                    .as_encoded_bytes()
                    .ct_eq(self.value.as_encoded_bytes()),
            )
        {
            return Err(Status::unauthenticated("service identity required"));
        }
        Ok(request)
    }
}

#[derive(Clone)]
pub struct InventoryApi {
    pool: PgPool,
    capacity: Arc<Semaphore>,
}

impl InventoryApi {
    pub fn new(pool: PgPool) -> Self {
        Self {
            pool,
            capacity: Arc::new(Semaphore::new(16)),
        }
    }

    fn enter(&self) -> Result<OwnedSemaphorePermit, Status> {
        self.capacity
            .clone()
            .try_acquire_owned()
            .map_err(|_| Status::resource_exhausted("inventory capacity exhausted"))
    }

    async fn apply(
        &self,
        command: ReservationCommand,
        action: Action,
    ) -> Result<Response<ReservationReply>, Status> {
        let _permit = self.enter()?;
        let input = Command {
            saga_id: parse_id(&command.saga_id)?,
            product_id: command.product_id,
            quantity: command.quantity,
            unit_price_cents: command.unit_price_cents,
        };
        let state = execute(&self.pool, &input, action)
            .await
            .map_err(map_error)?;
        Ok(Response::new(reply(&input, state)?))
    }
}

fn parse_id(raw: &str) -> Result<Uuid, Status> {
    let id = Uuid::parse_str(raw).map_err(|_| Status::invalid_argument("invalid saga UUID"))?;
    if id.is_nil() {
        return Err(Status::invalid_argument("nil saga UUID"));
    }
    Ok(id)
}

fn reply(command: &Command, state: State) -> Result<ReservationReply, Status> {
    let state = match state {
        State::Held => ReservationState::Held,
        State::Confirmed => ReservationState::Confirmed,
        State::Released => ReservationState::Released,
        State::Rejected => ReservationState::Rejected,
        State::Pending => return Err(Status::internal("reservation result unavailable")),
    };
    Ok(ReservationReply {
        saga_id: command.saga_id.to_string(),
        product_id: command.product_id,
        quantity: command.quantity,
        unit_price_cents: command.unit_price_cents,
        state: state as i32,
    })
}

fn row_reply(row: Reservation) -> Result<ReservationReply, Status> {
    let state = State::from_stored(&row.state).map_err(map_error)?;
    reply(
        &Command {
            saga_id: row.saga_id,
            product_id: row.product_id,
            quantity: row.quantity,
            unit_price_cents: row.unit_price_cents,
        },
        state,
    )
}

pub fn map_error(error: Error) -> Status {
    match error {
        Error::InvalidInput => Status::invalid_argument("invalid reservation input"),
        Error::IdentityConflict => Status::failed_precondition("reservation identity conflict"),
        Error::Deadline => Status::deadline_exceeded("inventory result may be unknown"),
        Error::Database(error) => {
            tracing::error!(%error, "inventory database failure");
            let code = error.as_database_error().and_then(|e| e.code());
            match code.as_deref() {
                Some("55P03") => Status::unavailable("inventory lock unavailable"),
                Some("57014") => Status::deadline_exceeded("inventory database budget exhausted"),
                Some("40001" | "40P01") => Status::aborted("inventory transaction must be retried"),
                _ => Status::internal("inventory database failure"),
            }
        }
        Error::CorruptState => {
            tracing::error!("invalid inventory reservation state");
            Status::internal("inventory stored state invalid")
        }
    }
}

#[tonic::async_trait]
impl Inventory for InventoryApi {
    async fn reserve(
        &self,
        request: Request<ReservationCommand>,
    ) -> Result<Response<ReservationReply>, Status> {
        self.apply(request.into_inner(), Action::Reserve).await
    }

    async fn confirm(
        &self,
        request: Request<ReservationCommand>,
    ) -> Result<Response<ReservationReply>, Status> {
        self.apply(request.into_inner(), Action::Confirm).await
    }

    async fn release(
        &self,
        request: Request<ReservationCommand>,
    ) -> Result<Response<ReservationReply>, Status> {
        self.apply(request.into_inner(), Action::Release).await
    }

    async fn get_reservation(
        &self,
        request: Request<GetReservationRequest>,
    ) -> Result<Response<ReservationReply>, Status> {
        let _permit = self.enter()?;
        let id = parse_id(&request.into_inner().saga_id)?;
        let row = find(&self.pool, id)
            .await
            .map_err(map_error)?
            .ok_or_else(|| Status::not_found("reservation not found"))?;
        Ok(Response::new(row_reply(row)?))
    }
}

            .append(SERVICE_TOKEN_HEADER, "wrong".parse().unwrap());
        assert_eq!(
            key.call(duplicate).unwrap_err().code(),
            tonic::Code::Unauthenticated
        );
    }

    #[tokio::test]
    async fn clones_share_the_same_capacity() {
        let pool = sqlx::postgres::PgPoolOptions::new()
            .connect_lazy("postgres://localhost/not_connected")
            .unwrap();
        let api = InventoryApi::new(pool);
        let clone = api.clone();
        let permits: Vec<_> = (0..16).map(|_| api.enter().unwrap()).collect();
        assert_eq!(
            clone.enter().unwrap_err().code(),
            tonic::Code::ResourceExhausted
        );
        drop(permits);
        assert!(clone.enter().is_ok());
    }
```

service函数把InventoryApi、生成的InventoryServer、消息限制与凭据拦截器组装起来。调用方只需要传入池与已解析ServiceKey，不必在不同入口重复拼接一份认证规则。

### 31.4.2 【进阶】凭据是有约束的类型

ServiceKey::parse要求32到256个ASCII字母、数字、连字符或下划线。解析成功以后保留MetadataValue&lt;Ascii&gt;，attach可以安全地写入固定元数据键。

这个格式与生成器的URL安全随机值兼容。它不自动提供轮换、撤销或TLS；凭据仍应通过受控环境分发。不要把“字符串足够长”当成“来源一定随机”，因此本章使用随机生成器而不使用固定书中口令。

### 31.4.3 【进阶】重复身份字段明确拒绝

拦截器取得x-rustmall-service-token的全部值。缺失或多于一个值都返回Unauthenticated，避免不同代理或组件分别选择第一项、最后一项而产生身份解释差异。

字节比较使用ConstantTimeEq，减少按内容提前退出的差异。这只描述比较操作，不宣称整个网络请求的时延恒定，也不能取代凭据保密与网络访问限制。

### 31.4.4 【进阶】并发上限由克隆共享

InventoryApi持有Arc&lt;Semaphore&gt;，初始十六个许可。每个写操作与查询先try_acquire_owned，满载立即ResourceExhausted，不在内存里无限排队。

许可保持到请求处理结束，错误返回也由作用域释放。克隆API共享同一个Semaphore，不是每克隆一次再分到十六个名额。单测会从一个实例占满许可，再从克隆实例确认拒绝。

### 31.4.5 【进阶】查询和命令共用容量的取舍

共享容量简单，但故障恢复时的查询也可能遇到ResourceExhausted。调用方此时仍不能推断“原预留不存在”，只能知道当前查询没有得到结果。

如果业务需要为恢复查询保留容量，后续可以按操作类别隔离预算；这还需要连接池与数据库资源一起规划。本章先落实一个明确的总上限，不通过无限排队掩盖过载。

### 31.4.6 【进阶】消息限制与业务校验各守一层

服务端最大编码、解码消息均为64KiB，客户端也配置相同限制。它约束单条gRPC消息大小，不能代替字段范围、业务数量上限或传输层所有资源限制。

原始客户端即使绕过InventoryRemote，发送七十多KiB的UUID字段，也应在进入正常库存事务前被拒绝。具体拒绝可能由框架返回OutOfRange或ResourceExhausted，测试不把某个显示字符串当作稳定协议。

### 31.4.7 【精通】服务器并发不等于数据库连接预算

十六个在处理的RPC与十条数据库池连接不是同一资源。部分请求可能等待连接，然后被获取连接或整体事务预算限制。增加Semaphore值不能自动提高PostgreSQL吞吐。

应观察取得连接时间、事务时间、锁等待和拒绝数量，再调整各层配置。后面的容量与治理章节会继续测量；本章的数字是学习实验值，不是所有部署都应照抄的容量结论。

## 31.5 把数据库错误转换为可理解的Status

### 31.5.1 【入门】输入错误与身份冲突

非法UUID、nil UUID、数量越界等返回InvalidArgument；同UUID换商品、数量或单价返回FailedPrecondition。这两类都不应该通过换一个连接无限重试解决。

身份冲突也不是数据库暂时繁忙。调用方应检查原命令与收据，找出为什么同一标识代表了不同参数，防止按错误数量执行释放。

### 31.5.2 【进阶】锁等待与事务冲突

SQLSTATE 55P03映射为Unavailable，表示本次没能按预算取得锁；40001与40P01映射为Aborted，提示应在理解原因后重新执行整个事务。

客户端仍需保留原业务标识和参数，并结合剩余期限决定是否重试。不是收到Aborted就从失败事务中间那条SQL接着执行，也不是每层各做三次重试而不计算总体请求数量。

### 31.5.3 【进阶】超时与内部故障

数据库57014映射为DeadlineExceeded，库存外层预算耗尽也返回结果可能未知的DeadlineExceeded。其他数据库错误统一Internal，在服务端记录必要诊断，不把SQL、连接地址或约束内部细节送给调用方。

客户端本地超时也可能以Cancelled表现，因此不能仅按状态码名字推断提交结果。恢复协议依靠持久收据，而不是猜测某个库版本用了哪个英文错误名。

### 31.5.4 【精通】服务端有界等待不证明取消已传播到底

本章库存事务保留400毫秒锁等待、500毫秒语句与700毫秒整体限制，避免服务端无限执行。gRPC客户端也携带期限，但它与数据库事务不是同一个取消机制。

客户端放弃后，运行中的事务可能已经提交；库停止等待future，也不构成跨数据库的撤销证明。服务端应控制资源与清理，调用方则必须对未知结果采取查询或同身份恢复。

## 31.6 客户端：验证回复，再决定下一步

### 31.6.1 【入门】完整远程客户端

创建inventory/src/remote.rs：
```rust
use crate::{
    model::{Action, Command, State},
    rpc::{MAX_MESSAGE_BYTES, ServiceKey},
};
use contracts::catalog::{
    GetReservationRequest, ReservationCommand, ReservationReply, ReservationState,
    inventory_client::InventoryClient,
};
use std::time::Duration;
use tonic::{
    Request, Status,
    transport::{Channel, Endpoint},
};
use uuid::Uuid;

#[derive(Clone)]
pub struct InventoryRemote {
    client: InventoryClient<Channel>,
    key: ServiceKey,
}

fn validate_reply(row: &ReservationReply, saga_id: Uuid) -> Result<State, Status> {
    if Uuid::parse_str(&row.saga_id).ok() != Some(saga_id)
        || row.product_id <= 0
        || !(1..=999).contains(&row.quantity)
        || row.unit_price_cents < 0
    {
        return Err(Status::data_loss("invalid reservation reply identity"));
    }
    match ReservationState::try_from(row.state) {
        Ok(ReservationState::Held) => Ok(State::Held),
        Ok(ReservationState::Confirmed) => Ok(State::Confirmed),
        Ok(ReservationState::Released) => Ok(State::Released),
        Ok(ReservationState::Rejected) => Ok(State::Rejected),
        _ => Err(Status::data_loss("unknown reservation reply state")),
    }
}

impl InventoryRemote {
    pub async fn connect(address: &str, key: ServiceKey) -> anyhow::Result<Self> {
        let endpoint = Endpoint::from_shared(address.to_owned())?
            .connect_timeout(Duration::from_millis(300))
            .timeout(Duration::from_millis(900));
        let channel = tokio::time::timeout(Duration::from_secs(1), endpoint.connect()).await??;
        Ok(Self {
            client: InventoryClient::new(channel)
                .max_decoding_message_size(MAX_MESSAGE_BYTES)
                .max_encoding_message_size(MAX_MESSAGE_BYTES),
            key,
        })
    }

    pub async fn apply(&self, command: &Command, action: Action) -> Result<State, Status> {
        command
            .validate()
            .map_err(|_| Status::invalid_argument("invalid reservation input"))?;
        let mut request = Request::new(ReservationCommand {
            saga_id: command.saga_id.to_string(),
            product_id: command.product_id,
            quantity: command.quantity,
            unit_price_cents: command.unit_price_cents,
        });
        self.key.attach(&mut request);
        request.set_timeout(Duration::from_millis(900));
        let mut client = self.client.clone();
        let response = tokio::time::timeout(Duration::from_secs(1), async {
            match action {
                Action::Reserve => client.reserve(request).await,
                Action::Confirm => client.confirm(request).await,
                Action::Release => client.release(request).await,
            }
        })
        .await
        .map_err(|_| Status::deadline_exceeded("inventory result may be unknown"))??
        .into_inner();
        let state = validate_reply(&response, command.saga_id)?;
        if (
            response.product_id,
            response.quantity,
            response.unit_price_cents,
        ) != (
            command.product_id,
            command.quantity,
            command.unit_price_cents,
        ) {
            return Err(Status::data_loss("reservation reply parameters differ"));
        }
        Ok(state)
    }

    pub async fn query(&self, saga_id: Uuid) -> Result<Option<ReservationReply>, Status> {
        if saga_id.is_nil() {
            return Err(Status::invalid_argument("nil saga UUID"));
        }
        let mut request = Request::new(GetReservationRequest {
            saga_id: saga_id.to_string(),
        });
        self.key.attach(&mut request);
        request.set_timeout(Duration::from_millis(900));
        let mut client = self.client.clone();
        match tokio::time::timeout(Duration::from_secs(1), client.get_reservation(request)).await {
            Err(_) => Err(Status::deadline_exceeded(
                "inventory query budget exhausted",
            )),
            Ok(Err(error)) if error.code() == tonic::Code::NotFound => Ok(None),
            Ok(Err(error)) => Err(error),
            Ok(Ok(response)) => {
                let row = response.into_inner();
                validate_reply(&row, saga_id)?;
                Ok(Some(row))
            }
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn future_or_unspecified_state_is_not_assumed_successful() {
        let id = Uuid::new_v4();
        let mut reply = ReservationReply {
            saga_id: id.to_string(),
            product_id: 1,
            quantity: 1,
            unit_price_cents: 19900,
            state: 0,
        };
        assert_eq!(
            validate_reply(&reply, id).unwrap_err().code(),
            tonic::Code::DataLoss
        );
        reply.state = 99;
        assert!(validate_reply(&reply, id).is_err());
        reply.state = ReservationState::Held as i32;
        assert_eq!(validate_reply(&reply, id).unwrap(), State::Held);
        assert!(validate_reply(&reply, Uuid::new_v4()).is_err());
    }
}
```

InventoryRemote保存可复用的Channel和ServiceKey，每次克隆生成客户端句柄，不为每条RPC重新构造整个连接管理器。它没有内置无限重试，调用方能够明确观察错误并根据业务意图恢复。

### 31.6.2 【进阶】三层客户端预算

连接阶段有300毫秒connect_timeout，建立连接的整体等待再由一秒Tokio限制。每次调用携带900毫秒grpc-timeout，本地通道也配置900毫秒等待，最外层一秒守护避免调用代码无限等待。

多个预算不是把时长相加后才超时，也不保证每次由同一层先触发。DNS、连接、排队、处理和响应阶段的耗时分布不同，测试应判断所需行为与等待上界，不固定到毫秒级调度次序。

### 31.6.3 【进阶】先验证请求，再发网络

apply先调用Command::validate。非法数量、负价、无效标识等在本地就能拒绝，减少无意义流量。服务端仍重复验证，因为其他客户端可以绕过这层封装。

两端校验分别保护不同信任边界，不是为了让合法输入被改写成两种规则。领域范围继续由同一个Command定义，RPC层解析字符串身份，最终事务再核对收据参数。

### 31.6.4 【进阶】回复身份必须与请求一致

validate_reply解析返回UUID、检查商品id、数量、单价范围和已知状态。apply随后比较商品、数量与单价是否对应本次命令，错误内容返回DataLoss。

这样可以发现“请求商品A，却返回商品B的合法结构”。仅重新构造一个合法对象仍不够，还应验证它属于这次请求；这与前面修复缓存键和payload身份不一致是同一类边界问题。

### 31.6.5 【进阶】query返回的是什么证据

query返回Option&lt;ReservationReply&gt;，不存在是None，其他错误继续保留，不能全部转换为None。返回对象已通过UUID、范围与状态校验，但query只接收UUID，无法自行知道调用方原先期望的商品与数量。

恢复调用方应将回复字段与保存的原命令核对，再解释State。不能只看某个回复state为Held就放弃参数检查；后续Confirm/Release也继续携带原参数，由服务端核对同一意图。

### 31.6.6 【精通】为什么没有自动切到本地SQL

客户端连接失败时不会偷偷直接连商品数据库。否则服务身份、并发限制和协议演进被绕开，调用方也获得了不属于它的数据写权限。

也不能把库存RPC故障退化为旧商品PUT修改stock。第30章已关闭这条绕行入口，错误恢复必须围绕库存收据和明确命令继续，而不是寻找另一条能改数字的路径。

### 31.7.1 【入门】完整catalog入口

更新services/catalog/src/main.rs：
```rust
use anyhow::Context;
use contracts::catalog::catalog_server::CatalogServer;
use platform::ShutdownBudget;
use sqlx::postgres::PgPoolOptions;
use std::time::Duration;
use tokio_util::sync::CancellationToken;
use tonic::{Request, Status, transport::Server};
use tonic_health::ServingStatus;

async fn signal() {
    #[cfg(unix)]
    {
        let mut term = tokio::signal::unix::signal(tokio::signal::unix::SignalKind::terminate())
            .expect("install SIGTERM handler");
        tokio::select! { _ = tokio::signal::ctrl_c() => {}, _ = term.recv() => {} }
    }
    #[cfg(not(unix))]
    {
        tokio::signal::ctrl_c()
            .await
            .expect("install ctrl-c handler");
    }
}
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    tracing_subscriber::fmt()
        .with_env_filter("info,catalog=debug")
        .init();
    let key = std::env::var("RUSTMALL_CATALOG_TOKEN").context("catalog token missing")?;
    anyhow::ensure!(
        key.len() >= 32 && key.bytes().all(|byte| byte.is_ascii_graphic()),
        "catalog token must be >=32 visible ASCII bytes"
    );
    let inventory_raw =
        std::env::var("RUSTMALL_INVENTORY_TOKEN").context("inventory token missing")?;
    anyhow::ensure!(
        inventory_raw != key,
        "catalog and inventory tokens must differ"
    );
    let inventory_key = inventory::rpc::ServiceKey::parse(&inventory_raw)?;
    let url = std::env::var("DATABASE_URL").context("catalog database missing")?;
    let pool = PgPoolOptions::new()
        .max_connections(10)
        .acquire_timeout(Duration::from_millis(500))
        .connect(&url)
        .await?;
    let api = catalog::CatalogApi::new(pool.clone());
    let auth = move |request: Request<()>| -> Result<Request<()>, Status> {
        match request
            .metadata()
            .get("x-rustmall-service-token")
            .and_then(|v| v.to_str().ok())
        {
            Some(value) if value == key => Ok(request),
            _ => Err(Status::unauthenticated("service identity required")),
        }
    };
    let (reporter, health) = tonic_health::server::health_reporter();
    reporter
        .set_service_status("liveness", ServingStatus::Serving)
        .await;
    reporter
        .set_service_status("readiness", ServingStatus::NotServing)
        .await;
    let token = CancellationToken::new();
    let health_pool = pool.clone();
    let health_token = token.clone();
    let mut checker = tokio::spawn(async move {
        loop {
            let ok = matches!(
                tokio::time::timeout(
                    Duration::from_millis(500),
                    sqlx::query("SELECT 1").execute(&health_pool)
                )
                .await,
                Ok(Ok(_))
            );
            reporter
                .set_service_status(
                    "readiness",
                    if ok {
                        ServingStatus::Serving
                    } else {
                        ServingStatus::NotServing
                    },
                )
                .await;
            tokio::select! {
                () = health_token.cancelled() => break,
                () = tokio::time::sleep(Duration::from_secs(2)) => {}
            }
        }
    });
    let addr = std::env::var("CATALOG_ADDR")
        .unwrap_or_else(|_| "127.0.0.1:50051".into())
        .parse()?;
    let server = Server::builder()
        .add_service(health)
        .add_service(inventory::rpc::service(pool.clone(), inventory_key))
        .add_service(CatalogServer::with_interceptor(api, auth))
        .serve_with_shutdown(addr, token.clone().cancelled_owned());
    tokio::pin!(server);
    let (result, budget) = tokio::select! {
       result = &mut server => {
            token.cancel();
            (result.context("gRPC server failed"), ShutdownBudget::new(Duration::from_secs(20)))
       },
       () = signal() => {
            token.cancel();
            let budget = ShutdownBudget::new(Duration::from_secs(20));
            let result = match budget.wait("gRPC", &mut server).await {
                Ok(result) => result.context("gRPC server failed"),
                Err(error) => { checker.abort(); return Err(error); }
            };
            (result, budget)
       }
    };
    match budget.wait("health checker", &mut checker).await {
        Ok(result) => result?,
        Err(error) => {
            checker.abort();
            return Err(error);
        }
    }
    budget.wait("database", pool.close()).await?;
    result
}
```

在已有健康服务和Catalog服务之外注册Inventory，继续共享PgPool、正常信号处理、CancellationToken与ShutdownBudget。没有在每个RPC处理函数里启动一个新运行时或新连接池。

### 31.7.2 【进阶】凭据分开，故障域尚未分开

启动要求RUSTMALL_INVENTORY_TOKEN存在，且与RUSTMALL_CATALOG_TOKEN不同。普通商品调用者掌握商品凭据，不因此获得库存命令权限。

两个服务仍在同一catalog进程内，同一进程或数据库故障会影响两者。凭据隔离是能力边界，不代表已经实现独立部署、独立容量或机器级故障隔离。

### 31.7.3 【进阶】原健康检查继续保留

liveness和readiness仍使用现有gRPC Health协议：基本进程存活与商品数据库SELECT 1。注册新Inventory并不会自动让健康检查覆盖每种业务动作、服务凭据或所有表。

本章实际通过Inventory调用验证预留与查询，补足单看readiness的不足。后续治理可以进一步区分不同能力的就绪与恢复策略，但不能因为共享端口就认定一次健康成功代表全部RPC正确。

## 31.8 通过未知结果恢复，而非盲目重试

### 31.8.1 【入门】提交成功、回复没收到

设库存事务已经把十件变成九件并保存Held，响应在到达调用方之前延迟或断开。调用方只看见超时，此时可以确定的是自己没有拿到最终回复，不能确定库存没有变化。

如果直接用新UUID再Reserve，可能再减一件。正确恢复要保留原标识和参数，查询收据；查到原Held后可以按流程继续，重复原命令也应汇聚为同一效果。

### 31.8.2 【进阶】查询失败不等于None

连接失败、资源耗尽和查询超时都可能让query返回Err。这与服务端明确返回NotFound转换成Ok(None)不同。错误分支不能被`.ok().flatten()`一类写法吞成“没有预留”。

业务流程应保存未知状态并在有界计划内继续观察，或根据期限发送同一意图的关闭动作。未知结果是需要持久化协调的状态，不是临时日志里的一句抱怨。

### 31.8.3 【进阶】收到Rejected后何时使用新标识

Rejected表示这次合法意图已经得到稳定拒绝。过一会儿补货并不让同一UUID重新占用成功。如果用户确实重新发起另一轮购买，可以产生新标识，但应作为新的业务尝试记录。

这与超时重试截然不同。超时可能已经成功，不能自动换标识；Rejected是明确结果，可以由业务决定是否允许新尝试。区分它们能避免把补货恢复与网络重试混在一起。

### 31.8.4 【精通】业务取消与RPC取消

取消RPC表示调用者不再等待这次传输；Release是有身份、参数和持久化效果的业务命令。前者不会自动创建库存取消屏障，后者即使先于Reserve到达，也会留下Released防止迟到占用。

因此不能只在订单超时后drop一个RPC future，就认为库存已经安全释放。协调器还需要查询、发出同一意图的Release并观察最终状态，这会在持久化订单章节继续展开。

### 31.8.5 【精通】重试范围与预算

没有结果时可以重复同一幂等命令，但仍要限制次数、总时长和并发。错误凭据、参数冲突、未知枚举不能靠重试修复；暂时锁冲突等也必须结合剩余业务期限与退避。

本章客户端只提供一次调用与查询原语，后续协调器负责持久计划。这样不会在网络封装、服务层和订单worker各自藏一套重试，再让一次操作放大成几十次请求。

### 31.9.2 【进阶】先得到类型正确的拒绝

错误商品凭据与重复metadata应返回Code::Unauthenticated，数量非法返回InvalidArgument，身份参数不同返回FailedPrecondition。测试比较枚举，不比较Status显示文案。

### 31.9.3 【进阶】重建传输实验的证据边界

一个测试先完成Reserve、丢弃业务结果，然后停止服务器任务，在同一数据库上重建服务器和连接。重复原意图仍为Held且只扣一次，证明收据不依赖原连接或服务器任务内存。

它本身没有让一个已经提交的回复在网络中丢失；第一遍调用实际已收到成功。不能把这个测试单独描述为“已经验证客户端超时后恢复”。我们另外增加下一项更明确的故障窗口。

### 31.9.4 【精通】完整提交后超时实验

创建inventory/tests/rpc_uncertain.rs：
```rust
use contracts::catalog::{
    GetReservationRequest, ReservationCommand, ReservationReply,
    inventory_client::InventoryClient,
    inventory_server::{Inventory, InventoryServer},
};
use inventory::{
    model::{Action, Command, State},
    remote::InventoryRemote,
    rpc::{InventoryApi, ServiceKey},
};
use messaging::store::{self, Draft};
use sqlx::PgPool;
use std::{
    sync::{
        Arc,
        atomic::{AtomicBool, Ordering},
    },
    time::Duration,
};
use tokio::sync::Notify;
use tokio_util::sync::CancellationToken;
use tonic::{
    Code, Request, Response, Status,
    transport::{Endpoint, Server},
};
use uuid::Uuid;

const KEY: &str = "inventory-response-loss-lab-token-0123456789";
#[derive(Clone)]
struct HoldFirstReply {
    inner: InventoryApi,
    first: Arc<AtomicBool>,
    committed: Arc<Notify>,
    release_reply: Arc<Notify>,
}
#[tonic::async_trait]
impl Inventory for HoldFirstReply {
    async fn reserve(
        &self,
        request: Request<ReservationCommand>,
    ) -> Result<Response<ReservationReply>, Status> {
        let response = self.inner.reserve(request).await?;
        // The real inventory transaction has committed, but no reply has been returned.
        if self.first.swap(false, Ordering::SeqCst) {
            self.committed.notify_one();
            self.release_reply.notified().await;
        }
        Ok(response)
    }
    async fn confirm(
        &self,
        request: Request<ReservationCommand>,
    ) -> Result<Response<ReservationReply>, Status> {
        self.inner.confirm(request).await
    }
    async fn release(
        &self,
        request: Request<ReservationCommand>,
    ) -> Result<Response<ReservationReply>, Status> {
        self.inner.release(request).await
    }
    async fn get_reservation(
        &self,
        request: Request<GetReservationRequest>,
    ) -> Result<Response<ReservationReply>, Status> {
        self.inner.get_reservation(request).await
    }
}

async fn client_deadline_after_commit_recovers_by_same_identity(pool: PgPool) {
    for sql in [
        include_str!("../../services/catalog/migrations/0001_catalog.sql"),
        include_str!("../../services/catalog/migrations/0002_product_outbox.sql"),
        include_str!("../../services/catalog/migrations/0003_inventory_reservations.sql"),
    ] {
        sqlx::raw_sql(sql).execute(&pool).await.unwrap();
    }
    let event = store::create(
        &pool,
        &Draft {
            name: "响应丢失实验".into(),
            price_cents: 19900,
            stock: 10,
        },
    )
    .await
    .unwrap();
    let command = Command {
        saga_id: Uuid::new_v4(),
        product_id: event.aggregate_id,
        quantity: 1,
        unit_price_cents: 19900,
    };
    let committed = Arc::new(Notify::new());
    let release_reply = Arc::new(Notify::new());
    let api = HoldFirstReply {
        inner: InventoryApi::new(pool.clone()),
        first: Arc::new(AtomicBool::new(true)),
        committed: committed.clone(),
        release_reply: release_reply.clone(),
    };
    let listener = tokio::net::TcpListener::bind("127.0.0.1:0").await.unwrap();
    let address = format!("http://{}", listener.local_addr().unwrap());
    let stop = CancellationToken::new();
    let shutdown = stop.clone();
    let mut server = tokio::spawn(async move {
        Server::builder()
            .add_service(InventoryServer::with_interceptor(
                api,
                ServiceKey::parse(KEY).unwrap(),
            ))
            .serve_with_incoming_shutdown(
                tokio_stream::wrappers::TcpListenerStream::new(listener),
                shutdown.cancelled_owned(),
            )
            .await
            .unwrap();
    });
    let channel = Endpoint::from_shared(address.clone())
        .unwrap()
        .connect()
        .await
        .unwrap();
    let mut raw = InventoryClient::new(channel);
    let mut request = Request::new(ReservationCommand {
        saga_id: command.saga_id.to_string(),
        product_id: command.product_id,
        quantity: 1,
        unit_price_cents: 19900,
    });
    ServiceKey::parse(KEY).unwrap().attach(&mut request);
    request.set_timeout(Duration::from_secs(1));
    let pending = tokio::spawn(async move { raw.reserve(request).await });
    tokio::time::timeout(Duration::from_millis(900), committed.notified())
        .await
        .expect("real transaction must commit before the client deadline");
    let result = tokio::time::timeout(Duration::from_secs(2), pending)
        .await
        .expect("client must not wait forever")
        .unwrap();
    let error = result.expect_err("first reply must not reach the caller");
    assert!(matches!(
        error.code(),
        Code::Cancelled | Code::DeadlineExceeded
    ));
    // Release the test handler even if the transport already cancelled it.
    release_reply.notify_one();
    let client = InventoryRemote::connect(&address, ServiceKey::parse(KEY).unwrap())
        .await
        .unwrap();
    let receipt = client.query(command.saga_id).await.unwrap().unwrap();
    assert_eq!(
        (
            receipt.product_id,
            receipt.quantity,
            receipt.unit_price_cents
        ),
        (command.product_id, 1, 19900)
    );
    assert_eq!(
        client.apply(&command, Action::Reserve).await.unwrap(),
        State::Held
    );
    let state: (i32, i64, i64) = sqlx::query_as("SELECT stock,revision,(SELECT count(*) FROM product_outbox WHERE aggregate_id=$1) FROM products WHERE id=$1").bind(command.product_id).fetch_one(&pool).await.unwrap();
    assert_eq!(state, (9, 2, 2));
    drop(client);
    stop.cancel();
    match tokio::time::timeout(Duration::from_secs(2), &mut server).await {
        Ok(result) => result.unwrap(),
        Err(_) => {
            server.abort();
            let outcome = server.await;
            assert!(outcome.is_ok() || outcome.unwrap_err().is_cancelled());
        }
    }
}
```

HoldFirstReply先委托真实InventoryApi完成事务，再通知测试“已经提交”，随后阻止第一次返回响应。客户端携带一秒期限，必须先观察到提交通知，再收到Cancelled或DeadlineExceeded，而不是成功Reply。

之后用原UUID查询收据、比较参数并重复Reserve，最终库存九、商品修订二、事件两条。两个版本分别是商品初始创建和一次预留，没有因为恢复多扣库存。这个实验明确覆盖数据库成功与客户端失败同时成立的情形。

## 31.10 排错、分层练习与下一章

### 31.10.1 【入门】按证据排查

| 现象 | 收集什么 | 判断与修复 |
| --- | --- | --- |
| 启动提示inventory token missing | 服务终端是否加载库存配置 | 明确提供独立库存凭据，不关闭认证 |
| 两种令牌相同而启动失败 | 配置变量来源 | 分开生成，避免复制商品凭据 |
| 商品RPC可用，库存Unauthenticated | 请求方法与使用凭据类别 | 库存能力有独立权限，不使用商品令牌 |
| Reserve返回Ok但没拿到货 | Reply中的明确state | Rejected是正确业务拒绝，不是Held |
| DataLoss | 回复UUID、参数和枚举整数 | 不把未知或不匹配回复当成功，检查版本或服务缺陷 |
| ResourceExhausted | 同进程在途请求与共享许可 | 满载立即拒绝，不能推断原操作未提交 |
| Unavailable伴锁等待 | SQLSTATE与阻塞事务 | 找出锁持有者，按同一意图有界恢复 |
| 超时后重试库存少两次 | 是否换过UUID与参数 | 重试必须保留身份，查询原收据 |
| query失败被当作不存在 | Err与Ok(None)分支 | 保留错误，不吞成空收据 |
| 客户端断开却收据Held | 提交时序和持久化状态 | RPC取消不等于业务Release，按恢复协议继续 |
| 独立实验停止与容器行为不同 | Ctrl-C和SIGTERM处理入口 | 实验仅处理Ctrl-C，正式入口用已有停机预算 |

### 31.10.2 【入门练习】区分三种拒绝

库存不足、库存令牌错误、同UUID改数量，分别是怎样的返回？

参考答案：库存不足是正常Reply中的Rejected；错误令牌是Unauthenticated；身份参数冲突是FailedPrecondition。第一种是业务判断完成，另外两种分别属于调用身份与意图不一致。

### 31.10.3 【操作练习】用两个进程验证同一意图

启动正式catalog，用两个远程CLI进程重复同一UUID的Reserve，核对回复、收据、stock、revision和Outbox，再执行Release两次。

评分要点：两次Reserve只有一次库存效果，Release也只归还一次，参数保持一致；没有给客户端数据库凭据，也没有用商品PUT修复数字。请求到达先后可以不同，业务结果应稳定。

### 31.10.4 【推理练习】超时后查询也失败

客户端Reserve超时，随后query返回Unavailable。能否将订单视为未占库，再用新UUID发起预留？

参考答案：不能。两个传输失败都没有提供未提交证明，应保留原意图与未知结果，按总预算继续查询或发同身份关闭动作。新UUID可能与已提交的旧预留同时成立。

### 31.10.5 【推理练习】未知枚举为何返回DataLoss

服务端返回结构可解码、state为99。为何不把它当作Rejected继续运行？

参考答案：当前客户端不知道这个值表达什么，随意归类可能错误释放、重试或确认。应拒绝解释并诊断版本兼容或异常回复，不能让协议新增值默默改变旧业务状态机。

### 31.10.6 【扩展练习】给恢复查询保留容量

若十六个命令全部等待数据库，恢复查询也拿不到许可，你会怎样设计更细的预算？

参考要点：可以区分查询与命令许可、保留少量查询通道，配合数据库连接预算、上游总期限与负载测量；还要限制查询风暴。只增加一个无界队列或不断增大连接池，不能保证恢复请求及时完成。

### 31.10.7 【衔接】从预留继续到可审计库存调整

现在库存事务有了有界RPC、独立凭据、严格回复验证和未知结果恢复原语。完整订单协调、跨服务业务期限与资金补偿仍需后面继续实现。

第30章已禁止普通商品更新覆盖stock；下一章在这一边界上增加专门库存调整命令、幂等调整收据与可追查的事务效果，补足补货和盘点场景。不会重新打开一个任意替换库存的普通CRUD入口。

关于传输取消与期限，可对照[gRPC取消说明](https://grpc.io/docs/guides/cancellation/)与[期限指南](https://grpc.io/docs/guides/deadlines/)。它们描述调用生命周期，本章用实际数据库故障窗口进一步验证了业务恢复所需的事实。

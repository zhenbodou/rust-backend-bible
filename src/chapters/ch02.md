# 第 2 章 所有权、借用与生命周期

所有权是 Rust 最独特的设计：它让 Rust 不需要垃圾回收，也能在编译期保证没有野指针、没有重复释放、没有数据竞争。初学时常见的编译错误有不少与本章有关，建议把本章每个示例都亲手运行、故意改错、阅读报错。

## 2.1 内存基础：栈、堆与三种内存管理方式

### 2.1.1 【入门】程序运行时的两块主要内存

程序运行时，数据主要放在两个地方：栈（stack）和堆（heap）。用餐厅来比喻：

栈像服务员手里的一摞托盘：只能在最上面放、从最上面拿（后进先出），速度极快。但每个托盘的大小在放上去之前就必须确定。

堆像餐厅的储物仓库：可以随时申请任意大小的空间，但要先找管理员登记、找空位（分配），用完要归还（释放），比较慢；拿东西时也要按“仓位号”（指针）去找。

| 维度 | 栈 | 堆 |
| --- | --- | --- |
| 管理 | 调用栈上的帧随控制流建立和退出 | 通过分配器申请空间，由拥有者负责释放 |
| 大小 | 局部值布局需要满足编译要求；不<br>意味着所有数据都在栈上 | 申请的容量可以在运行时确定 |
| 常见内容 | 局部变量、返回信息，以及容器的<br>管理字段等 | String、Vec 等容器管理的动态存储 |
| 性能 | 帧管理通常简单，但访问和实际布<br>局仍受优化影响 | 分配与释放需要额外工作；元素访问未必比栈慢 |
| 容量限制 | 取决于平台、链接与线程配置 | 受地址空间、资源限制和可用内存等约束 |

以 let s = String::from("键盘"); 为例，下图按常见 64 位目标画出概念布局。具体字段顺序不应据此假定：

```text
        栈（变量 s，24 字节）                   堆（6 字节）
   ┌──────────┬────────────────┐
   │ ptr      │ 0x7f..a0 ──────┼──────────►  ┌────┬────┬────┬────┬────┬────┐
   ├──────────┼────────────────┤             │ e9 │ 94 │ ae │ e7 │ 9b │ 98 │  ← "键盘" 的UTF-8 字节
   │ len      │ 6              │             └────┴────┴────┴────┴────┴────┘
   ├──────────┼────────────────┤
   │ capacity │ 6              │
   └──────────┴────────────────┘
```

String 、Vec 都是这种“栈上一个小头部（指针 + 长度 + 容量），真正数据在堆上”的结构。理解这张图，本章所有概念都会变得直观。

### 2.1.2 【入门】堆内存的核心难题：谁来释放

栈上的数据随函数返回自动消失，没有问题。难的是堆：申请了的内存必须在不再使用后、恰好释放一次。历史上有三种解决方案：

| 方式 | 常见机制 | 优势 | 需要理解的限制 |
| --- | --- | --- | --- |
| 手动管理与 RAII | C 可显式分配释放；现代<br>C++ 也大量使用 RAII 和智<br>能指针 | 可控制资源生命周期 | 误用原始指针可能造成释放后使用、<br>重复释放等问题 |
| 垃圾回收 | 不同运行时使用追踪、引用<br>计数等不同机制 | 自动处理许多内存回收<br>工作 | 时间、内存和停顿特征取决于具体<br>机制与工作负载 |
| Rust 所有权与 RAII | 编译器检查移动和借用，安<br>排相应的析构逻辑 | 在安全抽象成立的前提<br>下预防多类内存错误 | 不保证没有泄漏；分配器、引用计<br>数及析构仍可能有运行成本 |

### 2.1.3 【进阶】这和后端开发有什么关系

延迟分析：Rust 通常不依赖追踪式 GC，但这不保证 P99 自动平稳。分配器、锁竞争、磁盘与网络等待、任务调度和业务代码仍会造成延迟，需要通过测量定位。

内存管理：所有权有助于明确资源生命周期，但实际内存需求取决于并发量、缓存、队列、依赖与输入规模。容器资源限制应以测量结果为依据，不预设所有服务都能用同一小内存额度运行。

并发安全：所有权规则同时保证了多线程下不会发生数据竞争（第 6、10 章），这正是高并发后端最难调试的那类 bug。

资源管理统一：不止内存，数据库连接、文件句柄、锁、网络连接都靠同一套规则在离开作用域时自动归还（RAII，见 2.2.6），仍需防范长时间持有连接、任务未结束、显式遗忘资源等导致的池耗尽。

### 2.1.4 【精通】栈帧、指针大小与几个事实

每次函数调用会在栈上压入一个栈帧，存放参数、局部变量和返回地址；函数返回时整个栈帧弹出。递归过深会耗尽栈空间，导致 thread 'main' has overflowed its stack 。线程栈大小与运行时配置和平台有关；异步 Future 的存储位置也取决于构造和调度方式。超大局部对象、Future 或深递归都需要具体分析。

64 位系统上指针是 8 字节，所以 String 、Vec&lt;T&gt; 的栈上部分固定是 24 字节（指针、长度、容量各 8 字节），&amp;str 和 &amp;\[T\] 是 16 字节（指针 + 长度，称为“胖指针”），指向 Sized 类型的普通引用 &amp;T 通常为 8 字节；指向动态大小类型的引用还携带元数据。

分配器：Rust 默认使用系统分配器（Linux 上是 glibc malloc）。高并发服务常替换为 mimalloc 或jemalloc （通过 #\[global\_allocator\] ），是否改善碎片、吞吐或延迟，需要针对实际工作负载比较；不能把替换分配器当成必然优化。

Box::new(x) 是把值显式放到堆上的最简单方式（第 7 章），本章暂不需要。

## 2.2 所有权三规则：移动、克隆、Copy 与 Drop

### 2.2.1 【入门】三条规则

整个所有权系统只有三条规则，务必背下来：

1. Rust 中的每一个值都有一个所有者（owner），即拥有它的那个变量。

2. 同一时刻，一个值只能有一个所有者。

3. 当所有者离开作用域时，这个值会被自动释放（drop）。

用“一本实体书”来比喻：书只能放在一个人的书架上；书可以送给别人（移动），送出后你就没有了；书的主人搬走（离开作用域）时，书被一起处理掉。

### 2.2.2 【入门】作用域与自动释放

```rust
fn main() {
    // s 还不存在
    {
        // s 从这里开始有效，堆上分配了 6 字节
        let s = String::from("键盘");
 
        // 使用 s
        println!("{s}");
 
    // 作用域结束：Rust 自动调用 drop，释放堆内存
    }
    // println!("{s}");                 // 编译错误 E0425：s 已不在作用域
}
```

离开作用域时自动释放，是编译器在 } 处帮你插入了释放代码。你不需要、也不能手动 free。

### 2.2.3 【入门】移动（move）：赋值即转交所有权

```rust
fn main() {
    let a = String::from("键盘");
 
    // 所有权从 a 移动到 b
    let b = a;
 
    // 正确
    println!("{b}");
    // println!("{a}");            // 编译错误 E0382: borrow of moved value: `a`
}
```

编译器的完整报错非常有教学意义，务必读懂：

```text
error[E0382]: borrow of moved value: `a`
 --> src/main.rs:5:16
  |
2 |     let a = String::from("键盘");
  |         - move occurs because `a` has type `String`, which does not implement the `Copy` 
     trait
3 |     let b = a;
  |             - value moved here
4 |     println!("{b}");
5 |     println!("{a}");
  |                ^^^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let b = a.clone();
  |              ++++++++
```

它告诉你：值在哪里被移走、在哪里又被使用、为什么会移动（String 没有实现 Copy）、以及一种修复方

式。Rust 编译器的报错是最好的老师，养成从头到尾读完的习惯。

为什么要这样设计？ 回看 2.1.1 的内存图。let b = a; 只复制了栈上的 24 字节头部（指针、长度、容量），两个变量的指针指向同一块堆内存。如果 a 和 b 都有效，离开作用域时两者都会去释放那块内存——这就是 C 语言里的“双重释放”漏洞。Rust 的解决办法是：复制头部后，让 a 失效。这样永远只有一个所有者负责释放。

```text
   let b = a; 之后：
   a（已失效，不能再使用）
   b: ptr ─────────►  堆上的 "键盘"
      len = 6
      capacity = 6
```

移动的成本很低：无论 String 多长，移动都只复制 24 字节。

### 2.2.4 【入门】克隆（clone）：显式深拷贝

确实需要两份独立数据时，调用 .clone() ：

```rust
fn main() {
    let a = String::from("键盘");
 
    // 在堆上分配新内存并复制全部内容
    let b = a.clone();
 
    // 两者都有效，各自独立
    println!("{a} {b}");
}
```

clone() 的成本与数据大小成正比：克隆一个有 10 万个元素的 Vec 就要复制 10 万个元素。Rust 把它设计成必须显式书写，就是为了让昂贵的操作在代码中一眼可见。

关于 clone 的实用态度：初学阶段遇到所有权报错，用 .clone() 先让程序跑起来完全没问题，后端代码中克隆一个短字符串的开销通常可以忽略（相比一次数据库查询的几毫秒，复制几十字节只要几纳秒）。随着理解加深，再把不必要的 clone 改为借用（2.4 节）。不要为了“消灭所有 clone”而写出难以维护的代码。

### 2.2.5 【入门】Copy 类型：赋值即复制

```rust
fn main() {
    let x = 5;
 
    // i32 实现了 Copy：复制一份，x 仍然有效
    let y = x;
 
    // 正确
    println!("{x} {y}");
 
    let p = (1, 2.5, true);
 
    // 元素全是 Copy 类型的元组也是 Copy
    let q = p;
    println!("{p:?} {q:?}");
}
```

Copy 是类型显式实现的 trait；不能仅凭存储位置或复制成本判断。常见实现它的类型包括：

所有整数、浮点、bool 、char

共享引用 &amp;T （复制的是指针，见 2.4 节）

元素都是 Copy 的元组和数组，如 (i64, i32) 、\[u8; 16\]

函数指针

不是 Copy 的：String 、Vec 、HashMap 、Box ，以及任何拥有堆内存或需要清理资源的类型。规则是：一个类型如果实现了 Drop（需要清理），就不能是 Copy。自定义结构体可以用#\[derive(Clone,Copy)\] 声明为 Copy，前提是所有字段都是 Copy（第 3 章）。

### 2.2.6 【进阶】Drop 与 RAII：资源管理的统一方式

值被释放时会调用它的 Drop::drop 方法。我们可以为自己的类型实现它来观察释放时机（结构体语法在第 3 章详讲，这里只需看懂）：

```rust
struct DbConnection {
    id: u32,
}
 
impl Drop for DbConnection {
    fn drop(&mut self) {
        println!("连接 {} 已归还连接池", self.id);
    }
}
 
fn main() {
    let _c1 = DbConnection { id: 1 };
    {
        let _c2 = DbConnection { id: 2 };
        println!("内部作用域结束前");
 
    // 输出：连接 2 已归还连接池
    }
    let c3 = DbConnection { id: 3 };
 
    // 手动提前释放：输出 连接 3 已归还连接池
    drop(c3);
 
    // let _ 不绑定：立即释放，输出 连接 4 已归还连接池
    let _ = DbConnection { id: 4 };
    println!("main 结束前");
 
// 输出：连接 1 已归还连接池
}
```

完整输出：

```text
内部作用域结束前
连接 2 已归还连接池
连接 3 已归还连接池
连接 4 已归还连接池
main 结束前
连接 1 已归还连接池
```

要点：

释放顺序：同一作用域内的变量按声明的相反顺序释放（后声明的先释放）。

drop(x) 是标准库函数，它获取 x 的所有权后什么都不做，函数结束时 x 自然被释放——这就是“手动提前释放”的原理。不能直接调用 x.drop() （编译错误 E0040）。

对本节新建的普通临时对象，let \_ = expr; 在语句结束时释放；let \_name = expr; 建立绑定并保留到销毁作用域结束。若右侧是已有变量，忽略模式本身不意味着移动并销毁它（1.2.8 节埋下的伏笔，在这里得到验证）。

这种“获取资源时绑定到一个值，值销毁时自动释放资源”的模式叫 RAII（Resource Acquisition Is Initialization，资源获取即初始化）。后端中处处是 RAII：

| 资源 | 取得方式示例 | 释放或清理行为 |
| --- | --- | --- |
| 池化数据库连接 | pool.acquire().await | 池化包装对象销毁时由连接池接管归还或清理 |
| 数据库事务 | pool.begin().await | 未提交事务按驱动的 Drop 机制发起回滚；不能<br>把 Drop 当作可等待的确认 |

| 资源 | 取得方式示例 | 释放或清理行为 |
| --- | --- | --- |
| 互斥锁守卫 | mutex.lock() | 守卫销毁时释放所持锁 |
| 文件句柄 | File::open | 文件对象销毁时关闭句柄；需确认写入结果时显<br>式检查 flush / sync 等操作 |
| span 进入守卫 | span.enter() | 守卫销毁时退出当前 span；不等于 span 对象<br>被销毁 |
| 信号量许可 | semaphore.acquire().await | 许可对象销毁时归还许可 |

数据库事务的 Drop 行为是安全网，显式 commit / rollback 才是检查提交与回滚结果的位置。对异步驱动，销毁对象通常只能安排回滚，不能在 Drop 中 await 并确认服务器已完成操作；后续数据库章节需结合驱动与连接池行为说明。

### 2.2.7 【精通】移动语义的细节

移动是浅拷贝 + 源失效，由编译器静态跟踪，运行时没有任何“失效标记”开销（某些条件分支中的移动除外，编译器会生成一个 drop 标志位）。

重新赋值会先释放旧值：let mut s = String::from("a"); s = String::from("b");第二行会先 drop 掉 "a"。

被移走的变量可以重新赋值后再使用：let mut a = String::new(); let b = a;a=String::from("新"); println!("{a}"); 是合法的。

内存泄漏不算不安全：Rust 保证不会访问无效内存，但不保证一定不泄漏。std::mem::forget(x)、Box::leak 、引用计数的循环引用（第 7 章）都会导致泄漏，它们在安全 Rust 中是允许的。服务中若发现内存持续增长，排查方向往往是无界的缓存或队列，而不是“忘记释放”。

Drop 中不要 panic，也不要执行耗时的阻塞操作；异步代码中 Drop 不能 .await （第 11 章会讲异步资源清理的正确做法）。

Clone 与 Copy 的关系：Copy 要求同时实现 Clone ；对 Copy 类型调用 .clone() 与直接赋值等价，clippy 会提示 clone\_on\_copy 。

### 2.2.8 常见编译错误与解读

| 诊断 | 原因 | 处理 |
| --- | --- | --- |
| E0382：移动后使用 | 非 Copy 值已转交 | 只读时借用；确需独立副本才 clone |
| E0382：循环前一轮已移动 | 下一轮仍想用已被消耗的值 | 调整所有权交接或改为借用 |
| E0505 | 借用仍需使用时移动拥有者 | 让借用先结束，或重新设计返回值 |

| 诊断 | 原因 | 处理 |
| --- | --- | --- |
| E0507 | 试图从共享引用中移出非 Copy 值 | 借用或 clone；拥有可变访问权限时才考虑<br>take / replace |
| E0040 | 显式调用析构方法 x.drop() | 需要提前释放时调用 drop(x) |
| E0184 / E0204 | 为有析构要求或非 Copy 字段的类<br>型实现 Copy | 按含义仅实现 Clone，或修改类型设计 |

## 2.3 所有权与函数：传参、返回值与部分移动

### 2.3.1 【入门】传参就是赋值

把值传给函数，和 let 赋值的规则完全一样：非 Copy 类型会移动进函数，Copy 类型会被复制。

```rust
// name 获得所有权
fn save_product(name: String) {
    println!("保存商品：{name}");
 
// name 在这里被释放
}
 
// i32 是 Copy，传入的是副本
fn double(n: i32) -> i32 { n * 2 }
 
fn main() {
    let name = String::from("机械键盘");
 
    // name 被移动进函数
    save_product(name);
    // println!("{name}");                // 编译错误 E0382：name 已被移动
    let qty = 3;
    let d = double(qty);
 
    // qty 仍然可用
    println!("{qty} {d}");
}
```

### 2.3.2 【入门】返回值转移所有权

```rust
fn create_sku(category: &str, id: i64) -> String {
    // 在函数内部创建
    let sku = format!("{category}-{id:06}");
 
    // 所有权转移给调用者，不会被释放
    sku
}
 
// 拿走所有权、修改、再还回去
fn add_suffix(mut s: String) -> String {
    s.push_str("-NEW");
    s
}
 
fn main() {
    // "KB-000042"
    let sku = create_sku("KB", 42);
 
    // 移进去，再移出来（用隐藏接住）
    let sku = add_suffix(sku);
 
    // KB-000042-NEW
    println!("{sku}");
}
```

注意 fn add\_suffix(mut s: String) ：参数前的 mut 表示函数内部可以修改这个参数，这与调用方的变量是否 mut 无关——所有权已经转交，新主人想怎么处理都可以。

“移进去再移出来”的写法虽然可行，但很繁琐：如果函数只是想看一看或改一改数据，却要拿走所有权再还回来，太麻烦了。这正是下一节“借用”要解决的问题。

### 2.3.3 【入门】选择参数类型的决策表

这张表是写后端函数时每天都要用的，建议贴在显示器旁边：

| 用途 | 典型参数 | 例子 |
| --- | --- | --- |
| 只读 | &amp;T；字符串常用 &amp;str，序列常用<br>&amp;\[T\] | fn validate(name: &amp;str) -&gt; bool |
| 修改但不取得所有权 | &amp;mut T 或 &amp;mut \[T\] | fn apply\_discount(items: &amp;mut \[i64\]) |

| 用途 | 典型参数 | 例子 |
| --- | --- | --- |
| 保存或转交数据 | T 或满足需求的拥有型参数 | fn new(name: String) -&gt; Product |
| 小的 Copy 值 | 直接传 T | fn find(id: i64) |

校验通常借用输入，构造实体通常取得拥有型字段；发送到独立任务前，应检查实际的生命周期和Send 等约束。

### 2.3.4 【进阶】部分移动（partial move）

从元组或结构体中移出一个字段，会导致整体不能再使用，但其余字段仍然可用：

```rust
fn main() {
    let order = (String::from("A001"), String::from("alice"), 19_900_i64);
 
    // 移出第 0 个字段
    let order_no = order.0;
    println!("{order_no}");
 
    // 正确：第 1 个字段没被移动
    println!("{}", order.1);
 
    // 正确：i64 是 Copy
    println!("{}", order.2);
    // println!("{order:?}");             // 错误 E0382：borrow of partially moved value: 
// `order`
}
```

模式匹配解构时也会发生部分移动；只想借用字段时，用 ref 关键字或匹配引用（第 3 章详解）。

### 2.3.5 【进阶】从容器中取出值

不能直接从 Vec 中“移出”一个元素，因为那会在 Vec 中留下一个空洞：

```rust
fn main() {
    let mut names = vec![String::from("键盘"), String::from("鼠标")];
 
    // let first = names[0];               // 错误 E0507: cannot move out of index of 
// `Vec<String>`
    // 方法 1：借用
    let first = &names[0];
 
    // 方法 2：克隆
    let copied = names[0].clone();
 
    // 方法 3：用会转移所有权的方法：pop、remove、swap_remove
    let last = names.pop();
 
    // 方法 4：拿走值，原位置留下默认值（空字符串）
    let taken = std::mem::take(&mut names[0]);
    // 方法 5：替换
    let replaced = std::mem::replace(&mut names[0], String::from("耳机"));
 
    println!("{first:?}");
    // 上面这行其实会编译失败：first 借用了 names，之后又可变地修改了 names。
    // 这正是 2.4 节借用规则要解释的内容——请把 println 移到 let first 之后立即执行再试。
    println!("{copied} {last:?} {taken:?} {replaced} {names:?}");
}
```

（这个例子故意留了一个借用错误，请亲手运行并按注释修复，体会 2.4 节的规则。）std::mem::take和 std::mem::replace 在实现状态转换时很常用，例如把一个订单中的明细列表整体取走去处理，同时留下空列表。

### 2.3.6 【精通】所有权与性能的真相

移动不复制堆数据：把一个 100 MB 的 Vec 传进函数，不需要克隆每个堆上元素；具体管理字段大小依目标平台而定。移动与 clone 的成本应区分开来，不能据此保证任意函数调用都很快。

编译器会进一步优化：返回值通常被直接构造在调用者的栈帧里（返回值优化），连 24 字节的复制都省了。

impl Into&lt;String&gt; 参数：构造函数常写成 fn new(name: impl Into&lt;String&gt;) ，这样调用方既可以传 &amp;str （内部自动转为 String），也可以传已有的 String （直接移动，无需复制）。第 5 章讲完 trait 后会大量使用。

Cow&lt;str&gt; （写时克隆）：函数大多数情况下原样返回输入、偶尔需要修改时，返回 Cow&lt;'\_,str&gt;可以避免不必要的分配。例如规范化用户名时，如果输入本来就是小写且无空格，就直接借用原字符串。

### 2.3.7 常见编译错误与解读

| E0382：调用后值已移动 | 函数按值取得 String | 只读用途改收 &amp;str |
| E0507：无法移出 Vec 下标 | 索引访问不能留下未初始化元素 | 借用、clone，或按用途 pop / remove / take |
| E0382：整体被部分移动 | 一个字段已被移出 | 仅使用剩余字段，或原先改为借用字段 |

| E0308 | 拥有型与借用型不匹配 | 按实际用途借用，或明确构造拥有型值 |

## 2.4 引用与借用

### 2.4.1 【入门】引用：不拿走所有权地使用数据

引用（reference）就像图书馆的借书证：你可以凭它看书，但书的所有权还是图书馆的。创建引用的行为叫借用（borrowing）。

```rust
// 参数类型 &String：一个对 String 的引用
fn name_length(name: &String) -> usize {
    name.chars().count()
// name 是引用，离开作用域时不会释放它指向的数据
}
 
fn main() {
    let product = String::from("机械键盘");
 
    // &product：创建一个引用传进去
    let len = name_length(&product);
 
    // product 仍然有效！
    println!("{product} 有 {len} 个字");
}
```

内存示意：

```text
  name（引用，8 字节）      product（String，24 字节）        堆
  ┌──────────┐             ┌──────────┬────────┐
  │ ptr ─────┼───────────► │ ptr      │ ───────┼──────►  "机械键盘"
  └──────────┘             │ len      │ 12     │
                           │ capacity │ 12     │
                           └──────────┴────────┘
```

共享引用可以复制，复制不克隆被引用数据；可变引用不实现 Copy，不能照搬共享引用的复制规则。（按 1.4.5 节的黄金法则，这里参数更好的写法是 &amp;str ，2.4.6 节会解释为什么两者都能工作。）

### 2.4.2 【入门】可变引用：借来修改

```rust
// &mut i32：可变引用
fn restock(stock: &mut i32, qty: i32) {
    // *stock：解引用，访问引用指向的值
    *stock += qty;
}
 
fn add_tag(tags: &mut Vec<String>, tag: &str) {
    // 调用方法时编译器自动解引用，不用写 (*tags).push
    tags.push(tag.to_string());
}
 
fn main() {
    // 被可变借用的变量本身必须是 mut
    let mut stock = 10;
 
    // 创建可变引用：&mut
    restock(&mut stock, 5);
    let mut tags = vec![];
    add_tag(&mut tags, "热销");
 
    // 15 ["热销"]
    println!("{stock} {tags:?}");
}
```

\* 是解引用运算符。对整数这种简单值进行赋值时需要显式写 \* ；调用方法和访问字段时，编译器会自动解引用（称为“自动解引用”），所以 tags.push(...) 不用写成(\*tags).push(...) 。

### 2.4.3 【入门】借用的两条铁律

在任意时刻，对于同一份数据，你只能拥有以下两者之一：

1. 任意多个共享引用 &amp;T （只读）；

2. 恰好一个可变引用 &amp;mut T （可读写）。

并且：引用必须始终有效（不能比它指向的数据活得更久）。

口诀：多读，或单写，不可同时。 这和数据库的读写锁、文档的“只读共享 / 独占编辑”是同一个思想。

```rust
fn main() {
    let mut s = String::from("键盘");
 
    let r1 = &s;
 
    // 正确：多个只读引用可以共存
    let r2 = &s;
    println!("{r1} {r2}");
 
    // 正确：r1、r2 在上一行后不再使用，借用已结束（见 2.4.4 NLL）
    let w = &mut s;
    w.push_str("青轴");
    println!("{w}");
    let r3 = &s;
 
    // 错误 E0502：cannot borrow `s` as mutable because it is also borrowed as immutable
    let w2 = &mut s;
 
    // ← 因为 r3 在这里还要用
    println!("{r3}");
    w2.push('!');
}
```

为什么要这样限制？ 想象一个场景：你拿着一个指向 Vec 第一个元素的引用，同时另一段代码往 Vec里 push 了一个元素，触发扩容（1.4.3 节），整个数组被搬到新地址，旧内存被释放——你手里的引用就指向了已释放的内存。这在 C++ 中叫“迭代器失效”，是经典 bug。Rust 的规则在编译期就禁止了这种情况：

```rust
fn main() {
    let mut v = vec![1, 2, 3];
 
    // 只读借用 v
    let first = &v[0];
 
    // 错误 E0502：push 需要可变借用 v，而 first 还在用
    v.push(4);
    println!("{first}");
}
```

同样的规则也在多线程中防止了数据竞争：数据竞争的定义恰好是“两个线程同时访问同一数据，至少一个在写，且没有同步”——“单写”规则让它根本无法出现（第 7 章详解）。

### 2.4.4 【进阶】NLL：借用在“最后一次使用”时结束

早期 Rust 中引用的有效期一直持续到作用域末尾 } ，规则显得很死板。现在的编译器使用 NLL（Non-Lexical Lifetimes，非词法生命周期）：引用的借用期从创建开始，到最后一次被使用时结束。

```rust
fn main() {
    let mut stock = vec![10, 20];
 
    // 借用只存在于这一行内部
    let total: i32 = stock.iter().sum();
 
    // 正确：之前的借用已经结束
    stock.push(total);
 
    let first = &stock[0];
 
    // first 最后一次使用
    println!("首个库存 {first}");
 
    // 正确：first 已不再使用
    stock.clear();
}
```

修复借用错误的头号技巧：调整代码顺序，让只读引用的最后一次使用发生在修改之前。 很多报错只需挪动一两行就能解决。

### 2.4.5 【进阶】悬垂引用：编译器替你兜底

```rust
// 错误 E0106：missing lifetime specifier
fn dangle() -> &String {
    let s = String::from("临时");
 
    // 返回 s 的引用……
    &s
// ……但 s 在这里被释放了，引用将指向无效内存
}
 
// 正确做法：直接返回所有权
fn no_dangle() -> String {
    String::from("临时")
}
```

编译器拒绝编译 dangle ，并在 help 中建议你返回 String 。在 C 语言中，返回局部变量的地址是能编译通过的，运行时才出现诡异的错误。

### 2.4.6 【进阶】自动借用转换：为什么 &amp;String 能传给 &amp;str 参数

```rust
fn greet(name: &str) { println!("你好，{name}"); }
 
fn main() {
    let owned = String::from("Alice");
 
    // &String 自动转换为 &str
    greet(&owned);
    let v = vec![1, 2, 3];
 
    // &Vec<i32> 自动转换为 &[i32]
    let s: &[i32] = &v;
    println!("{s:?}");
}
```

这叫 Deref 强制转换（deref coercion）：String 实现了 Deref&lt;Target = str&gt; ，Vec&lt;T&gt;实现了 Deref&lt;Target = \[T\]&gt; ，编译器在需要时会自动插入转换。所以以 &amp;str 、&amp;\[T\] 为参数的函数能接受更多类型（第 7 章讲智能指针时深入）。

### 2.4.7 【进阶】遍历中的借用：回顾 1.4.3 节

现在可以彻底解释 1.4.3 节的三种遍历：

| 写法 | 迭代方式 | 元素类型 | 遍历结束后 |
| --- | --- | --- | --- |
| for x in &amp;v | v.iter() | &amp;T | v 仍可使用 |
| for x in &amp;mut v | v.iter\_mut() | &amp;mut T | v 仍可使用，元素可能已修改 |
| for x in v | v.into\_iter() | T | 对 Vec 而言 v 被消耗 |

持有元素借用的迭代期间，不能再调用要求冲突可变借用的 push / remove。需要按条件删除可考虑retain；需要根据遍历结果修改集合结构时，可以先收集结果，再结束遍历并修改。

### 2.4.8 【精通】借用检查器的工作方式与局限

借用检查发生在编译期的 MIR（中间表示）阶段，对每个引用计算它“活着”的区域，再检查区域内是否存在冲突的访问。运行时零开销。

它是保守的：对满足安全抽象契约的安全 Rust，检查器会拒绝冲突的借用；某些事实上可行的访问模式也可能无法通过。unsafe 代码及依赖仍有各自的正确性责任。经典例子：

```rust
struct Cart { items: Vec<String>, total: i64 }
fn main() {
    let mut cart = Cart { items: vec![], total: 0 };
    // 同时可变借用结构体的两个不同字段：允许（借用检查器能区分字段）
    let items = &mut cart.items;
    let total = &mut cart.total;
    items.push("键盘".into());
    *total += 19_900;
}
```

但如果通过方法 cart.items\_mut() 和 cart.total\_mut() 分别获取，就会报错——编译器只看函数签名，认为每个方法都借用了整个 cart 。解决方式是直接访问字段，或设计一个同时返回两个引用的方法。

借用检查器的能力会随工具链演进。阅读某个新方案的介绍时，应区分研究目标、实验实现与所用稳定编译器的实际行为，以当前工具链的诊断为准。

内部可变性：有时需要“通过共享引用修改数据”（如缓存、计数器），Rust 提供 Cell 、RefCell、Mutex 、原子类型，把检查推迟到运行时或用同步原语保证安全（第 7 章）。

重借用（reborrow）：把 &amp;mut T 传给函数时，编译器会自动创建一个临时的 &amp;mut \*x ，所以 fn f(x: &amp;mut i32) 调用后，原来的可变引用仍可使用。

## 2.5 生命周期

### 2.5.1 【入门】生命周期是什么

生命周期（lifetime）是引用保持有效的那段代码区域。 每个引用都有生命周期，绝大多数时候编译器能自动推断，你看不到它。只有当编译器无法从函数签名推断“返回的引用借自哪个参数”时，才需要你用标注告诉它。

要特别强调：生命周期标注不会改变任何值实际存活的时间，它只是给编译器的“说明书”，描述多个引用之间的关系，让编译器能检查调用方是否安全。

### 2.5.2 【入门】为什么需要标注：一个例子

```rust
// 返回两个商品名中较长的一个
// 错误 E0106: missing lifetime specifier
fn longer(a: &str, b: &str) -> &str {
    if a.chars().count() >= b.chars().count() { a } else { b }
}
```

编译器的困惑是：返回的引用到底借自 a 还是 b ？这决定了调用方需要让哪个值活得更久。函数体在运行时才决定返回谁，编译器只看签名无法得知，于是要求你写清楚：

```rust
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.chars().count() >= b.chars().count() { a } else { b }
}
```

语法：

&lt;'a&gt; ：在函数名后声明一个生命周期参数，名字以单引号开头，惯例用 'a 、'b 。

&amp;'a str ：带生命周期的引用类型。

这个签名的含义是：返回值的有效期，不超过 a 和 b 中较短的那个。

调用方因此受到约束：

```rust
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.chars().count() >= b.chars().count() { a } else { b }
}

fn main() {
    let name1 = String::from("机械键盘");
    let result;
    {
        let name2 = String::from("鼠标");
        result = longer(&name1, &name2);
 
        // 正确：此时 name1、name2 都有效
        println!("{result}");
 
    // name2 在这里被释放
    }
    // println!("{result}");      // 错误 E0597: `name2` does not live long enough
}
```

即使这次实际返回的是 name1（更长），编译器也会拒绝——因为签名声明了 result 可能借自 name2。编译器依据的是“合同”，而不是某次运行的结果。

### 2.5.3 【入门】生命周期省略规则：为什么大多数时候不用写

编译器按三条省略规则自动补全生命周期，补全成功就不需要手写：

1. 每个引用参数各自获得一个独立的生命周期参数。

2. 如果只有一个输入生命周期，它被赋给所有输出引用。

3. 如果有多个输入生命周期，但其中一个是 &amp;self 或 &amp;mut self （方法），self 的生命周期被赋给所有输出引用。

```rust
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}
// 按规则 1、2 自动变成：fn first_word<'a>(s: &'a str) -> &'a str
 
fn longest_name(names: &[String]) -> Option<&String> {
    names.iter().max_by_key(|name| name.chars().count())
}
// 只有一个引用参数：规则 2 适用，所以 2.4.10 练习 3 不需要标注
 
struct Product { name: String }

impl Product {
    // 规则 3：返回值借自 self
    fn name(&self) -> &str { &self.name }
}
```

只有当三条规则都无法确定输出生命周期时（典型情况：多个引用参数且返回引用、不是方法），才需要手写。

### 2.5.4 【进阶】不同参数可以有不同的生命周期

只有真正相关的参数才需要共享生命周期：

```rust
// 返回值只可能借自 text，与 keyword 无关
fn find_after<'a, 'b>(text: &'a str, keyword: &'b str) -> Option<&'a str> {
    text.find(keyword).map(|i| &text[i + keyword.len()..])
}
 
fn main() {
    let text = String::from("订单号:RM0001");
    let rest;
    {
        let kw = String::from("订单号:");
        rest = find_after(&text, &kw);
 
    // kw 被释放
    }
 
    // 正确：rest 只与 text 相关
    println!("{rest:?}");
}
```

如果把签名写成两个参数都是 'a ，上面的 main 就会编译失败。精确地标注生命周期 = 给调用方最大的自由。实际上这个函数还能简写为 fn find\_after&lt;'a&gt;(text: &amp;'a str, keyword: &amp;str)-&gt;Option&lt;&amp;'a str&gt; ，未标注的 keyword 自动获得独立的生命周期。

### 2.5.5 【进阶】结构体中的引用

结构体字段是引用时，必须标注生命周期，表示“这个结构体实例不能比它借用的数据活得更久”：

```rust
/// 解析后的搜索请求，字段借用原始查询字符串，避免复制
struct SearchQuery<'a> {
    keyword: &'a str,
    category: Option<&'a str>,
}
 
// '_ 表示“由编译器按省略规则推断”
fn parse_query(q: &str) -> SearchQuery<'_> {
    match q.split_once(':') {
        Some((cat, kw)) => SearchQuery { keyword: kw.trim(), category: Some(cat.trim()) },
        None => SearchQuery { keyword: q.trim(), category: None },
    }
}
 
fn main() {
    let raw = String::from("外设: 机械键盘");
    let query = parse_query(&raw);
    println!("{:?} {}", query.category, query.keyword);
    // drop(raw);                     // 若在 query 使用前释放 raw：E0505
// cannot move out of `raw` because it is borrowed
}
```

后端的设计取舍（非常重要）：

带引用的结构体零拷贝、性能好，适合“解析 → 立即使用 → 丢弃”的短生命周期场景，例如解析请求头、解析查询字符串、serde 零拷贝反序列化（第 10 章）。

借用关系可能继续约束上层类型与函数。借自短期局部数据的实例不能直接放进要求 'static 的独立任务；如果实际借用的是 'static 数据，或采用别的有效生命周期设计，则需按具体类型判断。

所以业务实体（商品、订单、用户）和需要长期保存的数据一律使用拥有所有权的字段（String、Vec ）。这是第 1 版教程中“后端结构体一般存 String”那句话的完整原因。

### 2.5.6 【进阶】'static：活得和程序一样久

'static 是一个特殊的生命周期，表示引用在整个程序运行期间都有效。

```text
// 字符串字面量编译进程序的只读数据段，永远有效
let s: &'static str = "RustMall";
 
// const 和 static 中的 &str 默认就是 'static
const API_PREFIX: &str = "/api/v1";
```

'static 在后端开发中最常出现在约束里，而不是引用上：T: 'static 的意思是“类型 T 中不包含任何非 'static 的引用”，也就是 T 要么完全拥有自己的数据，要么只借用永久有效的数据。

```text
// tokio::spawn 的签名（简化）：
// pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
// where F: Future + Send + 'static
```

后台任务可能比创建它的函数活得更久，所以它不能借用函数的局部变量。这就是为什么第 11 章会频繁看到 async move { ... } （把所有权移进任务）和 Arc::clone(&amp;state) （共享所有权）。

常见误解：String 满足 'static 约束吗？满足！T: 'static 不要求值永远存在，只要求它不借用短命的数据。String 拥有自己的数据，所以 String: 'static 成立。

### 2.5.7 【精通】更多生命周期知识

生命周期子类型：'long: 'short 读作“'long 比 'short 活得久”。较长生命周期的引用可以用在需要较短生命周期的地方，反之不行。

'\_ 匿名生命周期：在类型中省略具体名字，例如 impl Iterator&lt;Item = &amp;'\_ str&gt; 、SearchQuery&lt;'\_&gt; ，代码更简洁，含义交给省略规则。2018 Edition 之后推荐在结构体返回值中写出&lt;'\_&gt; ，让读者知道这里有借用（可用 Rust 的 elided\_lifetimes\_in\_paths lint 检查省略）。

高阶生命周期（HRTB） for&lt;'a&gt; Fn(&amp;'a str) -&gt; &amp;'a str ：表示“对任意生命周期都成立”的闭包约束，在编写接受回调的中间件时偶尔会遇到，第 12 章 Tower 部分会看到。

方差（variance）：决定了 &amp;'a T 、&amp;'a mut T 、Cell&lt;&amp;'a T&gt; 中的生命周期能否被缩短，是理解某些复杂报错的钥匙；业务开发中极少直接涉及，推荐阅读《The Rustonomicon》中的 Subtyping and Variance 一节。

自引用结构体：一个结构体字段引用自己另一个字段，在安全 Rust 中无法直接表达，这正是异步Future 需要 Pin 的原因（第 11 章精通部分）。

实用建议：当你发现自己在给业务代码加越来越多的生命周期参数时，通常意味着应该改用所有权（String ）或共享所有权（Arc&lt;str&gt; ），而不是继续和借用检查器较劲。

## 2.6 后端视角：服务代码中的所有权模式

本节把前面的规则落到后端开发的真实场景上。下面这些模式会在第 10〜30 章反复出现，提前建立直觉能让后面的学习顺畅很多。

### 2.6.1 【进阶】一次请求中数据的所有权流转

以第 14 章“创建商品”接口为例，数据的所有权是这样流动的：

1. Axum 提取器把请求体反序列化成 CreateProduct { name: String, ... } ，handler 函数拥有这个值。

2. handler 把它借给校验函数：validate(&amp;input)? ——校验只读，不需要所有权。

3. handler 把它借给仓储层执行 SQL：repo.insert(&amp;input).await? ——SQLx 绑定参数时只需要借用。

4. 数据库返回新行，SQLx 创建一个拥有所有权的 Product 返回给 handler。

5. handler 把 Product 移动进 Json(product) ，再移动给 Axum 序列化成响应。

6. 请求结束，input 在 handler 作用域结束时被释放。

整个过程没有一次不必要的复制：只读的地方借用，交接的地方移动。

### 2.6.2 【进阶】五种常用模式

模式一：入参借用、出参拥有。 服务层函数接收 &amp;str / &amp;T ，返回 String / T 。调用方保留自己的数据，返回值的所有权归调用方。

模式二：构造函数拿走所有权。 Product::new(name: String, ...) 直接把 String 移进结构体，没有额外复制。调用方手上只有 &amp;str 时由调用方 .to\_string() ，开销是显式可见的。

模式三：共享只读状态用 Arc 。 配置、数据库连接池、缓存客户端需要被成千上万个并发请求同时使用，它们不能“属于”某一个请求。解决方式是共享所有权 Arc&lt;T&gt; ：克隆 Arc 通常只增加强引用计数，不克隆内部的 T，具体耗时受原子操作和竞争影响，最后一个持有者释放时数据才被销毁（第 7 章原理、第 12 章 Axum State 实战）。

模式四：跨任务传递用 move。 把数据交给后台任务（发送事件、异步写日志）时，用 move 把捕获值转交给任务，并分别检查 'static 与 Send 约束；如果捕获的是短期引用，move 不会自动把它变成拥有型数据。

模式五：短生命周期解析用借用。 解析请求头、拆分查询参数等“解析完立刻用完”的操作，返回&amp;str 切片而不分配新字符串，热点路径上的性能收益明显。2.7 节的项目代码就是这种模式。

### 2.6.3 【进阶】借用报错的修复套路（按优先级排序）

遇到所有权或借用报错时，按下面的顺序尝试，绝大多数问题在前三步就能解决：

| 顺序 | 办法 | 适用情况 | 代价 |
| --- | --- | --- | --- |
| 1 | 读完整诊断与 help | 先确定谁拥有数据、谁<br>仍在使用借用 | 无运行成本 |
| 2 | 只读参数改成 &amp;T / &amp;str /<br>&amp;\[T\] | 函数不需要保存或消耗<br>输入 | 通常无数据复制 |
| 3 | 调整语句顺序 | 引用最后使用发生在修<br>改或移动之后 | 通常无额外运行成本 |

| 顺序 | 办法 | 适用情况 | 代价 |
| --- | --- | --- | --- |
| 4 | 提前取出需要的 Copy 值或<br>计算结果 | 之后只需一个数值、布<br>尔值等 | 取决于具体计算 |
| 5 | 缩小借用作用域 | 借用只需覆盖一小段操<br>作 | 通常无额外运行成本 |
| 6 | 有理由地 clone | 确实需要独立的数据副<br>本 | 由 Clone 的具体实现决定 |
| 7 | 改为拥有型字段或 Arc | 跨对象或跨任务保存数<br>据 | 需要评估分配与引用计数 |
| 8 | 重新设计数据结构 | 数据流和共享关系过于<br>复杂 | 依具体方案而定 |

### 2.6.4 【精通】识别“与借用检查器打架”的信号

函数签名里出现了三个以上的生命周期参数。

为了满足借用规则，到处出现 .clone() 且克隆的是大集合。

想在结构体里保存对另一个结构体的引用（“对象图”思维，来自 Java/C# 的习惯）。

想要两个对象互相引用（父子双向指针）。

这些信号说明需要换一种建模方式：用 ID 代替引用（订单里存 product\_id: i64 而不是&amp;Product，这 本来也是数据库的建模方式）；用所有权树代替对象图；需要共享时用 Arc ；需要循环结构时用 Weak

（第 7 章）。Rust 的所有权规则倾向于推动你写出数据流向清晰的设计，这在大型后端项目中恰恰是优 点。

### 2.7.3 第 1 步：新建 search.rs

文件：rustmall/common/src/search.rs （新建）

````rust
//! 商品搜索词解析。
//!
//! 分类和关键词借用解析输入；Vec 与 HashSet 仍需要存储空间，
//! 规范化步骤还可能创建拥有型字符串。
//! 适合“解析后立即用于构造查询”的短生命周期场景。

use std::borrow::Cow;
use std::collections::HashSet;

/// 一次搜索最多使用的关键词数量。
pub const MAX_KEYWORDS: usize = 5;

/// 解析后的搜索请求。
///
/// 生命周期 `'a` 表示：本结构体借用的字符串来自同一个输入，
/// 结构体实例不能比该输入活得更久。
#[derive(Debug, PartialEq, Eq)]
pub struct ParsedQuery<'a> {
    /// 分类前缀，例如 `外设`
    pub category: Option<&'a str>,
    /// 去重后的关键词，按出现顺序
    pub keywords: Vec<&'a str>,
}

/// 规范化搜索词：去除首尾空白并转为小写。
///
/// 无需大小写转换时直接借用输入（`Cow::Borrowed`，零分配）；
/// 需要大小写转换时才分配新字符串（`Cow::Owned`）。
pub fn normalize_query(input: &str) -> Cow<'_, str> {
    let trimmed = input.trim();
    if trimmed
        .chars()
        .any(|c| c.to_lowercase().ne(std::iter::once(c)))
    {
        Cow::Owned(trimmed.to_lowercase())
    } else {
        Cow::Borrowed(trimmed)
    }
}

/// 拆分分类前缀，支持半角 `:` 与全角 `：`。
///
/// 返回 `(分类, 其余部分)`，两者都借用自 `query`。
pub fn split_category(query: &str) -> (Option<&str>, &str) {
    let is_sep = |c: char| c == ':' || c == '：';
    match query.find(is_sep) {
        Some(index) => {
            let (category, rest) = query.split_at(index);
            // 分隔符可能是 1 字节（:）或 3 字节（：），按实际字符长度跳过
            let sep_len = rest.chars().next().map_or(0, char::len_utf8);
            let category = category.trim();
            let keywords = rest[sep_len..].trim();
            ((!category.is_empty()).then_some(category), keywords)
        }
        None => (None, query.trim()),
    }
}

/// 按空白与中英文逗号切分关键词，保序去重，最多保留 [`MAX_KEYWORDS`] 个。
pub fn split_keywords(text: &str) -> Vec<&str> {
    let mut seen = HashSet::new();
    text.split(|c: char| c.is_whitespace() || c == ',' || c == '，')
        .filter(|word| !word.is_empty())
        .filter(|word| seen.insert(*word))
        .take(MAX_KEYWORDS)
        .collect()
}

/// 返回字符数最多的关键词；并列时返回最后一个。
///
/// 注意签名中的 `'a`：返回值借自**原始文本**，而不是借自切片 `keywords` 本身，
/// 因此即使关键词列表被释放，返回值依然有效。
pub fn longest_keyword<'a>(keywords: &[&'a str]) -> Option<&'a str> {
    keywords.iter().copied().max_by_key(|k| k.chars().count())
}

/// 完整解析一个搜索请求。
///
/// ```
/// use common::search::parse;
/// let p = parse("外设: 机械键盘 青轴");
/// assert_eq!(p.category, Some("外设"));
/// assert_eq!(p.keywords, vec!["机械键盘", "青轴"]);
/// ```
pub fn parse(query: &str) -> ParsedQuery<'_> {
    let (category, rest) = split_category(query);
    ParsedQuery {
        category,
        keywords: split_keywords(rest),
    }
}

#[cfg(test)]

            // keywords 在这里被释放，但 best 借自 text，仍然有效
        }
        assert_eq!(best, Some("机械键盘"));
    }
    #[test]
    fn parse_after_normalize() {
        let raw = String::from("  外设: RGB 键盘 ");

        // Cow：可能借用 raw，也可能拥有新字符串
        let normalized = normalize_query(&raw);

        // parsed 借用 normalized
        let parsed = parse(&normalized);
        assert_eq!(parsed.category, Some("外设"));
        assert_eq!(parsed.keywords, vec!["rgb", "键盘"]);
    }
}
````

### 2.7.4 代码精讲

normalize\_query 与 Cow：Cow&lt;'\_, str&gt; （Clone-on-Write，写时克隆）是一个枚举，要么是 Borrowed(&amp;str) ，要么是 Owned(String) 。它解决“多数情况不用修改、少数情况需要修改”的问题：对无需大小写转换的输入，函数直接借用裁剪后的字符串；检测逐字符比较小写映射，也覆盖需要转换的标题形式字母。Cow 实现了 Deref，可以像&amp;str 一样使用，测试 parse\_after\_normalize 中 parse(&amp;normalized) 就是自动转换成 &amp;str 的结果（2.4.6 节）。

split\_category 的 UTF-8 细节：全角冒号 ： 在 UTF-8 中占 3 字节。find 返回的是字节下标，所以跳过分隔符时不能写死 + 1 ，否则会切在字符中间导致 panic（1.4.5 节）。代码用 char::len\_utf8 取得分隔符的真实字节长度，这是处理中文输入的必备细节。(!category.is\_empty()).then\_some(category)是 if 非空 { Some(category) } else {None }的简洁写法。

split\_keywords 的借用链：split 返回的每一项都是借自 text 的 &amp;str ；HashSet&lt;&amp;str&gt; 中存的也是借用；最终 Vec&lt;&amp;str&gt; 中的每个元素都指回原始字符串。整个函数除了 Vec 和 HashSet 本身外没有分配任何字符串。返回值的生命周期按省略规则 2（只有一个输入引用）自动与 text 绑定。

longest\_keyword 为什么要手写 'a ：参数 &amp;\[&amp;str\] 中其实有两层引用——对切片本身的引用，以及切片里每个字符串的引用。按省略规则 1，它们会各自获得一个生命周期，于是输入有两个生命周期，规则 2 不再适用，编译器无法判断返回值借自哪一层，直接报 E0106（missing lifetime specifier）。我们手写的签名 fn longest\_keyword&lt;'a&gt;(keywords: &amp;\[&amp;'a str\]) -&gt; Option&lt;&amp;'a str&gt; 精确地说明“返回值借自切片里的字符串（即原始文本），与切片本身无关”。正因如此，测试 longest\_keyword\_outlives\_the\_list 中 keywords 被释放后 best 依然有效。如果改成粗糙的写法 fn longest\_keyword&lt;'a&gt;(keywords: &amp;'a \[&amp;'a str\]) -&gt; Option&lt;&amp;'a str&gt; ，函数本身能编译，但返回值被绑到了切片的生命周期上，这个测试就会报 E0597（keywords does not live long enough）。这正是 2.5.4 节“精确标注 = 给调用方最大的自由”的实际例子。

ParsedQuery&lt;'a&gt; ：按 2.5.5 节的取舍，它只用于“解析后立即构造 SQL”，不会被长期保存，所以使用借用是合适的。第 14 章需要把查询条件传给异步数据库调用时，我们会看到它仍然可用，因为整个请求处理都在同一个 async fn 内完成，没有被 spawn 到别的任务。

### 2.7.8 常见问题排查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| HashSet 元素类型无法推断 | 缺少足够的类型约束 | 按实际用途标注，如 HashSet::&lt;&amp;str&gt;::new() |

### 2.7.9 本章小结

栈和堆是理解运行时存储的概念工具，具体位置还受拥有者、分配方式与优化影响。所有权和借用检查预防多类内存错误，但不保证没有泄漏，也不保证服务没有延迟尖峰。

所有权三规则：每个值有一个所有者；同一时刻只有一个所有者；所有者离开作用域时值被释放。赋值、传参、返回都会移动非 Copy 类型；需要两份数据时显式 clone 。

Drop 与 RAII 统一管理内存、连接、锁、事务等所有资源；未提交事务依驱动机制安排回滚；需要确认结果时采用显式事务操作。

借用规则：多个只读引用，或一个可变引用，不能同时存在；引用不能比数据活得久。NLL 让借用在最后一次使用时结束，调整代码顺序是修复借用错误的头号技巧。

生命周期标注只描述引用之间的关系，不改变值的存活时间；省略规则覆盖了绝大多数情况；T:'static 表示不含短命借用，是 tokio::spawn 的要求。

后端建模：业务实体使用拥有所有权的字段；共享状态使用 Arc ；短生命周期解析使用借用和 Cow；用 ID 代替对象之间的引用。

下一章讲结构体、枚举与模式匹配：我们将正式定义 RustMall 的领域模型——商品、订单、订单状态机，并把第 1、2 章写的函数组织成方法。

# 第 41 章 PostgreSQL 深入：执行计划、快照、锁与可验证恢复

第40章已经把同一个RustMall装进容器，并用迁移、权限和探针约束启动过程。现在假设系统没有报错，订单领取却逐渐消耗更多数据库资源：表上明明有索引，为什么worker仍反复读大量行？又假设备份文件已经生成，我们能否证明恢复后的约束、序列和迁移记录仍在？

本章继续使用现有商品库、订单库和SQLx代码。先区分连接等待、执行与锁等待，再沿真实领取SQL观察计划；随后用两个事务实验理解快照、死锁与序列化失败，最后将订单库恢复到全新验证库。库存、付款、订单幂等与租约的正确性约束都保留，性能改进不以取消这些保护为代价。

学完后，应能读出计划树的工作量，解释三个时间函数的差别，判断错误发生在连接池还是数据库，演示SKIP LOCKED的边界，并按数据、约束、序列和应用身份分别检查恢复结果。

## 41.1 先定位时间花在哪里

### 41.1.1 【入门】一次数据库调用包含多段等待

请求进入服务后可能先等HTTP名额，再等连接池；取得连接后才发送SQL，服务器还可能等锁、读取页面、排序和返回结果。应用层的一次耗时计量不一定等于数据库执行时间。

因此看到接口慢，先问“是哪段变慢”。连接池已经排队时，增加索引可能有帮助，也可能完全没有触及当前瓶颈；同一商品行竞争严重时，增加连接数通常只会允许更多请求同时等待同一把锁。

### 41.1.2 【入门】本章文件与运行边界
```text
services/commerce/src/sql/claim_order.sql
services/commerce/tests/postgres_concurrency.rs
scripts/check-postgres.py
scripts/pg-archive.py
ops/postgres41/diagnostics.sql
```

领取SQL是运行中的worker真正使用的语句，实验直接读取它，避免另写一条“看起来相同”的查询进行优化。其余新增程序只面向受控实验和运维，不增加公开管理接口。

### 41.1.3 【进阶】先在独立数据集复现

在本检查点根目录构建镜像，再选择一个不存在的报告目录：
```sh
docker build --build-arg RUST_IMAGE=public.ecr.aws/docker/library/rust:1.92.0-bookworm \
  --tag rustmall/book:ch41-candidate .

python3 scripts/check-postgres.py \
  --image rustmall/book:ch41-candidate \
  --report-dir /tmp/rustmall-postgres41-report
```

脚本创建随机命名的PostgreSQL容器与私有网络，不发布数据库端口。它使用实际镜像中的catalog-migrate与订单迁移程序，因此包含真正的表、索引、约束和SQLx迁移账，不是另造一套简化结构。

实验以管理员批量生成合成数据。它不会把这些直接SQL插入当作真实HTTP下单，也不会将缺少付款与库存参与者的实验订单放入正式系统。容器和网络在结束时清理；报告和合成数据的归档保存在指定目录。

### 41.1.4 【精通】实验测量与生产容量分开

本章选择二十万条未来重试订单，是为了清楚展示一个查询形状的差别。某次运行的毫秒数受机器、缓存和并发影响，不是生产延迟承诺。比耗时更稳定的证据包括：是否形成Index Cond、扫描或过滤多少行、访问多少共享缓冲块，以及修改前后业务结果是否一致。

## 41.2 从计划树看见工作量

### 41.2.1 【入门】先分清估算与实测
```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT id,name,price_cents,stock
FROM products
WHERE delisted_at IS NULL
ORDER BY created_at DESC,id DESC
LIMIT 20;
```

EXPLAIN选择的计划由一组父子节点组成。最底层负责读取行，向上可能经过过滤、排序、聚合和LIMIT。估算成本不是毫秒；Actual Rows和实际时间才来自本次ANALYZE执行。

ANALYZE在这里是EXPLAIN选项，与单独更新统计信息的ANALYZE命令需要结合上下文区分。前者实际执行被分析语句，包括写语句；后者为计划器采样表内容。

### 41.2.2 【进阶】从底向上读，而不是只看第一行

| 观察项 | 先问的问题 | 容易误读的地方 |
| --- | --- | --- |
| Plan Rows与Actual Rows | 估算与实际是否差很多 | 估算不是保证 |
| Actual Loops | 同一节点执行了多少次 | 行数和时间可能是每循环平均值 |
| Index Cond | 哪些条件真的缩小索引范围 | Filter不一定减少已读取的索引项 |
| Rows Removed by Filter | 读到后又丢掉多少行 | 返回0行不代表没有工作 |
| Sort | 输入规模、方法和是否写临时块 | LIMIT不保证无需处理大量输入 |
| Buffers | 访问命中块还是读取块 | 各层可能包含子节点，不能随意累加 |

Seq Scan并不自动等于错误。小表、需要返回大部分行的查询，顺序读取可能更合理。也不能为了让实验出现Index Scan，先关闭enable_seqscan再宣布生产优化成功。

### 41.2.3 【精通】EXPLAIN ANALYZE写语句不能随手在生产运行

本章对领取UPDATE做实测，是因为实验库中的订单全部尚未到期，结果应为0行，并且库本身可丢弃。即便把写语句包在事务里最后ROLLBACK，也不能据此断言毫无影响：它仍会取锁、执行部分计算或触发器，某些外部副作用也不随数据库回滚。

实验脚本检查没有新增lease_token，保留完整JSON计划。读者应先理解数据前提，再使用ANALYZE选项。参阅[PostgreSQL 17执行计划说明](https://www.postgresql.org/docs/17/using-explain.html)。

### 41.2.4 【进阶】把实际计划还原为工作过程

领取查询的形状可以读成下面这棵简化树，具体节点名称以JSON报告为准：
```text
更新订单并返回收据字段
  CTE picked
    Limit 1
      LockRows
        按next_attempt、id读取候选
          索引范围或逐行Filter
  用picked.id定位并更新被领取订单
```

先在最底层确定候选，再尝试行锁，最后只让一条进入picked。上层返回空集合时，要沿树往下看它为什么为空：确实没有范围内的行、行被状态过滤，还是候选被别的事务锁住。三者的业务与性能含义不同。

含loops的节点还要先区分单次与合计。例如某内层扫描平均返回5行、循环1000次，不能把它当成整个查询只处理5行。反过来，父节点总时间通常已经包含子节点工作，也不能把每一层时间简单相加后报告一个虚高总耗时。

### 41.2.5 【精通】共享命中块也不是零成本

命中共享缓冲意味着所需块已在PostgreSQL缓冲中，不等于没有查找、锁存、可见性检查和CPU处理。即使没有真实磁盘读取，反复命中几千个块的轮询，也可能在大量worker同时运行时积累开销。

同一块被重复访问时，缓冲计数并不必然等于唯一物理页面数。本章用顶层节点记录整体命中与读取，避免把父子节点的累计值重复计入。操作系统缓存又是另一层，不能把Shared Read Blocks直接解释成每次都发生了机械磁盘I/O。

## 41.3 真实问题：未来订单为什么也要扫描

### 41.3.1 【入门】已有索引，但筛选条件仍然重要

订单迁移中已有下面的部分索引：
```sql
CREATE INDEX orders_work ON orders(next_attempt,id)
WHERE state NOT IN ('completed','cancelled','manual');
```

索引排除了终态，剩余条目按next_attempt和id排序。它服务于“挑选最早已到重试时间的非终态订单”。索引存在只是条件之一，查询还必须给出可以用于定位范围的表达式。

旧查询用next_attempt&lt;=clock_timestamp()。这个函数在同一语句执行过程中也可能变化，数据库不能把它简单当作固定的索引边界。结果可能是沿索引读取，再逐行检查是否到期；全部订单都在未来时，即使最终返回0行，也可能过滤二十万行。

### 41.3.2 【进阶】三个时间函数回答不同问题

| 函数 | 在本章中的含义 | 适合的职责 |
| --- | --- | --- |
| transaction_timestamp()，也称now() | 当前事务开始的时间 | 同一事务内统一的业务时间基准 |
| statement_timestamp() | 当前语句开始的时间 | 本次领取尝试的一致筛选边界 |
| clock_timestamp() | 调用时的实际时钟 | 真正发放租约以及检查是否过期 |

不能为了可索引就把所有clock_timestamp都换成now。一个很早开始、后来才运行领取语句的事务，如果继续使用旧事务时间，可能漏掉在此期间已经到期的订单。

参阅[PostgreSQL时间函数](https://www.postgresql.org/docs/17/functions-datetime.html)。这里的时间来自数据库服务器；它们也不是跨机器的单调时钟证明，时钟假设还会在分布式原理章节继续讨论。

### 41.3.3 【进阶】完整的新领取SQL
```sql
WITH picked AS (
    SELECT id FROM orders
    WHERE state NOT IN ('completed','cancelled','manual')
      AND next_attempt <= statement_timestamp()
      AND (leased_until IS NULL OR leased_until <= statement_timestamp())
    ORDER BY next_attempt,id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE orders AS o
SET lease_token=$1,
    leased_until=clock_timestamp()+interval '15 seconds',
    attempts=LEAST(o.attempts::bigint+1,1000000)::integer
FROM picked AS p WHERE o.id=p.id
RETURNING o.id,o.actor_id,o.request_key,o.product_id,o.quantity,
          o.unit_price,o.amount,o.state,o.attempts
```

两个筛选条件使用同一个语句时刻。租约真正写入时仍以clock_timestamp加15秒；完成或延后步骤的条件写仍检查当前真实时间，不能让旧worker因一个过早固定的时刻继续写入已经过期的租约。

Rust入口也要同步修改，不能只新增一个没有被调用的SQL文件：
```rust
/// Exact production statement, also used for EXPLAIN in the isolated chapter41 lab.
pub const CLAIM_SQL: &str = include_str!("sql/claim_order.sql");

pub async fn claim(pool: &PgPool) -> anyhow::Result<Option<(Order, Uuid)>> {
    let token = Uuid::new_v4();
    let row = sqlx::query_as::<_, Order>(CLAIM_SQL)
        .bind(token)
        .fetch_optional(pool)
        .await?;
    if let Some(row) = &row {
        anyhow::ensure!(row.valid(), "invalid stored order");
    }
    Ok(row.map(|row| (row, token)))
}
```

在语句执行期间才到期的订单，可以留到下一轮尝试。这个保守边界不会提前抢占未过期租约。SKIP LOCKED和原有token、旧步骤、有效期条件都没有移除，attempts也继续饱和增长。

### 41.3.4 【精通】实测要同时核对性能形状和业务结果

本章实验对同一份生产语句生成旧函数版本与新函数版本，使用相同二十万条未来订单、相同参数和相同索引。没有关闭顺序扫描，也没有为了结果另建只对实验有利的索引。

已观察到旧版本过滤二十万行、新版本出现next_attempt的索引范围条件并过滤0行。本轮完整通过记录的共享命中块为4625与3；36.298毫秒与0.089毫秒只是该次环境中的观察。最终完整报告以脚本输出为准，不把这组比值推广到所有负载。

这个改动不需要新增表或迁移版本，因为改变的是语句使用现有索引的方式。正确性仍由完整工作区测试和真实订单链路核对，不能只凭一张更快的计划判断可以上线。

## 41.4 商品分页、联合索引与覆盖索引

### 41.4.1 【入门】排序必须有明确的并列顺序

商品列表按created_at DESC,id DESC排序。多条商品可能具有相同时间戳，id为它们提供确定的并列次序。只按时间排序，不能假定每次分页都以相同方式安排同一秒的商品。

现有products_listed_created_idx按相同方向保存这两列，并只索引未下架商品。本章不添加一个内容相同的新索引；重复索引会增加写入与维护成本。

### 41.4.2 【进阶】B-tree定位范围后仍可能回表

可以把B-tree理解为用有序键组织的多层入口：内部节点帮助定位范围，叶子层记录键与对应行位置。找到索引项以后，普通Index Scan通常还要取得表中的行，并判断当前事务能否看见它。

索引顺序与表物理位置不必一致。如果匹配大量且分散的行，逐项访问堆的成本可能很高。Bitmap路径会先组织匹配位置，再按页面访问；它与直接沿索引顺序输出有不同代价，也未必保留所需排序。

联合索引的列顺序由访问方式决定。商品列表先按created_at范围与顺序读取，再由id处理并列；订单领取先限定next_attempt范围，再按id确定顺序。把所有字段拼进一个大索引，既不保证每个查询都能有效使用，也会增加写入、空间和维护成本。

### 41.4.3 【进阶】深OFFSET仍要跳过前面的行
```sql
SELECT id,name,price_cents,stock FROM products
WHERE delisted_at IS NULL
ORDER BY created_at DESC,id DESC
LIMIT 20 OFFSET 100000;
```

返回20条不代表只访问20条。实验计划中的索引读取节点输出100020条，再由上层LIMIT跳过前100000条。索引可以避免额外排序，却不使OFFSET的跳过成本消失。

### 41.4.4 【进阶】游标条件先确定上一页边界
```sql
SELECT id,name,price_cents,stock FROM products
WHERE delisted_at IS NULL
  AND (created_at,id)<($1,$2)
ORDER BY created_at DESC,id DESC
LIMIT 20;
```

参数代表上一页最后一条的时间与id。实验有意生成重复时间戳，并验证游标页与同一数据快照下的OFFSET页返回完全相同的20个ID。游标条件让计划从边界继续，本次测量只读取20条。

公共HTTP/gRPC契约目前仍保留原OFFSET分页。本章演示的是替代SQL设计，不能把实验偷换成已经修改了接口。真正切换还需定义游标编码、过滤条件、非法参数、兼容性和并发插删时的语义。

### 41.4.5 【精通】INCLUDE与index-only scan不是同一个承诺

第32章已有按product_id索引的held部分索引，并INCLUDE(quantity)，用于库存调整期间统计同商品尚持有的数量。按updated_at,saga_id的另一个held索引有不同用途，不能因为二者都有held谓词就当作相同索引。

INCLUDE把需要的值保存在索引中，不保证永远不访问堆。可见性判断、页面是否all-visible以及最近更新都会影响Heap Fetches。本章在独立实验中VACUUM后观察计划；不要把这个安静环境的行为当作持续写入环境中的保证。

部分索引还要求查询条件能表达对应谓词。使用过度泛化的参数化状态条件时，要检查通用计划能否证明谓词，而不是只看索引定义。[部分索引说明](https://www.postgresql.org/docs/17/indexes-partial.html)提供了判断背景。

### 41.4.6 【精通】索引类型围绕访问操作选择

| 类型 | 典型访问形状 | 放回本项目时先确认 |
| --- | --- | --- |
| B-tree | 等值、范围、有序读取 | 当前商品列表、订单领取是否与键顺序匹配 |
| Hash | 等值比较 | 是否真的优于已有B-tree，而非因名字更像哈希表就替换 |
| GIN | 一行中包含多个可搜索项 | 是否确有JSONB包含、数组或全文检索查询 |
| GiST | 依赖操作类的空间、范围等检索 | 业务是否需要对应运算，而不只是普通排序 |
| SP-GiST | 适合操作类的空间分割检索 | 数据与分割策略是否匹配，而非替代所有B-tree |
| BRIN | 物理块范围与键值有相关性的大表 | 审计时间与物理写入顺序是否相关、重检成本如何 |

本章没有为product_outbox.payload自动添加GIN：relay读取的是待投递状态与时间，不是任意JSON键搜索。也没有给小型核心表套BRIN来追求“更多类型”。是否增加索引，应由实际查询、数据分布、写入代价和维护约束共同判断。参阅[索引类型](https://www.postgresql.org/docs/17/indexes-types.html)。

## 41.5 MVCC：同一事务究竟看见什么

### 41.5.1 【入门】行版本让读写不必完全互斥

更新并不要求立刻抹掉所有读者可能使用的旧版本。普通读取按快照判断可见性，因此可以与很多写操作并存。这不意味着没有锁、没有清理工作，也不意味着读者总会看到最新提交。

先用两个终端理解实验：A开始事务并读取订单数量；B插入订单并提交；A再读一次。A第二次能否看见新订单，要看隔离级别与快照，而不是看两次SQL字符串是否相同。

### 41.5.2 【进阶】Read Committed与Repeatable Read的差别

新增测试先让Repeatable Read只读事务读到1条订单，再由另一个连接插入，第二次仍读到1条。退出后以Read Committed开始，第一次读到2条，另一个连接再插入，第二次读到3条。

现有Catalog列表与total本来就在同一个Repeatable Read只读事务中查询，避免二者因语句级快照不同而互相矛盾。这种一致性只覆盖该次事务，不冻结后续HTTP分页之间的整个数据集。

### 41.5.3 【精通】长快照有维护成本

一个持续很久的事务可能仍需要旧版本，影响它们何时可以回收。只读事务也不必然“没有运行影响”。交互式终端执行BEGIN后离开、应用拿着连接等待外部HTTP，都是需要识别的情况。

应观察xact_start、backend_xmin、状态和等待原因，再判断需要如何结束责任。不要仅因存在旧事务就随意终止进程；先确定是谁、在保护什么数据以及取消后的业务结果如何恢复。

参阅[事务隔离说明](https://www.postgresql.org/docs/17/transaction-iso.html)。

## 41.6 锁、队列领取与错误码

### 41.6.1 【入门】锁保护的是具体不变量

库存事务先锁商品行，再进行预留或调整。这个顺序使影响同商品可售量与释放空间的写入在明确位置串行化。只写“这里加事务”无法解释哪两个并发操作会互相等待，也不能证明不会发生取锁环。

订单领取则让不同worker跳过已被别的事务锁住的候选，领取其他可用订单。它追求队列工作分配，不是用SKIP LOCKED替代普通查询所需的一致性语义。

### 41.6.2 【进阶】真实worker测试如何验证跳过锁定头部

测试创建两条同样到期的订单，在一个独立事务里锁住排序靠前的一条，再调用真正的orders::claim。预期它领取第二条；两条分别处于“被行锁占用”和“已有新鲜租约”时，再次领取应为空。

释放第一条的行锁后，下一次调用才领取它。两次token必须不同，两个订单attempts均为1。这个测试既覆盖SKIP LOCKED，也防止优化后绕过新鲜租约。

### 41.6.3 【进阶】四类数据库错误与连接池等待

| 现象 | 常见标识 | 本章实验验证的含义 |
| --- | --- | --- |
| 行锁超过lock_timeout | 55P03 | 此次锁等待未成功 |
| 语句超过statement_timeout | 57014 | 本次服务器语句被取消 |
| 可序列化事务冲突 | 40001 | 需要重新评估完整事务尝试 |
| 死锁受害事务 | 40P01 | 数据库打破等待环，不能只续发最后一条 |
| 连接池没有空位 | SQLx PoolTimedOut | 尚未取得连接，不是服务器SQLSTATE |
| 已失败事务继续执行 | 25P02 | 应先结束失败事务，而不是假装还能正常提交 |

错误码仍要结合调用阶段判断。尤其提交响应丢失与跨服务超时，不能凭“本地收到了错误”认定远端没有效果。原订单与付款身份继续承担查询、去重和恢复职责。

### 41.6.4 【精通】死锁要用取锁顺序解释

A锁订单1，B锁订单2；A再等订单2，B再等订单1，就形成等待环。测试先确保前两把锁已取得，再并发请求反向的两把锁，确认恰有一个40P01受害者。

避免死锁的方向是统一取锁顺序、缩短事务和减少不必要的锁。若业务允许重试，应从事务的读取与决策重新开始，并受预算与幂等约束；在已中止事务里重发一条UPDATE没有修复整个决策过程。

### 41.6.5 【精通】Serializable也需要调用方参与

教学测试使用两名值班人员，要求至少一人值班。两个事务都读到两人在岗，再各自下班，会产生写偏斜。以Serializable执行时，实验要求只有一个事务提交，另一个得到40001，最终仍有一人值班。

这是独立的隔离级别小实验，不是为订单系统新增“值班表”业务。它说明更高隔离级别会把某些冲突变成必须处理的失败，不会免除应用理解事务边界的责任。

### 41.7.2 【精通】SET LOCAL与连接复用

连接池会复用会话。修改会话级设置后忘记恢复，可能让下一位借用者意外继承超时或其他选项。本章测试在一个单连接池中记录原设置，在事务内SET LOCAL，再结束事务并核对同一会话恢复原值。

这个实验不意味着所有需要的设置都改成LOCAL：应用池初始化的默认statement_timeout仍是有意的会话策略。要分清稳定默认值与单次事务覆盖。

### 41.7.3 【精通】连接预算按进程和发布过程计算

如果每个users实例最多10连接，两副本平时最多20；滚动发布额外一个实例时可能达到30。系统还要计入商品、订单API、worker、支付、relay、投影、迁移与运维。

不要把服务器max_connections全部分配给业务池，也不要把最大连接数当作可同时高效执行的查询数。连接代理能改变连接管理方式，但事务池模式、会话设置与预处理语句的兼容性要单独验证，不能只加一个代理地址就视为解决容量问题。

## 41.8 统计信息与持续维护

### 41.8.1 【入门】计划器需要数据分布信息

ANALYZE帮助计划器估计选择性和数据规模；表增长、分布偏斜、状态比例变化，都可能改变原本合适的计划。实验在生成大量数据后更新统计信息，并保留计划JSON，避免拿空表计划解释大表行为。

### 41.8.2 【进阶】估算偏差需要追问分布与相关性

一张订单表可能大多数已经完成，剩余非终态里又大多数处于未来重试时间。单列分布与列之间的关系都会影响估算。不能只拿总行数乘一个固定比例，期待任意状态和时间组合都准确。

先比较估算与实际的节点，再确认统计是否新鲜、参数是否有明显偏斜、多个筛选条件是否相关。扩展统计信息能帮助特定组合的估算，但不是任何范围条件或任意跨表查询的万能修复。不要在没有对应查询证据时批量创建统计对象。

本次领取改进不是靠把估算参数“调到喜欢的答案”，而是让真正的筛选边界能够进入索引条件；现有索引和ANALYZE仍然保留。参阅[计划器统计信息](https://www.postgresql.org/docs/17/planner-stats.html)。

### 41.8.3 【进阶】VACUUM不是只有磁盘满才执行

旧版本清理、可见性信息和事务ID维护都需要持续关注。n_dead_tup等统计是估算，不能当作每一时刻精确的垃圾行数量。普通VACUUM与VACUUM FULL也不能互换；后者重写表并要求更强的锁，可能造成明显停顿。

不应先关闭autovacuum追求短时跑分，再把后续膨胀算成数据库突然变慢。应结合写入、长事务、维护进度、I/O和容量观察。[日常维护说明](https://www.postgresql.org/docs/17/routine-vacuuming.html)解释了这些工作的不同职责。

### 41.8.4 【精通】创建索引也属于发布过程

在有流量的大表上增加索引，要考虑构建锁、资源、失败后的残留与旧新程序共存。CREATE INDEX CONCURRENTLY有自己的限制，不能简单塞进任何事务化迁移后期待它正常运行。

本章没有为领取优化增加新索引，更没有把刚讨论的运维DDL偷偷放进应用启动流程。需要新增时应设计单独可观察、可重试和可核对的操作，参阅[CREATE INDEX说明](https://www.postgresql.org/docs/17/sql-createindex.html)。

### 41.8.5 【精通】分区和分片要解决不同问题

分区将一张逻辑表的数据按规则分到多个物理分区，常见动机是保留周期和分区裁剪。它不是把每个分区都变成独立数据库服务器。本项目的审计和事件历史若持续增长，可以围绕保留策略讨论分区；需要按全局命令身份去重的收据表，则还要仔细处理唯一性与保留责任。

例如把orders按created_at分区，不能假定原PRIMARY KEY(id)和UNIQUE(actor_id,request_key)仍能原样提供跨分区唯一性。分区表的唯一约束受分区键限制；简单把created_at追加进请求键约束，又可能允许同一业务键在不同时间重复出现，从而改变原幂等语义。设计时要同时解决这两个层次，而不是只让DDL通过。

按时间删除旧分区虽然方便，也可能删除仍用于去重或恢复的事实。必须先回答：多久以后重复命令不再需要旧收据？订单是否还可能由人工恢复？Kafka历史是否仍能覆盖重建需求？不能只因为分区删除快，就把业务恢复窗口缩短。

跨数据库分片进一步增加路由、全局唯一性、跨分片查询与迁移问题。当前六库拆分按服务职责进行，不等于订单表已经水平分片。本章没有以“分布式”为由制造不必要的分片实现。[分区文档](https://www.postgresql.org/docs/17/ddl-partitioning.html)说明其机制与约束。

## 41.9 运维诊断从只读查询开始

### 41.9.1 【进阶】完整诊断脚本
```sql
\set ON_ERROR_STOP on
BEGIN READ ONLY;
SET LOCAL statement_timeout='3s';
SELECT current_database(),version(),current_setting('max_connections') AS max_connections;
SELECT state,wait_event_type,wait_event,count(*) AS sessions
FROM pg_stat_activity WHERE datname=current_database()
GROUP BY state,wait_event_type,wait_event ORDER BY sessions DESC;
SELECT pid,application_name,state,wait_event_type,wait_event,
       clock_timestamp()-xact_start AS transaction_age,
       backend_xmin,pg_blocking_pids(pid) AS blockers
FROM pg_stat_activity WHERE datname=current_database() AND pid<>pg_backend_pid()
ORDER BY xact_start NULLS LAST LIMIT 20;
SELECT relname,n_live_tup,n_dead_tup,last_autovacuum,last_autoanalyze,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables ORDER BY pg_total_relation_size(relid) DESC LIMIT 20;
SELECT indexrelname,idx_scan,idx_tup_read,idx_tup_fetch
FROM pg_stat_user_indexes ORDER BY indexrelname;
SELECT to_regclass('public.pg_stat_statements') IS NOT NULL AS has_statements \gset
\if :has_statements
SELECT queryid,calls,round(mean_exec_time::numeric,3) AS mean_ms,
       rows,shared_blks_hit,shared_blks_read,temp_blks_written
FROM pg_stat_statements
WHERE dbid=(SELECT oid FROM pg_database WHERE datname=current_database())
ORDER BY total_exec_time DESC LIMIT 20;
\endif
COMMIT;
```

在受控运维连接中运行它，先确认当前库，再查看会话状态、阻塞者、长事务、表与索引统计。业务账号不因此获得整个实例的监控权限。脚本不输出完整SQL文本与会话秘密；pg_stat_statements存在时才查询对应汇总。

### 41.9.2 【精通】看见等待者还要找到阻塞责任

pg_blocking_pids帮助沿等待关系定位阻塞者。行锁等待不一定在pg_locks中表现成“一行对应一把直观的tuple锁”；应结合事务ID等待、活动状态和应用责任解释。

对长事务的处理要保留因果证据：哪个服务、多久、持有什么锁、为何尚未提交。简单杀掉最慢查询可能释放局部压力，也可能使调用方进入结果未知的恢复流程。诊断与修复不是同一个动作。

## 41.10 备份必须由恢复证明

### 41.10.1 【入门】复制、备份与高可用各解决一部分问题

副本可能很快复制误删除；备份可能保存删除前的状态，但恢复需要时间；高可用切换也不能自动恢复已被错误更新的业务事实。RPO表达允许损失的数据窗口，RTO表达允许中断的时间，要围绕具体业务制定和演练。

### 41.10.2 【进阶】逻辑归档保留的不只是行数

pg_dump自定义格式可以保存对象定义与数据。恢复验证还应核对约束、索引、序列、迁移账和业务金额等事实。只比较count(*)，可能漏掉金额错误或下一次插入就发生序列冲突的问题。

本章工具明确不保存原所有者与ACL，恢复目标是新的验证库。它没有自动恢复全局角色或将应用切到新库；不能直接把第40章固定库名的授权脚本当成恢复验证库的通用切流脚本。

### 41.10.3 【进阶】完整归档工具
```python
"""Logical backups and NEW verification-database restores for the book's PostgreSQL17 lab.

Uses trusted container-local PostgreSQL admin access. Does not switch applications,
restore global roles, or claim cross-database consistency. Python3.11+ and Docker.
"""
import argparse,hashlib,json,os,re,subprocess,tempfile
from pathlib import Path

def digest(path):
    with path.open('rb') as stream:return hashlib.file_digest(stream,'sha256').hexdigest()
def run(container,command,**kwargs):
    result=subprocess.run(['docker','exec','-i',container,*command],stderr=subprocess.PIPE,timeout=900,**kwargs)
    if result.returncode:raise RuntimeError(f'{command[0]} failed with exit {result.returncode}; database response values suppressed')
def validate(container,path):
    # Raw IO keeps the OS descriptor position aligned when handing it to Docker.
    with path.open('rb',buffering=0) as stream:
        if stream.read(5)!=b'PGDMP':raise ValueError('not a custom-format archive')
        stream.seek(0);run(container,['pg_restore','--list'],stdin=stream,stdout=subprocess.DEVNULL)
def main():
    p=argparse.ArgumentParser(description=__doc__)
    p.add_argument('operation',choices=['backup','restore']);p.add_argument('--container',required=True)
    p.add_argument('--database',choices=['rustmall_'+x for x in ['catalog','users','payments','orders','projection','rebuild']])
    p.add_argument('--output',type=Path);p.add_argument('--archive',type=Path)
    p.add_argument('--target');p.add_argument('--expected-sha256');a=p.parse_args()
    if not re.fullmatch(r'[A-Za-z0-9][A-Za-z0-9_.-]{0,127}',a.container):p.error('invalid container identity')
    if a.operation=='backup':
        if not a.database or not a.output or a.archive or a.target or a.expected_sha256:p.error('backup requires only database and output')
        partial=None
        try:
            with tempfile.NamedTemporaryFile(prefix='.rustmall-backup-',dir=a.output.parent,delete=False) as stream:
                partial=Path(stream.name)
                run(a.container,['pg_dump','-U','postgres','--format=custom','--no-owner','--no-acl','--dbname',a.database],stdout=stream)
                stream.flush();os.fsync(stream.fileno())
            validate(a.container,partial)
            # Same-filesystem link atomically refuses to overwrite any existing target.
            os.link(partial,a.output)
            report={'operation':'backup','database':a.database,'file':str(a.output),'bytes':a.output.stat().st_size,'sha256':digest(a.output)}
        finally:
            if partial is not None:partial.unlink(missing_ok=True)
    else:
        if not a.archive or not a.target or not a.expected_sha256 or a.output or a.database:p.error('restore requires only archive, target and expected-sha256')
        if not re.fullmatch(r'rustmall_restore_[a-z0-9_]{1,40}',a.target):p.error('target must be a new rustmall_restore_* verification database')
        if not re.fullmatch(r'[0-9a-f]{64}',a.expected_sha256) or digest(a.archive)!=a.expected_sha256:raise ValueError('archive checksum mismatch')
        validate(a.container,a.archive)
        # No --clean, DROP DATABASE, or reuse-existing behavior.
        run(a.container,['createdb','-U','postgres','--template=template0',a.target],stdout=subprocess.DEVNULL)
        with a.archive.open('rb') as stream:
            run(a.container,['pg_restore','-U','postgres','--exit-on-error','--single-transaction','--no-owner','--no-acl','--dbname',a.target],stdin=stream,stdout=subprocess.DEVNULL)
        report={'operation':'restore','target':a.target,'sha256':a.expected_sha256,'scope':'new verification DB only; owner/ACL/global-role and cross-service cutover not restored'}
    print(json.dumps(report,ensure_ascii=False))
if __name__=='__main__':
    try:main()
    except (OSError,ValueError,RuntimeError,subprocess.TimeoutExpired) as error:
        detail=str(error) if not isinstance(error,subprocess.TimeoutExpired) else 'archive subprocess timeout'
        raise SystemExit('Archive operation failed: '+detail+'. No success is claimed; original databases are not dropped.')
```

备份先写私有临时文件，成功且能读取归档目录后才以不覆盖方式放到目标路径。验证头部时使用无缓冲文件，保证随后子进程从文件描述符的开头读取。文件权限为0600；SHA256用于核对这份归档是否发生变化，它不是加密，也不独自证明来源可信或所有数据块都可恢复。

恢复要求提供预期摘要，目标只能使用新的rustmall_restore_前缀。程序不运行DROP DATABASE或--clean；目标已存在就失败。恢复使用单事务和遇错退出，失败时保留新验证库供核查，不把“命令返回错误”冒充“所有远端动作必定没发生”。

### 41.10.4 【进阶】备份与新库恢复命令

如果按第40章方式启动了本检查点的手动容器环境，可先取得本地PostgreSQL身份并创建私有归档目录：
```sh
POSTGRES_CONTAINER=$(docker compose --env-file .delivery.local/compose.env ps -q postgres)
mkdir -m 700 .postgres41.local

```

目录已有内容时保留它，不要为了重跑删除已有归档。下面的ARCHIVE_SHA256应取自成功backup输出，不能随意填写：
```sh
python3 scripts/pg-archive.py backup \
  --container "$POSTGRES_CONTAINER" --database rustmall_orders \
  --output "$PRIVATE_BACKUP_DIRECTORY/orders.dump"

python3 scripts/pg-archive.py restore \
  --container "$POSTGRES_CONTAINER" \
  --archive "$PRIVATE_BACKUP_DIRECTORY/orders.dump" \
  --expected-sha256 "$ARCHIVE_SHA256" \

```

父目录应预先创建并限制访问。归档含业务内容，即使没有数据库口令也不是公开资料。归档操作与恢复检查必须由具有相应权限的运维环境完成，不能把管理员秘密交给业务Pod。

### 41.10.5 【精通】恢复实验检查哪些事实

隔离实验除二十万条未来订单外，另外保存一笔已完成订单与三条转换记录。恢复后比较订单数、金额总和、转换数、迁移账和约束数量；再故意违反金额约束，确认数据库拒绝。

最后只在恢复库中创建新的合成订单及转换，确认序列继续向前，并核对原库没有增加记录。重复备份到原输出、恢复到已有目标、使用错误摘要，都必须被拒绝。检查通过前不将该步骤写成已经验收。

### 41.10.6 【精通】用时间线判断跨库恢复为何不一致
```text
T0：订单尚未创建，支付库没有该付款身份
T1：订单正在charging，库存已held
T2：付款收据paid已提交
T3：库存confirmed，订单completed
```

如果恢复T3的订单库，却恢复T0的支付库，单看订单库会得到一笔completed订单，支付库却没有对应paid事实。每个库自己的约束都可能通过，但系统整体已经失去一致的业务解释。

同样，恢复库存到held、订单到completed，也不能靠重启worker自动推导正确结果：终态订单不会按普通队列继续领取。需要明确恢复时选取哪些事实、如何查询原参与者或渠道、何时重放、何时进入人工对账。本书后续恢复章节必须继续完成这些责任。

### 41.10.7 【精通】单库逻辑恢复的边界

一份订单库dump不包含同一业务时刻的支付库、库存收据和Kafka位置。逐个备份六个库，也不会自动产生跨库一致恢复点。跨服务恢复需要停写或协调窗口、保留事实来源、定义重放与对账，后续恢复章节继续完成这些工作。

物理基础备份配合连续WAL可以支持另一类恢复；pg_dump归档不是可用于WAL回放的基础备份。不要把逻辑恢复演练冒写成已经完成PITR、异地容灾或多节点自动切换。[持续归档与PITR说明](https://www.postgresql.org/docs/17/continuous-archiving.html)给出其独立前提。

## 41.11 排错与分层练习

### 41.11.1 【入门】按证据选择下一步

| 现象 | 先核对 | 不应直接得出的结论 |
| --- | --- | --- |
| 返回0行却很慢 | 实际扫描、过滤、循环与缓冲块 | 没有返回数据就没有工作 |
| 有索引仍读取很多 | Index Cond与Filter的区别 | 再建一个相同索引就好 |
| 列表与total不一致 | 是否共享同一快照 | 每条SQL单独正确就整体一致 |
| SQLx等连接超时 | 池占用与获取预算 | 一定是数据库语句57014 |
| 事务出错后持续25P02 | 完整事务是否已回滚 | 继续发SQL就会自动恢复 |
| 死锁偶发 | 事务取锁顺序与责任 | 重发最后一条语句即可 |
| 归档存在但恢复失败 | 版本、完整性、权限与目标前提 | 文件不为空就算可靠备份 |
| 恢复后下一次插入失败 | 序列、约束、所有者和权限 | 行数相同就可立即切流 |

### 41.11.2 【入门练习】解释一张没有结果的计划

假设领取查询返回0行，计划显示Rows Removed by Filter=200000。为什么不能仅凭返回行数判断开销？答案要点：服务器已读取并判断这些候选，LIMIT只约束返回；应继续观察索引边界、过滤与实际缓冲工作量。

### 41.11.3 【进阶练习】选择时间函数

为什么领取筛选适合statement_timestamp，而租约发放和完成时有效期校验继续使用clock_timestamp？答案要点：前者固定本次候选集合并允许形成索引范围；后者保护真实发放时刻与过期边界。不能把事务开始时间误当作任意后续语句的当前时间。

### 41.11.4 【进阶练习】设计完整的锁实验

画出两事务的取锁顺序，说明如何保证测试形成真正的等待环，怎样识别受害者，又为什么要结束整个失败事务。答案要点：先分别取得第一把锁，再同时请求另一把；核对40P01，回滚并重新读取与决策，不把模拟错误当作实际死锁。

### 41.11.5 【精通练习】定义可交付的恢复结论

某次恢复行数与金额都相同，但应用账号无权查询，序列也停在旧值。能否宣布恢复成功？答案要点：只能说明部分数据核对通过。需要补齐对象与序列、所有者与ACL、业务跨库事实、连接配置及切流/回退步骤；不能扩大证据范围。

# 第 40 章 把完整微服务项目交付出去：容器、流水线与 Kubernetes

第39章已经让订单在支付故障、worker崩溃和竞争库存时保留可恢复的责任。现在换一个问题：如果把整套工程交给另一台机器，谁负责建表、谁拥有数据库密码、哪个进程先启动、哪个版本可以回滚？如果这些问题只能靠作者记住，项目还没有完成工程交付。

本章继续同一个RustMall。用户、商品、库存、支付、持久订单、Outbox、双投影、观测和治理都保留。我们先把原生进程装进同一份Linux镜像，再建立空数据集的初始化顺序，最后把相同运行角色映射到Helm和GitOps。不要跳过Compose的真实业务验收，直接从“模板渲染成功”推断微服务已经部署正确。

学完以后，应能从空实验目录启动十个运行角色，解释迁移账号与业务账号的差别，沿一笔订单检查库存和付款效果，判断探针是否会误杀进程，并推演一次迁移失败、滚动发布失败和回滚后的数据库状态。

## 40.1 先画清楚本章交付的对象

### 40.1.1 【入门】程序、镜像、容器和数据不是同一件事

Rust源码描述程序，编译器把它转换为特定平台的可执行文件。镜像把程序及必要运行库组织成可分发的文件系统和启动配置。容器是从镜像启动的进程及其隔离环境；一个镜像可以启动多个容器，每个容器也可以使用不同参数。

数据库卷保存运行中产生的数据。删除应用容器后，只要卷仍在，订单账通常仍在；删掉数据库卷后，即使重新启动完全相同的应用镜像，已经产生的订单和付款效果也不会自动回来。因此“镜像已备份”不能代替“业务数据可恢复”。

本书当前应用镜像包含13个可执行程序；运行配置选择其中一个程序和参数。十个长期运行角色共用这一份应用镜像。迁移程序和管理工具也包含在镜像中，但只有对应任务拿到专用凭据时才有能力操作数据库。

### 40.1.2 【入门】十个运行角色分别做什么

| 角色 | 主要职责 | 使用的状态或上游 |
| --- | --- | --- |
| catalog | 商品和库存的gRPC权威写入口 | 商品库、商品与库存服务凭据 |
| users | 注册、登录、身份查询和持久撤销 | 用户库、认证Redis、JWT签名密钥 |
| payments | 幂等实验支付和退款屏障 | 支付库、支付服务凭据 |
| orders | 校验用户和商品后创建持久订单 | 订单库、users、catalog |
| worker | 租约驱动订单步骤和恢复 | 订单库、库存RPC、payments |
| catalog-http | HTTP商品接口和身份转换 | users、catalog |
| edge | 浏览器入口和路径代理 | users、orders、catalog-http |
| relay | 发布已经提交的商品Outbox | 商品库Outbox、Kafka |
| projection | 正式消费身份和读模型 | Kafka、正式投影库 |
| projection-rebuild | 独立消费身份和重建读模型 | Kafka、重建投影库 |

重建投影拥有自己的数据库和消费身份。它不是把正式消费者的offset改成0，也不是清空正式Inbox后重来。第37章已经解释过这种操作为什么可能破坏正在提供服务的视图。

### 40.1.3 【进阶】六个数据库不等于六台数据库服务器

本地实验在一个PostgreSQL实例中创建六个逻辑数据库：catalog、users、payments、orders、projection、rebuild，各自带rustmall_前缀。不同账号限制连接和表操作，便于观察边界。

这能验证账号隔离和服务持久状态的分工，不能证明存储、CPU、故障域已经隔离。一个PostgreSQL进程停机，六个库仍会同时受影响。后续数据库恢复和SRE章节继续讨论备份、容量及故障域；不要把本章的逻辑拆分称为数据库高可用。

### 40.1.4 【精通】交付必须保持哪些旧约束

商品资料仍允许修改名称和价格，但不能用普通PUT覆盖绝对库存；库存调整走带命令身份和审计的工具。重复下单沿用原Idempotency-Key，付款未知时沿原Saga身份查询和恢复。注销先持久撤销，再处理Redis；不能因缓存缺失恢复会话。消息先提交投影和Inbox，再提交offset。

容器化没有给这些规则添加例外。后面验收会再次核对它们；如果一套新部署只能通过关闭认证、绕过事务或丢弃历史账启动，就没有正确承接前文项目。

### 40.2.2 【入门】观察成功与一次性任务
```sh
docker compose --env-file .delivery.local/compose.env \
  -f deploy/delivery40/compose.yaml ps --all

curl --fail http://127.0.0.1:18086/readyz
```

六个迁移任务、授权任务和主题创建任务成功后退出0，是预期结果。长期业务容器应保持运行并通过各自探针。不要为了让状态列表“全部是running”给迁移任务配置无限重启，它们可能反复运行或永远无法满足完成依赖。

浏览器入口是宿主机回环地址18086。数据库、Redis、Kafka、内部HTTP、gRPC和指标端口都没有直接发布到宿主机。edge同时连接前端网络和内部网络：它需要从宿主机接收请求，也需要访问内部服务。其余业务角色只接内部网络。

### 40.2.3 【进阶】修改配置不会自动修改已经存在的数据

初始化SQL只在PostgreSQL镜像识别到空数据目录时执行。已有卷启动时，修改本地凭据文件不会神奇地改变数据库账号的口令。反过来，丢掉旧凭据文件再随机生成一套，也可能导致所有服务无法登录原数据库。

因此配置生成器拒绝覆盖已有目录。保留数据卷时也要保留与它对应的秘密配置；口令轮换要明确修改数据库和运行凭据的先后顺序。不要把“删卷重建后能用”当作修复已有环境的通用方法。

### 40.2.4 【精通】完整验收与手动实验分开运行
```sh
python3 scripts/check-delivery.py \
  --image rustmall/book:ch40-candidate \
  --report-dir /tmp/rustmall-delivery40-report
```

脚本创建随机Compose项目名、私有临时凭据和空数据卷，使用指定镜像执行完整业务及越权检查。结束时清理自己创建的资源，清理失败同样算失败。报告中保存实际镜像身份和已通过的检查，不保存实验口令。

脚本也使用回环18086；运行它以前，先停止占用该端口的手动实验。随机项目名解决容器资源的身份冲突，不能解决相同宿主机端口冲突。这个限制应明确写出来，不能把“随机命名”误解成任意数量测试都可并行。

## 40.3 构建一份多角色Linux镜像

### 40.3.1 【入门】为什么不能直接复制本机的target目录

在Apple芯片的macOS上编译出的文件不能直接当作Linux程序运行；即使两边都是arm64，操作系统和二进制接口仍然不同。在x86机器上构建的Linux程序，也不能假定直接运行在arm64机器上。

Dockerfile的构建阶段在Linux工具链中编译。当前已验证的是Linux arm64产物；它不是多架构发布的证明。若将来发布amd64和arm64，需要分别验证相应平台产物，再生成对应索引，而不是给单平台镜像贴上“多架构”说明。

### 40.3.2 【入门】完整Dockerfile
```dockerfile
# Use the Docker engine bundled BuildKit frontend; no separate frontend image fetch.
ARG RUST_IMAGE=rust:1.92.0-bookworm
ARG RUNTIME_IMAGE=debian:bookworm-slim
FROM ${RUST_IMAGE} AS build
RUN apt-get update && apt-get install -y --no-install-recommends \
    cmake pkg-config libssl-dev libzstd-dev zlib1g-dev && rm -rf /var/lib/apt/lists/*
ARG CARGO_BUILD_JOBS=2
ENV CARGO_BUILD_JOBS=${CARGO_BUILD_JOBS} CARGO_PROFILE_RELEASE_STRIP=symbols
WORKDIR /build
COPY . .
RUN --mount=type=cache,target=/usr/local/cargo/registry \
    --mount=type=cache,target=/usr/local/cargo/git \
    --mount=type=cache,target=/build/target \
    cargo build --locked --release --all-features --bins \
      -p commerce -p catalog -p messaging -p inventory -p platform && \
    mkdir -p /out && \
    for name in rustmall-service catalog catalog-migrate outbox-relay \
      projection-worker projection-migrate inventory-rpc inventory-adjust \
      outbox-replay projection-audit payment-command rustmall-probe rustmall-launch; do \
      cp "target/release/$name" /out/; done && \
    ldd /out/* > /out/runtime-libraries.txt
FROM ${RUNTIME_IMAGE} AS runtime
RUN apt-get update && apt-get install -y --no-install-recommends \
    ca-certificates libssl3 libzstd1 zlib1g libstdc++6 && \
    rm -rf /var/lib/apt/lists/* && \
    groupadd --gid 10001 rustmall && useradd --uid 10001 --gid 10001 --no-create-home rustmall
WORKDIR /app
COPY --from=build /out/ /app/
USER 10001:10001
ENV RUST_LOG=info
STOPSIGNAL SIGTERM
ENTRYPOINT ["/app/rustmall-launch"]
CMD ["/app/rustmall-service","edge"]
```

第一条ARG允许显式选择构建镜像。构建层安装CMake、OpenSSL和压缩库开发文件，原因是Kafka客户端等依赖包含原生编译部分。最终层只保留运行程序、证书和运行时共享库，不复制编译器和整个源码目录。

`--locked`要求按照Cargo.lock解析已有依赖；它不会固定apt仓库当日返回的所有系统包。基础镜像也应记录实际digest。这里保留易于本地实验的版本标签；严格发布还要把基础镜像、系统包来源和构建记录纳入供应链策略。

### 40.3.3 【进阶】缓存为什么不能当作产物身份

Cargo registry和target缓存减少重复下载和编译，缓存挂载本身不会作为最终镜像层自动发布。构建命令在同一条RUN里把选定程序复制到/out，再由运行阶段复制/out，所以缓存清空以后仍能重新生成运行层。

缓存命中说明某些中间结果可重用，不说明业务测试已经执行。测试与构建产物之间仍要建立独立证据；本章的容器验收比较实际运行的image ID，而不是只检查镜像标签字符串。

`ldd`输出保存在运行库清单中，便于诊断“文件存在却启动失败”的问题。动态链接器或共享库缺失也可能导致启动失败，不能只确认/app下有可执行文件。

### 40.3.5 【精通】非root、只读根和能力限制各保护什么

UID10001使应用不以容器root身份运行；只读根文件系统限制对程序与系统文件的写入；cap_drop清掉额外Linux能力；禁止提权限制执行文件利用权限标志改变身份。它们互相补充。

这些配置不会让拥有Docker管理权限的宿主机用户失去查看容器的能力，也不能弥补业务SQL权限过大。临时目录被单独挂载并限制容量；如果以后增加文件上传或本地缓存，需要明确新的存储职责，不能为方便直接撤掉整个只读根限制。

## 40.4 秘密如何到达进程

### 40.4.1 【入门】先生成私有实验配置
```python
"""Create a NEW isolated container dataset. Never overwrites an existing profile.

Files are readable inside non-root containers; their host directory is0700.
No credential value is printed or included in Compose's environment file.
"""
import argparse,json,os,secrets,uuid
from pathlib import Path
ROOT=Path(__file__).resolve().parents[1]
p=argparse.ArgumentParser(description=__doc__)
p.add_argument('--output-dir',type=Path,default=Path('.delivery.local'))
p.add_argument('--image',default='rustmall/book:ch40-candidate')
a=p.parse_args();root=a.output_dir.resolve();root.mkdir(mode=0o700);secret_dir=root/'secrets';secret_dir.mkdir(mode=0o700)
roles=json.loads((ROOT/'deploy/delivery40/roles.json').read_text())['databases']
def write(name,value,mode=0o444):
    fd=os.open(secret_dir/name,os.O_WRONLY|os.O_CREAT|os.O_EXCL,mode)
    with os.fdopen(fd,'w') as out:out.write(value+'\n')
for db,spec in roles.items():
    for role in [spec['owner']]+spec['runtime']:
        password=secrets.token_urlsafe(48)
        write(role+'_password',password)
        write(role+'_url',f'postgres://{role}:{password}@postgres:5432/rustmall_{db}?sslmode=disable')
for key in ['postgres_admin_password','jwt_key','catalog_token','inventory_token','payment_token']:
    write(key,secrets.token_urlsafe(48))
redis_user,redis_monitor=secrets.token_urlsafe(48),secrets.token_urlsafe(48)
write('redis_users_url',f'redis://app_users:{redis_user}@redis:6379/0')
write('redis_monitor_password',redis_monitor)
write('redis_acl',f'''user default off
user app_users on >{redis_user} ~users:v1:* +auth +hello +ping +quit +select +client|setname +client|setinfo +eval +evalsha +script|load +incr +expire +exists +set
user monitor on >{redis_monitor} -@all +auth +hello +ping +quit
'''.rstrip())
group='catalog-view-'+uuid.uuid4().hex
fd=os.open(root/'compose.env',os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o600)
with os.fdopen(fd,'w') as out:
    out.write(f'RUSTMALL_SECRET_DIR={secret_dir}\nRUSTMALL_IMAGE={a.image}\nPROJECTION_GROUP={group}\nREBUILD_GROUP={group}-rebuild\n')
print('Created private container profile; keep it with its volumes. No credentials printed.')
```

配置生成器创建0700目录，秘密文件放在其中；普通compose.env只记录文件目录、镜像名和稳定消费身份，不记录口令值。目录已存在时立即失败，防止误覆盖与已有数据库卷绑定的秘密。

URL里的口令由URL安全字符构成，避免手工拼接时把@或冒号误当作连接串分隔符。实验URL明确使用本地明文连接；这不是外网数据库的TLS配置。第44章继续处理证书、主机名校验与加密连接，不能仅靠把地址从localhost换成公网域名就宣布生产可用。

### 40.4.2 【进阶】为什么秘密文件是0444而外层目录是0700

本机Compose文件秘密通常通过单文件绑定挂载到容器，不会自动把宿主文件拥有者改成容器中的10001。把宿主文件设成仅原用户可读，可能让非root应用无法读取挂载文件。

本实验在宿主机以0700目录限制路径遍历，同时把单独挂入容器的文件设为可读。目录权限和文件权限承担不同职责。宿主机管理员、能管理Docker的人，以及能读取应用进程环境的人仍然处在信任边界内。这种实验方案不等于外部秘密管理服务或静态加密。

Kubernetes Secret投影采用另一套权限模型：本章设置0440并使用Pod的fsGroup，使非root进程能够读取。不要把Compose文件权限的经验原样套到所有编排系统上。

### 40.4.3 【入门】入口程序只读取明确列出的文件
```rust
//! Read only explicitly named runtime secrets, then exec without a shell.
use std::{ffi::OsString, path::Path, process::Command};
const NAMES: [&str; 9] = [
    "DATABASE_URL",
    "CATALOG_DATABASE_URL",
    "PROJECTION_DATABASE_URL",
    "REDIS_URL",
    "JWT_SECRET",
    "RUSTMALL_CATALOG_TOKEN",
    "RUSTMALL_INVENTORY_TOKEN",
    "PAYMENT_TOKEN",
    "APP_AUTH__JWT_SECRET",
];
fn main() {
    if run().is_err() {
        eprintln!("runtime launch failed; check command and mounted secret files (values hidden)");
        std::process::exit(1);
    }
}
fn run() -> Result<(), Box<dyn std::error::Error>> {
    let mut args = std::env::args_os().skip(1);
    let executable = args.next().ok_or("missing executable")?;
    let mut command = Command::new(executable);
    command.args(args);
    for name in NAMES {
        let key = format!("{name}_FILE");
        if let Some(path) = std::env::var_os(&key) {
            if std::env::var_os(name).is_some() {
                return Err("value and file both configured".into());
            }
            let metadata = std::fs::metadata(Path::new(&path))?;
            if !metadata.is_file() || metadata.len() > 16 * 1024 {
                return Err("invalid secret file".into());
            }
            let raw = std::fs::read_to_string(path)?;
            let value = raw.trim_end_matches(['\r', '\n']);
            if value.is_empty() || value.contains(['\r', '\n', '\0']) {
                return Err("invalid secret value".into());
            }
            command.env(name, OsString::from(value)).env_remove(key);
        }
    }
    #[cfg(unix)]
    {
        use std::os::unix::process::CommandExt;
        Err(command.exec().into())
    }
    #[cfg(not(unix))]
    {
        let status = command.status()?;
        std::process::exit(status.code().unwrap_or(1));
    }
}
```

程序只识别白名单中的变量，例如DATABASE_URL_FILE和PAYMENT_TOKEN_FILE。它拒绝同时配置直接值和文件，因为两种来源并存时“到底用了哪个密码”很难审计。文件必须是普通文件、大小有限，内容不能空、不能含多行或NUL。

读完后，入口只为子进程设置对应变量并移除文件变量。错误信息不包含秘密值。它没有把参数拼接成shell字符串，所以传入的分号、美元符号等只是参数数据，不会被入口重新解释为命令。

### 40.4.4 【精通】为什么使用exec而不是在shell后面挂子进程

Unix上的exec用目标程序替换入口进程。容器接收到SIGTERM时，信号因此直接到达真正的业务程序；业务程序既有的优雅停止逻辑可以继续工作。若入口额外留下一个没有转发信号的shell，部署系统可能只终止shell，最后超时强杀真正的业务进程。

本章为生命周期留出30秒，其中preStop等待3秒，剩余时间要覆盖应用停止接入、在途请求收尾和遥测导出。这个预算不是“所有分布式事务必须在30秒内完成”的要求：持久订单、租约和Outbox允许新进程继续恢复未完成责任。

## 40.5 数据库与Redis最小权限

### 40.5.1 【入门】账号要按职责拆，而不是所有服务共用管理员
```json
{
  "databases": {
    "catalog": {"owner": "migrate_catalog", "runtime": ["app_catalog", "relay_catalog", "inventory_admin"]},
    "users": {"owner": "migrate_users", "runtime": ["app_users"]},
```

六个迁移所有者负责各自库的DDL。九个业务账号承担不同运行职责：商品API、relay和库存管理虽然访问同一个商品库，却拿不同账号；订单API和worker也分开。这样数据库能够拒绝不属于调用者职责的写入。

“服务代码目前没有调用DELETE”只是实现现状；“数据库账号没有DELETE权限”才是额外约束。前者不能替代后者。权限边界也不是业务规则的完整替代，例如库存事务中的行锁、状态机和幂等校验依旧由程序实现。

### 40.5.4 【精通】用失败证明边界确实存在

验收会真的执行本应失败的SQL，而不是只读授权文件。下面两个语句即使WHERE false不修改任何行，数据库仍应拒绝缺少的列权限：
```sql
UPDATE users SET role='admin' WHERE false;
UPDATE product_outbox SET payload='{}'::jsonb WHERE false;
```

第一条以app_users执行，第二条以relay_catalog执行。使用WHERE false可以验证权限而不改业务数据，但必须确认命令确实返回permission denied，不能把语法错或“表不存在”也统计成权限检查通过。

完整容器验收还覆盖订单终态、worker创建、库存、付款审计、投影删除与消费身份，共九项拒绝。验证只证明选定职责的这些边界；生产还要管理拥有超级用户权限的运维通道。

### 40.5.5 【进阶】Redis只允许用户服务需要的命令

生成器关闭默认用户，app_users只访问users:v1:*前缀，并允许当前限流Lua及会话撤销所需命令；monitor只有探测职责。登录、限流和注销必须正常工作，同时应用账号的FLUSHDB必须被拒绝。

Redis是会话辅助状态，不是持久撤销记录的替代。即使运维账号误清了Redis，用户库中的revoked_at也不能消失。第34章的数据库优先撤销和第39章的故障实验都保留。

Redis本地实验关闭持久化，原因是这里不把它当作唯一权威账；这不等于所有Redis使用场景都应关闭持久化。缓存、限流和业务主存储有不同恢复要求，第42章会继续区分。

## 40.6 把依赖顺序写进Compose

### 40.6.1 【入门】启动顺序表达的是完成条件
```text
空PostgreSQL卷初始化
  -> 六套各库迁移成功
  -> 列级授权成功
  -> 业务角色启动

Kafka就绪
  -> 主题创建成功
  -> relay与两个投影启动
```

service_started只说明依赖进程曾启动，service_healthy说明通过配置的健康检查，service_completed_successfully用于一次性任务。把迁移任务误写成service_started，会让应用与DDL竞争；把已退出的迁移任务当作必须一直healthy，也可能永远无法启动。

PostgreSQL探针显式连接127.0.0.1的TCP端口，避免空卷初始化期间临时Unix套接字服务器被提前当作正式可用服务器。探针本身也要与镜像真实的启动过程相符。

### 40.6.3 【进阶】主题、保留时间与重建窗口

本地主题使用三分区、单副本、delete清理和七天保留。单副本只适合本章实验，不提供副本容错。保留七天也意味着任意旧时刻的完整重建未必可能：最早需要的事件已经删除时，单靠把offset设为earliest不能恢复缺失历史。

本章保留第37章的新数据库、新消费身份和完整对账方法。不要为了节省空间随手改成compaction，并假定压缩后的日志必然保留每个商品的最高revision；并发发布和同键顺序还需要第43章进一步分析。

### 40.6.4 【精通】Compose依赖不是运行期故障控制器

启动依赖保证首次启动的条件，不会在任何依赖以后崩溃时自动推导正确的业务恢复策略。运行时仍要靠请求预算、熔断、持久重试、租约和幂等保护业务。

本地实验以显式重启便于观察进程状态；生产编排会按Pod重启策略恢复进程。健康检查失败的含义必须准确，否则控制器会反复重启仍有机会恢复的程序，放大原故障。

## 40.7 探针、指标与真实可用性

### 40.7.1 【入门】存活与就绪回答不同问题

存活探针问“这个进程是否还应继续运行”，就绪探针问“现在是否应把流量送给它”。用户服务在Redis短暂停机时不能完成正常身份流程，应退出就绪集合；如果进程本身仍响应，不能仅因此触发无休止重启。

HTTP角色分别使用/healthz和/readyz；catalog的gRPC健康服务也分别命名liveness和readiness。启动探针给初始化留出额外时间，在它成功之前暂缓存活与就绪判断。

### 40.7.2 【进阶】不带业务凭据的短探针

入口与探针放在platform/src/bin中，Cargo会按文件名发现二进制。platform的完整清单如下；探针用到reqwest、tonic和tonic-health，不能只复制Rust文件却漏掉依赖。

```rust
//! A short dependency-aware probe. It never reads application credentials.
use std::time::Duration;
#[tokio::main]
async fn main() {
    if run().await.is_err() {
        eprintln!("probe failed");
        std::process::exit(1);
    }
}
async fn run() -> anyhow::Result<()> {
    let args: Vec<_> = std::env::args().skip(1).collect();
    match args.first().map(String::as_str) {
        Some("http") if args.len() == 2 => {
            let reply = reqwest::Client::builder()
                .no_proxy()
                .redirect(reqwest::redirect::Policy::none())
                .timeout(Duration::from_secs(2))
                .build()?
                .get(&args[1])
                .send()
                .await?;
            anyhow::ensure!(
                reply.status() == reqwest::StatusCode::OK,
                "unhealthy HTTP response"
            );
        }
        Some("grpc") if args.len() == 3 => {
            use tonic_health::pb::{
                HealthCheckRequest, health_check_response::ServingStatus,
                health_client::HealthClient,
            };
            anyhow::ensure!(
                matches!(args[2].as_str(), "readiness" | "liveness"),
                "unknown probe service"
            );
            tokio::time::timeout(Duration::from_secs(2), async {
                let channel = tonic::transport::Endpoint::from_shared(args[1].clone())?
                    .connect_timeout(Duration::from_millis(500))
                    .timeout(Duration::from_secs(1))
                    .connect()
                    .await?;
                let reply = HealthClient::new(channel)
                    .check(tonic::Request::new(HealthCheckRequest {
                        service: args[2].clone(),
                    }))
                    .await?;
                anyhow::ensure!(
                    reply.get_ref().status == ServingStatus::Serving as i32,
                    "grpc not serving"
                );
                Ok::<_, anyhow::Error>(())
            })
            .await??;
        }
        _ => anyhow::bail!("usage: rustmall-probe http URL | grpc URL readiness/liveness"),
    }
    Ok(())
}
```

HTTP探针禁用代理和重定向，只接受200，并限制等待时间。RPC探针只查询健康协议中的明确服务名，不携带管理员或业务令牌。探针命令本身最多等约两秒，编排层给三秒，避免编排层先于探针自己的超时强制终止它。

这不是公开业务接口的认证豁免。健康协议只返回受限状态；真实管理和写接口仍保留原认证与权限检查。

### 40.7.3 【精通】后台角色没有“接收HTTP流量”的同等就绪语义

worker、relay和投影用指标端点判断进程是否还响应。这能发现进程退出或事件循环失去响应，不能单独证明订单在推进、Kafka可用或投影没有积压。

业务进展依赖第38章的订单待处理年龄、Outbox最老年龄、失败与租约，以及第37章的全量对账。不要把一个/metrics返回200写成“消息已经全部消费”。

数据库测试使用一次性CI管理员，因为SQLx测试需要创建隔离数据库；运行部署中的业务账号仍是前面的最小权限账号。这两类账号不能混用，也不能把测试管理员口令带进正式运行Secret。

### 40.8.3 【进阶】一次构建、原产物验收与发布
```sh
#!/usr/bin/env bash
set -euo pipefail
# 只允许一次性 GitHub runner；本地验收使用 check-delivery.py。
[[ "${CI:-}" == true && "${GITHUB_ACTIONS:-}" == true ]] || {
  echo '请在 GitHub Actions 的临时 runner 中执行。' >&2; exit 2;
}
[[ "${GITHUB_RUN_ID:-}" =~ ^[0-9]+$ && "${GITHUB_RUN_ATTEMPT:-}" =~ ^[0-9]+$ ]] || {
  echo '缺少有效的运行编号。' >&2; exit 2;
}
[[ -n "${GITHUB_OUTPUT:-}" ]] || { echo '缺少步骤输出文件。' >&2; exit 2; }
image="rustmall/ci:run-${GITHUB_RUN_ID}-${GITHUB_RUN_ATTEMPT}"
report_dir="${RUNNER_TEMP:?}/rustmall-delivery-${GITHUB_RUN_ID}-${GITHUB_RUN_ATTEMPT}"
build_args=()
if [[ -n "${RUSTMALL_RUST_IMAGE:-}" ]]; then
  build_args+=(--build-arg "RUST_IMAGE=$RUSTMALL_RUST_IMAGE")
fi
docker build "${build_args[@]}" --tag "$image" .
python3 scripts/check-delivery.py --image "$image" --report-dir "$report_dir"
# 直接取本次验收记录的镜像 ID；发布步骤不能重新 build，也不能只相信可变标签。
python3 - "$report_dir/container.json" "$GITHUB_OUTPUT" <<'PY'
import json,re,sys
from pathlib import Path
r=json.loads(Path(sys.argv[1]).read_text())
assert r['success'] and r['cleanup_exit']==0 and r['passed']==7
image=r['image_id'];assert re.fullmatch(r'sha256:[0-9a-f]{64}',image)
with open(sys.argv[2],'a') as f:f.write('tested_image_id='+image+'\n')
PY
```

脚本把本次验收报告中的image ID写入步骤输出。后续发布通过这个身份打标签，不再次执行build。若先测试A、发布前又重新构建B，即使二者来自相同源码，也可能因基础镜像、系统包或构建环境变化而产生不同产物。

容器验收逐个检查十个实际运行容器的Image身份，还检查UID、只读根与能力限制。这比“十个配置里image字符串相同”更强；标签可变，配置相同不能证明实际容器没有继续运行旧镜像。

### 40.8.4 【精通】提交号、image ID、注册表digest和证明材料

提交号标识源码状态，本地image ID标识Docker存储中的镜像对象，注册表digest标识可拉取的manifest或索引。它们不是可以随意互换的字符串。发布后应记录注册表返回的digest，并在集群部署时固定这个digest。

构建来源声明和SBOM分别帮助回答产物从哪里来、包含哪些组件。它们不能代替功能测试。本章不把Docker默认导出的某种attestation冒写成“所有平台已生成并验证完整SBOM和来源证明”；当前证据范围在章末单独列出。

参阅[GitHub任务依赖](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-jobs)与[Docker镜像推送](https://docs.docker.com/reference/cli/docker/image/push/)。把官方配置语义与本书真正执行过的本地检查分开，读者才能判断还有哪些发布环节需要在自己的仓库完成。

## 40.9 把相同角色映射到Kubernetes

### 40.9.1 【入门】Pod、Deployment、Service与Job

Pod是共同调度和共享部分运行环境的一组容器。本章每个业务Pod只有一个应用容器。Deployment维护期望副本数并管理滚动更新；Service为一组被标签选中的就绪Pod提供稳定地址；Job表达需要成功完成的一次性工作，例如数据库迁移。

Kubernetes不会因为创建了Service就帮我们建立数据库，也不会从容器名字自动知道需要什么Secret。Chart只部署应用层、迁移和授权任务；数据库账号、六个数据库、Redis ACL、Kafka主题、监控与Secret必须由平台准备。

### 40.9.2 【入门】Chart的文件树
```text

  values.yaml
  values.schema.json
  files/permissions.sql
  templates/_helpers.tpl
```

单副本实验默认关闭PDB。把minAvailable=1套到唯一副本，可能阻止自愿驱逐，却不能提供第二个副本。两副本PDB约束的是自愿中断，不防节点崩溃，也不保证数据库仍有容量承接所有副本。

滚动策略maxUnavailable=0、maxSurge=1给新Pod通过就绪检查前保留旧Pod的机会。它需要足够的额外资源；如果调度容量只够旧副本，发布可能等待而不是自动成功。

### 40.9.6 【精通】副本数会扩大连接和准入容量

第39章的速率和并发限制属于每个实例。把HTTP副本从1改为2，不会自动得到一个全局32次/秒的配额。数据库连接池也按进程创建：users两副本可能占用最多20条连接，订单API和worker分别还要计入。

滚动发布时还可能同时存在旧新Pod、迁移连接与后台任务。应按各程序真实连接池上限、最大副本与发布期间额外副本计算，再为运维和恢复留余量。不能只看values里的CPU请求就判断数据库容量足够。

### 40.10.2 【精通】一个容易被忽略的ConfigMap生命周期

授权SQL所在ConfigMap处于最早阶段，六个迁移位于下一阶段，授权Job最后运行。若ConfigMap也配置“hook成功后删除”，它可能在自己创建成功后就被删除，后面的授权Job反而无法挂载。

本章ConfigMap只在下次hook创建前替换，保留给后续Job读取；迁移和授权Job成功后可清理，失败保留诊断。Helm hook资源并不自动等同于普通发布资源的完整生命周期，卸载时还应核对保留的hook资源。

在Helm模式，权重为-20、-10、-5；在Argo模式，相应的PreSync wave顺序一致。相同wave里的六个任务都必须成功，才能进入后续阶段。参阅[Helm hook生命周期](https://helm.sh/docs/topics/charts_hooks/)与[Argo同步阶段和波次](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-waves/)。

### 40.10.4 【精通】渲染、API接收和策略执行是三层证据

`helm template`证明模板能生成资源；API接收证明目标版本接受资源结构；真正的流量允许和拒绝实验才证明网络插件执行了策略。Kind默认网络不能作为NetworkPolicy已经生效的证据。

同样，Secret对象能被创建，不等于某个Pod一定能读取；Pod能读Secret，不等于数据库口令和权限正确。逐层验证比看到一行“configured”后跳过后续检查可靠。

## 40.11 交付命令、GitOps与回滚实验

### 40.11.1 【入门】部署前先列出外部前提

目标namespace中要有六个库的所有者Secret、各运行角色Secret和授权任务管理Secret。Secret名字及key以values为准；只复制键名表，不要在Git里保存填好的密码文件。数据库必须已创建各账号、撤销不必要连接权限；Kafka主题与Redis ACL也应提前就绪。

管理Secret包含PGHOST、PGPORT、PGUSER、PGPASSWORD、PGDATABASE、PGSSLMODE。运行角色的Secret按secretFiles中的文件名保存连接URL或令牌。生产数据库应使用正确TLS验证配置；本章隔离实验使用disable，不能把它作为公网部署示范。

### 40.11.2 【进阶】先做本地配置检查

```sh
helm lint charts/rustmall --strict
```

配置检查核对十个工作负载、十个Service、六个迁移和授权Job；比较所有者与业务凭据、检查探针和安全上下文、拒绝不完整digest与冲突配置，并分别渲染Helm和Argo两种生命周期。它不连接集群，不能替代真实运行验收。

### 40.11.3 【进阶】使用明确的集群配置与不可变镜像

下面的环境变量必须由读者填成自己的真实值，不能把本地image ID当成注册表digest。使用独立kubeconfig并先核对目标集群，避免在默认上下文里误操作。
```sh
kubectl --kubeconfig "$LAB_KUBECONFIG" cluster-info

helm --kubeconfig "$LAB_KUBECONFIG" -n rustmall-book \
```

namespace和外部Secret应先准备。不要为了让上面命令立刻成功，临时给所有程序设置同一个超级用户连接串。

本地Kind可以加载已构建的单平台镜像并设置image.pullPolicy=Never。Docker使用容器化镜像存储时，本机缓存的多平台索引可能引用未下载的平台层；默认按全部平台导入会报缺少digest内容。应导出并导入实际验证的平台，记录对应镜像身份，不把这个处理称为多架构测试成功。

如需在本机复现本章的完整集群实验，配套工程另有隔离入口。先按[Kind官方安装说明](https://kind.sigs.k8s.io/docs/user/quick-start/)准备kind与kubectl，并按[Helm官方安装说明](https://helm.sh/docs/intro/install/)准备helm。本轮采用Kind 0.33.0、Kubernetes 1.36.4、Helm 4.3.1与Docker 29.7.2；构建镜像的平台必须与节点的原生平台一致。
```sh

```

这个入口创建随机命名的单节点Kind集群和独立kubeconfig，不修改读者默认集群配置。它先启动独立的PostgreSQL、Redis和Kafka实验基础设施，通过集群Service与EndpointSlice提供给应用，再创建各角色Secret，执行完整Chart安装及故障实验。结束后清理自己创建的集群和数据卷。它也使用本机18086端口，不能与手动实验或Compose验收并行运行。

这里的外部基础设施表示“在应用Chart之外管理”，不是生产托管服务；本机Docker故障仍会同时影响它们和Kind。脚本会校对应用镜像与节点架构，按实际平台导入镜像，不能靠模拟另一种架构凑出通过结果。

### 40.11.4 【精通】迁移失败时应该观察什么

在可丢弃的隔离环境中，把users迁移Secret临时改成无效连接地址，再首次安装。预期迁移Job失败、发布失败，并且业务Deployment尚未创建。恢复Secret后重试，迁移程序应识别已经成功的旧迁移，不能重复破坏表。

如果首次安装时Secret还不存在，不应临时跳过迁移继续发布。先修复外部前提，再重试原发布身份。失败Job日志应说明是哪一层连接、DDL或权限出错；不要输出所有环境变量来“方便诊断”。

### 40.11.5 【进阶】滚动失败与回滚不是数据库倒带
```sh
helm --kubeconfig "$LAB_KUBECONFIG" -n rustmall-book history book

helm --kubeconfig "$LAB_KUBECONFIG" -n rustmall-book \
  rollback book "$GOOD_REVISION" --wait --timeout 5m
```

在隔离环境里把users的HTTP_ADDR改成非法地址，可以观察新Pod启动失败而旧就绪Pod仍保留。回滚把工作负载配置恢复到指定历史版本，随后还要检查原订单、付款效果和库存是否保持一致。

回滚镜像或配置不会撤销已经完成的外部付款，不会把删除的数据库列变回来，也不能自动重放Kafka里已经过期的数据。这里验证的是发布配置恢复与业务账保留，不是“所有副作用都回到了过去”。

### 40.11.6 【精通】数据库采用扩展、迁移、收缩

假设要把单个name字段拆成两个字段。先添加允许旧程序继续工作的字段和约束，再让新程序兼容新旧表示，分批回填并记录进度；确认旧程序不再运行、数据已核对，最后在另一次发布收缩旧结构。

如果先删旧列再发布新程序，即使旧Pod还在运行，也会立刻遇到查询错误。回滚到旧镜像反而更不可能成功。数据库变更的兼容窗口必须覆盖滚动更新、故障恢复和回滚所需的时间。

### 40.11.7 【进阶】GitOps把发布变更变成可审查状态
```python
"""生成需要审查的 Argo CD Application；不连接集群或远端仓库。"""
import argparse
import json
import re
from urllib.parse import urlsplit

parser = argparse.ArgumentParser()
parser.add_argument("--repo", required=True, help="不包含令牌的 HTTPS Git 仓库地址")
parser.add_argument("--revision", required=True, help="经过审查的完整 Git 提交 SHA")
parser.add_argument("--image-repository", required=True, help="已发布镜像的仓库名，不含标签")
parser.add_argument("--image-digest", required=True, help="注册表返回的已验证sha256摘要")
args = parser.parse_args()
if (not re.fullmatch(r"[a-z0-9][a-z0-9._:/-]*", args.image_repository)
        or ":" in args.image_repository.rsplit("/",1)[-1]
        or "//" in args.image_repository or ".." in args.image_repository):
    parser.error("image-repository 必须是无标签、无凭据的镜像仓库名")
if not re.fullmatch(r"sha256:[0-9a-f]{64}",args.image_digest):
    parser.error("image-digest 必须是注册表的完整sha256摘要")
try:
    url = urlsplit(args.repo)
except ValueError:
    parser.error("仓库 URL 无法解析")
if (url.scheme != "https" or not url.hostname or not url.path.strip("/")
        or url.username is not None or url.password is not None or url.query or url.fragment):
    parser.error("仓库必须是无内嵌凭据、无查询参数的 HTTPS 地址")
if not re.fullmatch(r"[0-9a-f]{40}", args.revision):
    parser.error("revision 必须是完整的 40 位小写十六进制 Git SHA")
application = {
    "apiVersion": "argoproj.io/v1alpha1",
    "kind": "Application",
    "metadata": {"name": "rustmall-lab", "namespace": "argocd"},
    "spec": {
        "project": "default",
        "source": {
            "repoURL": args.repo,
            "targetRevision": args.revision,
            "path": "charts/rustmall",
            "helm": {
                "releaseName": "book",
                "valueFiles": ["../../deploy/environments/lab.yaml"],
                "parameters": [
                    {"name":"controller","value":"argocd"},
                    {"name":"image.repository","value":args.image_repository},
                    {"name":"image.digest","value":args.image_digest},
                    {"name":"image.requireDigest","value":"true"},
                ],
            },
        },
        "destination": {
            "server": "https://kubernetes.default.svc",
            "namespace": "rustmall-gitops",
        },
    },
}
# JSON 也是 YAML 可接受的表示；这里使用标准库避免额外模板替换与转义依赖。
print(json.dumps(application, ensure_ascii=False, indent=2))
```

生成器要求无内嵌凭据的真实HTTPS仓库地址、完整提交SHA、镜像仓库和注册表digest。它只生成Application，不连接集群，也不帮读者创建远端仓库。输出固定提交与镜像，并显式选择argocd控制模式。
```sh
python3 scripts/render-gitops-app.py \
  --repo "$GIT_REPOSITORY" \
  --revision "$GIT_REVISION" \
  --image-repository "$IMAGE_REPOSITORY" \
  --image-digest "$IMAGE_DIGEST" \
  > /tmp/rustmall-application.json
```

读者应先评审输出，再交给自己的Argo环境。生成器默认没有打开自动同步；外部基础设施和Secret仍须先于PreSync就绪。不要同时让Helm CLI与Argo自动管理同一个发布，否则两个控制器会互相覆盖期望状态。

## 40.12 验收、排错与分层练习

### 40.12.1 【入门】真实业务验收应观察持久事实

一笔数量2、初始库存10的订单完成后，库存应为8，支付效果中paid恰好一条。相同请求键再次提交，应返回原订单身份，不能重复付款或扣库存。受控管理工具增加3后，库存为11；商品下架后，两套投影最终应保存库存11且listed=false的墓碑。

这些状态跨越HTTP、RPC、数据库事务、worker、Kafka和投影。只有入口返回202不够，只有日志里打印“completed”也不够；必须读权威账并确认幂等效果。

### 40.12.2 【进阶】常见故障从哪层排查

| 现象 | 先检查 | 不应直接采取的处理 |
| --- | --- | --- |
| 编译前下载超时 | 具体镜像源、网络与失败层 | 随机修改Rust业务代码 |
| 文件存在却不能启动 | 平台、动态链接器、共享库 | 把所有容器改成root |
| Secret挂载后读取失败 | 文件模式、UID/GID、fsGroup | 把全部秘密写进镜像 |
| PostgreSQL看似ready但迁移连不上 | 是否误测初始化临时服务器 | 忽略迁移失败继续启动 |
| 新口令重启后无效 | 旧卷是否保留旧账号口令 | 未经确认删除数据卷 |
| edge映射端口无法访问 | 网络配置、绑定地址、内部/前端网络 | 对外发布每个服务和数据库 |
| 探针200但订单积压 | worker状态、租约、依赖、持久重试时间 | 把指标可达当作业务已完成 |
| 新Pod起不来且发布等待 | Secret、迁移、就绪、资源与新旧副本 | 立即删除所有旧健康Pod |
| 配置回滚成功但接口报列缺失 | 数据库兼容性与DDL历史 | 反复回滚相同镜像 |
| 网络策略应用后仍可访问 | CNI是否支持并执行策略 | 仅凭YAML断言隔离已生效 |

### 40.12.3 【入门练习】从现象解释对象

解释下面三种状态为什么可以同时发生：镜像完全相同，两个容器运行角色不同；业务Pod全部健康，投影仍有积压；应用容器已删除，订单数据库仍有记录。

答案要点：镜像提供程序集合，参数与凭据决定运行职责；进程健康与业务进展分开；数据库卷或外部数据库独立于应用容器生命周期。不要把镜像、进程和数据混为一体。

### 40.12.4 【进阶练习】设计一次会失败的权限检查

为relay设计一条不会修改业务数据、但能证明它不能重写事件内容的语句，并说明如何排除假阳性。再为app_orders设计一条不能直接推进订单终态的检查。

答案要点：以各自运行账号执行带WHERE false的UPDATE，检查真实返回permission denied；同时证明连接到了正确数据库、表与列已存在。不能把连接失败或语法错误当成权限保护成功。

### 40.12.5 【进阶练习】两副本时估算发布资源

假设users平时两副本，每个池最多10连接，maxSurge为1。本服务滚动期间理论上可能占用多少连接？为什么这个值仍不是整个系统的数据库容量？

答案要点：只计算该服务，三个并存Pod最多30连接；还要计入订单、worker、支付、商品、relay、迁移、后台任务与运维余量。连接上限还不等于可承受的活跃查询数量。

### 40.12.6 【精通练习】让回滚保留业务责任

设计一次新配置使users无法启动的发布实验。说明如何确认旧Pod仍提供服务，怎样选择回滚版本，以及回滚后要检查哪些业务账。

答案要点：在隔离环境保留一笔已完成订单；发布前记录健康版本和订单身份；观察新Pod失败、旧Pod可用及发布状态；回滚后核对原订单completed、付款效果只有一条、库存和投影仍符合预期。不能以创建一笔新订单成功替代原订单事实核对。

### 40.12.7 【精通练习】审查一个错误的hook设计

有人把授权SQL ConfigMap设为PreSync -20，六个迁移设为-10，授权Job设为-5，并给所有hook都加HookSucceeded删除。顺序看似正确，为什么首次安装仍可能失败？

答案要点：ConfigMap自己的创建成功可能触发删除，后续授权Job挂载时对象已消失。依赖关系不仅有创建顺序，还有资源保留寿命。应保留配置至其消费者完成，并明确下一次替换与卸载清理策略。

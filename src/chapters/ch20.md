# 第 20 章 Docker：构建与运行 RustMall

第 19 章让我们能确定“正在交付哪次修改”。本章继续回答：为什么同一个提交在开发机能运行，换到服务器却找不到配置、连不上数据库，甚至提示文件不存在？这些问题不仅与 Rust 代码有关，还与操作系统、构建工具、动态库、进程权限和网络位置有关。

本章承接第 18 章的 monolith，不提前切到尚未引入的微服务。学习顺序是先运行一个极小容器，观察进程、文件和端口，再理解 Dockerfile，最后编写 RustMall 镜像与健康检查。学完应能独立定位一次构建失败、一次运行失败和一次接口未就绪，而不是只记住 docker run 的参数。

## 20.1 镜像、容器与进程：先建立准确模型

### 20.1.1 【入门】程序需要的不只有源代码

Rust 源码经过编译得到可执行程序。这个程序还可能依赖特定操作系统接口、动态链接库、证书和配置文件。cargo run 能运行，部分原因是你当前终端已经具备这些条件；换到新机器时，它们未必存在。

容器化把应用的运行文件、启动方式和相应用户空间环境组合为可分发镜像。它减少环境准备的随意性，但不会消除内核、处理器架构、网络和外部数据库的要求。

先把问题拆成三层：源码与构建输入决定产生什么程序；镜像决定程序带着什么文件启动；运行配置决定它此刻连接哪里、拥有什么权限。后面的排错会反复沿这三层展开。

### 20.1.2 【入门】镜像像模板，容器是正在运行的一次实例

同一镜像可以创建多个容器，每个容器有独立的运行状态和可写层。停止一个容器不会自动停止由同一镜像创建的另一个容器；重新使用镜像创建容器，也不代表原容器写入的文件自动出现。

模板类比帮助理解“一个定义、多个实例”，但镜像不是一个抽象图纸。它包含实际文件系统层与运行配置。容器启动后也不是一台完整虚拟机，而是受相应隔离与资源规则约束的进程集合。

### 20.1.3 【入门】客户端、daemon 与 registry

Docker 客户端解析 docker 命令，与 Docker Engine 服务端通信。服务端负责管理镜像、容器、网络与卷。registry 保存可分发镜像，供 pull 与 push 使用；它与第 19 章的 Git 仓库保存不同对象。

因此有三种不同故障：本机没有客户端；客户端存在但连不到服务端；服务端正常但访问镜像仓库失败。先区分故障发生在哪一跳，再排查安装、服务状态或网络，不要一律重装应用。

### 20.1.4 【进阶】容器与虚拟机的区别

Linux 容器中的进程共享所依赖 Linux 内核的能力，并通过命名空间等机制获得隔离视图。虚拟机则提供虚拟硬件环境并运行自己的客体内核。两者可以组合：macOS 与 Windows 上的 Docker Desktop 为 Linux 容器提供相应 Linux 环境。

这意味着容器中的 uname、进程与文件系统看到的是容器或其 Linux 环境的视图，不是把宿主操作系统原封不动装进去了。不能把 macOS 编译的可执行文件直接复制到 Linux 镜像，就认为同为 ARM64 一定能运行。

### 20.1.5 【进阶】隔离与资源限制是两组问题

命名空间帮助隔离进程、网络、挂载等视图；cgroup 等机制用于资源控制与统计。一个容器能看到较少文件，不表示它已经有合适的 CPU 和内存上限。

资源上限也不保证程序自动适配。如果给 RustMall 很低的内存额度，密码哈希、连接和缓存仍需要内存，进程可能被终止。后面会通过实际资源观测选择额度，而不是把“容器化”理解成资源成本消失。

### 20.1.6 【精通】构建、运行和交付身份需要相互关联

Git 提交标识源码状态，Cargo.lock 固定解析出的依赖图，镜像 digest 标识镜像内容，运行容器再使用某一份配置与外部数据。定位问题时，至少知道这四者，才可能判断两个环境是否真的在执行同一版本。

仅写一个镜像 tag 还不够，因为 tag 可以被重新指向。仅记录提交号也不够，因为构建工具和依赖、基础镜像、配置不同，仍可能得到不同产物或行为。本章先保留清楚的构建与启动记录，第 22 章再把这些步骤接进流水线。

## 20.2 安装与连接检查：确认自己操作的是哪一台 Engine

### 20.2.1 【入门】macOS 的准备步骤

按 Docker 官方安装页选择与你处理器相符的 Docker Desktop 安装包，完成安装并启动应用，等待服务端就绪。Apple 芯片与 Intel 对应不同架构，不能只看电脑外壳是否相同。

随后在终端执行 docker version。应同时看到客户端和服务端信息；如果只有客户端部分并提示连接失败，说明命令可用但 Engine 尚不可达。此时先检查 Desktop 是否已启动、当前 context 是否正确，再检查应用报错。

本书不固定安装器界面的按钮位置，因为它会随版本变化；固定的是需要证明的状态：客户端能连接到负责本次实验的服务端。

### 20.2.2 【入门】Windows 与 Linux 的区别

Windows 读者按官方 Docker Desktop 安装页准备受支持的 Linux 容器后端，并使用 Git Bash 或 WSL 中一致的项目目录。不要在两个环境中混用不同路径、不同 Docker context，再把端口或文件权限差异误认为 Rust 问题。

Linux 读者可以选择官方 Docker Engine 安装流程。Ubuntu 使用官方软件源安装时，要先确认发行版与现有软件情况，配置来源和签名，再安装 Engine、CLI、Buildx 与 Compose 插件。已有机器不要机械卸载 containerd 或其他组件：它们可能被其他服务使用。

安装属于系统维护；本章在全新实验机器按官方对应系统说明完成，不把一条下载后直接执行的脚本当成所有机器的通用准备步骤。

### 20.2.3 【入门】三个检查命令各证明什么
```bash
docker version
docker info
docker context show
```

version 证明客户端和服务端版本及连接情况；info 查看当前服务端的环境能力；context show 说明客户端当前选择的连接目标。它们都不证明你的应用已经构建或端口可达。

如果机器上有本地与远程多个 context，误用远程目标可能把实验容器建到另一台机器。遇到“本机找不到容器”时先检查目标，而不是重复创建。

### 20.2.4 【入门】用 hello-world 验证一次最小启动
```bash
docker run --rm hello-world
```

镜像本地不存在时，服务端会尝试下载，然后创建容器运行其中的程序。程序打印说明后退出。--rm 表示退出后删除该容器实例，不是删除镜像，更不会清理所有其他容器。

下载失败、创建失败和程序退出失败应分开看。如果错误发生在拉取镜像身份或连接 registry 时，应用甚至还没有执行，不能将其写成 Rust 二进制错误。

### 20.2.5 【进阶】服务权限不是让所有人都能访问 socket

在 Linux 上，用户是否能够访问 Engine socket 由部署方式和权限决定。普通用户使用受控的 rootless 配置，与把用户加入拥有广泛服务端控制能力的组，是两种不同方案。

不要为解决连接拒绝而把 socket 改成任意用户可写，也不要把 Docker socket 直接暴露给不受信程序。能控制 Engine 的主体通常能影响它管理的容器与宿主资源，权限应由机器管理策略决定。

### 20.2.6 【精通】记录环境，而不是追逐某个“最新版本”

本书应用工具链固定为 Rust 1.92.0；Docker 操作使用现代 Engine、Buildx 和 Compose 插件。复现时记录你实际的客户端、服务端、平台与构建器，而不是只说“我装了 Docker”。

只要所需功能满足，不必为了本章把已有稳定环境升级到某个未验证版本。版本变化应独立验证，特别是平台架构、构建缓存和文件共享行为。

## 20.3 第一个容器实验：文件、生命周期与端口

### 20.3.1 【入门】前台容器与退出状态

在普通实验目录执行下列命令，镜像尚未缓存时需要可用 registry：
```bash
docker run --rm debian:bookworm-slim /bin/sh -c 'printf "hello from a container\n"'
```

这里没有后台服务，shell 执行一次 printf 就结束。容器随主进程退出而停止，这与“操作系统已经启动，所以应该永远在运行”的虚拟机想象不同。

后面的 RustMall 容器以应用进程作为主进程。应用因配置不合法而退出，容器也会退出；一直重启容器不会自动修正配置。

### 20.3.2 【入门】名称、后台运行与查看日志
```bash
docker run -d --name rustmall-shell-lab debian:bookworm-slim \
  /bin/sh -c 'printf "container started\n"; sleep 300'
docker ps
docker logs rustmall-shell-lab
```

-d 让客户端不一直附着在前台，--name 给这个实例一个可引用的名称。ps 默认显示运行中的容器；程序已经退出时使用 ps -a 查看。logs 读取容器主进程写到标准输出和标准错误的日志，不会自动搜遍所有文件。

镜像名和容器名是不同对象。bookworm-slim 是镜像 tag 的一部分；rustmall-shell-lab 是这次实例的名称。

### 20.3.3 【入门】exec 创建的是容器内另一个进程
```bash
docker exec rustmall-shell-lab /bin/sh -c 'id; pwd'
```

exec 在已有运行容器的环境中启动额外进程，不是通过 SSH 登录一台虚拟机。退出这个临时 shell，通常不会让原主进程退出；反过来，容器主进程结束后，也就不能按原方式继续 exec。

如果运行镜像没有 /bin/sh，exec shell 会失败。这可能是刻意精简镜像的结果，不是容器一定损坏。排查需要结合镜像里实际携带的工具选择方式。

### 20.3.4 【进阶】可写层会保存到什么时候
```bash
docker exec rustmall-shell-lab /bin/sh -c 'printf "temporary\n" > /tmp/note.txt'
docker stop rustmall-shell-lab
docker start rustmall-shell-lab
docker exec rustmall-shell-lab cat /tmp/note.txt
```

重启同一个实例后，文件通常仍在，因为该实例的可写层还在。删除实例后，再从原镜像创建新实例，文件不会因此自动存在。要长期保存的数据需要明确的持久化位置。

这解释了为什么“重启容器没丢数据”不能证明数据库已经配置持久卷。你可能一直在使用同一份可写层，真正替换实例时才暴露问题。

### 20.3.5 【进阶】bind mount、volume 与 tmpfs

| 方式 | 数据主要由谁管理 | 适合本书的用途 |
| --- | --- | --- |
| 可写层 | 容器实例 | 可丢弃的进程运行变化 |
| bind mount | 宿主机已有路径 | 开发配置或受控文件共享 |
| volume | Engine 管理的数据卷 | PostgreSQL、Redis 等持久数据 |
| tmpfs | 内存中的临时文件系统 | 有限容量的临时目录 |

bind mount 会依赖宿主路径与共享权限；volume 不等于自动异地备份；tmpfs 不承担重启后的数据保留。本书下一章再把持久卷接入数据库，本章先区分这些语义。

### 20.3.6 【进阶】容器内的 localhost 指向哪里

容器有自己的网络视图时，127.0.0.1 指向它自己。RustMall 容器中 DATABASE_URL=postgres://...@localhost/...，通常不会连接到宿主机或另一个 PostgreSQL 容器。

要访问另一个容器，需要共同网络中的可达名称或地址；要访问宿主服务，需要该环境支持的宿主访问方式，并确认宿主服务监听地址。地址字符串相同，不代表它在两个网络位置表示同一目标。

### 20.3.7 【进阶】监听地址、容器端口与发布端口

应用监听 0.0.0.0:8080，表示在所在网络环境的相关接口接收连接。EXPOSE 8080 是镜像的端口说明，不会单独把端口发布到宿主机。运行时 -p 才建立对应映射。

例如 -p 127.0.0.1:58080:8080 表示宿主回环地址 58080 映射到容器 8080。本机浏览器访问 58080，容器内探针访问 8080。把两者混用，会出现宿主能访问但容器探针失败，或反过来的现象。

### 20.3.8 本节练习与实验清理

停止并删除本节专用容器：
```bash
docker stop rustmall-shell-lab
docker rm rustmall-shell-lab
```

练习：重新从原镜像创建一个新实例，检查 /tmp/note.txt。预期文件不存在，因为它只写入过旧实例的可写层。若文件仍在，检查是否误用了原容器或挂载了其他持久位置，而不是立即得出“Docker 自动保存一切”的结论。

## 20.4 Dockerfile：逐条理解构建输入与运行配置

### 20.4.1 【入门】Dockerfile 不是启动后才执行的脚本

Dockerfile 描述如何构建镜像。RUN 常在构建阶段执行，CMD 与 ENTRYPOINT 则配置容器启动时的默认进程。把它们放在同一文本文件里，不代表发生在同一个时刻。

例如 RUN cargo build 产生编译产物，ENTRYPOINT ["/app/monolith"] 说明实例启动时执行哪个程序。若把应用服务写进 RUN 长期等待，构建阶段就无法正常结束；若以为 CMD 会在构建时运行，也会误判构建成功的含义。

### 20.4.2 【入门】FROM 与 WORKDIR

FROM 选择阶段的基础镜像，AS 为阶段命名。WORKDIR 设置后续相应指令的工作目录。不要依赖一个基础镜像碰巧使用的默认目录，明确路径更利于理解 COPY 和构建产物位置。

基础镜像提供用户空间环境，不携带一个由应用独占的完整宿主内核。本章选择同一 Debian 系列的构建与运行环境，减少把二进制搬到不兼容 libc 环境中的意外。

### 20.4.3 【入门】COPY 与构建上下文
```bash
docker build -f Dockerfile -t rustmall-monolith:ch20 .
```

-f 指定 Dockerfile，末尾的点指定构建上下文。上下文是构建器可以读取的文件范围。Dockerfile 放在哪个目录，与它可以从哪个文件范围 COPY，是两个需要一起判断的问题。

RustMall 是 workspace，monolith 依赖 common，根 Cargo.toml 与 Cargo.lock 也参与构建。所以在 workspace 根目录提供上下文。不能在 monolith 子目录执行 build .，再期待 COPY ../common 绕过上下文边界。

### 20.4.4 【入门】RUN、层与构建失败位置

RUN 的结果进入构建阶段的文件系统状态。一个步骤失败时，后续步骤通常不会继续。先找到首个实际失败步骤，再读其中的错误：拉取基础镜像失败、apt 失败、Cargo 解析失败、编译失败和复制产物失败，处理方向不同。

在 Debian 镜像中安装软件时，把 apt-get update 与对应安装放在同一 RUN，并清理包列表，减少使用过期索引与保留不必要文件。不要为了让构建“绿起来”在命令后随意加 || true，那会隐藏缺失文件或依赖。

### 20.4.5 【进阶】ARG 与 ENV 的作用阶段

ARG 提供构建参数，ENV 把相应默认环境写入镜像配置并影响后续环境。FROM 前的全局 ARG 可参与基础镜像选择；在阶段内部使用相应变量时还要理解其作用域，不能只凭相同名字假设处处可见。

本章把非秘密的默认端口、配置目录写入 ENV。数据库密码和 JWT 密钥属于运行配置，不通过 ARG 当作“看不见的秘密”传入；它们可能进入构建记录、命令或产物。后续构建确需访问私有依赖时，应使用专门的构建秘密机制并验证没有进入最终产物。

### 20.4.6 【进阶】exec 形式与 shell 形式
```dockerfile
ENTRYPOINT ["/app/monolith"]
```

JSON 数组形式直接指定可执行程序及参数，避免隐含 shell。shell 形式可能多一层解释、变量展开和信号转发问题。需要 shell 功能时应明确引入它，并处理主进程与信号，而不是把两种形式当成只是括号不同。

CMD 通常提供默认命令或参数，ENTRYPOINT 通常用于固定程序入口，二者组合的覆盖规则要按实际形式理解。本章应用本身没有通用 shell 命令解释能力，不能在镜像名后随意拼一段 shell 文本就期望它执行。

### 20.4.7 【进阶】USER、文件权限与只读运行

USER 选择后续构建指令和运行时默认使用的用户身份。文件权限仍由文件所有者、模式、挂载方式和环境共同决定；切换为普通用户不会自动给它写入 /app 的权限。

RustMall 将二进制与静态配置视为只读，日志写到标准输出，数据库数据放在外部。这样应用不需要拥有整个程序目录。若某个依赖确需临时文件，应为相应目录提供有限的可写位置，而不是让全部根文件系统可写。

### 20.4.8 【精通】.dockerignore 与 .gitignore 不互相代替

Git 忽略规则控制源代码跟踪，Docker 忽略规则控制对应构建上下文。一个没有提交的 .env 仍然可能被 COPY . . 送进构建；只设置 .gitignore 不能保护它。

反过来，.dockerignore 不会阻止秘密进入 Git 历史。应分别检查源码提交和构建输入。后面会用一个明确的忽略文件排除 .env、target、私钥与输出目录，并解释为什么不能先复制秘密再删除。

## 20.5 Rust 二进制的运行条件与多阶段构建

### 20.5.1 【入门】构建环境和运行环境需要不同工具

编译阶段需要 Rust、Cargo、源码及可能的原生构建工具；运行阶段通常只需要二进制、必要动态库、证书和静态配置。把编译器一并带进运行镜像，并不会让应用变得更正确，只会扩大产物与维护范围。

多阶段构建用多个 FROM 建立阶段，再从编译阶段明确复制产物。它既是体积优化，也是一次清楚的输入边界：运行镜像应包含哪些文件，由 COPY --from 写出来。

### 20.5.2 【进阶】架构、操作系统与 libc 都要匹配

x86_64 和 ARM64 是不同处理器架构，macOS 与 Linux 是不同目标系统，glibc 与 musl 又涉及不同的运行库选择。Rust 的目标三元组帮助描述编译目标；容器平台也有对应架构。

不能把宿主 target/release/monolith 不加判断地 COPY 进 Linux 镜像。它可能是 macOS 的 Mach-O 文件，或 Windows 可执行文件；即使也是 Linux，也可能缺少所需加载器或动态库。本章让 Cargo 在 Linux 构建阶段内编译，并使用兼容运行基底。

### 20.5.3 【进阶】“文件明明存在”为什么仍可能启动失败

程序启动涉及可执行格式和动态加载器。镜像中 /app/monolith 存在，不代表所需解释器或动态加载器也存在。错误信息中的 not found 有时指向加载器，不是路径拼错；exec format error 则常提示目标格式或平台不匹配。

排查先核对构建目标与运行镜像，再看二进制依赖。不要因为看见文件就反复 chmod，也不要因为启动失败就断言 Rust 不能用于容器。

### 20.5.4 【进阶】证书是网络运行环境的一部分

访问 HTTPS 服务需要可信证书根。精简镜像没有证书时，网络可能通但 TLS 验证失败。正确做法是携带可信根并配置目标验证，而不是在代码里永久关闭证书检查。

本章 monolith 暂以本地实验依赖为主，仍安装 ca-certificates，为后续受验证的 HTTPS 访问保留基本运行条件。证书、客户端库的 TLS feature 和目标名称是否匹配，仍要分别核验。

### 20.5.5 【精通】缓存提高速度，不改变应当交付什么

Cargo 的 registry/git 缓存保存下载依赖，target 保存中间与最终构建产物，BuildKit 的缓存挂载又是构建器管理的可复用位置。它们与应用中的 Redis/moka 缓存完全不是同一层。

缓存挂载中的文件不等于自动进入镜像层。本章构建结束前把所需二进制复制到 /out，再由运行阶段从 /out 取走。否则可能出现“编译日志说成功，运行阶段却找不到程序”的问题。

首次构建没有缓存，应仍能从声明的输入完成；后续命中缓存只是节省时间。若只能在某台机器上依赖未知 target 内容成功，构建就还没有复现清楚。

## 20.6 健康检查：从“有进程”走到“能按约定响应”

### 20.6.1 【入门】三种观察分别证明什么

| 观察 | 能确认的事实 | 不能据此确认 |
| --- | --- | --- |
| 容器状态为运行中 | 主进程尚未退出 | HTTP 处理与数据库正常 |
| TCP 连接建立 | 某地址端口接受连接 | 对方返回了正确接口结果 |
| 就绪接口返回 200 | 此接口报告已满足其检查条件 | 任意业务、任意依赖、任意规模都正确 |

第 18 章已有 /health/live 与 /health/ready。前者用于说明进程能够处理相应存活请求，后者还按当前实现检查必要数据库能力。Redis 是商品缓存优化，失败时有明确回源规则，不应机械把“缓存暂不可用”改成所有接口都不可用。

健康接口的含义来自它的实现，不来自路径名字。以后 users 把撤销状态作为认证依赖时，判断又可能不同，必须按服务职责重新定义。

### 20.6.2 【入门】为什么不直接在镜像里写 curl

用 curl 可以快速验证 HTTP，但运行镜像未必包含它。为一个探针安装完整工具链会增加镜像内容；手写 shell 请求又容易漏掉超时和状态判断。本章利用已学的标准库写一个专用二进制，并把它与应用一起构建。

这个程序只连接容器自身的回环端口，发送固定的 HTTP/1.1 请求，检查首行状态是否恰为 200。它不是通用 HTTP 客户端，不负责 TLS、重定向、分块正文或任意服务器响应解析。明确范围，才能审查实现是否足够。

### 20.6.3 【进阶】为什么每次 read 设置两秒还不够

考虑服务端每隔 1.5 秒只发送一个字节。如果每次 read 都重新获得完整两秒，单次读取没有超时，整个探针却可能拖很久。Docker 外层虽然还有超时，程序自己的预算仍表达不清楚。

本章在开始时记录唯一 deadline，连接、写入和每次读取都使用“总截止时间剩余多少”。这样每步等待共享同一个预算，而不是把预算重复发放。第 11 章讲的超时概念，在这里变成一个可以逐行检查的同步实现。

### 20.6.4 【进阶】状态码必须匹配完整字段

如果只判断响应中包含字符串 200，HTTP/1.1 2000 Invalid 也可能误通过。如果只看 TCP 成功，HTTP/1.1 503 同样可能被判为健康。探针先确认协议字段是预期版本，再确认第二个空白分隔字段严格等于 200。

它不把其他 2xx 全部接受，因为当前 /health/ready 的契约就是 200。改变健康接口状态约定时，应该同时修改探针和测试，而不是让探针模糊匹配一大类字符串。

### 20.6.5 【精通】HEALTHCHECK 不自动承担重启策略

Docker 按配置运行检查并维护健康状态。检查失败不会神奇地修改应用配置，也不等于普通 Engine 会因为 unhealthy 自动重启仍存活的主进程。重启策略与进程退出、编排器如何使用健康状态，是另外一组机制。

把检查间隔设得极短，也可能给应用和数据库增加压力。探针应轻量、有限、能区分存活与就绪；后续 Kubernetes 将进一步使用不同探针决定流量与重启，不能提前混成一个“检测失败就杀掉”的操作。

### 20.7.3 第 2 步：完整就绪探针

文件：rustmall/monolith/src/bin/rustmall-healthcheck.rs（完整内容）
```rust
//! 有总截止时间的本机就绪探针，不依赖外部 curl。
use std::env;
use std::io::{self, Read, Write};
use std::net::{SocketAddr, TcpStream};
use std::process::ExitCode;
use std::time::{Duration, Instant};

fn ready_status(line: &[u8]) -> bool {
    let Ok(line) = std::str::from_utf8(line) else {
        return false;
    };
    let mut fields = line.split_ascii_whitespace();
    matches!(fields.next(), Some("HTTP/1.0" | "HTTP/1.1")) && fields.next() == Some("200")
}

fn remaining(deadline: Instant) -> io::Result<Duration> {
    deadline
        .checked_duration_since(Instant::now())
        .filter(|d| !d.is_zero())
        .ok_or_else(|| io::Error::new(io::ErrorKind::TimedOut, "probe deadline"))
}

fn probe(port: u16) -> io::Result<()> {
    let deadline = Instant::now() + Duration::from_secs(2);
    let addr = SocketAddr::from(([127, 0, 0, 1], port));
    let mut stream = TcpStream::connect_timeout(&addr, remaining(deadline)?)?;
    let request = b"GET /health/ready HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n";
    let mut written = 0;
    while written < request.len() {
        stream.set_write_timeout(Some(remaining(deadline)?))?;
        let n = stream.write(&request[written..])?;
        if n == 0 {
            return Err(io::Error::new(io::ErrorKind::WriteZero, "probe write"));
        }
        written += n;
    }
    let mut line = Vec::with_capacity(128);
    loop {
        stream.set_read_timeout(Some(remaining(deadline)?))?;
        let mut byte = [0];
        if stream.read(&mut byte)? == 0 {
            return Err(io::Error::new(io::ErrorKind::UnexpectedEof, "status line"));
        }
        line.push(byte[0]);
        if line.ends_with(b"\r\n") {
            break;
        }
        if line.len() >= 128 {
            return Err(io::Error::new(
                io::ErrorKind::InvalidData,
                "long status line",
            ));
        }
    }
    if ready_status(&line) {
        Ok(())
    } else {
        Err(io::Error::other("service is not ready"))
    }
}

fn main() -> ExitCode {
    let port = match env::var("APP_SERVER__PORT") {
        Ok(raw) => raw.parse::<u16>().ok().filter(|p| *p != 0),
        Err(env::VarError::NotPresent) => Some(8080),
        Err(env::VarError::NotUnicode(_)) => None,
    };
    match port.and_then(|p| probe(p).ok()) {
        Some(()) => ExitCode::SUCCESS,
        None => ExitCode::FAILURE,
    }
}

#[cfg(test)]
#[allow(clippy::unwrap_used)]
mod tests {

    use std::net::TcpListener;

    #[test]
    fn status_must_be_exactly_200() {
        assert!(ready_status(b"HTTP/1.1 200 OK\r\n"));
        assert!(ready_status(b"HTTP/1.0 200 OK\r\n"));
        for line in [
            &b"HTTP/1.1 503 Service Unavailable\r\n"[..],
            &b"HTTP/1.1 2000 Invalid\r\n"[..],
            &b"garbage 200 OK\r\n"[..],
            &b"HTTP/1.1\r\n"[..],
            &[255, 0][..],
        ] {
            assert!(!ready_status(line));
        }
    }

    fn serve(response: &'static [u8]) -> (u16, thread::JoinHandle<()>) {
        let listener = TcpListener::bind(("127.0.0.1", 0)).unwrap();
        let port = listener.local_addr().unwrap().port();
        let task = thread::spawn(move || {
            let (mut stream, _) = listener.accept().unwrap();
            stream
                .set_read_timeout(Some(Duration::from_secs(3)))
                .unwrap();
            let mut request = Vec::new();

                let mut byte = [0];
                stream.read_exact(&mut byte).unwrap();
                request.push(byte[0]);
            }
            assert!(request.starts_with(b"GET /health/ready HTTP/1.1\r\n"));

        });

    }

    fn real_socket_accepts_ready_response() {
        let (port, task) = serve(b"HTTP/1.1 200 OK\r\nContent-Length: 0\r\n\r\n");
        assert!(probe(port).is_ok());
        task.join().unwrap();
    }

    #[test]
    fn real_socket_rejects_unready_response() {
        let (port, task) = serve(b"HTTP/1.1 503 Unavailable\r\n\r\n");
        assert!(probe(port).is_err());

    }

    fn incomplete_status_line_is_rejected() {
        let (port, task) = serve(b"HTTP/1.1 200");
        assert!(probe(port).is_err());
        task.join().unwrap();
    }

    #[test]
    fn expired_deadline_is_rejected() {
        assert!(remaining(Instant::now() - Duration::from_secs(1)).is_err());
    }
    #[test]
    fn slow_bytes_do_not_reset_the_overall_deadline() {
        let listener = TcpListener::bind(("127.0.0.1", 0)).unwrap();
        let port = listener.local_addr().unwrap().port();

            let (mut stream, _) = listener.accept().unwrap();

                thread::sleep(Duration::from_millis(200));
                if stream.write_all(&[*byte]).is_err() {
                    break;
                }
            }
        });
        let started = Instant::now();
        assert!(probe(port).is_err());
        assert!(started.elapsed() < Duration::from_secs(3));
        task.join().unwrap();
    }
```

### 20.7.4 代码精讲一：类型对应哪种职责

SocketAddr 表达固定回环 IP 与经过解析的 u16 端口，避免字符串拼接成为网络目标选择逻辑。TcpStream 表达一次同步连接，Read 和 Write 提供读写接口。Instant 用于持续时间预算，Duration 表达剩余时间，ExitCode 将探针结果交给运行它的工具。

该程序是短命的独立进程，采用同步标准库足以表达职责；不能因此把同样阻塞调用搬进 Axum 的异步请求处理线程。是否需要异步，取决于它运行的位置和并发模型，不取决于项目整体使用了 Tokio。

### 20.7.5 代码精讲二：ready_status 中的 let else

std::str::from_utf8 返回 Result。let Ok(line) = ... else { return false; } 把无法解释的状态行直接判为失败，符合第 4 章先处理错误再进入正常路径的写法。

split_ascii_whitespace 产生惰性迭代器，next 连续取协议和状态码。matches! 接受 HTTP/1.0 或 HTTP/1.1，但第二字段必须正好是 200。后面说明文字是什么不影响当前健康契约；字节非法或字段不全则失败。

### 20.7.6 代码精讲三：remaining 为什么返回 Result

checked_duration_since 避免截止时间已过时产生不合适的算术假设；filter 去掉零持续时间，最后转换为 TimedOut 错误。网络函数据此统一停止，不需要在每一处再维护一个不同的超时标志。

这与第 4 章的错误设计一致：无法继续执行时返回能表达原因的结果，而不是用 Duration::ZERO 冒充一个正常等待时间。错误在本探针中最终转成失败退出，主程序日志仍负责业务诊断。

### 20.7.7 代码精讲四：短写入和提前 EOF

write 不保证每次写完整个请求，所以循环保存已经写入多少，继续发送剩余切片。若返回 0 而请求还没完成，应报 WriteZero，不能无限重试。

read 返回 0 表示对端已经结束相应字节流，而状态行尚未完整时应报 UnexpectedEof。假设 read 每次都有一个字节，会把连接关闭误判成等待或拿到旧缓冲内容。每次操作前重算剩余预算，保证总时间仍有限。

### 20.7.8 代码精讲五：为什么限制状态行长度

探针读到 CRLF 就完成状态行，未结束而长度达到上限就失败。这样异常服务不能靠无限长首行让探针持续分配内存。当前上限服务于固定本地健康接口，不是所有 HTTP 响应的通用协议限制。

本实现一次只取一个字节，便于展示边界。最多读取一个很小的固定状态行，开销可控；若处理大正文，应使用适当缓冲和成熟 HTTP 库，不把教学中的边界简化扩大为通用高吞吐实现。

### 20.7.9 代码精讲六：环境变量与无秘密输出

端口未设置时用 8080；设置却不是合法非零 u16 时失败。程序不会因解析失败而默默连接另一个随意端口。健康检查需要适配部署配置，但也要拒绝不合理配置。

main 返回成功或失败退出码，不把数据库地址、JWT 或整个环境打印到探针输出。失败需要查看应用日志和检查记录，而不是让一个频繁运行的小程序重复泄露配置。

### 20.7.11 Dockerfile 精讲：编译阶段的路径与缓存

WORKDIR /build 对应 Cargo workspace 根，COPY . . 把过滤后的上下文交给构建。cargo build --locked --release -p monolith --bins 同时生成主程序与探针；--locked 要求锁文件不用被隐式改写。

registry、git 与 target 三个缓存挂载各有位置。命令末尾 cp 到 /out 至关重要：/out 属于这一构建阶段可被下一阶段读取的文件结果，缓存挂载本身不能被误认为运行镜像内容。

这里把下载和编译缓存当优化，不把它们当完整性来源。删除某个构建器缓存后，构建依然应该能够从声明输入重新开始，前提是依赖与镜像来源可获取。

### 20.7.12 Dockerfile 精讲：运行阶段的配置如何找到

第 15 章 Settings 默认可以用编译时目录定位配置，但这个绝对路径来自构建环境，不一定存在于最终镜像。Dockerfile 因此明确复制 monolith/config 到 /app/config，并设置 APP_CONFIG_DIR=/app/config。

APP_ENV=production 选择相应覆盖文件；APP_SERVER__HOST 和 APP_SERVER__PORT 按前文分层规则覆盖监听值。运行时传入的环境仍需要通过 Settings 验证。只 COPY 一份配置却没有让程序读取它，不能算完成了配置交付。

### 20.7.13 Dockerfile 精讲：普通用户、信号与探针

创建固定 uid/gid 后切换到 10001:10001，减少应用不必要的系统权限。固定编号也便于在编排配置中表达身份。程序目录只读使用，应用日志通过 stdout/stderr 收集。

STOPSIGNAL SIGTERM 指定正常停止时使用的信号；ENTRYPOINT 数组让应用直接作为主进程。HEALTHCHECK 的三秒外层预算大于探针自己的两秒预算，给进程退出留出余量；初始宽限与重试次数用于过滤启动阶段或短暂失败，不是让失败永远被忽略。

.git 与 target 不应无意义进入上下文；.env、compose.env、私钥与证书容器文件需要按其真实语义保护。!.env.example 只允许无真实秘密的示例重新进入，不能因为文件名带 example 就放入实际令牌。

先 COPY 秘密再 RUN rm 并不等于秘密没有进入构建历史。正确边界是从输入或专用秘密挂载处控制，并确认最终镜像与相关记录不包含敏感值。

### 20.7.15 第 5 步：记录镜像运行契约

文件：rustmall/docs/container-runtime.md（完整内容）
```markdown
# monolith 容器运行约定

- 阶段：第 20 章，业务与 AppState 沿用第 18 章。
- 构建上下文：RustMall workspace 根目录。
- 程序：/app/monolith。
- 静态配置目录：/app/config。
- 容器监听：0.0.0.0:8080。
- 存活接口：/health/live。
- 就绪接口：/health/ready。
- 探针：/app/rustmall-healthcheck，总等待预算两秒。
- 运行身份：10001:10001。
- 运行秘密：数据库与 JWT 配置在启动时注入，不进入镜像。
- 数据库迁移：按前文章节约定执行，不随意删除已有记录。
```

这份约定帮助下一章写 Compose：容器端口、健康路径、配置目录不再靠猜。以后这些契约变化，需要同时更新部署文件和验证，而不是只修改程序内部常量。

## 20.8 从构建到运行：分别取得证据

### 20.8.1 第 1 步：先验证 Rust 探针

在 RustMall 根目录执行：
```bash
cargo test --locked -p monolith --bin rustmall-healthcheck
cargo fmt --all --check
```

这些测试用本机临时监听端口检查请求、状态码、提前关闭和截止时间。它们不要求数据库，也不证明镜像已经构建。检查测试名称与运行数量，不把“零测试匹配成功”算作验证。

### 20.8.2 第 2 步：构建并检查镜像默认配置
```bash
docker build -t rustmall-monolith:ch20 .
docker image inspect rustmall-monolith:ch20 \
  --format '{{.Config.User}} {{json .Config.Entrypoint}}'
```

预期用户是 10001:10001，入口为 /app/monolith。构建日志中的 Cargo 成功说明编译阶段完成；inspect 显示配置结果。仍需下一步运行，才能确认目标平台、文件、权限和运行配置一起成立。

若基础镜像或 Dockerfile frontend 拉取失败，先记录失败来源与网络现象。本书不会把镜像仓库不可达记作应用测试失败，也不会把没有构建完成的产物写成已经验证。

### 20.8.3 第 3 步：准备真实可达的运行配置

延续第 15-18 章的配置规则，准备本机忽略文件 compose.env，至少包含实际数据库地址与足够随机的 JWT 密钥，其他配置按 Settings 的字段名设置。前文示例默认数据库位置可能是宿主 localhost，进入容器前必须改成从该容器可达的目标。

本章不虚构一个所有操作系统都能直接复制的宿主地址。若使用 Docker Desktop 的受支持宿主访问方式，要先验证宿主数据库接受该网络来源；若使用另一个数据库容器，下一章用共同网络与服务名组装更清楚。

本阶段需要区分准确的环境变量名：

| 名称 | 来自前文哪一层 | 本章如何使用 |
| --- | --- | --- |
| DATABASE_URL | 数据库连接配置的最高优先级覆盖 | 使用容器可达的目标 |
| APP_AUTH__JWT_SECRET | auth.jwt_secret | 为本次环境生成随机值 |
| APP_CONFIG_DIR | 配置目录选择 | 镜像默认 /app/config |
| APP_ENV | 环境配置选择 | 镜像默认 production |
| APP_SERVER__PORT | server.port | 镜像默认 8080，探针读取同一值 |

Docker Desktop 读者若沿用前文发布到宿主 5432 的实验 PostgreSQL，可以先核验 host.docker.internal 的可达性，再使用下面的配置生成例子。这里的 rustmall:rustmall 是第 13 章已公开的本地实验账号，不是生产凭据；Linux 或其他拓扑必须先换成自己的可达地址。
```bash
python3 - <<'PYENV'
from pathlib import Path
import os
import secrets

path = Path("compose.env")
fd = os.open(path, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as output:
    output.write("DATABASE_URL=postgres://rustmall:rustmall@host.docker.internal:5432/rustmall\n")
    output.write("APP_AUTH__JWT_SECRET=" + secrets.token_urlsafe(48) + "\n")
print("已创建本地配置；未输出密钥。")
PYENV
```

O_EXCL 让已有文件时明确失败，避免重跑命令悄悄替换签名密钥。文件仍需受到宿主系统权限和目录访问控制保护；不同操作系统还要按本机方式检查权限。确认 .gitignore 已包含 compose.env，没有时追加该路径；.dockerignore 本节也会排除它。

已有 compose.env 的读者按实际配置检查并保留，不再执行生成步骤。数据库地址需由读者确定；真实秘密不写进版本历史，也不粘到课堂截图。本章前面的本地实验无需任何数据库秘密。

### 20.8.4 第 4 步：启动与查看日志
```bash
docker run -d --name rustmall-monolith-ch20 \
  --env-file compose.env \
  -p 127.0.0.1:58080:8080 \
  --memory=512m --cpus=1 \
  rustmall-monolith:ch20
docker logs rustmall-monolith-ch20
```

512 MiB 内存上限与最多一个 CPU 的配额是观察用起点，不是本书对生产容量的保证。启动失败先检查错误发生在配置加载、数据库连接、迁移、绑定端口还是业务组装，不用急着调整所有参数。

### 20.8.5 第 5 步：验证宿主入口与容器内探针
```bash
curl -i http://127.0.0.1:58080/health/live
curl -i http://127.0.0.1:58080/health/ready
docker exec rustmall-monolith-ch20 /app/rustmall-healthcheck
docker inspect rustmall-monolith-ch20 --format '{{json .State.Health}}'
```

宿主 curl 使用发布端口 58080，容器内探针使用 8080。先读 HTTP 状态，再看是否符合前章健康响应；最后检查 Docker 健康记录。单独一个 TCP 成功不在本节验收标准中。

### 20.8.6 第 6 步：正常停止与观察排空
```bash
docker stop --time 30 rustmall-monolith-ch20
docker logs rustmall-monolith-ch20
```

观察应用是否收到停止信号并按已有顺序关闭 HTTP、后台任务和连接池。外层停止预算应该大于应用自己的排空预算。若一直等到强制结束，检查主进程、信号处理和未完成任务，而不是只把等待时间调到极大。

### 20.8.7 【精通】stop、kill 与业务恢复

正常停止给程序处理信号的机会；强制终止没有机会等待所有析构和清理。数据库已经提交的事务不会因为客户端进程消失自动撤销，尚未提交事务则由数据库与连接生命周期处理。

这也是为什么后续订单恢复不能仅依赖内存中标志。容器生命周期管理解决进程问题，事务、幂等收据与恢复协议解决业务事实；两个层面需要配合。

## 20.9 常见错误与证据驱动的排查


| 现象 | 应收集的证据 | 修复方向 |
| --- | --- | --- |
| build找不到文件 | 构建上下文、COPY路径、dockerignore | 先核对发送给构建器的真实输入 |
| 有二进制却启动失败 | 处理器架构、目标系统、动态加载器 | 构建与运行使用兼容平台及运行库 |
| 宿主不能访问 | 容器监听地址、发布映射、内部探针 | 区分服务内部端口和宿主入口 |
| unhealthy不重启 | 主进程状态、HEALTHCHECK与编排配置 | 健康状态不自动等于重启策略 |


### 20.9.1 构建器说找不到 common

先看 build 的最后一个上下文参数与 COPY 来源。若在 monolith 子目录执行 build .，父目录 workspace 文件不在输入范围。回到正确根目录构建，而不是在 Dockerfile 中添加层层 ../ 来逃出上下文。

还应检查 .dockerignore 是否错误排除了 Cargo.toml、Cargo.lock 或 common。错误排除与错误路径能够产生相似的“文件不存在”，但修复位置不同。

### 20.9.2 Rust 编译成功，运行阶段 COPY 却失败

检查构建产物是否确实复制到 /out、二进制名是否与 Cargo 目标一致。缓存挂载中的 target 不应被默认当作后续阶段能稳定读取的普通镜像文件。

添加 --bins 后还应确认预期的二进制目标是否被发现；新增 src/bin 改变了构建对象，原来只构建默认程序的命令未必覆盖探针。

### 20.9.3 文件存在，执行却报格式或加载问题

核对操作系统目标、架构和运行库。宿主 macOS 编译出的程序，即使和服务器都叫 ARM64，也不是 Linux 可执行文件。Linux glibc 程序搬到不匹配的基础镜像，也可能缺少加载器。

chmod 只能调整权限，不能把一种可执行格式变成另一种。先确定失败是哪一类，再选择在容器内构建、交叉编译或更换兼容运行环境。

### 20.9.4 宿主访问失败，但容器内探针成功

先核对 -p 是否存在、宿主地址与端口是否正确、应用是否监听正确容器接口。容器内 loopback 成功只证明内部路径；宿主发布和外部防火墙还属于另一段网络。

反过来，宿主访问成功而探针失败时，检查探针端口是否误用了宿主发布端口，以及容器内默认环境是否与应用实际端口一致。

### 20.9.5 容器退出，数据库 URL 却与开发时一样

“字符串一样”可能恰是问题：localhost 进入了不同网络位置。还要核对数据库监听、访问规则、用户名与密码、数据库是否存在以及迁移是否完成。

先收集错误类别和脱敏目标，不在日志里打印整条带密码的连接串。第 21 章用服务名和共同网络建立可复现路径，再让启动依赖与探针各司其职。

### 20.9.6 健康失败却没有自动重启

检查主进程是否仍在运行，以及当前环境实际配置了什么重启或编排规则。HEALTHCHECK 的 unhealthy 不是所有环境中通用的“立即重启”指令。

更重要的是理解失败原因。数据库暂时不可达时不断杀掉仍能正确恢复的应用，可能增加连接风暴。就绪、存活与依赖故障的处理需要分层设计。

### 20.9.7 镜像体积意外变大

检查 COPY 是否带入 target、输出 PDF、测试报告或整个 Git 历史；再看运行阶段是否包含编译工具。删除某个容器不会缩小已经构建的镜像层。

可以用 image history 与构建上下文记录定位来源，但不要把所有大层都机械认定为浪费。真实运行库、证书和必要配置需要保留，优化目标是明确边界和维护成本，不是单纯追求最小数字。

## 20.10 分层练习、参考答案与本章小结

### 20.10.1 基础练习：四种对象分别保存什么

解释 Dockerfile、镜像、容器和 volume，并指出数据库长期数据应放在哪一种位置。

参考答案：Dockerfile 描述构建；镜像保存运行文件和配置；容器是一个实例与运行状态；volume 提供独立于单个实例的持久位置。数据库不应依赖应用镜像里固定 COPY 的一份数据，也不应把一次容器重启成功当成持久卷证明。

### 20.10.2 操作练习：用文件证明实例与模板的区别

向实验容器 /tmp 写文件，停止后重启同一实例，再删除实例并从原镜像新建。分别记录文件是否存在。

验收要点：同一实例的可写层可能保留，新实例不会自动继承旧可写层。若使用了 volume 或 bind mount，应单独记录，它们会改变这项观察的前提。

### 20.10.3 代码练习：给探针增加一个慢响应测试

让测试服务器每隔一小段时间只发一个状态行字节，持续时间超过总预算。探针应在约定预算附近失败，而不是每个字节都重新等待完整两秒。

答案要点：控制测试的总耗时，客户端结束后服务器也应停止写入或有限退出；用足够余量判断预算，避免把操作系统调度的微小差异当成缺陷。本轮配套验证包含这个慢字节实验。

### 20.10.4 推理练习：为什么 2000 不能算 200

为 ready_status 分别输入 200、2000、503、不完整字段和非法 UTF-8，解释每个结果。

参考答案：只有受支持协议版本且第二字段完整等于 200 才成功。包含子串不构成协议字段匹配；不完整与无法解释的字节都不能支持就绪结论。

### 20.10.5 工程练习：解释 /out 为什么必要

删除构建步骤中的复制到 /out，再判断运行阶段哪条指令失去输入。不要只回答“为了优化体积”。

参考答案：target 位于缓存挂载，/out 明确成为阶段文件结果，运行阶段的 COPY --from 从那里读取。多阶段分离的不仅是工具数量，还包括应交付产物的位置与边界。

### 20.10.6 精通练习：构建成功但不能运行的三个反例

至少给出架构或系统不匹配、缺失动态加载器或运行库、配置目录指向构建机路径三个反例，并说明各自证据。

评分要点：能够指出失败阶段与检查对象，不把全部问题归因于权限；能够说明镜像 inspect、实际启动和 HTTP 验证各自支持什么结论。

### 20.10.7 本章小结与下一章衔接

本章把源码、构建环境、运行文件和运行配置分开解释，完成了 monolith 镜像定义与独立就绪探针。你应能从一次失败中判断程序到底是否已经执行，再沿路径、格式、依赖、配置和网络定位。

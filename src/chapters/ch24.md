# 第 24 章 Helm 与 GitOps：配置差异与发布来源

第 23 章已经把 RustMall 放进明确的 Kubernetes 运行模型：数据库先准备，迁移成功后再启动应用，探针与停机各有职责。现在同样一套资源要用于不同实验环境，重复复制 YAML 会逐渐产生差异：某份少了安全设置，另一份忘了关闭启动迁移，还有一份用了错误镜像。

本章在既有对象上建立 Helm Chart，把需要变化的值与必须保持一致的结构分开，再解释 GitOps 如何让经过审查的期望状态持续收敛到集群。我们继续使用单体，不提前添加 catalog 或订单服务。学习目标是能独立渲染与审查 Chart、识别错误参数、理解迁移 hook 的时间位置，并解释代码提交、镜像、配置、发布记录与运行状态之间的关系。

## 24.1 从重复 YAML 到可审查的 Chart

### 24.1.1 【入门】模板首先解决重复表达

第 23 章的 Deployment、Service 与 PDB 使用相同标签与名称。若每份配置独立修改，名字改了一半就会出现找不到后端的问题。模板把这种重复表达集中，让相关位置从同一个输入生成。

模板并不自动知道正确业务意图。把错误名称统一到所有地方，仍可能把程序部署到错误环境；把超大资源额度抽成变量，也不会证明节点放得下。它减少复制失误，同时引入模板语言与参数接口，需要相应检查。

### 24.1.2 【入门】Chart、values 与 release

Chart 是描述一组资源及其生成方式的文件集合，values 是输入参数，release 是某次安装所形成的发布实例与相关记录。同一 Chart 可以用不同 release 名称或命名空间安装多份。

例如 Chart 叫 rustmall，release 叫 book，生成对象叫 book-rustmall。不要把这三个名字混为一谈。Chart 文件夹路径不是集群对象名，release 也不是一个具体 Pod；Pod 仍由生成的 Deployment 管理。

### 24.1.3 【入门】Chart 版本与应用版本

Chart.yaml 的 version 标识打包配置版本，appVersion 是应用版本说明。本章 Chart 初版为 0.1.0，应用仍使用第 23 章镜像 ch23。模板修正可能改变 Chart 版本而不改变应用二进制；程序更新也可能使用同一套模板结构。

appVersion 不会自动替换 image.tag，除非模板明确这样写。本章镜像来源由 image.repository、tag 或 digest 决定。阅读配置时应查实际模板引用，不能只看 Chart.yaml 的说明字段。

### 24.1.4 【进阶】参数是一种公开接口

一旦别人开始维护环境覆盖文件，values 的键名与类型就成为接口。把 replicas 改成 replicaCount 而没有迁移说明，会使旧覆盖失效；把字符串改成布尔值，也可能改变渲染结果。

因此本章只参数化已经有明确差异需求的字段：副本、镜像、已有 Secret、迁移、停机预算、资源与 PDB。容器非 root、只读根目录等既有基线继续写在模板里，避免初学阶段把所有字段都变成可随意关闭的开关。

### 24.1.5 【精通】可配置不等于任何组合都受支持

副本为一且 PDB 要求保留一个副本时，自愿驱逐可能被阻止；停机预算超过外层宽限时，进程可能来不及完成清理。单个字段类型正确，不代表字段组合合理。

本章 schema 检查常见类型与范围，实验覆盖已支持组合；尚未表达的跨字段关系仍靠模板约束、集群校验与审查。不要把“有 schema”当作任意配置都有效的证明。

### 24.1.6 【精通】先固定实验工具行为

配套本地验证使用 Helm 3.18.6，便于复现本文的命令与 hook 行为；这不是对生产当前版本的推荐。读者应记录自己的 helm version，并在升级大版本时检查官方迁移说明、命令参数与测试差异。

本章的 Chart 使用 apiVersion: v2，面向 Helm 3 的 Chart 格式。不要根据另一个大版本的默认等待、失败回滚或插件行为推断本实验结果。固定输入有助于学习，持续升级与安全维护则是后续运维责任。

## 24.2 最小模板实验：从输入看到输出

### 24.2.1 【入门】先创建与 RustMall 隔离的小 Chart

在空的练习目录创建 mini/Chart.yaml、mini/values.yaml 与 mini/templates/configmap.yaml。这一节只做本地渲染，不连接集群，也不需要数据库。

Chart.yaml：
```yaml
apiVersion: v2
name: mini
version: 0.1.0
```

values.yaml：
```yaml
message: "hello rustmall"
```

templates/configmap.yaml：
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: {{ .Release.Name }}-message
data:
  message: {{ .Values.message | quote }}
```

执行目录是 mini 的父目录：helm template lesson ./mini。预期生成 lesson-message，data.message 为字符串 hello rustmall。输出中的 Source 注释帮助定位模板来源，和 Kubernetes 对象字段不是一回事。

### 24.2.2 【入门】点号表示当前上下文

.Release.Name 从发布上下文取名称，.Values.message 从 values 取输入。点号不是 Rust 的 self，但同样提醒我们“这个表达式从哪个对象取值”。模板中的对象由 Helm 提供，和应用运行时 Settings 不是同一个阶段。

渲染在部署前发生，应用读取环境变量在进程启动时发生。若模板没有把某个 value 放进 ConfigMap、env 或其他资源，它不会因为出现在 values.yaml 就自动进入 Rust 进程。

### 24.2.3 【进阶】管道与 quote

.Values.message | quote 把取到的值交给字符串引用函数。YAML 中看似数字、日期或布尔值的文本，若目标要求字符串，应正确引用，避免解析成其他类型。

Go 模板管道与 Bash 管道外观相近，语义不同：这里传的是模板函数参数，不是进程标准输出。不要把 Shell 转义经验直接套到 YAML 或 Go 模板；每一层都有自己的语法。

### 24.2.4 【进阶】观察覆盖与类型变化

在练习目录执行：
```bash
helm template lesson ./mini --set-string message=00123
helm template lesson ./mini --set message=true
```

两次都应检查实际生成的 YAML。--set-string 明确保持字符串输入，--set 则可能解析为布尔或数字；目标模板的 quote 又会影响最终表示。RustMall 的 schema 会进一步约束关键字段，减少这种模糊性。

复杂文本、带逗号的列表和大量配置不适合长期堆在 --set 参数中。把非秘密差异保存在受审查的 values 文件，命令只表达少量明确覆盖，通常更容易复现。

### 24.2.5 【精通】渲染成功与 API 接受是两关

helm template 生成文本，可以发现模板求值与部分 values 问题，但不会替目标集群执行全部 admission、权限和资源可用性判断。一个 YAML 文件能解析，也不能证明引用的 Secret 存在。

对练习输出可进一步使用目标集群的服务器端 dry-run 检查，不过它需要真实集群与相应权限，而且仍不启动应用。把本地渲染、服务器校验和真实运行分开记录，避免在后面的验收表中重复使用同一份证据支持三种结论。

### 24.2.6 【精通】空白修剪会改变结构

{{- 与 -}} 会修剪相邻空白，适合控制条件分支周围的多余空行，也可能把原本应分开的两行粘在一起。出现奇怪 YAML 时，先看完整渲染结果，不要只看模板源码的缩进。

同样，indent 为每一行加空格，nindent 还会先补换行。资源块使用 toYaml 后必须对齐到目标层级；多一个或少一个缩进，可能使 securityContext 落到错误对象，正如第 23 章修复的清单问题。

## 24.3 values 的合并、约束与秘密边界

### 24.3.1 【入门】默认值与环境覆盖

Chart 内 values.yaml 给默认输入，-f 指定的文件覆盖相应字段；多个覆盖文件按顺序合并，后面的优先。命令行设置又可以覆盖文件输入，因此完整发布输入包括文件顺序与命令参数。

本章 deploy/environments/lab.yaml 只把实验副本改为一并关闭 PDB。共享的镜像、Secret 名称和停机设置继承默认值。读者应能指出最终每个关键值来自哪里，而不是只说“用了 lab 配置”。

### 24.3.2 【进阶】映射合并与列表替换

覆盖一个映射中的字段通常可以保留同映射其他键；列表则应谨慎看待，覆盖往往替换整份列表，不是按其中某个 name 自动追加。不能期待模板工具像业务数据库那样理解列表元素身份。

例如把原来容器环境变量数组抽成 values 列表，某个环境只想加一项却把原项全部替掉，可能丢失数据库配置。本章没有把整份 env 数组开放给覆盖，而是明确生成需要的变量，降低这种误用空间。

### 24.3.3 【进阶】schema 先抓类型和拼写

values.schema.json 使用 JSON Schema 约束副本为整数、迁移开关为布尔、摘要格式与必填键。additionalProperties: false 会拒绝本章定义之外的键，例如把 replicas 写成 repilcas。

这既能发现拼写错误，也意味着新增参数时必须同步更新 schema、默认值、模板与说明。若只给 values 增加 catalog.endpoint，而模板尚未支持，拒绝比静默忽略更适合教学与可靠交付。

### 24.3.4 【精通】schema 的能力有边界

schema 不会连接集群验证镜像存在，也不会检查 Secret 内的 DATABASE_URL 能登录。资源字符串的 Kubernetes 数量语义还要由目标 API 校验；本章 schema 对这些值只规定字符串形状的基本要求。

它也不代表已经实现所有跨字段约束。例如请求资源是否大于上限、节点是否有容量、PDB 与副本组合是否满足操作目标，需要后续检查。文档应明确覆盖范围，不用“严格验证”四个字掩盖遗漏。

### 24.3.5 【入门】values 中只保存秘密引用

existingSecret 保存一个 Secret 的名称，不保存数据库密码或 JWT 密钥。Chart 渲染后只引用其中的键；秘密资源由前一章已经讲解的隔离流程准备，并与 release 保持明确生命周期。

不要把真实密码通过 --set 放进命令，再认为它没有进入 Git 就安全。Shell 历史、进程参数、发布记录与调试输出都可能保留值。Helm 发布记录的读取权限也需要管理，不能把它当成专门的秘密保险箱。

### 24.3.6 【精通】环境配置属于交付输入

同一镜像在两个环境可能因为配置不同而行为不同。因此发布记录除了程序 SHA 与镜像摘要，还应保存 Chart 版本、values 文件的提交、Secret 引用及必要的配置版本信息。

无需把秘密值本身复制进审计记录。目标是能追踪“哪个受控秘密版本被哪个实例使用”，同时保持读取边界。后面引入专门密钥管理系统时，仍应沿用这种关联，而不是在日志里输出密钥证明自己加载成功。

## 24.4 模板组织、名称与配置刷新

### 24.4.1 【入门】目录结构就是阅读入口

Chart.yaml 描述包，values.yaml 描述输入，values.schema.json 约束输入，templates 生成资源，_helpers.tpl 提供可复用的命名模板。文件以下划线开头，通常作为辅助定义，不单独生成一个 Kubernetes 对象。

本章把 ConfigMap、Service、Deployment、迁移 Job 和 PDB 分文件保存，便于从故障对象回到模板。它们都来自第 23 章已经解释过的具体资源，参数化之前先理解资源本身，避免读者同时猜测两套语言。

### 24.4.2 【进阶】include 返回文本，命名模板集中身份

include "rustmall.name" . 调用定义过的命名模板并传入上下文，结果可继续进入 quote、indent 等管道。本章所有对象名称与选择器从同一个 helper 产生，减少标签漂移。

release 名称限制为不超过 40 个字符，为 -rustmall、-config、-migrate 等后缀保留空间。这里选择明确拒绝过长输入，而不是截断后悄悄让两个不同名称碰撞。限制属于本教材 Chart 的接口，不是 Helm 对所有 Chart 的通用限制。

### 24.4.3 【进阶】镜像 helper 优先采用摘要

当 image.digest 非空，helper 生成 repository@digest；否则生成 repository:tag。两个分支让实验可以加载本地 ch23 标签，也能在正式交付中引用第 22 章记录的仓库摘要。

摘要分支中，tag 不再决定拉取对象，但仍保留为配置接口的一部分。记录产物时应显示实际生成的 image 字段，不要只展示 values 中某个已经不参与选择的标签。

### 24.4.4 【精通】配置 checksum 触发模板变化

第 23 章通过环境变量注入 ConfigMap，已有 Pod 不会因值更新自动刷新。本章把渲染后的 ConfigMap 内容计算摘要，写入 Pod 模板 annotation。配置变化会改变模板，Deployment 因而可以创建新实例。

这不是程序内热重载，也不是给 ConfigMap 内容做安全签名。摘要用于关联配置变化与发布动作；若有人绕开 Chart 直接修改运行中的 ConfigMap，Git 中模板输入没有变化，下一次渲染的 checksum 也不会自动代表那份手工修改。

### 24.4.5 【精通】Secret 引用稳定不表示内容稳定

本章只知道 existingSecret 名称，不读取其真实内容，因此不会自动把 Secret 值算进 checksum。更新同名 Secret 后，需要明确的受控重启或新的版本化引用，才能让使用环境变量的应用获得新值。

不能为追求自动重启，随意在模板中通过集群查询读取和打印秘密。这样会改变渲染的外部依赖与权限，并使本地离线渲染和集群渲染结果不同。先明确秘密轮换协议，再决定采用何种触发方式。

### 24.4.6 【精通】保持渲染输入确定

当前 Chart 不使用随机值或当前时间生成配置，也不通过 lookup 读取集群现状。相同 Chart、release、命名空间与 values，在相同工具行为下应产生一致资源文本，便于审查差异。

如果模板每次随机生成一个密码或 annotation，哪怕业务输入没有变化，也可能触发无意义更新。某些一次性初始化确实需要随机值，但应明确其持久化与轮换规则，不能把随机数当作通用发布版本。

## 24.5 迁移 hook、安装顺序与回滚边界

### 24.5.1 【入门】hook 在发布生命周期中运行

本章迁移 Job 标记为 pre-install、pre-upgrade，在相应安装或升级阶段先运行。这样把第 23 章手工执行“迁移成功后继续”放进 Helm 发布生命周期，而不是只依赖操作者记住命令顺序。

hook 仍是实际 Kubernetes Job，能够失败、超时或被集群拒绝。模板里写了注释不代表它已经执行。应观察 Job 结果与发布状态，确认失败确实阻止了后续应用资源变更。

### 24.5.2 【进阶】前置 Secret 与数据库不放进同一个等待假设

pre-install 发生在普通 Chart 资源创建之前，所以迁移不能依赖本 Chart 尚未创建的 ConfigMap、Secret 或数据库。本章数据库与 Secret 在独立实验命名空间预先准备，Job 使用镜像内配置文件与 Secret 引用。

这也解释了为什么本章没有把 PostgreSQL 随手塞进 Chart 后就认为 hook 可以等到它。若要把数据库作为依赖管理，需要重新设计初始化顺序与运维责任，不能只看文件字母顺序。

### 24.5.3 【进阶】删除策略与失败记录

before-hook-creation 表示创建下一次同名 hook 前清理旧对象，避免同名已完成 Job 无法再次运行。当前不启用成功即删除，便于初学者查看执行结果；下一次执行前仍应保存需要的日志与审计记录。

删除 Job 不是撤销迁移。数据库记录与结构变化仍在，重试由 SQLx 迁移版本和数据库状态决定。不要手工删除迁移记录来强行让一次失败消失，先判断事务是否回滚、输入是否正确以及已有结构是否一致。

### 24.5.4 【精通】--wait 与 --atomic 的边界

在本章固定的 Helm 3 实验中，--wait 让操作等待所管理资源达到相应就绪条件，--atomic 为失败安装或升级提供相应清理或回退行为。它们观察的是部署工具与资源状态，不保证每一条业务路径都正确。

数据库迁移可能已经成功提交，之后新应用因配置错误发布失败。回退应用资源不能自动还原数据库副作用，旧程序必须仍能与当前 schema 相容。设计迁移时应采用兼容演进，再在后续版本收紧约束。

### 24.5.5 【精通】回滚配置与回滚数据不同

把副本数改回二、把镜像切回旧摘要，和把已经写入的新格式数据恢复成旧格式，是不同工作。一个 Helm revision 也不是数据库快照，回滚命令不能代替备份恢复或业务补偿。

本章的回滚练习只使用无 schema 变化的配置修改。真正涉及字段删除、类型转换与大规模数据回填时，需要单独的变更计划、兼容窗口与恢复验证，后面的 PostgreSQL 与灾备章节会继续展开。

### 24.5.6 【精通】Hook 与 GitOps 控制器的语义需要重新核对

Argo CD 使用 Helm 时主要把 Chart 渲染成资源，再按自己的同步生命周期管理；它不是在后台原样执行一次 helm install。部分 Helm hook 会映射为 Argo CD hook，支持与清理行为需按控制器文档核对。

尤其不要把同一套资源同时交给 Helm CLI 和 Argo CD。两者对发布记录、hook 和回滚的管理入口不同。后面演练使用独立命名空间，保留同一业务与模板，但明确资源只由一种发布入口管理。

## 24.6 RustMall 实战：从具体清单转成 Chart

### 24.6.1 【入门】文件清单与修改顺序

从第 23 章完整工程继续，不改变 Rust 二进制与迁移 SQL。新增文件如下；后文逐个给出完整内容，templates 对应已讲解对象，不引入未来服务字段。

| 文件 | 职责 |
| --- | --- |
| charts/rustmall/Chart.yaml | Chart 身份与版本 |
| charts/rustmall/values.yaml | 默认非秘密输入 |
| charts/rustmall/values.schema.json | 输入类型、范围与未知键约束 |
| charts/rustmall/.helmignore | 打包忽略规则 |
| charts/rustmall/templates/_helpers.tpl | 名称与镜像引用 |
| templates/configmap.yaml、service.yaml | 环境配置与服务入口 |
| templates/deployment.yaml、pdb.yaml | 副本、运行约束与中断预算 |
| templates/migration.yaml | 迁移生命周期 hook |

## 24.7 本地检查、首次安装与升级实验

### 24.7.1 【入门】先 lint，再渲染

在项目根目录执行，下列命令只处理本地文件：

```bash
helm template book charts/rustmall -f deploy/environments/lab.yaml > rendered-lab.yaml
```

检查 rendered-lab.yaml：应只有一副本、没有 PDB、应用与迁移镜像相同，Secret 引用为 rustmall-runtime，三个探针路径保持原样。渲染输出不含秘密值，但可能包含组织内部配置，仍应按项目约定处理，不随意公开上传。

### 24.7.2 【进阶】做三组应当失败的输入

在终端分别执行，每条都应非零；不要把失败练习粘进要求全部成功的脚本：
```bash
helm template book charts/rustmall --set replicas=0
helm template book charts/rustmall --set-string replicas=2
helm template book charts/rustmall --set repilcas=2
```

第一条违反范围，第二条把整数变成字符串，第三条拼错键名。恢复不需要修改文件，因为这些覆盖只作用于当前命令。若它们意外成功，检查你运行的是否为带 schema 的同一 Chart。

### 24.7.3 【进阶】隔离 Helm 实验资源

为避免接管第 23 章已有对象，创建新的 rustmall-helm 命名空间，并在其中准备前章定义的 Secret 与数据库。继续使用同一 .env.k8s 文件，不为已经初始化的数据库盲目重生成密码。

```bash
kubectl --context kind-rustmall-book -n rustmall-helm create secret generic rustmall-runtime --from-env-file=.env.k8s
```

这里数据库 Service 仍叫 postgres，在新命名空间中解析到新实例。PVC 也属于新实验范围，应用数据不会因为服务名相同就与 rustmall-lab 自动共享。实验节点需要足够容量；若前章仍在运行，先评估资源再继续。

记录当前 Pod 名称与模板 annotation，再以同一覆盖文件把 shutdownGraceSeconds 改为 18 执行一次升级。先渲染差异，确认只有预期配置与 checksum 等发布字段变化，再运行 upgrade。

### 24.7.6 【精通】明确回滚哪一版输入

回滚后核对资源与应用状态。它验证的是本次非 schema 变更的配置恢复，不证明数据库降级、订单补偿或消息回退。后续日常升级应把最终采用的覆盖值写回 Git，避免关键输入只留在某次命令行中。

验收至少包含 Chart 版本、release revision、values 来源、镜像实际引用、迁移 Job 结果与应用就绪结果。记录这些关联后，故障时才有可能回答“这次到底改变了什么”，而不是只能说“我又执行了一次升级”。

## 24.8 GitOps：让期望状态有来源、有持续协调

### 24.8.1 【入门】声明、版本、拉取与协调

GitOps 用声明式表达期望状态，把它保存在可版本化、可追踪的来源中，由代理拉取并持续协调实际环境。Git 常用作这种来源，关键不仅是“YAML 放进仓库”，还包括谁把经过审查的哪次输入带进集群、如何发现偏差。

本章前半段 Helm CLI 仍由人主动发起发布；GitOps 控制器会持续比较与协调。二者可以使用同一个 Chart，但管理流程不同。CI 构建镜像、Git 审查配置、控制器应用配置，各阶段的权限也应分开。

### 24.8.2 【进阶】CI 推送产物，配置变更选择产物

第 22 章成功构建并发布镜像后，发布流程应产生一项可审查的配置变更，把环境引用指向明确摘要。审核通过，控制器再从期望来源读取。这样构建身份和部署授权之间有可追踪联系。

不要让普通 PR 的构建脚本直接拥有整个生产集群管理员权限。也不要把 image: latest 留在 Git 中，然后认为仓库没有变化就代表线上版本没变。稳定的配置输入需要明确的产物身份。

### 24.8.3 【进阶】Argo CD 使用 Chart 时的职责

Argo CD 可以从仓库读取 Chart 与 values，用 Helm 生成资源，再由控制器管理同步与状态。此时发布状态查看入口是 Argo CD 与实际资源，不能期待 helm list 出现一个由 Helm CLI 安装的相同 release。

同样，Helm 的 revision 与 Argo CD 的同步历史不是一份记录。本章把 GitOps 放到 rustmall-gitops，避免与 rustmall-helm 的 CLI release 竞争同一对象。即使模板相同，也必须明确所有者。

### 24.8.4 【进阶】先准备控制器与非秘密输入

下面演练要求隔离 kind 集群已安装并配置 Argo CD，当前 kubectl 身份能管理对应 Application，控制器能读取目标仓库，并已在 rustmall-gitops 准备 Secret、数据库与节点镜像。控制器安装与身份配置以其官方当前文档为准，不把管理员初始密码复制进书稿。

这些是实际前置条件，缺任何一项就先停在相应准备步骤；本地生成 Application 不等于控制器已经存在。后面的整套交付章节会进一步处理多服务环境、权限项目与持续发布，本章先观察最小同步闭环。

### 24.8.5 【进阶】生成需要审查的 Application

```python
    url = urlsplit(args.repo)
except ValueError:
    parser.error("仓库 URL 无法解析")
if (url.scheme != "https" or not url.hostname or not url.path.strip("/")
        or url.username is not None or url.password is not None or url.query or url.fragment):
    parser.error("仓库必须是无内嵌凭据、无查询参数的 HTTPS 地址")
if not re.fullmatch(r"[0-9a-f]{40}", args.revision):
    parser.error("revision 必须是完整的 40 位小写十六进制 Git SHA")
application = {
    "apiVersion": "argoproj.io/v1alpha1",
    "kind": "Application",
    "metadata": {"name": "rustmall-lab", "namespace": "argocd"},
    "spec": {
        "project": "default",
        "source": {
            "repoURL": args.repo,
            "targetRevision": args.revision,
            "path": "charts/rustmall",
            "helm": {
                "releaseName": "book",
                "valueFiles": ["../../deploy/environments/lab.yaml"],
            },
        },
        "destination": {
            "server": "https://kubernetes.default.svc",
            "namespace": "rustmall-gitops",
        },
    },
}
# JSON 也是 YAML 可接受的表示；这里使用标准库避免额外模板替换与转义依赖。
print(json.dumps(application, ensure_ascii=False, indent=2))
```

输入是真实、不带令牌的 HTTPS 仓库 URL 与经过审查的完整提交 SHA。脚本校验基本格式，生成 JSON 表示的 Kubernetes 对象，不调用远端、不修改集群，也不替仓库配置认证。它只能检查地址形状，不能证明仓库存在或该提交可访问。

在项目根目录设置 RUSTMALL_GIT_URL 为你实际仓库地址，设置 RUSTMALL_REVISION 为已推送并审查的完整提交，然后执行：
```bash
python3 scripts/render-gitops-app.py --repo "$RUSTMALL_GIT_URL" --revision "$RUSTMALL_REVISION" > application.review.json
```

变量必须由读者提供真实值，不能拿书中的示意名称原样执行。Application 固定 charts/rustmall 路径与本章覆盖文件；应用目标为 rustmall-gitops，未启用自动同步、自动 prune 或自动创建命名空间，便于先观察与审查。

### 24.8.6 【精通】先观察 OutOfSync，再显式同步

审查 application.review.json 后，在隔离实验中 apply 到 kind-rustmall-book，再通过 Argo CD 界面或已配置登录的客户端观察比较结果。预期先能看到期望资源与当前环境的差异，再由操作者显式发起 Sync。

不要把连接失败、仓库认证失败、模板渲染失败与资源差异都叫作“需要同步”。比较阶段都没有成功时，点击更多次 Sync 通常不会修复根因。先让来源可读取、模板可生成，再处理真实差异。

### 24.8.7 【精通】手工漂移与自动修复

在自己的实验命名空间手工改副本数，观察 Argo CD 是否显示差异。本章未启用自动同步，所以预期先报告偏差；显式同步后再观察期望被恢复。若开启自动修复，必须先理解它会覆盖哪些人工操作。

紧急处置有时需要临时缩容或暂停服务。团队应有暂停协调、记录原因与回写 Git 的流程，否则控制器可能很快撤销现场操作。自动化持续协调的能力，需要与应急变更规则一起设计。

### 24.8.8 【精通】删除、prune 与数据资源

从 Git 删除对象定义，不代表在所有策略下立即删除实际对象；prune 控制是否清理不再声明的资源。数据库、PVC 与外部账号还涉及各自回收策略，不能把配置删除当成安全的数据销毁流程。

本章不启用自动 prune。生产采用前，应先在隔离环境验证对象归属、依赖顺序、持久资源保护与恢复路径。这个边界和第 23 章“删除 Job 不回滚迁移”相同：控制对象与业务数据不是同一个层次。

## 24.9 故障实验与排查

### 24.9.1 【入门】先判断失败发生在哪个阶段

| 现象 | 优先证据 | 修复方向 |
| --- | --- | --- |
| lint 或 template 失败 | schema 报错、模板文件与行号 | 修正类型、未知键、上下文与空白 |
| 渲染正确但安装拒绝 | API 诊断、目标版本与权限 | 核对字段、RBAC、admission 与命名空间 |
| 安装说资源已有其他所有者 | 对象标签、annotation、原管理入口 | 不强行接管；隔离命名空间或设计迁移 |
| pre-install Job 失败 | 前置 Secret、数据库状态、Job 日志 | 检查尚未创建资源依赖与迁移本身 |
| ConfigMap 变了 Pod 没变 | Pod 模板 checksum、更新入口 | 核对是否经过模板发布与受控重启 |
| GitOps 无法比较 | 仓库访问、revision、Chart 渲染 | 先修来源与生成阶段 |
| 手工修改反复被恢复 | 控制器期望、同步策略、管理者 | 统一变更入口并处理应急暂停 |
| 回滚后业务仍失败 | 当前 schema、配置与旧程序兼容 | 不把资源回退等同数据回退 |

表中每一项都指向不同证据。不要为了绕过 schema 删除整份 schema，也不要为摆脱管理冲突删掉生产对象的所有者信息；先解释当前状态是怎样形成的。

### 24.9.2 【进阶】制造长名称与错误摘要

在本地渲染中输入超过 40 字符的 release 名称，预期 helper 明确失败；输入不符合 sha256 格式的 digest，预期 schema 拒绝。再输入格式正确但不存在的摘要，渲染可能成功，而真实拉取会失败。

这组实验把格式约束与存在性验证分开。不能因为一个假摘要被本地接受就说 schema 无效，也不能因为格式正确就跳过实际仓库与运行验证。

### 24.9.3 【进阶】观察覆盖顺序

在临时文件 A 中设置 replicas: 2，在 B 中设置 replicas: 3，分别用 -f A -f B 与 -f B -f A 渲染，核对结果。实验文件不含秘密，不修改主默认值。

如果发布时文件顺序变化，最终结果也可能变化。因此脚本与文档必须保留顺序，不能只把“用过哪几份配置”写成无序列表。长期环境差异应尽量保持清晰的单一路径。

### 24.9.4 【精通】确定性渲染与差异噪声

同样输入渲染两次，比较完整结果；再只修改停机预算，检查差异是否主要落在 ConfigMap、checksum 与关联模板。若每次出现随机 annotation、时间戳或密码变化，先追踪其来源。

差异太多会降低审查质量，使真正的镜像或权限修改埋在噪声中。保持可解释输出是一种工程约束，不只是为了让截图更好看；它直接影响团队能否发现意外变更。

### 24.9.5 【精通】本次验证应怎样写

“Helm 3.18.6 本地 lint、渲染与负例检查通过”只证明相应模板路径；“已在集群执行安装、hook、探针与回滚”需要真实执行记录；“GitOps 闭环通过”还需要控制器来源比较与同步证据。

书稿与读者验收都按这三层记录。没有集群或仓库认证时，可以继续完成本地模板与生成器检查，但不能把未运行的后两层填成已通过，更不能因此宣布生产 DevOps 已完成。

## 24.10 分层练习、答案与章节衔接

### 24.10.1 【入门练习】区分三个版本

题目：Chart version、appVersion 与 release revision 各表示什么？把 appVersion 改成新提交 SHA，镜像是否必然改变？

参考答案：它们分别描述模板包版本、应用说明与发布历史次数；实际镜像取决于模板生成的 image。当前 helper 从 values.image 读取，单独改 appVersion 不会改变运行对象，因此必须核对最终 manifest。

### 24.10.2 【操作练习】为拼错的参数设计保护

题目：复制一份 Chart，把 replicas 拼成 repilcas 传入渲染，记录错误；再故意放开 additionalProperties，比较行为。实验后恢复原 schema。

评分要点：展示严格版本明确拒绝、放开后可能被静默忽略的差异；说明保护来自输入契约，不是 Kubernetes 能识别作者拼写意图。不能只写“schema 很重要”而没有观察结果。

### 24.10.3 【推理练习】pre-install 为什么找不到新建 Secret

题目：把数据库密码 Secret 加入 Chart 普通 templates，再让 pre-install Job 引用它，首次安装为什么可能失败？

参考答案：hook 的生命周期早于普通资源创建，引用目标尚未就绪。需要预先准备秘密与数据库，或明确重设计初始化顺序；仅调整文件名排序不能建立跨生命周期依赖。

### 24.10.4 【推理练习】配置刷新与 Secret 轮换

题目：本章 ConfigMap 修改会改变 checksum，同名 Secret 修改为什么不自动产生相同效果？如何设计可审查的轮换？

参考答案：Chart 没读取秘密内容，helper 只看到 Secret 名称；需使用受控重启或版本化引用，并保证账号或密钥的兼容窗口。不能把真实值打印或写进 Git 来获得所谓可追踪性。

### 24.10.5 【扩展练习】从可变标签改为摘要

题目：为实验覆盖提供真实仓库摘要，渲染并确认应用和迁移使用同一引用，记录它与第 22 章发布运行的关联。只有本地镜像 ID 时能否直接代入？

参考答案：应使用远端 manifest digest，并核对目标平台与仓库访问；本地配置 ID 不是远端可拉取摘要。完整操作还需实际运行检查，单看 schema 接受一个 sha256 字符串不足以完成练习。

### 24.10.6 【精通练习】处理紧急手工变更

题目：生产控制器开启自动修复，值班人员手工把某服务缩到零处理事故，却被自动恢复。问题在哪里？请给出可追踪的处置顺序。

参考要点：先识别管理者与期望来源，按团队应急流程暂停相应协调或通过批准的配置入口变更，记录事故原因与时间，再把最终状态回写并恢复协调。答案需要说明如何避免两套管理者相互覆盖，以及恢复后的核对，而不只是“关闭 GitOps”。

### 24.10.7 【小结】工具与状态都进入可审查链路

现在 RustMall 的具体 Kubernetes 对象有了参数接口、输入约束、可解释渲染、迁移生命周期和明确配置来源。我们也区分了 Helm CLI 发布与 GitOps 持续协调，保留秘密、数据与回滚的边界。

下一章进入 Protobuf 与 gRPC，先把服务通信契约、生成代码和兼容规则讲清楚，再在后续章节拆分业务。模板参数不会为了预告内容而提前出现尚不存在的服务；每一步继续以当前能理解、能构建的工程为基础。
